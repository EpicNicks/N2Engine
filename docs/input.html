Input

The input system polls GLFW once per frame and turns keyboard, mouse and gamepad state into named actions grouped in action maps. This page covers who owns it, how bindings combine into a value, the action phase machine and its callbacks, what is safe to change from inside a callback, mouse picking and the OnMouse* callbacks, the JSON format and the Lua surface.

Ownership and lifetime

The InputSystem is owned by the Window (std::unique_ptr), not by Application. It is created at the very end of a successful Window::InitWindow, after the GLFW window and the renderer are up, and destroyed in Window::Shutdown before the GLFW window is destroyed (so the Mouse can unregister its scroll callback on a live window).

SituationWindow::GetInputSystem()
InitWindow succeeded (including isHeadless, which only hides the window)Valid pointer
glfwInit failed, window creation failed, or the renderer failed (FailInit)nullptr
After Window::Shutdownnullptr

Game code reaches it as Application::GetInstance().GetWindow().GetInputSystem() and must handle nullptr. See Application & frame loop for subsystem health reporting.

Constructing without a window

An InputSystem can be constructed from a Window that was never initialized (its GLFW handle is null). Mouse is null-safe: with no window it registers no scroll callback, and position, position delta and buttons stay as they are (zero and up, unless a test injects a pointer state with InjectPointer Picking), while scroll accumulation still works. The input tests rely on this: InputSystemHeadlessTest builds Window _window; InputSystem _input{_window}; and drives actions through a fake binding.

Guarantee PR #39

Keyboard, mouse-button and composite (WASD) bindings never hand GLFW a null window. Created with a null GLFWwindow* (for example by an InputSystem on a Window that never opened), getValue returns released: false, or (0, 0) for a composite, without calling GLFW. So a headless InputSystem can update actions built from JSON. Before, the null pointer went straight to glfwGetKey/glfwGetMouseButton. Gamepad bindings poll by joystick id and need no window.

Tests: NullWindowBindingTest.KeyboardBindingReadsReleased, NullWindowBindingTest.MouseBindingReadsReleased, NullWindowBindingTest.CompositeBindingReadsZero, InputMapSwitchCancelTest.HeadlessSystemUpdatesKeyboardAndMouseActions.

Where input runs in the frame

Input is the first thing in each frame. Application::Run calls Window::PollEvents, which does:

  1. glfwPollEvents(): GLFW callbacks run, including the scroll callback, which only buffers the offset.
  2. InputSystem::Update(), if there is an input system:
    1. Mouse::Update(): publishes the buffered scroll and samples the cursor position and the eight mouse buttons Picking.
    2. The current action map's ActionMap::Update(): every action polls its bindings, updates its phase and fires OnStateChanged callbacks.

Only then does Run call Time::Update, process the attach queue, run fixed steps, send the pointer callbacks Picking, then Update, coroutines and LateUpdate. So input callbacks run before any component update in the same frame, and before Time::Update (a callback that reads the delta time sees the previous frame's value). PollEvents does nothing when the window is null. Application::RenderEditorFrame also calls PollEvents, so input is updated in editor frames too.

Note

Only the current map is updated. Actions in other maps are not polled and keep whatever phase and value they had when they last updated (see Disabling actions and maps).

Action maps and actions

  • An InputSystem holds named ActionMaps (unique by name) and the name of the current map.
  • An ActionMap holds named InputActions (unique by name) and a public disabled flag. Its name is const.
  • An InputAction holds an ordered list of InputBindings, a current ActionPhase, a current InputValue (initially false), a disabled flag, and an OnStateChanged event (Base::EventHandler<InputAction&>).
  • An InputBinding reads one physical control (or a key set) and returns an InputValue: a std::variant<bool, float, Vector2>.

ActionMap::operator[](name) uses unordered_map::at, so an unknown action name throws std::out_of_range in C++ (Lua's map:Get returns nil instead). RemoveInputAction returns false for an unknown name. InputAction and ActionMap can be neither copied nor moved PR #31: both are always heap-held (std::unique_ptr), and each owns a Base::LifetimeToken that expires when it is freed, which is what the Lua handles check (see Lua API).

auto &window = Application::GetInstance().GetWindow();
auto *input = window.GetInputSystem();
if (input)
{
    input->MakeActionMap("Gameplay", [&](Input::ActionMap *map)
    {
        map->MakeInputAction("Jump", [&](Input::InputAction *action)
        {
            action->AddBinding(std::make_unique<Input::KeyboardButtonBinding>(window, Input::Key::Space))
                   .AddBinding(std::make_unique<Input::GamepadButtonBinding>(window, Input::GamepadButton::South));
        });
    }).LoadActionMap("Gameplay");

    (*input->GetActionMap("Gameplay"))["Jump"].GetOnStateChanged() += [](Input::InputAction &jump)
    {
        if (jump.WasStarted()) { /* jump */ }
    };
}

Adding, replacing and switching maps

CallEffect
AddActionMap(std::unique_ptr<ActionMap>&&)Inserts or replaces the map with that name. If no map is current yet, this one becomes current.
MakeActionMap(name, fn)Creates a map, lets fn fill it, then AddActionMap. Returns the InputSystem& for chaining.

Guarantee

GetActionMap has no side effect on the active map; only LoadActionMap switches. (Before PR #22 it switched as well.)

Warning

Replacing a map by name creates new InputAction objects. Subscriptions made on the old map's actions do not carry over, and pointers to the old map or its actions become dangling once it is freed: immediately when replaced outside an input update, or when the outermost update ends when replaced from a callback. Re-fetch the map and re-subscribe after replacing it. The same holds for InputSystem::Deserialize, which replaces every map. Lua handles to the old map or its actions do not dangle: they become invalid at the same moment and raise a Lua error when used (see Lua API).

Whole-system serialization

InputSystem::Serialize writes {"actionMaps": {name: map, ...}}. InputSystem::Deserialize:

  • returns false and changes nothing if actionMaps is missing or not an object;
  • builds all new maps first, silently skipping maps without an actions object, logging a warning for actions without a bindings array and for each invalid binding (which is skipped, including one with a wrongly typed optional field); a map whose disabled is not a boolean is skipped with a warning PR #37 (see JSON format and validation);
  • then replaces all maps at once and returns true;
  • keeps the current map name if a map of that name still exists, otherwise picks _actionMaps.begin() (an arbitrary map, since the container is an unordered_map), or clears it if there are no maps.

How bindings combine into a value

Each update, InputAction::CalculateCombinedValue reads every binding and decides the action's value type from the types its bindings returned, not from their magnitudes:

  1. No bindings: false.
  2. Any binding returned a Vector2: the action is a Vector2. All Vector2 values are summed; if the sum is longer than 1 it is normalized (clamped to the unit circle). bool and float bindings on the same action are ignored, even while the 2D input is at rest.
  3. Else any binding returned a float: the action is a float: the value with the largest absolute value, sign kept (on a tie the first one wins). If that strongest axis is exactly 0 and some button binding is pressed, the value is 1.0.
  4. Else: the action is a bool: true if any binding is pressed.

Guarantee

A small stick deflection stays small (it no longer becomes a full-strength (1, 0)); several 2D bindings add up within the unit circle; axis values keep their sign; button-only actions are booleans.

The accessors convert between types:

Note

Because the type follows the bindings, don't mix a 2D binding with 1D or button bindings on one action expecting them to add; split them into separate actions. PR #22 called this out as a behaviour change from the old additive combination.

Deadzones and axis normalization

Single axes: AxisBinding::NormalizeAxis

  1. Triggers (LeftTrigger, RightTrigger): GLFW reports −1 at rest and +1 fully pulled. They are remapped to 0..1 with (raw + 1) / 2, so a released trigger reads 0. Sticks keep −1..1.
  2. Deadzone: a fixed AxisBinding::Deadzone = 0.1. Magnitudes ≤ 0.1 become exactly 0.
  3. Rescale: the rest is rescaled as min(1, (|v| − 0.1) / 0.9) with the sign restored, so the output still spans the full range.

The deadzone of an AxisBinding is not configurable. Before PR #22 a trigger at rest counted as held forever.

Sticks: GamepadStickBinding

The stick applies its own radial deadzone (default 0.15, configurable per binding as deadzone) to the 2D vector after inversion: below the deadzone the result is (0, 0); above it the direction is kept and the magnitude is rescaled to (|v| − deadzone) / (1 − deadzone), capped at 1. Sticks do not go through NormalizeAxis, so binding a trigger axis into a stick binding gets no trigger remapping.

Guarantee

A released trigger reads 0, a fully pulled one reads 1, a half-pulled one reads more than 0; stick drift within ±0.05 reads 0 and ±1 reads ±1.

Source: engine/src/input/InputBinding.cpp — AxisBinding::NormalizeAxis, GamepadStickBinding::getValue; tests: AxisBindingTest.ReleasedTriggerReadsZero, AxisBindingTest.StickAxisHasDeadzoneAndKeepsRange

Action phases and callbacks

Each action runs a small state machine on "has input" (GetBoolValue() of the combined value), once per update of its map:

Current phaseInput this updateNext phase
WaitingyesStarted
WaitingnoWaiting
StartedyesPerformed
StartednoCancelled (released after one update)
PerformedyesPerformed
PerformednoWaiting
CancelledyesStarted
CancellednoWaiting

So a key held for several frames goes Started → Performed (held) → Waiting on release. A one-frame tap goes Started → Cancelled → Waiting.

When OnStateChanged fires

InputAction::Update invokes OnStateChanged(action) at most once per update, when either:

  • the phase changed, or
  • the value changed by more than 0.001 in either component of GetVector2Value(). For a float action that is the float itself; for a Vector2 action, either axis. So analog input fires on every meaningful movement while in Performed.

Disabling an active action, disabling its map, or switching away from its map fires one extra callback (see below). Callbacks run synchronously inside InputSystem::Update; handlers query the action they are given.

Phase helpers

MethodTrue when
WasStarted()Phase is Started and the previous phase was Waiting. A restart from Cancelled (tap, then press again on the next frame) does not count.
WasPerformed()Phase is Performed (every held frame, not just the first).
WasCancelled()Phase is Cancelled.

Note

The shipped scripts react to a press with GetPhase() == ActionPhase.Started inside the callback (QuitHandler.lua), which covers both the Waiting and Cancelled entry paths. Release of a held action is the transition to Waiting, not to Cancelled.

Disabling actions and maps

InputAction::SetDisabled only stores the flag; the transition is applied on the action's next update:

  • Disabled while active (Started/Performed): the next update sets the phase to Cancelled, resets the value to false, and fires OnStateChanged once. Further updates while disabled do nothing.
  • Disabled while not active: no callback; phase and value stay as they were.
  • Re-enabled: on the next update a Cancelled phase is reset to Waiting silently, then the update proceeds normally in the same call (so a still-held key starts again with Started).

A whole map stops being polled when it is disabled (ActionMap::disabled = true) or when InputSystem::LoadActionMap switches to another map. Its active actions are cancelled the same way a single disabled action is PR #39, so subscribers always see the release:

  • Map disabled: the first ActionMap::Update that sees disabled cancels the map's active actions, then polls nothing. Later updates while disabled do nothing.
  • Map switched away from: LoadActionMap(other) cancels the previous map's active actions immediately, inside the call. Called from a callback of the map that InputSystem::Update is polling, that map's loop polls no further actions (ActionMap::StopUpdating), and the cancel runs when the loop ends. So nothing in the map that was left starts after the switch; only actions polled before it can still be active, and they are cancelled then. Loading the map that is already current cancels nothing.
  • Cancel (InputAction::CancelIfActive, also available for a whole map as ActionMap::CancelActiveActions): an action in Started/Performed goes to Cancelled, its value is reset to false, and OnStateChanged fires once. An inactive action is left alone, with no callback.
  • Back again (map re-enabled or loaded again): on the action's next update, Cancelled is reset to Waiting silently, then the update proceeds normally, so a still-held key starts again with Started (WasStarted() true), and a released one stays Waiting with no callback.

Callbacks fired by a cancel may add, replace or remove actions or maps: the cancel pass works on a snapshot, and a map replaced during it is retired until the pass ends, as during InputSystem::Update.

Guarantee PR #39

An action never stays Started/Performed in a map that is no longer polled: disabling its map or switching to another map cancels it and fires OnStateChanged exactly once. Before, it kept reporting IsActive() and its last value, with no callback, until its map was updated again.

Mouse position, buttons and scroll

InputSystem owns one Mouse. Mouse::Get() reaches it through Application::GetInstance().GetWindow().GetInputSystem() and returns nullptr when there is no input system (the window failed to open, or after shutdown).

AccessorMeaning
GetPosition()Cursor position from glfwGetCursorPos (window coordinates), sampled in Mouse::Update.
GetPositionDelta()Position change since the previous Mouse::Update. The first update measures from the position sampled in the constructor.
GetScrollDelta()Sum of all scroll offsets (x, y) that arrived since the previous Mouse::Update.
GetButton(b) PickingWhether button b is held, as sampled by the last Mouse::Update (glfwGetMouseButton). Buttons are 0..7 as in Unity: 0 left, 1 right, 2 middle; there are also MouseButton overloads. An out-of-range button reads false.
GetButtonDown(b), GetButtonUp(b) PickingTrue for exactly one Update: the one in which the button went down (held now, not in the previous Update), or was released.

Scroll timing

Scroll events arrive in GLFW callbacks during glfwPollEvents. The callback finds the mouse through the window's user pointer (which stays the Window, so the resize callback keeps working) and calls AccumulateScroll, which adds to a pending buffer. Mouse::Update, which runs right after the poll, moves the pending sum into the published delta and clears the buffer. So scroll is visible for exactly the frame after it arrives, then reads zero again.

Guarantee

Several scroll events between two updates add up; the delta is visible after the next Update and is zero after the one after it (it used to be zeroed before anyone could read it).

Without a window the mouse registers no callback and position/position delta stay zero; scroll accumulation and publication still work.

Buttons and the pointer test seam Picking

Buttons are sampled in Mouse::Update, in the same place as the cursor, so every reader in a frame sees the same state and the same edges. A press and release that both happen between two polls are not seen. Picking and Input.GetMouseButton* read this state; mouse-button bindings in action maps poll GLFW themselves and are unaffected.

InjectPointer(position, buttons) is a test seam like AccumulateScroll: the next Update takes that position and button mask (Mouse::ButtonBit(n) per button) instead of reading the device. It covers one Update; after that the device is sampled again, or, without a window, the injected state is kept. So a headless test injects a press, calls Update (GetButtonDown is true), calls Update again (held, no edge), then injects the release.

Picking and OnMouse* callbacks Picking

Clicking objects works as in Unity: a component overrides OnMouseDown (or another OnMouse* callback) and is called when the left button is pressed over its object. Application owns an Input::PointerDispatcher (Application::GetPointerDispatcher()), and Run calls its Update once per frame, after the fixed steps and before Scene::Update, which is where Unity sends these messages (see the frame loop). Nothing is sent while no scene is loaded, in RenderEditorFrame, or without a window (no Mouse).

CallbackWhen it is sent
OnMouseEnter()The pointer moved onto the object
OnMouseOver()Every frame the pointer is over the object, starting with the frame it entered
OnMouseExit()The pointer moved off the object
OnMouseDown()The left button was pressed over the object. The object captures the pointer.
OnMouseDrag()Every frame the button stays held after a Down on the object, wherever the pointer is. Not in the Down frame itself.
OnMouseUp()The button was released after a Down on the object, wherever the pointer is
OnMouseUpAsButton()The button was released over the object that got the Down (a click). Sent just before its OnMouseUp.

Each frame the dispatcher:

  1. Drops the hovered and capturing objects if they were destroyed or deactivated since the last frame. They get no OnMouseExit or OnMouseUp.
  2. Finds the target under the cursor (Mouse::GetPosition). It asks the UI hit provider first; there is none until UI exists (#42). Otherwise the world hit provider decides. The default one casts the main camera's Camera::ScreenPointToRay, with the window size as the viewport, using Raycast::Single from the near plane to the far plane with the pick mask (SetPickMask; Layers::DefaultRaycastMask to start with, so objects on the Ignore Raycast layer can't be clicked). The target is the hit collider's GameObject: for a collider on a child object, that is the child, not the body's owner. An object that is inactive or destroyed is never a target. Without a physics backend (including a build without PhysX) nothing is hit, and the dispatcher still runs.
  3. Handles the left button, in Unity's order: if it went down this frame, OnMouseDown to the target, which captures the pointer; otherwise, if it is up and something has the capture, OnMouseUpAsButton (only if the target is that object) and then OnMouseUp to it, ending the capture; otherwise, if it is held and something has the capture, OnMouseDrag to it.
  4. Handles hover: if the target is the hovered object, OnMouseOver; if it changed, OnMouseExit to the old object, then OnMouseEnter and OnMouseOver to the new one.

Delivery follows the physics event rule: each callback goes to every component of the object, a disabled component included, as long as the object is active in the hierarchy and not destroyed. The component list is snapshotted and each component's lifetime token is checked before its call, so callbacks may add, remove or destroy components and objects. Once a callback destroys or deactivates the object, its remaining components get nothing more that frame. "Destroyed" means marked for destruction, as for physics: inside a scene, Destroy() takes effect when the destroy queue runs at the end of the frame.

  • Left button only, as in Unity. The other buttons are read with Mouse::GetButton.
  • Action maps are independent. Picking reads Mouse directly, so a gameplay action bound to the left button still fires whatever the pointer is over. PointerDispatcher::IsPointerOverUI() (Lua Input.IsPointerOverUI()) lets a game ignore clicks that land on UI; it is false until UI exists.
  • Timing. Picking uses the physics scene as of the last fixed step. A fast body can be picked where it was at that step, up to one step behind what is drawn.
  • One camera. The default pick uses the main camera and the window size, in window coordinates (the cursor's space, not the framebuffer's, which differs on high-DPI displays). A host with its own viewport, or a game with another camera, installs its own world provider: SetWorldHitProvider([&](const Vector2 &p) { return PointerDispatcher::PickWorld(camera, p, viewport, mask); }). Passing nullptr restores the default.
  • Queries. GetHovered() and GetCaptured() return the current objects (or nullptr). Reset() forgets both without sending anything.

Design decision: Unity's OnMouse* callbacks, delivered like physics events

The click API is Unity's OnMouse* set as Component virtuals. It fits the existing callback model and LuaComponent forwarding, needs no scene setup, and ports directly from Unity. Hit providers sit behind the dispatcher, so UI (#42) can claim the pointer before the world, and an interface-based event system with bubbling and other buttons could be added later without breaking these callbacks. Callbacks run before Update, where Unity sends them, so a click is seen by the same frame's update code. Delivery reuses the physics rule rather than adding a new one: callbacks reach the components of active objects only (a disabled script still gets them, so its own Enter/Exit stay balanced), and an object that is destroyed or deactivated while hovered or captured is dropped silently, as physics drops its pairs. It gets OnDisable instead, which is where per-hover state belongs. The ray runs from the near plane to the far plane, so what the camera can't see can't be clicked, and it uses the default raycast mask so the Ignore Raycast layer stays unclickable.

Camera::ScreenPointToRay Picking

ScreenPointToRay(screenPosition, viewportSize, nearToFar = nullptr) returns a Math::Ray (origin, unit direction, GetPoint(d); math/Ray.hpp) that starts on the near plane and points away from the camera, as in Unity.

  • Screen positions are window coordinates, like Mouse::GetPosition: origin at the top-left, y down. The function flips y, so the window's top edge is the top of the view.
  • The viewport is passed in rather than read from the window, so a host whose viewport is not the window (the editor) can use it. A zero or negative size gives the ray through the centre of the view.
  • The near and far points are unprojected through the inverse of view × projection. That works for perspective and orthographic cameras alike: orthographic rays are parallel, with origins spread across the near plane. The projection is inverted in closed form, because the general 4×4 inverse rejects the tiny determinant of a wide orthographic projection (a pixel-sized 2D camera) as singular.
  • nearToFar, if given, receives the length of the ray from the near plane to the far plane. The default pick uses it as the raycast distance.

Modifying input from callbacks

Callbacks may subscribe, unsubscribe, add/replace/remove actions, replace maps, switch maps and reload the whole configuration while an update is running. The rules:

EventHandler dispatch

  • handler += fn returns a size_t id. A subscriber added during dispatch is first called on the next dispatch (dispatch iterates by index over the subscribers present when it started, and copies each function before calling it, so reallocation is safe).
  • handler -= id flags the subscriber as removed: it is not called again, including later in the current dispatch. Flagged entries are erased once the outermost dispatch finishes (or immediately if no dispatch is running). An unknown id is ignored.
  • A handler can unsubscribe itself (the "fire once" idiom) without skipping the next subscriber.
  • GetSubscriberCount() counts only subscribers not flagged as removed.

Guarantee

Self-unsubscribe, subscribing another handler, and removing a later handler during dispatch all behave as above.

ActionMap and InputSystem updates

  • ActionMap::Update takes a snapshot of its action pointers first, then updates each one only if it is still the action registered under its name. Actions added during the update are not updated until the next frame; actions removed or replaced earlier in the same update are skipped.
  • While a map is updating, AddInputAction (replacing a name) and RemoveInputAction move the old action to a retired list instead of freeing it, because its Update may be on the stack.
  • While InputSystem::Update runs, AddActionMap replacing an existing map, and Deserialize (all maps), retire the old maps the same way.
  • Both updates hold their "updating" flag in an RAII scope: it is cleared even if a handler throws, and only the outermost update frees the retired lists (a handler that re-enters an update does not free what the outer loop still holds).
  • LoadActionMap from a callback switches the current map; the map that is updating finishes its loop, and the new current map is first updated on the next frame. The loop of the map that was left stops polling at that point, and its active actions are cancelled once the loop ends PR #39.

Guarantee

Replacing the active map from its own action's callback, reloading all bindings with Deserialize from a callback, and actions removing each other from their callbacks are all safe; the replacement map updates normally on the next frame.

Binding validation (CreateBindingFromJson)

Returns std::expected<std::unique_ptr<InputBinding>, BindingParseError>. Checks run in this order:

InputError
type missing or not a stringMissingType
type not a known binding type name (e.g. "Keyboard")InvalidType
Required field missing (key / button / axis or either stick axis / any composite direction)MissingKey / MissingButton / MissingAxis / MissingCompositeKeys
A key, button or axis name that is not an enumerator (e.g. "Escpae"), or not a stringInvalidValue
An optional field the binding type reads is present with the wrong type: gamepadId not an integer from 0 to INT_MAX, deadzone not a number, invertX/invertY not a boolean (e.g. "deadzone": "0.2", "invertY": 1, "gamepadId": 1.5, null) PR #37InvalidOptionalField

A name is accepted only if converting it to the enum and back gives the same string. This closes the nlohmann pitfall where an unknown string silently became the enum's first value. Names are case-sensitive. A missing optional field gets the default listed above. A present one is type-checked before it is read; it used to go straight to json::value, whose nlohmann::json::type_error escaped every parser on the path, Lua's Input.CreateActionMap included PR #37. Fields a binding type does not read are ignored. A map's disabled must be a boolean when present; otherwise ActionMap::Deserialize returns InvalidDisabledType.

How BindingParseErrors and the other parse errors surface depends on the caller:

  • InputAction::Deserialize: an invalid binding is skipped with Logger::Warn naming the action and the BindingParseErrorToString reason; a missing or non-array bindings returns MissingBindings / InvalidBindingsType.
  • ActionMap::Deserialize: an invalid action is skipped with a warning; a missing or non-object actions returns MissingActions / InvalidActionsType, and a non-boolean disabled returns InvalidDisabledType; CreateActionMapFromJson (and so Input.CreateActionMap) logs these as an error and returns nullptr (nil in Lua).
  • InputSystem::Deserialize: see above; invalid bindings are skipped with a "Malformed binding" warning, and a map with a non-boolean disabled is skipped with a warning.

Guarantee

Unknown type names give InvalidType and unknown key/button/axis names give InvalidValue; every valid key, button and axis round-trips through Serialize and CreateBindingFromJson unchanged; defaults for a missing gamepadId, deadzone, invertX/invertY are as listed. No input JSON makes these parsers throw: a present optional field of the wrong type is InvalidOptionalField and is skipped like any other bad binding PR #37.

Guarantee PR #31

A map or action handle kept in a script never dangles. It is valid until its object is freed: the map replaced (Input.CreateActionMap with the same name, InputSystem::Deserialize), the action removed or replaced, or its map freed. After that, every method, property read (map.name), index (map["X"]) and assignment (map.disabled = true) raises "attempt to use a destroyed ActionMap" or "attempt to use a destroyed InputAction". A map or action replaced from inside an input callback is retired until the outermost input update ends (see ActionMap and InputSystem updates), so its handles keep working for the rest of that callback. A dead handle is not == nil; check IsValid(). Re-fetch the map after replacing it. Why handles work this way: design decision.

Mouse.Get() still returns a plain pointer: the mouse lives as long as the window's input system, which outlives every script call.

Scripts get the OnMouse* callbacks by defining methods of the same names (see Lua lifecycle callbacks), and build rays with Camera:ScreenPointToRay(x, y) and Physics.Raycast Picking.

Connected gamepads

InputSystem::GetConnectedGamepads() (static) scans GLFW joystick slots 1–16 and returns {name, gamepadId} for each present device. Devices with a gamepad mapping report the mapping name ("Nameless Gamepad" if none); joysticks without a mapping are listed with an "Unrecognized Gamepad Mapping" prefix. Gamepad bindings only read devices with a mapping, because they use glfwGetGamepadState. The gamepadId in bindings is the GLFW joystick id (0 is the first slot).
