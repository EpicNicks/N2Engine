Soft bodies

The SoftBody component makes the MeshRenderer on its object squash and wobble under gravity. The engine tetrahedralises the mesh's surface into a voxel body when play starts, a simulation backend moves it (the engine's CPU backend, on every machine, headless hosts included, or the PhysX GPU backend on an NVIDIA GPU) and the component feeds the deformed vertices back to the renderer through a runtime-only mesh override. This page covers the component, how a body is built from a mesh, the CPU solver and its limits, backend selection, play mode, drawing and the Lua API PR #143; the PhysX GPU backend has its own section PR #146.

Quick start

Put a SoftBody next to a MeshRenderer and play the scene. The mesh should be a closed surface (a sphere, a cube, a character's body); a flat quad has no volume and the component says so and does nothing.

local blob = GameObject.Create("Blob")
local mr = blob:AddComponent("MeshRenderer")
mr:SetMesh("Sphere")                    -- or the path of a model's mesh
local sb = blob:AddComponent("SoftBody")
sb:SetResolution(10)                    -- voxels along the longest axis
sb:SetStiffness(30000)                  -- Young's modulus in pascals: a soft gel
sb:SetGround(true, 0)                   -- rest on the plane y = 0
blob:GetPositionable():SetPosition(Vector3(0, 3, 0))
SceneManager.GetCurrentScene():AddRootGameObject(blob)

-- later
sb:AddVelocity(Vector3(2, 4, 0))        -- a push
sb:Reset()                              -- back to the rest shape at the current pose

The SoftBody component PR #143

Physics::SoftBody (engine/include/engine/physics/SoftBody.hpp) is an ordinary component, not an IRenderable: it draws nothing itself. All of its settings are public fields that the scene file saves and the editor's inspector shows (no editor protocol change: the fields come from GetComponentTypes like any other, and backend is an enum field). The deformation is runtime state and is never saved.

Requirements

  • A MeshRenderer with a mesh on the same GameObject. Without one (or with an empty mesh slot) the SoftBody is inert and logs one warning when it starts.
  • No Rigidbody on the same GameObject. A rigid body moves the object while the soft body deforms its mesh, so the combination is refused: inert, one warning.
  • A mesh the tetrahedraliser accepts: at least one real triangle and some thickness (Making a tetrahedral body). Otherwise inert, one warning that says why.

Backends and the seam PR #143

A body is simulated by an ISoftBodyBackend (the seam PR #138). The component only ever talks to the interface. PR #143 adds to it AddVelocity(handle, v) and the data a backend needs in SoftBodyDesc: the shared tetrahedral mesh with the render-vertex embedding, the mesh-to-world transform (a 3×4 matrix) and the parameters (now including gravity and the ground plane).

This is exactly the particles' selection (SoftBodies::SelectSoftBodyBackend). The choice is made once, when the component attaches; changing backend afterwards takes effect the next time the body starts (Reset() starts it again). With physics.gpu off (the default) the physics backend has none, so every body runs on the CPU; the logic of the PhysX backend is tested in CI against a fake driver. The same generation rules as particles apply: a body on a GPU backend that is replaced or recreated (its handle's generation no longer matches, handles carry the generation of their backend) restarts at rest on the CPU backend with one warning, and with the physics backend removed entirely it is inert, not a crash. A GPU backend that refuses to create a body makes the body start on the CPU with one warning, and one that gives up later restarts its bodies on the CPU with one warning each (Failure and fallback).

Making a tetrahedral body PR #143

SoftBodies::Tetrahedralise (engine/include/engine/softbody/Tetrahedraliser.hpp) turns the MeshRenderer's mesh into a TetMeshData: node positions, tetrahedra (four node indices each) and an embedding of every render vertex. It is pure engine code with no PhysX, compiled and tested in every build.

  1. Weld. Imported meshes split vertices at UV and normal seams (a cube has 24 vertices, a UV sphere has a duplicated seam column and one vertex per pole per column). Vertices within 1e-5 of the bounding box's diagonal are one position, and triangles that collapse are dropped. Fewer than one real triangle is an error.
  2. Voxelise. A grid of cubic voxels, resolution along the longest axis of the bounding box and centred on it. A voxel is inside when at least two of three ray-parity tests agree: from the voxel's centre a ray along +x, +y and +z each crosses the surface an odd number of times. The majority vote is the tolerance to holes: a crack or a missing triangle that fools one direction is outvoted. The rays are shifted by a small fraction of a voxel so they never run along an edge shared by two triangles. A voxel that holds a welded vertex is inside too, so every vertex lies in some tetrahedron (a thin fin still gets voxels). The mesh needs thickness: an extent under 1e-5 of the longest is "flat" and an error.
  3. Tetrahedra. 5 per inside voxel (a central tetrahedron and four at the corners). The split alternates with the parity of the voxel's (i + j + k) so that the diagonals on a shared face agree and the mesh conforms; every tetrahedron is ordered to have a positive volume.
  4. Embed. Every original (unwelded) render vertex gets a tetrahedron and four barycentric weights that sum to 1 and reproduce its rest position exactly. The embedding is computed once per welded position and copied to the duplicates, so seam duplicates move together and never tear apart.

The body is a voxel approximation: its outline is blocky, and a render vertex rides on the tetrahedron it sits in, so it follows the body's motion but a coarse body deforms a detailed mesh coarsely. Raise resolution for a finer body.

Caps

resolution is clamped to 2 to 32, and a body may have at most Physics::kMaxTetsPerBody (20000) tetrahedra: the tetrahedraliser lowers the resolution until it fits (a 32-voxel unit box would be 163840 tetrahedra and becomes 15 voxels), and the component logs one warning. The CPU backend refuses a body above the cap. 20000 tetrahedra is already more than a single thread solves at 60 Hz; a few thousand is the practical size.

The in-memory cache

Tetrahedralising a large mesh is the slow part of starting a body, so results are kept: SoftBodies::TetCache is keyed by the Mesh object, its Mesh::GetVersion() and the requested resolution, so a second body on the same mesh and entering play again are cache hits, while Mesh::SetData or another resolution misses. Resolutions of one mesh version coexist; building a new version of a mesh drops that mesh's entries for older versions only. It holds meshes weakly (an entry whose mesh is gone never matches) and keeps at most 32 entries. It deliberately does not use Mesh::SetCpuCache: that slot holds one object per mesh (the picking BVH), and a second type would evict it. Tetrahedra are generated at attach, which is play start; a large mesh can stall entering play until its body is built (not measured: Not verified).

The CPU solver and its limits PR #143

Physics::CpuSoftBodyBackend is position-based dynamics in its extended form (XPBD) on the body's tetrahedra. Constraints: one distance constraint per unique edge (resists shear and stretch) and one volume constraint per tetrahedron (resists compression). XPBD gives each constraint a compliance (the inverse of a stiffness), which is what makes the result independent of the time step and iteration count, unlike plain PBD. The compliances come from stiffness (Young's modulus E, Pa) and poisson (ν), the way a linear elastic solid would:

QuantityFormulaUnits
Shear modulus GE / (2 (1 + ν))Pa
Bulk modulus KE / (3 (1 − 2ν)) (ν is clamped to at most 0.49)Pa
Edge complianceα = 1 / (G · L0), with the edge's rest length L0m/N
Volume complianceα = V0 / K, with the tetrahedron's rest volume V0m&sup5;/N
Solver complianceα̃ = α / h² for the sub-step h

The mapping is a heuristic, not an FEM discretisation: a larger stiffness gives a stiffer body and a larger poisson a more incompressible one, but the numbers are not PhysX's, so the same field values do not look the same on the CPU and on the future GPU backend.

  • Time stepping. Each fixed step (Step(dt), once per OnFixedUpdate) runs 4 fixed sub-steps of dt / 4. A sub-step integrates gravity and the velocity decay (v /= 1 + damping · h), moves the nodes, runs solverIterations Gauss-Seidel iterations (all edges, then all tetrahedra, in index order, each with its accumulated Lagrange multiplier), keeps every node above the ground plane and derives the velocities from the motion. A body is the same at any frame rate; a different fixed step is a different simulation.
  • Mass. A node's mass is a quarter of the density times the volume of every tetrahedron around it, so scaling the object's transform changes the mass.
  • Ground. With collideWithGround a node below the plane y = groundHeight is put on it (inelastic: it does not bounce) and its tangential motion that sub-step is reduced by friction times the penetration depth (Coulomb friction in PBD). A render vertex is embedded in the tetrahedra, so it never goes below the plane either.
  • Determinism. Plain float code in a fixed order, a single thread, no hash-ordered iteration and no dependence on time or addresses: the same bodies stepped with the same dt and calls give bitwise-equal positions within one build (not across compilers or architectures).
  • Safety. Non-finite parameters are replaced by defaults, a bad dt is ignored, and a body whose positions turn non-finite restarts from its rest shape instead of reaching the renderer. Handles are generation-counted.

Limits

  • Ground plane only. No collision with colliders or other bodies, and no self collision (a body can fold through itself).
  • No two-way coupling. A soft body does not push Rigidbodys and they do not push it; the CPU backend never queries the physics world.
  • Single threaded, and slow at size: a few thousand tetrahedra per body is what one thread solves at 60 Hz; the cap is 20000, above that nothing is accepted. A scene's cost is the sum of its bodies'.
  • CPU and PhysX differ. A different solver and different parameter meanings: an Auto project can look different on a GPU machine with physics.gpu on once the PhysX backend exists. backend = CPU is the same everywhere.
  • No pinning or attachments, and no tetrahedral mesh import (no pinning in v1).

The PhysX GPU backend PR #146

PhysX 5.6.1 simulates soft bodies only as deformable volumes (FEM), which exist only on the GPU: PxPhysics::createDeformableVolume needs a CUDA context manager and a scene with GPU dynamics and the GPU broad phase, the same scene as the PBD particles. So the backend exists only with physics.gpu auto or on, a Ready probe and a Windows build with the PhysX GPU library; with physics.gpu off (the default) the scene is built by exactly the code it always was, and GetSoftBodyBackend() is nullptr. It is the same single PhysXGpu_64.dll as particles (not verified: Not verified); nothing new ships.

The mesh and the skinning

The driver cooks the engine's own tetrahedra (SoftBodies::Tetrahedralise, already cached per mesh version and resolution) as both the collision and the simulation mesh of the volume, with PxCookingParams::buildGPUData = true (the way PxDeformableVolumeExt::createDeformableVolumeMeshNoVoxels uses one mesh for both). That keeps the render-vertex embedding valid, so the host skins the render vertices from the volume's node positions with the same code the CPU backend uses (SoftBodies::SkinSurface, engine/include/engine/softbody/TetSkinning.hpp) and the CPU and PhysX bodies are the same mesh with a different solver. After every scene step the backend copies each volume's collision positions back from the device (memcpyDtoH of getPositionInvMassBufferD under a scoped CUDA lock, as SnippetDeformableVolume does), writes the nodes into the engine's node order and skins from that cache: CopySurfacePositions makes no GPU call and allocates nothing once the output vector has grown.

  • Node order. Cooking sorts tetrahedra, and may in principle reorder vertices. The cooking step compares the cooked vertices with its input and, if they differ, builds a node map by exact position; the driver reports it with GetNodeMap and the backend reads each node through it. The cooking tests check the map for a box, a sphere and a seamed cube under every transform below.
  • Transforms. The mesh is cooked in world space under the body's transform (the rest shape at its pose), so there is no PxDeformableVolumeExt::transform (which takes a rigid transform and a uniform scale): non-uniform and mirrored scales work as on the CPU backend. A mirrored transform (negative determinant) turns every tetrahedron inside out, so SoftBodies::OrientTets swaps two corners of each affected tetrahedron before cooking and the skinning swaps the matching embedding weights. Tests cover (-1,1,1), (1,-1,1), (-1,-1,-1), a mirrored non-uniform scale and a non-uniform one that is not mirrored.
  • Mass. PxDeformableVolumeExt::updateMass from the density with a maximum inverse-mass ratio of 50 (the snippet's value); the density is read when the body is created.

What the GPU body does differently

  • It collides with the scene's colliders, not the ground plane. collideWithGround and groundHeight are ignored (CPU only); a floor is a static collider (BoxCollider and so on). Gravity is the scene's.
  • The material model and self collision are PhysX's. materialModel picks eCO_ROTATIONAL or eNEO_HOOKEAN and selfCollision clears eDISABLE_SELF_COLLISION. Stiffness is Young's modulus, poisson Poisson's ratio, friction the material's dynamic friction and damping the body's linear damping; the material's elasticity damping stays 0. The solver runs 4 times solverIterations position iterations.
  • It will not match the CPU body. FEM against XPBD on the same tetrahedra, different parameter meanings and an untuned mapping: an Auto project looks different on a GPU machine with physics.gpu on. Pick backend = CPU for the same body everywhere.
  • The whole scene is a GPU scene. As for particles, enabling it moves every rigid body to the GPU pipeline (different performance and contact behaviour, more video memory): a project-wide decision.
  • Pushes. AddVelocity is a read-modify-write: the simulation velocities are copied back, the push is added to every node that has mass, and they are uploaded with markDirty(eSIM_VELOCITY) (positions are not touched). It is only ever done outside a scene step.

Limits

  • 4095 deformable volumes per scene (PhysX's PX_MAX_NB_DEFORMABLE_VOLUME): the driver refuses the 4096th, which counts as a failure of the feature (below). A destroyed body frees its room. The engine's own cap of kMaxTetsPerBody (20000) is far below PhysX's 1,048,575 tetrahedra per volume; a body above it is refused without failing the feature.
  • Video memory. A volume holds device copies of its collision and simulation meshes, rest positions, velocities and the GPU cooking data, plus pinned host mirrors (four PxVec4 arrays of vertices). There is no budget or measurement yet: not verified, and the particles' arrays and the whole GPU scene come on top.
  • No pinning, no attachments, no kinematic targets (no pinning in v1). No tetrahedral mesh import.
  • Hardware as for particles: NVIDIA compute capability 7.0 or newer and a recent driver; Windows only until the Linux GPU asset exists (the soft-body backend follows when N2ENGINE_PHYSX_GPU_PROBE turns on there).

Failure and fallback

The GPU is allowed to say no, and nothing else changes when it does. A body the driver refuses (the volume limit, cooking rejecting the mesh, out of GPU memory, a missing GPU library) or a transfer that fails makes the backend remember why, log one warning and do nothing more with the GPU (HasFailed). PhysXBackend then calls FailSoftBodies: it releases the volumes, sets the soft-body failure (Failed with physics.gpu=on, Unavailable with auto), logs one more warning and stops offering the backend, so GetSoftBodyBackend() is nullptr again. It never touches the scene status, Physics.IsGpuAvailable(), the particle backend or the Particles row (tested both ways round); GPU features. The SoftBodies that used it restart at rest on the CPU backend with one warning each, and a body that asked for PhysX when the backend refuses it starts on the CPU with the component's warning. GetSoftBodiesGpuStatus() now passes hasBackend = _softBodies != nullptr, so the SoftBodies row is Running PhysX GPU: <device> only while the backend exists. Builds without the GPU library (Linux CPU-only libraries, Windows with PhysX off) never compile the real driver: GetSoftBodyBackend() stays nullptr, Auto goes to the CPU quietly and PhysX goes to the CPU with one warning, as selection defines.

Generation-counted handles apply as everywhere (the design decision): a handle of a replaced or recreated backend, even at the same address, is ignored, and a body whose backend changed restarts on the CPU with one warning. Indexes are never reused, so a stale handle of a destroyed body names nothing.

Play mode, pause and saving PR #143

The same rules as particles:

  • The body exists only while the scene is playing. A scene opened for editing never attaches its components, so nothing is simulated and the editor shows the undeformed mesh; MeshRenderer's saved mesh is never changed.
  • The body is built when the component attaches (play starts) and OnFixedUpdate steps it once per fixed step.
  • The deformation is never saved: SoftBody saves only its fields and the MeshRenderer saves exactly what it saved before.
  • Leaving play mode destroys the body with the snapshot scene; OnDestroy releases the backend's body and clears the mesh override.
  • Pausing (time scale 0) freezes it: no fixed step runs, the picture stays, frames still draw.
  • The simulation is in world space: moving the GameObject in play does not drag the body. Each update converts the body's vertices into the object's local space with its current inverse transform, so the body stays where the simulation put it. Reset() restarts the body at the object's current pose.

Drawing PR #143

A SoftBody draws nothing itself. It owns a runtime copy of the mesh (same vertex count, indices and submeshes) and hands it to the sibling MeshRenderer through MeshRenderer::SetDeformedMesh, a runtime-only override: while it is set the renderer draws, bounds and queues the copy instead of its mesh. After each step the body writes the embedded positions (skinned from the tetrahedra, then converted to local space) and area-weighted normals recomputed from the triangles into the copy and calls Mesh::SetData, which bumps the version so GpuCache re-uploads the GPU mesh in place (IRenderer::UpdateMesh). There are no renderer changes: the OpenGL and software renderers draw it like any mesh, and the Vulkan renderer draws nothing for meshes (as for every mesh until the Vulkan stage that adds them).

  • The override is never serialized. It is not a registered field, MeshRenderer saves the same "_mesh" and "_materials" as ever, and GetMesh() (which scripts read) still returns the saved mesh. It is cleared when the SoftBody is destroyed or removed and when the MeshRenderer is destroyed. Picking follows what is drawn. While the override is set, the world bounds and the exact ray test both use the deformed mesh (a plain triangle loop, as its geometry changes every step and no BVH is cached for it; a copy over 100000 triangles is picked by its box), so a moved soft body is picked where it is seen.
  • Tangents stay the rest ones, so a normal map is slightly off under large deformation; texture coordinates, vertex colours, submeshes and materials are unchanged.
  • Each step costs a copy of the vertices, the normal pass, the mesh's validation and bounds, and a 64-byte-per-vertex upload: a 10000-vertex mesh uploads 640 KB per frame. Drive a decimated mesh for large models.
  • Replacing the MeshRenderer's mesh while the body runs does not change what the body drives; Reset() rebuilds from the new mesh.

The SoftBodies health row PR #143

The row's state comes from GetSoftBodiesGpuStatus() (the SoftBodies row): Disabled with the reason in CI and wherever physics.gpu is off, Running PhysX GPU: <device> only while the PhysX soft-body backend exists PR #146, Failed only with physics.gpu=on and a soft-body failure. Its detail now also names the backends the live SoftBody components use, like the Particles row: SoftBodies: 1 CPU or SoftBodies: 2 CPU, 1 PhysX, appended after the status's own detail with "; ". With no bodies the row is exactly what Application::Init made, and the usage is also shown with no physics backend at all (every body then runs on the CPU). The editor needs nothing: SubsystemStatus is generic.

Design decisions

Design decision: a real CPU backend with the engine's own tetrahedraliser PR #143

Decided by the user on 2026-10-14. PhysX 5.6.1 soft bodies are GPU-only, and physics.gpu is off by default, so without a CPU path most projects would see nothing. The CPU simulation implements the same ISoftBodyBackend the PhysX one will, and the tetrahedraliser is engine code rather than PxTetMaker, so a soft body works in a build with PhysX off, on Linux and arm64, and in CI. The PhysX backend (PR #146) cooks these same tetrahedra rather than PhysX's own conforming mesh (below), so the meshes match and only the solver differs.

Design decision: tetrahedra from the surface at play start, cached in memory PR #143

Decided by the user on 2026-10-14: tetrahedra are generated from the mesh surface when play starts, with an in-memory cache, not at import into .meta or a sidecar and not authored. The cost is a possible stall entering play for a large mesh; if it matters, import-time caching or tetrahedral mesh import is a later stage. The cache is the soft-body code's own, never Mesh::SetCpuCache.

Design decision: backend = Auto, physics.gpu stays off PR #143

Decided by the user on 2026-10-14, consistent with particles: Auto is the default and means the CPU unless the project turns GPU physics on and the GPU works, and physics.gpu stays off by default. With it off every body runs on the CPU either way.

Design decision: the body drives a sibling MeshRenderer through a runtime-only override PR #143

Decided by the user on 2026-10-14, instead of a second renderable with its own mesh and material fields. A SoftBody that drew by itself would need all of MeshRenderer's material, submesh, lighting and shadow handling again. With the override the renderer is unchanged: materials, submeshes, lights and shadows all work, and an object is a soft body by adding a component. The override is never serialized, so the scene file and the editor never see the deformed mesh.

Design decision: no pinning in v1 PR #143

Decided by the user on 2026-10-14: version 1 bodies only fall and squash, with no pinned vertices, attachments to a Rigidbody or collision with colliders. Those are later stages, so the fields have no pin settings.

Design decision: the PhysX body is cooked from the engine's own tetrahedra, in world space PR #146

The plan preferred this over PhysX's own pipeline (createDeformableVolumeMesh: a conforming collision mesh plus a voxel simulation mesh, or PxTetMaker), and it was implemented that way: the same tetrahedra as collision and simulation mesh. The render embedding, computed once for both backends, stays valid and the picture is skinned by shared code, so there is one mesh and one test for it and no second embedding (PxTetrahedronMeshExt::createPointsToTetrahedronMap) to keep in step. The mesh is cooked after the body's transform is applied, not before and transformed on the device: PxDeformableVolumeExt::transform takes a rigid transform and a uniform scale only. The price is a cook per body (CPU, at play start) instead of one per mesh, and the fallback to PhysX's own mesh (which would need re-embedding and make the two bodies differ) is not built. If a GPU scene rejects the cooked mesh at CreateVolume the body falls back to the CPU as for any refusal; whether it does is not verified.

Design decision: a refused body fails the soft-body feature, with the CPU as the answer PR #146

As for particles, a body or transfer the GPU refuses switches the PhysX soft-body backend off (one warning, the SoftBodies row Unavailable or Failed, only that row) and its bodies restart on the CPU, instead of retrying the GPU body by body. The 4095-volume limit is such a refusal. A body the CPU would also refuse (no mesh, over 20000 tetrahedra, a non-finite transform) is refused without marking the feature failed.

Design decision: ray parity with a majority vote, plus the voxels that hold a vertex PR #143

The plan left the inside test to the implementation (ray parity or generalised winding number). Parity along three axes with a two-of-three vote was chosen: it costs one pass over the triangles per axis (the rays are binned by voxel column), where a winding number is a sum over every triangle for every voxel, and it tolerates a small hole. It does not handle a mesh that is badly open or self-intersecting everywhere, and it adds the voxels that hold a vertex so that every vertex is embedded inside a tetrahedron even for thin parts.

Tests and what is not verified

All of this runs in engine_tests on every CI leg, including the PhysX-off ones, except what the next sentences name: see Testing & CI for the files. PR #146 The PhysX backend's logic runs on every leg against a fake driver; the cooking tests (DeformableCookingTest.*) and the PhysXBackend wiring tests (PhysXSoftBodiesBackendTest.*) run on every PhysX ON leg (not the Windows PhysX-off one); PhysXGpuSoftBodiesGoldenTest.* is registered and skipped in CI.

A runnable example is the GPU smoke demo's soft-body station PR #145 (demo station 11, key -): cubes of three stiffnesses, two dampings and a robot body dropped on a floor, with the backend each one asked for and the backend running on its sign (Testing & CI). Not verified in CI

The visual quality and the parameter tuning of the CPU solver on real imported meshes (seamed, non-manifold, thousands of vertices): the tests use boxes, a UV sphere and the built-in cube. Performance with large meshes: the stall while the tetrahedra are built at play start, and the per-step SetData and upload cost. How the editor's frontend shows the component and the health row (the frontend is not built or tested here).

The PhysX backend's GPU half PR #146 is only compiled in CI, never run. From the PhysX 5.6.1 headers and snippets, not confirmed by a run: that a volume made from the cooked mesh (the same tetrahedra as collision and simulation mesh, buildGPUData) is accepted by a GPU scene, and that cooking did not reorder vertices in a way the node map misses on real meshes; that PxScene::fetchResults(true) alone makes the device buffers safe to read (the snippet suggests so; the particles' separate fetchResultsParticleSystem is documented for particles only); read-back timing and its cost per body per step; video memory per body and in total; performance with N bodies and with particles in the same scene; that the same PhysXGpu_64.dll serves particles and deformable volumes; PGS solver quality (the engine sets no solver type, the snippets use TGS for deformables); how CoRotational and NeoHookean behave on real seamed or non-manifold meshes and how the parameter mapping (stiffness to Young's modulus, damping to linear damping, 4 times the iterations) looks next to the CPU body; the release order of actor, shape, material, mesh and pinned memory; whether a soft body pushes a Rigidbody; and what happens with PhysXGpu_64.dll missing. The GPU test and the checklist are what check them, on a PC with a GPU.
