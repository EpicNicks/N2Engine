GameObjects & components

A GameObject is a named container of components, children and an optional Positionable. This page covers when component callbacks run, how active state propagates, how deferred destruction and the single teardown sequence work, hierarchy edits, component lookup and removal, and what is safe to do from inside a callback.

Callbacks in the frame

Application::Run drives the loaded scene in this order every frame. Component callbacks are only ever called from these points (plus collision callbacks, dispatched by the physics backend inside the fixed step, and the immediate callbacks described below for SetActive, RemoveComponent and scene switches).

  1. Scene::ProcessAttachQueue: OnAttach for every queued component.
  2. Zero or more fixed steps: OnFixedUpdate, physics simulation, transform sync-back, then collision/trigger callbacks. See Physics.
  3. The pointer dispatcher: OnMouse* callbacks on the object under the cursor. See Picking Picking.
  4. Scene::Update: OnUpdate.
  5. Scene::AdvanceCoroutines: see Coroutines.
  6. Scene::LateUpdate: OnLateUpdate.
  7. Audio update, then render.
  8. Scene::ProcessDestroyed: OnDisable/OnDestroy for objects destroyed this frame, then they are released.
  9. SceneManager::ProcessAnyPendingSceneChange: a scene switch tears the old scene down (see Scenes).

When the run ends (window closed or Application::Quit()), OnApplicationQuit is called on the active components of the loaded scene. The full loop is described in Application & frame loop.

Creating objects

Create objects with GameObject::Create(name), which returns a std::shared_ptr<GameObject> (GameObject::Ptr). The default name is "GameObject". A new object is active, has no parent, no scene, no components and no Positionable. Call CreatePositionable() if it needs a transform (it is a no-op if one exists). See Transforms.

Objects must be owned by a shared_ptr: AddChild, SetParent, GetRoot, IsParentOf, GetHierarchyPath and Destroy (in a scene) use shared_from_this(). The public constructors exist, but a stack-allocated object cannot be used with those calls.

An object joins a scene by being added as a root (Scene::AddRootGameObject) or as a child of an object that is in a scene. Ownership: the scene's root list and each parent's child list hold shared_ptrs; a child holds only a weak_ptr to its parent.

#include "engine/GameObjectScene.hpp"

auto player = N2Engine::GameObject::Create("Player");
player->CreatePositionable();
auto *health = player->AddComponent<Health>();   // queued; OnAttach runs once the object is in a scene
scene.AddRootGameObject(player);                    // queues the components on this scene

A GameObject is not copyable (it owns unique_ptr members), and Component's copy operations are deleted PR #29.

Source: engine/include/engine/GameObject.hpp; engine/src/gameobject/GameObject.cpp — GameObject::Create, GameObject::CreatePositionable

AddComponent and the attach queue

AddComponent<T>() constructs T(GameObject&) immediately, appends it to the object's component list and returns a raw pointer that stays valid until the component is removed or the object is released. T must derive from Component (DerivedFromComponent concept).

  • If T::IsSingleton is true (for example AudioListener), and GetComponent<T>() already finds one, that existing component is returned and nothing is added. The default for Component is false.
  • If the object is in a scene, the component is pushed onto that object's own scene's attach queue (not necessarily the loaded scene). If not, nothing is queued yet: every component is queued when the object joins a scene.
  • OnAttach runs in the next ProcessAttachQueue, at the start of the next frame. A component added during a frame therefore gets OnAttach at the start of the next frame and its first OnUpdate later that same next frame. Until attached it receives no other callbacks, and scene lookups (FindObjectsByType) do not see it.
  • The queue is drained one live entry at a time, so OnAttach can add components (they are attached in the same pass) or remove pending ones (they are dropped from the queue).
  • A component whose OnAttach removes it, or moves its object to another scene, is not registered or touched afterwards. The scene tracks the components currently in OnAttach on a stack, and DetachComponent clears their entries, so this also holds for an OnAttach that drains the queue again (nested attach) PR #34. Test: ComponentRemovingItselfFromOnAttach.
  • OnAttach runs regardless of active state: components on inactive objects and components whose own flag is disabled are still attached.
  • After OnAttach, a component is registered for updates. Rendering::Light components (and subclasses) are registered for updates like any other component and are also added to the scene's light list, which rendering reads PR #39. Registration is idempotent.

Guarantee

OnAttach runs once per scene the object joins. Reparenting within the same scene does not re-queue components, so they are not attached or updated twice. Removing a component before it is attached leaves nothing in the queue.

Tests: ReparentingWithinSceneDoesNotAttachTwice, RemoveComponentBeforeAttachLeavesNothingQueued, DestroyRemovesObjectAtEndOfFrame.

Note

"Once per scene" means that an object leaving a scene and joining one again (for example RemoveRootGameObject and then AddRootGameObject) gets OnAttach again, with no OnDestroy in between: SetScene detaches and re-queues without running teardown callbacks.

Guarantee PR #39

A Light (or a subclass) gets OnUpdate, OnFixedUpdate, OnLateUpdate and OnApplicationQuit on the same terms as any other component, once per frame, and the generic Scene::FindObjectByType<T> for a base type of Light (e.g. Component) returns lights too. It is still in the light list that CollectLighting reads, and FindObjectByType<Rendering::Light> still searches that list. Before, ProcessAttachQueue put lights only in the light list, so a Light subclass never got the per-frame callbacks.

Tests: LightCallbacksTest.LightReceivesFrameCallbacks, LightCallbacksTest.LightStaysInTheLightListAndTypeLookups, LightCallbacksTest.DestroyedLightStopsUpdating.

There is no Awake/Start: use the constructor for state that does not need the scene, and OnAttach for setup that does.

An exception thrown from OnUpdate (or any callback run by Scene::Update/FixedUpdate/LateUpdate) is not caught by the scene: it propagates out of the call. The iteration bookkeeping is unwound correctly, so later frames behave normally (ThrowingComponentDoesNotWedgeIteration). Contrast coroutines, whose exceptions are caught and logged.

    explicit Health(N2Engine::GameObject &go) : Component(go) {}

    void OnUpdate() override  { /* per frame */ }
    void OnDisable() override { /* pairs with OnEnable, also runs before OnDestroy */ }
    void OnDestroy() override { /* release what OnAttach acquired */ }
};

Active state

There are two independent flags:

  • GameObject's own flag, GameObject::SetActive / IsActive(). IsActiveInHierarchy() is true when the object and every ancestor are active, and the object is not marked for destruction.
  • Component's own flag, Component::SetActive. Component::IsActive() returns own flag and not destroyed and the object's IsActiveInHierarchy().

GameObject::SetActive

  1. If the flag already has the requested value, nothing happens (no callbacks).
  2. Otherwise the flag changes and the cached IsActiveInHierarchy of the object and its whole subtree is invalidated.
  3. If the effective state (IsActiveInHierarchy) changed, OnEnable or OnDisable runs synchronously, before SetActive returns, on: every component of the object whose own flag is enabled and that is not destroyed, then recursively on children whose own flag is active. A child that is inactive itself is skipped with its whole subtree, since its effective state did not change.

Reparenting (AddChild, RemoveChild, SetParent) compares the child's effective state before and after and fires the same notifications, so parenting under an inactive object disables the child's subtree.

SetActiveRecursive(active) calls SetActive on the object and then on every descendant, so it overwrites the descendants' own flags.

Component::SetActive

Component::SetActive only sets the flag. It fires no OnEnable/OnDisable. A disabled component is skipped by the update loops from the next iteration, and its flag is never overwritten by GameObject toggles.

When the flag actually changes (and the component is not being torn down), SetActive calls the protected virtual Component::OnActiveFlagChanged() PR #37. The base version does nothing. A component that must react to its own flag overrides it and checks IsActive(); the physics components use it to take their body or shapes out of the simulation (see Physics). Setting the same value calls nothing.

Guarantee

Deactivating an ancestor makes every descendant report inactive (no stale cache), and fires OnDisable once; reactivating fires OnEnable once. A component's own disabled flag survives object toggles and its component receives neither callback. A child that is inactive itself gets nothing when its parent toggles. Setting the same state fires nothing. Reparenting under an inactive parent disables, and back under an active one enables.

Tests: DeactivatingRootDeactivatesGrandchild, ToggleKeepsComponentsOwnEnabledFlag, InactiveChildStaysInactiveWhenParentToggles, SettingSameStateFiresNothing, ReparentingUnderInactiveParentDisables.

Note

OnEnable/OnDisable track transitions of the object's effective state only. Because OnEnable is not called on attach and Component::SetActive fires nothing, a component that starts enabled gets no OnEnable before its first update, and one disabled through its own flag gets no OnDisable (and none at teardown either, see below). Do initial setup in OnAttach.

Destroy

GameObject::Destroy() is deferred when the object is in a scene:

  1. Destroy() pushes the object onto its scene's destruction queue (Scene::DestroyGameObject). Nothing else changes: IsDestroyed() is still false, the object still updates for the rest of the frame (LateUpdate, render), and it can still be found.
  2. At the end of the frame, Scene::ProcessDestroyed drains the queue. For each queued object not already marked, it marks the object and its whole subtree (IsDestroyed() becomes true, IsActiveInHierarchy() becomes false) and collects them, parents before children.
  3. For every collected object, in that order: each component runs the teardown sequence (OnDisable if applicable, then OnDestroy), then the object's coroutines are stopped.
  4. Only after every collected object's callbacks have run, each is purged: removed from its parent (unless the parent is also being destroyed) or from the scene's roots, detached from the scene, its components freed, children list cleared, Positionable released, and IsTornDown() set.

Because callbacks for the whole batch run before any purge, a component's OnDestroy can still use other objects destroyed in the same batch.

SituationResult
Destroy() twice (same frame or later)Queued twice; the second entry is skipped because the object is already marked. OnDestroy runs once.

Destroy an object that is not in a sceneImmediate: IsDestroyed() and IsTornDown() become true. No callbacks run and the components are not freed; children are not touched. Guarantee

Destruction happens at the end of the frame. After ProcessDestroyed, the object is gone from the scene (search, serialization, FindObjectsByType) and its components never update again. Destroying twice runs OnDestroy once; destroying a parent destroys its children once each; a light on a destroyed object is removed from the scene's lighting.

Note

Before PR #17, Destroy() marked the object first, and ProcessDestroyed skipped marked objects, so nothing was ever destroyed. That is why Destroy() deliberately leaves IsDestroyed() false until the end-of-frame pass. If you need "destroy requested" state, track it yourself.

Guarantee PR #34

A scene only destroys its own objects. Scene::DestroyGameObject refuses an object whose scene is a different one (or none): it logs a warning and returns false. Scene::ProcessDestroyed also skips a queued object that has moved to another scene since it was queued, so it is never purged from the wrong root list or scheduler. GameObject::Destroy() always uses the object's own scene; the check matters for direct calls from C++ and from Lua (scene:DestroyGameObject(go)).

The teardown sequence

Every path that ends a component's life in a scene runs the same private function, Component::RunDestroyCallbacks(objectWasActiveInHierarchy):

  1. If the component is already marked destroyed, or its teardown callbacks are already running, return. So it runs at most once (unless a callback throws; see the Guarantee below), whichever path gets there first, even if its own OnDisable/OnDestroy re-enters teardown (see below).
  2. If the component's own flag is enabled and the object was active in the hierarchy before teardown started, call OnDisable().
  3. Call OnDestroy().
  4. Mark the component destroyed (IsDestroyed() true).

"Was active" is computed ignoring the destruction mark (IsActiveInHierarchyIgnoringDestruction), because objects are already marked when the callbacks run.

It does not check that the component was ever attached. A component added and destroyed in the same frame, or one in a scene that is switched away before its first frame, gets OnDisable/OnDestroy without having had OnAttach, so OnDestroy must cope with setup that never happened.

The one path that does check is a scene dropped without being loaded PR #39: its destructor tears down only the components that attached to it, and frees the rest with no callbacks (see Scenes).

Guarantee

On Destroy, RemoveComponent and scene switch, a component sees OnDisable then OnDestroy if it was enabled in an active hierarchy, otherwise only OnDestroy; OnDestroy runs once unless a callback throws. _isMarkedForDestruction is set only after OnDestroy returns, so a throwing callback leaves the component unmarked and a later teardown path (for example a scene Clear after a failed editor DestroyEntity) runs its callbacks again.

Changes made by teardown callbacks PR #34

A component's OnDisable/OnDestroy may remove or destroy itself, remove or add other components on the same object, or reparent children:

  • Re-entry guard. A private flag (_isRunningDestroyCallbacks) is set for the duration of the callbacks and cleared by a scope guard, even if a callback throws. While it is set, RunDestroyCallbacks does nothing, so the sequence cannot recurse.
  • RemoveComponent on a component in its own teardown returns false and frees nothing: the teardown that is already running frees it once the callbacks return. This applies to a self-removal from OnDisable/OnDestroy, and to one made while the component is torn down by Destroy, a scene switch or RemoveAllComponents. RemoveAllComponents called from such a callback likewise skips the component whose callbacks are running.
  • Snapshot iteration. Scene::CallOnDestroyForGameObject, GameObject::RemoveAllComponents and GameObject::NotifyActiveChanged (which fires OnEnable/OnDisable for SetActive and reparenting) iterate a copy of the component or child list. Before each call they check that the component is still owned by the object (or the child still has this parent), so anything a callback already freed or moved is skipped. RemoveAllComponents also frees components that its own callbacks added.

Guarantee

A component that removes itself from its own teardown callbacks gets OnDisable/OnDestroy once and is freed once, by the outer teardown. Adding or removing components from teardown or activation callbacks never invalidates the iteration in progress.

Tests: ComponentRemovingItselfFromOnDisableIsRemovedOnce, ComponentRemovingItselfFromOnDestroyIsRemovedOnce, ComponentRemovingItselfWhileItsObjectIsDestroyed, RemoveAllComponentsFromOnDestroyWhileTheObjectIsDestroyed, AddComponentFromOnDestroy, AddComponentFromOnDestroyDuringRemoveAllComponents, AddComponentFromOnDisableWhenDeactivated (HierarchyLifetimeTests).

Purge and ~GameObject

Purge (private, called by the destroy pass) only releases: no callbacks. ~GameObject detaches every component from the scene it still points at and stops its coroutines there, however the object was dropped; it runs no callbacks either. A scene that is destroyed first clears the scene pointer of the objects it can still find (Scene::~Scene): its roots (and, through SetScene, their subtrees) and the owners of entries in its component list and attach queue.

Guarantee PR #34

No object keeps a pointer to a freed scene. Every object in a scene is either a root or under one, because RemoveChild re-roots the child. Scene::Clear (a scene switch) tears down everything reachable from the roots and then clears the scene pointer of every torn-down object that still belongs to this scene, including one an OnDestroy unlinked from its parent. An object a callback moved to another scene keeps that scene. A child removed before a switch therefore gets OnDisable/OnDestroy with the rest of the scene, and can still be used (with no scene) and released safely afterwards.

Tests: RemovedChildIsTornDownBySceneSwitch, RemoveChildMakesTheChildARootOfItsScene (HierarchyLifetimeTests); RemovedChildKeepsItsCoroutinesUntilItLeavesTheScene (CoroutineTests).

Warning

Releasing an object that has left its scene without being destroyed (RemoveRootGameObject, then dropping the last shared_ptr) frees its components without OnDisable/OnDestroy. Anything a component acquired in OnAttach (physics bodies, audio sources) is then released only by the component's own destructor, if it has one. Use Destroy() to end an object's life with callbacks.

Hierarchy: AddChild, RemoveChild, SetParent

All three take keepWorldPosition (default true). It only has an effect when both the child and the parent involved have a Positionable; the child's world position, rotation and scale are then restored after the relationship changes. Details and limits are on Transforms.

Parenting a root removes it from the scene's roots. Parenting an ancestor under its own descendant is refused and leaves the hierarchy unchanged, whether through AddChild or SetParent PR #34. RemoveChild in a scene makes the child a root of that scene; outside a scene it only detaches. Scene::AddRootGameObject on a root of another scene moves it: it is removed from the other scene's root list PR #34.

Design decision: RemoveChild re-roots, as in Unity PR #34

Removing a child from its parent does not take it out of the world; that is what Destroy (or RemoveRootGameObject) is for. Unity's SetParent(null) has the same meaning, so code ported from Unity behaves as expected. The old rule (unlink only) left the child in the scene but under no root: it kept updating, was never rendered or serialized, and was skipped by a scene switch, after which it pointed at the freed scene (a use-after-free reachable from Lua). Making it a root keeps every object in a scene reachable from that scene's roots, which is what teardown, serialization and search rely on. The destroy paths, which must not put a dying object back into the scene, use the private DetachChild instead. The Lua binding follows the same rule for ownership: parent:RemoveChild(child) gives the script ownership only when the child is not a scene root afterwards PR #31 (see Lua handles).

Note

Reparenting a root from inside a Scene::TraverseAll/TraverseUntil callback is not supported: AddChild, RemoveChild and SetParent(nullptr) edit the root list the traversal is iterating (as RemoveRootGameObject does).

Other hierarchy helpers: GetParent, GetChildren, GetChild(i) (null if out of range), FindChild(name) (direct children), FindChildRecursive(name) (breadth of direct children first, then depth), GetChildrenRecursive (pre-order), IsChildOf (any ancestor), IsParentOf (any descendant), GetRoot, GetHierarchyDepth, GetHierarchyPath ("Root/Child/Leaf").

Warning

GetComponent<Base>() does not find a derived component: the lookup map is keyed by the concrete type. For example GetComponent<Physics::ICollider>() returns nullptr on an object with a BoxCollider. Use GetComponents<Base>() for base-class queries (the engine does so for colliders).

Guarantee

GetComponent returns the first component of a type (Unity's rule). Removing it makes the next one of that type findable. Deserialized objects follow the same rule.

Tests: GetComponentReturnsTheFirstOfAType, RemovingTheFirstComponentExposesTheNext.

Design decision: GetComponent returns the first of its exact type

An object can hold several components of one type, so GetComponent needs a stable answer. "First added" is Unity's rule and does not change when later components are added, so a script that caches the result keeps seeing the same instance. It also survives a save/load round trip, because components are serialized and re-added in order. The lookup is a map from the concrete typeid to that first instance, which makes it O(1); the price is that base-class queries miss, which is why GetComponents<Base>() (a dynamic_cast scan) exists alongside it. RemoveComponent<T>() removes the same instance GetComponent<T>() returns, and the next one of that type then takes its place in the map.

After removal the scene no longer lists the component and it never updates again; a specific instance can be removed while the first stays mapped; removing twice returns false.

Changing components during a callback

Scene::Update, FixedUpdate, LateUpdate and OnApplicationQuit all go through Scene::OnAllActiveComponents, which iterates the scene's component list by index:

  • Adding a component during an update does not touch this list (new components are only registered by ProcessAttachQueue), so it first updates next frame, after its OnAttach.
  • Removing a component during an update: while any iteration is running (a depth counter), DetachComponent replaces its entry with nullptr instead of erasing it. The loop skips null entries, and the list is compacted when the outermost iteration finishes.
  • Each entry is re-checked for IsActiveInHierarchy() and IsActive() just before its callback, so a component disabled or deactivated earlier in the same loop is skipped.
  • The depth counter is restored by a scope guard even if a callback throws.

Guarantee

A component removed by an earlier component's OnUpdate in the same pass is skipped (never called after being freed) and later frames update normally; a throwing component does not leave the scene stuck in "iterating" mode.

Tests: RemoveComponentDuringUpdateSkipsIt, ThrowingComponentDoesNotWedgeIteration.

Lifetime token and copies PR #29

Each component owns a std::shared_ptr<const bool> that nothing else owns. GetLifetimeToken() returns a std::weak_ptr to it, which expires exactly when the component is freed. Code that must keep a reference to a component without dangling (the Lua ComponentRef handles are the in-tree user) stores the token and checks expired() before use.

std::weak_ptr<const bool> token = rb->GetLifetimeToken();
// ... later, possibly after RemoveComponent or a scene switch
if (!token.expired())
{
    rb->AddForce(push);   // still the same live component
}

Copy construction and copy assignment of Component are deleted, because a copy would share the token and expire with the original.

Note

An expired token means the memory is gone. A live token does not mean the component is usable: during and after its teardown callbacks it still exists with IsDestroyed() true until it is freed. Lua handles additionally check the owner's IsTornDown().

Names, tags and search helpers

  • GetName/SetName: free-form, not unique. Scene::FindGameObject(name) returns the first match in a pre-order traversal from the roots.
  • Tags PR #39: every GameObject has one string tag, "Untagged" by default (GameObject::DefaultTag, as in Unity). GetTag/SetTag take any string; there is no list of allowed tags. CompareTag(tag) is an exact, case-sensitive comparison. The tag is saved with the object (the "tag" field, see Serialization).
  • Scene::FindGameObjectWithTag(tag) returns the first object with that tag in the same pre-order traversal, or nullptr; Scene::FindGameObjectsWithTag(tag) returns all of them in traversal order. Both include inactive objects. FindGameObjectsByTag is the older name for FindGameObjectsWithTag and does the same.
  • The static helpers GameObject::FindGameObjectByName(name, scene), FindGameObjectWithTag(tag, scene), FindGameObjectsWithTag(tag, scene) and FindGameObjectsByTag(tag, scene) call the same search on the given scene, and return nothing for a null scene PR #39. Before, they were stubs that always returned nothing.
  • Scene::FindObjectByType<T>/FindObjectsByType<T> search attached components (not ones still in the attach queue) with dynamic_cast; destroyed ones are skipped, and inactive ones are skipped when includeInactive is false.

From Lua, GameObjects and components are reached through checked handles; the binding exposes a subset (no SetParent or RemoveComponent on the Lua GameObject type, for example). See Lua scripting.

Layer PR #44

  • Every GameObject is on one layer, an index 0–31 (see Layers and the collision matrix for the names, masks and matrix). It starts on 0, Default.
  • GetLayer()/SetLayer(layer). A value outside 0–31 is clamped into range with a warning. Setting a layer moves the object's attached collider shapes to it straight away: queries see it at once, and contacts and triggers are filtered again in the next physics step.
  • Children keep their own layer, as in Unity: a collider uses its own GameObject's layer, never its parent's. SetLayerRecursive(layer) sets the object and all its descendants.
  • The layer is saved with the object as the "layer" index (see Serialization), so renaming a layer doesn't change which layer objects are on.
  • Lua: GameObject:GetLayer(), SetLayer(layer), SetLayerRecursive(layer).
