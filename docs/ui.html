UI

Screen-space overlay UI, built from ordinary GameObjects and components as in Unity's uGUI: a Canvas at the root, RectTransform layout instead of a Positionable, and Image and UIText graphics. The UI is drawn in its own pass after the scene and gets the pointer before world picking. This page covers the coordinate space, layout, draw order, the UI pass, images, text, pointer input and the Lua API. Buttons and world-space canvases come later in issue #42.

UI objects PR #50

A UI is a tree of GameObjects under an object with a Canvas. Each element has a RectTransform and usually a graphic such as Image. UI objects need no Positionable, so layout stays separate from 3D transforms and physics. Because they are ordinary scene objects, they are saved with the scene, appear in the editor's entity list, can be added from Lua by name, and receive the usual lifecycle callbacks.

ComponentRole
UI::CanvasThe root of a UI tree. Has a sortOrder; the render mode is always ScreenSpaceOverlay for now. One per object.
UI::RectTransformAnchors, pivot, anchored position and size delta; the element's rect is resolved from its parent's rect. One per object (AddComponent returns the existing one).
UI::UIGraphicBase of everything the UI pass draws: a colour, a raycastTarget flag, a tint (PR #TBD, below), and RenderUI(renderer, rect, state). It is not an IRenderable, so the scene pass never draws it.
UI::ImageA UIGraphic that fills its rect with its colour, optionally multiplied by a texture.
UI::UIText PR #53A UIGraphic that draws text inside its rect with an SDF font (Text).
UI::Button PR #TBDMakes its object clickable: tints a target graphic for the pointer's state and invokes an OnClick event (Button).
UI::UISystemStatic functions: layout, the UI pass, the hit test, and the helpers below.

UISystem::CreateCanvas(name) returns a new object on the UI layer (layer 5) with a Canvas. UISystem::CreateElement(name) returns one on the UI layer with a RectTransform. UISystem::CreateText(name, text) PR #53 is CreateElement plus a UIText showing text. UISystem::CreateButton(name, label) PR #TBD is a ready-made button. Adding the components by hand works too: the components never change an object's layer, because a scene's saved layer is read before its components are created. The UI ignores layers. The hit test doesn't filter by layer, and the world pick's mask doesn't affect UI.

auto canvas = UI::UISystem::CreateCanvas("HUD");
scene.AddRootGameObject(canvas);

auto panel = UI::UISystem::CreateElement("HealthBar");
auto *rect = panel->GetComponent<UI::RectTransform>();
rect->SetAnchorMin({0.0f, 1.0f});      // top-left corner of the canvas
rect->SetAnchorMax({0.0f, 1.0f});
rect->SetPivot({0.0f, 1.0f});
rect->SetAnchoredPosition({16.0f, -16.0f});
rect->SetSizeDelta({200.0f, 24.0f});
panel->AddComponent<UI::Image>()->SetColor(Common::Color{0.8f, 0.1f, 0.1f, 1.0f});
canvas->AddChild(panel, false);

Canvas space

Layout uses canvas space: pixels in window coordinates' units, with the origin at the canvas's bottom-left and y pointing up, as in Unity's screen space. A UI::Rect is x, y (its bottom-left corner), width and height.

  • The cursor (Mouse::GetPosition, Lua Input.GetMousePosition) is in window coordinates, with the origin at the top-left and y down. UISystem::WindowToCanvas(point, viewport) converts a point: y' = height - y.
  • The viewport is the window's size in window coordinates (Window::GetWindowDimensions), not the framebuffer's. On a high-DPI display the framebuffer is larger. The UI projection maps the canvas onto whatever the framebuffer is, so the UI is the same size in window units on any display, and the cursor lines up with it.
  • Rect::Contains(point) includes all four edges, so neighbouring rects leave no gap between them. A rect whose width or height is zero or negative has no area: it isn't drawn and nothing hits it.

RectTransform layout PR #50

An element's rect is worked out from its parent's rect, the same way as in Unity:

FieldMeaningDefault
anchorMin, anchorMaxThe corners of the anchor box, as fractions of the parent rect: (0, 0) is its bottom-left and (1, 1) its top-right. When the anchors are equal, the element is pinned to one point of the parent. When they differ, the element stretches with the parent.(0.5, 0.5) both
pivotThe point of the element that anchoredPosition places, as a fraction of its own size(0.5, 0.5)
anchoredPositionThe pivot's offset in pixels from the reference point, the point at pivot inside the anchor box(0, 0)
sizeDeltaThe element's size minus the anchor box's size. With equal anchors it is simply the size.(100, 100)
 
box.min  = parent.min + anchorMin * parent.size
box.size = (anchorMax - anchorMin) * parent.size
size     = box.size + sizeDelta
pivotPos = box.min + pivot * box.size + anchoredPosition
rect     = (pivotPos - pivot * size, size)
  • GetOffsetMin and GetOffsetMax give the corners' offsets from the anchor box's corners, as Unity's offsetMin and offsetMax do. SetOffsetMin moves the bottom-left corner and keeps the top-right one where it is. SetOffsetMax does the reverse. Both rewrite sizeDelta and anchoredPosition with Unity's formulas.
  • StretchToParent() sets anchors (0, 0)–(1, 1) with zero offsets, so the element covers its parent exactly.
  • ResolveIn(parentRect) and the static Resolve(...) compute a rect without changing anything. GetRect() returns the rect from the last layout. A layout runs every time the UI pass draws and every time the pointer is hit-tested. An inactive object's GetRect() isn't updated.
  • An object under a canvas that has no RectTransform takes its parent's rect, as if it were stretched with zero offsets, and its children lay out inside that rect.
  • There is no rotation or scale, and no layout groups. A RectTransform's own enabled flag is ignored.

Guarantee: layout follows the viewport

Layout is a pure function of the hierarchy, the components' values and the viewport size, so it gives the same result with or without a window. After a resize, stretched elements stretch and anchored elements keep their size and their distance from their anchor. Canvases and draw order PR #50

UISystem::CollectGraphics(scene, viewport) lays out the scene's UI and returns its graphics in draw order. The UI pass and the hit test both use it.

  1. Find the canvases. A canvas is an enabled Canvas component on an object that is active in the hierarchy and has no Canvas above it. Objects are visited depth first, with roots in scene order. Inactive objects are skipped with their subtrees, and so is the tree of a disabled root Canvas. A Canvas below another one is ignored, enabled or not: its object is an ordinary element of the outer canvas.
  2. Sort them by sortOrder, lowest first. The sort is stable, so canvases with equal sort orders keep hierarchy order. A higher sortOrder draws on top.
  3. Lay out each canvas. The canvas's rect is the whole viewport, (0, 0, width, height), whatever a RectTransform on its object says (the canvas's RectTransform, if any, is given that rect). The tree is walked depth first, parents before children and children in order, skipping inactive objects and their subtrees.
  4. List the graphics. Each object's enabled UIGraphic components are listed in component order, with the object's rect.

So later items draw over earlier ones: a later canvas over an earlier one, a later sibling over an earlier sibling, and a child over its parent. A Canvas nested under another canvas has no effect of its own: its object is laid out and drawn as an ordinary element of the outer canvas, and its sortOrder is ignored. A UI object that isn't under any canvas is never drawn or hit.

Source: engine/src/ui/UISystem.cpp — UISystem::CollectGraphics, FindCanvases; tests: UIPassTest.HierarchyOrderWithinACanvasAndSortOrderAcrossCanvases, UIPassTest.SkipsInactiveDisabledAndEmptyAndNestedCanvasesJoinTheirParent

The UI pass PR #50

Application::Render calls UISystem::Render(scene, renderer, viewport) right after Scene::Render and before EndFrame, with the window's size as the viewport (see Rendering the scene). It does the following:

  1. Collects the graphics. If there are none (no canvas, or a zero-size viewport such as a minimised window), it returns without touching the renderer.
  2. Sets the view to identity and the projection to UISystem::OverlayProjection(viewport). This is an orthographic projection of x 0..width, y 0..height (y up) and z −1..1, so a canvas-space point is a pixel.
  3. Calls RenderUI(renderer, rect, UISystem::OverlayState()) on each graphic whose rect has an area, in draw order.
RenderState fieldUI passWhy
depthTest, depthWriteoffUI is drawn over the scene, in order. The scene's depth buffer doesn't matter, and later UI simply covers earlier UI.
cullNoneWinding doesn't matter in a flat 2D pass, and a projection or quad that flips it can't make UI disappear.
blendonSemi-transparent panels show what is under them.

There is no Overlay render queue: the scene's queues are only Opaque and Transparent (two render queues). The UI pass leaves the UI view and projection on the renderer until the next frame sets the camera's again. IRenderer::SetViewProjection applies to the draws submitted after it, so the scene's draws keep the camera.

Backends

  • OpenGL draws the UI as described.
  • Software draws it too, now that each draw keeps the view and projection it was submitted with PR #50 (the backend used to apply the frame's last view and projection to every draw). UI draws don't write depth, so they keep their submitted order. The software renderer has no blending, so semi-transparent UI is drawn opaque. A headless golden test checks that an Image fills its rect there (SoftwareUIGoldenTest) PR #51. UIText is alpha-tested there, like world text; golden tests check where its ink lands in the rect and that it draws over an Image in hierarchy order PR #53.
  • Vulkan draws nothing yet (#43).

As with IRenderable::Render, RenderUI must not add, remove or destroy components or GameObjects immediately. Destroy is fine because it is deferred.

Image PR #50

Image draws its rect in its colour (SetColor; white by default) with the renderer's standard unlit shader. It uses one quad per Image: the unit square (0, 0)–(1, 1), wound counter-clockwise in canvas space, with uv (0, 0) at the bottom-left. Its model matrix (Image::ModelMatrixFor(rect)) scales the square to the rect and moves it there. The quad and material are created with the renderer the first time the Image draws, and released in OnDestroy. If a different renderer draws it later, or a new renderer at the old one's address (the window was re-created), it creates them again. It destroys the old ones only if their renderer still exists, which it knows from the renderer's lifetime token.

SetTexture(ITexture*) multiplies the colour by a texture made with IRenderer::CreateTexture. The first row of the pixel data (v = 0) is drawn at the bottom of the rect, so image data stored top row first, as most image files are, must be flipped before CreateTexture to show upright. The Image neither owns nor saves the texture. Whoever made it keeps it alive while the Image uses it, and calls SetTexture(nullptr) before destroying it. There is no texture asset yet, so a saved scene doesn't keep the texture.

Every graphic also has a tint PR #TBD (UIGraphic::GetTint/SetTint, white by default): Image and UIText draw with GetDrawColor(), their colour multiplied by the tint channel by channel, alpha included. The tint is what a Button sets; it is not saved, and it never changes the colour itself.

Source: engine/src/ui/Image.cpp — Image::RenderUI, Image::EnsureResources; engine/src/ui/UIGraphic.cpp — UIGraphic::GetDrawColor; tests: UIPassTest.ImageCreatesItsQuadOnceAndReleasesItOnDestroy

Text (UIText) PR #53

UIText draws a block of UTF-8 text inside its object's rect, with the same SDF fonts, layout and shader as the world-space TextRenderer. Layout and mesh building come from the text work (#1); the canvas, rect and UI pass from this page (#42).

auto label = UI::UISystem::CreateText("Score", "Score: 0");
auto *rect = label->GetComponent<UI::RectTransform>();
rect->SetAnchorMin({1.0f, 1.0f});      // top-right corner of the canvas
rect->SetAnchorMax({1.0f, 1.0f});
rect->SetPivot({1.0f, 1.0f});
rect->SetAnchoredPosition({-16.0f, -16.0f});
rect->SetSizeDelta({240.0f, 40.0f});
auto *text = label->GetComponent<UI::UIText>();
text->SetFontSize(28.0f);              // pixels per em
text->SetHorizontalAlign(Text::HorizontalAlign::Right);
text->SetVerticalAlign(Text::VerticalAlign::Middle);
canvas->AddChild(label, false);

Font::Layout places lines relative to an origin: Left starts them there, Center centres them on it, Right ends them there; Top puts the first line's ascent there, Middle centres the block on it, Bottom puts the last line's descent there, and Baseline the first line's baseline (see Layout). UIText puts that origin, the anchor (UIText::AnchorFor(rect, h, v)), at the matching point of the rect:

AlignmentAnchor in the rectResult
Left / Center / Rightx = left edge / centre / right edgeEach line starts at the left edge, is centred, or ends at the right edge
Topy = top edgeThe first line's ascent touches the top edge
Middley = vertical centreThe block (first ascent to last descent) is centred
Bottomy = bottom edgeThe last line's descent touches the bottom edge
Baseliney = vertical centreThe first line's baseline is on the rect's vertical centre, as TextMesh Pro's Baseline does

Nothing is clipped: text taller than the rect, or wider with wrap off, overflows it. GetLayout(rect) returns the layout relative to the anchor, GetBoundsIn(rect) the block in canvas space, and GetCurrentRect() the rect the last layout resolved (its RectTransform's, or the rect it was last drawn in).

Drawing:

  • It draws with IRenderer::GetStandardTextShader() and the UI pass's state: no depth, no culling, blending on. On the software renderer, which can't blend, the text shader alpha-tests the glyphs instead, so text drawn over an Image covers it exactly where its glyphs are. Where the text shader is null (Vulkan until #43) nothing is drawn, and one warning is logged per process.
  • The mesh is built relative to the anchor, and the model matrix (UIText::ModelMatrixFor(anchor), a translation) moves it to the rect. So the layout and mesh are rebuilt only when the text, font, size, an alignment, spacing, wrap or, with wrap on, the rect's width changes. Moving the rect, or changing only its height, changes nothing but the model matrix. A rebuilt mesh is updated in place with IRenderer::UpdateMesh, or recreated where the backend can't.
  • Each font's atlas is one texture per (renderer, font), shared with every TextRenderer and UIText drawing that font on that renderer and destroyed with its last user. The mesh, material and atlas share are created when the text first draws and released in OnDestroy. Like Image, it uses the renderer's lifetime token: a new renderer, or one re-created at the old address, gets new resources, and the old ones are destroyed only if their renderer still exists.
  • Empty text, or text with only spaces, draws nothing.

Design decision: the component is called UIText

N2Engine::Text is already the text library's namespace (Text::Font, Text::HorizontalAlign). A class UI::Text would hide that namespace inside N2Engine::UI, so every Text:: there would need qualifying, and "Text" would be a vague scene and Lua type name next to TextRenderer. UIText is unambiguous everywhere and is the name the text plan used.

Design decision: font size in pixels per em, wrapping to the rect

The UI is laid out in canvas pixels, so the font size is too: 24 means an em of 24 pixels, the same unit as the rect it sits in, and the same number a designer reads off a mockup. (TextRenderer's size is world units per em for the same reason.) The rect is the text box: wrapping at its width is the default, as in Unity's Text, so a label that doesn't fit breaks into lines instead of running off a panel; wrap off gives single-line labels that may overflow. There is no clipping or best-fit sizing yet. SDF keeps glyphs sharp at any size, so one atlas per font serves every pixel size.

Design decision: text is not a raycast target by default

Unity's Text is a raycast target by default, and a caption on a button then catches the clicks meant for the button's Image; in practice almost every label has the flag turned off. Here the default is off: the pointer goes through text to what is underneath, UI or world. Text that should take clicks itself (a link, say) turns it on with SetRaycastTarget(true). Its hit area is then the whole rect, not the glyphs.

Design decision: one drawing helper for world and UI text

TextRenderer and UIText share Rendering::TextDrawing (engine/include/engine/rendering/TextDrawing.hpp): the layout cache (LayoutCache, which compares the text in place and lays out again only on a change), the glyph mesh (BuildMesh), and the GPU resources (DrawResources: the mesh updated in place, the material, and the per-(renderer, font) atlas texture cache with its lifetime tokens). The two components only differ in where the text goes (the object's transform, or the anchor in the rect) and in the render state they pass. Sharing the atlas cache means a font used in both the world and the UI is uploaded once per renderer.

Pointer input PR #50

The application's PointerDispatcher has UISystem::MakeApplicationHitProvider() as its UI hit provider. It is installed when Application is constructed. Each frame the dispatcher asks it first (see Picking). The provider runs UISystem::HitTestWindowPoint on the current scene with the window's size:

  1. A cursor outside the viewport (anything but 0 <= x < width and 0 <= y < height) hits nothing, the same rule as the world pick. Without a window or a loaded scene, nothing is hit either.
  2. The point is converted to canvas space, and the scene is laid out for the viewport (CollectGraphics).
  3. The graphics are tried in reverse draw order, so the topmost comes first. The first graphic with raycastTarget set whose rect contains the point is the hit, and the target is that graphic's GameObject.

When the UI hits an element, the world pick doesn't run, and PointerDispatcher::IsPointerOverUI() (Lua Input.IsPointerOverUI()) is true for that frame. The element's object gets the same OnMouse* callbacks a picked world object gets, with the same capture rules: OnMouseDown captures, OnMouseDrag follows the pointer off the element and onto the world, and OnMouseUpAsButton fires only if the button is released over the element. Delivery follows the same rule as picking: every component of an active object, disabled ones included. An element deactivated while hovered is dropped without OnMouseExit.

Design decision: UI is GameObjects drawn in a canvas pass after the scene

UI elements are GameObjects with Canvas, RectTransform and graphic components, as in Unity's uGUI, not a separate UI tree or an immediate-mode API. That way they get serialization, the editor's entity list, Lua AddComponent and the lifecycle for free. They have no Positionable, so layout never touches 3D transforms or physics. The layout uses Unity's anchor model and Unity's screen space (bottom-left origin, y up), so values from Unity layouts carry over. Graphics are not IRenderables and the render queues have no Overlay queue. Instead, the UI draws in its own pass after the scene, with depth off (later draws cover earlier ones in hierarchy order), culling off and blending on, which keeps the scene's queues simple. The UI is hit-tested with plain rect tests against the same draw order, topmost first, and gives the pointer to the existing OnMouse* callbacks through the dispatcher's UI hook. One dispatcher and one set of callbacks therefore serve both UI and world objects, and a UI hit keeps the click from reaching the world.

Button PR #TBD

UI::Button makes its object clickable, as Unity's Selectable and Button do together. Put it on an object with a raycast-target graphic, usually an Image: the graphic is what the UI hit test finds, and the dispatcher then sends the object the OnMouse* callbacks that drive the button. A UIText label is not a raycast target, so a caption on the button lets the pointer through to its Image. A Button on an object with no raycast-target graphic never receives the pointer (it can still be clicked from code with Click()). Closes the Button part of #42.

auto play = UI::UISystem::CreateButton("Play", "Start game");  // Image + Button + "Label" child
canvas->AddChild(play, false);

auto *button = play->GetComponent<UI::Button>();
button->SetHighlightedColor(Common::Color{0.9f, 0.9f, 1.0f, 1.0f});
const UI::Button::ListenerId id = button->AddOnClick([] { SceneManager::LoadScene("Level1"); });
// later: button->RemoveOnClick(id);

UISystem::CreateButton(name, label) returns an element sized 160 x 40 (centred in its parent, as CreateElement does) with a white Image, a Button, and a child named "Label": a UIText showing label, stretched over the button, centred both ways, 20 px, unwrapped and dark grey. Like the other helpers it takes no parent: add the result under a canvas or element.

States and tint

The state is worked out from what the pointer did, in this order:

StateWhenTint (times colorMultiplier)Default colour
Disabledinteractable is offdisabledColor(200, 200, 200, 128) / 255
PressedThe left button went down on it (OnMouseDown) and the pointer is over itpressedColor(200, 200, 200, 255) / 255
HighlightedThe pointer is over it (OnMouseEnter until OnMouseExit)highlightedColor(245, 245, 245, 255) / 255
NormalOtherwise, including pressed but dragged off itnormalColorwhite

The defaults are Unity's ColorBlock; colorMultiplier is 1. So: Enter highlights, Down presses, Exit returns to normal (a press dragged off shows normal, and pressed again when dragged back on), and Up returns to highlighted if the pointer is over it, otherwise normal. GetState() returns the state and GetCurrentTint() the tint applied now.

The tint goes to the target graphic through UIGraphic::SetTint, so it is drawn as the graphic's own colour times the state's colour times the multiplier (GetDrawColor()). The graphic's colour is never written: in the normal state (white) the graphic looks exactly as it was set, and changing its colour while it is tinted keeps the tint on top of the new colour.

  • Target graphic. By default, the first live UIGraphic on the button's own object, looked up each time (normally the Image). SetTargetGraphic(graphic) picks another, on any object; nullptr goes back to the default. An explicit target is held by its component lifetime token, never by a bare pointer: once it is destroyed, GetTargetGraphic() returns nullptr and nothing is tinted (it doesn't fall back to the default). A graphic that stops being the target gets a white tint back, and so does the last one tinted when the button is destroyed.
  • Fading. fadeDuration (default 0.1 s, Unity's) moves the tint from where it is to the new state's tint over that many seconds of unscaled time, in OnUpdate (Time::GetUnscaledDeltaTime()), so a paused game (timeScale 0) still animates its menu. 0 or less changes the tint at once. UpdateFade(seconds) advances a fade by hand (tests use it as a fixed time step); IsFading() tells whether one is under way. Changing a colour, enabling or disabling the component, and attaching it to a scene apply the tint at once.
  • interactable (IsInteractable/SetInteractable) off shows disabledColor and makes clicks do nothing. The hover and press are still followed, so turning it back on while the pointer is over the button shows Highlighted straight away.

OnClick

OnClick fires on OnMouseUpAsButton: the left button was pressed on the object and released over it (see Picking). A press dragged off and back on before release is one click; a release elsewhere is none, and so is a press that started elsewhere and was released over the button. It fires only if the button is interactable, the component is enabled on an object active in the hierarchy, and the component saw the press itself. Click() invokes it from code with the same interactable and enabled checks and returns whether it did (Unity's Press).

The listeners live in a Base::EventHandler<>, the engine's event type, which gained Clear(). Each listener is wrapped so that one that throws is logged with Logger::Error and the others still run. A listener may destroy the button, even with RemoveComponent, which frees it at once: the event is shared, so it outlives the button for the rest of the call, the destroy clears it so no later listener runs, and the button touches nothing of itself afterwards.

Disabled components and deactivated objects

The dispatcher sends OnMouse* to every component of an active object, disabled ones included. A disabled Button ignores them, as a disabled Unity Selectable gets no pointer events: no state changes and no clicks. Disabling the component (SetActive(false), through OnActiveFlagChanged) or deactivating its object (OnDisable) forgets the hover and the press and puts the tint straight back to the resting state, so a button disabled while pressed or hovered doesn't stay tinted. The dispatcher sends a deactivated object no OnMouseExit or OnMouseUp, which is why the button must forget them itself. Once enabled again, the pointer has to come onto it again to highlight it, and a press it forgot doesn't make a click when released.

AddOnClick(fn) returns an integer id for RemoveOnClick(id); ClearOnClick() removes them all. The function is wrapped like the engine's other script callbacks (MakeScriptCallback, as InputAction:Subscribe does): an error in it is logged (Button.OnClick callback error: ...) and the other listeners still run; if a component script added it, it is skipped once that component is destroyed. The Lua state lives for the whole process, so a function held by a button never outlives it, and a button's listeners are released when the button is destroyed. A listener that captures an owning handle to the button's own object (the one UI.CreateButton returned, before the object joins a scene or parent) keeps it alive through the Lua registry, the same caveat as for any Lua-owned object; capture self.gameObject or a component handle instead, which don't own.

Design decision: a tint multiplied in at draw time, not a replaced colour

Unity's ColorTint transition multiplies the state's colour into the graphic's CanvasRenderer colour, leaving Graphic.color alone. The engine has no canvas renderer, so the tint is a separate, unsaved field on UIGraphic that the graphics multiply into their colour when they draw. Replacing the colour instead (or multiplying it in place) would lose the graphic's own colour: a red button would turn grey and stay grey, a colour set by a script while the button was pressed would be overwritten on release, and a scene saved mid-hover would save the tinted colour. With a separate tint, white means "as set", the colour is always what the user set, and any graphic, Image or UIText, can be a target.

Design decision: OnClick is an EventHandler driven by OnMouseUpAsButton

The button adds no input path of its own: the dispatcher's existing OnMouse* callbacks and their Unity capture rules (Down captures, UpAsButton only when released over the same object) already are a button's behaviour, for UI and world objects alike. OnClick reuses Base::EventHandler, which already allows adding and removing during an invoke and which the Lua bindings already wrap. The button adds what a UI event needs on top: a per-listener guard against exceptions, an event that survives the button being destroyed by one of its own listeners, and Clear() on destroy so listeners (and the script functions they hold) go with the button.

Design decision: listeners are not serialized

Unity's persistent listeners save an object, a method name and an argument, and call the method by reflection. The engine has no reflection for that, and C++ lambdas and Lua functions can't be saved. So a scene saves a button's colours, colorMultiplier, fadeDuration and interactable, but not its listeners: the code or script that builds or loads the scene adds them, typically in a script's OnAttach. The explicit target graphic isn't saved either; a loaded button tints the first graphic on its object.

Design decision: the button needs a raycast target on its own object

The dispatcher sends the OnMouse* callbacks to the object whose graphic was hit, not to its parents, so the button has to be on that object. Image is a raycast target by default and UIText isn't, so the usual button (an Image with a label child) works as is: the label lets the pointer through to the Image. A child that is a raycast target (an icon Image on the button, say) takes the pointer away from the button where it covers it; turn its raycastTarget off. Bubbling events up to a parent, as Unity's event system does, may come later.

Serialization

Canvas, RectTransform, Image, UIText and Button are built-in components, registered under those names. They save their fields like any SerializableComponent:

  • Canvas saves sortOrder.
  • RectTransform saves anchorMin, anchorMax, pivot, anchoredPosition and sizeDelta, each as {"x", "y"}.
  • Image saves color and raycastTarget.
  • UIText PR #53 saves color, raycastTarget, text, font (the font asset's UUID, or null for the default font), fontSize, horizontalAlign and verticalAlign (by name, such as "Center", as TextRenderer does), wrap, lineSpacing and letterSpacing.
  • Button PR #TBD saves interactable, normalColor, highlightedColor, pressedColor, disabledColor, colorMultiplier and fadeDuration. Its OnClick listeners and an explicitly set target graphic are not saved (why); a loaded button tints the first graphic on its object, and shows its saved state's tint when it attaches to the scene.

A missing field keeps its default (for UIText, raycastTarget stays off). The resolved rect, the texture, the text's layout and mesh, and a graphic's tint are not saved.
