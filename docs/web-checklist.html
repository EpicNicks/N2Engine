Web player checklist PR #170

What to check by hand in a real browser for the web player, which CI cannot do: the CI job builds the package and runs it headless under node with a mocked canvas, so nothing about a browser (the canvas, the events, the page, hosting, speed) has been seen. Report which steps pass, the browser and its version, and the text of anything in the page's error box or the DevTools console.

Not verified until this is done

Every item below is unverified: that the page loads, that frames reach the canvas the right way up and in the right colours, that keyboard, mouse and wheel reach the game, that resizing and the pointer mapping are right, that the folder works from a subdirectory and with a wrong .wasm MIME type, and that the software renderer is fast enough in a tab.

Requirements

  • A recent desktop Chrome or Edge, and Firefox (and Safari if you have it). Nothing else: no GPU feature, no special flags.
  • The package folder from CI or a local build (Building and hosting the package): index.html, index.js, index.wasm, index.data. To build it yourself: Emscripten 4.0.10, then emcmake cmake -S . -B build-web -G Ninja -DCMAKE_BUILD_TYPE=Release -DN2ENGINE_WEB_PROFILE=speed and cmake --build build-web --target web-package.
  • Any static file server. The simplest: cd build-web/web-package && python -m http.server 8080.

1. It loads

  • Open http://localhost:8080/ with DevTools open (Console and Network). Expected: the dark page says "Loading the engine...", then "Ready." and the Click to start button turns on. Network shows index.js, index.wasm and index.data, all relative to the page, all 200.
  • No red errors in the Console (a warning from the audio system about having no device is expected: audio is not in the build yet).
  • Note the time from opening the page to "Ready." and the transferred sizes (a first, uncached load).

2. The canvas shows the scene

  • Click Click to start. Expected: the page-covering gate goes away and the canvas shows the lua_project scene (station 1: a lit cube, a sphere and a floor on a dark background, and the demo's text). The picture is the right way up (the floor at the bottom) and the colours are right (not red and blue swapped).
  • Things move: the scene animates (spinning objects, particles). The cube and the sphere do not fall: there is no physics in the web build.
  • Note the frame rate you see (a counter in the demo's HUD if it has one, or DevTools Performance) at your window size.

3. Keyboard, mouse and wheel

  • Keyboard: keys 1 to 7 move the camera between stations (as in the native lua_project); the arrow keys and Space do not scroll the page.
  • Mouse: moving the pointer and clicking in the scene work as in the native player (for example the UI station: hover and click). Check that the pointer's position matches what is drawn under it: click on a corner and on the centre of a UI element and see that the hit is where the cursor is. Repeat after resizing the window (step 4) and in a window larger than 1280 pixels wide, where the canvas is scaled.
  • Right and middle buttons: right click does not open a browser menu over the canvas; holding the right or middle button is seen by the game (the scene's mouse-button demo, if any).
  • Wheel: scrolling over the canvas is seen by the game (zoom or the scroll demo) and does not scroll the page; one notch is about one unit in both Chrome and Firefox.
  • Focus: hold a movement key, switch to another tab or window and release it there, then come back: the key must not be stuck down.
  • F5 reloads, F12 opens DevTools, Ctrl+R and Ctrl+L still work while the game runs.
  • Escape quits the game (the scene's Quit action): the page shows "The game has ended. Reload the page to play again." and the console shows no error.

4. Resize

  • Drag the window narrower, wider and to a very different shape (tall and narrow, then wide and short). Expected: the picture keeps its shape (not stretched: the camera's aspect follows), it fills the window, and nothing flickers or stays at the old size.
  • Maximise and restore, and use the browser's zoom (Ctrl +/-). Expected: the same.
  • Make the window small enough that the canvas is a few pixels, then large again: no crash and no error box.

5. Hosting

  • Subdirectory. Copy the package into a subfolder of another folder, serve the parent, and open http://localhost:8080/some/deeper/path/ (and the same with index.html at the end). Expected: identical behaviour, with every request under that path (Network).
  • No special headers. The server above sends none: that is the test. In the Console, crossOriginIsolated is false and the game still runs.
  • Wrong MIME type. Serve .wasm as text/plain (a one-line server that sets that type, or the Network panel's overrides). Expected: the game still starts. (n2-loader.js falls back to ArrayBuffer instantiation; the Network panel shows index.wasm requested twice, and CI has only tested this under node.)
  • Download progress and errors (stage 3). With the Network panel's throttling on a slow connection, load the page. Expected: a bar and "Downloading x of y MB" that rise to the total, then "Ready.". Then rename index.wasm and reload: the error box names index.wasm and the 404. Restore it, rebuild (or change a byte) and reload: the new files are requested with a new ?v= and not taken from the cache.
  • Precompressed copies (stage 3). Behind a server set up as in the recipes, index.wasm arrives with Content-Encoding: br (or gzip) and the game runs. On a server that does neither it arrives plain and the game runs.
  • Another host. If you can, upload the folder to a real static host (GitHub Pages, any bucket) and open it there. Expected: the same. Opening index.html from disk (file://) is not expected to work: browsers do not let a page fetch its own .wasm from there.
  • Embedded. Put the page in an <iframe> of a page on another origin or port. Expected: it loads and runs (click into the frame first so it gets the keyboard).

6. Error display (optional)

  • Delete index.data from the served folder and reload: the page must say something went wrong (the error box with a message) rather than stay on "Loading the engine..." forever.
  • Delete index.wasm and reload: the same.

7. Performance (a note, not a pass or fail)

The software renderer runs on one thread in the tab. Note, for the dev, size and speed profiles if you build them, the frame rate at about 1280x720 on your machine, and whether the tab stays responsive (the page can still be scrolled in DevTools, other tabs are fine). The render size is capped at 1280 pixels wide whatever the window; if that feels too soft or too slow, say which way.

What to report

  • For each step: pass, fail, or not tried, with the browser and its version.
  • Anything in the error box, and the Console text around it.
  • Load time and frame rate (steps 1, 2 and 7).
