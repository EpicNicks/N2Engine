Web player checklist PR #170 PR #181

What to check by hand in a real browser for the web player, which CI cannot do: the CI job builds the package and runs it headless under node with a mocked canvas, so nothing about a browser (the canvas, the events, the page, hosting, speed) has been seen. Report which steps pass, the browser and its version, and the text of anything in the page's error box or the DevTools console.

Not verified until this is done

Every item below is unverified: that the page loads, that frames reach the canvas the right way up and in the right colours, that keyboard, mouse and wheel reach the game, that resizing and the pointer mapping are right, that the folder works from a subdirectory and with a wrong .wasm MIME type, and that the software renderer is fast enough in a tab. Stage 4 adds audio: that sound is heard, that the page's unlock starts it after the first input per browser, that the hidden tab silences and restores it, and that a blocked or missing Web Audio leaves a quiet game (step 8).

Requirements

  • A recent desktop Chrome or Edge, and Firefox (and Safari if you have it). Nothing else: no GPU feature, no special flags.
  • The package folder from CI or a local build (Building and hosting the package): index.html, index.js, index.wasm, index.data. To build it yourself: Emscripten 4.0.10, then emcmake cmake -S . -B build-web -G Ninja -DCMAKE_BUILD_TYPE=Release -DN2ENGINE_WEB_PROFILE=speed and cmake --build build-web --target web-package.
  • Any static file server. The simplest: cd build-web/web-package && python -m http.server 8080.

1. It loads

  • Open http://localhost:8080/ with DevTools open (Console and Network). Expected: the dark page says "Loading the engine...", then "Ready." and the Click to start button turns on. Network shows index.js, index.wasm and index.data, all relative to the page, all 200.
  • No red errors in the Console (the audio system should not warn here: with Web Audio working it has no failure to report; an "Audio failed" warning means the browser gave no audio output, see step 8).
  • Note the time from opening the page to "Ready." and the transferred sizes (a first, uncached load).

2. The canvas shows the scene

  • Click Click to start. Expected: the page-covering gate goes away and the canvas shows the lua_project scene (station 1: a lit cube, a sphere and a floor on a dark background, and the demo's text). The picture is the right way up (the floor at the bottom) and the colours are right (not red and blue swapped).
  • Things move: the scene animates (spinning objects, particles). The cube and the sphere do not fall: there is no physics in the web build.
  • Note the frame rate you see (a counter in the demo's HUD if it has one, or DevTools Performance) at your window size.

3. Keyboard, mouse and wheel

  • Keyboard: keys 1 to 7 move the camera between stations (as in the native lua_project); the arrow keys and Space do not scroll the page.
  • Mouse: moving the pointer and clicking in the scene work as in the native player (for example the UI station: hover and click). Check that the pointer's position matches what is drawn under it: click on a corner and on the centre of a UI element and see that the hit is where the cursor is. Repeat after resizing the window (step 4) and in a window larger than 1280 pixels wide, where the canvas is scaled.
  • Right and middle buttons: right click does not open a browser menu over the canvas; holding the right or middle button is seen by the game (the scene's mouse-button demo, if any).
  • Wheel: scrolling over the canvas is seen by the game (zoom or the scroll demo) and does not scroll the page; one notch is about one unit in both Chrome and Firefox.
  • Focus: hold a movement key, switch to another tab or window and release it there, then come back: the key must not be stuck down.
  • F5 reloads, F12 opens DevTools, Ctrl+R and Ctrl+L still work while the game runs.
  • Escape quits the game (the scene's Quit action): the page shows "The game has ended. Reload the page to play again." and the console shows no error.

4. Resize

  • Drag the window narrower, wider and to a very different shape (tall and narrow, then wide and short). Expected: the picture keeps its shape (not stretched: the camera's aspect follows), it fills the window, and nothing flickers or stays at the old size.
  • Maximise and restore, and use the browser's zoom (Ctrl +/-). Expected: the same.
  • Make the window small enough that the canvas is a few pixels, then large again: no crash and no error box.

5. Hosting

  • Subdirectory. Copy the package into a subfolder of another folder, serve the parent, and open http://localhost:8080/some/deeper/path/ (and the same with index.html at the end). Expected: identical behaviour, with every request under that path (Network).
  • No special headers. The server above sends none: that is the test. In the Console, crossOriginIsolated is false and the game still runs.
  • Wrong MIME type. Serve .wasm as text/plain (a one-line server that sets that type, or the Network panel's overrides). Expected: the game still starts. (n2-loader.js falls back to ArrayBuffer instantiation; the Network panel shows index.wasm requested once, and CI has only tested this under node.)
  • Download progress and errors (stage 3). With the Network panel's throttling on a slow connection, load the page. Expected: a bar and "Downloading x of y MB" that rise to the total, then "Ready.". Then rename index.wasm and reload: the error box names index.wasm and the 404. Restore it, rebuild (or change a byte) and reload: the new files, index.js and n2-loader.js included, are requested with a new ?v= and not taken from the cache. With the host serving index.html without Cache-Control: no-cache, an old cached page that meets a new build shows "This page is an older copy than the build on the server ... Reload the page" rather than a link error.
  • Precompressed copies (stage 3). Behind a server set up as in the recipes, index.wasm arrives with Content-Encoding: br (or gzip) and the game runs. On a server that does neither it arrives plain and the game runs.
  • Another host. If you can, upload the folder to a real static host (GitHub Pages, any bucket) and open it there. Expected: the same. Opening index.html from disk (file://) is not expected to work: browsers do not let a page fetch its own .wasm from there.
  • Embedded. Put the page in an <iframe> of a page on another origin or port. Expected: it loads and runs (click into the frame first so it gets the keyboard).

6. Error display (optional)

  • Delete index.data from the served folder and reload: the page must say something went wrong (the error box with a message) rather than stay on "Loading the engine..." forever.
  • Delete index.wasm and reload: the same.

7. Performance (a note, not a pass or fail)

The software renderer runs on one thread in the tab. Note, for the dev, size and speed profiles if you build them, the frame rate at about 1280x720 on your machine, and whether the tab stays responsive (the page can still be scrolled in DevTools, other tabs are fine). The render size is capped at 1280 pixels wide whatever the window; if that feels too soft or too slow, say which way.

8. Audio (stage 4) PR #181

Everything in this section is unverified: CI has no browser and no sound device (it checks only that the player links Emscripten's OpenAL, that start-up with no AudioContext leaves the audio status failed under node, and that the loader's unlock script works against a mock). Background and the rules: Web build: Audio.

You need a project with sound. lua_project has no audio asset, so the default package is silent and a step below that says "hear" cannot pass with it. Build the package with -DN2_WEB_PROJECT_DIR=/path/to/a/project (it needs project.n2proj and assets/scene.lua) whose scene has: (a) a looping AudioSource with play on awake (music or a tone); (b) a few short AudioSources that a Lua script plays on a key (source:Play(); Lua cannot assign a clip, so the clips are set in the scene data); (c) one spatial source away from the camera; (d) an AudioListener on the camera. A .wav, .ogg, .mp3 or .flac in assets/ works (AudioClip and loaders). Open DevTools (Console) first.

  • Before any input. Load the page and do not click or press anything. Expected: no sound and no errors in the Console (the page is not in a state to play; the "Click to start" button is the first input). Note any warning text.
  • Sound after the first click. Click Click to start. Expected: the looping source (a) is heard within about a second, and the Console shows no error. Note per browser whether it played at once or only after a further click or key press.
  • Sound asked for too early is dropped, not piled up. Only if you can start a sound before the Start click (for example by a project that autostarts, or by editing shell.html to call callMain on load): reload without any input. Expected: nothing is heard and nothing is logged as an error (the log has one Info line about a dropped sound); then click or press a key: sounds started after that play, and the earlier ones do not all burst out at once. Report what you hear: this is the documented "dropped" behaviour (The user-gesture rule).
  • The unlock script. Open DevTools, Elements, Event Listeners, and look at document. Right after the Start click, with no further input, pointerdown, pointerup, keydown and touchend listeners from n2-loader.js are expected to be there: they are added for every context the engine creates, whatever its state, and stay until the first gesture after the context exists (the Start click itself came before the context, so it does not count). Then click the page once (or press a key, or tap) and look again. Expected: those four are gone (the gesture found the context running, or resumed it); a visibilitychange listener stays. On a touch device the listeners stay through a touch that only goes down, and are removed by the lift (pointerup/touchend); they also stay while the context is not running after a gesture's resume() (still pending, refused, or resolved but interrupted), and after the tab comes back visible until the context runs again (the next tap retries; the listeners are removed after the fourth refusal of a gesture's resume, counted since the last time every context was found running, the last successful resume, or the last new context).
  • Hidden tab. Switch to another tab for a few seconds, then come back. Expected: silence while hidden, and the sound continues when visible, with no click needed in Chrome and Firefox; if a browser keeps it silent until you click or press a key, note which browser (the unlock listens again after a refused resume). No errors in the Console.
  • Volume. With a script calling Audio.SetMasterVolume(0.2) (and 1 again) on a key, and a mixer group change if the project has one: the loudness changes. There is no mute button in the page.
  • Looping and short sounds. The loop is seamless (no gap or click at the loop point, a known difference between WebAudio and OpenAL Soft is worth noting if heard). Each key plays its short sound once and it ends (a played-out source returns to the pool: pressing the key 100 times does not go silent).
  • Many simultaneous sources. Trigger far more than 32 sounds at once (32 sources are pre-allocated; more are created on demand, and a mixer group's concurrency limit can refuse sounds, as natively). Expected: no crash, no hang and no error box; note whether the sound stays clean or crackles, and the tab's CPU use.
  • Spatial. Move the camera (or the listener) toward and away from the spatial source (c): it gets louder and quieter and pans left and right. Note whether a very distant sound is ever fully cut off (the web build has no cut-off at the maximum distance: expected not).
  • Escape / end of game. Quit the game with its Quit action. Expected: the sound stops, no error in the Console.
  • Failure path. In a browser (or a profile) with Web Audio blocked or disabled, or with window.AudioContext and webkitAudioContext set to undefined in the Console before clicking Start: the game starts with no sound, shows its picture, does not hang, and there is no error box. The engine should log one warning, Subsystem Audio failed: No WebAudio output ... (by reading the code; CI could not count it, because the engine's log did not appear in the node smoke output, so also report whether any engine log line reaches the Console at all).

Browser notes. Chrome and Edge: a context created inside the Start click should be running at once; a click on the page counts as the gesture. Firefox: same; its autoplay policy can also block audio until a gesture, which the unlock handles; note any "The AudioContext was not allowed to start" console message (it is a warning, not a failure, if sound plays after the first input). Safari (desktop and iOS): the least certain. A context may start suspended or interrupted and may only be resumed inside a gesture handler: if sound never starts, note that, and whether a second click, a key press or a touch start it. iOS also silences Web Audio when the ringer switch is off. Report the browser and its version for each result.

9. Physics (stage 5) PR #184

Everything in this section is unverified: CI runs the engine's physics tests and a stack of 200 boxes under node (the same WebAssembly, no browser), and prints what that costs there. Nothing has run in a browser, so what you note down here is the evidence. Background and the build: Web build: PhysX on the web.

The default package (lua_project) has two stations that use physics. Station 1 (key 1): a blue cube and a red sphere above a static floor, which fall when the game starts (the sphere is offset so it lands on the cube's edge). Station 9 (key 9): a world-space panel with two buttons, one behind a trigger volume (a yellow frame) and one behind a solid block, which a click's ray is tested against. Open DevTools (Console) first.

  • Physics starts. Reload, click Click to start. Expected: no Console line saying Failed to initialize PhysX backend!, Physics will be disabled or Physics backend not available - Rigidbody disabled, and no line starting PhysX with invalid, internal error, out of memory or abort (the web build writes PhysX's own errors and warnings to the engine log, PhysX <kind>: <message> (<file>:<line>)). Copy any PhysX warning or PhysX performance warning line. As in step 8, also report whether any engine log line reaches the Console at all: if none does, this step cannot show a failure and the next ones carry it.
  • Bodies fall and collide. Station 1 starts as the game starts, so reload and look from the click. Expected: the cube and the sphere fall, the sphere hits the cube's edge and rolls off, both come to rest on the floor, and nothing falls through the floor, stays frozen in the air or keeps jittering once at rest. Note roughly how long they take to settle (a few seconds) and whether it looks the same in each browser.
  • Raycast (the pointer ray). Press 9. Click button A: its counter goes up (the trigger volume in front of it never blocks the ray). Click button B: its counter stays at 0 (the solid block in front of it takes the hit). This is the physics query (Raycast with trigger and layer filtering) running through the WebAssembly PhysX.
  • Performance on a stack of N bodies. The default project has no big stack, so make a copy of lua_project and add this to its assets/scene.lua, just before the final for _, gameObject in ipairs(roots) do loop (it builds N boxes in 5 by 5 layers above the floor of station 1; change STACK_N to 50, 200 and 500 for three builds or three edits): 
    local STACK_N = 200
for i = 1, STACK_N do
    local box = GameObject.Create("StackBox" .. i)
    box:CreatePositionable()
    box:GetPositionable():SetPosition(Vector3(((i - 1) % 5) * 1.2 - 2.4, -4.0 + math.floor((i - 1) / 25) * 1.2, (math.floor((i - 1) / 5) % 5) * 1.2 - 2.4))
    box:AddComponent("CubeRenderer"):SetColor(Color.Blue)
    box:AddComponent("BoxCollider"):SetSize(Vector3.One)
    local body = box:AddComponent("Rigidbody")
    body:SetBodyType(BodyType.Dynamic)
    body:SetGravityEnabled(true)
    table.insert(roots, box)
end
    Build the package with -DN2_WEB_PROJECT_DIR=/path/to/the/copy (the speed profile is the one to judge), press 1 and look at the stack. Expected: the boxes settle into a pile on the floor without exploding or sinking. Note, per N and per browser, the frame rate (DevTools, Performance, or the browser's own FPS meter) and whether the tab stays responsive. CI's number for orientation only: under node the 200-box scene costs 0.8 ms per physics step (the dev profile, not a browser, and the renderer is not included); the physics step is not the only cost per frame, since the software renderer draws every box. Say which N first drops under 30 frames per second, and if the stack is much slower than the same scene without bodies (delete the Rigidbody lines to compare), say so: that is the measurement that decides whether the scalar PhysX is fast enough (Scalar math).
  • Memory. With the 500-box stack running, note the tab's memory (the browser's task manager, or DevTools, Memory). Expected: it grows while the scene is built and then stays flat; a steady climb while the boxes lie still is a leak and worth reporting. On a phone or tablet, note whether the tab survives the 500-box scene at all.
  • Quit. Press Escape: the game ends as in step 3, with no error in the Console.

Report: browser and version, the results above, the frame rates per N, and any PhysX lines from the Console.

What to report

  • For each step: pass, fail, or not tried, with the browser and its version.
  • Anything in the error box, and the Console text around it.
  • Load time and frame rate (steps 1, 2 and 7), for step 8 each browser's result with its version, and for step 9 the frame rate per number of boxes and any PhysX line from the Console.
