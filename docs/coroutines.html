Coroutines

Coroutines are C++23 std::generator functions that yield wait objects. Each scene has a CoroutineScheduler that advances them once per frame; every coroutine belongs to a GameObject and stops when that object is deactivated, destroyed or leaves the scene. This page gives the exact frame arithmetic, the stop rules, re-entrancy and error handling.

Writing a coroutine

A coroutine is any function returning std::generator<N2Engine::Scheduling::ICoroutineWait>. Each co_yield hands the scheduler a wait object; the body resumes after the wait is over. Returning from the body (or falling off its end) completes it.

#include <generator>
#include "engine/GameObjectScene.hpp"
#include "engine/scheduling/CoroutineWait.hpp"

using namespace N2Engine::Scheduling;

std::generator<ICoroutineWait> Blink(N2Engine::GameObject *light, int times)
{
    for (int i = 0; i < times; ++i)
    {
        co_yield WaitForSeconds{0.25f};   // scaled time
        light->SetActive(!light->IsActive());
        co_yield WaitForNextFrame{};
    }
}

// In a component:
Coroutine *blink = GetGameObject().StartCoroutine(Blink(lamp.get(), 6));

ICoroutineWait is a type-erased holder with 32 bytes of inline storage; any type with a bool Wait() member that fits converts to it implicitly (see Custom waits).

Source: engine/include/engine/scheduling/CoroutineWait.hpp; engine/include/engine/scheduling/Coroutine.hpp

Starting a coroutine

GameObject::StartCoroutine(std::generator<ICoroutineWait> &&) registers the coroutine with the object's own scene's scheduler (not necessarily the loaded scene) and returns a Scheduling::Coroutine* handle. Starting does not run any of the body.

SituationResult
Object active in hierarchy, in a sceneRegistered; returns the handle.
Object not in a sceneReturns nullptr and logs a warning ("StartCoroutine on '<name>', which isn't in a scene").
Object inactive in hierarchy (itself or an ancestor), or already marked destroyed by ProcessDestroyedReturns nullptr, no log. The generator is discarded without running.
Called from a teardown callback (OnDisable/OnDestroy) of an object that is dying (Destroy pass or scene switch), or from an OnDisable fired by SetActive(false)Returns nullptr, no log: the object is already marked destroyed, or its flag has already changed, so it is not active in hierarchy when the callback runs.

The scheduler also has static overloads taking an explicit const Scene*, and Scene::GetCoroutineScheduler() gives direct access; GameObject::StartCoroutine is the normal entry point.

Guarantee

StartCoroutine on an inactive object returns nullptr; after reactivation, new coroutines can be started.

Tests: InactiveObjectCannotStart, DeactivatingObjectStopsItsCoroutines.

Source: engine/src/gameobject/GameObject.cpp — GameObject::StartCoroutine; engine/src/scheduling/CoroutineScheduler.cpp — CoroutineScheduler::StartCoroutine

When it runs in the frame

Application::Run calls Scene::AdvanceCoroutines() (which is CoroutineScheduler::Update()) once per frame, after Update and before LateUpdate. See Application & frame loop.

Each scheduler update:

  1. Requests a stop for every coroutine whose object is not active in hierarchy (this includes objects marked for destruction), then removes stopped and completed coroutines.
  2. Takes a snapshot of the remaining coroutines.
  3. For each snapshot entry still registered and not stop-requested, advances it once (Coroutine::MoveNext):
    • first advance: runs the body from the start to its first co_yield (or to its end) and holds the yielded wait;
    • later advances: call the held wait's Wait(); if it returns true, keep waiting; if false, drop it and run the body to its next co_yield (or end) in this same advance.
  4. Removes coroutines that completed or were stopped during this update.

The first advance happens on the first scheduler update after StartCoroutine:

Started fromBody first runs
OnAttach, OnFixedUpdate, collision callbacks or OnUpdate of frame FFrame F, in AdvanceCoroutines
OnLateUpdate, teardown callbacks of a RemoveComponent on a live object, or anything after AdvanceCoroutines in frame F (on a dying object, starting fails; see above)Frame F+1
Another coroutine's body (during frame F's update)Frame F+1 (not in the running snapshot)

Wait types and frame arithmetic

Number scheduler updates (frames) from the one where a co_yield happens, frame Y. The yielded wait is first checked at frame Y+1, never in the frame it was yielded.

YieldBody resumes atExact rule
WaitForNextFrame{}Y+1Wait() always returns false.
WaitForFrames{n}, n ≥ 1Y+nEach check increments a counter, then keeps waiting while counter < n.
WaitForFrames{0}Y+1Same as WaitForNextFrame.
WaitForSeconds{s}First frame Y+k where the sum of Time::GetDeltaTime() over frames Y+1 … Y+k is ≥ sScaled time; the delta of frame Y itself is not counted. s ≤ 0 resumes at Y+1. With timeScale 0 the delta is 0, so it never finishes while paused.
WaitForever{}NeverWait() always returns true. The coroutine stays registered until stopped (explicitly or by the stop rules).

Example from the tests, counting the first scheduler update as frame 1: a body that marks, yields WaitForNextFrame, marks, yields WaitForNextFrame, marks, records frames 1, 2, 3. A body that marks, yields WaitForFrames{2}, marks, records 1, 3.

Guarantee

The body runs to its first yield on the first update, then one step per frame for WaitForNextFrame; WaitForFrames(n) resumes n frames after the yield; WaitForever never resumes; WaitForSeconds keeps waiting while no time passes and resumes once the time is up (0 seconds: next frame).

Tests: RunsToFirstYieldThenOneStepPerFrame, WaitForFramesWaitsThatManyFrames, WaitForeverNeverResumes, WaitForSecondsKeepsWaitingUntilTimePasses, WaitForSecondsResumesOnceTimeIsUp.

Note

The tests never advance the engine clock, so WaitForSeconds with a positive duration is only tested as "still waiting"; the accumulation rule above is read from WaitForSeconds::Wait. Before PR #21 every real wait ended the coroutine at its first yield.

Source: engine/src/scheduling/CoroutineWait.cpp; engine/src/scheduling/Coroutine.cpp — Coroutine::MoveNext; engine/src/Time.cpp; tests: CoroutineTests

Custom waits

Any copyable, movable type with a non-const bool Wait() can be yielded. Wait() is called once per scheduler update, starting the frame after the yield; return true to keep waiting and false to resume the body (in the same update). Constraints are checked at compile time: sizeof at most 32 bytes and alignment at most alignof(std::max_align_t).

struct WaitUntilGrounded
{
    const CharacterMotor *motor;               // must outlive the wait
    bool Wait() { return !motor->IsGrounded(); }
};

std::generator<ICoroutineWait> Land(const CharacterMotor *motor)
{
    co_yield WaitUntilGrounded{motor};
    // ... runs on the first frame after the yield where the motor is grounded
}

Source: engine/include/engine/scheduling/CoroutineWait.hpp — ICoroutineWait

Stopping

CallBehaviourReturns
go->StopCoroutine(c)Requests a stop. Outside a scheduler update the coroutine is removed (freed) immediately; during one, removal is deferred to the end of the update. Works whether or not the object is active.false if the object is not in a scene, c is not a live coroutine of this object, or it is already stop-requested; otherwise true
go->StopAllCoroutines()Requests a stop on all of the object's coroutines. Outside an update its entry is erased immediately; during one, at the end of the update. No-op if the object is not in a scene.(void)

A stopped coroutine does not run any further part of its body. Stopping destroys the generator, which destroys its frame and the locals in it.

Guarantee

StopCoroutine stops it and a second call returns false; StopAllCoroutines stops every coroutine of the object; a coroutine that is still waiting (WaitForSeconds) can be stopped explicitly.

Tests: StopCoroutineStopsIt, StopAllCoroutinesStopsEveryOne, WaitForSecondsKeepsWaitingUntilTimePasses.

Warning

The returned Coroutine* is owned by the scheduler and freed when the coroutine completes or is stopped. StopCoroutine only compares the pointer against the object's live coroutines, so a stale pointer normally just returns false; but if a new coroutine on the same object happens to reuse the address, the new one is stopped. Clear stored handles when a coroutine finishes.

Source: engine/src/gameobject/GameObject.cpp — GameObject::StopCoroutine, StopAllCoroutines; engine/src/scheduling/CoroutineScheduler.cpp — StopCoroutine, StopAllCoroutines, Contains, RemoveFinished; tests: CoroutineTests

Automatic stop rules

Coroutines are keyed by their GameObject, as in Unity:

EventWhen the coroutines stop
Object (or an ancestor) deactivatedAt the start of the next scheduler update. Not immediately: see the note below.
Object destroyed (Destroy)In ProcessDestroyed at the end of the frame, right after its components' OnDisable/OnDestroy. Between Destroy() and that point they keep running, since the object is not yet marked.
Object leaves its scene (Scene::RemoveRootGameObject, parented under an object in another scene or none)Immediately, in GameObject::SetScene, on the scene being left.
Object removed with RemoveChildNot stopped: the object becomes a root of the same scene PR #34, so its coroutines keep running. They stop when it leaves the scene, is destroyed, or the scene is switched.
Object released (last shared_ptr dropped) while still pointing at a sceneImmediately, in ~GameObject. The scene is always alive at that point: a scene clears the scene pointer of its objects when it is cleared or destroyed.
Scene switch (Scene::Clear)During the teardown pass for each object in the root hierarchy, which includes children removed with RemoveChild.
Scene destroyedIts scheduler is destroyed with it.
Component that started it removedNot stopped: coroutines belong to the GameObject, not to a component.

Reactivating an object does not restart coroutines that were stopped by deactivation.

Guarantee

Deactivating, destroying or removing an object from the scene stops its coroutines, and reactivation does not resume them. A child removed with RemoveChild stays in the scene as a root, so its coroutines keep running until it leaves the scene; after that, releasing it leaves the scheduler nothing to read PR #34. No object outlives its scene with a pointer to the freed scheduler (see Scenes).

Tests: DeactivatingObjectStopsItsCoroutines, DestroyedObjectsCoroutinesStop, ObjectLeavingSceneStopsItsCoroutines, RemovedChildKeepsItsCoroutinesUntilItLeavesTheScene.

Note

Deactivation is only checked at the start of each scheduler update. Two consequences follow from the code (not covered by tests): an object deactivated and reactivated within the same frame, before AdvanceCoroutines, keeps its coroutines; and if a coroutine body deactivates an object during an update, that object's other coroutines in the same snapshot still advance once in that update and are stopped at the next one. Unity stops them at once.

Source: engine/src/scheduling/CoroutineScheduler.cpp — CoroutineScheduler::Update; engine/src/gameobject/GameObject.cpp — GameObject::SetScene, GameObject::~GameObject; engine/src/sceneManagement/Scene.cpp — CallOnDestroyForGameObject, Scene::Clear; tests: CoroutineTests

Re-entrancy

A coroutine body may call scheduler functions while it runs:

From inside a bodyResult
Stop itself (StopCoroutine(self))Takes effect at the end of this update; the rest of the current step (up to the next co_yield) still runs, nothing after it does. The coroutine is never freed while its own body is executing.
Stop another coroutineDeferred removal; if the other one comes later in the snapshot, it is skipped this update.
StopAllCoroutinesAll marked stopped; the entry is erased at the end of the update.
Start a coroutineRegistered now; its body first runs on the next update.
Scene::AdvanceCoroutines() (directly or via something that ticks the scene)Ignored: the nested Update returns immediately.

Guarantee

Self-stop runs the rest of the current step only; a coroutine started from a body runs from the next frame; a nested scheduler update is ignored and other coroutines are unaffected.

Tests: CoroutineCanStopItself, CoroutineCanStartAnother, TickingTheSceneFromACoroutineIsIgnored.

std::generator<ICoroutineWait> Once(N2Engine::GameObject *go, Coroutine **self)
{
    co_yield WaitForNextFrame{};
    go->StopCoroutine(*self);   // safe: removal is deferred to the end of this update
    DoTheThing();               // still runs (same step)
    co_yield WaitForNextFrame{};
    NeverRuns();
}

Source: engine/src/scheduling/CoroutineScheduler.cpp — Update (_updating flag, snapshot), StopCoroutine, StopAllCoroutines; tests: CoroutineTests

Exceptions

An exception escaping a coroutine body is caught by the scheduler. It is logged with Logger::Error ("Coroutine threw and was stopped: <what()>", or "Coroutine threw a non-standard exception and was stopped"), the coroutine is stopped, and the remaining coroutines in the update continue. The exception does not reach the caller of AdvanceCoroutines. This differs from component callbacks, whose exceptions propagate (see component callbacks).

Guarantee

A throwing coroutine is stopped and the others continue.

Test: ThrowingCoroutineIsStoppedAndOthersContinue.

An exception from a custom wait's Wait() is handled the same way, since it is called from Coroutine::MoveNext inside the same try.

Source: engine/src/scheduling/CoroutineScheduler.cpp — CoroutineScheduler::AdvanceCoroutine; tests: ThrowingCoroutineIsStoppedAndOthersContinue

Lifetimes and dangling references

  • Pass arguments to a coroutine function by value or by pointer to something that outlives it. std::generator keeps by-value parameters in its frame; reference parameters bind to the caller's objects, which are usually gone by the first resume.
  • The owning GameObject is safe to reference through a raw pointer for the coroutine's whole life: every path that frees or detaches the object stops its coroutines first.
  • A component pointer (including this in a lambda or member coroutine) is not protected: removing the component does not stop coroutines on its object. Stop them in the component's OnDestroy, or check a lifetime token (Component::GetLifetimeToken, PR #29) before use.
  • Other objects referenced by the body can be destroyed independently; hold a std::weak_ptr<GameObject> and check IsDestroyed().
void Spawner::OnDestroy()
{
    // Coroutines belong to the GameObject; stop the ones that use this component
    if (_routine)
    {
        GetGameObject().StopCoroutine(_routine);
        _routine = nullptr;
    }
}

Source: engine/src/gameobject/GameObject.cpp — RemoveComponent, SetScene, ~GameObject; engine/include/engine/scheduling/CoroutineScheduler.hpp

Lua

Coroutines are C++ only. No scheduler or wait type is bound to Lua, and the Lua runtime opens only the base, math, string and table libraries (package is no longer opened PR #34), so Lua's own coroutine library is not available to scripts either. Lua scripts that need timed behaviour have to count time in OnUpdate. See Lua scripting.

Source: engine/src/scripting/LuaRuntime.cpp — open_libraries; engine/src/scripting/bindings/ (no coroutine bindings)
