Math & SIMD

The math static library: vector, quaternion and matrix types, scalar helpers, random numbers and UUIDs, plus the runtime SIMD dispatch that picks scalar or SSE/AVX implementations. This page covers conventions, what the SIMD paths guarantee relative to scalar code, and the known flaws.

Build requirement: AVX PR #27

math/CMakeLists.txt compiles the library with PUBLIC /arch:AVX on MSVC and -msse2 -msse4.1 -mavx elsewhere. Because the option is PUBLIC, every target linking math (the engine, games, tests) is compiled for AVX, so the whole binary requires an AVX-capable CPU. The lower SIMD tiers select between algorithms; they are not a fallback for older hardware.

Design decision: SIMD tiers are an algorithm choice, not a compatibility fallback

The build targets AVX once, for every target, instead of producing per-CPU binaries or per-function target attributes. The compiler may then use AVX encodings anywhere, so the binary needs an AVX CPU whatever tier is selected. The runtime tiers exist so that each implementation (scalar, SSE2, SSE4.1, AVX) can be selected, tested against scalar in the same process, and benchmarked. That is why the default is scalar, why SetSIMDLevel can switch in either direction, and why every tier has a written contract: bit-exact for the rounding, sign and min/max operations, within a relative 1e-5 for the rest (see Correctness relative to scalar). Supporting pre-AVX CPUs would mean dropping the PUBLIC flag and isolating the AVX code, not selecting a lower tier.

MSVC never defines __SSE4_1__, even with /arch:AVX. CpuInfo.hpp therefore defines N2_MATH_SSE41 when either __SSE4_1__ or __AVX__ is defined, and the dispatched types compile their SSE4.1 implementations under that macro. Before PR #27 the SSE4.1 code was dead on MSVC.

SIMD dispatch tiers PR #27

Vector3, Vector4 PR #30, Quaternion, Matrix<float,4,4> and Matrix<float,3,3> route their operations through static function pointers. The tier is a process-wide setting:

enum class SIMDLevel { Scalar, SSE2, SSE41, AVX }; // lowest to highest

SIMDLevel DetectSIMDLevel();               // highest tier this CPU and OS support
SIMDLevel ClampSIMDLevel(SIMDLevel level); // min(level, DetectSIMDLevel())
void SetSIMDLevel(SIMDLevel level);        // switch all five types (clamped)
void InitializeSIMD();                     // SetSIMDLevel(DetectSIMDLevel()), with a report on stdout
  • Default is scalar. Every function pointer is initialised to its scalar implementation, so all math works before any initialisation. (Before PR #24 the matrix pointers were null until InitializeSIMD, and early matrix math crashed.)
  • Application startup. Application::Init calls Math::InitializeSIMD() early, right after Lua initialisation, not first thing (anything that runs before it uses scalar code), so a running game uses the highest supported tier. Hosts and tests that never call Application::Init stay on scalar unless they call it themselves.
  • Re-callable. SetSIMDLevel can be called any number of times, in either direction. Each type resets every pointer to scalar first, then overrides what the chosen tier accelerates, so switching down fully restores the lower tier. It replaces the earlier one-way per-type InitializeSIMD and its initialized flag.
  • Clamped. A tier above what the CPU supports is silently lowered to the detected tier. Tests use DetectSIMDLevel to skip tiers the CPU cannot run, so they never silently test a lower tier.
  • Not thread-safe. The tier is a set of plain static pointers. Change it only while no other thread is doing math.

CPU detection

DetectSIMDLevel runs CPUID once (a function-local static) and caches the result:

  • AVX requires the CPUID AVX bit and OSXSAVE and an XGETBV check that the OS saves the YMM state (XCR0 & 0x6 == 0x6). XGETBV is only executed when OSXSAVE is reported, since it is undefined otherwise. AVX2 additionally requires AVX.
  • The tier is AVX if AVX and SSE4.1 are available, else SSE4.1, else SSE2, else Scalar.

Correctness relative to scalar PR #27

  • Round follows std::round at every tier: halfway cases round away from zero (2.5 → 3, -2.5 → -3), the input's sign is kept (Round(-0.3) is -0), and NaN and ±inf pass through. The SSE4.1 version truncates and then steps away from zero, because the hardware's round-to-nearest mode rounds halves to even.
  • Min/Max match std::min(a, b) = (b < a) ? b : a and std::max(a, b) = (a < b) ? b : a, including which operand wins for NaN and for ±0.
  • Normalize uses a real square root and divide at every tier (no 12-bit rsqrt approximation), with the same near-zero rule as scalar: a Vector3 or Vector4 shorter than Constants::EPSILON (1e-5) normalises to Zero; a quaternion shorter than 1e-6 normalises to Identity.

Guarantee PR #27

Switching the SIMD tier never changes the result of Vector3 Floor, Ceil, Round, Abs, Min or Max, or of Vector4 Floor, Ceil, Round, Abs, Negate, Min, Max or Clamp PR #30, by even one bit, and changes every other dispatched Vector3, Vector4, Quaternion and float matrix operation by at most a relative 1e-5 (SimdDispatchTest, all tiers the CPU supports).

Vector3

  • Constructors set the padding lane w to 0. Copies copy all four lanes. w is public but is not part of the value: no dispatched result depends on it.
  • operator== is approximate: each component within an absolute Constants::EPSILON (1e-5).
  • Division by a scalar whose magnitude is below 1e-5 returns Vector3::Zero instead of infinities, at every tier.
  • Sign() returns -1, 0 or +1 per component. AngleTo returns 0 when either vector has zero length. Project onto a zero vector returns zero.
  • Direction constants: Up (0,1,0), Down, Right (1,0,0), Left, Forward (0,0,1), Back (0,0,-1), plus Zero and One.
  • Implicitly converts to and from VectorN<float, 3>.

Source: math/include/math/Vector3.hpp, math/src/math/Vector3.cpp

Batch operations

Vector3::AddBatch, DotBatch and NormalizeBatch process two vectors per 256-bit register at the AVX tier, with a per-element tail loop for an odd count. ScalarMulBatch works differently at the AVX tier: it gathers 8 vectors per iteration into separate x, y and z registers (structure of arrays), multiplies them and scatters them back, with a per-element tail loop for the last count % 8. At lower tiers they loop over the dispatched single operation. SubBatch, CrossBatch and TransformBatch always loop. The batch functions read the selected tier (simd_level) rather than running CPUID on every call. NormalizeBatch turns near-zero vectors into Zero, like the scalar version (it used to produce NaN, and divided the second vector of each pair by the first one's length).

std::vector<Vector3> normals = LoadNormals();
Vector3::NormalizeBatch(normals.data(), normals.size()); // AVX pairs at the AVX tier

std::vector<float> dots(a.size());
Vector3::DotBatch(a.data(), b.data(), dots.data(), a.size()); // caller sizes the output

Vector4, Vector2 and VectorN

Warning: Vector4 is (w, x, y, z)

Vector4(float w, float x, float y, float z) takes w first, stores it in lane 0, and converts to VectorN<float, 4> as {w, x, y, z}. Vector4(1, 2, 3, 4) has x == 2.

  • Vector4 is dispatched like Vector3 PR #30. It has private scalar, SSE2 and SSE4.1 implementations behind static function pointers that default to scalar, so it runs scalar code until InitializeSIMD or Math::SetSIMDLevel is called (before PR #30 it always used SIMD chosen at compile time). Vector4::SetSIMDLevel clamps the tier like the other types. Batch operations use AVX only at the AVX tier. See the tier table.
  • Vector2 is plain scalar code for single operations. Its batch operations use AVX whenever the build defines __AVX__ (which it always does), independent of the selected tier.
  • VectorN is a generic fixed-size vector. Initialiser-list or iterator-range construction with the wrong number of elements throws std::invalid_argument. Normalized() of an exactly zero vector returns zero. operator== is exact, unlike Vector2/3/4, which compare within 1e-5.

Guarantee: Vector4 agrees with scalar at every tier PR #30

  • Dot order. The scalar dot product sums (w+x)+(y+z), the same order as dpps, the SSE2 reduction and the AVX horizontal add, so Dot, Length, Normalize and the dot-based batch results are bit-identical across tiers.
  • Normalize is a full-precision sqrt and divide (it used _mm_rsqrt_ps, about 12 bits). A vector shorter than 1e-5 becomes Zero. The AVX NormalizeBatch masks only lanes where length < EPSILON (an ordered compare), so a NaN input stays NaN, as in scalar code; it used to become zero.
  • Round matches std::round (halves away from zero, sign of zero kept, NaN and ±inf pass through); it used to round halves to even under SSE4.1.
  • Min/Max match std::min/std::max for NaN and ±0 (operands passed as (b, a)). Unary minus multiplies by -1, so -(+0) is -0.
  • Same code on every compiler. The SSE4.1 and AVX paths are guarded by N2_MATH_SSE41 and __AVX__, like the other types. They used __SSE4_1__, which MSVC never defines, so MSVC and GCC/Clang builds took different paths.

Tests: Vector4KnownValues, Vector4Operations, Vector4ExactOperations, Vector4BatchOperations.

Note

Every Vector4 operation is now an indirect call that cannot be inlined. Today's callers are Lua, Camera and serialization; this only matters if Vector4 moves into hot loops. The public API is unchanged: Dot, Length and Normalize stay single non-static members, because the Lua bindings take their addresses.

Warning: raw-pointer batch APIs and Color

The raw-pointer Vector4 batch functions (AddBatch(const Vector4*, ...) and the others) accept a Common::Color* implicitly, because Color derives from Vector4. sizeof(Color) is 48 bytes (it has reference members), so the batch would walk it with the wrong stride. Pass only contiguous Vector4 arrays. Nothing outside the math library calls these today.

Quaternion conventions

  • Component order. The 4-argument constructor is Quaternion(w, x, y, z); the default constructor is the identity (1, 0, 0, 0). Read components with GetW/GetX/GetY/GetZ.
  • Angles are radians. FromAxisAngle(axis, angle) does not normalise axis; pass a unit axis.
  • Multiplication is the Hamilton product. Rotation application is v' = q v q* (Rotate, also q * v), so (a * b) * v rotates by b first, then by a. Multiplication is associative and not commutative.
  • Handedness of rotation. A positive angle rotates counter-clockwise looking down the axis towards the origin: 90° about Y takes (1,0,0) to (0,0,-1); about X takes (0,1,0) to (0,0,1); about Z takes (1,0,0) to (0,1,0).
  • Rotate assumes a unit quaternion; it does not normalise.
  • Euler angles. FromEulerAngles(pitch, yaw, roll) builds the rotation that applies pitch about X first, then yaw about Y, then roll about Z (q = qz(roll) · qy(yaw) · qx(pitch)). ToEulerAngles() returns (pitch, yaw, roll) in the same convention, with yaw clamped to ±π/2 at the singularity. The round trip reproduces the same rotation (possibly as -q).
  • ToMatrix() returns a 4×4 rotation matrix for column vectors (M · v equals q.Rotate(v)).
  • LookRotation(forward, up) builds right = up × forward, then a re-orthogonalised up, and converts that basis to a quaternion: the result maps local +Z onto forward and local +Y towards up. That is the object convention; a camera looks down its local −Z, so Camera::LookAt passes the opposite direction (see Object forward and camera view direction). LookRotation itself does not handle a zero forward or an up parallel to it: the basis degenerates and the result is not a unit quaternion. The quaternion tests only check that the result is normalised (forward +Z and +X with up +Y); its direction is checked through the camera by CameraLookAtTest PR #TBD.
  • Slerp takes the shorter path (negating b when the dot product is negative) and falls back to Lerp when the dot product exceeds 0.9995. Lerp normalises its result. Neither clamps t.
  • Inverse() returns Identity when the squared length is below 1e-6; otherwise conjugate divided by squared length. operator/ does not check for zero. operator== compares components within 1e-6, so q and -q (the same rotation) compare unequal.
using namespace N2Engine::Math;
const Quaternion yaw90 = Quaternion::FromAxisAngle(Vector3::Up, Constants::HALF_PI);
const Quaternion pitch = Quaternion::FromAxisAngle(Vector3::Right, 0.3f);

const Quaternion combined = yaw90 * pitch;              // pitch first, then yaw
const Vector3 v = combined * Vector3::Forward;          // == yaw90.Rotate(pitch.Rotate(Forward))
const Vector3 r = yaw90.Rotate(Vector3(1.0f, 0.0f, 0.0f)); // (0, 0, -1)

Matrix layout and conventions

  • Row-major storage. operator()(row, col) is data[row * N + col], and Data() returns that row-major array. The OpenGL renderer uploads it with transpose = GL_TRUE.
  • Column vectors. Translation lives in column 3 (Translation sets (0,3), (1,3), (2,3)), and TransformPoint computes M · (x, y, z, 1). In a product A * B, B is applied to the point first, so T * R * S scales, then rotates, then translates.
  • TransformPoint divides by the resulting w when it is non-zero (so projective matrices work) and returns the undivided x, y, z when w is 0.
  • RotationX/Y/Z(angle) take radians and follow the same right-hand rule as Quaternion.
  • inverse() of a 4×4 matrix throws std::runtime_error("Matrix is singular and cannot be inverted") when |det| < 1e-7. Inverse and determinant always use the scalar implementation.
  • operator== on matrices is exact (every element compared with !=), unlike the vector types.
  • Constructing from an initialiser list of the wrong size throws std::invalid_argument.
  • The 3×3 specialisation offers arithmetic, transpose and RotationX/Y/Z; it has no inverse or determinant.
using Matrix4 = N2Engine::Math::Matrix<float, 4, 4>;
const Matrix4 model = Matrix4::Translation(position)
                    * Matrix4::RotationY(angle)
                    * Matrix4::Scale(2.0f, 2.0f, 2.0f);
const Vector3 world = model.TransformPoint(localPoint); // scale, then rotate, then translate

Object forward and camera view direction PR #TBD

Two conventions meet here, and they point opposite ways along local Z:

  • Objects face +Z. Vector3::Forward is (0, 0, 1), and Positionable::GetForward() is GetRotation() * Vector3::Forward. Quaternion::LookRotation(direction, up) turns local +Z onto direction, so it is the rotation that makes an object face direction.
  • The camera looks down −Z. The view matrix is inverse(rotation) · Translation(−position) and the perspective projection has (3, 2) = −1, the OpenGL convention: a point is in front of the camera when its view-space z is negative, and the screen's right and up are the camera's local +X and +Y. With the identity rotation the camera looks along world −Z.
  • Camera::LookAt(target, up) points the camera's −Z at the target. It calls LookRotation(position − target, up): the camera's +Z (its back) points away from the target, so its view direction points at it, and up is the top of the screen. A camera at (0, 0, 5) looking at the origin keeps the identity rotation and sees the origin at view z = −5, in the centre of the screen. Before this fix it called LookRotation(target − position, up), which turned the camera 180° and put the target behind it (#57).
  • Degenerate cases. A target at the camera's own position has no direction: LookAt keeps the current rotation. An up that is zero or parallel to the view direction leaves the right axis undefined: LookAt then uses world up (0, 1, 0), or world +Z (0, 0, 1) when the view is vertical. Neither case produces NaNs or a non-unit rotation. (Before, both fed a degenerate basis to LookRotation and stored a non-unit quaternion.)
  • Camera::GetForward(), GetUp() and GetRight() are the camera's rotation applied to −Z, +Y and +X: the view direction and the screen's up and right, in world space. GetForward is deliberately not rotation * Vector3::Forward, which would be the camera's back. The screen-centre ray of ScreenPointToRay points along GetForward(). Lua has the same three methods, and Camera:LookAt calls the same function.
  • Camera::SetRotation takes the rotation as is: with the identity, the camera looks down world −Z. The sample fly cameras (CameraController in test_project and lua_project) build the rotation with Quaternion::FromEulerAngles(pitch, yaw, 0) and move along rotation * (x, 0, −y), so they already follow this convention.
Camera camera;
camera.SetPosition({0.0f, 0.0f, 5.0f});
camera.LookAt({0.0f, 0.0f, 0.0f});               // the rotation stays the identity
camera.GetForward();                              // (0, 0, -1): towards the origin
camera.GetViewMatrix().TransformPoint({0, 0, 0}); // (0, 0, -5): in front of the eye

// An object faces +Z instead, so it uses LookRotation directly:
positionable->SetRotation(Quaternion::LookRotation(target - position, Vector3::Up));

Design decision: the camera looks down −Z while objects face +Z PR #TBD

The engine's objects follow Unity: Vector3::Forward is +Z, Positionable::GetForward is the rotation applied to +Z, and LookRotation turns +Z onto a direction. The camera's view and projection matrices follow OpenGL instead: the eye looks down its local −Z, and the perspective projection maps view z from −near to −far onto NDC z from −1 to 1. Both renderers, ScreenPointToRay, frustum culling and the transparent queue's depth sort are built on the OpenGL form, so making the camera look down +Z would mean a different projection, a mirrored image (or a handedness flip) and changes to all of those. The camera keeps its own position and rotation rather than a Positionable, so nothing forces the two conventions to agree.

LookAt is where they meet. It reconciles them by aiming the camera's back away from the target, LookRotation(position − target, up), rather than changing LookRotation (which is right for objects) or the view matrix. Camera::GetForward returns the real view direction, the rotation applied to −Z, so callers never have to remember the flip. Decided on #3 (decision 14); fixes #57.

Random

  • One process-wide std::mt19937, seeded once from std::random_device (GetRandomEngine()). There is no API to seed it, so sequences are not reproducible.
  • RandomFloat() uses uniform_real_distribution<float>(0, 1). That is nominally [0, 1), but the float distribution can round up and return exactly 1.0f (a known std::generate_canonical issue in common standard libraries), so treat the range as [0, 1], as the header comment says. RandomRange(min, max) scales it. RandomInt(min, max) is inclusive on both ends.
  • RandomOnUnitCircle() returns a unit Vector2; RandomInUnitCircle() is uniform over the disc (radius is sqrt of a uniform value).
  • The shared engine and the static distribution are not synchronised; do not call these from several threads at once.

Source: math/include/math/Random.hpp, math/src/math/Random.cpp

UUID

  • UUID() and UUID::ZERO are all zero bytes.
  • UUID::Random() produces an RFC 4122 version 4 UUID (version nibble 4, variant 10x) from a std::mt19937_64 freshly seeded from std::random_device on each call.
  • UUID::GenerateNameBased(namespaceUUID, name) produces a version 5 UUID: SHA-1 (TinySHA1) of the namespace's 16 bytes followed by the name's bytes, truncated to 16 bytes, with version and variant set. The same inputs always give the same UUID.
  • ToString() gives lowercase 8-4-4-4-12 hex. FromString requires exactly 36 characters with dashes at positions 8, 13, 18 and 23, accepts upper or lower case hex, and returns std::nullopt for anything else.
  • operator== compares bytes; GetBytes() exposes them for hashing.
const auto id = N2Engine::Math::UUID::Random();
const std::string text = id.ToString();               // e.g. "3f2b8c1e-...-..."
const auto parsed = N2Engine::Math::UUID::FromString(text);
assert(parsed && *parsed == id);

Source: math/include/math/UUID.hpp, math/src/math/UUID.cpp. UUIDs identify GameObjects and components in saved scenes; see Serialization.

Known flaws and open questions

Guarantee: Vector2 NormalizeBatch precision PR #39

Vector2::NormalizeBatch (math/src/math/Vector2.cpp) matches Vector2::Normalized to rounding, like the Vector3/Vector4 batches. Its AVX path (four vectors per iteration, compiled in when __AVX__ is defined; Vector2 has no runtime dispatch) adds each x² and y² within its own 128-bit half, divides by a real _mm256_sqrt_ps, and zeroes vectors whose length is below EPSILON with an ordered compare, so a NaN vector stays NaN as it does in Normalized. The scalar tail and the non-AVX build call Normalized.

Before, the AVX path used the 12-bit _mm256_rsqrt_ps approximation and broadcast the lengths to the wrong lanes: all four vectors of a block were scaled by vector 0's length, and the near-zero mask was in the wrong lanes too. The tail used Normalize, which turns NaN into zero.

Tests: Vector2BatchTest.NormalizeBatchMatchesNormalized, Vector2BatchTest.NormalizeBatchZeroAndNaN, Vector2BatchTest.NormalizeBatchHandlesShortCounts.

Note

InitializeSIMD prints its report with std::cout, not the engine logger. Its "compiler support" lines test __SSE4_1__ and __SSE2__, neither of which MSVC defines, so on MSVC both print "No" even though the SSE2 code is compiled in and the SSE4.1 code is compiled in through N2_MATH_SSE41. The "Math SIMD level" line is the one that reflects what runs.
