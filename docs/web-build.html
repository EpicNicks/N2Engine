Web build

N2Engine can be configured with Emscripten to build for WebAssembly. This is stage 0 of issue #155 PR #163: the toolchain, the build profiles, a size report and a CI job that builds the math and text libraries and runs their unit tests under node. There is no web player yet; this page says what exists, how to build it, and what does not.

Goal and decisions already taken

The aim is a web player (not the editor) whose output is plain static files that any host can serve. These decisions were taken by the maintainer on 2026-10-15 in issue #155 and this work builds on them:

  • Player only. The software renderer comes first, WebGPU later; WebGL2 is not a target.
  • The baseline build is single-threaded and needs no special response headers, in particular no cross-origin isolation (COOP/COEP). A threaded build is a possible later second file.
  • The profiles dev, size and speed are part of the build from the start, not added later.
  • The output must not depend on the host's MIME types or compression.

Toolchain and pinned version

The toolchain is Emscripten, used through CMake's own Emscripten toolchain file (emcmake cmake). CMake detects it (EMSCRIPTEN is set, or CMAKE_SYSTEM_NAME is Emscripten) and the root CMakeLists.txt sets the derived variable N2ENGINE_PLATFORM_WEB to ON, includes cmake/N2EngineWeb.cmake, and compiles every target with -DN2ENGINE_PLATFORM_WEB=1. On every other configuration the variable is OFF and nothing else changes: no native option, target, source list or flag differs.

The version is pinned to Emscripten 4.0.10 (the EMSCRIPTEN_VERSION variable in the CI job), installed with the official emsdk and not through a third-party action. Pinning keeps an upstream release from changing the build with no change in this repository; the 4.0 series was chosen for its recent LLVM and libc++ (the engine is C++23). Whether 4.0.10 is new enough is proven only by the CI job, see Unverified. Changing the pin means changing it in .github/workflows/tests.yml and here.

Building locally

Install and activate the pinned SDK once (Linux or macOS shell; on Windows use emsdk.bat and emsdk_env.bat), then configure with emcmake and build with CMake as usual. You need CMake 3.25 or newer and Ninja (or another generator).

git clone https://github.com/emscripten-core/emsdk.git
cd emsdk
./emsdk install 4.0.10
./emsdk activate 4.0.10
source ./emsdk_env.sh          # puts emcc, emcmake and the SDK's node on PATH (per shell)

cd /path/to/N2Engine
emcmake cmake -S . -B build-web -G Ninja -DCMAKE_BUILD_TYPE=Release -DN2ENGINE_WEB_PROFILE=dev
cmake --build build-web --target math_tests text_tests
ctest --test-dir build-web --output-on-failure
bash scripts/web-size-report.sh build-web/bin

Each test is built as build-web/bin/<name>.js plus a .wasm. CMake's Emscripten toolchain sets CMAKE_CROSSCOMPILING_EMULATOR to node, so ctest runs them with node; you can also run node build-web/bin/math_tests.js directly. A configure that is not under emcmake is a native configure and is unchanged.

The reduced target set and what is excluded

At stage 0 the web configuration builds the math and text libraries, their test executables (math_tests, text_tests), googletest (fetched), and the web-size-report target. Everything else is not added to the build when N2ENGINE_PLATFORM_WEB is ON, and the configure prints a Web: status line saying so.

ExcludedWhy
engine/ (the engine core)It links the renderer (GLFW, OpenGL, Vulkan, software) and OpenAL unconditionally and uses std::filesystem, std::thread and std::mutex in many files. Building it needs source changes (a window and input backend, a single-threaded fallback, a virtual filesystem decision) that are outside stage 0, which allows only small #ifdef guards. It is stage 1.
renderer/ (window, GLFW, OpenGL, Vulkan, software renderer)GLFW and OpenGL context creation do not exist on the web as they do natively, and the software renderer's RenderThread needs threads. The Vulkan renderer is forced off (N2ENGINE_RENDERER_VULKAN is set OFF) because there is no Vulkan in a browser.
OpenAL (fetched with FetchContent)The web uses Emscripten's own OpenAL on top of WebAudio, a later stage. The native fetch is skipped.
PhysXN2ENGINE_USE_PHYSX is set OFF: the downloaded binaries are native, and PhysX on WebAssembly is tracked in #156.
FreeType (N2ENGINE_TEXT_FREETYPE)It is fetched at configure time. Asking for it on the web gives a warning and the option is set OFF; the text library uses stb_truetype only.
lua and assetimport/Plain C and C++ that are expected to compile, but nothing built at stage 0 uses them (the engine is excluded), and their tests read files. They are the first candidates for stage 1.
editor-server/ (the editor host, raw sockets, Mbed TLS), test_project/, lua_project/The editor host is not part of a player; the two projects need the engine and a window.

Two source-level changes were needed. The math target takes no -msse4.1/-mavx flags on the web (Emscripten reports its processor as x86, but its compiler defines no x86 macros), so CpuInfo.hpp selects the scalar implementations, the same ones used on any architecture without a SIMD tier. And three tests in tests/math/UUIDRandomTests.cpp that start std::threads skip themselves in a build without threads (GTEST_SKIP under __EMSCRIPTEN__ without __EMSCRIPTEN_PTHREADS__); the single-threaded generation test still runs.

Design decision: stage 0 builds math and text only PR #163

The engine core cannot be built for the web without changing its sources (see the table above), and stage 0 is limited to the toolchain, the profiles, the size report and the CI leg. Building the two CPU-only libraries proves the toolchain, the flags and the node test runner end to end, with nothing that needs a decision about windows, threads or files. Each later stage adds targets by removing a row from the exclusion table.

Build profiles

N2ENGINE_WEB_PROFILE is a cache variable with the values dev (the default), size and speed; anything else is a configure error. It exists only in web configurations. The flags are applied to every target (compile and link) in cmake/N2EngineWeb.cmake, because LTO needs every object built with it. Every profile also links with -sALLOW_MEMORY_GROWTH=1 (Emscripten's default heap is a fixed 16 MB) and -sSTACK_SIZE=1048576 (its default stack is 64 KB). The unit tests add -sEXIT_RUNTIME=1 so node exits with the test result.

ProfileFlagsMeant for
dev-O1 -g, no LTOFast builds and links, DWARF debug info. The only profile built and tested in CI.
size-Oz -flto, link -Oz -flto -sASSERTIONS=0; no -g, so no debug info or names section; emcc runs wasm-opt -Oz at this levelThe smallest download. Exceptions and RTTI stay on: the engine is not known to build without them, so trimming them is a later, measured step.
speed-O3 -flto, link -O3 -flto -sASSERTIONS=0The fastest code.

The Emscripten defaults for C++ exceptions apply (a thrown exception that nothing in the wasm can catch is not caught): the stage 0 libraries throw only from a few Matrix argument checks and no test depends on catching one.

Output contract

This is the contract every later stage keeps; stage 0 produces test executables only, but the build is set up for it:

  • A folder of static files: .html, .js, .wasm and later an asset pack. No server logic.
  • Relative URLs only, so the folder works from any path or subdomain.
  • No special response headers. The baseline is single-threaded and does not use SharedArrayBuffer, so it does not need cross-origin isolation and can run in an iframe on another site.
  • MIME-agnostic and compression-agnostic: it must still load when a host serves .wasm with a wrong type (the loader falls back from streaming instantiation to an ArrayBuffer) and when the host does not compress. Precompressed .br/.gz copies are an addition for the size profile, never a requirement. Not implemented yet: stage 3.

The size report and budgets

scripts/web-size-report.sh [dir] (default build/bin) lists every .wasm and .js file under the directory with its raw and gzip -9 size, prints a table, and appends it to the GitHub job summary when GITHUB_STEP_SUMMARY is set. It fails (exit 1) only for a budget that is set and exceeded, and with exit 1 if it finds no files. Budgets are in bytes and come from environment variables, or from CMake cache variables when you use the web-size-report target:

Variable (environment and CMake)Budget for
N2ENGINE_WEB_BUDGET_WASM_GZIPThe gzip size of any one .wasm file.
N2ENGINE_WEB_BUDGET_TOTAL_GZIPThe gzip size of all .wasm and .js files together.
 
N2ENGINE_WEB_BUDGET_WASM_GZIP=1500000 bash scripts/web-size-report.sh build-web/bin
cmake -S . -B build-web -DN2ENGINE_WEB_BUDGET_TOTAL_GZIP=2000000 && cmake --build build-web --target web-size-report

No budget is set at stage 0 (the CI step only reports). Brotli sizes and time to first frame are not measured yet.

CI

The job web (Emscripten, dev profile, node tests) in .github/workflows/tests.yml PR #163 installs emsdk 4.0.10, configures the dev profile with emcmake, configures (only) the size and speed profiles without tests, builds math_tests and text_tests, runs ctest (node runs each test), and reports the artifact sizes in the job summary. It is not a required check; it follows the other build jobs: needs: changes and the same docs-only if, ccache is not used, and it uploads nothing. See Testing & CI.

What is not done yet

The stages are from issue #155; only stage 0 exists.

  1. Stage 0 (this page): toolchain, profiles, size report, CI leg for math and text.
  2. Stage 1: the headless engine core in WebAssembly (scene loading, Lua, software-renderer goldens under node). Needs the engine's threads, filesystem and renderer dependencies sorted out.
  3. Stage 2: the software renderer on a canvas, with window and input. The first playable web build.
  4. Stage 3: asset packing and async loading, the shell page, size and load-time budgets enforced in CI, precompressed outputs.
  5. Stage 4: audio through Emscripten's OpenAL.
  6. Stage 5: PhysX (or another physics) on WebAssembly.
  7. Stage 6: the optional threaded build, chosen by crossOriginIsolated.
  8. Stage 7: the WebGPU backend.

Unverified

Open question

Nothing here was built locally; the first CI run of the web job is the only proof. Not verified: that Emscripten 4.0.10 builds the C++23 code of math, text and googletest; that the toolchain's emulator runs the tests under node and returns their exit code; that googletest links without pthreads; that the size and speed flags work (only dev is built, the others are configured); and whether the engine core can be added with small guards (it is believed not).
