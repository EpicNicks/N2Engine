Web build

N2Engine can be configured with Emscripten to build for WebAssembly. This is stages 0 to 2 of issue #155: the toolchain, the build profiles and a size report PR #163, the headless engine core (scene, components, Lua, serialization, the software renderer) built for WebAssembly and tested under node with a single-threaded fallback PR #167, and the first playable web build: a player that draws the software renderer on a canvas, reads keyboard and mouse from the page and is packaged as plain static files PR #170. There is no audio, physics or touch yet; this page says what exists, how to build and host it, and what does not. What only a browser can show is in the manual browser checklist.

Goal and decisions already taken

The aim is a web player (not the editor) whose output is plain static files that any host can serve. These decisions were taken by the maintainer on 2026-10-15 in issue #155 and this work builds on them:

  • Player only. The software renderer comes first, WebGPU later; WebGL2 is not a target.
  • The baseline build is single-threaded and needs no special response headers, in particular no cross-origin isolation (COOP/COEP). A threaded build is a possible later second file.
  • The profiles dev, size and speed are part of the build from the start, not added later.
  • The output must not depend on the host's MIME types or compression.

Toolchain and pinned version

The toolchain is Emscripten, used through CMake's own Emscripten toolchain file (emcmake cmake). CMake detects it (EMSCRIPTEN is set, or CMAKE_SYSTEM_NAME is Emscripten) and the root CMakeLists.txt sets the derived variable N2ENGINE_PLATFORM_WEB to ON, includes cmake/N2EngineWeb.cmake, and compiles every target with -DN2ENGINE_PLATFORM_WEB=1 and -DN2ENGINE_SINGLE_THREADED=1. On every other configuration the variable is OFF and nothing else changes: no native option, target, source list or flag differs.

The version is pinned to Emscripten 4.0.10 (the EMSCRIPTEN_VERSION variable in the CI job), installed with the official emsdk and not through a third-party action. Pinning keeps an upstream release from changing the build with no change in this repository; the 4.0 series was chosen for its recent LLVM and libc++ (the engine is C++23). Emscripten 4.0.10 was built and tested by the CI job, see Verified and unverified. Changing the pin means changing it in .github/workflows/tests.yml and here.

Building locally

Install and activate the pinned SDK once (Linux or macOS shell; on Windows use emsdk.bat and emsdk_env.bat), then configure with emcmake and build with CMake as usual. You need CMake 3.25 or newer and Ninja (or another generator).

git clone https://github.com/emscripten-core/emsdk.git
cd emsdk
./emsdk install 4.0.10
./emsdk activate 4.0.10
source ./emsdk_env.sh          # puts emcc, emcmake and the SDK's node on PATH (per shell)

cd /path/to/N2Engine
emcmake cmake -S . -B build-web -G Ninja -DCMAKE_BUILD_TYPE=Release -DN2ENGINE_WEB_PROFILE=dev
cmake --build build-web --target math_tests text_tests assetimport_tests engine_tests renderer_tests
ctest --test-dir build-web --output-on-failure
bash scripts/web-size-report.sh build-web/bin
cmake --build build-web --target web_tests web-package    # the player: see "Building and hosting the package" below

The engine tests are large: with the dev profile's debug information engine_tests.wasm is over 300 MB (see the size report), which is not a size result. Each test is built as build-web/bin/<name>.js plus a .wasm. CMake's Emscripten toolchain sets CMAKE_CROSSCOMPILING_EMULATOR to node, so ctest runs them with node; you can also run node build-web/bin/math_tests.js directly. A configure that is not under emcmake is a native configure and is unchanged.

The reduced target set and what is excluded

The web configuration builds the math, text and assetimport libraries, lua, the renderer library (the software renderer; the OpenGL renderer's sources compile but no GL context exists), the engine library, a stand-in for GLFW and OpenAL (external/web-stubs), the test executables (math_tests, text_tests, assetimport_tests, engine_tests, renderer_tests and, from stage 2, web_tests), googletest (fetched), the web player N2WebPlayer with its web-package target PR #170 (web/), and the web-size-report target. The rows below are not built as the native build builds them, and the configure prints a Web: status line for them.

Design decision: stage 0 built math and text only PR #163

The engine core cannot be built for the web without changing its sources (see the table above), and stage 0 is limited to the toolchain, the profiles, the size report and the CI leg. Building the two CPU-only libraries proves the toolchain, the flags and the node test runner end to end, with nothing that needs a decision about windows, threads or files. Stage 1 then added the engine core, as the sections below describe.

The single-threaded fallback

The baseline web build has no threads (no pthreads, no SharedArrayBuffer). cmake/N2EngineWeb.cmake defines N2ENGINE_SINGLE_THREADED for every web target; code that would start or wait on a thread checks it. Where the engine uses threads:

  • The software renderer's RenderThread (renderer/include/renderer/software/RenderThread.hpp). With N2ENGINE_SINGLE_THREADED the class has the same interface but no thread, mutex or condition variable: SubmitFrame runs the frame's commands at once on the calling thread, in submission order, none dropped (a frame submitted while not started is dropped, as in the threaded class); WaitForFrame has nothing to wait for, because the frame is finished when SubmitFrame returns. The commands do not depend on which thread runs them, so the image is the same: the software-renderer goldens (tests/engine/rendering/Software*GoldenTests.cpp, tests/renderer/software/) pass under node. The threaded class is not changed.
  • The logger keeps per-thread line buffers and a mutex; both compile and behave with one thread (a std::mutex in a build without pthreads locks without blocking). Only the test that starts eight logging threads is skipped (see below).
  • The Vulkan renderer is not built, and the window is not created.

Design decision: frames run inline, not on a worker PR #167

Issue #155 makes the single-threaded build the baseline and a threaded build an optional second file. Running a submitted frame inside SubmitFrame keeps every call site of RenderThread unchanged and keeps the order and the set of commands identical to the threaded path; it only loses the overlap of rendering with the next frame's scene update, which the baseline gives up by definition. A threaded second artifact (stage 6) would simply not define N2ENGINE_SINGLE_THREADED.

The window and audio stand-ins, and std::generator

The engine's public headers include GLFW (the window, input and the renderer interface) and OpenAL (audio), and the engine and renderer libraries link them. external/web-stubs/CMakeLists.txt, added only on the web, downloads the headers of the tags the native build uses (GLFW 3.4, OpenAL Soft 1.24.0) and uses only their include directories, and builds two small C libraries (glfw, and openal_web aliased as OpenAL::OpenAL) that define the functions the engine calls with no behaviour: no window, no device. Native builds never see this directory.

Design decision: stand-ins now, the real thing in its own stage PR #167

Emscripten has ports of both libraries, but they do not cover what the engine calls (for example the GLFW gamepad functions and glfwSetWindowAttrib, and OpenAL Soft's loopback extension), and a window and WebAudio are stages 2 and 4 with their own decisions (a canvas, the user-gesture rule). Stage 1 only has to let the engine core link and run headless, which it already does natively with no window and an OpenAL loopback device. The stand-ins give the linker the symbols and make the "no window, no sound card" paths the ones that run; they are replaced, not extended, by stages 2 and 4. A GLFW or OpenAL function the engine starts to call needs a no-op added to the stand-in, or the web link fails with an undefined symbol.

std::generator (C++23), which the coroutine scheduler uses (std::generator<ICoroutineWait>), is not implemented by libc++, the standard library Emscripten ships. external/web-stubs/include/generator provides the part the engine uses (a move-only single-pass range, co_yield of a value or a copy, exception rethrow on resume) and includes the toolchain's own <generator> instead when there is one, so a later Emscripten takes over with no change. Nested generators (std::ranges::elements_of) and allocators are not supported by it and are compile errors. CoroutineTests and CoroutineOrderTests run on it. Two smaller libc++ and wasm32 differences are handled in engine/src/io/ResourceLoader.cpp: libc++ has no std::chrono::clock_cast (its file clock counts from the Unix epoch, so the file time is the system time directly), and a file size is cast to std::size_t, which is 32 bits on wasm32.

The web build compiles and links with -fwasm-exceptions: the engine, sol2, nlohmann::json and googletest throw and catch, and Emscripten's default (abort on a throw) would break them. It also makes Lua's setjmp/longjmp (a C library) use the wasm implementation. Application.GetPlatform() in Lua still answers Unknown on the web.

Files and the environment

The engine reads and writes files through std::filesystem and std::ifstream/ofstream, which work unchanged on Emscripten's virtual filesystem (MEMFS, empty at start). A shipped web build gets its assets from an asset pack or fetches them: stage 3. For the tests, the executables link with -sNODERAWFS=1, so node's real filesystem is used: the tests open lua_project/, tests/assets/ and renderer/shaders/ by absolute path and write their temporary projects under the system temporary folder. NODERAWFS is for the tests only (tests/CMakeLists.txt) and makes the .js run under node only. Emscripten also does not pass the host's environment variables to the program (HOME is /home/web_user and TMPDIR is unset), so the test executables are linked with --pre-js tests/web/node-env.js, which copies node's process.env into the program's environment before it starts; getenv then behaves as in a native run. Saves in a browser (IndexedDB through IDBFS) and synchronous loads are not addressed yet.

The web player (stage 2)

Stage 2 PR #170 is the first playable web build: N2WebPlayer (web/player/WebPlayer.cpp, built only under N2ENGINE_PLATFORM_WEB) runs a project folder on the software renderer, single-threaded, and shows each frame on a canvas. It runs lua_project (the scene of assets/scene.lua) by default. How it works:

  • No window, no GL. The player starts the engine as a headless software-renderer application (isHeadless = true), which takes the engine's existing no-window path (Window::UsesNoWindow): GLFW is never called, the renderer draws into its CPU buffer. After each frame the player reads the buffer back (IRenderer::ReadFramebuffer), flips it to top row first (FlipRows) and hands it to the page's JavaScript, Module.n2Present(pixels, width, height), which draws it with putImageData on a 2D canvas. The page owns the canvas; the C++ only calls the hook, so under node a mock can stand in for it. There are two copies of the frame per tick (the read-back and the flip); a renderer accessor that avoids them is a later optimisation. Headless also makes the audio system try a loopback device, which the OpenAL stand-in refuses: audio stays off (a warning in the log) until stage 4.
  • The main loop does not block. Application::Run() is now BeginRun(), then RunFrame() until it returns false, then EndRun(); the player calls RunFrame() (one Tick, with the same check for a closed window or Quit() as before) from emscripten_set_main_loop, which the browser paces with requestAnimationFrame. The fixed-step accumulator is the engine's own, unchanged: a slow frame runs several fixed steps up to the 0.25 s catch-up cap, as on every platform. When the game quits (Application.Quit(), the scene's Escape binding) the loop is cancelled, EndRun() sends OnApplicationQuit and shuts down, and the page says the game has ended.
  • Input comes from the page's events (HTML5 callbacks in emscripten/html5.h, registered once the player starts). Keys and mouse buttons are held in an Input::InjectedKeys installed as the engine's KeySource (the seam the editor's play child uses), so every binding, action map and Lua call reads them as it reads GLFW natively. The pointer position goes to Mouse::InjectPointer once per frame and the wheel to Mouse::AccumulateScroll. The translation is in web/player/WebInputMap.* and is unit tested under node (tests/web): KeyboardEvent.code (the physical key, layout independent, like GLFW's tokens) to Input::Key; MouseEvent.button to MouseButton (the DOM numbers right and middle the other way round); the pointer from viewport CSS pixels through the canvas's box to render pixels; wheel deltas to notches (100 pixels or 3 lines per notch, vertical sign flipped to the engine's up-is-positive). Page-scrolling keys (Space, arrows, Page Up/Down, Home, End, Tab, Backspace) are cancelled for the page while the game runs unless Ctrl, Alt or Meta is held; every other browser key (F5, F11, F12, shortcuts) keeps its meaning. The wheel does not scroll the page over the canvas; the context menu is off over it. Losing focus releases every key and button. A press counts only when it starts on the canvas; a release is taken wherever it happens.
  • Resize. Each frame the player measures the canvas's CSS box; the render size is that shape, at most 1280 pixels wide, and a change calls Window::SetRenderSize (which updates the camera's aspect and the UI and picking viewport) and resizes the canvas's pixel buffer. The browser scales the canvas up to its CSS size (the page makes it fill the window), so a large window renders at the cap and is shown larger; the pointer is mapped through the scale.
  • Assets. lua_project/assets and project.n2proj are packed into the virtual filesystem at /project with --preload-file and travel in index.data; the player opens the project there as lua_project does. Another folder: -DN2_WEB_PROJECT_DIR=/path (it needs project.n2proj and assets/scene.lua). user:// is the in-memory filesystem: nothing is saved between page loads yet.
  • The page (web/shell.html, emcc's --shell-file): a canvas, a "Click to start" gate (the engine starts on the click; browsers require a user gesture for audio, which the build does not have yet), and an error box that shows an abort, an uncaught error or a failed start together with the last 100 lines of the engine's output.

Design decision: the player uses the windowless path, not Emscripten's GLFW port PR #170

The software renderer already has a mode with no window, GLFW or GL context, built for CI and the editor's play child: it draws into a CPU buffer, and frames are read back. A canvas is exactly a consumer of that buffer, and the editor's remote input (KeySource, InjectPointer) is exactly the seam for events that do not come from a window. This avoids a WebGL context the decisions of #155 rule out, avoids the engine calling GLFW functions Emscripten's port does not implement (gamepads, window attributes), and changes no engine code that native builds run. The cost is that GLFW is still the no-op stand-in on the web (external/web-stubs), so there is no gamepad input and no window modes yet.

Design decision: Run() is split in three, not duplicated PR #170

A browser cannot run a blocking loop. Rather than copying the loop into the player (where the fixed-step handling and the end-of-run sequence could drift from the engine's), Run() itself is now BeginRun(), RunFrame() until false, EndRun(), with the same statements in the same order, so native behaviour is unchanged and the web driver is the same code.

Design decision: render at most 1280 pixels wide, scale in the browser PR #170

The software renderer's cost is its pixel count, and a browser window can be 4K or HiDPI. The render size therefore follows the canvas's shape but is capped, and devicePixelRatio is ignored: sharpness on HiDPI is traded for a frame rate the software renderer can hold. The cap is a constant in WebPlayer.cpp; whether it is the right number is for the maintainer to judge on real hardware (see the checklist).

Design decision: index.js is a module factory PR #170

The player links with -sMODULARIZE=1 -sEXPORT_NAME=createN2Player. The page calls the factory when it has loaded (and starts main on the button click with callMain), and the node smoke test calls it with its own arguments and canvas mock; a non-modular Emscripten script cannot be handed settings when loaded with require. This applies to the player only; the test executables are unchanged.

Building and hosting the package

emcmake cmake -S . -B build-web -G Ninja -DCMAKE_BUILD_TYPE=Release -DN2ENGINE_WEB_PROFILE=size
cmake --build build-web --target web-package
ls build-web/web-package          # index.html index.js index.wasm index.data
node scripts/web-package-smoke.mjs build-web/web-package 30 320x180   # checks the folder, runs 30 frames under node
bash scripts/web-size-report.sh build-web/web-package

cd build-web/web-package && python -m http.server 8080   # then open http://localhost:8080/

The folder is the whole site: copy it to any static host, under any path (https://host/games/demo/ works as / does: the page names index.js, and the loader finds index.wasm and index.data, all relative to the page). It needs no special response headers: the build has no threads and does not use SharedArrayBuffer, so no cross-origin isolation, and it can sit in an iframe. If a host serves .wasm with the wrong MIME type, Emscripten's loader logs a warning and falls back from streaming instantiation to fetching the bytes and instantiating them; a host that does not compress just sends bigger files. The page must be served over http(s): browsers do not let a page opened from file:// fetch its own .wasm and .data.

Build profiles

N2ENGINE_WEB_PROFILE is a cache variable with the values dev (the default), size and speed; anything else is a configure error. It exists only in web configurations. The flags are applied to every target (compile and link) in cmake/N2EngineWeb.cmake, because LTO needs every object built with it. Every profile also links with -sALLOW_MEMORY_GROWTH=1 (Emscripten's default heap is a fixed 16 MB) and -sSTACK_SIZE=1048576 (its default stack is 64 KB). The unit tests add -sEXIT_RUNTIME=1 so node exits with the test result.

ProfileFlagsMeant for
dev-O1 -g, no LTOFast builds and links, DWARF debug info. The only profile built and tested in CI.
size-Oz -flto, link -Oz -flto -sASSERTIONS=0; no -g, so no debug info or names section; emcc runs wasm-opt -Oz at this levelThe smallest download. Exceptions and RTTI stay on: the engine is not known to build without them, so trimming them is a later, measured step.
speed-O3 -flto, link -O3 -flto -sASSERTIONS=0The fastest code.

Every profile compiles and links with -fwasm-exceptions (WebAssembly exceptions, no JavaScript glue): the engine and its tests throw and catch.

Output contract

This is the contract every later stage keeps. Stage 2 is the first to produce a package that meets it (build-web/web-package, see Building and hosting the package); the size, asset-pack and precompression parts are stage 3:

  • A folder of static files: .html, .js, .wasm and the asset pack (index.data). No server logic.
  • Relative URLs only, so the folder works from any path or subdomain.
  • No special response headers. The baseline is single-threaded and does not use SharedArrayBuffer, so it does not need cross-origin isolation and can run in an iframe on another site.
  • MIME-agnostic and compression-agnostic: it must still load when a host serves .wasm with a wrong type (the loader falls back from streaming instantiation to an ArrayBuffer) and when the host does not compress. The MIME fallback is Emscripten's own loader behaviour (not exercised by CI: see the checklist). Precompressed .br/.gz copies are an addition for the size profile, never a requirement. Not implemented yet: stage 3.

The size report and budgets

scripts/web-size-report.sh [dir] (default build/bin) lists every .wasm and .js file under the directory (and, for a web package, its .data and .html files, which no budget counts) with its raw and gzip -9 size, prints a table, and appends it to the GitHub job summary when GITHUB_STEP_SUMMARY is set. It fails (exit 1) only for a budget that is set and exceeded, and with exit 1 if it finds no files. Budgets are in bytes and come from environment variables, or from CMake cache variables when you use the web-size-report target:

Variable (environment and CMake)Budget for
N2ENGINE_WEB_BUDGET_WASM_GZIPThe gzip size of any one .wasm file.
N2ENGINE_WEB_BUDGET_TOTAL_GZIPThe gzip size of all .wasm and .js files together.
 
N2ENGINE_WEB_BUDGET_WASM_GZIP=1500000 bash scripts/web-size-report.sh build-web/bin
cmake -S . -B build-web -DN2ENGINE_WEB_BUDGET_TOTAL_GZIP=2000000 && cmake --build build-web --target web-size-report

No budget is set at stage 0 (the CI step only reports). Brotli sizes and time to first frame are not measured yet.

CI

The job web (Emscripten, dev profile, node tests) in .github/workflows/tests.yml PR #163 installs emsdk 4.0.10, configures the dev profile with emcmake, configures (only) the size and speed profiles without tests, builds math_tests, text_tests, assetimport_tests, engine_tests and renderer_tests (with -k 0, so one run shows every compile error) PR #167, runs ctest (node runs each test), and reports the artifact sizes in the job summary. PR #170 The job also builds web_tests (the player's input translation, run by ctest), then, in three further steps, builds the web-package target, runs scripts/web-package-smoke.mjs build-web/web-package 30 320x180 (the folder's contents, then the player for 30 frames under node with the canvas mocked), and reports the package's sizes (no budget). No real browser is involved. The configure downloads the GLFW and OpenAL Soft headers (see the stand-ins). It is not a required check; it follows the other build jobs: needs: changes and the same docs-only if, ccache is not used, and it uploads nothing. See Testing & CI.

What is not done yet

The stages are from issue #155; stages 0 to 2 exist.

  1. Stage 0: toolchain, profiles, size report, CI leg for math and text.
  2. Stage 1 (this page): the headless engine core in WebAssembly: scene, components, Lua, serialization, the software renderer, single-threaded, with the engine, renderer, asset-import, math and text tests under node. Still missing from its scope: ufbx (FBX/OBJ import) and FreeType are left off; a shipped build's filesystem (asset pack, IDBFS saves) is stage 3; the Lua project and the demo are not built.
  3. Stage 2 PR #170: the software renderer on a canvas with keyboard, mouse and wheel input, a non-blocking main loop, lua_project preloaded, a shell page and a static package folder, with a node smoke test in CI. Left of its scope, not done: touch input, devicePixelRatio/HiDPI, fullscreen and pointer lock, gamepads (the GLFW stand-in has none), persistent saves, a golden image of the web render, and a faster present path (the frame is copied twice). Nothing about it has been seen in a real browser: that is the checklist.
  4. Stage 3 (the rest of it): asynchronous loading instead of one preloaded .data file, size and load-time budgets enforced in CI, precompressed outputs. (The shell page and the static package folder arrived with stage 2.)
  5. Stage 4: audio through WebAudio (replaces the OpenAL stand-in).
  6. Stage 5: PhysX (or another physics) on WebAssembly.
  7. Stage 6: the optional threaded build, chosen by crossOriginIsolated (does not define N2ENGINE_SINGLE_THREADED).
  8. Stage 7: the WebGPU backend.
