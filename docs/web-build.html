Web build

N2Engine can be configured with Emscripten to build for WebAssembly. This is stages 0 to 5 of issue #155: the toolchain, the build profiles and a size report PR #163, the headless engine core (scene, components, Lua, serialization, the software renderer) built for WebAssembly and tested under node with a single-threaded fallback PR #167, and the first playable web build: a player that draws the software renderer on a canvas, reads keyboard and mouse from the page and is packaged as plain static files PR #170, and the packaging around it: a loader with download progress and a MIME-type fallback, a manifest.json of sizes and hashes, precompressed .br/.gz copies, and size budgets enforced in CI for all three profiles PR #174, and audio: Emscripten's OpenAL on WebAudio, unlocked by a user gesture PR #181, and physics: PhysX built from source for WebAssembly as CPU-only, single-threaded static libraries behind the existing physics backend PR #184. There is no touch yet; this page says what exists, how to build and host it, and what does not. What only a browser can show is in the manual browser checklist.

Goal and decisions already taken

The aim is a web player (not the editor) whose output is plain static files that any host can serve. These decisions were taken by the maintainer on 2026-10-15 in issue #155 and this work builds on them:

  • Player only. The software renderer comes first, WebGPU later; WebGL2 is not a target.
  • The baseline build is single-threaded and needs no special response headers, in particular no cross-origin isolation (COOP/COEP). A threaded build is a possible later second file.
  • The profiles dev, size and speed are part of the build from the start, not added later.
  • The output must not depend on the host's MIME types or compression.

Toolchain and pinned version

The toolchain is Emscripten, used through CMake's own Emscripten toolchain file (emcmake cmake). CMake detects it (EMSCRIPTEN is set, or CMAKE_SYSTEM_NAME is Emscripten) and the root CMakeLists.txt sets the derived variable N2ENGINE_PLATFORM_WEB to ON, includes cmake/N2EngineWeb.cmake, and compiles every target with -DN2ENGINE_PLATFORM_WEB=1 and -DN2ENGINE_SINGLE_THREADED=1. On every other configuration the variable is OFF and nothing else changes: no native option, target, source list or flag differs.

The version is pinned to Emscripten 4.0.10 (the EMSCRIPTEN_VERSION variable in the CI job), installed with the official emsdk and not through a third-party action. Pinning keeps an upstream release from changing the build with no change in this repository; the 4.0 series was chosen for its recent LLVM and libc++ (the engine is C++23). Emscripten 4.0.10 was built and tested by the CI job, see Verified and unverified. Changing the pin means changing it in .github/workflows/tests.yml and here.

Building locally

Install and activate the pinned SDK once (Linux or macOS shell; on Windows use emsdk.bat and emsdk_env.bat), then configure with emcmake and build with CMake as usual. You need CMake 3.25 or newer and Ninja (or another generator).

git clone https://github.com/emscripten-core/emsdk.git
cd emsdk
./emsdk install 4.0.10
./emsdk activate 4.0.10
source ./emsdk_env.sh          # puts emcc, emcmake and the SDK's node on PATH (per shell)

cd /path/to/N2Engine
emcmake cmake -S . -B build-web -G Ninja -DCMAKE_BUILD_TYPE=Release -DN2ENGINE_WEB_PROFILE=dev
cmake --build build-web --target math_tests text_tests assetimport_tests engine_tests renderer_tests
ctest --test-dir build-web --output-on-failure
bash scripts/web-size-report.sh build-web/bin
cmake --build build-web --target web_tests web-package    # the player: see "Building and hosting the package" below

The engine tests are large: with the dev profile's debug information engine_tests.wasm is over 300 MB (see the size report), which is not a size result. Each test is built as build-web/bin/<name>.js plus a .wasm. CMake's Emscripten toolchain sets CMAKE_CROSSCOMPILING_EMULATOR to node, so ctest runs them with node; you can also run node build-web/bin/math_tests.js directly. A configure that is not under emcmake is a native configure and is unchanged.

The first configure builds PhysX PR #184: it needs bash, git, a Linux or WSL shell for sed (the script uses GNU sed), network access to github.com, and takes a few minutes (about 2 on the CI runner, 1 on a 16-core machine) the first time; the work is done in a temporary folder (several hundred MB: the PhysX checkout alone is about 320 MB; removed afterwards) and the result, about 14 MB, is kept in external/PhysX/physx/bin/emscripten.wasm32, which every later configure and every profile reuses. Delete that folder to build it again. See PhysX: source, pins and the build recipe.

The single-threaded fallback

The baseline web build has no threads (no pthreads, no SharedArrayBuffer). cmake/N2EngineWeb.cmake defines N2ENGINE_SINGLE_THREADED for every web target; code that would start or wait on a thread checks it. Where the engine uses threads:

  • The software renderer's RenderThread (renderer/include/renderer/software/RenderThread.hpp). With N2ENGINE_SINGLE_THREADED the class has the same interface but no thread, mutex or condition variable: SubmitFrame runs the frame's commands at once on the calling thread, in submission order, none dropped (a frame submitted while not started is dropped, as in the threaded class); WaitForFrame has nothing to wait for, because the frame is finished when SubmitFrame returns. The commands do not depend on which thread runs them, so the image is the same: the software-renderer goldens (tests/engine/rendering/Software*GoldenTests.cpp, tests/renderer/software/) pass under node. The threaded class is not changed.
  • The logger keeps per-thread line buffers and a mutex; both compile and behave with one thread (a std::mutex in a build without pthreads locks without blocking). Only the test that starts eight logging threads is skipped (see below).
  • The Vulkan renderer is not built, and the window is not created.
  • PhysX's CPU dispatcher PR #184 is created with 0 worker threads when N2ENGINE_SINGLE_THREADED is defined (PhysXBackend::Initialize), whatever physics.deterministic asks for: every PhysX task runs on the thread that calls simulate. Native builds keep 4 workers (0 with physics.deterministic). See PhysX: threads, memory and errors.
  • The editor host's declaration cache (ScriptDeclarationCache, PR #179) runs each Lua declaration evaluation on a worker thread and abandons it at a deadline. With N2ENGINE_SINGLE_THREADED it evaluates on the calling thread instead, bounded only by the evaluator's own wall-clock check, with nothing to abandon. The editor host (sockets, TLS) is not built for the web and nothing on the web sets the execution policy, so no web target uses the cache; the fallback keeps the engine library compiling, and the tests that need a thread skip themselves.

Design decision: frames run inline, not on a worker PR #167

Issue #155 makes the single-threaded build the baseline and a threaded build an optional second file. Running a submitted frame inside SubmitFrame keeps every call site of RenderThread unchanged and keeps the order and the set of commands identical to the threaded path; it only loses the overlap of rendering with the next frame's scene update, which the baseline gives up by definition. A threaded second artifact (stage 6) would simply not define N2ENGINE_SINGLE_THREADED.

The window and audio stand-ins, and std::generator

The engine's public headers include GLFW (the window, input and the renderer interface) and OpenAL (audio), and the engine and renderer libraries link them. external/web-stubs/CMakeLists.txt, added only on the web, downloads the headers of the tags the native build uses (GLFW 3.4, OpenAL Soft 1.24.0) and uses only their include directories, and builds a small C library for GLFW (glfw, no behaviour: no window) and openal_web, aliased as OpenAL::OpenAL. Until stage 4 openal_web was a no-op C library as well (no device); since PR #181 it is OpenAL Soft's headers plus a link to Emscripten's OpenAL by default, and the no-op library only with -DN2ENGINE_WEB_AUDIO=stub. Native builds never see this directory.

Design decision: stand-ins now, the real thing in its own stage PR #167

Emscripten has ports of both libraries, but they do not cover what the engine calls (for example the GLFW gamepad functions and glfwSetWindowAttrib, and OpenAL Soft's loopback extension), and a window and WebAudio are stages 2 and 4 with their own decisions (a canvas, the user-gesture rule). Stage 1 only has to let the engine core link and run headless, which it already does natively with no window and an OpenAL loopback device. The stand-ins give the linker the symbols and make the "no window, no sound card" paths the ones that run; they are replaced, not extended, by stages 2 and 4 (stage 4 did: Audio). A GLFW function the engine starts to call needs a no-op added to the stand-in, or the web link fails with an undefined symbol; an OpenAL function it starts to call must exist in Emscripten's port (libopenal.js), or have a no-op in openal_stub.c for the stub build.

std::generator (C++23), which the coroutine scheduler uses (std::generator<ICoroutineWait>), is not implemented by libc++, the standard library Emscripten ships. external/web-stubs/include/generator provides the part the engine uses (a move-only single-pass range, co_yield of a value or a copy, exception rethrow on resume) and includes the toolchain's own <generator> instead when there is one, so a later Emscripten takes over with no change. Nested generators (std::ranges::elements_of) and allocators are not supported by it and are compile errors. CoroutineTests and CoroutineOrderTests run on it. Two smaller libc++ and wasm32 differences are handled in engine/src/io/ResourceLoader.cpp: libc++ has no std::chrono::clock_cast (its file clock counts from the Unix epoch, so the file time is the system time directly), and a file size is cast to std::size_t, which is 32 bits on wasm32.

The web build compiles and links with -fwasm-exceptions: the engine, sol2, nlohmann::json and googletest throw and catch, and Emscripten's default (abort on a throw) would break them. It also makes Lua's setjmp/longjmp (a C library) use the wasm implementation. Application.GetPlatform() in Lua still answers Unknown on the web.

Files and the environment

The engine reads and writes files through std::filesystem and std::ifstream/ofstream, which work unchanged on Emscripten's virtual filesystem (MEMFS, empty at start). A shipped web build gets its assets from an asset pack or fetches them: stage 3. For the tests, the executables link with -sNODERAWFS=1, so node's real filesystem is used: the tests open lua_project/, tests/assets/ and renderer/shaders/ by absolute path and write their temporary projects under the system temporary folder. NODERAWFS is for the tests only (tests/CMakeLists.txt) and makes the .js run under node only. Emscripten also does not pass the host's environment variables to the program (HOME is /home/web_user and TMPDIR is unset), so the test executables are linked with --pre-js tests/web/node-env.js, which copies node's process.env into the program's environment before it starts; getenv then behaves as in a native run. Saves in a browser (IndexedDB through IDBFS) and synchronous loads are not addressed yet.

The web player (stage 2)

Stage 2 PR #170 is the first playable web build: N2WebPlayer (web/player/WebPlayer.cpp, built only under N2ENGINE_PLATFORM_WEB) runs a project folder on the software renderer, single-threaded, and shows each frame on a canvas. It runs lua_project (the scene of assets/scene.lua) by default. How it works:

  • No window, no GL. The player starts the engine as a headless software-renderer application (isHeadless = true), which takes the engine's existing no-window path (Window::UsesNoWindow): GLFW is never called, the renderer draws into its CPU buffer. After each frame the player reads the buffer back (IRenderer::ReadFramebuffer), flips it to top row first (FlipRows) and hands it to the page's JavaScript, Module.n2Present(pixels, width, height), which draws it with putImageData on a 2D canvas. The page owns the canvas; the C++ only calls the hook, so under node a mock can stand in for it. There are two copies of the frame per tick (the read-back and the flip); a renderer accessor that avoids them is a later optimisation. Headless used to make the audio system try a loopback device; on the web the engine now opens the browser's audio output instead (stage 4 PR #181, Audio).
  • The main loop does not block. Application::Run() is now BeginRun(), then RunFrame() until it returns false, then EndRun(); the player calls RunFrame() (one Tick, with the same check for a closed window or Quit() as before) from emscripten_set_main_loop, which the browser paces with requestAnimationFrame. The fixed-step accumulator is the engine's own, unchanged: a slow frame runs several fixed steps up to the 0.25 s catch-up cap, as on every platform. When the game quits (Application.Quit(), the scene's Escape binding) the loop is cancelled, EndRun() sends OnApplicationQuit and shuts down, and the page says the game has ended.
  • Input comes from the page's events (HTML5 callbacks in emscripten/html5.h, registered once the player starts). Keys and mouse buttons are held in an Input::InjectedKeys installed as the engine's KeySource (the seam the editor's play child uses), so every binding, action map and Lua call reads them as it reads GLFW natively. The pointer position goes to Mouse::InjectPointer once per frame and the wheel to Mouse::AccumulateScroll. The translation is in web/player/WebInputMap.* and is unit tested under node (tests/web): KeyboardEvent.code (the physical key, layout independent, like GLFW's tokens) to Input::Key; MouseEvent.button to MouseButton (the DOM numbers right and middle the other way round); the pointer from viewport CSS pixels through the canvas's box to render pixels; wheel deltas to notches (100 pixels or 3 lines per notch, vertical sign flipped to the engine's up-is-positive). Page-scrolling keys (Space, arrows, Page Up/Down, Home, End, Tab, Backspace) are cancelled for the page while the game runs unless Ctrl, Alt or Meta is held; every other browser key (F5, F11, F12, shortcuts) keeps its meaning. The wheel does not scroll the page over the canvas; the context menu is off over it. Losing focus releases every key and button. A press counts only when it starts on the canvas; a release is taken wherever it happens.
  • Resize. Each frame the player measures the canvas's CSS box; the render size is that shape, at most 1280 pixels wide, and a change calls Window::SetRenderSize (which updates the camera's aspect and the UI and picking viewport) and resizes the canvas's pixel buffer. The browser scales the canvas up to its CSS size (the page makes it fill the window), so a large window renders at the cap and is shown larger; the pointer is mapped through the scale.
  • Assets. lua_project/assets and project.n2proj are packed into the virtual filesystem at /project with --preload-file and travel in index.data; the player opens the project there as lua_project does. Another folder: -DN2_WEB_PROJECT_DIR=/path (it needs project.n2proj and assets/scene.lua). user:// is the in-memory filesystem: nothing is saved between page loads yet.
  • The page (web/shell.html, emcc's --shell-file): a canvas, a "Click to start" gate (the engine starts on the click, which is also the user gesture browsers require for audio; Audio), and an error box that shows an abort, an uncaught error or a failed start together with the last 100 lines of the engine's output.

Design decision: the player uses the windowless path, not Emscripten's GLFW port PR #170

The software renderer already has a mode with no window, GLFW or GL context, built for CI and the editor's play child: it draws into a CPU buffer, and frames are read back. A canvas is exactly a consumer of that buffer, and the editor's remote input (KeySource, InjectPointer) is exactly the seam for events that do not come from a window. This avoids a WebGL context the decisions of #155 rule out, avoids the engine calling GLFW functions Emscripten's port does not implement (gamepads, window attributes), and changes no engine code that native builds run. The cost is that GLFW is still the no-op stand-in on the web (external/web-stubs), so there is no gamepad input and no window modes yet.

Design decision: Run() is split in three, not duplicated PR #170

A browser cannot run a blocking loop. Rather than copying the loop into the player (where the fixed-step handling and the end-of-run sequence could drift from the engine's), Run() itself is now BeginRun(), RunFrame() until false, EndRun(), with the same statements in the same order, so native behaviour is unchanged and the web driver is the same code.

Design decision: render at most 1280 pixels wide, scale in the browser PR #170

The software renderer's cost is its pixel count, and a browser window can be 4K or HiDPI. The render size therefore follows the canvas's shape but is capped, and devicePixelRatio is ignored: sharpness on HiDPI is traded for a frame rate the software renderer can hold. The cap is a constant in WebPlayer.cpp; whether it is the right number is for the maintainer to judge on real hardware (see the checklist).

Design decision: index.js is a module factory PR #170

The player links with -sMODULARIZE=1 -sEXPORT_NAME=createN2Player. The page calls the factory when it has loaded (and starts main on the button click with callMain), and the node smoke test calls it with its own arguments and canvas mock; a non-modular Emscripten script cannot be handed settings when loaded with require. This applies to the player only; the test executables are unchanged.

Building and hosting the package

emcmake cmake -S . -B build-web -G Ninja -DCMAKE_BUILD_TYPE=Release -DN2ENGINE_WEB_PROFILE=size
cmake --build build-web --target web-package
ls build-web/web-package          # index.html index.js index.wasm index.data n2-loader.js manifest.json, plus .br and .gz copies with size or speed
node scripts/web-package-smoke.mjs build-web/web-package 30 320x180 --precompressed   # checks the folder, runs 30 frames under node (--precompressed: the .br/.gz copies must be there)
node scripts/web-budget-check.mjs build-web/web-package size   # the size budgets (web/budgets.json)

cd build-web/web-package && python -m http.server 8080   # then open http://localhost:8080/

The folder is the whole site: copy it to any static host, under any path (https://host/games/demo/ works as / does: the page names index.js, and the loader finds index.wasm and index.data, all relative to the page). It needs no special response headers: the build has no threads and does not use SharedArrayBuffer, so no cross-origin isolation, and it can sit in an iframe. If a host serves .wasm with the wrong MIME type, the loader (n2-loader.js) falls back from streaming instantiation to fetching the bytes and instantiating them; a host that does not compress just sends bigger files (the .br/.gz copies are an option for hosts that can use them, see the recipes). The page must be served over http(s): browsers do not let a page opened from file:// fetch its own .wasm and .data.

The loader, the manifest and precompressed outputs (stage 3)

Stage 3 PR #174 adds three things to the package folder. Nothing in them is required of the host: every one degrades to the plain files.

  • manifest.json (written by scripts/web-package-finalize.mjs, run by the web-package target after the link): for every file of the package, its raw size, sha256, gzip size (level 9) and brotli size (quality 11; null for the dev profile, whose 224 MB of debug info are not worth a brotli pass). manifest.json itself is not listed. The loader uses it for download sizes and cache busting; CI uses it for the budgets; the smoke test checks that its sizes and hashes are right.
  • n2-loader.js (web/n2-loader.js, copied into the package; the page loads it before index.js). It fetches manifest.json (with cache: 'no-cache'; a missing or unreadable manifest is not fatal, the files are then fetched without a version and without a known total), then index.data and index.wasm by index.<ext>?v=<first 12 hex digits of the sha256>, and the page loads index.js and n2-loader.js with the same kind of ?v=, which web-package-finalize.mjs writes into index.html when it packages the build (static files, no server logic). What that guarantees: a current index.html never runs with an older cached file of another build. It does not make index.html itself fresh: a host that lets browsers cache the page heuristically can hand out an old page, so hosts should serve index.html and manifest.json with Cache-Control: no-cache (every other file may be cached for as long as the host likes: its URL changes with its content). When an old page does get through, the loader notices that the page's index.js version differs from the one in manifest.json and asks the person to reload, instead of starting a mismatched build. It reads both files with progress (the page shows a bar and "Downloading 2.1 of 3.4 MB", the totals being the manifest's raw sizes, which stay right when the host compresses on the fly). Without a manifest, a response's Content-Length is used as its size only when it has no Content-Encoding (otherwise it is the compressed size and the decoded body is longer): with a compressing host and no manifest the download shows a byte count and no total, and the length is not checked. The wasm goes through WebAssembly.instantiateStreaming when the host sends Content-Type: application/wasm; with any other type, or in a browser without streaming, the same response is read into an ArrayBuffer for WebAssembly.instantiate, so the file is downloaded once either way (only if streaming fails for another reason with the right type is the rest of that body cancelled and the file fetched again). A LinkError or CompileError is not a hosting problem and does not take the fallback: it means index.wasm and index.js are from different builds (or the wasm is damaged), and the message says so and asks for a reload. A 404, a network failure or a file whose length differs from the manifest's raises a message naming the file ("Could not download index.wasm: the server answered 404. Is index.wasm next to index.html?"), which the page shows in its error box; the engine is not started without its asset pack. The asset pack is handed to Emscripten through Module.getPreloadedPackage and instantiateWasm is Emscripten's own hook, so no custom pack format exists.
  • Precompressed copies (size and speed profiles; -DN2ENGINE_WEB_PRECOMPRESS=on|off|auto, auto being on for those two): index.html.br, index.html.gz, and the same for index.js, index.wasm, index.data and n2-loader.js. They are made with node's zlib (gzip level 9, brotli quality 11), the one the emsdk ships and the CI job already uses, so there is no extra tool or pinned module and the output is reproducible (no timestamps). The plain files stay. The package works on a host that does neither; the copies only help a host that can serve them (see the recipes).

Design decision: our own wasm loader, and the pack prefetched by it PR #174

Emscripten's generated loader already falls back from streaming to ArrayBuffer instantiation and reports the pack's download through Module.setStatus, but it cannot show one progress figure for both files against the build's own sizes (the pack's Content-Length is the compressed size when a host compresses), cannot version the URLs, and reports a missing file as an abort. The loader here uses two documented Emscripten hooks (instantiateWasm, getPreloadedPackage) to do those things and leaves the rest of Emscripten's start-up as it was. The cost: the wasm download starts only after the pack has arrived (the pack is small; this keeps the code short), and the Emscripten release pin (4.0.10) is now also a pin on the shape of those two hooks.

Design decision: the asset pack is fetched asynchronously with progress, not lazily, and has no custom format PR #174

The optional "lazy asset pack" of stage 3 is the part that is cheap and safe: the pack is no longer fetched by Emscripten's own start-up code but by the loader, asynchronously and with progress and a clear error path, before the engine starts. Fetching individual assets while the game runs would need a pack format, a request path through the engine's synchronous file API, and a loading state for scenes: that is a separate piece of work and is not done. For the same reason the whole of lua_project's assets/ is one index.data (80 KB today).

Audio (stage 4) PR #181

The web player plays the engine's AudioSource and AudioListener sounds, and AudioSystem::PlayOneShot, through Emscripten's own OpenAL (-lopenal, library_openal.js, which builds the sound from Web Audio nodes). The engine's audio code is the native code, unchanged for native builds: every web difference sits behind N2ENGINE_PLATFORM_WEB and N2ENGINE_WEB_WEBAUDIO (the compile definition the default N2ENGINE_WEB_AUDIO=webaudio sets in cmake/N2EngineWeb.cmake). Which backend a web build gets, and the node path

N2ENGINE_WEB_AUDIO (a CMake cache variable, cmake/N2EngineWeb.cmake) is webaudio by default: OpenAL::OpenAL is an interface target with OpenAL Soft's headers that links openal (emcc turns it into -lopenal), and N2ENGINE_WEB_WEBAUDIO is defined for every target. stub links external/web-stubs/openal_stub.c (the stage 1 no-op library) and does not define it: the engine then never opens an output, and the web audio handling below is compiled out, except that the player still asks for the device output rather than the loopback (that choice in Application::Init depends on N2ENGINE_PLATFORM_WEB alone), so a stub build logs the same one warning (Subsystem Audio failed) and no loopback line. The player's own --frames smoke run under node goes through the same path. The stub option stays for a build that must not touch WebAudio at all; CI does not build it.

No device, blocked or failed context

The web player runs as a headless application (no window), which natively means "stream the mix through a loopback device". On the web Application::Init instead opens the browser's output with AudioSystem::Initialize(), as a game with a window does (engine/src/Application.cpp; the editor host is not built for the web). When that fails (no AudioContext, the constructor throws, or the port refuses a context) the audio system stays uninitialised and the subsystem is reported Failed with the detail "No WebAudio output: audio is off, the game continues without sound". The web build logs the individual failure at Info level (AudioSystem::OpenDevice) and leaves the one Warn line to the start-up summary (Subsystem Audio failed: ...), so there is one clear warning, not the several lines a native device failure logs. The game continues: every AudioSystem, AudioSource and AudioListener call on an uninitialised system is a no-op (tests/web/WebAudioTests.cpp covers the system calls under node; the package smoke test requires the audio health to be failed; that it is one warning is by reading the code, because the engine's log does not reach the smoke test's output and no test counts the lines). An autoplay policy that merely keeps a created context suspended is not a failure at all: see the next section.

The user-gesture rule

Browsers keep an AudioContext suspended until the page has had a user gesture, and suspend it again for a hidden tab. For a game author the rule is: start sound after an input. What the build does:

  • The context is created inside the Start click. The page's "Click to start" button runs the engine (callMain), and the engine opens its audio output there, in the click's call stack. That is a user gesture, so in most browsers the context is created running. A project's scene.lua and OnAwake/Start code run in that same click, so a sound started from them normally plays.
  • The page's unlock (createAudioUnlock in web/n2-loader.js, installed by web/shell.html before the engine starts). The engine creates its AudioContext inside Emscripten's code where the page cannot reach it, so the unlock wraps window.AudioContext (and webkitAudioContext) to remember every context created after it. Every remembered context, whatever its state (a context created running in the Start click too), adds pointerdown, pointerup, keydown and touchend listeners on the document. Only the events that grant user activation in HTML count: keydown (not Escape), a pointerdown from a mouse, a pointerup that is not from a mouse (touch, pen) and touchend. A touch or pen pointerdown does not grant it, so it neither resumes nor removes anything; on a tap the pointerup does. The first counting gesture calls resume(), once, on each context that is not running, closed or already resuming; the listeners are removed when no context needs a resume any more (at once when the gesture finds every context running, otherwise when the resume succeeds), so a later gesture does nothing. So they are present from the moment a context exists until the first gesture after it. A context created later adds them again; a gesture's resume() that is refused, throws, or settles with the context still not running (Safari's interrupted) keeps them for the next gesture, and after three such refusals the fourth removes them (until a new context is created). The count starts again on any successful resume, whenever every context is found running (or closed) with no gesture's resume pending, whichever way it got there (a gesture that finds it running, a settled resume, the tab becoming visible; this includes a context the browser resumed by itself, as iOS does after a call), and when a new context is created, which also adds the listeners back. A gesture's resume() that never settles keeps them too, and the next gesture does not ask that context again. Emscripten's port also resumes its context on keydown, mousedown and touchstart on the document and the canvas (once each); both run, and resuming twice is harmless.
  • Hidden and visible tabs. When the tab becomes hidden the unlock suspends the running contexts; when it is visible again it resumes the ones it suspended and, while one is not running yet, adds the gesture listeners back. That resume is not a gesture: its refusal does not count towards the three, and while it is pending (a browser may keep it pending until an allowed resume) a gesture still calls resume() again, which is harmless. Nothing is done for a context that was suspended for another reason. Browsers pause requestAnimationFrame in a hidden tab anyway, so the game loop mostly stops with it; the port's own timers (25 ms, for scheduling) may still tick.
  • Sounds asked for while the output is suspended are dropped, not queued. AudioSystem::IsOutputSuspended() (always false on a native build and on the stub build) asks the port's current AudioContext whether it is running. While it is not, PlayOneShot returns an invalid handle and AudioSource::Play() does nothing (so a looping music source started by its play-on-awake setting (OnEnable) before the unlock stays silent and not playing, and must be started again after it); the first such drop of a run logs one Info line saying why. Sounds already playing are not touched (they freeze with the context and continue on resume). A paused source resumed by UnPause() is not gated.

Design decision: drop, do not queue, sounds asked for before the unlock PR #181

The plan allowed either. A suspended AudioContext's clock does not advance, so a sound "queued" by starting it anyway is not queued at all: its source stays AL_PLAYING, holds a pooled source and a mixer-group slot (CountPlayingInGroup counts sources that report AL_PLAYING), and every such sound starts at once, in a burst, when the context is resumed, possibly seconds late. Dropping needs no timer or per-sound state and behaves the same in every browser. The cost is that a sound requested before the first input is lost, which for a game that starts from the Start click is none. A short queue with an expiry is a later option if a real game needs it.

Volume and mute

The master volume reaches the web backend: SetMasterVolume sets the listener gain (alListenerf(AL_GAIN)), which the port applies to the context's master gain node, and the mixer group volumes and mutes are applied per source as natively. No mute hook was added to the page. The only trivial JavaScript-side control, suspend()/resume() on the context, pauses every sound rather than silencing it, and it would fight the unlock's own suspend and resume for the hidden tab; a page that wants a mute button calls Audio.SetMasterVolume(0) from Lua. No public engine API was added for it.

PhysX on the web (stage 5) PR #184

PhysX 5.6.1, the version the native builds use, builds for WebAssembly as CPU-only, single-threaded static libraries, and the web build now runs the engine's physics through the same backend seam (IPhysicsBackend, PhysXBackend) as Windows and Linux: the web configuration no longer forces N2ENGINE_USE_PHYSX off, the web player already asks for the PhysX backend, and the engine's physics tests run under node. Source, pins and the build recipe

  • Source: https://github.com/NVIDIA-Omniverse/PhysX, tag 107.3-omni-and-physx-5.6.1, pinned by its commit 09ff24f3279b735e672ff27b155cbf49f6296f4d in cmake/PhysXWebPin.cmake. scripts/web-build-physx.sh fetches that hash (git fetch --depth 1 origin <commit>) and stops unless git rev-parse HEAD returns it; a commit hash covers the whole tree, so a moved tag cannot change what is built. It is the commit the Linux archives are built from, and PxPhysicsVersion.h in it reports 5.6.1, the version of the headers committed in external/PhysX/physx/include.
  • Why from source and not a prebuilt archive: the native platforms download archives that a workflow published to a release, pinned by SHA256. A web archive would need a new publishing workflow, a release and a hash bumped by hand with every compiler or flag change, and could drift from the source it claims. Building the pinned commit in the web job is a few minutes (below), has nothing to publish, and its inputs (commit, script, Emscripten release) are all in the repository or the job file. The cost of that choice is the CI time and that the libraries are not byte-for-byte reproducible (a compiler build is not), so what is pinned is the input, not the output.
  • Where it runs: the first configure of a web build (cmake/PhysXWeb.cmake, included from the root CMakeLists.txt when N2ENGINE_PLATFORM_WEB and N2ENGINE_USE_PHYSX are ON) runs the script into external/PhysX/physx/bin/emscripten.wasm32 (git-ignored, like the native bin/ folders). The folder holds lib/ (five static archives), include/ (the commit's headers with patches 2 and 3), LICENSE.md and .pin. Later configures, and the other profile directories, reuse it when .pin names the pinned commit, PHYSX_WEB_BUILD_REV (bumped by hand when the script's flags, patches or library list change) and the compiler version. Any failure turns PhysX OFF with a warning, as on the native platforms.
  • What is built: the PhysX public project, Linux platform files, -DCMAKE_BUILD_TYPE=release, -DPX_GENERATE_STATIC_LIBRARIES=True, snippets, samples, the PVD runtime and the GPU projects off, -w -DPX_SIMD_DISABLED on top of PhysX's own flags (-O3 -fno-rtti -fno-exceptions -ffunction-sections -fdata-sections, PX_SUPPORT_PVD=0, PX_SUPPORT_OMNI_PVD=0, DISABLE_CUDA_PHYSX), and only the targets PhysX, PhysXCommon, PhysXFoundation, PhysXExtensions and PhysXPvdSDK. The same libraries serve the dev, size and speed profiles: PhysX compiles at its own -O3 without LTO in all three (the final link of the size profile still runs wasm-opt -Oz over everything).
  • CI: in the web job, actions/cache keeps the output folder keyed by the Emscripten release and a hash of cmake/PhysXWebPin.cmake and scripts/web-build-physx.sh (so a new pin or recipe is a miss), saved right after the first configure. On a cold cache the PhysX build took 102 seconds on the runner's 4 jobs, and the first configure 122 seconds in all (fetching the pinned source, patching, configuring, building, the smoke test); the cache entry is 3.1 MB. With a hit the configure takes 4 seconds. The web job took 21 minutes 46 seconds and 29 minutes on its two green runs, both with a cache hit (runner speed varies by about a third; it was about 17.5 minutes before stage 5): physics costs about 4 to 5 minutes of job time at the same runner speed (bigger builds and links, the PhysX tests, the larger packages) and about 2 minutes more on a cold cache. A cache entry saved by a pull request is visible to that pull request only; the entry a push to master saves is the one other pull requests restore, so a pull request that finds none pays the 2 minutes once.

Design decision: build the pinned PhysX commit in the web job, no prebuilt archive PR #184

Options were a prebuilt wasm archive on a release (as for Linux and Windows) or building from source in CI. A prebuilt archive needs a publishing workflow and a manual hash bump for every flag change and says nothing about what it was built from; the source build is about four minutes of one job on a cold cache, nothing on a warm one, and is fully described by files in the repository. Not decided here and left for the maintainer: publishing the result as a release archive (the script already produces exactly the folder such an archive would hold) if the cold-cache minutes ever matter more than the extra moving part.

Scalar math

The libraries and the engine use PhysX's scalar math (PX_SIMD_DISABLED). The SIMD path would need -msse2 together with -msimd128, which makes the whole module use WebAssembly SIMD instructions and so refuse to load in a browser without WebAssembly SIMD support; the baseline web build asks nothing of the browser beyond WebAssembly exceptions, and the scalar path keeps that. The price is speed: PhysX's SIMD kernels are not used, and how much slower the scalar path is in a browser has not been measured (see What is not verified). A later optional SIMD artifact (like the threaded one of stage 6) could use it.

Design decision: scalar PhysX, no WebAssembly SIMD in the baseline PR #184

The PhysX source does not build for Emscripten without either SIMD or PX_SIMD_DISABLED. The baseline contract (static files, any host, no requirement on the browser beyond what stage 1 to 4 already need) decides for the scalar path. If a measurement in a browser shows the physics frame time is too high on a stack of bodies, the SIMD build is an option for a separate artifact, with a minimum-browser note, not a change to the baseline.

Threads, memory and errors

  • Threads: none. PhysXBackend::Initialize creates PxDefaultCpuDispatcher with 0 workers when N2ENGINE_SINGLE_THREADED is defined, whatever physics.deterministic or the testing seam (SetWorkerThreadsForTesting) ask for, so every PhysX task runs on the thread that calls simulate and fetchResults; PhysX creates no thread (the dispatcher has none to create). Native builds still use 4 workers (0 with physics.deterministic), unchanged. A threaded second artifact (stage 6) would not define the macro.
  • Memory: the link flags are unchanged by this stage: -sALLOW_MEMORY_GROWTH=1, the Emscripten default initial memory and a 1 MB stack (cmake/N2EngineWeb.cmake). PhysX allocates with PxDefaultAllocator (aligned malloc), so its memory comes from the same growing heap and nothing is reserved up front. web_tests prints the cost of a scene under node: PhysXWebTest.ABoxStackCostsAModestHeapGrowthAndSteps (200 boxes on a floor, 120 steps) allocated about 1.6 MB through malloc (1,602,928 bytes in use afterwards in the CI run, from mallinfo, for the SDK, the scene and the bodies) and did not grow the wasm heap, which was already 18,219,008 bytes (the size the test executable starts with); node ran the 120 steps in 97 ms (0.81 ms per step, dev profile, informational). The test fails if the scene needs more than 64 MB of new heap.
  • Errors: the web backend gives PxCreateFoundation a PhysXLoggerErrorCallback (engine/include/engine/physics/physx/PhysXLoggerErrorCallback.hpp) instead of PxDefaultErrorCallback: every PhysX error, warning and performance warning becomes an engine Logger line, PhysX <kind>: <message> (<file>:<line>) (info and no-error as Info, debug and performance warnings as Warn, everything else as Error), and so goes wherever the engine log goes (whether the player's log reaches the browser console is itself a checklist question, see step 8). The libraries are built as PhysX's release flavour (no PX_DEBUG or PX_CHECKED), in which PX_ASSERT compiles to nothing and the SDK's own error reports (an invalid version number given to PxCreatePhysics, which a test drives, is one) are not compiled out; so there is no assertion handler to route (PhysX 5.6.1's public headers have no setter for one). Native builds keep PxDefaultErrorCallback.

Hosting recipes for precompressed files

Nothing here is needed: a plain static host serves the plain files and the page works. These snippets let a host that can do it send the smaller .br or .gz file instead, with the right Content-Encoding and, for .wasm, the right Content-Type (application/wasm; the loader copes with the wrong one, but streaming compilation, which is faster, needs it). None of these has been run against a real server or browser by this project; they are the usual forms of each server's feature, to be checked on yours (open the Network panel and look for Content-Encoding: br on index.wasm).

nginx (the ngx_http_gzip_static_module serves .gz; .br needs the third-party ngx_brotli module, whose brotli_static on; does the same):

location /game/ {
    gzip_static on;
    brotli_static on;          # only with ngx_brotli
    types { application/wasm wasm; }
}

Apache (.htaccess, with mod_rewrite, mod_headers and mod_mime):

AddType application/wasm .wasm
RewriteEngine On
RewriteCond %{HTTP:Accept-Encoding} br
RewriteCond %{REQUEST_FILENAME}.br -f
RewriteRule ^(.*\.(js|wasm|data|html))$ $1.br [L]
RewriteCond %{HTTP:Accept-Encoding} gzip
RewriteCond %{REQUEST_FILENAME}.gz -f
RewriteRule ^(.*\.(js|wasm|data|html))$ $1.gz [L]
<FilesMatch "\.(js|wasm|data|html)\.br$">
    Header set Content-Encoding br
    Header append Vary Accept-Encoding
</FilesMatch>
<FilesMatch "\.(js|wasm|data|html)\.gz$">
    Header set Content-Encoding gzip
    Header append Vary Accept-Encoding
</FilesMatch>
# the rewritten file keeps its own type: also tell Apache what the originals are
<FilesMatch "\.wasm\.(br|gz)$">
    ForceType application/wasm
</FilesMatch>
<FilesMatch "\.js\.(br|gz)$">
    ForceType text/javascript
</FilesMatch>
<FilesMatch "\.html\.(br|gz)$">
    ForceType text/html
</FilesMatch>

Netlify, Cloudflare Pages and most CDNs compress plain files on the fly with brotli or gzip, so upload the plain files and delete the .br/.gz copies (or leave them: they are just extra files). GitHub Pages likewise compresses with gzip by itself and cannot set headers, so serving the copies by name is not possible there either; the plain files are what it serves. On object storage (S3 and the like) upload index.wasm.br as the key index.wasm with metadata Content-Encoding: br and Content-Type: application/wasm, the same for the other files; the loader's ?v= query does not change which object is served.

Output contract

This is the contract every later stage keeps. Stage 2 is the first to produce a package that meets it (build-web/web-package, see Building and hosting the package); stage 3 adds the manifest, the loader's behaviour, the precompressed copies and the budgets:

  • A folder of static files: .html, .js, .wasm, the asset pack (index.data), the loader (n2-loader.js) and manifest.json, with .br/.gz copies for the size and speed profiles. No server logic.
  • Relative URLs only, so the folder works from any path or subdomain.
  • No special response headers. The baseline is single-threaded and does not use SharedArrayBuffer, so it does not need cross-origin isolation and can run in an iframe on another site.
  • MIME-agnostic and compression-agnostic: it must still load when a host serves .wasm with a wrong type (the loader falls back from streaming instantiation to an ArrayBuffer) and when the host does not compress. The MIME fallback is in n2-loader.js and is exercised by CI under node with a mock fetch (not in a real browser: see the checklist). Precompressed .br/.gz copies are an addition, never a requirement and never a replacement of the plain files.
  • Size budgets enforced in CI (next section).
