Testing & CI

N2Engine's tests are GoogleTest executables, one per module, run headless through CTest. CI builds and runs them on Windows in Debug with and without PhysX and in Release with PhysX, then starts the editor host and talks to it over TCP. This page covers the layout, how to run the tests, the CI workflow, the conventions headless tests follow, and how to add one.

How tests are organised

Tests are only configured when N2ENGINE_BUILD_TESTS is ON (the default). The root CMakeLists.txt then fetches GoogleTest 1.17.0 with FetchContent (with gtest_force_shared_crt on), calls enable_testing() and adds tests/, which has one subdirectory per module:

Each subdirectory's CMakeLists.txt follows the same pattern:

  • Sources are collected with file(GLOB_RECURSE ... "*.cpp" "*.cc" "*.cxx"), so any source file in the directory tree is part of the executable. The glob runs at configure time (no CONFIGURE_DEPENDS): after adding a file, re-run the CMake configure step.
  • Linked with GTest::gtest and GTest::gtest_main; no test defines its own main.
  • C++23, no extensions, warnings at /W4 (MSVC) or -Wall -Wextra.
  • Registered with a single add_test(NAME <exe> COMMAND <exe>). CTest therefore sees six tests, one per executable, not one per GoogleTest case. Use --gtest_filter on the executable to run individual cases.

Design decision: one Python script for both operating systems, instead of PowerShell on Windows and something else on Linux PR #115

The host smoke tests started as two long PowerShell steps in tests.yml, which cannot run on the Linux leg without installing PowerShell and which mix a protocol client with Windows process handling. They are now tests/smoke/editor_host_smoke.py (the scenarios) and tests/smoke/n2_frames.py (the frame codec), Python 3 with only the standard library, so the same assertions run on Windows and on Linux with no package to install (both runners have Python). Gains: one copy of every assertion, so the two systems cannot drift apart; the script runs on a developer machine with the same command CI uses; Windows-only code (Add-Type, SslStream) is gone. Costs: the TLS check now uses Python's ssl module (OpenSSL) as the client, not .NET's SslStream, so a Schannel-only behaviour is no longer exercised; the script is no longer a place where Windows-specific host behaviour is visible in the step itself. The Play child smoke test (tests/editor-server/PlaySmokeTest.ps1) stays PowerShell: it needs a Windows renderer.

Conventions for headless tests

All tests run without a window, GPU or sound device. No test calls Application::Init; instead each test sets up only the parts it needs. Init does not require a window: without one it carries on and reports the window subsystem as Failed in its health result (the editor host relies on this in CI). Tests avoid it because a meaningful Init wants a real window and audio device, starts every subsystem in the shared singleton, and clears the quit flag that other tests may depend on. Every test in one executable shares the same process-wide singletons (Application, SceneManager, LuaRuntime, AudioSystem, Logger, ResourceLoader), so tests must leave them as they found them or tolerate earlier state.

Math types work without Math::InitializeSIMD(): Vector3, Quaternion and the 3×3/4×4 float matrices default to their scalar implementations (PR #24), and so does Vector4 PR #30. Tests should not need to initialise SIMD, and should not leave a non-scalar tier selected.

Pixels: the headless software renderer PR #51

Rendering is tested with real pixels through a SoftwareRenderer started with Initialize(nullptr, width, height), which never touches GL (headless mode), so it runs on the GPU-less CI runner. A test:

  1. constructs a SoftwareRenderer on the stack, asserts Initialize(nullptr, w, h), and sets a clear colour that no draw uses;
  2. runs a frame as Application::Render does: BeginFrame, SetViewProjection (a camera's matrices, or identity to draw in NDC), the draws (or Scene::Render, UISystem::Render), EndFrame, Present;
  3. reads the frame with ReadFramebuffer at the renderer's size (RGBA8, row 0 at the bottom, so y grows upwards like NDC);
  4. releases what components hold on the renderer (CleanupRenderResources), then calls Shutdown. Declare the renderer before the scene, so it outlives it.

Assertions are structural, never exact images or hashes (why): pixel counts and bounding boxes within a pixel or a few percent, colours exact only where they are flat (unlit and alpha-tested text are; lit shading and anything resampled are not), and comparisons between two frames of the same run. Pick colours that are 0 or 1 per channel so packing can't round them.

What cannot be tested headless

  • Application startup and the frame loop. Application::Init runs headless but only reports Failed health for the window and renderer, so the parts worth testing need a real window and audio device; Run() refuses to start without a valid window. The loop order on the Application page is not covered by a test; tests replicate parts of it by hand.
  • Windowing. Window::InitWindow with a window, window modes, resize callbacks. Only the uninitialised-window state (WindowHealthTest) and the no-window path (WindowlessWindowTest) PR #89 are tested.
  • GPU renderers. OpenGL and Vulkan need a context, so their pixels are not tested; the OpenGL text shader, including its effects (outline, shadow, softness) PR #66, is checked by eye, as is the rest of the OpenGL path, with the GPU smoke test PR #86. The software renderer is tested with real pixels in headless mode PR #51: its text shader, depth writes and read-back (SoftwareTextShaderTest, SoftwareHeadlessTest), material uniforms taken at DrawMesh and destroys during a frame in flight (SoftwareMaterialSnapshotTest, SoftwareResourceLifetimeTest) PR #55, a TextRenderer through Scene::Render and a UI Image and UIText PR #53 through the UI pass (SoftwareTextGoldenTest, SoftwareUIGoldenTest). Without pixels: the scene's draw order and per-draw state through a recording IRenderer (RenderQueueTest) and the software renderer's draw ordering (DrawOrderTest) PR #46; TextRenderer's meshes, resources and draws through a recording renderer (TextRendererTest) PR #49, and UIText's (UITextTest) PR #53; the polygon renderers' resource lifetime across renderers (PolygonRendererLifetimeTest) PR #52. The windowed software path (the GL blit in Present) is untested; RenderEditorFrame and the editor's RenderFrame command run in the CI smoke test on the windowless software renderer PR #89, which checks the frame's size and alpha but not its pixels.
  • Real input devices. Keyboard, mouse and gamepad state come from GLFW; tests use fake bindings.
  • Audible output. The null OpenAL backend accepts playback but produces nothing to check.
  • The editor server's rendering commands. Command handlers, payload and viewport limits, DeleteScene path checks and the command queue have unit tests, and on Windows EditorServerSocketTest drives a real loopback socket PR #33. RenderFrame on OpenGL needs a GL context and is untested; its frames are checked by eye in the Electron editor (the editor viewport) PR #86. The CI smoke test covers, against the real executable: Hello with the right and a wrong access token (--token-env) PR #89, GetEngineHealth, SetViewportSize and RenderFrame on the windowless software renderer (--renderer software; the frame's size and alpha, not its content) PR #89, GetAudio PR #56, RescanAssets with --project, the ready line with --port 0 PR #84, Shutdown, and --exit-on-disconnect PR #89. Playing streamed audio is the client's job: the Electron editor frontend unit-tests its decoding and jitter buffer in its own repository (frontend PR #1), but its Web Audio output, and playback against a real host, are not tested automatically (see Audio: client playback).

GPU smoke test PR #86

CI has no GPU, so the OpenGL renderer's pixels are never checked automatically. lua_project's scene is a checklist for checking them by eye on a machine with a GPU: seven stations, each showing one area. Every item has a caption saying what correct output looks like, and a HUD in the bottom-left corner names the station and what to look for there. Each station's camera keeps what matters in the top four fifths of a 16:9 or 4:3 window, clear of the HUD. One directional light, Sun, shines into the scene from the front upper left, the side the cameras are on (direction (0.4, −0.6, −0.7)); without it the engine's default light would come from behind the stations, leaving everything the cameras see at the ambient level. The same text as the HUD's is written to the log (GPU smoke test, Station 2/7: World text. Look for: ...), so a station can still be judged if text doesn't draw at all.

CI still builds the scene: LuaProjectSceneTest runs assets/scene.lua headless, checks every station's objects and components, clicks the buttons (Button::Click) and checks the counters, and EveryProjectAssetLoads loads every .mat file (with the texture it names), image and model under lua_project/assets, failing on a glTF import warning. A broken asset or a script error is caught there; only the pixels need a person.

The editor viewport

The editor host renders off screen on OpenGL, into a framebuffer of the client's viewport size, and sends each frame as RGBA, top row first (viewport frames) PR #85. Nothing in CI draws through that path, so it is checked separately, with the editor host and the Electron editor client (EpicNicks/N2Engine-Electron-Frontend) and lua_project/scenes/viewport_check.scene, a scene that looks different upside down, mirrored or with red and blue swapped:

  1. From the repository root (the --project path is relative to the current directory), build and start the host with lua_project as its project, and wait for its ready line, N2EditorHost ready port=9999 (see the ready line): 
    cmake --build build --config Debug --target N2EditorHost
build/bin/Debug/N2EditorHost.exe --port 9999 --project lua_project
  2. In a clone of the client repository, with Node 21 or later: npm install, then npm start.
  3. Press Open Project and pick the lua_project folder; press Connect if the status doesn't already say connected (the client connects to localhost:9999).
  4. In the file tree, open scenes and click viewport_check.scene, which the client sends with LoadScene.
  5. Look at the viewport: a blue cube on the left, a red sphere on the right, a green bar along the bottom and white text, "Top: this text, upright", at the top, reading left to right. The host logs one expected warning here, No lights found in scene 'Viewport Check'. Using default light.: the scene's shapes are unlit, so it doesn't matter.
  6. Resize the editor window. This step needs the client from frontend PR #9 (EpicNicks/N2Engine-Electron-Frontend) or later: older clients send the canvas's drawing-buffer size, which their render loop sets to the size of the last frame, so the viewport size never changes and the frame is only scaled. With PR #9 the client sends the viewport's size times devicePixelRatio, and the correct result is that the frame is rendered again at the new size: still sharp, not stretched or blurred, with the shapes keeping their proportions (the camera's aspect follows).

Failure looks like: the picture upside down (rows not flipped), the cube red and the sphere blue (BGRA read back as RGBA), with a PR #9 or later client, a blurred, stretched or cropped frame after a resize (the render target didn't follow the viewport size), a black viewport or an error "Couldn't create a WxH render target" (the framebuffer is incomplete), or "No renderer available" (see Engine health in the client).

Open question

No line-ending policy is written down or enforced (no .gitattributes, no CI check). Whether the repository should normalise to LF is undecided.

Adding a test

  1. Pick the executable by module: engine behaviour under tests/engine/<area>/, pure math under tests/math/, protocol encoding under tests/editor-server/.
  2. Create <Area>Tests.cpp (or add to an existing file for the same area). No CMake edit is needed; the directory is globbed. Re-run the CMake configure step so the new file is picked up.
  3. Name suites <Thing>Test and cases as a sentence describing the behaviour (ParentingARootRemovesItFromTheRoots). Other pages cite these names, so a good name documents the guarantee.
  4. Do not call Application::Init. Set up only what you need using the fixtures above; guard PhysX-dependent files with #ifdef N2ENGINE_PHYSX_ENABLED so the PhysX OFF leg still builds.
  5. Leave shared singletons as you found them: unique scene names, distinct Lua globals, restored Logger settings, scalar SIMD, physics backend removed.
  6. Build and run locally with --gtest_filter and, for anything touching shared state, --gtest_repeat=2. CI then runs it in all three legs (Debug with and without PhysX, Release with PhysX), so do not rely on assert for checks the test needs.
#include <gtest/gtest.h>

#include "engine/GameObjectScene.hpp"
#include "engine/sceneManagement/SceneManager.hpp"

using namespace N2Engine;

TEST(MyFeatureTest, AddedRootCanBeFoundByUUID)
{
    // A name unique to this test: re-adding a stored name replaces that scene
    SceneManager::AddScene(Scene::Create("MyFeatureTest_FindByUUID"), true);
    SceneManager::ProcessAnyPendingSceneChange();
    Scene &scene = SceneManager::GetCurSceneRef();

    auto go = GameObject::Create("Thing");
    scene.AddRootGameObject(go);

    EXPECT_EQ(scene.FindGameObjectByUUID(go->GetUUID()), go);
}
