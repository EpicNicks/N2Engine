Testing & CI

N2Engine's tests are GoogleTest executables, one per module, run headless through CTest. CI builds and runs them on Windows in Debug with and without PhysX and in Release with PhysX, then starts the editor host and talks to it over TCP. This page covers the layout, how to run the tests, the CI workflow, the conventions headless tests follow, and how to add one.

Each subdirectory's CMakeLists.txt follows the same pattern:

  • Sources are collected with file(GLOB_RECURSE ... "*.cpp" "*.cc" "*.cxx"), so any source file in the directory tree is part of the executable. The glob runs at configure time (no CONFIGURE_DEPENDS): after adding a file, re-run the CMake configure step.
  • Linked with GTest::gtest and GTest::gtest_main; no test defines its own main.
  • C++23, no extensions, warnings at /W4 (MSVC) or -Wall -Wextra.
  • On MSVC (and clang-cl) the root CMakeLists.txt defines _ENABLE_EXTENDED_ALIGNED_STORAGE for every target PR #139: newer MSVC STL toolsets static_assert (C2338) when stable_sort's temporary buffer holds an over-aligned element type. tests/math/StableSortAlignedTests.cpp (StableSortAlignedTest) stable-sorts an alignas(16) 80-byte type with std:: and std::ranges:: and fails to compile without it.
  • Registered with a single add_test(NAME <exe> COMMAND <exe>). CTest therefore sees six tests, one per executable, not one per GoogleTest case. Use --gtest_filter on the executable to run individual cases.

Source: CMakeLists.txt; tests/CMakeLists.txt; tests/*/CMakeLists.txt

One live run per pull request. tests.yml has a concurrency group per pull request with cancel-in-progress on for pull_request events only: a push to the PR, or "Update branch", cancels the run of the older head, which shows as cancelled; wait on the newest head's run. Docs-only pull requests skip the builds. A first job, changes (docs-only check), lists the files the PR changes (git diff from the merge base of the base branch to the PR head, a rename counting as a delete plus an add). The run lists 10 check-runs (the 9 legs, the web leg included, plus changes (docs-only check)). The protocol job always runs (it takes seconds).

Design decision: skip with job-level if, not paths-ignore PR #150

A paths-ignore filter on the trigger would leave the required check linux (Release, x86_64, Clang) never reported, and the PR would wait for it forever. A skipped job reports, so the check names stay and the PR can merge. If changes itself fails, the jobs that need it are skipped and changes shows red, so the run is red rather than green. The path rule is a plain case in shell, not a third-party paths filter. No test reads docs/, which is why it can be skipped.

ccache on the Linux legs PR #154

The three Linux jobs (x86_64 Clang, arm64 Clang, x86_64 GCC 14) build through ccache (ccache is on their apt line; CMake gets -DCMAKE_C_COMPILER_LAUNCHER=ccache -DCMAKE_CXX_COMPILER_LAUNCHER=ccache). The first run after this change is cold; the first warm numbers come from the first pull request after master has saved a cache.

Design decision: only master saves the compiler cache PR #154

GitHub caches are immutable and a cache made on a pull request is readable only by that pull request, while the default branch's caches are readable by all. Saving from every pull request would fill the 10 GB repository quota (three legs at up to 1 GB each, once per push) and evict the useful master caches; saving only from master adds three entries per merge. The cost is that a pull request's own objects are not kept for its next push: it rebuilds what differs from master, which is what the cache is for anyway. Nothing deletes older ccache-linux-* entries, so after a few merges the repository sits near the 10 GB quota and GitHub evicts the least recently used caches; expect the total to stay quota-filling rather than 3 GB.

Design decision: patch the vendored sol2 type-name path, instead of rewriting the engine's binding lambdas PR #119

PhysX determinism and the 1-ulp experiment PR #161

PhysXDeterminismTests.cpp keeps two kinds of result apart. Pixels: the headless software renderer PR #51

Rendering is tested with real pixels through a SoftwareRenderer started with Initialize(nullptr, width, height), which never touches GL (headless mode), so it runs on the GPU-less CI runner. A test:

  1. constructs a SoftwareRenderer on the stack, asserts Initialize(nullptr, w, h), and sets a clear colour that no draw uses;
  2. runs a frame as Application::Render does: BeginFrame, SetViewProjection (a camera's matrices, or identity to draw in NDC), the draws (or Scene::Render, UISystem::Render), EndFrame, Present;
  3. reads the frame with ReadFramebuffer at the renderer's size (RGBA8, row 0 at the bottom, so y grows upwards like NDC);
  4. releases what components hold on the renderer (CleanupRenderResources), then calls Shutdown. Declare the renderer before the scene, so it outlives it.

Assertions are structural, never exact images or hashes (why): pixel counts and bounding boxes within a pixel or a few percent, colours exact only where they are flat (unlit and alpha-tested text are; lit shading and anything resampled are not), and comparisons between two frames of the same run. Pick colours that are 0 or 1 per channel so packing can't round them.

Without a Vulkan device or validation layer a test GTEST_SKIPs (so a Windows machine without a driver still passes), unless the environment variable N2_REQUIRE_VULKAN=1 is set, which makes that a failure. The two Clang Test steps (x86_64 and arm64) set it, and also N2_VULKAN_EXPECT_CPU_DEVICE=1, which fails unless the device is a CPU device (lavapipe), so a green leg means the tests ran on lavapipe. The Windows legs only compile the Vulkan code and skip the tests, and the GCC 14 leg builds with -DN2ENGINE_RENDERER_VULKAN=OFF (no Vulkan headers, loader or driver installed), so the tests do not exist there.

To run them locally on Linux: sudo apt install mesa-vulkan-drivers vulkan-validationlayers, build renderer_tests, then VK_DRIVER_FILES=$(ls /usr/share/vulkan/icd.d/lvp_icd*.json | head -n 1) N2_REQUIRE_VULKAN=1 build/bin/renderer_tests --gtest_filter='*Vulkan*' (leave VK_DRIVER_FILES out to use your GPU's driver, and N2_REQUIRE_VULKAN out to let a missing device skip). On Windows the tests use the installed driver and validation layer (the Vulkan SDK ships the layer) and skip without a device. Setting N2_VULKAN_VALIDATION=1 turns validation on for the engine itself (the editor, a game); it is off by default in a Release build.

The Vulkan draw tests and the shader build step PR #144

Since stage B the Vulkan tests draw: real frames of the built-in unlit shader run on lavapipe with validation on, are read back with ReadFramebuffer and are checked with exact colours and pixel counts (a quad on a pixel boundary covers exactly its pixels), so the clip-space fix (the vertex shaders' z remap and the negative-height viewport), the winding and cull, the depth state, the upright texture and the IndexRange rules are proved with pixels. The Mesh golden scenes are drawn on both Vulkan and the software renderer and compared pixel by pixel (CrossBackendDiff.hpp). The tests that draw need the compiled shaders:

  • The shader build step. renderer/CMakeLists.txt compiles renderer/shaders/vulkan/*.vert|frag to SPIR-V with glslangValidator (or glslc) when the renderer is built, and prints Vulkan shader compiler: <tool> at <path> (--version: ...) in the configure log of every leg (look for it in the Configure step). The Linux legs and the Docker build stage have glslang-tools. The Windows legs use the SDK's: the Vulkan SDK action's stripdown: true cache keeps glslangValidator.exe, so they compile the shaders like Linux (the Configure log shows Vulkan shader compiler: glslangValidator at C:/VulkanSDK/<version>/Bin/glslangValidator.exe), and have no Vulkan device, so the device tests skip while the parity test runs.
  • Without the tool the configure warns ("Vulkan built-in shaders not compiled") and the build still succeeds; VulkanRenderer::HasBuiltInShaders() is then false and the draw tests GTEST_SKIP with that reason (N2_REQUIRE_BUILT_IN_SHADERS() in VulkanTestFixture.hpp), unless N2_REQUIRE_VULKAN=1, where they fail, so the Linux legs can never pass by silently skipping every draw. VulkanTest.TheBuiltInShadersAreCompiledIntoThisBuild is that check on its own, and VulkanTest.WithoutCompiledShadersTheRendererStillClearsAndReadsBackAndDrawsNothing exercises the fallback when a build is in it.
  • The parity test needs no device (it reads the GLSL as text), so it runs on every leg that builds the Vulkan renderer, including the Windows ones, where the device tests skip. The GCC 14 leg builds with N2ENGINE_RENDERER_VULKAN=OFF: it needs no glslang, no Vulkan package, and none of these tests exist there.

The lit cross-backend criterion PR #148

The lit and PBR scenes are drawn on Vulkan and on a headless software renderer and compared by CrossBackendDiff.hpp. Unlit, nearest-sampled scenes keep the strict rule (no compared pixel more than 2/255 off in any channel, nothing left out). For lit scenes, where the two backends round differently and sRGB textures are decoded before filtering on Vulkan and after it on the software renderer, the proposal's lit rule applies (Diff::Lit()): the comparison passes only when

  • the mean error over the compared pixels is at most 2/255, where a pixel's error is its largest colour-channel difference (the stricter of the two readings: a mean over the three channels would be smaller), so pixels between the tolerance and the second threshold count through the mean (an image where every pixel is off by 7/255 fails, which the harness tests prove); and
  • at most 1% of the compared pixels differ by more than 8/255; and
  • after leaving out a 1-pixel border around each coverage edge (rasterisation tie rules differ), where coverage comes from a flat unlit mask render of the same geometry on each backend (Options::coverageA/B; a flat-colour frame is its own mask): an edge pixel is one whose covered-ness differs from a neighbour's in either mask, or differs between the two masks. It never looks at the lit shading, so a lit object one backend shades black fails instead of being left out, and so a smoothly lit surface is not taken for an edge (the strict mode's colour-difference definition would have left out nearly every pixel of a lit cube); and
  • no more than 25% of the image was left out, and something was compared, so an over-broad exclusion can never pass vacuously.

The measured numbers of every lit scene are printed in the test log ([ cross-diff ] ... lines: compared and excluded pixels, mean error, share over 8/255, the largest difference) and are listed in PR #148. Measured on lavapipe (llvmpipe) in the Linux Clang legs, all 115 lit comparisons (the renderer-level lighting, normal-map and PBR draws, the lit cube, the model and both edit-mode goldens) agreed with the software renderer to a mean error of at most 0.033/255 and a largest channel difference of 1/255, with no pixel over 8/255. These figures were measured on lavapipe before the coverage masks replaced the "not the clear colour" definition. The mask change compares more pixels (the spot-cone falloff pixels that were previously excluded), and the figures have not been re-measured since: the CI logs do not print them, and the tests pass their thresholds. The edge exclusion of each scene is printed in the [ cross-diff ] lines (the cap is 25% of the image); no scene needed a looser threshold. The software renderer does not clamp directional lights to two, so the five-light clamp is checked on Vulkan only.

The blended Vulkan goldens and their reference PR #158

Stage D of #43 makes Vulkan blend like OpenGL, and the software renderer cannot blend (it draws a blended draw opaque). So a blended Vulkan frame is never compared with one software frame: that would encode Software-only behaviour. Per the proposal, an assertion that encodes Software-only behaviour gets a per-backend expectation, and Vulkan expects OpenGL's. Two checks replace the single diff, both in BlendReference.hpp and both device-free (BlendReferenceTests.cpp tests the helpers, so they run on every leg that builds the Vulkan tests):

  • Composite reference. Each blended layer is drawn opaque and alone on the software renderer (its colour and the pixels it covers); the reference frame is built on the CPU with OpenGL's equation, layer by layer in submission order, over the software frame of everything behind it: round(a * src + (1 - a) * dst), additive min(255, round(a * src + dst)), and the alpha channel by the same factors. The Vulkan frame is then compared with it by Diff::Compare: the strict rule for nearest-sampled unlit scenes, the lit rule for linear-filtered ones (the linear sprite gradient). The composite's own rounding is inside the 2/255 of the strict mode; no extra allowance was needed.
  • Opaque mask. Where the layers of a scene cannot be separated, the strict diff runs on the pixels no blended draw covers (the mask grown by a border so rasterisation tie rules at the blended edges do not count: Diff::Options::ignore, ignored pixels are counted as excluded) against the software frame, and the blended parts get per-backend structural expectations at interior pixels: the exact OpenGL-equation colour, within 1 or 2. The mixed-submesh mesh golden and the translucent Image over a scene mesh use it.

The scenes, by rule: the mixed opaque and blended submeshes (opaque part strict, blended half by expectation); the upright sprite (strict); a translucent checker sprite (strict); the linear sprite gradient (lit); a translucent Image over a scene mesh (opaque part strict, the Image by expectation); two overlapping half-alpha quads through the Transparent queue, both depth orders (the full composite, far then near, strict on every pixel). The particle and world-canvas goldens and the renderer-level blend tests are structural: exact colours and counts at interior pixels, computed with the same formula. Measured on lavapipe in the Linux Clang legs, every compared scene agreed exactly, a mean error of 0/255 and a largest difference of 0/255: the upright sprite 1600 pixels compared, the translucent checker 1600, the gradient 512, the translucent Image over a mesh 1920 compared and 2176 left out (53% of the image, by the Image's mask), the mixed submeshes 3196 compared and 900 left out (22%). The two-quad Transparent-queue scene was added in review after those measurements; its numbers are printed in the test log ([ cross-diff ] transparent queue back to front). No scene needed a looser threshold, and the strict mode is unchanged.

One divergence is known and asserted, not hidden: a blended lit draw in linear lighting. OpenGL blends it in linear space (its target is sRGB with GL_FRAMEBUFFER_SRGB on for that draw), while Vulkan's target is R8G8B8A8_UNORM and the lit shader encodes in the shader, so Vulkan blends the encoded values (design decision). Unlit, text, UI, particle and Gamma-lit blends match OpenGL; ABlendedLitDrawInLinearLightingBlendsTheEncodedValuesUnlikeGL documents the Linear case.

All the device tests of this section run on lavapipe in the two Linux Clang legs (N2_REQUIRE_VULKAN=1 and N2_VULKAN_EXPECT_CPU_DEVICE=1 turn a skip into a failure), skip on the Windows legs (no device) and do not exist on the GCC 14 leg (Vulkan off); the harness tests, the lighting block tests and the parity test need no device and run on every leg that builds the Vulkan tests.

The Vulkan text tests and the antialiased cross-check PR #165

Stage E of #43 draws text on Vulkan with a port of OpenGL's SDF shader, so Vulkan text is antialiased and blended where the software renderer's is alpha-tested (a glyph pixel is the text colour or untouched, and it writes depth). An assertion that encodes the software behaviour gets OpenGL's expectation on Vulkan, with a comment at the assertion; the software tests are untouched. The text tests are VulkanTextShaderTests.cpp (renderer level) and the three golden files (engine level) in the table above; the per-backend expectations:

  • Alpha-tested pixels become blended ones. Where a software test asserts that every touched pixel is exactly the text colour, the Vulkan test asserts that every pixel lies on the straight line from the background colour to the text colour (no other hue) and that in-between pixels exist, and then runs the software test's structure (bounding boxes against the layout, column runs, counts, alignment) on the frame thresholded at half coverage: the coverage ramp is centred on the 0.5 iso-line the software alpha test cuts at.
  • Transparent text writes no depth. The software test that draws an opaque quad behind the text afterwards and finds the glyph intact becomes, on Vulkan, that the quad covers the whole frame (the Transparent state writes no depth, as on OpenGL).
  • Layered effects (face, outline, shadow, passes) are read with the frame classified to the nearest layer colour, which cuts at the 0.5 iso-line of each layer, and the software tests' exact set equalities become allowances of a few pixels (2% of the layer, at least 6) where they depend on the pixels exactly on that line. Where the software renderer makes two frames equal because of the alpha test and OpenGL's equation does too (the same uniforms, the clamped effects, an order above zero), the test compares Vulkan frames byte for byte. Softness, which the software renderer ignores, is an effect on Vulkan, so the “effects off” case leaves it out and a separate check shows it widening the ramp around the same ink.

The cross-backend comparison of antialiased text. The same scene is rendered on the software renderer and on Vulkan, large (320×192 for the TextRenderer and the effects, 400×160 for the UIText, and 64×64 for the renderer-level disc), so that glyph stems are wide enough to have interiors, and compared by CrossBackendDiff's strict mode (2/255 per channel, never loosened) on the pixels away from the edges only:

  • Coverage-edge exclusion. A pixel is left out when its coverage (not the background colour) differs from a neighbour's, in either frame or between the two, with edge border 1 (the ramp is about one pixel wide, up to 1.4 at 45 degrees, and the software cut and the Vulkan ramp are centred on the same iso-line). For the frame of several layers (face, outline, shadow) a pixel is an edge when its colour differs from a neighbour's in either frame, so the boundaries between layers are left out too.
  • A cap on what is left out (15% for the disc, 25% for the glyph scenes, 40% for the three-layer one) and a floor on what is compared (50 ink pixels for the disc, 300 for the glyph scenes, 500 for the three-layer one: the glyph interiors), so the comparison is never of the background alone.
  • The area check. The sum of the Vulkan blend weights (how far each pixel lies from the background towards the text colour) against the software ink pixel count, within 4% (disc) or 5% (glyphs), so a glyph that is too thin or too fat fails. For the three-layer scene the Vulkan frame is classified to the nearest layer colour and the pixel counts are compared with the software layers': the face and the outline together, and the shadow, within 5% (or 10 pixels), the face and the outline each alone within 12% (their shared boundary is the one a CPU driver's rounding of a filtered sample moves; the numbers below).

Design decision: Vulkan runs on a software driver in CI PR #136

The runners have no GPU, and OpenGL's pixels are untestable for that reason (below). Vulkan does not have to be: the loader finds any driver, and Mesa's lavapipe is a conformant CPU one on Ubuntu 24.04. Running the real backend there, with the validation layer failing tests on errors and leaks, checks initialisation, synchronisation, layouts and shutdown on every PR. It does not check what only a real driver shows (format support, memory types, timing), the swapchain and present path (stage F of #43, which needs a GPU), or speed. Decided on #43 (proposal of 2026-10-14).

GPU smoke test PR #86

CI has no GPU, so the OpenGL renderer's pixels are never checked automatically. lua_project's scene is a checklist for checking them by eye on a machine with a GPU: seven stations, each showing one area. Every item has a caption saying what correct output looks like, and a HUD in the bottom-left corner names the station and what to look for there. Each station's camera keeps what matters in the top four fifths of a 16:9 or 4:3 window, clear of the HUD. One directional light, Sun, shines into the scene from the front upper left, the side the cameras are on (direction (0.4, −0.6, −0.7)); without it the engine's default light would come from behind the stations, leaving everything the cameras see at the ambient level. The same text as the HUD's is written to the log (GPU smoke test, Station 2/7: World text. Look for: ...), so a station can still be judged if text doesn't draw at all.

CI still builds the scene: LuaProjectSceneTest runs assets/scene.lua headless, checks every station's objects and components, clicks the buttons (Button::Click) and checks the counters, and EveryProjectAssetLoads loads every .mat file (with the texture it names), image and model under lua_project/assets, failing on a glTF import warning. A broken asset or a script error is caught there; only the pixels need a person.

Particles: CPU and GPU

  • The CPU backend runs everywhere, with or without a GPU, so the station always works and every sign says running: CPU by default. Auto picks PhysX when the physics backend offers a GPU particle backend and the CPU otherwise; CPU always runs on the CPU; PhysX asks for the GPU one and falls back to the CPU, with one warning in the log per emitter, where there is none. The sign says so: running: CPU (PhysX asked: fell back), and the info sign at the top of the station says it too. Pressing K replaces the three emitters, because a system reads its backend only when it starts.
  • The PhysX GPU backend needs a Windows PC with an NVIDIA GPU, a build with PhysX, the project setting physics.gpu set to auto or on PR #129. lua_project passes its project folder to Application::Init, which reads physics.gpu from project.n2proj, so the demo enables it like any project: edit lua_project/project.n2proj so that "settings" holds { "physics": { "gpu": "auto" } } (the default, off, is not changed in the repository) and restart. The info sign shows Physics.IsGpuAvailable(); when it says true, Auto and PhysX should show running: PhysX GPU and compare against CPU with K.
  • Water, sand and smoke set pbdMaterial (Water, Sand, Smoke, the PBD preset the PhysX backend uses: water flows and pools, sand piles up, smoke drifts) and are also tuned with the fields the CPU backend reads (emission rate, cone, speed, lifetime, size, colours, gravity scale, drag, the ground plane); the CPU backend ignores pbdMaterial, the PhysX backend ignores the ground plane (it collides with the scene's colliders, so the demo's floor must be a collider). Particles are billboards on the OpenGL and software renderers only: the Vulkan renderer draws them opaque for now, as it has no blending yet (Particles). The software renderer cannot blend, so the water and the smoke are opaque there.

Soft bodies: CPU and GPU PR #145

  • Every body runs on the CPU today. Without a GPU (every CI leg, Linux, any machine with physics.gpu off, which is the default) the CPU backend simulates every body and the signs say running: CPU. Asking for PhysX with J shows running: CPU (PhysX asked: fell back) and the info sign says so, with one warning per body in the log. The PhysX GPU backend (a deformable-volume backend for a Windows PC with an NVIDIA GPU and physics.gpu auto or on) does not exist yet: until it merges the physics backend offers no soft-body backend anywhere, so a sign never says PhysX GPU today. Pressing J replaces the six bodies, because a SoftBody reads its backend only when it starts, and they fall again from their start pose.
  • The floor is two things. The CPU backend collides only with the plane y = groundHeight (SetGround(true, floorTop) on every body); the PhysX backend will collide with the scene's colliders, so the floor also has a static BoxCollider at the same height.
  • The signs show the resolution, not a tetrahedron count: the Lua API has no tetrahedron or node getter. Each body is a MeshRenderer and a SoftBody on one object with no Rigidbody (see Soft bodies).
  • Rendering. A soft body is drawn by its MeshRenderer, so OpenGL and the software renderer draw it. The Vulkan renderer draws the unlit and lit shaders since stages B and C of #43, so a soft body's lit mesh is drawn there too; no test draws one on Vulkan.

The editor viewport

The editor host renders off screen on OpenGL, into a framebuffer of the client's viewport size, and sends each frame as RGBA, top row first (viewport frames) PR #85. Nothing in CI draws through that path, so it is checked separately, with the editor host and the Electron editor client (EpicNicks/N2Engine-Electron-Frontend) and lua_project/scenes/viewport_check.scene, a scene that looks different upside down, mirrored or with red and blue swapped:

  1. From the repository root (the --project path is relative to the current directory), build and start the host with lua_project as its project, and wait for its ready line, N2EditorHost ready port=9999 (see the ready line): 
    cmake --build build --config Debug --target N2EditorHost
build/bin/Debug/N2EditorHost.exe --port 9999 --project lua_project
  2. In a clone of the client repository, with Node 21 or later: npm install, then npm start.
  3. Press Open Project and pick the lua_project folder; press Connect if the status doesn't already say connected (the client connects to localhost:9999).
  4. In the file tree, open scenes and click viewport_check.scene, which the client sends with LoadScene.
  5. Look at the viewport: a blue cube on the left, a red sphere on the right, a green bar along the bottom and white text, "Top: this text, upright", at the top, reading left to right. The host logs one expected warning here, No lights found in scene 'Viewport Check'. Using default light.: the scene's shapes are unlit, so it doesn't matter.
  6. Resize the editor window. This step needs the client from frontend PR #9 (EpicNicks/N2Engine-Electron-Frontend) or later: older clients send the canvas's drawing-buffer size, which their render loop sets to the size of the last frame, so the viewport size never changes and the frame is only scaled. With PR #9 the client sends the viewport's size times devicePixelRatio, and the correct result is that the frame is rendered again at the new size: still sharp, not stretched or blurred, with the shapes keeping their proportions (the camera's aspect follows).

Failure looks like: the picture upside down (rows not flipped), the cube red and the sphere blue (BGRA read back as RGBA), with a PR #9 or later client, a blurred, stretched or cropped frame after a resize (the render target didn't follow the viewport size), a black viewport or an error "Couldn't create a WxH render target" (the framebuffer is incomplete), or "No renderer available" (see Engine health in the client).

Line endings

The repository has no .gitattributes, and line endings in the index are mixed. git ls-files --eol on master shows, for example:

Across engine/, math/, renderer/, tests/, editor-server/ and .github/, roughly two thirds of tracked files are CRLF in the index; files added or largely rewritten recently tend to be LF. In practice: keep a file's existing line endings when you edit it, so diffs show only real changes, and expect new files to be LF. With core.autocrlf=true on Windows the working copy shows CRLF either way, so check the index with git ls-files --eol <path> (the i/ column) rather than an editor.

Open question

No line-ending policy is written down or enforced (no .gitattributes, no CI check). Whether the repository should normalise to LF is undecided.

Adding a test

  1. Pick the executable by module: engine behaviour under tests/engine/<area>/, pure math under tests/math/, protocol encoding under tests/editor-server/.
  2. Create <Area>Tests.cpp (or add to an existing file for the same area). No CMake edit is needed; the directory is globbed. Re-run the CMake configure step so the new file is picked up.
  3. Name suites <Thing>Test and cases as a sentence describing the behaviour (ParentingARootRemovesItFromTheRoots). Other pages cite these names, so a good name documents the guarantee.
  4. Do not call Application::Init. Set up only what you need using the fixtures above; guard PhysX-dependent files with #ifdef N2ENGINE_PHYSX_ENABLED so the PhysX OFF leg still builds.
  5. Leave shared singletons as you found them: unique scene names, distinct Lua globals, restored Logger settings, scalar SIMD, physics backend removed.
  6. Build and run locally with --gtest_filter and, for anything touching shared state, --gtest_repeat=2. CI then runs it in all three legs (Debug with and without PhysX, Release with PhysX), so do not rely on assert for checks the test needs.
#include <gtest/gtest.h>

#include "engine/GameObjectScene.hpp"
#include "engine/sceneManagement/SceneManager.hpp"

using namespace N2Engine;

TEST(MyFeatureTest, AddedRootCanBeFoundByUUID)
{
    // A name unique to this test: re-adding a stored name replaces that scene
    SceneManager::AddScene(Scene::Create("MyFeatureTest_FindByUUID"), true);
    SceneManager::ProcessAnyPendingSceneChange();
    Scene &scene = SceneManager::GetCurSceneRef();

    auto go = GameObject::Create("Thing");
    scene.AddRootGameObject(go);

    EXPECT_EQ(scene.FindGameObjectByUUID(go->GetUUID()), go);
}
