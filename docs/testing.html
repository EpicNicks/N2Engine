Testing & CI

N2Engine's tests are GoogleTest executables, one per module, run headless through CTest. CI builds and runs them on Windows in Debug with and without PhysX and in Release with PhysX, then starts the editor host and talks to it over TCP. This page covers the layout, how to run the tests, the CI workflow, the conventions headless tests follow, and how to add one.

Each subdirectory's CMakeLists.txt follows the same pattern:

  • Sources are collected with file(GLOB_RECURSE ... "*.cpp" "*.cc" "*.cxx"), so any source file in the directory tree is part of the executable. The glob runs at configure time (no CONFIGURE_DEPENDS): after adding a file, re-run the CMake configure step.
  • Linked with GTest::gtest and GTest::gtest_main; no test defines its own main.
  • C++23, no extensions, warnings at /W4 (MSVC) or -Wall -Wextra.
  • On MSVC (and clang-cl) the root CMakeLists.txt defines _ENABLE_EXTENDED_ALIGNED_STORAGE for every target PR #139: newer MSVC STL toolsets static_assert (C2338) when stable_sort's temporary buffer holds an over-aligned element type. tests/math/StableSortAlignedTests.cpp (StableSortAlignedTest) stable-sorts an alignas(16) 80-byte type with std:: and std::ranges:: and fails to compile without it.
  • Registered with a single add_test(NAME <exe> COMMAND <exe>). CTest therefore sees six tests, one per executable, not one per GoogleTest case. Use --gtest_filter on the executable to run individual cases.

Source: CMakeLists.txt; tests/CMakeLists.txt; tests/*/CMakeLists.txt

Building and running

Three CMake options matter for tests:

OptionDefaultEffect
N2ENGINE_BUILD_TESTSONFetch GoogleTest and build the four test executables.
N2ENGINE_USE_PHYSXONUse PhysX. On Windows PR #127 the slim archive physx-windows-x86_64-5.6.1-slim.zip is downloaded from the physx-dependencies-windows-5.6.1 release into external/PhysX/physx/bin at configure time and must match the SHA256 pinned in cmake/PhysXWindowsHashes.cmake; if the download fails or the hash differs, PhysX is turned off with a warning. An extracted tree from the old bin.zip (same file names, no hash stamp) is still reused. On Linux PR #120 the static Release archive for x86_64 or aarch64 is downloaded the same way, from the physx-dependencies-linux-5.6.1 release, and must match the SHA256 pinned in cmake/PhysXLinuxHashes.cmake or PhysX is turned off with a warning. PhysX is also turned off for MinGW/GCC on Windows. With PhysX off, N2ENGINE_PHYSX_ENABLED is not defined and PhysicsTests.cpp compiles to nothing.
N2ENGINE_RENDERER_VULKAN PR #136ONBuild the Vulkan renderer (status), with its vendored VulkanMemoryAllocator (external/VulkanMemoryAllocator/, MIT, PR #142; THIRD_PARTY_NOTICES.md). The renderer target defines N2ENGINE_RENDERER_VULKAN as 1 or 0 for everything that links it (renderer/common/RendererConfig.hpp defaults it to 1).

N2ENGINE_TEXT_FREETYPE PR #47OFFFetch and build FreeType and add the FreeType font backend. Every font test in text_tests then also runs against FreeType, and the cross-backend tests compare it with stb_truetype.

The same commands CI uses (Visual Studio generator, multi-config):

cmake -S . -B build -A x64 -DN2ENGINE_BUILD_TESTS=ON -DN2ENGINE_USE_PHYSX=ON
cmake --build build --config Debug --parallel
ctest --test-dir build --build-config Debug --output-on-failure

Executables land in build/bin/<Config>/ (build/bin/Debug/ here). For a Release build, pass --config Release to the build and --build-config Release to CTest; the test executables, the editor host and the copied PhysX DLLs are then in build/bin/Release/. To run part of one:

build/bin/Debug/engine_tests.exe --gtest_filter=CoreRobustnessTest.*
build/bin/Debug/engine_tests.exe --gtest_filter=SceneStorageTest.* --gtest_repeat=3

Note

Debug builds define N2ENGINE_DEBUG (Release builds do not, and define NDEBUG, so assert is compiled out). Tests never call Application::Init, so the debug console subscriber is not installed and engine log output is not printed during tests unless a test subscribes to Logger::logEvent.

Design decision: skip with job-level if, not paths-ignore PR #150

A paths-ignore filter on the trigger would leave the required check linux (Release, x86_64, Clang) never reported, and the PR would wait for it forever. A skipped job reports, so the check names stay and the PR can merge. If changes itself fails, the jobs that need it are skipped and changes shows red, so the run is red rather than green. ccache on the Linux legs PR #154

The three Linux jobs (x86_64 Clang, arm64 Clang, x86_64 GCC 14) build through ccache (ccache is on their apt line; CMake gets -DCMAKE_C_COMPILER_LAUNCHER=ccache -DCMAKE_CXX_COMPILER_LAUNCHER=ccache). The Windows legs have their own ccache (below); the Docker build does not use it. The cache directory is .ccache in the workspace, capped at 1 GB and compressed; CCACHE_COMPILERCHECK=content keys on the compiler binary, and CCACHE_BASEDIR with CCACHE_NOHASHDIR make the checkout path irrelevant. Each leg has its own cache (ccache-linux-x86_64-clang20-, ccache-linux-arm64-clang20-, ccache-linux-x86_64-gcc14- plus the run id), so different compilers and architectures never share objects. The Vulkan shader step (glslangValidator) and the PhysX and FetchContent downloads are not touched by it.

Only pushes to master save. Every run restores the newest cache of its leg (a pull request reads the one master saved); only a push to master saves one, after the tests, so a pull request run, a cancelled run or a workflow_dispatch run never writes to it. All cache steps are continue-on-error: a miss or a failed restore or save only makes a cold build. Reading the result: each Linux job's summary page has a "ccache (<leg>)" section with the restored cache key (none (cold build) when there was none) and ccache -s from zeroed statistics, so "Hits" against "Misses" (and the "Hits" percentage) are this run's hit rate, and "Cache size" is what the next master run will save. The first run after this change is cold; the first warm numbers come from the first pull request after master has saved a cache.

Design decision: only master saves the compiler cache PR #154

GitHub caches are immutable and a cache made on a pull request is readable only by that pull request, while the default branch's caches are readable by all. Saving from every pull request would fill the 10 GB repository quota (three legs at up to 1 GB each, once per push) and evict the useful master caches; saving only from master adds three entries per merge. The cost is that a pull request's own objects are not kept for its next push: it rebuilds what differs from master, which is what the cache is for anyway. Nothing deletes older ccache-linux-* entries, so after a few merges the repository sits near the 10 GB quota and GitHub evicts the least recently used caches; expect the total to stay quota-filling rather than 3 GB.

Editor host TLS smoke test PR #112 PR #115

Only in the legs built with N2ENGINE_EDITOR_TLS (the Windows TLS ON leg and the two Linux Clang legs, x86_64 and arm64): editor_host_smoke.py --scenario tls. It starts the real N2EditorHost with --tls --port 0 --renderer software --exit-on-disconnect, reads the ready line and requires exactly ^N2EditorHost ready port=(\d+) tls=1 fingerprint=([0-9a-f]{64})$, and checks that host-cert.pem and host-key.pem are in the user data folder's editor-tls (%APPDATA%\N2Engine\editor-tls on Windows, $XDG_DATA_HOME/n2engine/editor-tls or $HOME/.local/share/n2engine/editor-tls elsewhere), that the certificate file holds no private key and the key file does, and, on POSIX, that the key file's mode is exactly 0600. It connects with Python's ssl module, accepting any certificate in the handshake and then comparing the SHA-256 of the DER certificate it was shown with the ready line's fingerprint itself, as a pinning client does, sends Hello and requires ServerInfo, and requires the host to exit with code 0 once the client leaves. Then it starts a second --tls host and requires the same fingerprint: the identity is reused across restarts, so what a client pinned stays valid. The unit tests cover the handshake and the token gate in depth; this is the one place the real host's TLS startup (the user-folder paths, the file modes, the ready line, the exit) runs.

Design decision: one Python script for both operating systems, instead of PowerShell on Windows and something else on Linux PR #115

The host smoke tests started as two long PowerShell steps in tests.yml, which cannot run on the Linux leg without installing PowerShell and which mix a protocol client with Windows process handling. They are now tests/smoke/editor_host_smoke.py (the scenarios) and tests/smoke/n2_frames.py (the frame codec), Python 3 with only the standard library, so the same assertions run on Windows and on Linux with no package to install (both runners have Python). Costs: the TLS check now uses Python's ssl module (OpenSSL) as the client, not .NET's SslStream, so a Schannel-only behaviour is no longer exercised; the script is no longer a place where Windows-specific host behaviour is visible in the step itself. Design decision: patch the vendored sol2 type-name path, instead of rewriting the engine's binding lambdas PR #119

sol2 names the metatable of a bound function object from __PRETTY_FUNCTION__, and real GCC prints every lambda of one signature in one function as the same <lambda(int)>, so two such lambdas shared a metatable and Lua called the wrong one (Layers.MaskOf ran LayerToName). The fix is a marked patch in external/sol2/include/sol/sol.hpp (sol2 3.2.3 has no upstream fix or macro for it): under real GCC only (__GNUC__ without __clang__), a name that mentions a lambda gets the compiler's unique mangled typeid name appended. The Clang and MSVC paths are unchanged, and names of non-lambda types are unchanged. Changing the engine's many binding lambdas into named functors would have fixed only today's bindings; LuaLambdaBindingTests binds same-signature lambdas in one function and runs on every compiler. Conventions for headless tests

All tests run without a window, GPU or sound device. No test calls Application::Init; instead each test sets up only the parts it needs. Init does not require a window: without one it carries on and reports the window subsystem as Failed in its health result (the editor host relies on this in CI). PhysX determinism and the 1-ulp experiment PR #161

PhysXDeterminismTests.cpp keeps two kinds of result apart. Asserted: the wiring of physics.deterministic, and that the same scene (free fall of one sphere, a 10-box stack, a 100-body mixed pile of boxes, spheres and capsules, 600 steps at 1/60 s, built in a fixed order from an integer generator; every draw from the generator is its own statement, so the layout does not depend on the unspecified order in which a compiler evaluates function arguments and the pile is the same scene on MSVC, Clang and GCC) simulated in two fresh PhysX scenes in one process with the option on ends bit-identical: a 64-bit FNV-1a hash over the exact bits of every body's position, rotation, linear velocity and angular velocity, taken after every step and after the last. The golden replay job: physics-free replays across legs C2

The netcode design (orchestrator/proposals/netcode-runtime-design.md, section 6 "Golden determinism (cross-leg)") needs one test that tells whether the code a lockstep or rollback simulation will run gives the same bits on every platform: float arithmetic in transforms, the engine-owned Sin/Cos and the Lua math shims of C1, Ordered.pairs, and the seeded DeterministicRandom. It is the physics-free sibling of the physics determinism job and built the same way: every leg replays the same fixed input and prints hashes, one job downloads the files and demands equality.

The scenes (engine/src/replay/GoldenReplay.cpp, run by RunReplay; no Application, window, renderer, physics backend, clock or file access, so the result is a function of the replay file alone). Each runs 600 fixed ticks of 1/60 s under a FloatEnvironmentGuard and is hashed (64-bit FNV-1a over the exact bits of every float and double, NaN canonicalised) after every 60 ticks:

  • transforms: 24 transforms (Math::Vector3 positions, float yaws) moved by float code, Math::Sin/Math::Cos and a DeterministicRandom stream. It does not use the SIMD-dispatched Quaternion operations or Vector3 reductions, only element-wise float arithmetic, so a mismatch here is a compiler or FP-environment finding, not a SIMD-versus-scalar one.
  • lua_sim: the whole simulation is a Lua script in a state with only the base, math, string and table libraries, the C1 math shims (InstallDeterministicMath), Ordered.pairs and the random stream bound as rng_float, rng_range and rng_int (math.random is removed). String-keyed entities move with atan, cos, sin, exp and log, spawn and die; counters have mixed number and string keys. Every iteration that draws a random number or builds the hash goes through Ordered.pairs.
  • lua_driven: 16 C++ transforms steered by a Lua think function every tick (atan, exp, log, the random stream), the Lua accumulator hashed with them.

The replay file (tests/golden/replays/<scene>.n2replay.json, read and written by engine/include/engine/replay/ReplayLog.hpp). Format choice: JSON with an explicit "format": "n2replay" and an integer "version" (1), because every leg already parses JSON with nlohmann::json (so the committed text is the same input everywhere, including under node) and a human can read a desync replay. Fields: scene (a built-in scene name), seed (u32, seeds the scene's DeterministicRandom), ticks, hashInterval, and inputs: rows [tick, slot, moveX, moveY, buttons], sorted strictly by (tick, slot), each meaning "from this tick on slot slot holds this state until its next row" (all zeros before its first), moveX and moveY in [-127, 127], buttons a u32 bit set, slot in [0, 4). A reader refuses an unknown version, an unsorted or out-of-range row and anything not JSON; the serializer is canonical (one row per line), and a test keeps the committed files equal to what it writes. This is deliberately small and independent of the networked InputFrame (a separate stage, which may add fields): C3 (lockstep, replay files, the hash tree) will map InputFrame onto these rows or bump the version, so a version-1 file stays replayable. The checkpoint hash here is a whole-state FNV, not yet the per-net-id hash tree of design section 4.5.

The runner. In engine_tests, GoldenReplayCorpusTest replays the three files and prints [REPLAY] <scene> tick <n> <hash> lines; with N2_REPLAY_HASHES_OUT (and N2_REPLAY_LEG) it writes replay-hashes.json (the record shape of the physics corpus file: scene, kind state, tick, hash, plus a build fingerprint). The same code is the command-line program n2_replay (tests/replay, native builds): n2_replay tests/golden/replays/lua_sim.n2replay.json --out hashes.json prints the same lines, for a desk or a bug report; CI runs the test form, which also exists in the web build.

The job. Five legs run the corpus after their other tests, on the same strict floating-point builds as the physics corpus, and upload replay-hashes-<leg>: windows-release, linux-x86_64-clang, linux-arm64-clang, linux-x86_64-gcc and web-node. The job golden replay (cross-leg hashes) (ubuntu-24.04, 15-minute timeout, not a required check) needs changes and the five legs, runs even when a leg failed and is skipped on a docs-only pull request. It self-tests the comparison (python3 scripts/replay-determinism.py self-test: a differing record, a missing record, a missing scene, a missing leg, legs equal to each other but not to the golden and a single leg must each be reported), downloads the artifacts, uploads replay-determinism-golden-candidate (the golden as the Linux x86_64 Clang leg would write it) and runs compare, which fails unless every leg is present and complete, all legs are equal to each other and equal to tests/golden/replay-determinism.json, and names the first differing scene and tick. There is no tolerance and no way to skip a leg. Make it a required check only after two weeks green, as for the physics job.

The golden tests/golden/replay-determinism.json was first generated on one machine, a local Windows MSVC Release build with N2ENGINE_STRICT_FP=ON, and not on the Linux Clang leg its candidate normally comes from; the first CI run is therefore the first cross-leg measurement (design R2: whether wasm, x86-64 and arm64 agree for this codebase is unmeasured until that run). If a leg differs, that is the result: report it with the job summary, do not loosen the comparison. To change the golden (a changed scene or replay file, or a toolchain bump that proved safe), download the replay-determinism-golden-candidate artifact of a green run and commit it in a pull request that says why. To add a scene: add it to SceneNames() and MakeScene, add its replay file, add the name to SCENES in scripts/replay-determinism.py, and regenerate the golden. When physics scenes arrive with the deterministic backend (C4) they join this job.

Lockstep core: scheduler, hash tree, desync report, session replay C3

The library half of the deterministic runtime (design section 4.1 and 4.5), tested on the seeded SimTransport and wired into nothing yet: not N2Server, NetworkServer or NetworkClient, and not the networked InputFrame (PR #232). Input is a stand-in, LockstepInput (moveX, moveY, buttons), with the fields of a replay row.

  • Scheduler (engine/include/engine/network/n2net/Lockstep.hpp). Each slot's input sampled at tick T is for T + inputDelay (default 2); the first inputDelay ticks are neutral for everyone. A tick runs only when every slot's input is known. Ticks are 32-bit and compared as signed differences, so the scheduler runs across the 2^32 wrap. Inputs are accepted only inside a 128-tick window, which is also the fixed buffer: nothing a peer sends allocates. A repeated identical input is a duplicate, a different one for the same slot and tick is a conflict (the first stays). Loss is covered by redundancy: every datagram (InputBundle, at most 32 frames) carries the sender's frames from the receiver's acknowledged tick on, and the acknowledgement is the sender's own current tick. Missing input is never invented: after stallTimeoutPolls fruitless polls the status is TimedOut with the missing slots, and the host waits, ends the session, or calls DropSlot(slot, tick), which every peer must apply at the same tick (the relay decides; the slot is then neutral or holds its last input).
  • Hash tree (HashTree.hpp). tick, then per object (net id), then per field; a leaf is 64-bit FNV-1a (the engine's existing Fnv1a64, no Mbed TLS) over the field id, the length and the encoded bytes. The builder sorts, so the order the world is walked in does not matter, and refuses duplicates, more than 256 fields per object, more than 65536 objects. Peers exchange only the root (RootMessage, 13 bytes, the latest two checkpoints every frame so a lost one is covered). On a mismatch Bisect compares the hash of the objects with id in a range: it halves the 32-bit id space (left half first, so the result is the lowest divergence) until both sides hold at most 8 objects, asks for those, then for the fields of the first differing object. That is at most about 70 requests whatever the size of the world; an answer larger than the cap, unsorted, out of range or inconsistent with the summary is Malformed, never a conclusion.
  • Desync report (engine/src/replay/LockstepReplay.cpp). A JSON file, format n2desync version 1: peer, tick, both roots, the build fingerprint (BuildFingerprintJson), the determinism fingerprint the host supplies, the first divergence (kind, object id, field id, both hashes), the input log from tick 0 inline as an n2replay object, and the last K checkpoint trees (objects and field hashes, cut at 4096 objects and marked truncated).
  • Replay files. The C2 format already is a lockstep input log (a row is "from this tick on this slot holds this state"), so its version stays 1 and the golden files and golden hashes are untouched. LockstepRecorder turns the confirmed ticks into rows (only where a slot's state changes); ReplaySimulation (new, GoldenReplay.hpp; RunReplay is now built on it) steps a scene one tick at a time, so a live session and its replay run the same code. The test records a three-peer session on a lossy link and checks that RunReplay of the file gives the hashes the live peers printed, for all three golden scenes.

Not verified. Everything runs in one process on a virtual clock: no real UDP, no second machine, no OS scheduling, and the cross-platform claim (the same hashes on Windows, Linux, arm64 and web) rests on the C2 golden job, which this change does not extend. The hash tree has been built only over a synthetic world (the tests) and over the scene hash of the replay scenes; hashing real NetworkObject fields through the replication codecs, and the request/response encoding of the bisection over the wire (IHashTreePeer is the seam), are not written. The scheduler has not met the real InputFrame, the relay mode of N2Server, the web build's hidden-tab pause, or a long soak; the stall policy is mechanism only. The 32 frames per bundle and the 128-tick window are chosen, not measured.

Pixels: the headless software renderer PR #51

Rendering is tested with real pixels through a SoftwareRenderer started with Initialize(nullptr, width, height), which never touches GL (headless mode), so it runs on the GPU-less CI runner. A test:

  1. constructs a SoftwareRenderer on the stack, asserts Initialize(nullptr, w, h), and sets a clear colour that no draw uses;
  2. runs a frame as Application::Render does: BeginFrame, SetViewProjection (a camera's matrices, or identity to draw in NDC), the draws (or Scene::Render, UISystem::Render), EndFrame, Present;
  3. reads the frame with ReadFramebuffer at the renderer's size (RGBA8, row 0 at the bottom, so y grows upwards like NDC);
  4. releases what components hold on the renderer (CleanupRenderResources), then calls Shutdown. Declare the renderer before the scene, so it outlives it.

Assertions are structural, never exact images or hashes (why): pixel counts and bounding boxes within a pixel or a few percent, colours exact only where they are flat (unlit and alpha-tested text are; lit shading and anything resampled are not), and comparisons between two frames of the same run. Pick colours that are 0 or 1 per channel so packing can't round them.

The Vulkan renderer: lavapipe and validation layers PR #136

The lit cross-backend criterion PR #148

The lit and PBR scenes are drawn on Vulkan and on a headless software renderer and compared by CrossBackendDiff.hpp. Unlit, nearest-sampled scenes keep the strict rule (no compared pixel more than 2/255 off in any channel, nothing left out). For lit scenes, where the two backends round differently and sRGB textures are decoded before filtering on Vulkan and after it on the software renderer, the proposal's lit rule applies (Diff::Lit()): the comparison passes only when

  • the mean error over the compared pixels is at most 2/255, where a pixel's error is its largest colour-channel difference (the stricter of the two readings: a mean over the three channels would be smaller), so pixels between the tolerance and the second threshold count through the mean (an image where every pixel is off by 7/255 fails, which the harness tests prove); and
  • at most 1% of the compared pixels differ by more than 8/255; and
  • after leaving out a 1-pixel border around each coverage edge (rasterisation tie rules differ), where coverage comes from a flat unlit mask render of the same geometry on each backend (Options::coverageA/B; a flat-colour frame is its own mask): an edge pixel is one whose covered-ness differs from a neighbour's in either mask, or differs between the two masks. It never looks at the lit shading, so a lit object one backend shades black fails instead of being left out, and so a smoothly lit surface is not taken for an edge (the strict mode's colour-difference definition would have left out nearly every pixel of a lit cube); and
  • no more than 25% of the image was left out, and something was compared, so an over-broad exclusion can never pass vacuously.

The measured numbers of every lit scene are printed in the test log ([ cross-diff ] ... lines: compared and excluded pixels, mean error, share over 8/255, the largest difference) and are listed in PR #148. Measured on lavapipe (llvmpipe) in the Linux Clang legs, all 115 lit comparisons (the renderer-level lighting, normal-map and PBR draws, the lit cube, the model and both edit-mode goldens) agreed with the software renderer to a mean error of at most 0.033/255 and a largest channel difference of 1/255, with no pixel over 8/255. These figures were measured on lavapipe before the coverage masks replaced the "not the clear colour" definition. The mask change compares more pixels (the spot-cone falloff pixels that were previously excluded), and the figures have not been re-measured since: the CI logs do not print them, and the tests pass their thresholds. The edge exclusion of each scene is printed in the [ cross-diff ] lines (the cap is 25% of the image); no scene needed a looser threshold. The software renderer does not clamp directional lights to two, so the five-light clamp is checked on Vulkan only.

The blended Vulkan goldens and their reference PR #158

Stage D of #43 makes Vulkan blend like OpenGL, and the software renderer cannot blend (it draws a blended draw opaque). So a blended Vulkan frame is never compared with one software frame: that would encode Software-only behaviour. Per the proposal, an assertion that encodes Software-only behaviour gets a per-backend expectation, and Vulkan expects OpenGL's. Two checks replace the single diff, both in BlendReference.hpp and both device-free (BlendReferenceTests.cpp tests the helpers, so they run on every leg that builds the Vulkan tests):

  • Composite reference. Each blended layer is drawn opaque and alone on the software renderer (its colour and the pixels it covers); the reference frame is built on the CPU with OpenGL's equation, layer by layer in submission order, over the software frame of everything behind it: round(a * src + (1 - a) * dst), additive min(255, round(a * src + dst)), and the alpha channel by the same factors. The Vulkan frame is then compared with it by Diff::Compare: the strict rule for nearest-sampled unlit scenes, the lit rule for linear-filtered ones (the linear sprite gradient). The composite's own rounding is inside the 2/255 of the strict mode; no extra allowance was needed.
  • Opaque mask. Where the layers of a scene cannot be separated, the strict diff runs on the pixels no blended draw covers (the mask grown by a border so rasterisation tie rules at the blended edges do not count: Diff::Options::ignore, ignored pixels are counted as excluded) against the software frame, and the blended parts get per-backend structural expectations at interior pixels: the exact OpenGL-equation colour, within 1 or 2. The mixed-submesh mesh golden and the translucent Image over a scene mesh use it.

The scenes, by rule: the mixed opaque and blended submeshes (opaque part strict, blended half by expectation); the upright sprite (strict); a translucent checker sprite (strict); the linear sprite gradient (lit); a translucent Image over a scene mesh (opaque part strict, the Image by expectation); two overlapping half-alpha quads through the Transparent queue, both depth orders (the full composite, far then near, strict on every pixel). The particle and world-canvas goldens and the renderer-level blend tests are structural: exact colours and counts at interior pixels, computed with the same formula. Measured on lavapipe in the Linux Clang legs, every compared scene agreed exactly, a mean error of 0/255 and a largest difference of 0/255: the upright sprite 1600 pixels compared, the translucent checker 1600, the gradient 512, the translucent Image over a mesh 1920 compared and 2176 left out (53% of the image, by the Image's mask), the mixed submeshes 3196 compared and 900 left out (22%). The two-quad Transparent-queue scene was added in review after those measurements; its numbers are printed in the test log ([ cross-diff ] transparent queue back to front). No scene needed a looser threshold, and the strict mode is unchanged.

One divergence is known and asserted, not hidden: a blended lit draw in linear lighting. OpenGL blends it in linear space (its target is sRGB with GL_FRAMEBUFFER_SRGB on for that draw), while Vulkan's target is R8G8B8A8_UNORM and the lit shader encodes in the shader, so Vulkan blends the encoded values (design decision). Unlit, text, UI, particle and Gamma-lit blends match OpenGL; ABlendedLitDrawInLinearLightingBlendsTheEncodedValuesUnlikeGL documents the Linear case.

All the device tests of this section run on lavapipe in the two Linux Clang legs (N2_REQUIRE_VULKAN=1 and N2_VULKAN_EXPECT_CPU_DEVICE=1 turn a skip into a failure), skip on the Windows legs (no device) and do not exist on the GCC 14 leg (Vulkan off); the harness tests, the lighting block tests and the parity test need no device and run on every leg that builds the Vulkan tests.

The Vulkan text tests and the antialiased cross-check PR #165

Stage E of #43 draws text on Vulkan with a port of OpenGL's SDF shader, so Vulkan text is antialiased and blended where the software renderer's is alpha-tested (a glyph pixel is the text colour or untouched, and it writes depth). An assertion that encodes the software behaviour gets OpenGL's expectation on Vulkan, with a comment at the assertion; the software tests are untouched. The text tests are VulkanTextShaderTests.cpp (renderer level) and the three golden files (engine level) in the table above; the per-backend expectations:

  • Alpha-tested pixels become blended ones. Where a software test asserts that every touched pixel is exactly the text colour, the Vulkan test asserts that every pixel lies on the straight line from the background colour to the text colour (no other hue) and that in-between pixels exist, and then runs the software test's structure (bounding boxes against the layout, column runs, counts, alignment) on the frame thresholded at half coverage: the coverage ramp is centred on the 0.5 iso-line the software alpha test cuts at.
  • Transparent text writes no depth. The software test that draws an opaque quad behind the text afterwards and finds the glyph intact becomes, on Vulkan, that the quad covers the whole frame (the Transparent state writes no depth, as on OpenGL).
  • Layered effects (face, outline, shadow, passes) are read with the frame classified to the nearest layer colour, which cuts at the 0.5 iso-line of each layer, and the software tests' exact set equalities become allowances of a few pixels (2% of the layer, at least 6) where they depend on the pixels exactly on that line. Where the software renderer makes two frames equal because of the alpha test and OpenGL's equation does too (the same uniforms, the clamped effects, an order above zero), the test compares Vulkan frames byte for byte. Softness, which the software renderer ignores, is an effect on Vulkan, so the “effects off” case leaves it out and a separate check shows it widening the ramp around the same ink.

The cross-backend comparison of antialiased text. The same scene is rendered on the software renderer and on Vulkan, large (320×192 for the TextRenderer and the effects, 400×160 for the UIText, and 64×64 for the renderer-level disc), so that glyph stems are wide enough to have interiors, and compared by CrossBackendDiff's strict mode (2/255 per channel, never loosened) on the pixels away from the edges only:

  • Coverage-edge exclusion. A pixel is left out when its coverage (not the background colour) differs from a neighbour's, in either frame or between the two, with edge border 1 (the ramp is about one pixel wide, up to 1.4 at 45 degrees, and the software cut and the Vulkan ramp are centred on the same iso-line). For the frame of several layers (face, outline, shadow) a pixel is an edge when its colour differs from a neighbour's in either frame, so the boundaries between layers are left out too.
  • A cap on what is left out (15% for the disc, 25% for the glyph scenes, 40% for the three-layer one) and a floor on what is compared (50 ink pixels for the disc, 300 for the glyph scenes, 500 for the three-layer one: the glyph interiors), so the comparison is never of the background alone.

The sum of the Vulkan blend weights (how far each pixel lies from the background towards the text colour) against the software ink pixel count, within 4% (disc) or 5% (glyphs), so a glyph that is too thin or too fat fails. For the three-layer scene the Vulkan frame is classified to the nearest layer colour and the pixel counts are compared with the software layers': the face and the outline together, and the shadow, within 5% (or 10 pixels), the face and the outline each alone within 12% (their shared boundary is the one a CPU driver's rounding of a filtered sample moves; the numbers below).

Design decision: Vulkan runs on a software driver in CI PR #136

The runners have no GPU, and OpenGL's pixels are untestable for that reason (below). Vulkan does not have to be: the loader finds any driver, and Mesa's lavapipe is a conformant CPU one on Ubuntu 24.04. Running the real backend there, with the validation layer failing tests on errors and leaks, checks initialisation, synchronisation, layouts and shutdown on every PR. It does not check what only a real driver shows (format support, memory types, timing), the swapchain and present path (stage F of #43, which needs a GPU), or speed. Decided on #43 (proposal of 2026-10-14).

The WebGPU shaders: parity and validation PR #190

Stage G1 of the WebGPU backend has two checks and no GPU. The parity test, tests/renderer/webgpu/WebGpuShaderParityTests.cpp (WebGpuShaderParityTest.*), reads renderer/shaders/webgpu/*.wgsl as text, so it runs on every leg that runs renderer_tests: Windows, the Linux legs with or without Vulkan, and the web leg under node. It parses the structs, the module-scope resources and the two entry points, computes the byte layout of each uniform struct with a small calculator for the WGSL uniform address space (scalars, vectors, mat4x4, structs, arrays whose stride must be a multiple of 16), and checks, for the unlit, lit and text shaders:

  • every uniform struct declares the members of renderer/common/GpuShaderInterface.hpp's table in order, with its type, array count, byte offset and size (the per-draw block is 192 bytes, the lighting block 752, the material blocks end where MaterialBlockSize says and fit kMaterialBlockRange once rounded up to their alignment), and the light structs member by member (offsets, strides 32, 48 and 64, array counts 2, 8 and 4);
  • the resources are exactly the table's: group 0 binding 0 per-draw (binding 1 the lighting block, lit only), group 1 binding 0 material, every table sampler as a texture_2d<f32> of the table's name at the table's binding and a sampler named <name>Sampler at that binding plus kSamplerCount, no other resource, nothing in a group above 1;
  • the vertex inputs are the table's attributes (location, name, component count) and Common::Vertex's offsets, what the vertex stage outputs is what the fragment stage takes (location, name, type, nothing left over), and the fragment stage writes @location(0) vec4<f32>;
  • every uniform Material::ApplyUniforms sets (for Lit and Pbr against the lit shader, for Unlit against the unlit one, as GpuCache picks them), every material default of the table and the seven text effect uniforms is a member of the WGSL material struct;
  • the maths the ports must keep: the clip-space z remap and the matrix product order, the PBR constants against LightingMath.hpp, the environment-BRDF fit, the GGX and sRGB functions, the three lighting loops, the inverse3 adjugate and the normal matrix, the SDF ramp of the text shader and the unlit alpha test;
  • the uniformity rule: every textureSample and fwidth comes before the first discard, and in the lit shader all five samples come before the first loop;
  • the files are plain ASCII (the embedding cuts them at arbitrary characters), and the WGSL embedded by CMake (renderer/webgpu/WgslSources.hpp) is the files' text, ignoring carriage returns (CMake writes the header with the platform's line ends).

Every failure message names the file, the group and binding (or the struct and member) and the expected and actual values. A renamed or forgotten uniform, a reordered block member, a moved binding, a changed type, a texture without its sampler or a member whose WGSL offset is not the std140 one fails here instead of drawing wrong colours (an unknown uniform name is otherwise silently ignored by the block material). It is the WGSL twin of the Vulkan shader parity test, and like it checks the interface and the listed maths, not the maths in general.

The validation job, wgsl (Tint, naga) (what it runs and how the tools are pinned), is the proof that the files are valid WGSL, which no C++ test can be: Tint (Chrome and Edge) and naga (Firefox) both accept all three, with uniformity analysis and the SPIR-V, MSL and HLSL backends where the tool has them, and the negative controls in scripts/wgsl-negative/ must be rejected (a type error by both tools; a derivative in non-uniform control flow by Tint only, because naga's analysis lets it through), each for its own reason, which the script checks in the tool's message. It is not a required check, does not run on a docs-only pull request, and costs about one minute of runner time, measured: 60 s for the whole job with a cold cache (the Tint download 3 s, the naga build 49 s, the validation itself under a second); a cache hit skips the naga build. Run the same checks by hand with TINT=... NAGA=... scripts/validate-wgsl.sh on a Linux machine after scripts/install-wgsl-validators.sh <dir>.

What is not tested by either: that a shader draws the right pixels (stages G2 and G3 on Dawn over lavapipe, then the user's browsers), that the backend transposes the matrices on upload, and that Safari's WebKit compiler accepts the files (no CI path; a check by hand in stage G5).

The netcode packet layer and its simulator PR #197

The tests of n2net run in engine_tests on every leg (Windows, Linux x86_64 and arm64, and web under node) with nothing excluded. Apart from the UDP transport file below they use no sockets, threads, files or wall clock: two Connections are wired over a SimNetwork, whose virtual clock the test advances. The conventions:

  • Seeded. Every simulated network takes a seed, and a failing run reproduces from it. Randomness inside the tests (fuzz inputs, message sizes) comes from the library's own SimRandom, never from std::random_device or the standard distributions.
  • Golden hashes. Three tests hash what happened with a 64-bit FNV-1a (written out in N2NetTestUtil.hpp, over explicit integers and bytes, never over struct memory) and compare it to a constant in the source: the random stream (StreamIsFixedAcrossPlatforms); a simulator run of 3000 datagrams of 1 to 1200 bytes (and a third as many back the other way) over a link with every impairment on, hashing every event's time, endpoint, type, peer and bytes (GoldenTraceIsTheSameOnEveryPlatform); and a bidirectional session of 400 reliable messages each way plus unreliable traffic over a lossy link, hashing every delivery (when, channel, bytes) and the final statistics of both ends (GoldenSessionTraceIsTheSameOnEveryPlatform). The same constant must come out on every leg, which is how cross-platform determinism of the simulator is checked without a second machine. If an intended change to the simulator or the packet layer changes the trace, update the constants in the same PR and say why.
  • Hostile input. N2NetFuzzTest feeds a connection 40,000 random, truncated and mutated datagrams, every prefix and every single-byte change of valid packets, floods of maximum-size units and an endless message; none may crash, deliver a message over the caps, or take the connection past MemoryBoundBytes(). The counts are fixed, so the run time is bounded (it is small enough for the wasm leg). Run locally under AddressSanitizer and UndefinedBehaviorSanitizer for out-of-bounds reads; CI runs the ordinary build.

The UDP transport tests PR #203 (N2NetUdpTransportTests.cpp) are the exception to all of the above: they open real UDP sockets on loopback (127.0.0.1, and ::1 where available) with ephemeral ports, so they cannot be seeded or virtual-clocked. They keep the run time bounded in two ways: every wait is a poll loop against a deadline (20 s, only reached when something is broken), never a fixed sleep that a result has to fit inside, and the only fixed waits are short (50 ms) checks that something was not sent, plus one deliberate stall of three idle timeouts (900 ms) in AStallLongerThanTheIdleTimeoutKeepsPeersWhoseDatagramsAreQueued, which is the condition under test rather than a wait for a result PR #207. The loss case puts a seeded SimRandom shim in front of each transport and drops 15% of datagrams each way; loopback itself loses nothing. A small raw socket in the test plays the other host for the oversize, unknown-source and peer-cap cases. The file compiles to nothing on the web build (no sockets there), and its IPv6 and dual-stack tests GTEST_SKIP when the machine has no IPv6 loopback or refuses a dual-stack socket. Three tests bind all interfaces briefly on an ephemeral port (InsecureBindOverridesWithOneLoudWarning and the dual-stack test with insecureBind, EncryptionAvailableAllowsANonLoopbackBindWithoutTheFlagOrAWarning with the encryption parameter); the refusal tests never create a socket.

The secure layer's tests PR #210 (N2NetSecureTransportTests.cpp) follow the simulator conventions for everything but one test: a server and a client SecureTransport over a perfect SimNetwork link, with one virtual clock the test moves (it drives the transports' clockMicros, and so the cookie times and the admission policy's clocks, and the network's time). A TapTransport between the client and its endpoint records every datagram sent and can send raw bytes, which is how the tests replay and alter sealed packets; extra endpoints linked to the server send hand-made handshake packets (a request with a made-up key, its echo with a real or forged cookie). Time moves only when a test moves it (up to a few tens of virtual seconds), and none sleeps. The exception, ChannelsOverLoopbackUdpThroughTheSecureLayer, runs over real loopback sockets with a 20 s deadline like the UDP tests, and TheSecureLayerAllowsANonLoopbackBindWithoutTheInsecureFlag binds all interfaces briefly on an ephemeral port. Everything but the Connection packet-size test is compiled only where the crypto library is (N2NET_HAS_SECURE), so the web leg runs just that one.

The WebGPU renderer tests: Dawn over lavapipe PR #196

Stage G2 of the WebGPU backend runs a real renderer without a window or a GPU: webgpu_tests (tests/renderer/webgpu/WebGpuRenderer*Tests.cpp, fixture in WebGpuTestFixture.hpp) construct Renderer::WebGpu::WebGpuRenderer directly (there is no way to select it otherwise), which runs on Dawn's Vulkan backend over Mesa lavapipe, the CPU driver the Linux legs already install. The program exists only with N2ENGINE_RENDERER_WEBGPU=ON; the job that builds it is above. The rules are the Vulkan tests' (above), with WebGPU's own tools:

  • Skip or fail. Without an instance or an adapter the tests GTEST_SKIP, unless N2_REQUIRE_WEBGPU=1 (set in the CI job) makes that a failure; N2_WEBGPU_EXPECT_CPU_DEVICE=1 makes the renderer take only a CPU adapter and the fixture assert it did (WGPUAdapterType_CPU: lavapipe).
  • No error, no leak, in every test. The fixture fails a test whose renderers' GetValidationErrorCount() is not zero at teardown (every uncaptured error and every unexpected device loss, with the messages; there is no validation layer in WebGPU, the device's error callbacks are the equivalent), and one that leaves a WebGPU reference behind (GetLiveObjectCountForTest() against its value at SetUp). Negative controls prove both can fail: ErrorCounterNegativeControl... makes a buffer with no usage and a texture of no size through the raw device and checks they are counted, kept with their text and reported (and that the fixture's report is then not empty), ALostDeviceIsCounted... destroys the raw device and checks the loss is counted once, frames are skipped and a new Initialize recovers; each ends by resetting the counters so its own teardown passes.
  • Exact pixels. The clear colour is chosen as k/255 so the 8-bit target holds exactly k, and the helpers compare every pixel. The orientation and unpadding tests write PatternPixel(x, y), a different colour for every pixel, into the colour target through wgpuQueueWriteTexture on the raw queue and read it back at widths whose rows are not a multiple of 256 bytes; the expected pixel at output row y is the texture's row h - 1 - y (bottom row first, as the software and Vulkan renderers). There is no draw yet, so a regional clear is not possible; the cross-backend comparison with the software renderer starts with G3a.
  • Depth is checked as far as a clear can: the depth target (Depth32Float) reads back as 1.0 everywhere after any frame, after a resize and after a mid-frame clear (ReadDepthForTest). Depth testing and writing need draws.
  • Environment tests. AdapterSelectionFollowsThePreferenceAndTheEnvironment sets N2_WEBGPU_EXPECT_CPU_DEVICE in the process and checks the adapter type; WithoutAVulkanDriverInitializeFailsWithNoAdapter... points VK_DRIVER_FILES at a missing file and checks Initialize returns NoAdapter with a message naming the adapter (it skips, saying so, if the loader still finds a driver).
  • Leaks. TenCreateDestroyCyclesLeakNothing (live-reference count back to its start after each of ten renderers, one of them destroyed with a frame open) and RepeatedCyclesOfLargeTargetsDoNotGrowTheProcessWithoutBound (resident set from /proc/self/statm: ten 2048x2048 cycles after a warm-up may add less than 150 MB, where a leak of the targets and the readback buffer would add about 480 MB; the job log prints the two numbers; measured in a container, 135 MB and 137 MB). Run locally in a container, the same program was clean under AddressSanitizer, UBSan and LeakSanitizer; CI does not run sanitizers.

What is not tested at stage G2: anything on a real GPU or in a browser; the draws (stage G3a PR #201 tests them, below, and stage G3b PR #204 the lit, text and blended ones, below that); that the same source compiles with emdawnwebgpu (G4); a leak inside Dawn that does not show in the process's memory.

The WebGPU resource, unlit draw and golden tests PR #201

Stage G3a of the WebGPU backend adds three files to webgpu_tests (same program, same fixture, same job as above; 149 tests in all, about 9.5 seconds of test time on lavapipe, 3.8 of them the first test of a run, which starts Dawn and the Vulkan driver). Every test still fails on any WebGPU error and on a leaked reference. The rules of the Vulkan tests apply (above), with these differences:

  • Vulkan's values, scene by scene. WebGpuRendererUnlitDrawTests.cpp repeats the structural assertions of VulkanUnlitDrawTests.cpp and VulkanPipelineTests.cpp (counts, colours and bounding boxes of exact quads), because a WebGPU frame must be held to what the Vulkan frame is held to. Each test also asserts that both frames hold something other than the clear colour, so a scene that drew nothing cannot agree with itself, and prints [ cross-diff ] lines with the numbers (and, not asserted, the same frames with nothing left out).

Blending, which the software renderer cannot do either, is tested in stage G3b (below).
  • The in-frame UpdateMesh rule is checked twice: by the buffer handles (UpdateMeshWritesInPlaceUnlessTheMeshWasAlreadyDrawnInTheFrameBeingRecorded: in place outside a frame, new buffers for another size, in place inside a frame for a mesh not yet drawn, new buffers after a draw in the same frame, in place again after the frame) and by pixels (UpdateMeshAfterADrawLeavesThatDrawWithTheDataItWasDrawnWith: both halves of the frame are red only if the first draw kept the old vertices). Not a cross-diff: the software renderer reads a mesh when it rasterises at EndFrame, so an update between two draws changes both of its draws.
  • The ring is tested for isolation, not only for growth: 4096 draws of one pixel each, each with its own colour set on one material between draws (a snapshot per draw), on 16 KiB chunks, so a slot that overlapped another's would show as a wrong pixel; the chunk count is then constant over three more frames (the ring is reused). The device's alignment is asserted to be a power of two of at least 4.
  • Device loss is injected by destroying the raw device (the same injection the G2 loss test uses); the golden scenes of stage G3b link the engine but never lose a device, so recreation is tested through its contract, the lifetime token: it expires on the next Initialize and not before, and the old pointers are foreign to the new device.

What is not tested: a real GPU or a browser; performance (the ring test's four frames of 4096 draws take 0.65 seconds on a CPU rasteriser, which says nothing about a GPU); the Emscripten compile of the same sources (G4); a live WebGPU-versus-Vulkan diff (above); the lit-linear-filtering sRGB difference between the backends (a nearest sRGB texture is compared, a linearly filtered one is not, by design).

Exact-value tests for the deterministic math PR #200

DeterministicMathTests.cpp compares results with tables of exact bit patterns, not with tolerances, because the point of the engine-owned functions is that every platform gives the same bits: the same table is asserted on every leg of the matrix (MSVC, GCC, Clang, arm64, wasm), so one bit of difference on one leg fails there. The tables were computed once from the implementation and cross-checked against the C library and a 90-digit reference. The accuracy tests are the other half: they use a double-double reference computed in the test file (the C library only seeds a Newton step) and assert the ulp bounds exactly as documented in math, so a table cannot hide an algorithm that is exactly reproducible but wrong. To change an algorithm on purpose, regenerate the tables and list the old and new values in the pull request.

FloatEnvironmentTests.cpp and the two guard tests in SimulationClockTests.cpp change the processor's floating-point control register on purpose, so every one puts it back with a scope object (a failed assertion cannot leave a test program rounding toward zero), and each checks that its perturbation took (FloatEnvironmentTests.cpp by what the arithmetic does, the two in SimulationClockTests.cpp by asserting that FloatEnvironment::IsDeterministic() is false after the write) before testing the guard. They are skipped on WebAssembly, which has no such register.

GPU smoke test PR #86

CI has no GPU, so the OpenGL renderer's pixels are never checked automatically. lua_project's scene is a checklist for checking them by eye on a machine with a GPU: seven stations, each showing one area. Every item has a caption saying what correct output looks like, and a HUD in the bottom-left corner names the station and what to look for there. Each station's camera keeps what matters in the top four fifths of a 16:9 or 4:3 window, clear of the HUD. One directional light, Sun, shines into the scene from the front upper left, the side the cameras are on (direction (0.4, −0.6, −0.7)); without it the engine's default light would come from behind the stations, leaving everything the cameras see at the ambient level. The same text as the HUD's is written to the log (GPU smoke test, Station 2/7: World text. Look for: ...), so a station can still be judged if text doesn't draw at all.

CI still builds the scene: LuaProjectSceneTest runs assets/scene.lua headless, checks every station's objects and components, clicks the buttons (Button::Click) and checks the counters, and EveryProjectAssetLoads loads every .mat file (with the texture it names), image and model under lua_project/assets, failing on a glTF import warning. A broken asset or a script error is caught there; only the pixels need a person.

Particles: CPU and GPU

  • The CPU backend runs everywhere, with or without a GPU, so the station always works and every sign says running: CPU by default. Auto picks PhysX when the physics backend offers a GPU particle backend and the CPU otherwise; CPU always runs on the CPU; PhysX asks for the GPU one and falls back to the CPU, with one warning in the log per emitter, where there is none. The sign says so: running: CPU (PhysX asked: fell back), and the info sign at the top of the station says it too. Pressing K replaces the three emitters, because a system reads its backend only when it starts.
  • The PhysX GPU backend needs a Windows PC with an NVIDIA GPU, a build with PhysX, the project setting physics.gpu set to auto or on PR #129. lua_project passes its project folder to Application::Init, which reads physics.gpu from project.n2proj, so the demo enables it like any project: edit lua_project/project.n2proj so that "settings" holds { "physics": { "gpu": "auto" } } (the default, off, is not changed in the repository) and restart. The info sign shows Physics.IsGpuAvailable(); when it says true, Auto and PhysX should show running: PhysX GPU and compare against CPU with K.
  • Water, sand and smoke set pbdMaterial (Water, Sand, Smoke, the PBD preset the PhysX backend uses: water flows and pools, sand piles up, smoke drifts) and are also tuned with the fields the CPU backend reads (emission rate, cone, speed, lifetime, size, colours, gravity scale, drag, the ground plane); the CPU backend ignores pbdMaterial, the PhysX backend ignores the ground plane (it collides with the scene's colliders, so the demo's floor must be a collider). Particles are billboards on the OpenGL and software renderers only: the Vulkan renderer draws them opaque for now, as it has no blending yet (Particles). The software renderer cannot blend, so the water and the smoke are opaque there.

Soft bodies: CPU and GPU PR #145

  • Every body runs on the CPU today. Without a GPU (every CI leg, Linux, any machine with physics.gpu off, which is the default) the CPU backend simulates every body and the signs say running: CPU. Asking for PhysX with J shows running: CPU (PhysX asked: fell back) and the info sign says so, with one warning per body in the log. The PhysX GPU backend (a deformable-volume backend for a Windows PC with an NVIDIA GPU and physics.gpu auto or on) does not exist yet: until it merges the physics backend offers no soft-body backend anywhere, so a sign never says PhysX GPU today. Pressing J replaces the six bodies, because a SoftBody reads its backend only when it starts, and they fall again from their start pose.
  • The floor is two things. The CPU backend collides only with the plane y = groundHeight (SetGround(true, floorTop) on every body); the PhysX backend will collide with the scene's colliders, so the floor also has a static BoxCollider at the same height.
  • The signs show the resolution, not a tetrahedron count: the Lua API has no tetrahedron or node getter. Each body is a MeshRenderer and a SoftBody on one object with no Rigidbody (see Soft bodies).
  • Rendering. A soft body is drawn by its MeshRenderer, so OpenGL and the software renderer draw it. The Vulkan renderer draws the unlit and lit shaders since stages B and C of #43, so a soft body's lit mesh is drawn there too; no test draws one on Vulkan.

The editor host renders off screen on OpenGL, into a framebuffer of the client's viewport size, and sends each frame as RGBA, top row first (viewport frames) PR #85. Adding a test

  1. Pick the executable by module: engine behaviour under tests/engine/<area>/, pure math under tests/math/, protocol encoding under tests/editor-server/.
  2. Create <Area>Tests.cpp (or add to an existing file for the same area). No CMake edit is needed; the directory is globbed. Re-run the CMake configure step so the new file is picked up.
  3. Name suites <Thing>Test and cases as a sentence describing the behaviour (ParentingARootRemovesItFromTheRoots). Other pages cite these names, so a good name documents the guarantee.
  4. Do not call Application::Init. Set up only what you need using the fixtures above; guard PhysX-dependent files with #ifdef N2ENGINE_PHYSX_ENABLED so the PhysX OFF leg still builds.
  5. Leave shared singletons as you found them: unique scene names, distinct Lua globals, restored Logger settings, scalar SIMD, physics backend removed.
  6. Build and run locally with --gtest_filter and, for anything touching shared state, --gtest_repeat=2. CI then runs it in all three legs (Debug with and without PhysX, Release with PhysX), so do not rely on assert for checks the test needs.
