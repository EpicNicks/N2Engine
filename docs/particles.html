Particles

The ParticleSystem component emits small camera-facing quads that start at its object, fly under gravity and fade away. A simulation backend moves them (the CPU backend on every machine, headless hosts included, or the PhysX GPU backend where the project enables GPU physics and an NVIDIA GPU works) and the component draws them as one mesh per frame. This page covers the component, the backend seam and how one is chosen, the PhysX GPU backend and its limits, the simulation rules, play mode, drawing and the Lua API PR #125 PR #129.

Quick start

Add the component to an object and play the scene. The defaults make a gently falling stream of white specks that fade out; everything else is a field.

local fx = GameObject.Create("Sparks")
local ps = fx:AddComponent("ParticleSystem")
ps:SetShape("Sphere")
ps:SetShapeRadius(0.2)
ps:SetSpeed(1, 3)
ps:SetLifetime(0.5, 1.5)
ps:SetStartColor(Color.new(1.0, 0.8, 0.2, 1.0))
ps:SetEndColor(Color.new(1.0, 0.1, 0.0, 0.0))   -- alpha 0: fades out
ps:SetBlendMode("Additive")
SceneManager.GetCurrentScene():AddRootGameObject(fx)

-- later
ps:EmitBurst(40)   -- 40 particles now
ps:Stop()          -- no new ones; the flying ones finish

The ParticleSystem component PR #125

ParticleSystem is an IRenderable in the Transparent queue. All of its settings are public fields that the scene file saves and the editor's inspector shows (the editor needs no protocol change: backend is an ordinary enum field, listed by GetComponentTypes like any other). Particles themselves are runtime state and are never saved.

C++ methods: Play(), Stop(), Clear(), EmitBurst(n), IsPlaying(), GetAliveCount(), GetParticles(out) (world positions and age fractions) and GetActiveBackendName() ("CPU", "PhysX", or empty before the system has started).

  • Play starts the stream and emits burstCount particles once. Stop only stops emitting: the particles in flight finish their lives. Clear removes every particle and leaves the stream as it was. EmitBurst(n) starts n particles now whether or not the system is playing (zero or negative does nothing).
  • A burst or Play asked for before the system has started (a script ran before the scene attached it) is remembered and emitted when it starts, once.
  • Particles start at the object's position when they are emitted and are simulated in world space: moving the object moves where new particles start, not the ones already flying. The cone points along the object's local +Y axis, turned by its rotation.

Backends and the seam PR #125

A ParticleSystem does not simulate anything itself: it emits (rate, shape, speed) and hands the new particles to an IParticleBackend (engine/include/engine/physics/IParticleBackend.hpp), which moves them and expires them. The interface has no PhysX or CUDA type in it. Its calls: CreateSystem(desc) returning a handle, Spawn(handle, positions, velocities), SetParams, Clear, Destroy, Step(dt), GetAliveCount and CopyPositions(handle, out), which fills one Vector4 per living particle: x, y, z the world position and w the age as a fraction of the lifetime (the drawing code turns that into size and colour).

BackendWhere it comes fromRuns on
CpuParticleBackendCreated by each ParticleSystem that needs it (engine/src/particles/CpuParticleBackend.cpp)Every machine: no PhysX, no GPU, no window. Stepped by the component once per fixed step.
PhysX GPU backend PR #129IPhysicsBackend::GetParticleBackend(), which returns nullptr by default; PhysXBackend returns its PbdParticleBackend when the GPU scene is up (physics.gpu auto or on, the probe Ready, a build with the GPU library: Windows) and until the GPU refuses itAn NVIDIA GPU, through PhysX PBD particles. It steps inside the physics scene, so its Step does nothing (details).

Choosing a backend

backendThe physics backend offers a GPU particle backendIt does not (physics.gpu off, no GPU, no PhysX, no physics backend)
AutoPhysXCPU, no warning
PhysXPhysXCPU, one warning per system naming the object and the GPU probe's reason
CPUCPUCPU

The choice is made once, when the component attaches (Particles::SelectParticleBackend); changing backend afterwards takes effect the next time the system starts. Because physics.gpu defaults to off, a default project always uses the CPU backend, so particles behave the same on every machine and on the headless host.

Design decision: the CPU backend is a real backend, not a fallback path PR #125

The user asked for both a PhysX GPU simulation and a CPU one, selectable. So the CPU simulation implements the same IParticleBackend as the PhysX one will, and the component only ever talks to the interface. A ParticleSystem never cares which one it has, and a project that sets backend to CPU runs identically with or without a GPU. The physics backend is asked for its particle backend each time it is needed (never cached), so a component that outlives the physics backend goes inert instead of dangling. If the physics backend is replaced by another one, the stale handle is dropped and the system restarts empty on the CPU backend with one warning (generation-counted handles).

Design decision: handles carry the generation of the backend that issued them PR #129

PR #125 recognised a stale handle by comparing the particle backend's address, which a freed and reallocated backend can share. A ParticleSystemHandle is now a 64-bit value: the upper 32 bits are the generation of the backend that issued it, the lower 32 the system's index. Every IParticleBackend object takes the next number from a process-wide counter (never 0) when it is constructed, and every backend (CPU and PhysX) looks a handle up only if its generation matches, so a handle of a replaced or recreated backend, even one constructed at the same address, is ignored instead of naming one of the new backend's systems (both would have the same index). The component asks IParticleBackend::OwnsHandle instead of comparing pointers. The documented behaviour is unchanged: a replaced physics backend restarts the system on the CPU with one warning; with the physics backend removed entirely the system is inert. A wrapper that hands out another backend's handles constructs it with its own generation (CpuParticleBackend(generation), used by the test fake).

Source: engine/include/engine/physics/IParticleBackend.hpp, ParticleSystem::Backend; tests: PbdParticleBackendTest.ABackendRecreatedAtTheSameAddressDoesNotKnowTheOldHandles, PbdParticleBackendTest.AHandleOfAnotherBackendIsIgnored*, ParticleSystemTest.ARecreatedGpuBackendAtTheSameAddressStillInvalidatesTheOldHandle

The PhysX GPU backend PR #129

The backend is split in two so that nearly all of it is tested in CI without a GPU. PbdParticleBackend (engine/src/particles/PbdParticleBackend.cpp) holds the logic; it talks only to an IPbdDriver (engine/include/engine/particles/PbdDriver.hpp), a thin layer with no PhysX types: create a PBD system (material, particle system, buffer, phase), a host mirror of the buffer, Upload, ReadBack, SetMaterial, the scene gravity and the device name. PhysXPbdDriver (engine/src/physics/physx/PhysXPbdDriver.cpp) is the one implementation and the only place a CUDA context, a PBD system or a device pointer appears. It is compiled only where the GPU library is (Windows with PhysX ON; N2ENGINE_PHYSX_GPU_PROBE), and never on Linux, whose PhysX libraries are CPU-only.

  • Slots. One PBD particle system, material and particle buffer per ParticleSystem, with room for maxParticles. Slots 0 to count-1 are the living particles. A system of 0 particles exists without a GPU system and accepts nothing.
  • Emission. Spawn writes the new particles after the last slot of the pinned host arrays (position and inverse mass, velocity, phase), capped at maxParticles (it returns how many fit), then Upload copies the arrays to the device buffer under the scoped CUDA lock, sets the active count and raises the update flags. PhysX has no emitter: this is how particles are made.
  • The scene steps them. The physics scene simulates the particles, so Step(dt) does nothing. After every simulate and fetchResults, PhysXBackend::Update calls PbdParticleBackend::OnSceneStepped(dt): it copies positions and velocities back to the host mirror (scoped CUDA lock), ages every particle by dt, removes the ones past their lifetime by moving the last living particle into the slot (the CPU backend's rule), and uploads the compacted arrays when anything died. CopyPositions and GetAliveCount read the mirror only (one Vector4 per particle, w the age fraction) and feed the same billboard path as the CPU backend.
  • Ageing runs on the host because PhysX particles have no lifetime. Each particle's lifetime is picked from [lifetimeMin, lifetimeMax] when it spawns, from the system's seed.
  • Parameters. SetParams (every fixed step) changes the material only when it differs: the PBD gravity scale is the part of the wanted gravity along the scene's gravity (never negative; a scene without gravity gives 0), and drag is added to the preset's damping. collideWithGround, groundHeight and bounce are ignored: PhysX particles collide with the scene's colliders.
  • Clear / Stop / Destroy. Clear empties the system and sets the active count to 0; Stop only stops emission, as on the CPU. Destroy releases the buffer, the system (removed from the scene), the material and the pinned memory; so does leaving play mode, and shutting the physics backend down releases every system before the scene and the CUDA context.
  • Soft failure. If the driver refuses a system (no GPU library, out of GPU memory) or a transfer fails, the backend logs one warning, does nothing more with the GPU, and the physics backend drops it: GetParticleBackend() returns nullptr, the Particles health row becomes Disabled (Failed with physics.gpu=on) with the reason, and the systems that used it restart on the CPU backend (one warning each). A system whose creation is refused starts on the CPU at once. The rigid-body GPU scene keeps running.

Material presets

Each pbdMaterial is a set of PxPhysics::createPBDMaterial parameters plus the particle spacing and density that size the solver's offsets and the particle mass. A particle's mass is density times spacing cubed.

PresetBehaviourMaterial (friction / damping / viscosity / vorticity / surface tension / cohesion)Spacing, density, phase
WaterFlows, pools, splashes0.05 / 0.05 / 0.001 / 0.5 / 0.005 / 0.010.1, 1000, fluid + self collide
SandPiles up0.6 / 0.1 / 0 / 0 / 0 / 00.08, 1600, self collide
SmokeDrifts0 / 0.8 / 0.01 / 0.2 / 0 / 00.2, 100, fluid + self collide

These are starting values taken from PhysX's PBF snippet and the behaviour each material should have; they have not been tuned on a GPU. Particle spacing is not the billboard size: startSize and endSize only size the quads.

Limits and notes

  • Hardware. An NVIDIA GPU (compute capability 7.0 or newer) with a driver recent enough for the PhysX 5.6.1 GPU library (CUDA 12.8 class), on Windows, with PhysXGpu_64.dll next to the executable. AMD, Intel and macOS have no PhysX GPU, and Linux has no GPU library yet (a later change); there the CPU backend is used.
  • Whole-scene GPU dynamics. PBD particles need a GPU scene, and a GPU scene moves every rigid body to the GPU pipeline (see GPU physics). That is why physics.gpu is off by default.
  • Video memory. Each ParticleSystem allocates a PBD system and a buffer for its full maxParticles (positions, velocities and phases: 36 bytes a particle on the device, the same again in pinned host memory) on top of the GPU scene's own memory. 100000 particles is a few megabytes of buffer; the solver's working memory is the larger part and was not measured.
  • Host copy. Positions come back to the host every step (16 bytes a particle, velocities too) and the billboards are built on the CPU, as for the CPU backend. A step that expires or spawns particles also uploads the arrays again.
  • Cap. maxParticles is at most 100000 per system, and a spawn beyond room is dropped with the one "reached maxParticles" warning.
  • Gravity. Only gravity along the scene's gravity direction can be made.

Design decision: a thin driver seam under the PhysX backend PR #129

Nothing that needs a CUDA context can run in CI, so all logic that can be tested without one (slots, the cap, emission, ageing and compaction, presets, handles, failure) lives in PbdParticleBackend against IPbdDriver, and the tests run it against a fake driver with a fake device (FakePbdDriver) on every leg. The real driver is a mechanical translation of the interface into PhysX calls; it is compiled on the Windows legs and run only by the GPU test. Positions are read back to the host, not shared through CUDA-OpenGL interop, so the backend works for the OpenGL, software and any later renderer with no extra driver libraries (the proposal's recommendation; interop stays a later optimisation).

Design decision: ageing and compaction on the host, the host mirror always current PR #129

PhysX particles have no lifetime and no emitter. The backend ages them on the host and, when some die, writes the compacted state back; it reads the device state into the mirror after every scene step, so a later spawn never uploads stale positions over particles that have moved. The cost is a device-to-host copy per step per live system and a full upload on steps where particles spawn or die. That was chosen over partial copies for simplicity; it can be optimised once there is a measurement.

Running the GPU test PR #129

The GPU golden test PhysXGpuParticlesGoldenTest.SpawnedParticlesFallRespectTheCapAndReleaseCleanly (tests/engine/physics/PhysXGpuParticlesTests.cpp) is part of engine_tests and so registered with ctest, but it is skipped (GTEST_SKIP with the reason) unless all of these hold: a Windows build with PhysX and its GPU library, not a GitHub Actions run (GITHUB_ACTIONS is not set), PxGetSuggestedCudaDeviceOrdinal() >= 0, and a GPU scene that actually came up. It reports "skipped" on every CI leg and does its work on a PC with an NVIDIA GPU.

cmake -S . -B build -A x64 -DN2ENGINE_BUILD_TESTS=ON -DN2ENGINE_USE_PHYSX=ON
cmake --build build --config Release --parallel --target engine_tests
build\bin\Release\engine_tests.exe --gtest_filter=PhysXGpuParticlesGoldenTest.*

Expected on a working GPU: a line [ GPU ] PhysX GPU: <your card> (CUDA device 0), then [ OK ]. The test creates a water system of 100 particles and offers 125 (the cap: 100 fit, then 0 more), checks all 100 exist and are finite, steps the scene for half a second with no colliders and checks the cloud fell between 0.5 and 3 metres, creates a sand system whose particles live 0.1 s and checks all are gone after 0.2 s, that Clear and Destroy work and that a destroyed handle is dead, then shuts the backend down with a system still alive (it must not crash or hang) and starts a second backend that does not know the old handle. A run that prints [ SKIPPED ] says why (no GPU, no PhysXGpu_64.dll, ...). The full hand-run list, including a scene with a PhysX particle system, is the GPU particles checklist.

Emission and simulation PR #125

  • Fixed step. ParticleSystem::OnFixedUpdate steps the backend by the scaled fixed timestep and then emits what the rate has accumulated, once per fixed step. The result depends on the timestep and the calls made, never on the frame rate. The fractional part of the rate carries over, so 7 particles per second at a 0.02 s step emits one every seventh step with no drift (ParticleEmitter::Advance); a single step emits at most 4096.
  • Shapes. Cone: from a disc of shapeRadius on the object's local XZ plane, in directions spread uniformly within coneAngle degrees (half angle) of local +Y. Sphere: from a random point inside a sphere of shapeRadius, moving straight away from its centre. Speeds come from speedMin to speedMax; an inverted range counts as its minimum.
  • Integration. Semi-implicit Euler per particle: velocity gets gravity, then drag, then the position moves. A particle that reaches its lifetime is removed by moving the last particle into its slot, so the order of particles changes as they die (the same way every run).
  • Determinism. The same seed and the same calls give the same particles: the generator (ParticleRandom) is integer-only, the simulation is plain float code in a fixed order, and the emitter and the backend have separate seeded streams. It is exact on one machine and build; floats are not promised to match bit for bit across compilers.
  • The cap. A system never holds more than maxParticles (limit 100000: a larger setting is lowered with a warning). Particles that don't fit are dropped, and the system logs one warning naming the object ("reached maxParticles"), not one per particle. Clear lets it warn again.
  • Collision. Only the optional ground plane. Particles do not collide with colliders or with each other, and the CPU backend never queries the physics world (so it behaves the same with no physics backend). Collision with rigid bodies is what the PhysX backend is for.
  • No per-step allocation. The backend's arrays, the spawn buffers and the position copy keep their capacity, so a steady system allocates nothing after it has grown.

Design decision: the ground plane is the only CPU collision PR #125

A raycast per particle per step against the physics world is not cheap, needs a physics backend (the headless host and CI may have none) and would make the CPU backend depend on it. The plan allowed it only if cheap, so the CPU backend does a ground plane and nothing else; documented here and in the field's tooltip. Real collision comes with the PhysX backend.

Source: engine/src/particles/CpuParticleBackend.cpp, ParticleEmitter.cpp, ParticleRandom.hpp; tests: CpuParticleBackendTest.*, ParticleEmitterTest.*, ParticleRandomTest.* (tests/engine/particles/ParticleSimulationTests.cpp)

Play mode, pause and saving PR #125

  • Only while playing. The system starts in OnAttach, which a scene runs when it plays. A scene opened for editing never attaches its components, so nothing is simulated or drawn in edit mode (there is no editor preview).
  • Never saved. The scene file holds the fields above and nothing else; a reflection test pins that the saved keys are exactly the fields. A scene saved and loaded gives a system with the same settings and no particles.
  • Exit clears. Leaving play mode replaces the scene, which destroys its components: OnDestroy destroys the backend system and the GPU mesh, so nothing outlives play.
  • Pause freezes. A time scale of 0 runs no fixed step (Application), so nothing is emitted or moved, and the frozen particles are still drawn.

Drawing PR #125

  • Billboards. Every frame the quads are rebuilt on the CPU from the backend's positions (Particles::BuildBillboards): 4 vertices and 6 indices a particle, facing the camera of the frame being drawn. Scene::Render makes its camera current for the duration of the draw (Rendering::RenderCamera), because IRenderable::RenderInQueue gets no camera. Drawn outside a Scene::Render, the quads face a default camera looking down -Z.
  • One mesh. The mesh is updated in place with IRenderer::UpdateMesh (recreated on a renderer that can't), the same way TextRenderer does. The rebuild of the vertices is the one per-frame cost beyond the simulation; the vertex and index vectors keep their capacity, and the indices are written only for quads the mesh did not have before. 100000 particles is 400000 vertices a frame.
  • State. The Transparent queue's state (blended, depth-tested, not writing depth) with culling off, in world space (identity model matrix), through the standard unlit shader: the particle's colour as the vertex colour times the optional texture. Additive blends with (SRC_ALPHA, ONE) on OpenGL (RenderState::additive).
  • Renderers. OpenGL and the software renderer draw particles. The software renderer cannot blend: quads are opaque there and Additive is drawn as Alpha; a fully transparent quad (alpha below 0.01) is skipped. The Vulkan renderer blends like OpenGL since stage D of #43 PR 158: Alpha particles blend with SRC_ALPHA / ONE_MINUS_SRC_ALPHA, Additive ones with SRC_ALPHA / ONE, and a fully faded particle is drawn at alpha 0, which leaves the frame as it was. The one mesh is updated every frame through UpdateMesh (a new buffer each time, the old one retired once the GPU is done with it). Lavapipe goldens cover it (VulkanParticlesGoldenTests.cpp, testing).
  • Bounds. A particle system reports no world bounds (GetWorldBounds is empty), so the editor picks its object by a small sphere around its position.

Design decision: CPU-built billboards through UpdateMesh, no new renderer API PR #125

Version 1 needs no change to the renderer interface: the particles are one dynamic mesh like a text block, which works on OpenGL and the software renderer today. Instanced or point-sprite drawing and CUDA-OpenGL interop are later optimisations (the cost ceiling is the CPU rebuild). The one renderer change is the additive flag on RenderState.

Source: engine/src/particles/ParticleBillboards.cpp, engine/include/engine/rendering/RenderCamera.hpp, ParticleSystem::RenderInQueue; tests: ParticleBillboardsTest.*, ParticleRendererTest.* (tests/engine/rendering/ParticleRendererTests.cpp), SoftwareParticlesGoldenTest.*

The Particles health row PR #125

The Particles row of engine health follows the physics backend's particle GPU status (Disabled with the reason when physics.gpu is off or no GPU works, Running with the detail PhysX GPU: <device> (CUDA device N) when the GPU scene and its particle backend are up, Failed only for physics.gpu=on with a failed probe or particle backend) PR #129; it is read again when health is asked for, so a GPU that stops working for particles shows as Disabled. Once ParticleSystem components are running, its detail also says which backends they use, for example physics.gpu is off; ParticleSystems: 2 CPU. With none running the row is exactly what the probe made. The editor protocol already carries the row as a generic SubsystemStatus, so nothing changes there.

Source: Application::GetHealth, Particles::ParticleUsage; tests: ParticleHealthDetailTest.*, ParticleUsageTest.*, ParticleBackendSelectionTest.*

Tests and what is not verified

  • Pure data tests with no window or renderer: the CPU backend (determinism, the cap, lifetimes, gravity, drag, the ground plane, bad parameters), the emitter, backend selection with a fake physics backend that offers a GPU particle backend, the billboard builder.
  • Component tests: registration and reflection, save and load, play/stop/clear/burst, the cap warning, the fallback warning, a fake GPU backend through the seam, an outliving physics backend, pause.
  • Drawing: a recording renderer (draw count, state, in-place updates, resource release) and golden images on the headless software renderer (colour, position, camera-facing, colour and size by age).
  • A headless Application::Tick run with the software renderer and no physics backend, including drawing a frame and leaving the scene (ParticleHeadlessTest.*).
  • The PhysX backend's logic against a fake driver and fake device, on every leg PR #129 (PbdParticleBackendTest.*, tests/engine/particles/PbdParticleBackendTests.cpp): creation and the preset's material, spawn into the mirror and its upload, the cap and a burst larger than it, read-back after a step, spawning after a step not reverting the living, ageing and swap-last compaction, expiry making room, Clear and Destroy, the presets and the gravity and drag mapping, SetParams changing the material only when it differs, generation-counted handles (two backends, a recreated backend at the same address, the CPU backend's handles), and the soft failure paths (refused system, failed upload, failed read-back, a too small mirror). Component tests cover a recreated backend at the same address, a refused system falling back to the CPU, and the pbdMaterial field.

Not verified in CI

Particles drawn by the OpenGL renderer on a real GPU (CI has none; the OpenGL draw path is the same UpdateMesh and DrawMesh calls as text, plus the additive blend function). This wording is for OpenGL only. The Vulkan renderer's particles are verified without a GPU: the lavapipe goldens draw them blended and additive and check the pixels against OpenGL's blend equation (stage D of #43). What is not verified is a real Vulkan driver (blend rounding on hardware) and the cost of the per-frame UpdateMesh with very large particle counts.

The real PhysX driver needs a CUDA context, so it is compiled on the Windows legs but never run in CI. It was verified manually: on 2026-10-14 the maintainer ran the GPU golden test and the checklist on a Windows PC with an NVIDIA GPU, and both passed. That run exercised the driver's assumptions about PhysX 5.6.1: that the buffer's position, velocity and phase pointers are device pointers that a plain host-to-device copy plus raiseFlags updates; that the solver keeps particles in buffer order (the host ages by slot); that setNbActiveParticles and the flags may be set between steps; and the order the buffer, system, scene actor and material are released in.

Not recorded or not verified: no VRAM figures or timings were captured, and the water, sand and smoke presets (and the solver offsets and maximum velocity) were not tuned. Nothing was verified on other GPUs, vendors or drivers, or on Linux (the Linux GPU asset is deferred).
