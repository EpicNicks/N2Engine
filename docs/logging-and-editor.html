Logging, health & editor

The Logger is the engine's single log channel: messages go to whoever subscribes, optionally queued until someone does. EngineHealth reports which subsystems started. The editor server (N2EditorHost) is a headless engine process that an external editor drives over a small binary TCP protocol.

Logger

Logger is a static class. It does not write anywhere by itself: Logger::Log(message, level) raises Logger::logEvent, an EventHandler<std::string_view, LogLevel>, and subscribers decide what to do (print, show in a GUI, collect in a test).

LevelHelperUsed for
LogLevel::InfoLogger::InfoProgress (subsystem started, scene loaded).
LogLevel::WarnLogger::WarnDegraded but continuing (failed subsystem, replaced scene data).
LogLevel::ErrorLogger::ErrorAn operation failed. Many engine APIs report errors only this way and return a null/false value.

There is no level filter; every subscriber receives every level.

Backlog

What Log does depends on Logger::broadcastUnbroadcastLogs (default false) and on whether anyone is subscribed:

broadcastUnbroadcastLogsSubscribersResult
falsenoneThe message is dropped.
truenoneThe message is queued.
eitherat least oneThe queued backlog is delivered first, oldest first, then this message.

The backlog is drained from a queue swapped out before delivery. A subscriber that logs while the backlog is being delivered re-enters Log, finds an empty queue, and its message is delivered in place. Before PR #24 the nested call drained the same queue and delivered entries twice.

Source: engine/include/engine/Logger.hpp, engine/src/Logger.cpp — Logger::Log; tests: CoreRobustnessTest.LoggerDeliversBacklogOnceWhenASubscriberLogs

Guarantee

Queued messages are delivered exactly once, in order, the first time a message is logged with a subscriber present, even if a subscriber logs during delivery. With two queued messages and a handler that logs "nested" on its first call, the order is first, nested, second, trigger. Test: CoreRobustnessTest.LoggerDeliversBacklogOnceWhenASubscriberLogs.

Subscribing

logEvent is a Logger::LogEventHandler: the same +=, -=, call and GetSubscriberCount() as an EventHandler, each taken under the Logger's lock Remaining defects. logEvent += handler returns an id; logEvent -= id removes it. Both are safe during dispatch and from any thread: a handler added during a log is first called on the next message; a handler removed during a log (even itself) is not called again. Subscribing does not flush the backlog; the next Log call does.

N2Engine::Logger::broadcastUnbroadcastLogs = true; // keep early messages until the UI subscribes
// ...
const size_t id = N2Engine::Logger::logEvent += [](std::string_view msg, N2Engine::Logger::LogLevel level)
{
    myConsole.Append(level, std::string(msg)); // copy: the view is only valid during the call
};
// ...
N2Engine::Logger::logEvent -= id;

Source: engine/include/engine/Logger.hpp — Logger::LogEventHandler; engine/include/engine/base/EventHandler.hpp — EventHandler::operator+=, operator-=, operator(); tests: EventHandlerTest.*

Note

The message is passed as a std::string_view. Handlers that keep it must copy it.

Logging from other threads Remaining defects

Logger::Log (and Info/Warn/Error), subscribing, unsubscribing and the debug console's redirected streams may be used from any thread. They share one recursive mutex:

  • Log holds it from the backlog check until the message (and any backlog) has been delivered, so a message reaches every subscriber whole, and messages from different threads are delivered one after another, never interleaved.
  • Subscribers run on the thread that logged, while it holds the lock. A UI subscriber that must touch main-thread-only state should copy the message and queue it.
  • Being recursive, the lock lets a subscriber log (or write to a redirected std::cout) on its own thread: that message is delivered in place, as described above.
  • A subscriber must not wait for another thread that logs: that thread blocks on the lock, a deadlock.
  • The redirected streams take the same lock per character, so their line buffers are safe, but characters written by two threads at once can still mix within a line. Use Logger directly from worker threads.
  • The mutex is never destroyed, so logging during static destruction still works. It is not async-signal-safe: a POSIX signal handler must not log (the editor host's handler only sets a flag).

Source: engine/src/Logger.cpp — LogMutex, Logger::Log, Logger::LogEventHandler, LoggerStreambuf::overflow, sync; editor-server/src/Main.cpp — SignalHandler; tests: CoreRobustnessTest.LoggerIsSafeToUseFromManyThreads, CoreRobustnessTest.LoggerDeliversBacklogOnceWhenASubscriberLogs

Design decision: deliver on the logging thread, under one lock

The alternative, queueing other threads' messages for the main thread to deliver, would keep subscribers single-threaded but lose messages logged just before a crash or during shutdown (when the main loop no longer drains), and would reorder them against main-thread messages. Logging is a diagnostic channel, so delivering immediately and in order matters more. One recursive lock keeps the existing re-entrancy rule (a subscriber may log) and makes subscription changes safe while another thread logs. The cost is that subscribers can be called on any thread, which is documented above; the engine's own console subscriber only writes to a stream.

Debug console and stream redirection

Logger::InitializeDebugConsoleHelper() is called by Application::Init only when N2ENGINE_DEBUG is defined. The engine target defines N2ENGINE_DEBUG=1 (PUBLIC) for the Debug configuration only, so Release builds have no console output unless the program subscribes itself. N2EditorHost does not subscribe, so a Release build of the host prints no logs at all.

The helper:

  1. Runs once per process; later calls return immediately. Before PR #24 a second Application::Init added a second console subscriber and every line was printed twice.
  2. Redirects std::cout to the Logger at Info and std::cerr at Error, without echoing to the original streams.
  3. Subscribes a handler that writes [LEVEL] message to the original stdout. Levels are coloured (Info blue, Warn yellow, Error red) when stdout is a terminal and, on Windows, virtual-terminal processing can be enabled; on other platforms when TERM is set and not dumb.

The original-stdout stream is allocated with new and never destroyed, because it is created after the Application singleton and would otherwise be destroyed first, crashing log calls made during later teardown.

Stream redirection can also be used directly: RedirectStdout, RedirectStderr and RedirectStream(stream, level, echo) install a StreamRedirector that turns each completed line (split on \n, \r dropped, empty lines skipped) into a log event. Redirectors are kept for the life of the process. Note that redirected lines are raised on logEvent directly and bypass the backlog queue.

Source: engine/src/Logger.cpp — Logger::InitializeDebugConsoleHelper, LoggerStreambuf::overflow, Logger::RedirectStream; engine/CMakeLists.txt; engine/src/Application.cpp — Application::Init

The editor host process

editor-server/ builds two targets: the static library N2EditorServer (everything except Main.cpp, so linking it never pulls in a main) and the executable N2EditorHost.

OptionMeaning
-p, --port <port>TCP port to listen on (default 9999). Must be a whole number from 1 to 65535 (std::from_chars, no trailing characters); otherwise the host prints "Invalid port: ..." to stderr and exits with code 1 PR #33.
--bind <ipv4>Address to listen on (default 127.0.0.1) PR #33. Any other value logs a warning that the server has no authentication. An address that is not a valid IPv4 address makes Start fail. See why loopback is the default.
--project <path>Stored in ApplicationOptions::projectPath (which Application::Init does not currently use), and sets the server's scenes directory to <path>/scenes, the only place DeleteScene may delete files PR #33. Without it, DeleteScene is disabled.
-h, --helpPrint usage and exit 0.

Startup and shutdown sequence:

  1. Install SIGINT/SIGTERM handlers that only clear a g_running flag (the Logger is thread-safe, but logging is not async-signal-safe; see Logging from other threads).
  2. Application::Init with PhysX, OpenGL and isHeadless = true (hidden window, audio Disabled).
  3. EditorServer::Start(port, bindAddress): bind to the bind address (loopback by default) PR #33, listen with a backlog of 1, start the network thread. SO_REUSEADDR is set on POSIX only, so a restarted host can rebind while the last connection is in TIME_WAIT; on Windows it is left off (there it would allow another process to take over the port, and the default already rebinds). On an invalid address or a socket/bind/listen failure, Start logs and returns false, and the host skips the loop and exits with code 1 PR #33.
  4. Main loop, while g_running, the server is running, no quit was requested, and the window (if valid) is not closing: window.PollEvents(), then server.ProcessCommands(16 ms), which runs the queued editor requests and waits up to 16 ms for one to arrive (this replaces the old fixed 16 ms sleep). See Threading.
  5. A last ProcessCommands() to flush log lines the network thread posted, server.Stop(), then OnApplicationQuit() on the current scene if any, then Application::Shutdown(). Stop() returns within about 100 ms even with an idle client connected PR #33: it clears the running flag, closes the command queue (waking a network thread that waits for a result), joins the thread, and only then closes the sockets.
  6. Exit 0; exit 1 if the server failed to start, or if a std::exception escaped (logged as "Fatal error: ...").

The server accepts one client at a time: the network thread accepts a connection, serves it until it disconnects or sends Shutdown, closes it, and goes back to accept. Start() may be called again after a client's Shutdown or after Stop(), on the same port, and the server listens again PR #33.

Source: editor-server/src/Main.cpp — main, ParsePort; editor-server/src/EditorServer.cpp — EditorServer::Start, Stop, ServerLoop, HandleClient, WaitUntilReady; tests: EditorServerSocketTest.ListensOnLoopbackAndRunsCommandsOnTheDrainingThread, EditorServerSocketTest.StopReturnsWithNoClient, EditorServerSocketTest.RestartsOnTheSamePortAfterAClientShutdown, EditorServerSocketTest.RejectsAnInvalidBindAddress (Windows only)

Wire format

Requests and responses use the same frame:

[type: uint8][length: uint32][payload: length bytes]
  • Request type is a CommandType, response type a ResponseType; each request gets exactly one response.
  • Integers and floats are written with memcpy in host byte order, which is little-endian on the supported (x86-64 Windows) targets. The CI smoke test relies on little-endian.
  • A string is [uint32 length][bytes] with no terminator. A bool is one byte (0 or 1). A vec3 is three float32.
  • Error responses are the exception: their payload is the raw message bytes, not a length-prefixed string; the frame length is the message length.

Response types: Ok 0x00 (empty), Error 0x01, FrameData 0x02, CameraPosition 0x03, EntityTransform 0x04, EntityList 0x05, EntityCreated 0x06, SceneData 0x07, ScriptData 0x08, EngineHealth 0x09.

Source: editor-server/include/editor-server/Protocol.hpp; editor-server/include/editor-server/Serialization.hpp — BufferWriter, BufferReader; editor-server/include/editor-server/Commands.hpp — Write* builders

# PowerShell: ask a running host for its health (from .github/workflows/tests.yml)
$client = [System.Net.Sockets.TcpClient]::new("127.0.0.1", 9999)
$stream = $client.GetStream()
$bytes = [byte[]](@(0x50) + [BitConverter]::GetBytes([uint32]0))  # GetEngineHealth, empty payload

editor-server/protocol/protocol.json describes every command (id, request fields, response type and fields), the shared types (vec3, EntityInfo, SubsystemStatus) and the response ids. Three Python generators in editor-server/protocol/generators/ turn it into client-side declarations (enums of command and response ids, request and response structs; no encoding code):

Threading: commands run on the main thread

Every command that touches engine state runs on the host's main thread PR #33. The server has two sides:

  • Network thread. Accepts the client, reads each frame (header, size check, payload) and enqueues ExecuteCommand(type, payload) as a std::packaged_task on a CommandQueue. It then blocks on the task's future and sends the response frame it gets back. It never touches scenes, Lua, GLFW/GL or the Logger; its own log lines are posted to the main thread as queued tasks (PostLog). Every socket call waits in 100 ms select() slices and checks the running flag, so the thread never blocks forever and no socket is closed from another thread.
  • Main thread. The host loop calls server.ProcessCommands(16 ms) after PollEvents. It runs everything queued, in order, outside the queue's lock. Handlers, RenderFrame (GL and GLFW calls), LoadScene's scene switch and all logging happen here.

Two things are answered on the network thread without queueing, because neither touches the engine: Shutdown, and the Error for an oversized payload. Closing the queue (Stop()) drops pending work and breaks its futures, which wakes a network thread waiting for a result; that thread then drops the connection.

A response is built in full before it is sent, so a request is answered only after the main loop has drained it. A host that never calls ProcessCommands leaves every client waiting.

Source: editor-server/include/editor-server/CommandQueue.hpp — CommandQueue::Enqueue, Drain, Close; editor-server/include/editor-server/EditorServer.hpp (threading model comment); editor-server/src/EditorServer.cpp — EditorServer::HandleClient, ExecuteCommand, PostLog, WaitUntilReady; tests: CommandQueueTest.WorkEnqueuedFromAnotherThreadRunsOnTheDrainingThread, CommandQueueTest.ProducerBlockedOnTheResultIsAnsweredByDrain, CommandQueueTest.DrainRunsEverythingInOrder, CommandQueueTest.DrainWaitsForWorkUpToTheTimeout, CommandQueueTest.ExceptionFromWorkReachesTheFuture, CommandQueueTest.CloseBreaksPendingAndLaterWork, CommandQueueTest.CloseWakesAProducerWaitingOnItsResult, EditorServerSocketTest.ListensOnLoopbackAndRunsCommandsOnTheDrainingThread

Guarantee PR #33

Editor commands never run concurrently with the frame loop: they run on the thread that calls ProcessCommands, between PollEvents calls. Before PR #33 they ran on the server thread with no lock, while the main thread kept polling input, and RenderFrame made GL and GLFW calls from the wrong thread. DeleteScene rules

DeleteScene takes a scene name, not a path PR #33. EditorServer::ResolveSceneFile turns it into a file inside the scenes directory (<project>/scenes, from --project) or rejects it:

  • .json is appended unless the name already ends with it, in any case. So "Level.1" names Level.1.json, and "notes.txt" names notes.txt.json: no other extension can be reached.
  • Rejected: an empty name, a NUL character, absolute paths, drive-relative and rooted paths (C:x, \x), UNC and \\?\ paths, and names that end in a directory (dir/, ., ..).
  • The parent directory is canonicalised (symlinks and .. resolved) and must be the scenes directory or a directory inside it. Subdirectories are allowed; .. escapes are not.
  • The file name itself is not resolved, so a symlinked scene file deletes the link, never its target.
  • Only a regular file is removed. The file of the currently loaded scene (same stem as its sceneName) is refused, as SceneManager::DeleteScene refuses to delete the loaded scene.
  • Without --project there is no scenes directory and every DeleteScene is an Error.

Before PR #33 the request string went straight to std::filesystem::remove, so any client could delete any file the host could write. protocol.json already named the field sceneName; the server now matches it. Checking and then removing is not atomic; exploiting that needs local write access to scenes/, which is accepted for a dev tool.

Source: editor-server/src/EditorServer.cpp — EditorServer::ResolveSceneFile, EditorServer::HandleDeleteScene; tests: DeleteSceneTest.ResolvesSceneFilesInsideTheScenesDirectory, RejectsPathTraversal, RejectsAbsolutePaths, OnlyEverNamesSceneFiles, RejectsEmptyAndNulInput, DeletesASymlinkedSceneAsTheLinkNotItsTarget, DeleteSceneOnlyDeletesInsideTheScenesDirectory, DeleteSceneIsDisabledWithoutAScenesDirectory. The loaded-scene refusal is not covered by a test.

Malformed requests and errors

A bad request gets an Error response and the host keeps serving PR #33. Before PR #33 nothing on the server thread caught exceptions, so any throwing handler terminated the host.

InputWhat happens
Payload length over 64 MiB (MaxPayloadBytes)Checked from the header before allocating. The network thread sends Error "Payload of N bytes exceeds the 67108864 byte limit" and closes the connection, because the unread payload makes the stream impossible to resynchronise. If the client has already sent payload bytes, it may see a connection reset instead of the Error.
Payload shorter than the command needsBufferReader checks bounds on every read (including a string's declared length) and throws; the exception becomes an Error.
Viewport size outside 1–4096Error; the previous size is kept. The frame buffer is at most 4096 × 4096 × 4 bytes (64 MiB), and it is moved into the response rather than copied.
Invalid JSON in LoadSceneParsed without throwing; Error "The scene passed is not valid JSON".
No scene loadedError from SaveScene, GetCurrentScene, DestroyEntity, Get/SetEntityTransform ("No scene loaded") and CreateEntity ("No scene present"). GetAllEntities returns an empty list.
Any other exception in a handler (engine code, a Lua callback during DestroyEntity)ExecuteCommand catches it, logs "Command 0x.. failed: ..." and returns Error "Command failed: ...". A handler that produces no response gets the same treatment.
Anything escaping HandleClient on the network thread (for example bad_alloc)Caught; the connection is dropped and the server goes back to accept.

Serving without a window, and quitting

The host keeps serving when the window or renderer failed (for example on a machine without a GPU). It logs "No window or renderer; rendering commands will be unavailable" and loops on its other conditions only. Everything except RenderFrame works; clients should call GetEngineHealth to find out what is available. This is exactly the CI configuration (see CI).

The host's loop ends on any of:

TriggerHow it is seen
SIGINT / SIGTERMg_running becomes false.
Shutdown command (0xFF)server.IsRunning() becomes false.
Application::Quit() from game code or Luaapp.IsQuitRequested().
Window closed (only when a valid window exists)window.ShouldClose().
Server failed to startserver.IsRunning() was never true; the host exits with code 1 PR #33.

Whatever the trigger, the host then stops the server, calls OnApplicationQuit() on the current scene (as Application::Run does), and calls Application::Shutdown() before returning from main, so teardown does not rely on static destruction. Quit handling for Run() is described in Quitting, and why Quit() is only a request in this design note.

Security and remaining gaps

Warning

The editor protocol has no authentication. Since PR #33 the host listens on 127.0.0.1 only, so other machines cannot reach it unless you pass --bind. But any process on the same machine can still connect and send any command. It can load arbitrary scene JSON, including LuaComponents whose scripts then run in the host (inside the Lua sandbox); read the viewport; and delete .json files under <project>/scenes. Do not pass --bind with a non-loopback address on a network you do not trust: whoever can reach the port gets the same control. A shared-secret token would change the protocol and is not implemented.

Design decision: a loopback-only editor server

N2EditorHost is a development tool that an editor on the same machine drives. The protocol carries no credentials, so the only safe default is to be unreachable from other machines: the server binds to 127.0.0.1, and listening anywhere else takes an explicit --bind that logs a warning. Authentication was left out rather than bolted on, because it would change the wire format for every client. For the same reason the server limits what a command can do: DeleteScene only ever deletes .json files inside the project's scenes directory, and malformed input gets an Error instead of crashing the host.

Commands run on the main thread for a separate reason: engine state is single-threaded. Scenes, Lua and GLFW/OpenGL (a context is current on one thread, and GLFW event polling must be on the main thread) have no locks; only the Logger is thread-safe (see Logging from other threads). Queueing commands for the main loop makes every handler behave like ordinary game code between frames, instead of adding locks across the engine. Lua handles rely on the same assumption (see why Lua handles stay valid).

Open question

Spec drift. Protocol.hpp still declares an unused EntityTransformRequest with an int32 entity id, while the protocol uses UUID strings (editor-server/include/editor-server/Protocol.hpp). Whether it should be removed is not decided.
