Logging, health & editor

The Logger is the engine's single log channel: messages go to whoever subscribes, optionally queued until someone does. EngineHealth reports which subsystems started. The editor server (N2EditorHost) is a headless engine process that an external editor drives over a small binary TCP protocol.

Logger

Logger is a static class. It does not write anywhere by itself: Logger::Log(message, level) raises Logger::logEvent, an EventHandler<std::string_view, LogLevel>, and subscribers decide what to do (print, show in a GUI, collect in a test).

LevelHelperUsed for
LogLevel::InfoLogger::InfoProgress (subsystem started, scene loaded).
LogLevel::WarnLogger::WarnDegraded but continuing (failed subsystem, replaced scene data).
LogLevel::ErrorLogger::ErrorAn operation failed. Many engine APIs report errors only this way and return a null/false value.

There is no level filter; every subscriber receives every level.

Backlog

What Log does depends on Logger::broadcastUnbroadcastLogs (default false) and on whether anyone is subscribed:

broadcastUnbroadcastLogsSubscribersResult
falsenoneThe message is dropped.
truenoneThe message is queued.
eitherat least oneThe queued backlog is delivered first, oldest first, then this message.

The backlog is drained from a queue swapped out before delivery. A subscriber that logs while the backlog is being delivered re-enters Log, finds an empty queue, and its message is delivered in place. Before PR #24 the nested call drained the same queue and delivered entries twice.

Source: engine/include/engine/Logger.hpp, engine/src/Logger.cpp — Logger::Log; tests: CoreRobustnessTest.LoggerDeliversBacklogOnceWhenASubscriberLogs

Guarantee

Queued messages are delivered exactly once, in order, the first time a message is logged with a subscriber present, even if a subscriber logs during delivery. With two queued messages and a handler that logs "nested" on its first call, the order is first, nested, second, trigger. Test: CoreRobustnessTest.LoggerDeliversBacklogOnceWhenASubscriberLogs.

Subscribing

logEvent += handler returns an id; logEvent -= id removes it. Both are safe during dispatch: a handler added during a log is first called on the next message; a handler removed during a log (even itself) is not called again. Subscribing does not flush the backlog; the next Log call does.

N2Engine::Logger::broadcastUnbroadcastLogs = true; // keep early messages until the UI subscribes
// ...
const size_t id = N2Engine::Logger::logEvent += [](std::string_view msg, N2Engine::Logger::LogLevel level)
{
    myConsole.Append(level, std::string(msg)); // copy: the view is only valid during the call
};
// ...
N2Engine::Logger::logEvent -= id;

Source: engine/include/engine/base/EventHandler.hpp — EventHandler::operator+=, operator-=, operator(); tests: EventHandlerTest.*

Note

The message is passed as a std::string_view. Handlers that keep it must copy it.

Open question

Logger::Log and EventHandler have no locking. The editor server logs from its network thread while the main thread can also log (engine/src/Logger.cpp — Logger::Log; editor-server/src/EditorServer.cpp). Whether the Logger is meant to be thread-safe is not stated.

Debug console and stream redirection

Logger::InitializeDebugConsoleHelper() is called by Application::Init only when N2ENGINE_DEBUG is defined. The engine target defines N2ENGINE_DEBUG=1 (PUBLIC) for the Debug configuration only, so Release builds have no console output unless the program subscribes itself.

The helper:

  1. Runs once per process; later calls return immediately. Before PR #24 a second Application::Init added a second console subscriber and every line was printed twice.
  2. Redirects std::cout to the Logger at Info and std::cerr at Error, without echoing to the original streams.
  3. Subscribes a handler that writes [LEVEL] message to the original stdout. Levels are coloured (Info blue, Warn yellow, Error red) when stdout is a terminal and, on Windows, virtual-terminal processing can be enabled; on other platforms when TERM is set and not dumb.

The original-stdout stream is allocated with new and never destroyed, because it is created after the Application singleton and would otherwise be destroyed first, crashing log calls made during later teardown.

Stream redirection can also be used directly: RedirectStdout, RedirectStderr and RedirectStream(stream, level, echo) install a StreamRedirector that turns each completed line (split on \n, \r dropped, empty lines skipped) into a log event. Redirectors are kept for the life of the process. Note that redirected lines are raised on logEvent directly and bypass the backlog queue.

Source: engine/src/Logger.cpp — Logger::InitializeDebugConsoleHelper, LoggerStreambuf::overflow, Logger::RedirectStream; engine/CMakeLists.txt; engine/src/Application.cpp — Application::Init

Health

engine/include/engine/Health.hpp defines the health report that Application::Init returns and Application::GetHealth() keeps:

enum class SubsystemState { NotStarted, Running, Disabled, Failed };

struct SubsystemStatus { std::string name; SubsystemState state; std::string detail; };

struct EngineHealth
{
    std::vector<SubsystemStatus> subsystems;
    bool IsHealthy() const;                                 // no subsystem is Failed
    const SubsystemStatus* Find(std::string_view name) const; // nullptr if absent
};

constexpr std::string_view ToString(SubsystemState);        // "NotStarted", "Running", ...

The subsystem names, their order, and what each state means for the engine are documented on the Application page: Subsystem health.

The editor host process

editor-server/ builds two targets: the static library N2EditorServer (everything except Main.cpp, so linking it never pulls in a main) and the executable N2EditorHost.

OptionMeaning
-p, --port <port>TCP port to listen on (default 9999). Parsed with std::stoi; a non-number throws before the main try block.
--project <path>Stored in ApplicationOptions::projectPath (which Application::Init does not currently use).
-h, --helpPrint usage and exit 0.

Startup and shutdown sequence:

  1. Install SIGINT/SIGTERM handlers that clear a g_running flag.
  2. Application::Init with PhysX, OpenGL and isHeadless = true (hidden window, audio Disabled).
  3. EditorServer::Start(port): bind to all interfaces (INADDR_ANY) with SO_REUSEADDR, listen with a backlog of 1, start the server thread. On socket/bind/listen failure it logs and returns with the server not running, so the main loop exits at once.
  4. Main loop, every ~16 ms: window.PollEvents(), while g_running, the server is running, no quit was requested, and the window (if valid) is not closing.
  5. server.Stop(), then OnApplicationQuit() on the current scene if any, then Application::Shutdown().
  6. Exit 0; or exit 1 if a std::exception escaped (logged as "Fatal error: ...").

The server accepts one client at a time: the server thread accepts a connection, serves it until it disconnects or sends Shutdown, closes it, and goes back to accept.

Source: editor-server/src/Main.cpp — main; editor-server/src/EditorServer.cpp — EditorServer::Start, Stop, ServerLoop, HandleClient; editor-server/CMakeLists.txt

Wire format

Requests and responses use the same frame:

[type: uint8][length: uint32][payload: length bytes]
  • Request type is a CommandType, response type a ResponseType; each request gets exactly one response.
  • Integers and floats are written with memcpy in host byte order, which is little-endian on the supported (x86-64 Windows) targets. The CI smoke test relies on little-endian.
  • A string is [uint32 length][bytes] with no terminator. A bool is one byte (0 or 1). A vec3 is three float32.
  • Error responses are the exception: their payload is the raw message bytes, not a length-prefixed string; the frame length is the message length.

Response types: Ok 0x00 (empty), Error 0x01, FrameData 0x02, CameraPosition 0x03, EntityTransform 0x04, EntityList 0x05, EntityCreated 0x06, SceneData 0x07, ScriptData 0x08, EngineHealth 0x09.

Source: editor-server/include/editor-server/Protocol.hpp; editor-server/include/editor-server/Serialization.hpp — BufferWriter, BufferReader; editor-server/include/editor-server/Commands.hpp — Write* builders

# PowerShell: ask a running host for its health (from .github/workflows/tests.yml)
$client = [System.Net.Sockets.TcpClient]::new("127.0.0.1", 9999)
$stream = $client.GetStream()
$bytes = [byte[]](@(0x50) + [BitConverter]::GetBytes([uint32]0))  # GetEngineHealth, empty payload
$stream.Write($bytes, 0, $bytes.Length)
# read 5 header bytes: [0x09][uint32 payload length], then the payload

protocol.json and generated clients

editor-server/protocol/protocol.json describes every command (id, request fields, response type and fields), the shared types (vec3, EntityInfo, SubsystemStatus) and the response ids. Three Python generators in editor-server/protocol/generators/ turn it into client-side declarations (enums of command and response ids, request and response structs; no encoding code):

GeneratorOutput (checked in)
generate_cpp.pyeditor-server/clients/cpp/Protocol.generated.hpp
generate_csharp.pyeditor-server/clients/csharp/Protocol.generated.cs
generate_typescript.pyeditor-server/clients/web/protocol.generated.ts

The server does not use the generated files; its own definitions are Protocol.hpp (ids) and Commands.hpp (decoders and response builders). After changing the protocol, update protocol.json, the server headers and the handlers together, then rerun the three generators. protocol.json and the generators are installed to share/n2engine/protocol.

Source: editor-server/protocol/protocol.json; editor-server/protocol/generators/*.py; editor-server/CMakeLists.txt

Open question

editor-server/CMakeLists.txt declares a N2ProtocolGenerate custom command whose OUTPUT is include/editor/protocol/Generated.hpp, but generate_cpp.py writes clients/cpp/Protocol.generated.hpp. The declared output is never produced, so the build step either reruns every build or is effectively dead. Which file the build is meant to generate is unclear.

Commands

Commands run on the server thread, one at a time, in the order received. Unknown ids get Error "Unknown command". Every command except RenderFrame is logged as "Command Issued: 0x..".

Note

Why CreateScene refuses existing names PR #28: SceneManager::AddScene now replaces a stored scene with the same name (with a warning) instead of appending an unreachable duplicate. Without the check, creating a scene with an existing name would silently wipe that scene's saved data. See Scenes.

Serving without a window, and quitting

The host keeps serving when the window or renderer failed (for example on a machine without a GPU). It logs "No window or renderer; rendering commands will be unavailable" and loops on its other conditions only. Everything except RenderFrame works; clients should call GetEngineHealth to find out what is available. This is exactly the CI configuration (see CI).

The host's loop ends on any of:

TriggerHow it is seen
SIGINT / SIGTERMg_running becomes false.
Shutdown command (0xFF)server.IsRunning() becomes false.
Application::Quit() from game code or Luaapp.IsQuitRequested().
Window closed (only when a valid window exists)window.ShouldClose().
Server failed to startserver.IsRunning() was never true.

Whatever the trigger, the host then stops the server, calls OnApplicationQuit() on the current scene (as Application::Run does), and calls Application::Shutdown() before returning from main, so teardown does not rely on static destruction. Quit handling for Run() is described in Quitting.

Source: editor-server/src/Main.cpp — main; editor-server/src/EditorServer.cpp — EditorServer::HandleClient

Known gaps in the editor server

These come from reading editor-server/src/EditorServer.cpp and its headers; none is covered by a test.

Open question

Threading. All commands run on the server thread, while the main thread keeps calling Window::PollEvents (which runs InputSystem::Update). Commands read and modify the scene, SceneManager and camera, and RenderFrame calls RenderEditorFrame (which also calls PollEvents) from the server thread, although GLFW event polling is main-thread-only and the OpenGL context is made current only on the thread that initialised the renderer. There is no lock. Whether commands should be marshalled to the main thread is not decided.

Open question

Malformed requests. BufferReader (Serialization.hpp) does no bounds checking, so a payload shorter than the command expects reads past the buffer. HandleLoadScene calls nlohmann::json::parse outside any try, so invalid JSON throws on the server thread, where nothing catches it (std::terminate). How the server should answer a malformed request is not specified.

Open question

No-scene checks. HandleDestroyEntity, HandleSetEntityTransform and HandleGetEntityTransform call SceneManager::GetCurSceneRef() without checking that a scene is loaded; GetCurSceneRef dereferences a null pointer in that case. The other scene commands check first.

Open question

SaveScene response. HandleSaveScene passes an nlohmann::json object to WriteSceneData(BufferWriter&, const std::string&), which goes through nlohmann's implicit conversion to std::string. For an object value that conversion throws type_error instead of serialising; CreateScene and GetCurrentScene call .dump(). The snapshot update happens before the throw. Intended behaviour is clearly the dumped JSON; whether this path has been exercised is unknown.

Open question

Spec drift. protocol.json names the DeleteScene request field sceneName, but the server treats it as a filesystem path and deletes that file. Protocol.hpp still declares an unused EntityTransformRequest with an int32 entity id, while the protocol uses UUID strings. Which side is authoritative for DeleteScene is unclear.
