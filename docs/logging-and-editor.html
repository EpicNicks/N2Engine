Logging, health & editor

The Logger is the engine's single log channel: messages go to whoever subscribes, optionally queued until someone does. EngineHealth reports which subsystems started. The editor server (N2EditorHost) is a headless engine process that an external editor drives over a small binary TCP protocol. Projects, scene files and the project commands are on Editor projects.

Logger

Logger is a static class. It does not write anywhere by itself: Logger::Log(message, level) raises Logger::logEvent, an EventHandler<std::string_view, LogLevel>, and subscribers decide what to do (print, show in a GUI, collect in a test).

LevelHelperUsed for
LogLevel::InfoLogger::InfoProgress (subsystem started, scene loaded).
LogLevel::WarnLogger::WarnDegraded but continuing (failed subsystem, replaced scene data).
LogLevel::ErrorLogger::ErrorAn operation failed. Many engine APIs report errors only this way and return a null/false value.

There is no level filter; every subscriber receives every level.

Backlog

What Log does depends on Logger::broadcastUnbroadcastLogs (default false) and on whether anyone is subscribed:

broadcastUnbroadcastLogsSubscribersResult
falsenoneThe message is dropped.
truenoneThe message is queued.
eitherat least oneThe queued backlog is delivered first, oldest first, then this message.

The backlog is drained from a queue swapped out before delivery. A subscriber that logs while the backlog is being delivered re-enters Log, finds an empty queue, and its message is delivered in place. Before PR #24 the nested call drained the same queue and delivered entries twice.

Source: engine/include/engine/Logger.hpp, engine/src/Logger.cpp — Logger::Log; tests: CoreRobustnessTest.LoggerDeliversBacklogOnceWhenASubscriberLogs

Guarantee

Queued messages are delivered exactly once, in order, the first time a message is logged with a subscriber present, even if a subscriber logs during delivery. With two queued messages and a handler that logs "nested" on its first call, the order is first, nested, second, trigger. Test: CoreRobustnessTest.LoggerDeliversBacklogOnceWhenASubscriberLogs.

Subscribing

logEvent is a Logger::LogEventHandler: the same +=, -=, call and GetSubscriberCount() as an EventHandler, each taken under the Logger's lock PR #37. logEvent += handler returns an id; logEvent -= id removes it. Both are safe during dispatch and from any thread: a handler added during a log is first called on the next message; a handler removed during a log (even itself) is not called again. Subscribing does not flush the backlog; the next Log call does.

N2Engine::Logger::broadcastUnbroadcastLogs = true; // keep early messages until the UI subscribes
// ...
const size_t id = N2Engine::Logger::logEvent += [](std::string_view msg, N2Engine::Logger::LogLevel level)
{
    myConsole.Append(level, std::string(msg)); // copy: the view is only valid during the call
};
// ...
N2Engine::Logger::logEvent -= id;

Logging from other threads PR #37

Logger::Log (and Info/Warn/Error), subscribing, unsubscribing and the debug console's redirected streams may be used from any thread. They share one recursive mutex:

  • Log holds it from the backlog check until the message (and any backlog) has been delivered, so a message reaches every subscriber whole, and messages from different threads are delivered one after another, never interleaved.
  • Subscribers run on the thread that logged, while it holds the lock. A UI subscriber that must touch main-thread-only state should copy the message and queue it.
  • Being recursive, the lock lets a subscriber log (or write to a redirected std::cout) on its own thread: that message is delivered in place, as described above.
  • A subscriber must not wait for another thread that logs: that thread blocks on the lock, a deadlock.
  • The redirected streams take the same lock per character and keep one partial line per writing thread, so lines written to std::cout by two threads at once each reach the log whole. (The echo to the original stream, when enabled, is still per character.)
  • The mutex is never destroyed, so logging during static destruction still works. It is not async-signal-safe: a POSIX signal handler must not log (the editor host's handler only sets a flag).

Source: engine/src/Logger.cpp — LogMutex, Logger::Log, Logger::LogEventHandler, LoggerStreambuf::overflow, FlushLine, sync; editor-server/src/Host.cpp — SignalHandler; tests: CoreRobustnessTest.LoggerIsSafeToUseFromManyThreads, CoreRobustnessTest.LoggerDeliversBacklogOnceWhenASubscriberLogs

Design decision: deliver on the logging thread, under one lock

The alternative, queueing other threads' messages for the main thread to deliver, would keep subscribers single-threaded but lose messages logged just before a crash or during shutdown (when the main loop no longer drains), and would reorder them against main-thread messages. Logging is a diagnostic channel, so delivering immediately and in order matters more. One recursive lock keeps the existing re-entrancy rule (a subscriber may log) and makes subscription changes safe while another thread logs. The cost is that subscribers can be called on any thread, which is documented above; the engine's own console subscriber only writes to a stream.

Debug console and stream redirection

Logger::InitializeDebugConsoleHelper() is called by Application::Init only when N2ENGINE_DEBUG is defined. The engine target defines N2ENGINE_DEBUG=1 (PUBLIC) for the Debug configuration only, so Release builds have no console output unless the program subscribes itself. N2EditorHost does not subscribe a console, so a Release build of the host prints no logs at all; its editor server does subscribe, to keep every line for PollEvents PR #88.

The helper:

  1. Runs once per process; later calls return immediately. Before PR #24 a second Application::Init added a second console subscriber and every line was printed twice.
  2. Redirects std::cout to the Logger at Info and std::cerr at Error, without echoing to the original streams.
  3. Subscribes a handler that writes [LEVEL] message to the original stdout. Levels are coloured (Info blue, Warn yellow, Error red) when stdout is a terminal and, on Windows, virtual-terminal processing can be enabled; on other platforms when TERM is set and not dumb.

The original-stdout stream is allocated with new and never destroyed, because it is created after the Application singleton and would otherwise be destroyed first, crashing log calls made during later teardown.

Stream redirection can also be used directly: RedirectStdout, RedirectStderr and RedirectStream(stream, level, echo) install a StreamRedirector that turns each completed line (split on \n, \r dropped, empty lines skipped) into a log event. Redirectors are kept for the life of the process. Note that redirected lines are raised on logEvent directly and bypass the backlog queue.

The editor host process

editor-server/ builds two targets: the static library N2EditorServer (everything except Main.cpp, so linking it never pulls in a main) and the executable N2EditorHost. The host's whole body is Editor::RunHost, in the library PR #89: Main.cpp is one line, return N2Engine::Editor::RunHost(argc, argv);. See A game's own editor host. It also creates projects (--create, which exits without starting the engine) PR #90; see Creating a project.

OptionMeaning
-p, --port <port>TCP port to listen on (default 9999). Must be a whole decimal number, read with std::from_chars (which already rejects +, leading whitespace and hex) with no trailing characters; otherwise the host prints "Invalid port: ..." to stderr and exits with code 1 PR #33. The range is 0 to 65535: accepting 0 is new PR #84, and lets the OS pick a free port, which the ready line reports. A leading - is rejected explicitly, because from_chars reads -0 as 0 PR #84.
--bind <ipv4>Address to listen on (default 127.0.0.1) PR #33. Any other value logs a warning: without --token-env, that the server has no authentication; with it, that the access token isn't encrypted, so anything that can see the traffic can take it PR #89. An address that is not a valid IPv4 address makes Start fail. See why loopback is the default.
--project <path>The project to open: a folder holding a valid project.n2proj of this engine's major version PR #90. Otherwise the host prints one line to stderr ("Project folder not found or not a folder: ..." PR #84, "project.n2proj not found: ... (create one with N2EditorHost --create)", the file's validation error, or the engine version mismatch) and exits with code 1, before the engine starts. The host resolves the folder to its canonical absolute path, then initialises ResourceUUID with the project's projectId PR #90 and ResourceLoader with the folder and the project's own user:// folder, applies the project's settings, and opens its startup scene (or an empty one). See Opening a project and Project resources. It also sets the server's scenes directory to <path>/scenes, the only place the deprecated DeleteScene may delete files PR #33, and is stored in ApplicationOptions::projectPath (which Application::Init does not use). Without --project, there is no project, no project resources and no scene (as before), and DeleteScene is disabled.
--create <path> PR #90Makes <path> a project (IO::CreateProject), prints N2EditorHost created projectId=<uuid> startupScene=<res path> to stdout and exits, without starting the engine. Exit code 0 when created, 2 when the folder already has a project.n2proj (nothing is written), 1 for anything else. Can't be combined with --project; an empty value is "--create is missing a value". The exact contract is on Creating a project.
--name <name> PR #90With --create: the project's name (default: the folder's name). Without --create: "--name only goes with --create", exit code 1.
--project-id <uuid|from-path> PR #90With --create: the project's id, the namespace of its asset UUIDs (default: a new random UUID). from-path adopts the namespace the folder's assets had before projects had ids (ResourceUUID::NamespaceForProjectDir), keeping every UUID. Anything but a non-zero UUID or from-path is "Invalid --project-id: ...", exit code 1; without --create, "--project-id only goes with --create".
--renderer <opengl|software> PR #89The render backend. opengl (the default) opens a hidden GLFW window for its context, which fails on a machine without a GPU; the host then serves everything but RenderFrame (see Serving without a window). software runs the CPU renderer with no window at all (the no-window path), so RenderFrame works anywhere, the CI runner included. Exactly those two lowercase names; anything else is "Invalid renderer: <value> (expected opengl or software)" on stderr, exit code 1. Given twice, the last wins.
--token-env <variable> PR #89The name of an environment variable that holds the access token. The host reads it before the engine starts, removes it from its own environment, and gives the server the token (EditorServer::SetAccessToken), so every connection must send Hello with it before any other command. The token never appears on the command line (which other local processes can read) or in the log; the log says only which variable it came from. Unset, empty, or not a variable name (empty, or containing =): "--token-env: ..." on stderr, exit code 1. See why an environment variable.
--exit-on-disconnect PR #89Exit (code 0) once a client's session ends: its connection closes, for any reason, after a successful Hello (with --token-env) or after it connected (without). A connection that never authenticated can't make the host exit. An editor passes it to every host it launches, so a host never outlives an editor that crashed or was killed (#6, decision 2). See the design note.
--exit-on-stdin-eof PR #91Exit (code 0) once stdin reaches end of file or fails to read, including a stdin that is closed or absent (so the host exits at once). A launcher keeps the pipe it gave the child open for as long as it lives, and the operating system closes it when the launcher dies, even before any client has connected. Without the flag stdin is never read. See the design note.
-h, --helpPrint usage and exit 0. Help wins: if it appears anywhere, the host shows the usage and exits 0 even when other arguments are invalid PR #84.

--port, --bind, --project, --renderer, --token-env PR #89, --create, --name or --project-id PR #90 with no value is an error: "<option> is missing a value" on stderr, exit code 1 PR #84. A value that starts with -- counts as missing, so --project --port 0 is that error rather than a project folder called --port. Unknown arguments are ignored. The parsing lives in the N2EditorServer library (HostOptions.hpp: ParsePort, ParseRenderer, ParseHostArguments, ReadAccessToken, HostUsage (the help text) PR #89, FormatReadyLine, FormatCreatedLine PR #90), not in Main.cpp, so it is unit tested.

Startup and shutdown sequence, all in Editor::RunHost PR #89:

  1. With --help, print the usage and return 0. With --create, create the project and return (RunCreate; the engine never starts) PR #90. With --token-env, read the token and remove the variable (ReadAccessToken) PR #89; with --project, check the folder, read its project.n2proj and compare engine versions PR #90. Any of these failing prints to stderr and returns 1, before the engine starts.
  2. Install SIGINT/SIGTERM handlers (restoring the previous ones when RunHost returns PR #89) that only clear a g_running flag (the Logger is thread-safe, but logging is not async-signal-safe; see Logging from other threads).
  3. Construct the EditorServer (without starting it), which subscribes its event ring to the Logger, so every line from here on, Application::Init's included, is kept for PollEvents PR #88.
  4. Application::Init with PhysX, the --renderer backend (OpenGL unless --renderer software) PR #89 and isHeadless = true: with OpenGL a hidden window, with the software renderer no window at all (Window::UsesNoWindow) PR #89; audio on an OpenAL loopback device, streamed to the client through GetAudio PR #56, see Audio: loopback output.
  5. With --project: ResourceUUID::Initialize(projectId) PR #90, then ResourceLoader::Initialize(project, its user:// folder), which scans <project>/assets PR #84; apply the project's settings, give the server the project (SetProject) and open the startup scene, or an empty Untitled scene PR #90 (Opening a project). Without it, the host logs "No --project given: assets and asset references are unavailable".
  6. Give the server its access token (SetAccessToken, with --token-env) and, with --exit-on-disconnect, SetStopOnDisconnect(true) PR #89. Both must be set before Start.
  7. EditorServer::Start(port, bindAddress): bind to the bind address (loopback by default) PR #33, listen with a backlog of 1, start the network thread. SO_REUSEADDR is set on POSIX only, so a restarted host can rebind while the last connection is in TIME_WAIT; on Windows it is left off (there it would allow another process to take over the port, and the default already rebinds). On an invalid address or a socket/bind/listen failure, Start logs and returns false, and the host skips the loop and exits with code 1 PR #33.
  8. Once Start succeeds, print the ready line to stdout and flush it PR #84. A host that fails to start never prints it.
  9. Main loop, while g_running, the server is running (a Shutdown, or with --exit-on-disconnect the end of a session PR #89, stops it), no quit was requested, the window (if valid) is not closing (a windowless one never is PR #89), and, with --exit-on-stdin-eof PR #91, stdin has not closed: window.PollEvents(), then server.ProcessCommands(16 ms), which runs the queued editor requests and waits up to 16 ms for one to arrive (this replaces the old fixed 16 ms sleep). See Threading. Then server.UpdateAudio() mixes audio for the real time since the previous iteration, client or not, into a buffer capped at 250 ms PR #56.
  10. A last ProcessCommands() to flush log lines the network thread posted, server.Stop(), then OnApplicationQuit() on the current scene if any, then Application::Shutdown(). Stop() returns within about 100 ms even with an idle client connected PR #33: it clears the running flag, closes the command queue (waking a network thread that waits for a result), joins the thread, and only then closes the sockets.
  11. Exit 0; exit 1 if the server failed to start, or if a std::exception escaped (logged as "Fatal error: ...").

The server accepts one client at a time: the network thread accepts a connection, serves it until it disconnects or sends Shutdown, closes it, and goes back to accept. Start() may be called again after a client's Shutdown or after Stop(), on the same port, and the server listens again PR #33.

A game's own editor host: Editor::RunHost PR #89

The stock host knows the engine's built-in components and Lua scripts. A game with C++ components of its own (like test_project's Spin) builds its own host from the N2EditorServer library, which has everything N2EditorHost does:

#include <editor-server/Host.hpp>

int main(int argc, char *argv[])
{
    RegisterMyGameComponents(); // the game's own C++ components
    return N2Engine::Editor::RunHost(argc, argv);
}
  • int RunHost(int argc, char *argv[]) parses the arguments after the program name (ParseHostArguments), prints a parse error to stderr and returns 1, or returns RunHost(options).
  • int RunHost(const HostOptions &options) runs the whole sequence above and returns the exit code: 0, or 1 when the token, the project or the server can't be set up, or a std::exception escaped. With showHelp it only prints HostUsage(); with createPath it is RunCreate. A tool that builds HostOptions itself calls this one.
  • int RunCreate(const HostOptions &options) PR #90 is --create: IO::CreateProject, the created line, exit code 0, 2 or 1 (the contract).

It installs SIGINT/SIGTERM handlers and uses the Application singleton, so a process runs one host at a time. project.n2proj PR #90 doesn't name a host executable yet: a key such as "editorHost" is kept as an unknown key, and an editor launches whichever host it is configured with.

Design decision: the host is a library function, and a game builds its own host PR #89

The editor must be able to create a game's own C++ components, which only exist in that game's code. The two ways to get them into a host are loading the game as a plugin DLL at run time, or linking the game's code into a host executable of its own. A plugin ABI across MSVC builds is fragile (the runtime library, STL layouts and the engine's singletons would all have to match on both sides of the DLL), while the static library already exists. So the host's main moved, unchanged in behaviour, into Editor::RunHost, and a game's host is a main that registers its components and calls it. Taking argc/argv as well as HostOptions means a game's host accepts exactly the stock host's command line, so an editor launches either the same way. Decided on #6 (decision 18); #74.

The ready line PR #84

Once the server is listening, the host writes one line to stdout and flushes it:

N2EditorHost ready port=<port>

<port> is the bound port in decimal (EditorServer::GetPort()), which is the OS's pick when the host was started with --port 0. The socket is already listening when the line appears, so a launcher can connect straight away. The line is written once, after the engine's startup log lines, in the same stream (on Windows the line ends in \r\n).

How a launcher (the Electron main process, the CI smoke test) should read it:

  1. Read stdout line by line. Strip a trailing \r before matching: in .NET (and other engines), $ matches before a final \n but not before \r, so port=1234\r would not match. Consider only complete lines, and remember the ready line is often the last one: with no further output it can be the only line after the startup messages (as in a Release build, which writes no log lines to stdout).
  2. The ready line is the first line that starts with N2EditorHost ready . The rest of it is space-separated key=value fields. port is always present. Later versions may add fields (for example a protocol version), so ignore keys you don't know and don't depend on field order. A regular expression that does this for the port is ^N2EditorHost ready (?:.* )?port=(\d+)(?: |$).
  3. Every other line is a log line ([INFO] ..., [WARN] ..., [ERROR] ...) or other output; it never starts with N2EditorHost ready.
  4. If the process exits, or a timeout passes, before the ready line, startup failed; stderr and the log lines say why.

Design decision: a stdout ready line, not a fixed port PR #84

A launcher that picks a port itself races other processes for it. With --port 0 the OS assigns a free one, and the host has to report it, so the host prints it once the socket is listening. That also tells the launcher when to connect, which replaces the CI smoke test's connect-retry loop. stdout is used because the launcher already captures it. The line is written with C stdio (std::println(stdout, ...), then fflush), not std::cout: after Application::Init, std::cout is redirected into the Logger, which would add a level prefix. The Logger's console output goes to the same C stream, so ordering is kept: it writes to std::cout's original streambuf, saved before the redirection, and with the default sync_with_stdio(true) that streambuf writes straight through C stdio's stdout instead of keeping a buffer of its own. A piped stdout is fully buffered, so the flush is what makes the line arrive at once. The line is written on the main thread, and log lines from the network thread are posted to the main thread, so no log line can be written in the middle of it. The key=value form lets later versions add fields without breaking launchers that only read port.

Project resources PR #84

With --project <path>, after Application::Init (so their log lines reach the console) and before the server starts, the host runs PR #90:

// projectDir = std::filesystem::canonical(path), checked to be a directory;
// project = IO::ProjectFile::Load(projectDir), checked before Init
IO::ResourceUUID::Initialize(project.projectId);
IO::ResourceLoader::Instance().Initialize(projectDir, project.UserDataPath());

This is the same pair lua_project uses for a folder with a project file (see Resources and lua_project). Until PR #90 the namespace was ResourceUUID::NamespaceForProjectDir(projectDir) and user:// the shared folder; the project's projectId and its own user:// folder replace both (why). ResourceLoader::Initialize creates <path>/.import/, writes a .meta for each asset in <path>/assets, and from then on RescanAssets (0x41) picks up added files. Before this, the host never initialised either: RescanAssets only logged "Assets directory not found", and ResourceUUID::FromPath returned UUID::ZERO, so LoadScene could not resolve asset references in scene JSON.

Without --project, neither is initialised, as before: RescanAssets answers Ok but logs "Assets directory not found", and asset references don't resolve.

Design decision (superseded PR #90): one namespace, from the normalised project path, shared with lua_project, for now PR #84

Superseded by the project's projectId (Editor projects); NamespaceForProjectDir remains for --create --project-id from-path, which adopts it, and for lua_project on a folder without a project file. The original note: Asset UUIDs are derived from a project namespace and the asset's res:// path. The host and lua_project both get the namespace from ResourceUUID::NamespaceForProjectDir(projectDir), which hashes the folder spelled one way: weakly_canonical (absolute, . and .. resolved), forward slashes (generic_string), no trailing slash, and on Windows an upper-case drive letter. That is how CMake writes a source path (C:/...), so lua_project's default folder (N2_LUA_PROJECT_DIR) keeps the UUIDs it always had, and opening a folder in either tool gives the same UUIDs (a different namespace in each would rewrite every .meta on each switch). ./game, game\ and the absolute path agree. The drive letter is upper-cased because Windows paths are case-insensitive, and a relative path resolves against the current directory, whose drive letter may be lower-case. Moving or renaming the project folder still changes every asset UUID. This is temporary: the editor plan (#6, phase E3, #75) replaces it with a projectId in the project file, and --create --project-id <uuid> lets an existing project adopt the id that keeps these UUIDs. The folder must exist because ResourceLoader::Initialize would otherwise create it (for .import/), which would hide a mistyped path.

Wire format

Requests and responses use the same frame:

[type: uint8][length: uint32][payload: length bytes]
  • Request type is a CommandType, response type a ResponseType; each request gets exactly one response.
  • Integers and floats are written with memcpy in host byte order, which is little-endian on the supported (x86-64 Windows) targets. The CI smoke test relies on little-endian.
  • A string is [uint32 length][bytes] of UTF-8 with no terminator; the length counts bytes, not characters. A bool is one byte (0 or 1). A vec3 is three float32.
  • Error responses are the exception: their payload is the raw message bytes, not a length-prefixed string; the frame length is the message length. This stays, for compatibility, and every codec special-cases it.

The field types, as protocol.json's encoding.fieldTypes describes them PR #87:

TypeOn the wire
uint8, uint32, int32, float32, bool1, 4, 4, 4 and 1 bytes, little-endian.
stringuint32 byte count, then UTF-8.
json, json:<shape> PR #87Exactly a string: uint32 byte count, then UTF-8 JSON text. The shape is string, number, bool, json (any value), an entry of jsonTypes, or one of those followed by []. The server writes it compact (nlohmann's dump(), which sorts keys), but nothing depends on that: readers parse the text, so a client may write JSON with keys in any order and any spacing, and json fields are compared as parsed values, never as bytes.
bytesThe rest of the payload, no length prefix; only ever the last field.
vec3, quat PR #87Entries of types: 3 float32 (x, y, z) and 4 float32 (x, y, z, w).
mat4 PR #8716 float32, column-major: element col * 4 + row, for column vectors, so the translation is elements 12, 13 and 14.
<type> (EntityInfo, ...)An entry of types: its fields in order, no prefix.
<type>[]Elements back to back with no length prefix: their number is the uint32 field named count declared before the array (EntityList, EngineHealth).

No command uses quat or mat4 yet; the editor plan's camera, picking and transform commands (#6) will. Design decision: json is a string on the wire PR #87

The editor's tree and variant data (the hierarchy, component values of every kind, asset lists, events) would need a binary variant codec kept in step in three languages; the engine already has a tested JSON form of every value (Serialize()), and scene JSON already crosses the wire as a string. So json adds no wire format at all: it is a string whose text is JSON. A client or generator that doesn't know the type still reads it as a string, and only clients with codecs parse it. The :<shape> suffix and jsonTypes exist for the generated declarations (TypeScript interfaces, C# classes), not the wire. Hot paths (frames, audio, transforms) stay binary. Existing string fields that carry JSON (SceneData.sceneJson, LoadScene.sceneJson) stay string, so their TypeScript type doesn't change. Decided on #6 (decision 8); #72.

Design decision: quat is x, y, z, w and mat4 is column-major PR #87

Both layouts are chosen for the client, which does the viewport's camera and gizmo maths in TypeScript and hands matrices to the GPU. glTF, three.js and gl-matrix all order a quaternion x, y, z, w, and WebGL's uniformMatrix4fv and gl-matrix take column-major arrays, so a client uses the wire values as they are. The server's WriteQuat and WriteMat4 do the reordering and the transpose, once, in tested helpers. Versioning PR #87

protocol.json's version is now used: the server has it as ProtocolVersion (Protocol.hpp, pinned to the spec by ProtocolSpecTest.ProtocolVersionMatchesTheSpec), the TypeScript client as PROTOCOL_VERSION, the generated C++ header as ProtocolVersion and the C# one as ProtocolInfo.ProtocolVersion. A client sends its version in Hello, and the server answers with its own.

  • Minor bump: new commands, new responses, new trailing request fields and new trailing response fields.
  • Major bump: anything else (a changed id, field order or type, a removed field).
  • Both directions keep working within a major version PR #87. A newer client's trailing request field reaches an older server, which ignores request bytes it doesn't read (BufferReader doesn't check for trailing bytes). An older client doesn't send it to a newer server, so a server must read every trailing field added in a minor version only when the payload has bytes left, and default it otherwise: ReadTrailing(r, &BufferReader::ReadBool, true) (Commands.hpp) does that; reading it unconditionally would throw and answer Error. A newer server's trailing response field reaches an older client, whose generated decoders ignore bytes after the fields they know; a newer client relies on a response field added in a later minor version only once Hello has shown the server speaks that version.
  • Hello refuses a client of another major version. Same major, any minor or patch, is accepted: a client compares the server's version with its own to know which commands exist, and capabilities covers optional features the version doesn't imply. When the minor versions differ, the server logs the Hello as a warning PR #87, since commands only one side knows will fail with "Unknown command".

PR #87 made it 1.1.0: Hello, ServerInfo and the new field types add to 1.0.0 without changing anything a 1.0.0 client sends or reads. 1.2.0 adds PollEvents, its Events response and the EditorEvent shape PR #88, a minor bump for the same reason: a 1.1 client is unaffected, and a 1.2 client sends PollEvents only to a server whose Hello says 1.2 or later (an older one answers "Unknown command"). 1.3.0 PR #90 adds the scene-file commands (OpenScene, SaveSceneToFile, NewScene, GetOpenScene), the project commands (GetProjectInfo, SetProjectSettings, SetStartupScene), their responses SceneInfo and ProjectInfo, and the sceneChanged, assetsChanged and projectChanged events' optional keys in EditorEvent: again only additions.

Codecs and golden vectors PR #87

Three implementations encode the protocol: the server's hand-written C++, the generated TypeScript, and the golden-vector writer's Python. The golden vectors make them agree without running them together.

The TypeScript client (protocol.generated.ts) is framework-free (only Uint8Array, DataView, TextEncoder/TextDecoder), so it runs in Node, Electron and a browser. Besides PROTOCOL_VERSION, CommandType, ResponseType and an interface per message, type and JSON shape, it has:

  • encode<Command>Request(value) and decode<Command>Request(payload) for every command with request fields, and encode<Response>Response/decode<Response>Response for every response, including Ok ({}) and Error ({message}, the raw-bytes special case). Payloads exclude the 5-byte header. RequestCodecs and ResponseCodecs map names to them, and CommandResponse gives the response each command answers with.
  • json fields are parsed: their TypeScript type is the shape (json:string[] is string[]; plain json is unknown), encoded with JSON.stringify.
  • ProtocolWriter and ProtocolReader (exported, with write<Type>/read<Type> for each struct). Reading past the end throws RangeError, as the server's BufferReader throws. Writing a non-integer or out-of-range number to an integer field throws RangeError rather than wrapping. Decoders accept any Uint8Array view, Node Buffer slices included, and a bytes field is a view into the payload, not a copy.
  • For an array, the encoder writes the array's real length as count, whatever count says; the decoder returns both.
  • encodeFrame, decodeFrame (the first complete frame in a buffer, or null), parseProtocolVersion and isProtocolCompatible.
  • Views, not copies: decodeFrame's payload and a decoded bytes field (frame pixels, audio samples) point into the buffer they came from, so a client that reuses or grows its receive buffer, or sends the value over Electron IPC (where a view serialises its whole underlying buffer), copies it first with slice() PR #87.

Only erasable TypeScript syntax is generated (no enums, namespaces or parameter properties), so Node runs the file with --experimental-strip-types and the protocol's tests need no npm packages. It type-checks under strict plus noUnusedLocals, noUnusedParameters, noUncheckedIndexedAccess and exactOptionalPropertyTypes.

Sessions: Hello and the access token PR #87

Hello (0x04) opens a session. The request is clientName, protocolVersion (the client's PROTOCOL_VERSION) and token (the host's access token, or empty); the response, ServerInfo (0x0B), is protocolVersion (the server's), engineVersion (CMake's project version, EditorServer::EngineVersion), capabilities (json:string[]: optional features beyond what the version implies; none are defined yet, so []) and projectLoaded (the server has a project: the host was started with --project and opened it, EditorServer::HasProject; before PR #90 it meant that ResourceLoader had a project root).

The server checks, in order:

  1. The token, if the server has an access token: anything but an exact match is Error "Invalid access token". The comparison takes the same time whichever byte differs (EditorServer::TokensMatch). Checked first, so a client without the token learns nothing else.
  2. The version: not major.minor.patch (ParseProtocolVersion: digits only, at most 10 a part, leading zeros included, which from_chars alone would allow without limit PR #87; no signs, spaces or suffixes) is Error "Invalid protocol version '...' (expected major.minor.patch; this server speaks 1.3.0)"; another major version is Error "Protocol version mismatch: this server speaks 1.3.0, the client ... (the major versions must match)".
  3. Otherwise it answers ServerInfo, and logs "Editor client '<name>' said Hello (protocol ...)", as a warning when the minor versions differ.

The client's name and version reach the log and the Error only through EditorServer::SanitizeForLog PR #87: control characters (newlines included) become ?, and the text is cut at a UTF-8 character boundary (100 bytes for the name, 40 for the version) with "..." appended. So a version of 60 MB of zeros is neither echoed nor logged. The token is never logged.

The access token. EditorServer::SetAccessToken(token), called before Start (while running it logs a warning and returns false), gives the server one. Then, on each connection, until a Hello on it succeeds, the network thread answers every command except Hello, Shutdown included, with Error "Not authorized: this host requires Hello with its access token before any other command" (EditorServer::HelloRequiredError), without queueing it for the main thread. The server serves one connection at a time, so a connection that hasn't succeeded a Hello must not be able to keep it PR #87:

  • after that Error, the connection is closed, and so is it after a Hello that fails (wrong token or version), once its Error is sent;
  • a connection on which no Hello has succeeded within the Hello timeout of accepting it (5 s, EditorServer::DefaultHelloTimeout; SetHelloTimeout before Start) is closed, whether it sent nothing, part of a frame, or a frame that was refused;
  • before a successful Hello, a payload over 64 KiB (MaxPayloadBytesBeforeHello, far more than a Hello needs) is refused, and the connection closed, as one over 64 MiB always is, so an unauthorised client can't make the server allocate much.

Each close is logged as a warning ("Closing an editor connection that hasn't sent a successful Hello: ..."), and the server goes back to accept, free for the editor. Once a Hello has succeeded, none of these limits apply to the connection. Without an access token, none of this applies: connections are never closed for a missing or failed Hello, and there is no timeout. Without an access token (the default), Hello is optional, any token is accepted, and every command works as before, so existing clients are unaffected. N2EditorHost gets a token with --token-env <variable> PR #89, which reads it from an environment variable so it never appears on a command line (see the host's options).

Design decision: the token comes from an environment variable the host then removes PR #89

The launcher makes a random token and has to hand it to the host it starts. A command-line argument is the obvious way, but any local process can read another process's command line (Task Manager, wmic process, /proc/<pid>/cmdline), and the token exists to keep exactly those processes out. A process's environment is readable only by its own user (and administrators), and it is inherited by the child the launcher spawns, which Electron's spawn (env) and .NET's Process both support directly. So the command line carries only the variable's name. The host reads the variable before the engine (and with it Lua) starts, then removes it from its own environment, so nothing the host later runs or starts inherits it. A variable that is unset or empty is an error rather than "no token": a launcher that asked for a token must not get a host that silently accepts anyone. Decided on #6 (the proposal's launch command line); #74.

A session is the connection. Its state is one flag in the network thread's HandleClient: whether the connection's last Hello answered ServerInfo. A new connection starts without one, so a client that reconnects sends Hello again; a later Hello that fails ends the session. Nothing about a session outlives its connection.

Design decision: the session lives on the network thread, per connection PR #87

Commands run on the main thread, but which connection a command came from is only known on the network thread, which reads it, and the server serves one connection at a time from one loop. Design decision: an optional token, enforced only when the host has one PR #87

The token closes the "any local process can drive the host" gap for hosts an editor launches: the editor makes a random token and passes it to the host it starts, so another process on the machine can connect but can't do anything. A host started by hand (or by the CI smoke test, or an older client) has no token and works as before, so Hello is optional there and accepts any token rather than refusing a client that sends one. The token is checked before the version so a client without it can't even learn the protocol version, compared in constant time so the response time doesn't leak a prefix, and never logged. Enforcement is in the server now; how the host gets the token (--token-env) belongs with the launch flags in E2 (#74). A token alone isn't enough when connections are served one at a time: a process that connects and then says nothing, or keeps guessing, would hold the only slot, and the editor couldn't connect. So with a token a connection gets one chance (a refused command or Hello closes it) and a few seconds (the Hello timeout); generous enough for a real client, which sends Hello first, and short enough that the editor waits at most that long behind an intruder PR #87. Without a token, nothing is authenticated anyway, so closing connections would protect nothing and could only break existing clients. It is not encryption: on loopback there is no one in between to read it, and a remote host would need TLS as well (a later item in #6). Decided on #6 (decision 8); #72.

Events: PollEvents and the log ring PR #88

The server keeps an event ring (EventRing, editor-server/include/editor-server/EventRing.hpp) that a client reads with PollEvents (0x05). Its events are the host's log lines and, since PR #90, scene, asset and project changes; later phases of #6 add history and play-state events to the same ring. There is no server push: the client asks, about every 100 ms. Part of #6, phase E1b (#73).

The request is epoch (uint32: the epoch of the client's last response, 0 when it has none), afterSeq (uint32: the last seq the client has seen, 0 for everything the server still has) and maxEvents (uint32). The response, Events (0x0C), is epoch (uint32), nextSeq (uint32), dropped (uint32) and events (json:EditorEvent[], oldest first):

  • seq and epoch. Every event gets the next seq, starting at 1 and consecutive within an epoch: a random non-zero uint32 the server picks when it is constructed, so each host process has its own (and a new one when seqs run out, below). events holds those with a seq after afterSeq, at most maxEvents of them and never more than 1024 (EventRing::MaxEventsPerRead) in one response.
  • nextSeq is the afterSeq for the next poll, and the response's epoch its epoch: nextSeq is the last returned event's seq, or, when none is returned, the newest seq of the epoch (0 before any event). When there were more than it asked for, the client gets the rest on the next poll.
  • The rule. afterSeq counts within the epoch the request names. When that epoch is not 0 and isn't the server's, or afterSeq is newer than any seq of the server's epoch, the server reads afterSeq as 0. So a client polls with epoch 0 and afterSeq 0 first, then with each response's epoch and nextSeq, across reconnects too: to the same host it misses nothing still retained and gets nothing twice; to a restarted host (a new epoch) it gets that host's events from the start, and should treat that as a new log.
  • maxEvents 0 returns no events and nextSeq = the newest seq, so a client that doesn't want the backlog starts from there.
  • dropped counts the events after afterSeq that fell off the ring before this poll: the client never saw them, as GetAudio's droppedFrames counts audio it never got. It is computed from afterSeq (seqs are consecutive, so the oldest retained seq says how many are missing), so the server keeps nothing per client.
  • Bounds. The ring keeps the newest 4096 events (EventRing::DefaultMaxEvents) and about 2 MiB of them (DefaultMaxBytes: a log event costs its message's bytes plus 64), dropping the oldest beyond either. The newest event is always kept. A log message over 16 KiB (MaxLogMessageBytes) is cut at a UTF-8 character boundary and ends in "...". The byte count is an estimate (the text plus 64), not the JSON's size: escaping (a control character becomes six bytes) can make the JSON larger.
  • Seqs running out. Seqs are uint32 (at 1000 events a second they would last 49 days). The ring counts in 64 bits, and when the next seq would pass 4294967295 (EventRing::MaxSeq) it empties, starts again at 1 and picks a new epoch, so every client resyncs by the rule above. The events it held are lost, and counted in DroppedTotal but not in any response's dropped.

Push can still come later behind a Hello capability: ids 0xC0 to 0xFE stay reserved for it. Decided on #6 (decision 10); #73.

Design decision: the client holds its place, as an epoch and a seq PR #88

The server serves one connection at a time, but a client reconnects, and the play-mode child of #6 will have a second one: per-client cursors would need to know which client is which and when to forget one. With consecutive seqs the client's own afterSeq is its cursor, the server keeps nothing per client, and dropped follows from it (the oldest retained seq minus afterSeq, minus one), so two clients, or one that reconnects, each get their own correct count. A seq alone can't say which host it came from: seqs restart with the host, so a client reconnecting to a restarted host could hold an afterSeq the new host has already passed, and would silently skip that many of its events. The epoch, random per host process, names the numbering: an afterSeq from another epoch is read as 0, so the client gets the new host's events from the start, and one from the same epoch continues exactly where it was, with nothing lost or repeated. Random rather than a counter or a start time, so two hosts started together (or a host restarted within the clock's resolution) still differ, and not 0, which a client sends when it has no epoch yet. The same mechanism covers seqs running out: the ring starts a new epoch rather than wrapping, so no reader ever sees seqs go backwards within an epoch. A client that sends epoch 0 with a seq the server hasn't reached (one that ignores epochs) gets the backlog too. The epoch is new in 1.2.0, which had not been released, so the fields were added in place. Proposed in #6 §(c); #73.

Design decision: bounded by count and by bytes, newest kept PR #88

A script that logs every frame, or a stack of errors from a broken scene, must not grow the host's memory without bound while no client polls. 4096 events covers a long startup and minutes of normal logging, and the 2 MiB budget keeps a run of huge messages from holding much more than that; the 16 KiB cut keeps one message from taking the whole budget. The oldest go first because the newest are the ones an editor shows, and the newest event is always kept so a poll always sees the latest state. Since one read never returns more than the ring holds, a response's size is capped by the 2 MiB budget plus the one newest event the ring always keeps (at most 16 KiB of message), give or take JSON escaping, which the byte estimate doesn't count. The 1024-event cap bounds the work of one poll after a long gap; the next poll gets the rest. maxEvents 0 meaning "skip to the newest" gives a client that only wants live events a way to start without reading the backlog. Proposed in #6 §(c) ("for example 4096 events or 2 MiB"); #73.

Design decision: the server subscribes when constructed, and the host constructs it before Init PR #88

#6 proposed subscribing at Start and setting broadcastUnbroadcastLogs so the Logger keeps the startup lines until then. That keeps them only while nothing is subscribed: in a Debug build Application::Init subscribes the console, and the next line hands the backlog to the console alone, so the ring would miss everything between Init and Start, the resource scan's errors included. Subscribing in the constructor, and having the host construct the server first, gets every line in both builds without changing the Logger. It also means PollEvents works without Start, so tests drive it through ExecuteCommand with no socket. The host doesn't set broadcastUnbroadcastLogs: with the server subscribed from the start it would keep nothing, and it would do harm once the server is destroyed at the end of RunHost: with no subscriber left (a Release build has no console), every later line, "Fatal error" included, would be queued for good instead of dropped. Every EditorServer keeps a ring, which costs nothing until something logs. Decided for #73; refines #6 §(c).

Design decision: serving PollEvents logs nothing PR #88

The ring takes every line logged in the process, so anything PollEvents logged would be an event the next poll returns, and a client polling every 100 ms would never see an empty poll: ten lines a second about polling, burying the lines worth reading. Rather than filter the server's own lines out of the ring (which would also hide useful ones, such as "Editor connected" or a refused Hello), the command doesn't log: it is in IsPolledCommand (the PR #83 rule, which #6 planned for it), and neither its handler nor the ring logs anything, which the ring must not do anyway since it runs inside the Logger's dispatch. A failed PollEvents is still logged, as every polled command's failure is: it is an error worth seeing, and a client doesn't keep sending a malformed request. Decided on #6 (decision E); #73.

Design decision: one flat event shape, kind plus optional fields PR #88

jsonTypes describes objects, not unions, so the event kinds of #6 (log, sceneChanged, assetsChanged, historyChanged, playState, projectChanged) can't each be their own shape inside one array. EditorEvent is one object with seq and kind required and every kind's fields optional, so a client switches on kind and reads the fields that kind has. Adding a kind adds optional keys, a minor version change; an older client skips kinds it doesn't know. Nesting each kind's fields under a key of its own ({"seq", "kind", "log": {...}}) would have kept the kinds' fields apart, but added a level to every event for no gain while one kind exists, and the field names of the planned kinds don't collide. time is Unix milliseconds, a plain number every language reads, rather than a formatted string. Decided for #73.

Threading: commands run on the main thread

Every command that touches engine state runs on the host's main thread PR #33. The server has two sides:

  • Network thread. Accepts the client, reads each frame (header, size check, payload) and enqueues ExecuteCommand(type, payload) as a std::packaged_task on a CommandQueue. It then blocks on the task's future and sends the response frame it gets back. It never touches scenes, Lua, GLFW/GL or the Logger; its own log lines are posted to the main thread as queued tasks (PostLog). Every socket call waits in 100 ms select() slices and checks the running flag, so the thread never blocks forever and no socket is closed from another thread.
  • Main thread. The host loop calls server.ProcessCommands(16 ms) after PollEvents. It runs everything queued, in order, outside the queue's lock. Handlers, RenderFrame (GL and GLFW calls), LoadScene's scene switch and all logging happen here.

Two things are answered on the network thread without queueing, because neither touches the engine: Shutdown, and the Error for an oversized payload. Closing the queue (Stop()) drops pending work and breaks its futures, which wakes a network thread waiting for a result; that thread then drops the connection.

A response is built in full before it is sent, so a request is answered only after the main loop has drained it. A host that never calls ProcessCommands leaves every client waiting.

Viewport frames PR #85

FrameData.pixels has one layout whatever renders it: width × height pixels of 4 bytes, R, G, B, A, the top row first, left to right, with A always 255. width × height is the viewport size from SetViewportSize (1280 × 720 until it is called), and the frame is rendered at that size, so the pixels are neither a crop nor a resample. The wire format did not change (the same bytes field, to the end of the payload); only what the bytes mean is now fixed. Fixes #69, part of #6 (decision 15, phase E0).

  • Size. SetViewportSize calls Window::SetRenderSize(width, height), which calls IRenderer::SetRenderTargetSize and the camera's aspect update. OpenGL then renders every frame into an offscreen framebuffer of that size (RGBA8 colour, D24S8 depth and stencil) instead of the hidden window; the software renderer resizes its CPU colour buffer. From then on the window's own resizes no longer reach the renderer or the camera, and the UI pass, UI hit testing, world picking and Lua's default Camera:ScreenPointToRay viewport all use the render size (Window::GetRenderDimensions) rather than the window's PR #85. RenderFrame applies the size too, so the default 1280 × 720 is rendered at that size before any SetViewportSize.
  • Units. The viewport size is in the client's pixels, and the frame has exactly that many. A client should send its viewport in device pixels (CSS size × devicePixelRatio in Electron) so the frame is drawn 1:1 and sharp. Screen-space UI is laid out in those pixels too, so on a high-DPI client it looks smaller than in a game window of the same CSS size. Lua's Window.GetDimensions is still the hidden window's size, not the viewport.
  • Failure. If the renderer can't make a target of the size (IRenderer::SetRenderTargetSize returns false: OpenGL's framebuffer is incomplete), SetViewportSize and RenderFrame answer Error "Couldn't create a WxH render target" PR #85. The size is kept and no render size is stored, so each RenderFrame tries again rather than sending a frame of the wrong size.
  • Layout. EditorServer::ReadFrame reads the frame with IRenderer::ReadFramebuffer, which gives RGBA with the bottom row first on every backend (OpenGL now reads GL_RGBA, not GL_BGRA), reverses the rows with Renderer::Common::FlipRows and sets every alpha to 255.
  • Clients. The Electron editor (N2Engine-Electron-Frontend) already draws the bytes as RGBA with the top row first, so its viewport is now upright and in the right colours on both backends with no client change. Before, OpenGL frames showed upside down with red and blue swapped, and software frames upside down.

Design decision: frames are RGBA, top row first, normalised on the server PR #85

Every client would otherwise have to know which backend rendered a frame, and FrameData has no format field to tell it. Top row first with RGBA is what images, canvases (ImageData) and the existing Electron client expect, so the server converts once and no client converts at all. The work is split where each part belongs: backends agree on one readback contract (RGBA, bottom row first, as glReadPixels gives; OpenGL only had to ask for GL_RGBA), which leaves the renderer tests' bottom-up frames unchanged, and the editor server does the flip with a small tested helper, FlipRows, rather than every backend learning about the protocol. Alpha is forced to 255 because the viewport is opaque: blended draws leave partial alpha in the target, which a client drawing the bytes as an image would show as see-through. Decided on #6 (decision 15); #69.

Design decision: the renderer renders at the viewport size; OpenGL uses an offscreen framebuffer PR #85

Reading a viewport-sized region of a differently sized frame gives a crop (or undefined pixels past its edge), and resampling it blurs or blocks the image, so the frame has to be rendered at the viewport size. For OpenGL, resizing the hidden window would be the smallest change, but a window's size is limited by the desktop and the OS, its framebuffer can differ from its size on HiDPI displays, a hidden window's pixels aren't guaranteed to be kept, and reading its back buffer after Present swapped it gives undefined contents. An offscreen framebuffer has exactly the requested size, is read the same way, and leaves the window alone. The software renderer's frame is already offscreen, so it only resizes its buffer. Once a host sets a render size, window resizes stop reaching the renderer and camera, since a later resize of the hidden window would otherwise undo it. Decided on #6 (decision 15); #69.

DeleteScene rules

DeleteScene takes a scene name, not a path PR #33. EditorServer::ResolveSceneFile turns it into a file inside the scenes directory (<project>/scenes, from --project) or rejects it:

  • .json is appended unless the name already ends with it, in any case. So "Level.1" names Level.1.json, and "notes.txt" names notes.txt.json: no other extension can be reached.
  • Rejected: an empty name, a NUL character, absolute paths, drive-relative and rooted paths (C:x, \x), UNC and \\?\ paths, and names that end in a directory (dir/, ., ..).
  • The parent directory is canonicalised (symlinks and .. resolved) and must be the scenes directory or a directory inside it. Subdirectories are allowed; .. escapes are not.
  • The file name itself is not resolved, so a symlinked scene file deletes the link, never its target.
  • Only a regular file is removed. The file of the currently loaded scene (same stem as its sceneName) is refused, as SceneManager::DeleteScene refuses to delete the loaded scene.
  • Without --project there is no scenes directory and every DeleteScene is an Error.

Before PR #33 the request string went straight to std::filesystem::remove, so any client could delete any file the host could write. protocol.json already named the field sceneName; the server now matches it. Checking and then removing is not atomic; exploiting that needs local write access to scenes/, which is accepted for a dev tool.

Serving without a window, and quitting

The host keeps serving when the window or renderer failed (for example on a machine without a GPU). It logs "No window or renderer; rendering commands will be unavailable" and loops on its other conditions only. Everything except RenderFrame works; clients should call GetEngineHealth to find out what is available. This is the CI configuration of the default renderer (see CI).

With --renderer software PR #89 there is no window to fail: the software renderer runs headless with no window at all (the no-window path), so RenderFrame works on any machine, and the host logs "Rendering with the software renderer, without a window". GetEngineHealth then reports the window Disabled ("No window: the headless software renderer draws offscreen") and the renderer Running ("Software (headless)"), which is healthy. The CI smoke test renders a frame this way.

Exit on disconnect PR #89. With --exit-on-disconnect, the server stops once a client's session ends, as if it had sent Shutdown, and the host exits with code 0. A session is the connection: without an access token every connection has one; with a token, a connection has one from its first successful Hello. So connections that never authenticate (refused, timed out, or just closed) can't stop the host, but the editor's own connection closing, whether it quit, crashed or was killed, does. The server logs "Stopping the editor server: the client's session ended, and it stops on disconnect".

Design decision: an editor-launched host exits when its session ends PR #89

An editor that crashes or is killed can't shut down the hosts it started, and an orphaned host keeps its port, its project's files and (for a play-mode child) a running game. The host can't tell a crash from a quit, but it does see its connection close, and an editor holds its connection for as long as it uses the host, so the end of the session is the signal to go. Only a session counts: with a token, a local process that connects without it would otherwise be able to stop the host just by connecting and leaving, which the token exists to prevent. Without a token, anyone can already send Shutdown, so counting every connection adds nothing new. It is opt-in, because a host started by hand serves one client after another. It reuses the path a Shutdown takes (the network thread clears the running flag, the main loop sees !IsRunning()), so the shutdown that follows is the same, including OnApplicationQuit. Not covered: a launcher that dies before it ever connects; the editor's main process kills its host on quit, and --exit-on-stdin-eof PR #91 covers a launcher that dies first. Decided on #6 (decision 2: editor-launched hosts always get --exit-on-disconnect); #74.

Exit on stdin EOF PR #91. With --exit-on-stdin-eof, RunHost starts a watcher (StartStdinEofWatcher) just before the main loop. It is a detached thread that reads stdin with a raw ReadFile (Windows) or read(0) (elsewhere), discarding what it gets, and at end of file or on any read error (a broken pipe, a closed or missing stdin handle) sets an atomic flag. The main loop checks the flag each iteration and leaves through the same shutdown as a signal or Shutdown: it logs "Stdin closed", stops the server, runs OnApplicationQuit, shuts the engine down and exits with code 0. Without the flag nothing reads stdin, so a console, a closed handle or a pipe at end of file has no effect. The thread is detached because a read on a pipe that stays open can't be interrupted; it holds only a shared pointer to the flag, so it is harmless once the host has returned, and it ends with the process. It bypasses the C runtime's stdin so that process exit never waits on that stream's lock. The watcher starts once per process (a function-local static): the flag hands stdin to the host for the life of the process, the bytes it reads are discarded, and a second RunHost in the same process shares the first watcher and its flag. On Windows a pipe's end of file is the failed read (broken pipe), so a successful read of zero bytes from a pipe is read again rather than taken as the end. Give the host a pipe or a file as stdin, not a terminal: a POSIX background process reading its terminal is stopped by SIGTTIN, and a Windows console discards the lines typed into it (Ctrl+Z then Enter is its end of file, and exits the host).

Design decision: stdin EOF is an opt-in flag, not the default PR #91

--exit-on-disconnect can't help when the launcher dies before its client has connected and said Hello; the host then waits forever for a session that will never start. The launcher's stdin pipe to the child does close in that case, which makes it a reliable signal. Two ways to use it were considered: always exit on stdin EOF unless told otherwise (leaning on --token-env, which already marks a launched host), or an explicit flag. The flag was chosen: a launcher that closes the child's stdin on purpose, a service or script that starts the host with no stdin, or a host run from a shell with input redirected from an empty file would otherwise find the host gone the moment it started, with nothing in the arguments to explain why. Tying the behaviour to --token-env would have made one option mean two things, and a token is useful on a host that is not a child of anything. A launcher that wants orphan protection (the Electron editor keeps its child's stdin pipe open) passes the flag, and everyone else sees no change. Decided on #6.

Security and remaining gaps

Warning

Without --token-env, N2EditorHost has no authentication. Since PR #33 the host listens on 127.0.0.1 only, so other machines cannot reach it unless you pass --bind. But any process on the same machine can still connect and send any command. It can load arbitrary scene JSON, including LuaComponents whose scripts then run in the host (inside the Lua sandbox); read the viewport; delete .json files under <project>/scenes; and write .scene files under <project>/assets and the project's project.n2proj PR #90 (never anywhere else: scene paths are checked to stay inside the assets folder). Do not pass --bind with a non-loopback address on a network you do not trust: whoever can reach the port gets the same control. The server supports an access token (EditorServer::SetAccessToken, enforced through Hello) PR #87, and the host takes one with --token-env PR #89; an editor that launches a host should always give it one. The token isn't encrypted, so it protects a loopback host, not one reachable over a network.

Design decision: a loopback-only editor server

N2EditorHost is a development tool that an editor on the same machine drives. Without a token the protocol carries no credentials, so the only safe default is to be unreachable from other machines: the server binds to 127.0.0.1, and listening anywhere else takes an explicit --bind that logs a warning. Authentication was first left out because it would change the wire format for every client; the optional token PR #87 adds it as a new command (Hello), a minor version bump that leaves clients of hosts without a token unchanged (see why it is optional). For the same reason the server limits what a command can do: DeleteScene only ever deletes .json files inside the project's scenes directory, and malformed input gets an Error instead of crashing the host.

Commands run on the main thread for a separate reason: engine state is single-threaded. Scenes, Lua and GLFW/OpenGL (a context is current on one thread, and GLFW event polling must be on the main thread) have no locks; only the Logger is thread-safe (see Logging from other threads). Queueing commands for the main loop makes every handler behave like ordinary game code between frames, instead of adding locks across the engine. Lua handles rely on the same assumption (see why Lua handles stay valid).

Note: server structs match the spec PR #39

The server's hand-written request types follow protocol.json: one <Command>Cmd deserializer per command that has a request, with the spec's field names, as in the generated clients/cpp/Protocol.generated.hpp. LoadSceneCmd carries sceneJson (it had an unused path), SetEntityTransformCmd is the former EntityTransformCmd, DestroyEntityCmd and GetEntityTransformCmd are used by their handlers, and the request-less SaveScene has no struct. The unused EntityTransformRequest (with an int32 entity id; entity ids are UUID strings) is gone from Protocol.hpp. The wire format did not change, and protocol.json and the three generated clients already agreed with the server, so regenerating them changes nothing. ProtocolSpecTest checks Protocol.hpp's command and response ids against protocol.json, and, for every command with request fields, that a payload built from the spec's field list (in order, by type) is exactly what the server's deserializer reads. Field names are not on the wire, so they are kept in step by review. A bytes field (FrameData.pixels) is the rest of the payload, with no length prefix. Since PR #87 response layouts are checked too, and both directions byte for byte against the golden vectors.
