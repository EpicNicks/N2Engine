Build targets

n2build builds a game for a target (Windows, Linux or the web so far) and packages it, from a project folder, with one command. The final game is always a full build from source: the target's player is compiled with the project's module list, then packaged with the game's data. The editor will call the same tool. This is stage 1 of the build targets plan PR #328.

Using n2build

n2build is a node script with no packages to install (node 22 or newer). Run it from anywhere:

node tools/n2build/n2build.mjs list                                   # the targets, and which build on this machine
node tools/n2build/n2build.mjs doctor --target web                    # what the target needs, and what is missing
node tools/n2build/n2build.mjs build  --target windows --project path/to/game --archive zip
node tools/n2build/n2build.mjs run    --target web --project path/to/game   # build, then serve on http://127.0.0.1:8080/
OptionCommandsMeaning
--target NAMEdoctor, build, runA target from list
--project DIRbuild, run (doctor: optional)The game: a folder with project.n2proj and assets/. With doctor, also runs the physics check
--config debug|releasebuild, runDefault release. On the web, debug is the dev profile and release the size profile (Web build)
--out DIRbuild, runThe package folder. Default: <project>/.n2/out/<target>-<config>/<game name>
--build-dir DIRbuild, runWhere build trees go. Default: <project>/.n2/build
--archive zip|7zbuildAlso writes <package>.zip or .7z beside the package folder, with CMake's own archiver
--jobs Nbuild, runParallel compile jobs. Default: the machine's processor count
--dry-runbuildPrints the build tree, the CMake commands and the package folder, and runs nothing
--no-buildrunRuns the package already built
--frames NrunDesktop: the player quits after N frames. Web: runs the package under node for N frames (scripts/web-package-smoke.mjs) instead of serving it
--port Nrun (web)The local server's port. Default 8080; 0 picks a free one
--jsonallOne JSON event per line on stdout (JSON output)
--targets-dir DIRallAnother folder of target descriptors; can be repeated

Exit codes: 0 done, 1 a check or the build failed (the last line says why), 2 wrong usage.

  1. Checks, before anything compiles: the project file and its module list, the physics check, and the target's toolchains (the same report as doctor). A missing required tool stops here with how to fix it. A missing optional one (the Vulkan SDK) is a warning, and the build leaves that part out.
  2. Configure the build tree with CMake, only when the tree is new or its arguments changed. -DN2ENGINE_PROJECT is the project, so its module list applies (Project modules).
  3. Compile the target's CMake target. Ninja rebuilds only what changed.
  4. Package into the package folder, then write the archive when asked.

Source: tools/n2build/n2build.mjs, tools/n2build/lib/; tests: tools/n2build/n2build.test.mjs

Design decision: the final game is always a full build from source

Decided by the user on 2026-11-10 (D3 of orchestrator/proposals/build-targets-design.md). While a game is being made it runs in the editor's play mode, on the machine running the editor. A shipped build compiles the player with the game's module list, so a stripped engine is the normal case, not a special one. Prebuilt players (one compiled per engine version, plus the game's data) may come later as a fast option for test builds, never as a replacement. The cost is that every target's compiler must be on the building machine, which doctor checks.

The Vulkan renderer is built when the Vulkan SDK is found and left out otherwise; the software and OpenGL renderers are always in a desktop build.

Build trees and packages

A build tree is kept per target, configuration, module list and project: <project>/.n2/build/<target>-<config>-<hash>, where the hash covers the project's path, its module list and the CMake options. So a build after a script or asset edit only re-packages, a build after an engine update recompiles what changed, and switching a module list never rebuilds the other trees. .n2/ is the editor's per-machine folder, which a new project's .gitignore already leaves out (Editor projects).

<game>/                    a desktop package
  <game>.exe               n2player, named after the game (no .exe on Linux)
  OpenAL32.dll             and any other file players/desktop lists in n2player-files.txt
  game/
    project.n2proj
    assets/
    .import/               when the project has one: the stored asset UUIDs and import settings
  .n2build-package.json    what was built: target, configuration, game, engine commit, time (no local paths:
                           a web package is uploaded with it)

Guarantee: n2build only replaces a folder it made

A package folder is emptied before it is written only when it is empty or holds .n2build-package.json. Any other folder is refused, so a mistyped --out cannot delete files. Test: a package folder is only ever emptied when n2build made it.

The desktop player

players/desktop builds n2player, the program a desktop package ships. lua_project stays a demo project with its own executable; the player takes what it solved (decision D4).

n2player [game folder] [--renderer opengl|vulkan|software] [--console-log] [--frames N] [--help]
  • The game folder defaults to game/ beside the executable (found from the executable's own path, not the working directory). A folder without project.n2proj is refused with the reason and the usage.
  • Start: the project's startupScene (a .scene file) when it names one, else assets/scene.lua in an empty scene named after the game, as lua_project and the web player start.
  • The project is opened as the editor host opens it: its projectId is the asset UUID namespace, user:// is its own folder, and its settings apply (physics.backend among them; the player itself asks for no backend).
  • The window's title is the game's name; a Debug build adds the renderer.
  • Windows: a Release player is a windowed program, with no console window behind the game. --console-log still prints the log when it is started from a console or by n2build run. Debug keeps the console.
  • --frames N runs N frames through Application::BeginRun/RunFrame/EndRun and quits, for smoke runs.

Source: players/desktop/src/Main.cpp, players/desktop/src/PlayerOptions.cpp; tests: tests/players/PlayerOptionsTests.cpp

The physics check per target

A target lists the 3D physics values it can build (physics3d in its descriptor). A project whose build.modules.physics3d asks for one the target cannot build fails before configuring, with the target's list. A project without a list gets every backend the target has. Today all three targets build PhysX; the check matters for the mobile targets, which will build Jolt and Box2D only (decision D8). Test: build refuses a project whose physics the target cannot build, before compiling anything.

Per-target settings in the project protocol 1.29.0

A project keeps its settings for each target in project.n2proj, under build.targets, beside build.modules. The editor writes them with SetBuildTargets (Project commands); the Build Settings panel (stage 3) is where a person edits them.

"build": {
  "modules": { "physics3d": "none", "physics2d": true },
  "targets": {
    "windows": { "enabled": true, "displayName": "Triangle-Like", "version": "1.0.0", "buildNumber": 3, "renderer": "opengl" },
    "web":     { "enabled": true, "modules": { "physics2d": true } },
    "android": { "appId": "com.example.trianglelike", "orientation": "landscape", "signing": { "profile": "release" } }
  }
}
KeyValue
enabledtrue or false: whether the editor offers the target
displayNameThe game's name on that platform: 1 to 64 characters, no control characters
appIdThe reverse-domain id stores use, such as com.example.game: two or more segments of letters, digits and _, each starting with a letter; at most 150 characters
versionmajor.minor.patch, each part 1 to 5 digits
buildNumberA whole number from 1 to 2,100,000,000 (Android's versionCode range)
orientationany, landscape or portrait
rendererauto, software, opengl, vulkan or webgpu
configThe default configuration: debug or release
iconA res:// path to a .png inside the assets folder
modulesThe engine modules for this target, over build.modules: the same keys and values (Project modules)
signing{"profile": "<name>"} only: the name of a signing profile kept in the user's own n2build.json, 1 to 64 letters, digits, ., _ or -

Target names follow the descriptor rule (a lowercase letter, then lowercase letters, digits and -, at most 32), and a name need not be a target this machine knows, so a private target's settings can live in a shared project. At most 32 targets and 64 KiB of settings. A key this version does not know is kept, so a newer editor's setting survives an older one.

Guarantee: no signing secret is ever stored in the project

Project files are committed and shared, so a target refers to its signing material only by a profile's name. SetBuildTargets refuses, at any depth of a target, a key whose name looks like a secret (it contains password, passwd, passphrase, secret, token, privatekey, credential, apikey, storepass, keypass or certificatedata, ignoring case, _, -, . and spaces) and any string holding a PEM block (-----BEGIN). The error names the key and never echoes the value. Tests: BuildTargetsTest.NoSecretCanBeStoredAtAnyDepth, EditorProjectTest.SetBuildTargetsRefusesBadSettingsAndSecretsAndSavesNothing.

What n2build reads stage 3

A build for target T reads build.targets.T; the other targets' settings are not looked at. The rest of the keys (appId, orientation, renderer, icon, signing) belong to the stages that need them (Android, iOS).

KeyWhat n2build does with it
modulesLaid over build.modules key by key: {"physics3d": "jolt"} over {"physics3d": "both", "physics2d": true} builds Jolt and Box2D. The physics check per target, the build tree's key and the CMake configure all use that list: n2build passes -DN2ENGINE_TARGET=T, and cmake/N2EngineModules.cmake reads each module from build.targets.T.modules first, then build.modules. scripts/project-modules.mjs --target T checks the same list against what the project uses.
displayNameThe game's name for that target: the executable (Triangle-Like.exe), the package folder and game in the marker. Without it, the project's name.
version, buildNumberWritten into the package marker (.n2build-package.json) when set.
configThe configuration when --config is left out; else release. --config always wins.
enabledfalse hides the target in the editor's Build Settings panel. n2build still builds it when asked by name, with a warning.

n2build checks these five keys by the rules above when it reads them, so a hand-edited mistake fails the build with the key's name instead of producing an odd package. Tests (tools/n2build/n2build.test.mjs): a target's modules are laid over build.modules, key by key, displayName names the game on that target; version and buildNumber go into the marker, the configuration: --config, else the target's config, else release, build --dry-run uses the target's config and name, and warns when the target is turned off; scripts/project-modules.test.mjs: --target checks the target's list against the project.

A hand-edited mistake

A project whose build.targets was hand-edited into something refused still opens; the host logs a warning and SetBuildTargets refuses to save until a patch fixes it. n2build refuses to build that target until it is fixed.

Source: engine/src/io/BuildTargets.cpp, editor-server/src/EditorServer.cpp — HandleSetBuildTargets; tests: tests/engine/io/BuildTargetsTests.cpp, EditorProjectTest.SetBuildTargets*

Target descriptors

A target is data, not code: targets/<name>/target.json. n2build has no code path named after a target. More folders of descriptors come from "targetFolders" in the user's n2build.json (%APPDATA%\N2Engine\n2build.json, else $XDG_DATA_HOME/n2engine/ or ~/.local/share/n2engine/), from N2BUILD_TARGET_DIRS, and from --targets-dir. That is where a private target lives (a console SDK under NDA). A name defined twice is an error naming both files, so a private target can never silently replace a public one.

JSON output

With --json every line on stdout is one JSON object, and the last is the result. The editor's Build Settings panel (stage 3) reads these.

typeFields
stepid (configure, compile, package, archive, run, serve, plan), title
logstream (stdout, stderr), text: one line from a tool n2build runs, or from the game
warningtext
doctortarget, displayName, ok, checks (each: id, title, required, ok, version, detail, fix)
targetstargets (each: name, displayName, hostSystems, buildableHere, source)
resultok; on success output (the package folder), entry, archive, url (web run); on failure error

Not done yet

  • The editor. The Build Settings panel (stage 3, in the frontend). n2build already reads the per-target settings (above).
  • Packs. A package carries the game's folder as it is; zip and 7z packs come in stage 4.
  • CI builds and runs the Linux package through n2build. The Windows and web packages are built through n2build locally only; CI still builds those with CMake directly.
  • Package size on Windows. A build with PhysX ships PhysXGpu_64.dll (about 360 MB of the 374 MB lua_project package, measured 2026-11-10), because the engine's PhysX build always lists it. A game that does not use GPU physics (physics.gpu) does not need it; leaving it out is a follow-up. A project with "physics3d": "none" or "jolt" ships no PhysX at all.
  • Android, iOS, macOS and private targets: later stages of the plan.
