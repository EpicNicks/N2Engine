Application & frame loop

Application is the engine singleton. It starts the subsystems and reports which ones came up, runs the frame loop, turns a quit request into an orderly exit, and shuts the subsystems down in a fixed order. This page also covers Time, which the loop drives.

Init and ApplicationOptions

Application::GetInstance() returns a function-local static; the class cannot be copied or constructed elsewhere. Nothing is started until one of the Init overloads runs.

Init(options) runs these steps in order:

  1. If the application is already initialised (an Init with no Shutdown since), log the warning "Application::Init called again; ignored (call Shutdown first to re-initialize)" and return the stored health report. Nothing below runs PR #34.
  2. In Debug builds (N2ENGINE_DEBUG), install the console log subscriber, once per process (see Logger).
  3. Reset the health report and clear the quit flag (_quitRequested = false).
  4. Project file and Lua seed: load project.n2proj once when projectPath is set, and call LuaRuntime::SetLuaSeed with its determinism.luaSeed (unset without a project or a setting; a warning is logged when it is set, see the security note) PR #172.
  5. Network preset PR #187: it runs between loading the project file and setting the Lua seed (step 4 above). It reads the project's network block and checks the preset (ValidateNetwork). With the default preset none nothing is checked and nothing below changes. A deterministic project with an unmet requirement is refused here: one error is logged for the count and one for each unmet requirement, Init returns a health report in which the seven usual rows are NotStarted and the Network row is Failed, _initialized is cleared, and nothing after the project file runs (no Lua seed or state, no SIMD tier, no window, no camera, no physics, no audio). See the refusal. The physics backend is chosen at this point too (physics.backend, else the host's physicsBackend; Physics::ChooseBackend) PR #199, because the preset is checked against the selected backend: a backend that is not in the build refuses a Deterministic project here and falls back to the other backend, when the build has it, with a warning for any other preset; a Deterministic project is also refused while the selected backend lacks a feature group (the physics-features requirement) PR #211. The authoritative preset is checked after the physics step instead and only warns. A start that goes ahead with authoritative or deterministic sets the simulation mode right after Time::Init (Who sets the mode); none leaves it alone.
  6. Scripting: LuaRuntime::Instance().Initialize(). The result is cached by LuaRuntime, so an Init after Shutdown reports the first outcome again.
  7. Math::InitializeSIMD(request) with the project's math.simdTier (Auto without a project; the tier in use is logged, math PR #162), then Time::Init() (resets all clocks and timeScale to 1).
  8. Window and renderer: Window::InitWindow(options).
  9. Create the main camera, even without a window, so GetMainCamera() is never null after Init. Perspective 45°, near 0.1, far 100, at (0, 0, 10). Aspect is the window's, or 16:9 when the window has no size.
  10. Physics: construct and initialise the selected backend, PhysXBackend or, for physics.backend jolt in a build with N2ENGINE_USE_JOLT, JoltBackend PR #205 (selecting it); on failure the backend is destroyed and left null.
  11. Audio: skipped when headless, else AudioSystem::Instance().Initialize().
  12. Store the health report (the seven rows, then the Network row), log a warning for every failed subsystem, return a copy.

Subsystem health

Init returns an EngineHealth: a list of SubsystemStatus{name, state, detail} in the fixed order Window, Renderer, Physics, Particles, SoftBodies, Audio, Scripting, Network PR #138 PR #187. GetHealth() returns the same report later (as of the end of the last Init), except that the Particles and SoftBodies rows follow the physics backend's per-feature GPU status as it is now (GPU features) and the Particles and SoftBodies rows' details are refreshed with the live ParticleSystem and SoftBody counts on every call PR #143. Before any Init the list is empty, which counts as healthy.

The Network row PR #187 is a generic SubsystemStatus (the editor protocol is unchanged). It is Disabled with Preset none (offline): no network model for the default preset, and Disabled with Preset authoritative: settings validated, but the network runtime does not exist yet (followed by ; warning: ... for each warning, then ; physics backend physx, the BackendId() of the backend that actually runs, or none when it failed to start PR #199, then ; simulation mode authoritative, the mode read back from GetSimulationMode()) for a preset whose checks pass: like the SoftBodies row it never says Running for a feature that is not there. It is Failed, naming every unmet requirement, when a deterministic project was refused. A refused Init returns the same eight rows with the other seven NotStarted. Network presets.

Headless mode and a failed window

isHeadless = true does two things and nothing else:

  • The GLFW window is created with GLFW_VISIBLE = false. It is still a real window with a real renderer when the machine can provide one.
  • Audio is not initialised and is reported Disabled. Audio calls are then safe no-ops, and audio clips do not load (they need an OpenAL context) PR #37; see Audio: headless behaviour.

Physics and scripting start as usual. On a machine with no monitor, the window size falls back to 1280×720; on one with no GPU (such as the CI runner), the window or renderer fails and is reported Failed. The exceptions are a headless application on the software renderer (or WebGPU), which gets no window at all (below) PR #89, and RenderBackend::NONE, which has no window and no renderer whatever isHeadless says (below) PR #216.

The no-window path PR #89

Window::UsesNoWindow(options) is true for isHeadless with RenderBackend::SOFTWARE, and, since stage G4 of #155 PR #208, with RenderBackend::WEBGPU (WebGPU has no window path at all), and only then; RenderBackend::NONE also has no window, but InitWindow handles it first, before this function is asked (below). InitWindow then (for WEBGPU see the paragraph after the list):

  • never initialises GLFW and creates no window;
  • starts the software renderer headless at Window::FallbackWidth × FallbackHeight (1280×720), with SoftwareRenderer::Initialize(nullptr, ...) (headless mode), which makes no GL call;
  • creates the InputSystem as usual. Keyboard and mouse bindings read nothing without a window, as on a window that failed to open (InputBinding and Mouse check for one), and PollEvents still updates input, so injected pointer input and fake bindings work. Gamepads read nothing too: gamepad bindings and InputSystem::GetConnectedGamepads check Window::HasGlfw() (true only while GLFW is initialised, so false without a window) and never call GLFW, which would refuse with GLFW_NOT_INITIALIZED PR #89.

The window is then valid (IsValid(): a renderer, and a window or IsWindowless()), so Run() and RenderEditorFrame render. ShouldClose() is false while it is valid, since nothing can close it: Run() ends on Quit(). GetWindowDimensions() reports the renderer's starting size, and SetRenderSize resizes the renderer as with a window. Window-only calls (the GLFW title in SetTitle, SetWindowMode) do nothing. Shutdown clears it like any window. The editor host uses it for --renderer software (the host's options), which is how CI renders editor frames.

RenderBackend::WEBGPU PR #208. With a window (isHeadless false) InitWindow fails at once with "The WebGPU renderer runs only without a window (isHeadless), as in the web player". Headless, it takes the no-window path; in a native build it then fails with "The WebGPU renderer can only be chosen in the web build (natively it is the CI test harness of the backend, not a renderer an application can run)", even when N2ENGINE_RENDERER_WEBGPU is ON (W8 of #155). Both are refusals, not renderer failures (RendererFailed() is false), and neither calls GLFW. In the web build it makes the backend through Renderer::WebGpu::CreateWebGpuRenderer() (renderer/webgpu/WebGpuFactory.hpp, which names no WebGPU type, so the engine never includes webgpu.h) and initialises it headless at 1280×720 like the software renderer; if the page supplies no device (below), InitWindow returns false with "Failed to initialize the WebGPU renderer (see the log)" and RendererFailed() true. In the health report the first two leave the window Failed with that message and the renderer not started; the web build's failure reads "Closed because the renderer failed" / "WebGPU: Failed to initialize the WebGPU renderer (see the log)". The name the health report and the log use is "WebGPU" (and "No window: the headless WebGPU renderer draws offscreen" for a window that is deliberately absent, with presentation to the browser canvas in G5). tests/engine/WindowlessTests.cpp checks the refusal with a window, and the native refusal or the web failure, in both builds.

Design decision: a headless software application has no window at all PR #89

The software renderer draws into a CPU buffer; a window only gives it a GL context to blit that buffer to, so it can be seen. A headless application hides that window, so the blit is wasted work, and opening it needs GLFW and a GL 3.3 context, which a machine without a GPU or display (the CI runner, a server) doesn't have: the whole renderer used to fail there over a window nobody would see. So the combination that can't use a window gets none, and needs no new option: isHeadless already says "nobody looks at this window", and SOFTWARE is the only backend that renders without one (OpenGL needs the window for its context; Vulkan can initialise and render offscreen with no window at all, but until its swapchain lands in stage F of #43 it cannot show anything in one, so it is not a backend a headless application selects). Initialising no GLFW at all, rather than a hidden window that may fail, makes the path identical on every machine. The input system is still created, so code that expects one (actions, the pointer dispatcher, Lua's Input) behaves as on a window with no keys pressed. Decided on #6 (review correction 2 and decision A); #74.

No renderer at all: RenderBackend::NONE PR #216

A dedicated server draws nothing, so N2Server asks for no renderer (with audio = false and physicsGpu = false). InitWindow then initialises no GLFW, creates no window and no renderer, creates the InputSystem as on the no-window path, and succeeds. The window is not valid (IsValid() needs a renderer), IsWindowless() is true, GetRenderer() is null, GetWindowDimensions() is 0×0, ShouldClose() is false (a windowless window never closes: its host ends on its own conditions), and SetRenderSize is false. In the health report the Window and Renderer rows are Disabled ("No window: this host draws nothing", "No renderer: this host draws nothing"), not Failed. Run() and BeginRun() refuse such a window (they need a valid one): a host with no renderer runs its own loop, calling Tick with pollEvents and render off, as N2Server does. Resources::LoadShader returns null instead of dereferencing the missing renderer. Applying it to a host that renders is a mistake: nothing will be drawn.

The frame loop

Run() loops while the window is not closing and no quit was requested. Each iteration does the following, in this order:

  1. Window::PollEvents(): GLFW events, then InputSystem::Update() (actions fire here; see Input).
  2. Time::Update(): measure the frame delta and advance the clocks.
  3. Add min(unscaled delta, 0.25 s) to the fixed-step accumulator. With no scene loaded the accumulator is reset to 0 instead of being drained PR #34. (In a network simulation mode the whole delta is added, PR #186.)
  4. If a scene is loaded: Scene::ProcessAttachQueue(), so components added since the last frame get attached before anything updates. (A network simulation mode skips this step and processes the queue at each tick boundary instead PR #186.)
  5. If a scene is loaded: zero or more fixed steps (below).
  6. If a scene is loaded: PointerDispatcher::Update(): the OnMouse* callbacks for the object under the cursor, where Unity sends them (see Picking) PR #48.
  7. If a scene is loaded: Scene::Update().
  8. If a scene is loaded: Scene::AdvanceCoroutines() (see Coroutines).
  9. If a scene is loaded: Scene::LateUpdate().
  10. AudioSystem::Update(), after LateUpdate, where listeners and sources push their positions.
  11. Render(): clear, set the main camera's view/projection, upload scene lighting, render the scene (opaque, then transparent; see Rendering the scene), draw the UI over it (the UI pass), present. Skipped when there is no renderer.
  12. If a scene is loaded: Scene::ProcessDestroyed(): objects and components destroyed during the frame are torn down here.
  13. SceneManager::ProcessAnyPendingSceneChange(): a scene load requested during the frame takes effect now (see Scenes).

Rendering the scene PR #46

Application::Render calls BeginFrame, sets the main camera's view and projection and the scene lighting on the renderer, then calls Scene::Render(renderer, camera), then the UI pass PR #50 (UI::UISystem::Render: canvases over the scene with their own orthographic projection, no depth test, culling off), then EndFrame and Present. Scene::Render is public, so a host or a test can render a scene into any IRenderer with any camera.

Every IRenderable draws in one of two queues, chosen by GetRenderQueue(), which returns a RenderQueueKey{queue, sortKey}. The default is Opaque with sort key 0. There is no overlay queue: UI draws in its own canvas pass (see below). PR #65 A renderable can draw in both queues: IRenderable::DrawsInQueue(queue), asked for each queue, defaults to "only the queue GetRenderQueue() names", and a MeshRenderer with opaque and blended submeshes returns true for both.

  1. Collect. One traversal of the scene gathers the renderables to draw: active components on objects that are active in the hierarchy, depth first, parents before children, components in the order they were added. This is the order rendering has always used. Each renderable's queue (and DrawsInQueue for each queue) is read once, before anything draws.
  2. Opaque. The renderables that draw in the Opaque queue draw in that traversal order, unchanged from before the render queue, with RenderState::Opaque(). The sort key is ignored here.
  3. Transparent. The renderables that draw in the Transparent queue draw after every opaque one, stable-sorted by sort key (lowest first), then by camera-space depth of their object's world position, back to front. A renderable whose object has no Positionable sorts at depth 0, the camera's own depth. Equal keys and depths keep traversal order. They draw with RenderState::Transparent(): blended, depth-tested, not writing depth. A renderable in both queues sorts here by its GetRenderQueue() sort key.

Scene::Render calls IRenderable::RenderInQueue(renderer, state, queue) once per queue a renderable draws in, with that queue and its state PR #65 (the queue argument is new; before, it was RenderInQueue(renderer, state)), and the renderable passes the state to its draws as DrawMesh(mesh, model, material, state), drawing only what belongs in that queue. The default RenderInQueue calls Render(renderer), whose draws get the default state (the Opaque one), so renderables written before the render queue draw exactly as before.

Culling follows the winding on screen PR #65. A MeshRenderer or built-in shape whose world matrix mirrors it (a negative determinant: a negative _size on one axis, or an odd number of negative scales up its hierarchy) culls Front instead of Back, so it shows its outside. Visible change: a mirrored shape used to cull back faces and show its inside. The built-in sphere is also no longer wound inside out (the visible changes).

Blending follows the alpha mode PR #65. The Opaque queue's state, which is also the RenderState default and what DrawMesh(mesh, model, material) uses, no longer blends; only the Transparent queue (and the UI pass, with its own state) does. Materials pick their queue by alpha mode: Opaque and Mask draw in the Opaque queue unblended, Blend in the Transparent queue (design note). Visible change: an Opaque-queue draw with a translucent colour, such as a CubeRenderer whose _color has alpha below 1, drew blended over what was behind it on OpenGL and now draws opaque; give it a Blend material to keep it see-through. The software renderer never blended, so its images don't change.

Warning: don't change the scene while rendering

Scene::Render collects raw pointers to every renderable before any of them draws. A Render or RenderInQueue must not add, remove or destroy components or GameObjects immediately, because that could free a renderable that is still waiting to draw. Deferred destruction is fine: Destroy only queues the object, and it is torn down at step 11, after rendering (see GameObjects).

Guarantee: draw order within a frame

A renderer puts a frame's draws on screen in the order they were submitted, unless the backend documents otherwise (IRenderer in renderer/include/renderer/common/Renderer.hpp). The exceptions:

  • Software renderer. It decides by each draw's state, not by its queue. It reorders depth-writing draws front to back (each run of consecutive draws that both depth-test and write depth), so early-Z rejects hidden pixels before they are shaded. Without blending, this cannot change the image except where fragments have exactly equal depth. Every draw that doesn't both depth-test and write depth (normally the Transparent queue) keeps its submitted position. A Transparent renderable that doesn't override RenderInQueue draws with the default, depth-writing state, so its draws can be reordered too. It has no blending: blend is ignored and transparent draws are drawn opaque, without writing depth. Depth test, depth write and culling are honoured per draw. The one exception is the text shader, which alpha-tests and writes depth wherever it draws and the draw depth-tests, whatever depthWrite says PR #51; text is still ordered by the state it was submitted with, so a Transparent-queue text draw keeps its position (design note).
  • Vulkan renderer. Draws in submission order, like OpenGL: each draw is recorded into the frame's command buffer with its own pipeline (a cache keyed by shader, RenderState and wireframe) and takes a snapshot of its material and of the view and projection when it is made (#43, stage B PR #144; status). The unlit shader draws, and since stage C PR #148 the lit shader too (lit and PBR materials, scene lighting). Since stage D PR #158 blend and additive blend exactly as OpenGL does and the Transparent queue and the UI pass draw as they do there (details), and since stage E PR #165 the SDF text shader draws as OpenGL's does: antialiased and blended, depth only as the draw's state says (text).

Design decision: two render queues, with state passed per draw

Blended surfaces only look right drawn after the opaque geometry, back to front, without writing depth. Before the render queue, everything drew in hierarchy order with one global state, so a transparent surface could hide whatever was drawn behind it later. Two queues are enough for the world: Opaque keeps hierarchy order exactly, so existing scenes don't change, and Transparent sorts by an explicit key first (for layered effects that depth alone can't order) and depth second. UI isn't a third queue; it gets its own canvas pass.

Depth test, depth write, culling and blending travel with each draw as a RenderState rather than being set on the renderer. The software renderer records draws and reorders them on its render thread, so a global setter would apply to the wrong draws there. A per-draw state is the only form every backend can honour. OpenGL sends only the fields that change between draws, and resets all of them at BeginFrame. Decided on #1 (Q8).

Three IRenderer calls were added for TextRenderer. Each has a default body in IRenderer, so renderers and test fakes written before them still compile and behave as before.

  • CreateTexture(data, width, height, channels, options) takes a TextureOptions (renderer/include/renderer/common/TextureOptions.hpp): filter (Linear or Nearest), wrap (Repeat or ClampToEdge) and mipmaps. The pixel format still follows the channel count: 1 channel is a single-channel R8 texture, then RG8, RGB8, RGBA8. The defaults (linear, repeat, mipmaps) are what every texture had before, and the overload without options uses them. TextureOptions::SdfAtlas() is linear, clamped and without mipmaps. On OpenGL, rows are uploaded tightly packed (unpack alignment 1), so 1- to 3-channel textures of any width load correctly. The software renderer stores the options on its texture and honours wrap. Its unlit and lit shaders follow filter PR #64: bilinear for Linear (every channel, with the text shader's texel centres and weights), nearest for Nearest, picking texels as GL_NEAREST does (before, they always sampled nearest, and a texture two texels wide showed its second texel only at u = 1). The software renderer first waits for any frame still rasterizing on its render thread, which reads meshes. The Vulkan renderer, stages 0, A, B, C, D and E PR #136 PR #142 PR #144 PR #148 PR #158 PR #165

Status: headless clear and readback, meshes and textures (stage A), the built-in unlit shader with DrawMesh, IndexRange and DrawObjects (stage B), lit and PBR materials (normal, emissive, occlusion and metallic-roughness maps, 1x1 defaults for absent ones) with scene lighting of up to 2 directional, 8 point and 4 spot lights (stage C), and blending exactly as OpenGL (SRC_ALPHA / ONE_MINUS_SRC_ALPHA, additive SRC_ALPHA / ONE, the same factors for alpha) with depth write off for the Transparent queue and the UI pass, the UI pass's mid-frame SetViewProjection and dynamic meshes (particles) through UpdateMesh (stage D), and the SDF text shader with outline, softness and shadow, text materials and multi-pass text effects, antialiased and blended as on OpenGL (stage E); what remains of #43 is stage F (a window: surface, swapchain, present, resize and minimise, the GPU selection API, which needs a real GPU to verify) and the optional stage G (a Windows CI execution leg, runtime GLSL, the editor host's --renderer vulkan, a default-renderer change, each its own decision). It has no swapchain, so nothing reaches a window until stage F. Present presents nothing and logs one warning per renderer saying so (stage F). What is not there yet logs once and returns nullptr/false/nothing, and none of it crashes: CreateShaderProgram (custom GLSL is not in v1) returns nullptr, and so does the GPU selection API's stage F half. IRenderer is unchanged. Initialising with a window handle works but the handle is ignored for now.

  • Build. N2ENGINE_RENDERER_VULKAN (CMake, default ON) builds it; OFF compiles it out and needs no Vulkan headers or loader (options). On: the Vulkan SDK on Windows (found through VULKAN_SDK or C:/VulkanSDK) or libvulkan-dev on Linux, as before. OpenGL stays the default renderer, and the editor host still refuses --renderer vulkan.
  • Validation. The Khronos validation layer is loaded when N2_VULKAN_VALIDATION=1 (and then it must be installed, or Initialize fails), is never loaded with N2_VULKAN_VALIDATION=0, and otherwise follows the build: off in a Release build, on in a Debug build if the layer is installed (a missing layer only logs a warning). A debug messenger counts the errors and warnings (GetValidationStats), and logs them to stderr. Code that creates the renderer can override the variable with SetValidationMode before Initialize.
  • Device. The renderer takes the best physical device that has a graphics queue, Vulkan 1.1 and the two target formats (discrete GPU, then integrated, virtual, CPU). GetInitStatus says why an Initialize failed: no driver, no suitable device, validation demanded but missing, or another failure.
  • Target. The image is in TRANSFER_SRC_OPTIMAL between frames (the render pass leaves it there), which is what the readback copy, and stage F's blit to a swapchain, read. ReadFramebuffer flips the rows to the interface's bottom-row-first order; the draw tests check it (a quad over NDC y -1 to 0 fills the first half of the buffer, as the software renderer's does).
  • Resources (stage A). GPU memory comes from AMD VulkanMemoryAllocator 3.4.0 (MIT, vendored unmodified in external/VulkanMemoryAllocator/; it is private to renderer/src/vulkan/, so no public header, no engine code and no build with N2ENGINE_RENDERER_VULKAN=OFF sees it). The allocator imports the Vulkan functions statically (the renderer links the loader), is created for Vulkan 1.1 right after the device, and is destroyed just before it, after every allocation was freed. The stage 0 targets and readback buffer still use plain vkAllocateMemory. CreateMesh makes a device-local vertex buffer (the 64-byte Vertex) and a uint32 index buffer (none when there are no indices; a mesh needs vertices, else nullptr). CreateTexture makes an image of format R8 (1 channel), R8G8 (2), or R8G8B8A8 (3 and 4: RGB8 is not a sampled format everywhere, so 3 channels are expanded to RGBA with alpha 255 at upload); rows are tightly packed, so any width works. The image view swizzle makes a 1-channel texture sample (r, 0, 0, 1) and a 2-channel one (r, g, 0, 1), like OpenGL and the software renderer. srgb picks R8G8B8A8_SRGB for 3 and 4 channels, as OpenGL does (1 and 2 channels ignore it, which also avoids the optional R8/R8G8 sRGB formats); a device that cannot sample that format gets UNORM (logged once) and the colours are no longer decoded when sampled. Samplers follow TextureOptions (nearest or linear, with the matching mipmap mode; repeat or clamp-to-edge; anisotropy off, because the device feature is not enabled) and are cached by those options for the renderer's lifetime. Mipmaps are a full chain made with vkCmdBlitImage, only if the format supports linear filtering and blits as source and destination; otherwise the texture has one level (logged once). Every level ends in SHADER_READ_ONLY_OPTIMAL. A size over the device's limit, null data, a zero size and channels outside 1-4 give nullptr. Pointers this renderer did not make (another renderer's, another backend's, a test fake) are ignored: DestroyMesh and DestroyTexture do nothing and UpdateMesh returns false, because meshes and textures are tracked in a registry the renderer owns. Uploads are synchronous: each goes through a host-visible staging buffer and a one-time command buffer and waits for the queue, which works the same inside or outside a frame and costs a queue stall per call (a staging ring is a later optimisation; with text and particle meshes updated every frame this is the thing to measure on a real GPU).
  • Shaders (stage B). The three built-in shaders (unlit, lit, SDF text) are GLSL 450 in renderer/shaders/vulkan/, faithful ports of OpenGL's GLSL 330 ones (the same maths and constants: the lit port keeps the PBR terms and the environment-BRDF fit, the text port the antialiased fwidth ramp), with explicit layout(location, set, binding) and every non-opaque uniform a member of a std140 block (a GLSL bool is an int there, 0 or 1). All three are compiled and embedded, so glslang checks all of them on every build, and all three are handed out (GetStandardUnlitShader, since stage C PR #148 GetStandardLitShader, and since stage E PR #165 GetStandardTextShader). Custom GLSL is not in v1 (decision): CreateShaderProgram logs one warning and returns nullptr; LoadFromStrings on a built-in returns false; DestroyShaderProgram is always false (the renderer owns the built-ins) and UseShaderProgram does nothing (a draw takes its shader from its material); IShader::Set* do nothing on a built-in (the material carries the values); IsValidShader is true only for this renderer's built-ins. There is no SPIR-V reflection: renderer/common/GpuShaderInterface.hpp is the table of every block member (its block, std140 offset, type and size), vertex attribute and sampler binding, and a device-free parity test parses the GLSL as text and checks the table, Material::ApplyUniforms and OpenGL's defaults against it.

  • Pipeline layout and cache. One layout serves all three shaders. Set 0 is the frame: binding 0 the per-draw block (uModel, uView, uProjection, 192 bytes) as a UNIFORM_BUFFER_DYNAMIC, binding 1 the lighting block (752 bytes), also a UNIFORM_BUFFER_DYNAMIC since stage C PR #148: a copy of the scene lighting in the frame's ring, named by an offset per draw (how it gets there). Set 1 is the material: binding 0 the material block (a dynamic uniform buffer, 128 bytes covers every shader's block), bindings 1 to 5 combined image samplers, the base texture then the AuxTexture slots in enum order; a texture the material does not have (or that was destroyed since it was set) is a renderer-owned 1x1 default. A VkPipeline is made lazily, under the renderer's lock, on the first draw with a given (shader, RenderState, wireframe) and kept: depth compare LESS (as glDepthFunc(GL_LESS)), depth write only while the test is on (nothing writes depth with the test off, as GL), cull from CullMode, a vertex input of one 64-byte Vertex binding with exactly the attributes the shader reads, and a dynamic viewport and scissor, so SetRenderTargetSize and Resize never invalidate a pipeline. The colour blend attachment follows blend and additive as OpenGLRenderer::ApplyRenderState does (stage D PR #158, details); additive without blend is an opaque draw, so it shares the opaque pipeline. Wireframe (SetWireframe) uses VK_POLYGON_MODE_LINE and needs the device feature fillModeNonSolid, enabled at device creation only where the device has it; otherwise SetWireframe(true) is ignored with one log line. Shutdown destroys every pipeline, layout, pool, module, ring and default texture before the allocator and the device.
  • Clip space. The engine's matrices are OpenGL's: clip z from -w to w and y up. The vertex shaders write gl_Position.z = (z + w) / 2 (Vulkan's 0 to w), and BeginFrame sets a viewport with a negative height (y = height, height = -height; core in Vulkan 1.1), so a vertex at NDC y +1 is the top row of the image as in GL and ReadFramebuffer's bottom-row-first output matches the software renderer's. Vulkan judges the winding in that upright image, so GL's counter-clockwise front faces are VK_FRONT_FACE_COUNTER_CLOCKWISE here (an unflipped GL projection would give an upside-down image and need clockwise). The tests prove all of it with pixels, not by reasoning: the near plane (z = -1), the far plane (z = 1) and what lies beyond them, the depth order in both draw orders, the cull modes against both windings, and an upright texture on the cube's faces.
  • Draws, the uniform ring and the material snapshot. DrawMesh is immediate: under the renderer's lock it looks the mesh and material up in the renderer's own registries (a foreign or destroyed pointer is never dereferenced and draws nothing, as does a null model matrix, a draw outside BeginFrame to EndFrame, and a mesh without indices), takes the buffers from the mesh as they are now (an UpdateMesh later in the frame retires the old ones to the frame's slot, so the frame shows the data the draw was made with), and records bind and draw into the frame's command buffer. The draw's model, view and projection, and a snapshot of the material's block, are written into the frame slot's uniform ring at offsets aligned to minUniformBufferOffsetAlignment (192 bytes per draw would not fit the 128-byte push-constant minimum). So a change to the material after DrawMesh does not affect that draw, as on OpenGL and the software renderer, and a SetViewProjection in the middle of a frame (the UI pass) affects only the draws after it. The ring is a chain of host-visible, persistently mapped uniform buffers per frame slot: when one is full the frame takes the next, twice as big, so any number of draws works (a test makes 10000 in a frame), and the chunks are kept and reused. The matrices are row-major as the engine passes them and the GLSL block says row_major, the counterpart of GL's transposed upload, so they are copied as they are. The descriptor sets come from per-slot pools that BeginFrame resets after waiting for the slot's fence, and draws with the same textures share one material set, so nothing a frame in flight reads is ever rewritten.
  • Shared by GPU backends PR #188. The pieces of the Vulkan backend that hold no Vulkan are shared, so another GPU backend can use them: the shader interface table (renderer/common/GpuShaderInterface.hpp), the lighting block builder (renderer/common/GpuLighting.hpp, both in Renderer::Gpu) and the block material (renderer/common/BlockMaterial.hpp, BlockMaterial: the values of a built-in shader's std140 material block and its textures, the same class the Vulkan backend's CreateMaterial returns). The cross-backend test helpers (CrossBackendDiff.hpp, BlendReference.hpp) are in tests/renderer/common/ for the same reason.
  • Materials (stages B and C). CreateMaterial(shader[, texture]) returns a material of the unlit, the lit or (stage E PR #165) the text built-in with OpenGL's defaults: its values live in a CPU copy of the shader's std140 block, written through the name table (an unknown name or the wrong type, for example SetInt("uAlbedo", 3), is logged once and ignored), plus the base texture and the four AuxTexture slots, kept for GetTexture and GetAuxTexture. The defaults are a table in renderer/common/GpuShaderInterface.hpp that the parity test checks against OpenGLRenderer::CreateMaterial (name, type and value): unlit uAlbedo white, uHasTexture 1 with a texture, uAlphaCutoff 0; lit also uMetallic 0, uSmoothness 0.5, uEmissive 0, the four uHas*Texture flags 0, uOcclusionStrength 1, uNormalScale 1 and uPbr 0; text uAlbedo white and the six effect uniforms 0. CreateMaterial(nullptr) and with a shader this renderer did not make returns nullptr; DestroyMaterial ignores nullptr and foreign pointers; Shutdown frees the materials still alive.
  • Lit materials and their five samplers (stage C PR #148). The lit material block is 72 bytes (the descriptor covers 128, so one layout serves every shader). The five samplers are the base texture and then the AuxTexture slots in enum order (emissive, occlusion, normal, metallic-roughness); a slot whose texture is absent, was destroyed, or is not a texture of this renderer samples a renderer-owned 1x1 default: white for the base texture, black for emissive (adds nothing), white for occlusion (no occlusion), the flat normal (128, 128, 255) and white for metallic-roughness (the factors alone). The renderer does not infer the uHas*Texture flags from the textures: as on OpenGL, Material::ApplyUniforms sets them. The software renderer does infer them and stores an invalid texture as none, so the two agree on what is drawn only because the defaults are neutral: a flag on with a missing, foreign or destroyed texture draws exactly what the flag off draws (a test proves it). Normal-map handedness (tangent.w), a mirrored model matrix, a negative or tiny scale and a mesh without tangents are the lit shader's own maths, a faithful port of OpenGL's, and the tests draw each of them.
  • Scene lighting (stage C PR #148). UpdateSceneLighting(lighting, cameraPosition) fills the 752-byte std140 lighting block of the lit shader from a SceneLightingData exactly as OpenGLRenderer::UpdateSceneLighting sets its uniforms: the camera position, the ambient colour, uEncodeOutput, at most 2 directional, 8 point and 4 spot lights (the first four spot lights are the candidates; one with a zero axis lights nothing and is left out, the rest packed down; the axis is normalised; cosInner and cosOuter are the cosines of the cone angles, with no special case for an inner angle past the outer one), and zero everywhere else. The fill is a pure function (renderer/common/GpuLighting.hpp) whose every offset comes from the interface tables at compile time, so there is no second hand-typed copy; the parity test checks the tables against the GLSL member by member (the light structs, their std140 offsets and strides) and against every name OpenGL sets. It may be called inside the frame (the engine calls it after BeginFrame), outside one, or several times in a frame; before the first call the block holds SceneLightingData{} seen from the origin.
  • Colour space (stage C PR #148). OpenGL renders into an SRGB8_ALPHA8 target and lets the framebuffer encode only for the lit shader in linear lighting; the Vulkan target is R8G8B8A8_UNORM everywhere, so on Vulkan uEncodeOutput is simply 1 for linear lighting and the lit shader always encodes in the shader; SceneLightingData::forceShaderEncode (an OpenGL escape hatch for a driver that reports the wrong encoding) changes nothing. Unlit and text (stage E: the text shader has no uEncodeOutput, as on OpenGL) draw the same in both colour spaces. An sRGB texture (TextureOptions::srgb, a 3 or 4 channel texture; stage A makes it R8G8B8A8_SRGB, falling back to UNORM with a log where the device cannot sample it) decodes on sampling in both colour spaces, as OpenGL's SRGB8_ALPHA8 does; occlusion, normal and metallic-roughness maps are data and never decoded. The decode happens before filtering, as on OpenGL, where the software renderer decodes after it, so a linear-filtered sRGB texture differs slightly between them (the lit cross-diff tolerance is for that).
  • Blending, depth write and the queues (stage D PR #158). The pipelines blend exactly as OpenGL's ApplyRenderState: with blend the colour attachment uses SRC_ALPHA and ONE_MINUS_SRC_ALPHA (additive: SRC_ALPHA and ONE), equation ADD, and the same factors for alpha (glBlendFunc sets one pair for both), so the target's alpha is blended too: a * a + (1 - a) * dst.a, and ReadFramebuffer returns it. additive counts only together with blend: without it the draw is opaque and writes the shader's alpha as it is. The result is clamped by the UNORM target (additive draws saturate at 255). Depth write is depthTest && depthWrite, so a Transparent draw (depth test on, write off) is hidden by opaque geometry in front of it but writes no depth, and nothing writes depth with the test off. The renderer never reorders: draws reach the target in submission order, so the Opaque queue, then the back-to-front Transparent queue, then the UI pass land in that order with the states they were submitted with (RenderState::Opaque(), Transparent(), UISystem::OverlayState()). The UI pass calls SetViewProjection in the middle of the frame: each draw copies the matrices current when it was recorded into its own ring block, so the scene is neither moved by the UI pass nor moves it (tests interleave draws and matrix changes, also past one ring chunk). A mesh updated every frame (particles, through UpdateMesh) keeps its IMesh* while its buffers are replaced and retired, as described; UpdateMesh refuses an empty mesh, so a system with no particles alive draws nothing that frame. One known divergence from OpenGL: a blended lit draw in linear lighting.
  • Verification of blended scenes (stage D PR #158). The software renderer cannot blend, so a blended Vulkan frame is never compared with one software frame. The tests build a GL-semantics reference instead (the rule and the scenes).
  • Text (stage E PR #165). GetStandardTextShader returns the text built-in (nullptr only in a build without the compiled shaders, logged once as for the other two) and CreateMaterial(textShader[, atlas]) a material with OpenGL's text defaults, written through the name table into the shader's 92-byte std140 block: uAlbedo white, and uOutline, uOutlineColor, uSoftness, uShadowColor, uShadowOffset and uShadowSoftness all 0 (a name of another shader, such as uMetallic, logs once and is ignored). The shader is a port of OpenGL's: the atlas (the base sampler, read through .r) is a signed-distance field with the glyph edge at 0.5, the coverage ramps over about one screen pixel around it (fwidth; uSoftness widens the ramp), the outline and the shadow are composited under the face in one draw with a non-premultiplied over, and a fragment whose alpha ends up under 0.01 is discarded, writing neither colour nor depth. The draw is blended and depth-written as its RenderState says: the engine draws a TextRenderer in the Transparent queue (blended, depth-tested, no depth write) and a UIText in the UI pass (no depth test or write), so a later opaque quad behind a Transparent text is not rejected by it. Vulkan therefore matches OpenGL and not the software renderer, which alpha-tests (a glyph pixel is the text colour or untouched), writes depth wherever it draws, and ignores softness (the table). Text is unlit: with no uEncodeOutput it is identical in both colour spaces. Multi-pass effects (TextEffects.passes, and the shadow and outline settings, which are the first two passes) draw every pass with the same material and mesh, changing the effect uniforms between DrawMesh calls and drawing the face last; each DrawMesh snapshots the material's block into the frame's ring (above), so every pass draws with its own values within one frame, with no extra mechanism. UpdateMesh of the text mesh in place (when the layout changes) is the stage D path. A text material without an atlas draws nothing, as on OpenGL and the software renderer; so does one whose atlas was destroyed after SetTexture (how). IRenderer is unchanged.
  • Verification of text (stage E PR #165). Antialiased edges differ from the software renderer's alpha test by design, so the tests read an antialiased frame thresholded at half coverage (the 0.5 iso-line the software test cuts at) and compare the two backends only where they must agree: the rule, the scenes and the measured numbers.

Design decision: a buffer or image a frame may still read is never written or freed at once PR #142

With two frames in flight, the GPU may be reading a mesh or texture while the CPU asks to change or destroy it, and text, particles and the GPU cache call UpdateMesh every frame. So UpdateMesh never writes into a buffer: it uploads the new data into new buffers, keeps the same IMesh* and retires the old ones; DestroyMesh and DestroyTexture retire theirs. Each frame slot has a deletion list, and BeginFrame frees a slot's list right after it has waited for that slot's fence, when the frame that used the slot is known to have finished. Retiring inside an open frame uses that frame's slot (its own commands may use the object); retiring with no frame open uses the slot of the last submitted frame, which is the newest that can. When no frame is open and every frame fence is signalled (for example the synchronous upload of an UpdateMesh before any frame has run, which idles the queue), nothing can use the object, so it is freed at once and does not pile up. Shutdown waits for the device to go idle and frees all the lists and every resource the caller never destroyed, so with validation on a leak is an error. The cost is one allocation per update; the alternative, a ring of mapped buffers per mesh, needs a size known in advance, which text and particles do not have. Decided on #43 (2026-10-14).

Design decision: a blended lit draw in linear lighting blends encoded values on Vulkan PR #158

OpenGL renders into an SRGB8_ALPHA8 target and turns GL_FRAMEBUFFER_SRGB on only for the lit shader in linear lighting, so there a blended lit draw in linear lighting blends in linear space (the hardware decodes the destination, blends, and encodes), while every other draw blends the stored, encoded bytes. The Vulkan target is R8G8B8A8_UNORM and the lit shader encodes in the shader (stage C), so the blend sees encoded values for that one case: half-alpha red over blue gives about (128, 0, 128) on Vulkan where OpenGL gives about (188, 0, 188). The alternatives were an sRGB render target (it would blend in linear space but change what every other draw and the readback hold, and make unlit, text, UI and particle blends differ from OpenGL, which matter far more) or blending in the shader (a read of the target the pipeline does not have). Decided in stage C not to add an sRGB target; this is its known cost. Unlit, text, UI, particle and Gamma-lit blends match OpenGL. The Vulkan test documents the result and does not assert equality with OpenGL.

Design decision: the Vulkan shaders are compiled to SPIR-V when the renderer is built PR #144

Vulkan takes SPIR-V, not GLSL, so the engine needs a compiler somewhere. There were three places. Committed SPIR-V would need no tool to build, but the bytes differ between glslang versions, so a check that the committed file still matches the GLSL would be flaky unless the tool version were pinned, a reviewer cannot read it, and a stale file compiles fine. A compiler linked at run time (glslang or shaderc) would let a game load custom GLSL, but it adds tens of megabytes and the licence notices of glslang (BSD-3-Clause with NVIDIA, Khronos, BSD-2, MIT and Apache texts) and shaderc, which embeds it, to everything shipped; and nothing in the repository calls Resources::LoadShader, so v1 has no use for it. A build-time compiler (glslangValidator or glslc, found through FindVulkan) costs only that each builder has the tool (glslang-tools on Linux and in the Docker build stage, the Vulkan SDK's on Windows), generates the arrays from our own sources every build, checks on every build that all three GLSL files compile, and ships none of glslang, which is a build tool only. A build where no tool exists degrades to a documented no-draw fallback instead of failing, and the tests that need the shaders fail rather than skip under N2_REQUIRE_VULKAN=1. The built-in shaders are the only ones in v1; custom GLSL waits for a later runtime compiler. Decided on #43 (2026-10-14).

Design decision: scene lighting reaches the draws through the frame's ring, one copy per update PR #148

OpenGL stores the lighting in the lit program's uniforms: a draw uses what the last UpdateSceneLighting before it set, and a later update changes only later draws. Vulkan has two frames in flight, and stage B's one lighting buffer, bound by both frame slots, would have been rewritten while the other slot's frame might still read it, a race the validation layer does not always catch. So UpdateSceneLighting writes no GPU memory: it builds the block into a CPU copy and bumps a version. The first lit draw after an update copies the block into the current frame slot's uniform ring (the same host-visible chunks that hold the per-draw data, rewritten only after the slot's fence wait) and every lit draw names that copy with the dynamic offset of the frame set's second binding; each ring chunk holds at most one copy per version. A second update in the same frame therefore costs one more 752-byte copy at the next lit draw, and a frame with one update costs one per chunk. The alternative, one buffer per frame slot, is written only after the fence wait but needs this ring copy anyway for a second update within a frame, so it would have been two mechanisms. Decided with the stage C brief on #43 (2026-10-14); the performance of the copy on real hardware is unverified.

Design decision: Vulkan always renders offscreen PR #136

The Vulkan renderer never draws into a swapchain image directly: every frame goes to its own colour and depth images, and a window (stage F) will get a blit of the finished colour image at Present. The editor viewport and the tests need the frame as pixels anyway (ReadFramebuffer), so a design with a second path for "the window" would leave the code the window uses, which only a real GPU could run, different from the code the tests run. With this one, CI on lavapipe exercises everything a window uses except the final blit and present. Decided on #43 (2026-10-14).

Design decision: a text material without an atlas reads a transparent 1x1 texture and so draws nothing PR #165

OpenGL binds a material's base texture only when it is valid, so a text material without an atlas (or whose atlas was destroyed) draws nothing, and the software renderer does the same (SoftwareTextShaderTest.TextWithoutAnAtlasDrawsNothing). Vulkan always binds something: an absent base texture is a renderer-owned 1x1 default, white for the unlit and lit shaders, and for the text shader white would be a signed distance of 1, so the whole quad would be solid text. The text shader's base sampler therefore has its own default, a 1x1 (0, 0, 0, 0) texture made and destroyed with the other defaults: a distance of 0 gives coverage 0, the fragment is discarded and nothing is written, colour or depth. The alternative was to skip such draws in DrawMesh, which needs the material, its texture's registry entry and a kind check at the top of every draw and leaves a second place that decides what an absent texture means; the default keeps the one path that already handles a destroyed texture and costs 4 bytes of GPU memory. Decided in stage E (the brief left both open); tested for no atlas, a texture set back to null, and an atlas destroyed after SetTexture (also when a new texture is made at the destroyed one's address), each drawn with and without a depth-writing state. Real-driver behaviour of sampling a 1x1 texture is unverified.

The WebGPU shaders (WGSL), stage G1 PR #190

Status: the three built-in shaders exist as WGSL, are parity-tested against the shared interface table without a GPU, are validated by Tint and naga in CI, and are embedded as strings for the backend to come. That was all of stage G1: no WebGPU renderer, no N2ENGINE_RENDERER_WEBGPU option. Stage G2 PR #196 added the native harness and the backend's core (below; the native backend exists only for CI, W8 of #155), and still nothing drew with these files (G3a drew with the unlit one, below; stage G3b PR #204 draws with the lit and text ones, below). Not verified: that they draw anything (G2 and G3 run them on Dawn over lavapipe, G5 in real browsers), and that any backend fills the blocks the way they expect (the transposed matrices below).

  • Files. renderer/shaders/webgpu/unlit.wgsl, lit.wgsl and text.wgsl: one module each, with a vertex entry point vs_main and a fragment entry point fs_main, hand-written ports of the Vulkan GLSL (the same maths and constants: the lit port keeps the PBR terms and the environment-BRDF fit, the text port the antialiased fwidth ramp, the unlit port the alpha test).
  • Resources. Group 0 is the frame: binding 0 the per-draw block (uModel, uView, uProjection, 192 bytes), and, in the lit shader only, binding 1 the lighting block (752 bytes). Group 1 is the material: binding 0 the material block (a dynamic offset per draw, a 128-byte range), then the textures at the interface table's bindings 1 to 5 (the base texture uTexture, and for lit uEmissiveTexture, uOcclusionTexture, uNormalTexture, uMetallicRoughnessTexture, the AuxTexture slots in enum order) and their samplers at the same number plus 5 (kSamplerCount), 6 to 10, named like the texture plus Sampler. The unlit and text shaders have only the base texture (binding 1) and its sampler (binding 6). The table in renderer/common/GpuShaderInterface.hpp still holds the Vulkan bindings of the combined image samplers; the WebGPU ones follow from it by that offset, which the parity test checks.
  • Block layout. Every block member has the name and the byte offset the table gives it, and a GLSL int is an i32. The table's std140 offsets are valid WGSL uniform-buffer offsets for these blocks (a vec3 aligns to 16 and a float may follow it; the light structs round up to 32, 48 and 64 bytes, the strides of their arrays, which are multiples of 16 as the uniform address space needs), so one table serves both backends. The text material's members take 92 bytes and WGSL rounds the struct up to 96, inside the 128-byte range.
  • Matrices: transpose on upload. The engine's matrices are row-major. GLSL's row_major block qualifier reads them as they are; WGSL has only column-major matrices and no such qualifier, so a plain copy would read as the transpose. The backend transposes each of the three matrices when it fills the per-draw block (3 x 64 bytes of CPU work per draw); the bytes are then the matrices' columns, mat4x4<f32> reads the real matrices, and the shaders read exactly like the GLSL (uProjection * uView * uModel * v, mat3(uModel)). The other choice, writing the WGSL with row-vector products, was not taken: it needs no CPU work but makes every product read backwards against the GLSL and the table. Nothing fills the block yet (stage G3a does), so the convention is checked only as far as the shaders' product order is.
  • Separate samplers. WGSL has no combined image sampler: each Vulkan sampler2D is a texture_2d<f32> plus a sampler, sampled with textureSample(uTexture, uTextureSampler, uv). The one-channel text atlas is r8unorm, which samples as (r, 0, 0, 1); the shader reads .r.
  • inverse(). WGSL has no matrix inverse; lit.wgsl has inverse3, the 3x3 adjugate (the cross products of the columns, as rows) over the determinant, and the normal matrix is transpose(inverse3(mat3(uModel))) as in the GLSL, so a mirroring model matrix flips the normal exactly as GLSL's inverse does. A singular matrix gives non-finite numbers, as in GLSL.
  • Clip space. The engine's projection gives OpenGL clip space (z from -w to w), so each vertex shader remaps z = (z + w) / 2 as the Vulkan ones do. WebGPU's clip space is y up with row 0 of the framebuffer at the top, which is what Vulkan gets from its flipped viewport, so there is no y flip in the WGSL (and WebGPU does not allow a negative viewport). Culling and winding are pipeline state, for G3.
  • Uniformity. WGSL's uniformity analysis rejects textureSample and fwidth in non-uniform control flow, and a loop left by a non-uniform continue is non-uniform afterwards. The text and unlit shaders already sample at the top or under a condition on a uniform-buffer value (a material flag). The lit shader samples all five textures up front, each under such a flag, before its alpha-test discard and before the lighting loops (whose continue depends on the distance to the light), and uses the results where the GLSL sampled; a flag that is 0 skips the sample, as in the GLSL. The parity test keeps every textureSample and fwidth before the first discard (and the lit ones before the first loop); Tint's analysis is the proof that the rest is valid.
  • Embedding. renderer/CMakeLists.txt writes renderer/webgpu/WgslSources.hpp into the build tree at configure time (no tool, so native and web builds are alike; a changed .wgsl re-runs the configure, and the header is rewritten only when its text changes): Renderer::WebGpu::Wgsl::kUnlitWgsl, kLitWgsl and kTextWgsl as std::string_views, each cut into raw string literals of at most 8000 characters (MSVC's limit for one literal is 16380). The header-only target renderer_webgpu_shaders carries its include directory. Nothing links it but renderer_tests, which checks that the embedded text is the files' text.
  • Validation in CI. The job wgsl (Tint, naga) in tests.yml (not a required check, ubuntu-24.04, 20-minute timeout, no engine build; it needs changes and skips on a docs-only pull request like the jobs above) runs scripts/validate-wgsl.sh on the three files with two pinned tools, installed by scripts/install-wgsl-validators.sh. Tint (the WGSL compiler of Chrome and Edge) is bin/tint from Dawn's own prebuilt release archive (tag v20261016.190333, commit 67d4d6e, the ubuntu-latest Release build), its SHA-256 pinned and checked, not built here. naga (Firefox's) is naga-cli 30.0.1 built from its crates.io source package, the package's SHA-256 pinned and checked, with cargo install --locked so the package's own Cargo.lock decides every dependency, on a pinned Rust toolchain (1.99.1, through rustup, so a runner image update cannot change the compiler) (naga publishes no binaries). Tint runs the full front end with uniformity analysis, the SPIR-V writer with spirv-val (--validate) and a WGSL round trip; naga parses, validates and writes SPIR-V, MSL, HLSL and WGSL. Any non-zero exit, and any line starting with a warning, fails the job. So that it can fail at all, the script also requires the tools to reject the files in scripts/wgsl-negative/ (a type error: both tools; a derivative in non-uniform control flow: Tint only, because naga's analysis lets it through), each for the reason it exists (the tool's message is matched, and Tint runs with the same --ep and --validate flags as the real steps, so a bad flag cannot pass for a rejection). Cost: about one minute of runner time on a cache hit (the Tint download is seconds, the validation itself under a second). On a cold cache the job also installs the pinned Rust toolchain and builds naga: an earlier measurement, before the toolchain was pinned, was 60 s for the whole job (the naga build 49 s), and the toolchain install adds to that, so allow a few minutes; the cache is keyed on the install script, so it is cold only after that script changes. Both tools are CI tools only: nothing of them is linked or shipped (THIRD_PARTY_NOTICES.md, "Not shipped").
  • Parity test. tests/renderer/webgpu/WebGpuShaderParityTests.cpp reads the WGSL as text (no GPU; it runs on every leg that runs renderer_tests, the web one under node included): see Testing.

Design decision: the WebGPU shaders are hand-written WGSL, tied to the interface table by a parity test PR #190

Browsers take WGSL only. The options were to translate the Vulkan GLSL at build time (GLSL to SPIR-V to WGSL with Tint or naga), to translate at run time in the browser, or to write the WGSL by hand. Build-time translation would need Tint or naga in every web build, and the current GLSL hits what the translators handle least well (row_major blocks, combined samplers, inverse(), discard), so it would have to be rewritten for the translator anyway. Run-time translation ships a compiler of megabytes into a size-budgeted wasm, for custom shaders nothing in v1 uses. Hand-written WGSL keeps the web job free of build tools, reads like the GLSL, and writes the WGSL-specific parts (the transposed matrices, the separate samplers, inverse3, uniformity) once. The cost is a third copy of each shader (OpenGL's GLSL 330, Vulkan's GLSL 450, WGSL) that can drift: the parity test checks the interface (names, bindings, offsets, attribute locations) and the maths the ports must keep, not the maths in general, so the cross-backend goldens of the stages to come are what check the images. Custom WGSL shaders are not in v1, like custom GLSL on Vulkan. Decided on #155 (2026-10-20), W1, with W9 (v1 is the built-in shaders only).

Design decision: Tint and naga validate the WGSL in a small non-required job, from pinned and hash-checked tools PR #190

No compiler checks the WGSL in the normal builds, so a typo would first show in a browser. Chrome and Edge run Tint and Firefox runs naga, so both validate the files; Safari's WebKit has its own WGSL compiler, which has no CI path (a check by hand, stage G5). Where: a job of its own, because it needs no engine build and the required leg linux (Release, x86_64, Clang) must stay as it is; it is not required and follows the docs-only skip, so it adds a check without blocking a merge on a tool download. Tint: building it from Dawn's source needs Dawn's dependency fetch and a long compile, but Dawn publishes prebuilt archives per commit with a bin/tint in them, so the job downloads one (about 36 MB) and checks its SHA-256 against the pin; the Dawn that stage G2's native harness links PR #196 is the same release, from the same archive: the two pins are kept equal, and a CI step checks it. naga: there is no prebuilt binary, so it is built from its crates.io package, whose SHA-256 is pinned, with --locked (the package carries a Cargo.lock); the build is cached keyed on the install script, so a changed pin is a fresh build. What fails it: any error or warning from either tool, and any negative control the tools accept. A bump is a few edited lines in scripts/install-wgsl-validators.sh, with the hashes taken from the files with sha256sum. Decided on #155 (2026-10-20), W1.

The WebGPU backend: native harness and core, stage G2 PR #196

Status: a WebGpuRenderer exists and runs, for CI only: headless initialisation on Dawn's Vulkan backend (Mesa lavapipe in CI), an offscreen colour and depth target, a clearing frame, a synchronous ReadFramebuffer, SetRenderTargetSize, Shutdown with the lifetime token, and a count of every error the device reports that fails the tests. Not there yet at stage G2: meshes, textures, materials, shaders and every draw (stage G3a PR #201 added the resources and the unlit draws, below, and stage G3b PR #204 the lit and text shaders, the scene lighting and blending, below), the browser build (G4, with Emscripten's emdawnwebgpu), the player's canvas, Present and the loader's selection (G5). Not verified: anything on a real GPU or in a browser, performance, and the Emscripten compile of the same source file.

  • The option. N2ENGINE_RENDERER_WEBGPU (root CMakeLists.txt) is OFF by default, forced OFF for the web build until stage G4 (PR #208 forces it ON there, with emdawnwebgpu in place of Dawn: below), and a configure error natively anywhere but Linux x86_64 (Dawn publishes the one archive; the harness is not a shipped renderer). The renderer then compiles renderer/src/webgpu/ (otherwise filtered out of the glob, as Vulkan's is), links Dawn privately, and defines N2ENGINE_RENDERER_WEBGPU=1 (renderer/common/RendererConfig.hpp; unlike Vulkan's, a translation unit that gets no definition sees 0). It is not selectable at run time natively (W8 of #155): until stage G4 there was no RenderBackend::WEBGPU at all, and since G4 PR #208 the engine refuses that value in every native build (only the web player's --renderer webgpu names it, below); nothing in the editor host, lua_project or a project's settings names it, and the tests construct Renderer::WebGpu::WebGpuRenderer directly. The tests are their own program, webgpu_tests (tests/renderer/CMakeLists.txt; renderer_tests does not contain them), so the CI job builds the renderer and these tests; since stage G3b PR #204 the program also links the engine (the golden scenes of G3b draw through Scene::Render, as the Vulkan goldens of renderer_tests do), so the job builds the engine too.
  • Dawn, pinned. cmake/DawnPrebuilt.cmake downloads Dawn's own prebuilt release archive for Linux (Dawn-<commit>-ubuntu-latest-Release.tar.gz: tag v20261016.190333, commit 67d4d6e64b0755d638f76549794692badfdbc8ab, SHA-256 20ff88448def9645ceeff30911e07295aeb433be23e26180c96019b4300bff5a; CMake refuses it on a mismatch), unpacks it into the build tree (with a stamp, so a pin change fetches again), deletes what is not linked (Tint's libraries and the tools), and defines the imported target n2_dawn: lib64/libwebgpu_dawn.a, Dawn's monolithic static library with its Vulkan backend, and the headers under include/webgpu and include/dawn. The archive is a GCC 14 build with the libstdc++ C++11 ABI, position-independent; the job links it with GCC 14. It is the same release the wgsl (Tint, naga) job takes Tint from, so the validator and the renderer's Dawn are one revision; the new job's first step compares the two pins (tag, commit, hash) and fails when they differ.
  • The backend, against the C API. renderer/src/webgpu/WebGpuRenderer.cpp (stage G3a added three more files, below) includes only <webgpu/webgpu.h>: no webgpu_cpp.h, nothing from dawn/native, so stage G4 can compile the same file with emdawnwebgpu. What exists only natively is marked NATIVE ONLY in the source: asking for the Vulkan backend by type (WGPURequestAdapterOptions::backendType), and the blocking waits (wgpuInstanceWaitAny with a timeout, which needs the TimedWaitAny instance feature, and a browser cannot block on a map at all, so a browser readback will be asynchronous; stage G4 PR #208 compiles these parts only natively and gives the browser build an asynchronous ReadFramebuffer, below). Every handle is held by a small reference-counting wrapper that also counts the live references of the process, so a test can see a leak.
  • Initialisation. Initialize(nullptr, w, h) creates an instance (with TimedWaitAny), requests an adapter, then a device with the two error callbacks and its queue, then the targets; an error the device reports while doing so fails the initialisation, and the renderer releases everything it made (InitStatus: NoInstance and NoAdapter are the machine's doing and tests skip on them, Failed is anything else). Adapter selection: Dawn's preferred Vulkan adapter first, then Dawn's fallback adapter; with AdapterPreference::CpuOnly, or by default when N2_WEBGPU_EXPECT_CPU_DEVICE=1, an adapter is kept only if it reports itself a CPU adapter (WGPUAdapterType_CPU: lavapipe, SwiftShader) and the failure message names the variable. (Asking only for the fallback adapter found nothing on lavapipe when tried; the preferred request returns it, typed as a CPU adapter.)
  • Targets and frames. Colour is RGBA8Unorm (usages RenderAttachment, CopySrc and CopyDst: a test writes a pattern into it), depth is Depth32Float (RenderAttachment and CopySrc), both 2D, one mip, one sample, with the default views. BeginFrame opens a command encoder and a render pass that clears colour (the last Clear colour) and depth (1.0); EndFrame ends the pass, finishes the encoder and submits. A Clear inside a frame ends the pass and begins a new, clearing one (a render pass cannot clear part-way, and what the first pass drew is overwritten), so it replaces the frame so far as in the Vulkan renderer. There are no frames in flight to manage: the queue orders the work and Dawn defers destruction. A frame open when the targets are replaced, or the renderer shut down, is abandoned (its pass ended, its commands never submitted). Present logs one warning per renderer: there is no swapchain.
  • Synchronous readback. ReadFramebuffer copies the colour target into a temporary buffer whose rows are padded to 256 bytes (bytesPerRow of a texture-to-buffer copy must be a multiple of 256), maps it, waits for the map (wgpuInstanceWaitAny, at most 10 seconds; on a timeout or an error it logs and writes nothing), and copies the rows out without the padding and in reverse order: texture row 0 is the top of the picture and the interface wants the bottom row first, as glReadPixels and the software and Vulkan renderers give it. Another size than the target's is resampled nearest from pixel centres by the Vulkan renderer's arithmetic. Before the first frame the target reads as zero bytes (a new WebGPU texture is zero), where the Vulkan renderer clears to black first; both are (0, 0, 0, 0). The tests prove the orientation and the unpadding with a per-pixel pattern written through the raw queue (widths 63, 64, 65, 256 and 300: rows of 252, 256, 260, 1024 and 1200 bytes).
  • Sizes. SetRenderTargetSize recreates both textures and fixes the size (Resize and OnResize then do nothing); the same size again keeps the targets; false for a zero dimension (nothing changes), a size over the device's maxTextureDimension2D, a readback that would not fit maxBufferSize, or a lost device, and after a failure the old target is gone and frames are skipped until a later call succeeds, as in the Vulkan renderer. The renderer checks the limits itself, so a refused size is not a WebGPU error.
  • Error counting: the validation-layer analogue. The device is created with an uncaptured-error callback and a device-lost callback. GetValidationErrorCount() is the number of errors since the renderer object was made (not reset by Shutdown or Initialize, so one number covers a test): every uncaptured error (validation, out of memory, internal, unknown) and every device loss the renderer did not cause (GetDeviceLostCount(), IsDeviceLost(); the loss of its own Shutdown, which destroys the device, is expected and not counted). The first 32 messages are kept (GetValidationMessages()) and each is also logged to stderr. Dawn delivers errors asynchronously, so the count first processes events and waits for the queue to go idle (at most 5 seconds): an error caused by an earlier call is counted when the call returns. A lost device skips frames and writes no readback; a new Initialize makes a new device. ResetValidationErrors() is for the tests that provoke an error on purpose. The tests fail on any error: the fixture checks the count of every renderer a test made at teardown, and the negative controls prove it can be non-zero: a buffer with no usage and a texture of no size, made through the raw device (GetDeviceForTest()), are counted and kept with their text, and destroying the raw device is counted as one loss.
  • Shutdown and leaks. Shutdown abandons an open frame, has the device deliver what it holds, marks the coming loss as expected, releases the frame objects, releases every resource of stage G3a, destroys the target textures, releases the queue, destroys the device (its loss callback arrives, expected), processes events, and releases the device, the adapter and the instance; then it expires the lifetime token (EndLifetime, as the Vulkan renderer: a renderer initialised again is a new one for everything holding the old token), and it is safe twice or before Initialize. Design decision: Dawn is a pinned prebuilt release, not built from source PR #196

The native harness needs Dawn's library and C headers. The options were to build Dawn from source (FetchContent with Dawn's dependency fetch, or its pinned submodules) or to take the prebuilt archive Dawn publishes per release. A source build needs the dependency set Dawn normally gets with depot_tools (about a dozen repositories at their own pinned revisions), a compile of Dawn, Tint, Abseil and SPIRV-Tools that was estimated at 15 to 30 minutes of a cold CI cache, and a cache to tune. The prebuilt archive is one 36 MB file with the monolithic library and the headers built from one commit, checked by SHA-256, with nothing to compile; the Tint binary the shader job already pins is in the same archive, so one revision serves both. The costs: Linux x86_64 only (fine for a CI harness), the build options are Dawn's (the library carries OpenGL ES and Null backends the harness does not use, and no D3D or Metal), no way to patch Dawn, and the archive is built by Dawn's workflow with its compiler (GCC 14 with the libstdc++ ABI), so a toolchain with another standard library would not link it. Decided on #155 (2026-10-20), W2 (Dawn over lavapipe in a new non-required job) and W8 (CI only); the prebuilt form is this stage's choice within them.

Design decision: every device error fails the tests, counted by the renderer; the readback blocks natively PR #196

The Vulkan tests run with the validation layer on and fail on any message. WebGPU has no layer: a mistake is an uncaptured error delivered to a callback, in a browser as in Dawn, and a program that ignores it renders wrong or nothing. So the renderer counts them (and unexpected device losses) in the callbacks it creates the device with, and the fixture fails any test whose count is not zero, with the messages; the negative controls keep that check honest. Delivery is asynchronous, so the count flushes first. The readback waits (wgpuInstanceWaitAny with a timeout) because every other backend's ReadFramebuffer is synchronous and the golden tests of the stages to come are written against that; in a browser a map cannot be waited for, which is why that wait is the part marked native-only and why the player will present to a canvas instead of reading back (the design's section 4.3). The depth target is Depth32Float, not the design's depth24plus: only the 32-bit float format can be copied out, which the tests use to check the depth clear, and its precision does not depend on the implementation. Decided on #155 (2026-10-20), W2, W8.

The WebGPU backend: resources and unlit drawing, stage G3a PR #201

Status: the native harness draws. WebGpuRenderer makes meshes (with the in-frame UpdateMesh rule), textures (RGBA8, R8, RG8, sRGB, samplers, CPU-generated mip chains) and materials, keeps a pipeline cache, a bind-group cache and a per-draw uniform ring, and draws with the unlit built-in shader: DrawMesh, DrawMesh with an IndexRange and DrawObjects, with each draw's depth test, depth write and cull state. The frames agree with the software renderer's (exactly, or within 2/255 where triangle edges or filtering are involved: the tests). Not there at G3a (stage G3b PR #204 added them, below): the lit and text shaders (GetStandardLitShader and GetStandardTextShader returned null and logged once per renderer), blending (RenderState::blend and additive were in the pipeline cache key already, but every pipeline was opaque and a draw that asked for blending logged one line) and scene lighting (UpdateSceneLighting was ignored: only the lit shader reads it). Not there: custom shaders (CreateShaderProgram returns null and logs, as on the other GPU backends), wireframe (not in core WebGPU: SetWireframe(true) is ignored with one log line, W9 of #155), the browser build (G4, with emdawnwebgpu) and the canvas, Present and the loader's selection (G5). Not verified: a real GPU or a browser, performance, the Emscripten compile of these files, and recovery from a lost device beyond a new Initialize (below).

  • Files. renderer/src/webgpu/ now has three source files and a private header, all against the C API (<webgpu/webgpu.h> and the generated renderer/webgpu/WgslSources.hpp; no Dawn C++ header): WebGpuRenderer.cpp (device, targets, frames, readback: stage G2), WebGpuResources.cpp (meshes, textures, samplers), WebGpuDraw.cpp (the shader modules, bind-group layouts, materials, pipelines, the uniform ring, the draws) and WebGpuInternal.hpp (the handle wrappers, the error counters, the mesh, texture and shader classes and the renderer's State; never included from a public header). The renderer target links renderer_webgpu_shaders (stage G1's generated header) privately, and the modules are made from Wgsl::kUnlitWgsl (G3a) and, from stage G3b, kLitWgsl and kTextWgsl.
  • Meshes. CreateMesh makes a vertex buffer of Common::Vertex (64 bytes each; usage Vertex, CopyDst, CopySrc) and, when there are indices, a uint32 index buffer (Index, CopyDst, CopySrc), and writes both with wgpuQueueWriteBuffer. It returns null for no vertices, for a size over the device's maxBufferSize (checked by the renderer, so it is not a WebGPU error), and for an uninitialized or lost renderer. A mesh with vertices and no indices has an index count of 0 and no index buffer, and draws nothing, as on the other backends. Nothing is deferred. DestroyMesh, DestroyTexture and the replacement of a mesh's buffers only release the renderer's reference: WebGPU keeps an object alive for every command that was recorded or submitted with it, so the Vulkan backend's retire lists, frame slots and fences have no counterpart here, and wgpuBufferDestroy and wgpuTextureDestroy are deliberately not used for them (they would invalidate the open frame's commands). A destroyed or foreign pointer is only looked up in the renderer's registry, never dereferenced.
  • The in-frame UpdateMesh rule. A queue write runs on the queue's timeline when it is made, before the open frame's command buffer, which is submitted at EndFrame. So writing into a buffer that an earlier draw of the same frame reads would change what that draw shows. Each mesh remembers the serial of the last frame it was drawn in (BeginFrame counts it up). UpdateMesh on a mesh that was drawn in the frame being recorded makes new buffers (the earlier draws hold the old ones); on any other mesh, inside a frame or outside one, it writes in place when the vertex and index counts are unchanged and makes new buffers when they are not. Once a mesh was drawn in a frame the flag stays for the rest of that frame, so a second update in the same frame makes new buffers again (correct, not minimal). The tests see both paths by buffer handle (GetMeshInfoForTest) and by pixels (an update between two draws of one frame leaves the first draw with the old vertices).
  • Textures. One channel is R8Unorm and two is RG8Unorm (WebGPU samples them as (r, 0, 0, 1) and (r, g, 0, 1), so there is no swizzle), three are expanded to RGBA8 with alpha 255, four are RGBA8; TextureOptions::srgb picks RGBA8UnormSrgb for three and four channels (one and two ignore it, as on OpenGL and Vulkan) and is always available, so there is no fallback to UNORM. The colour target is RGBA8Unorm, so a sRGB texel is decoded when it is sampled and the result is stored as it is, without an encode. This is the one place the backends differ by design: the GPU decodes before it filters, the software renderer decodes after (through a table), so a linearly filtered sRGB texture is not compared with the software frame (a nearest one is, and agrees within 1/255). Uploads are wgpuQueueWriteTexture per mip level with tightly packed rows: a queue write needs no 256-byte row alignment (that rule is for buffer-to-texture copies), so the alignment is handled where a copy is made, the readback of a frame, a mesh and a texture level, whose rows are padded to 256 bytes and unpadded. The tests read textures back through those padded rows with widths 37, 70, 5 and others. A size over the device's maxTextureDimension2D returns null (logged, not a WebGPU error). Each texture gets an id from a counter that never repeats; a material remembers the id of the texture it was given, so a texture made at the address of a destroyed one is not taken for it (the slot gets the default).
  • Mip chains are made on the CPU. Core WebGPU has no blit, so with options.mipmaps the renderer builds the whole chain (1 + floor(log2(max(w, h))) levels, each max(1, size / 2)) when it uploads: each texel of the next level is the equal-weight average of the texels it covers, rounded half up. For the usual halving that is exactly the 2x2 box; for an odd size the covered ranges overlap by one texel (5 to 2 averages texels 0-2 and 2-4). A sRGB texture is averaged in linear light (the colour channels through a decode table, re-encoded; the alpha channel as it is), so a black-and-white pair averages to 188, not 128. This differs from Vulkan's vkCmdBlitImage chain for sizes that are not a power of two (the blit samples a scaled rectangle); the two are not compared, and the tests check the chain against a CPU reference and check the level the sampler's LOD picks (a minified texture shows level 1 of the CPU chain). The software renderer has no mipmaps at all.
  • Samplers are cached by (min and mag filter, mipmap filter, address mode): a nearest texture gets a nearest mipmap filter and a linear one a linear mipmap filter, repeat or clamp-to-edge on U, V and W, no anisotropy, LOD clamped to 0..32. Equal options share one sampler, which the renderer owns until it shuts down.
  • Materials and the shader. CreateMaterial is the shared Gpu::BlockMaterial of stage G0 (values written by name into a CPU copy of the shader's std140 block through GpuShaderInterface.hpp, snapshot at each DrawMesh, so a change after a draw does not affect that draw; an unknown name or the wrong type logs once and is ignored). At G3a only the unlit shader existed (stage G3b added the other two, below): one module with vs_main and fs_main each, made at Initialize; a WGSL error would be reported by the device and fails the initialisation like any device error. CreateMaterial returns null for any other shader (logged once). GetStandardUnlitShader is null before Initialize; IsValidShader is true only for the built-ins that exist; UseShaderProgram does nothing and DestroyShaderProgram is always false.
  • Resource layout. Two groups for every shader, so the lit and text shaders of G3b need no layout of their own: group 0, binding 0, the per-draw block (192 bytes: model, view, projection) in a uniform buffer with a dynamic offset (and, from G3b, binding 1, the lighting block, below); group 1, binding 0 the material block (a dynamic offset, 128 bytes bound: kMaterialBlockRange), bindings 1 to 5 the base texture and the four AuxTexture slots, bindings 6 to 10 their samplers. The unlit WGSL reads bindings 1 and 6 only; the layout is a superset, which WebGPU allows. A slot a material leaves empty gets a 1x1 default texture the renderer owns (white base, black emissive, white occlusion, flat normal (128, 128, 255), white metallic-roughness; nearest, clamped, no mips), and so does a texture that was destroyed after the material took it.
  • The uniform ring. A draw needs a per-draw block and a material block. Each takes an aligned slot in the current ring chunk, a uniform buffer (usage Uniform, CopyDst; 256 KiB by default, a bigger one when a single draw needs more) with a CPU copy beside it, and the draw writes into the CPU copy. EndFrame writes the used part of every chunk with one wgpuQueueWriteBuffer before it submits, and the next frame starts again from the first chunk. The slot size is AlignUp(192, A) + AlignUp(128, A) with A the device's minUniformBufferOffsetAlignment (read from the limits; 256 where it cannot say), so every dynamic offset is a multiple of it and no draw of a frame overwrites another's blocks; a full chunk makes the frame continue in the next, a new one if there is none, so any number of draws works (offsets are 32-bit, so a chunk stays under 4 GiB and under the device's buffer limit, else the draw is skipped with a log line). Why reuse across frames is safe: the writes of frame N+1 come after frame N's submit on the queue's timeline, so frame N has read its blocks by then. Chunks are kept until Shutdown. CreateDevice also checks that the device's limits are at least what this layout needs (at G3a a 192-byte uniform binding, two dynamic uniform buffers, two bind groups, eleven bindings and five textures and samplers per stage; stage G3b raised it, below), which every WebGPU device meets, and fails the initialisation otherwise.
  • Matrices. The engine's matrices are row-major and WGSL's are column-major. Each of the three is transposed once, when the draw fills its per-draw block (WriteTransposed: the bytes become the matrix's columns, which is what mat4x4<f32> reads), and nothing else transposes: the WGSL multiplies as the GLSL does and remaps clip-space z from GL's -w..w to WebGPU's 0..w (stage G1). The tests move a quad by a translation given in the model matrix, in the view, in the projection and in both (they add), which a missing or doubled transpose would break.
  • Bind groups are immutable and cached. Group 0 is made once per ring chunk. Group 1 is cached by (ring chunk, the five texture ids), so draws with the same textures in the same chunk share one, and it is dropped when a texture it names is destroyed (a draw recorded earlier keeps its own reference). A frame of any number of draws with the default textures makes one group 1 per chunk.
  • Pipelines are made on first use and cached by (shader, vertex layout, depth test, depth write, cull, blend, additive). The vertex layout is the shader's attribute set (ShaderInterface::Attributes: position, texture coordinates and colour for unlit and text, all five for lit) over one interleaved 64-byte buffer; it follows from the shader today and is a key field so another layout can never share a pipeline. Depth: compare Less (GL's default) with the test on and Always with it off, depth written only while the test is on (the key stores the effective write, so a test-off, write-on draw shares the pipeline of test-off, write-off). Cull: back, front or none, counter-clockwise front faces (WebGPU's CCW is GL's, seen on the screen). There is no viewport or scissor call: the interface has none, and the pass covers the whole target. Only a null handle from pipeline creation (which Dawn and browsers do not normally return; a pipeline that fails validation comes back as an error object) is remembered per key, logged once and skipped without retrying; a validation failure instead surfaces through the error counter and invalidates that frame's command buffer, and catching it earlier needs an error scope or async creation (G7). Creation is synchronous, which stalls the first draw of a state in a browser (the design leaves pre-warming and async creation to G7). With blend off there are at most 9 distinct pipelines per shader (3 depth states times 3 cull modes); at G3a the keys with blend on added 18 more that were the same opaque pipeline, and since stage G3b they are real (below).
  • Drawing. A draw is recorded into the open frame, in submission order (SetPipeline, two bind groups with one dynamic offset each, the vertex and index buffers, DrawIndexed), and takes a snapshot of the material and of the view and projection current at the call (SetViewProjection, identity until set, null arguments ignored). It is ignored without a message outside BeginFrame..EndFrame, for a null or foreign mesh, material or model matrix, for a mesh without indices, when the pipeline could not be made, and on a lost device. DrawMesh with an IndexRange draws [first, first + count) and nothing for a count of 0 or a range that is not inside the mesh's indices (the sum is taken in 64 bits), as OpenGL and Vulkan do; the software renderer clips such a range instead. DrawObjects is DrawMesh of each object's mesh, transform.model, material and state in order (the object's own view and projection are not used, as on Vulkan).
  • Lifetime and device loss. Shutdown releases every mesh, texture, material, pipeline, bind group, ring chunk and sampler (all handles, before the targets and the device), then the device as before, and expires the lifetime token. Initialize again without a Shutdown does the same first, so it is a new renderer for everything holding the old token: the engine's GpuCache re-acquires its meshes, textures and materials through that token (its entries are replaced when their token has expired), which is the recreation path on this backend as on Vulkan. When the device is lost, the renderer counts the loss as an error, skips frames, fails every new resource call (null or false) and ignores draws; destroying what was made before is harmless. Nothing re-acquires the device by itself in G3a (the design's one re-acquisition and the player's fallback are stage G5); the test injects the loss by destroying the raw device, then checks the failures, that a new Initialize expires the token, that the old pointers are foreign to the new device and that new resources draw. The test does not run GpuCache itself (the golden scenes of stage G3b link the engine but never lose a device): its token behaviour is covered by its own tests and by the token assertions here.
  • Test hooks (in WebGpuRenderer.hpp, borrowed handles): GetMeshInfoForTest, ReadMeshForTest, GetTextureInfoForTest, ReadTextureForTest (any mip level, tightly packed), GetTextureIdForTest, SetMaterialTextureIdForTest (forges a stale id), GetMaterialBlockForTest, the live mesh, texture and material counts, GetPipelineCountForTest, GetPipelineCreateAttemptCountForTest, CreatePipelineForTest, SetFailPipelineCreationForTest, GetBindGroupCountForTest, GetRingChunkCountForTest, SetRingChunkBytesForTest and GetUniformAlignmentForTest.

Design decision: UpdateMesh writes in place unless the mesh was drawn in the open frame PR #201

The design (section 4.3 of the proposal for #155) named the hazard: a queue write lands before the frame's commands are submitted. The options were to always make new buffers on update (simple, one allocation per update, which text meshes make every change), to write in place and submit the frame first when a drawn mesh is updated (which splits the frame), or the rule chosen: a per-mesh "drawn in this frame" flag, new buffers only when it is set. The flag costs one integer per mesh and one comparison per update, keeps the common case (an update before the mesh is drawn, or between frames) allocation-free, and is cheap to test through buffer handles. It is conservative (the flag stays set for the frame). Decided on #155 (2026-10-20), the design table of section 4.3.

Design decision: the uniform ring is CPU-staged, one queue write per chunk, dynamic offsets PR #201

The Vulkan ring is persistently mapped host memory with a descriptor set per chunk and frame slot. WebGPU has no persistent mapping on the queue path and no frames in flight to slot, so the options were a wgpuQueueWriteBuffer per draw (a copy and a call per draw), buffers made mappedAtCreation every frame (an allocation per frame), or the design's table: fill a CPU copy and write it once per chunk before the submit, with dynamic offsets into immutable bind groups. The last needs no per-frame allocation after the first frames, makes the frame's bind groups reusable across frames, and its only cost is the CPU copy (256 KiB per chunk). Alignment follows the device's limit, not 256, so a device that reports a smaller alignment wastes less. Decided on #155 (2026-10-20), the design table of section 4.3.

Design decision: mip chains are generated on the CPU at upload PR #201

Core WebGPU has no blit, so the Vulkan vkCmdBlitImage chain has no direct equivalent. The options were a render-pass downsampler per texture (a pipeline, a pass per level and a layout of its own), compute (not core in v1: W9), or the CPU: the design recommends a box filter at upload, in linear light for sRGB, because it is simple and testable without a GPU reference. It costs CPU time and one extra copy per level at upload, and for sizes that are not a power of two it differs from the Vulkan blit chain. Decided on #155 (2026-10-20), the design table of section 4.3 ("recommended, simple and testable").

The WebGPU backend: lit shading, blending and text, stage G3b PR #204

Status: the native harness draws everything the software renderer draws, through the three built-in shaders. WebGpuRenderer now has the lit shader (the aux textures, Blinn-Phong or metallic-roughness PBR, the scene lighting of UpdateSceneLighting), the text shader (the antialiased SDF shader with outline, shadow and softness), real blend states (alpha blending and additive), and a SetViewProjection that may change between the draws of one frame. The goldens of the Vulkan backend (meshes, a model, lighting, normal maps and PBR, edit-mode lighting, particles, UI images, a world canvas, blending, text) run on it, in ports that compare with the software renderer under the tolerances the Vulkan tests use. Not supported (W9 of #155): custom shaders (CreateShaderProgram returns null and logs once), wireframe (not in core WebGPU: SetWireframe(true) is ignored with one log line) and compute. Not verified: a real GPU or a browser (only Mesa lavapipe through Dawn ran these), performance, pipeline-creation stalls in a browser (creation is synchronous, as at G3a) and the Emscripten compile (G4). At G3b the option was still OFF by default and CI-only (W8): nothing outside webgpu_tests named the backend (stage G4 compiles it into the web build, below).

  • Shaders. All three modules (Wgsl::kUnlitWgsl, kLitWgsl, kTextWgsl, each with vs_main and fs_main) are made at Initialize; a WGSL error is a device error and fails the initialisation. GetStandardLitShader and GetStandardTextShader return them (null before Initialize), CreateMaterial takes any of the three, IsValidShader is true for all three. Nothing logs "not implemented yet" any more. The pipeline layout is still the one of G3a (a superset every shader fits), so no shader has a layout of its own: the vertex layout of a pipeline is the shader's attribute set (ShaderInterface::Attributes), all five attributes for lit and position, texture coordinates and colour for unlit and text.
  • The lit material is the shared Gpu::BlockMaterial (OpenGL's defaults, values by name into the 72-byte std140 block, a snapshot at every DrawMesh): the base texture and the four AuxTexture slots (emissive, occlusion, normal, metallic-roughness) take bindings 1 to 5 of group 1 with their samplers at 6 to 10, exactly the layout G3a made. A slot a material leaves empty, or whose texture was destroyed, reads the renderer's 1x1 default (white base, black emissive, white occlusion, flat normal, white metallic-roughness), as on Vulkan. The uHas*Texture flags are the caller's, as on OpenGL and Vulkan: Material::ApplyUniforms sets them.
  • The lighting block. Group 0 gets binding 1, the 752-byte lighting block (kLightingBlockSize), a uniform buffer with a dynamic offset like binding 0, visible to both stages; the unlit and text WGSL do not declare it and the layout is a superset, which WebGPU allows. UpdateSceneLighting builds the block with BuildLightingBlock (the shared function of stage C: the caps of 2, 8 and 4 lights, the spot lights with no axis dropped, uEncodeOutput for linear lighting) into a CPU copy and bumps a version; it touches no GPU memory and works inside or outside a frame. The first lit draw after an update copies the block into the ring, after that draw's material block, and every lit draw names the copy with the dynamic offset of binding 1: one copy per ring chunk per version. So a draw uses the lighting set by the last UpdateSceneLighting before it, and an update after a draw does not change that draw, as on OpenGL and Vulkan. A draw that does not read the lighting (unlit, text) names the chunk's copy if it has one, else offset 0, which is in range and never read: a chunk is never smaller than the aligned lighting block (the chunk size is at least 752 bytes rounded up to the alignment), because WebGPU validates the bound range against the buffer even for a draw whose shader ignores it. Every chunk's copy is forgotten at BeginFrame and EndFrame (a copy of an earlier frame is not this frame's). Before the first update the block holds SceneLightingData{} seen from the origin (the software renderer's defaults); Shutdown and a new Initialize reset it. The lit shader encodes its own output when lighting is linear, because the colour target is UNORM (forceShaderEncode therefore changes nothing, as on Vulkan); sRGB textures decode when they are sampled (rgba8unorm-srgb).
  • Blending is OpenGL's ApplyRenderState and Vulkan's pipeline: with RenderState::blend the colour target blends with source factor SRC_ALPHA and destination factor ONE_MINUS_SRC_ALPHA (ONE when additive), the same factors for colour and for alpha, equation ADD, so the target's alpha is blended too; without blend an additive flag changes nothing (an opaque draw that shares the opaque pipeline, alpha written as the shader gives it). Depth is unchanged from G3a: compare Less with the test on and Always with it off, depth written only while testing, which is how the Transparent queue's state (blend, no depth write) works. The order of transparent draws is the caller's: the renderer draws in submission order and sorts nothing; Scene::Render draws the Transparent queue back to front, and a test proves the order reaches the target (far then near, not the hierarchy order). The pipeline key already held blend and additive; there are at most 3 blend states times 3 depth states times 3 cull modes per shader.
  • Mid-frame SetViewProjection. Each draw copies the view and projection current at the call into its own ring slot (G3a's design: the per-draw block holds model, view and projection), so a later SetViewProjection, the UI pass and a world canvas, which change the matrices in the middle of a frame, never alter an earlier draw's. Tested with one draw per cell of a grid, each with its own view, over many ring chunks, for the unlit and the lit shader.
  • Text. The text shader is the OpenGL shader's port (G1): the coverage ramps over about one pixel around the 0.5 iso-line of the SDF atlas (fwidth), the outline, shadow and softness effects are material values (all 0 when off), and a fragment whose result alpha is below 0.01 is discarded (no colour, no depth). The atlas is the material's base texture (r8unorm, sampled as (r, 0, 0, 1)). The effects are snapshotted into the ring at every DrawMesh, so the multi-pass text effects (one material and mesh, the uniforms changed between DrawMesh calls, the face last) draw each pass with its own values in one frame, as on Vulkan. Atlas-less text: OpenGL binds the base texture only when it is valid and so draws nothing without one, so a text material whose atlas is absent or was destroyed reads a renderer-owned 1x1 (0, 0, 0, 0) texture (made at Initialize with the other defaults): sdf 0, coverage 0, the fragment is discarded. Text meshes that change are updated through UpdateMesh, with the in-frame rule of G3a. Text is blended per the draw's state and the engine draws it in the Transparent queue; a glyph edge is a blend of the text colour and what is behind it, where the software renderer alpha-tests (how the tests compare them). UI (UISystem, Image), world canvases and particles need nothing beyond these: they are unlit or text draws with blending, a second view and projection, and UpdateMesh.
  • The limits check at Initialize is raised for the lighting block: a uniform binding of at least max(192, 752) bytes (maxUniformBufferBindingSize; the core default is 65536), three dynamic uniform buffers per pipeline layout (per-draw, lighting, material; maxDynamicUniformBuffersPerPipelineLayout, default 8) and three uniform buffers per shader stage (maxUniformBuffersPerShaderStage, default 12), two bind groups, eleven bindings in a group and five sampled textures and five samplers per stage, as at G3a. A device below them fails the initialisation with a message naming the numbers; every WebGPU device meets the core defaults.
  • Test hooks added: GetLightingBlockForTest (the CPU copy of the lighting block as the next lit draw would copy it). The pipeline hooks now serve all three shaders (CreatePipelineForTest returns true for lit and text).

Design decision: the lighting block is copied into the uniform ring, one copy per chunk per version PR #204

The lit shader reads the scene lighting, which the engine updates in the middle of a frame (the tests call UpdateSceneLighting inside a frame, as the engine does before the scene pass), and a draw must see the lighting of its time, as on OpenGL, where a uniform set before a draw stays for that draw. The options were one lighting buffer written with wgpuQueueWriteBuffer at each update (a queue write lands before the frame's commands are submitted, so every draw of the frame would see the last update: wrong for a second update in a frame), a copy of the block in every draw's slot (752 more bytes per draw, copied again and again for no change), or the Vulkan backend's rule: one copy per ring chunk per version, made by the first lit draw after an update and named by a dynamic offset. The last costs a CPU copy of 752 bytes per update that a lit draw follows, needs no extra buffer and no per-frame allocation, and keeps every draw's lighting immutable once recorded. Its price is a second dynamic binding in group 0 that unlit and text draws must also bind (at an offset in range); that is why a ring chunk is never smaller than the lighting block. Decided in stage G3b (the design table of section 4.3 of the #155 proposal lists the lighting block as reused as is, and does not say how it reaches the GPU).

Design decision: blending follows OpenGL exactly, and the renderer never sorts PR #204

The software renderer cannot blend, so OpenGL is the reference (ApplyRenderState): glBlendFunc(GL_SRC_ALPHA, additive ? GL_ONE : GL_ONE_MINUS_SRC_ALPHA), which sets the same factors for colour and alpha, so the target's alpha is blended. The WebGPU blend state is set the same way (the common alternative, a separate alpha equation that keeps destination alpha, would differ from OpenGL and Vulkan in the stored alpha, which the readback shows). Ordering is not the renderer's business on any backend: the engine's Scene::Render sorts the Transparent queue back to front, and the renderer draws in submission order (a test checks that order reaches the target). Decided in stage G3b, the plan's "blend/additive/Transparent ordering semantics as the software and Vulkan renderers define".

Design decision: webgpu_tests links the engine, so the golden scenes are the Vulkan ones PR #204

The Vulkan goldens for particles, UI images, world canvases, text, models and meshes are scenes of the engine (Scene::Render, MeshRenderer, ParticleSystem, UISystem, TextDrawing), not calls on the renderer. To run the same scenes on WebGPU the test program links the engine, which makes the webgpu (Dawn, lavapipe) job build it (G2 and G3a built the renderer and the tests only). The alternative was to redraw the scenes by hand against IRenderer, which would test the renderer but not the engine's use of it (the second view and projection of the UI pass, UpdateMesh every frame, the Transparent queue's sort, multi-pass text), and would be a second copy of every scene. The cost is the engine's compile in this job (measured in the CI section); the job is not a required check. The tests are ports of the Vulkan files, kept as close as the backends allow, so a change in a scene can be carried over by a diff.

Software wireframe

SoftwareRenderer::SetWireframe(true) draws a one-pixel inward band along each triangle's boundary; its interior writes neither colour nor depth. The option is copied when DrawMesh records a draw, including indexed subranges, so solid and wireframe draws may share a frame and a later toggle cannot change submitted work. The boundary pixels use the normal material, textures, lighting, alpha tests, face culling and depth state. Turning the option off restores filled triangles.

Homogeneous clipping produces a convex polygon. Wireframe shows that polygon's boundary, including the new clipping edges, without the internal diagonals introduced by fan triangulation. Every fan triangle checks the complete polygon boundary, preserving the band even beside a very narrow fan wedge. Collapsed projected edges are ignored. The software result uses the existing top-left coverage rule, has no antialiasing or configurable line width, and does not promise the exact pixels of GPU line rasterization. Degenerate triangles draw nothing. It still scans the triangle's bounded pixel area, so wireframe reduces shading work rather than guaranteeing faster rasterization.

The software renderer's headless mode PR #51

SoftwareRenderer::Initialize(nullptr, width, height) starts the software renderer without a window. It makes no GL or GLFW call at all: no context, no glad, no blit texture or shader. Everything else is as with a window:

  • Frames are recorded between BeginFrame and EndFrame and rasterized on the render thread into the CPU colour and depth buffers, with the same shaders and draw order.
  • Present only waits for the frame to finish (with a window it then uploads and draws it).
  • ReadFramebuffer(buffer, width, height) waits for the frame in flight, then copies the colour buffer as RGBA8, 4 bytes per pixel, bottom row first, the row order of glReadPixels. A size other than the renderer's is resampled, nearest. This also holds with a window. OpenGL's ReadFramebuffer gives the same layout, RGBA bottom row first PR #85 (it gave BGRA before), but reads the framebuffer's bottom-left region without resampling; Vulkan reads back its offscreen target, all black before its first frame, and resamples a different size nearest like the software renderer PR #136. See Rendering at a fixed size.
  • Resize waits for a frame in flight before reallocating the buffers (with or without a window).
  • Shutdown stops the render thread and frees every resource; it deletes GL objects only if it created them, so it is safe headless, without Initialize, and twice. Destroying the renderer without Shutdown still stops the render thread first.

The built-in unlit, lit and text shaders exist from construction, so they are valid before Initialize. Window uses headless mode for a headless application on the software renderer, which then has no window at all PR #89 (the no-window path); otherwise it is for tests and tools that construct a SoftwareRenderer themselves. The golden-image tests use it (Testing).

Design decision: a headless software renderer for pixel tests PR #51

The CI runner has no GPU, so neither OpenGL nor a windowed software renderer can start there, and until now no test saw a pixel. The software renderer only uses GL to show its finished CPU image; rasterizing never needed it. So a null window skips exactly the GL parts (loading GL, the blit resources, the upload in Present) and nothing else, and the frames tests render go through the same render thread, draw ordering and shaders as a windowed frame. A separate offscreen class or a mock would have tested something other than what runs. ReadFramebuffer waits for the frame itself so a test can't read a half-rasterized buffer, and keeps glReadPixels' bottom-up rows so the editor and tests see one row order on every backend. Decided on #1 (Q11).

The software renderer's frame in flight PR #55

EndFrame hands the frame's draws to the render thread, which rasterizes them while the main thread goes on to the next frame, until Present (or ReadFramebuffer, Resize, UpdateMesh) waits for it. What the main thread may do meanwhile:

  • Material uniforms are taken at DrawMesh, as on OpenGL. DrawMesh copies everything the software shaders read from the material into the draw (SWMaterialSnapshot): uAlbedo, uSmoothness, uAlphaCutoff PR #65, the texture (when it has pixels) and the shader type (unlit, lit or text). The render thread shades from that copy and never reads the SWMaterial. So a material changed after DrawMesh, before or during the rasterization of its frame, only affects later draws, and two draws of one material with a colour set between them show both colours, as OpenGL applies uniforms when a draw is submitted. (Before, the colour read was whatever the material held when the render thread reached the draw, which was also a data race.) Nothing else a software shader reads comes from the material: lighting, the camera position and the clear colour are copied once per frame by EndFrame and passed to the render thread's clear and rasterizer as arguments (the render thread never writes them back to the renderer's members, so Clear or UpdateSceneLighting for the next frame can't race with the frame in flight), and uHasTexture is not read (the software shaders sample whenever the material has a texture). Rasterization output is unchanged.
  • DestroyMesh and DestroyTexture wait for the frame in flight before freeing, as UpdateMesh and Resize already did: its draws still point at meshes, and at textures, whose pixels are sampled while rasterizing. The wait returns at once when no frame is in flight. DestroyMaterial and DestroyShaderProgram don't wait: the frame in flight only has its copies.

Destroying a mesh or texture that a draw recorded this frame (after DrawMesh, before EndFrame) is still not allowed, on this renderer as on any: the draw keeps the pointer. The engine never does it (destroyed objects are freed after the frame is rendered).

Design decision: copy material uniforms at draw time; destroys always wait PR #55

Copying the material into each draw puts the software renderer on OpenGL's semantics and removes the render thread's only read of an object the main thread freely changes. The copy is a few floats, a pointer and an enum per draw, taken with the same lookups the render thread made per draw before. Textures stay pointers: copying pixels per draw would cost far more, and a software texture's pixels never change after creation, so the only hazard is freeing one, which the wait covers.

A destroy waits whenever a frame is in flight, without checking whether that frame uses the resource. The frame's draws have been moved to the render thread, so checking would mean keeping a second record of what each frame references. Destroys are rare (a component releasing its resources), the wait is at most the rest of one frame's rasterization, which Present would wait for anyway, and it returns at once when nothing is in flight. Materials and shaders need no wait at all once draws carry their own copies.

Fixed steps and physics

This is the None loop, the default (the simulation clock section has the network modes') PR #186. The accumulator is a double held by the SimulationClock that Application owns, starting at 0. Each frame adds the unscaled frame delta, clamped to 0.25 s, then, while a scene is loaded:

while (accumulator >= Time::GetFixedUnscaledDeltaTime())   // 0.02 s
{
    if (Time::GetFixedDeltaTime() > 0.0f)                    // scaled; 0 when paused
    {
        ++tick;                                                 // Time::GetTick()
        PhysicsUpdate(curScene);
    }
    accumulator -= Time::GetFixedUnscaledDeltaTime();
}
  • Cadence is real time. Steps happen every 0.02 s of unscaled time regardless of timeScale; each step passes the scaled fixedDeltaTime to physics. Slow motion means the same number of smaller steps.
  • Clamp. A stall (debugger, loading) contributes at most 0.25 s, so at most 12 steps catch up in one frame instead of hundreds. The delta is used directly rather than a difference of float absolute times, which lost precision after hours of running (code review #16, fixed in PR #24).
  • Paused. With timeScale 0 the accumulator still drains at the same rate but no step runs: neither physics nor FixedUpdate. Stepping PhysX by 0 is an error, and this matches Unity. Unpausing does not replay the paused time.

PhysicsUpdate(scene) does, per step:

  1. backend->ApplyPendingChanges(): transform and body changes made by game code since the last step.
  2. scene.FixedUpdate(): component FixedUpdate callbacks.
  3. backend->Update(Time::GetFixedDeltaTime()): simulate.
  4. backend->SyncTransforms(): write simulated poses back to GameObjects.
  5. backend->ProcessCollisionCallbacks(): dispatch collision and trigger events.

Without a backend (PhysX failed, disabled, or not built), a step is just scene.FixedUpdate(). See Physics for the backend side.

Note PR #34

The accumulator only builds up while a scene is loaded. In a frame with no scene (GetCurSceneIndex() == -1) it is reset to 0, so the first scene to load starts with at most one frame's worth of steps instead of a burst of catch-up steps for the time spent without a scene. Before PR #34 it kept accumulating, and the per-frame 0.25 s clamp did not limit the total.

The simulation clock and the tick counter PR #186

How many fixed ticks a frame runs is decided by a SimulationClock (engine/include/engine/SimulationClock.hpp) that Application owns. It holds the fixed-step accumulator and a 64-bit tick counter, Time::GetTick(): 0 before the first tick, incremented once at the start of every tick, so inside tick N's FixedUpdate (and in the OnAttach that runs at that tick's boundary) it is N, and between frames it is the number of ticks run so far. It is 64 bits wide and does not wrap in practice. Time::GetTick() is static, like the rest of Time; Lua reads it as Time.tick (a read-only integer). Time::Init sets it back to 0.

Falling behind. A network-mode frame that ends with at least one whole tick still owed (it hit the catch-up limit) leaves that time in the accumulator, sets SimulationClock::IsBehind() and calls the handler set with SetBehindHandler, with a SimulationBehind{tick, ticksOwed, ticksRunThisFrame, owedSeconds}, once per such frame. The loop discards the time only past a bound PR #199: the debt is paid, up to the limit's number of ticks a frame, until it is gone, unless the netcode decides to resync and calls SimulationClock::ResetAccumulator(). The bound is SimulationClock::MaxOwedSeconds (1 s): a frame that ends with more than that owed was never going to catch up. With a behind handler installed the report carries beyondLimit = true and the handler owns the decision (the clock keeps the debt); with no handler the clock resyncs itself, calling ResetAccumulator() and logging one warning (The <mode> simulation loop ended a frame ... s behind ...), so an unattended server does not run catch-up ticks for ever. This applies only to Authoritative and Deterministic; None never owes more than its 0.25 s clamp. With the limit at 0 a long stall runs every tick it owes in one frame, so a frame delta that is huge is the caller's to keep out. A NaN, infinite or negative delta is not time: a network-mode clock adds nothing for it, rather than poisoning the accumulator. Switching back to None keeps at most 0.25 s of any debt, so the None loop never inherits a burst of ticks. Design decision: a bounded resync when nobody handles being behind PR #199

A follow-up of the netcode A1 review: the network modes never drop time, and nothing resynced a clock that fell behind for good (for example a stalled server), so it would run catch-up ticks for ever. The clock now has a named bound, MaxOwedSeconds = 1 s (the plan suggested about one second of ticks). Beyond it a handler is told and decides; with none the clock resets itself with a logged warning. Judgement calls the plan did not cover: the bound is a constant, not a setting; it applies to both network modes, including Deterministic (a lockstep peer that fell a full second behind with nobody to resync it is not in lockstep any more, and the warning says so); and the bound is checked at the end of a frame against the time still owed, not against the frame delta, so a long single stall that the catch-up limit pays off in the same frame is not dropped.

Headless stepping. Application::StepTicks(n) runs exactly n ticks of the current scene (each one the tick a Tick runs) with no window events, no clock, no Update, coroutines, LateUpdate, drawing or destroyed-object cleanup, and leaves the accumulator and Time::GetTime() alone. It returns the number that ran: in None mode that is 0 while timeScale is 0, and the attach queue is processed once before the first tick, as a frame would; a network mode processes it at every tick boundary. For whole frames use Tick with TickOptions::deltaSeconds.

A driver for the fixed steps C5. Application::SetFixedTickDriver(driver) hands the fixed-step loop to a network session: while a driver is set, Tick calls it once per frame with the frame's unscaled delta where it would run its own fixed steps (the driver decides which ticks run and runs each with StepTicks(1)), then clears the clock's accumulator; the rest of the frame is unchanged. An empty function gives the loop back, Shutdown clears it, HasFixedTickDriver() says whether one is set. SimulationClock::SetTick(n) sets the tick counter, so a rollback that runs a tick again can give it the Time::GetTick() it had the first time. The one driver in the engine is Network::RollbackRuntime (netcode).

Guarantee PR #186

With the mode None, which nothing sets by default, the fixed-step loop does what it did before the clock existed: the same accumulator arithmetic (min(float delta, 0.25) added; while (acc >= float(step)), the step skipped while the scaled fixed delta is 0, acc -= float(step)), the same attach-queue call once per frame before the steps, the same fixed delta (fixedUnscaled × timeScale). The tick counter is the only addition, and it only counts. Test: SimulationClockTest.NoneModeKeepsTheLoopOfBeforeTheClock feeds ten frame deltas (including a frame of no time and two over the clamp) at timeScale 1, 0.5, 2 and 0 and compares each frame's step count, accumulator and fixed delta with constants worked out from the old loop's arithmetic.

Design decision: the network modes own the tick, and timeScale becomes presentation-only PR #186

Two peers (or a client and a server) that pause or slow time differently would step their physics by different amounts and diverge, and a loop that drops time past 0.25 s or attaches components once per frame gives each peer a different tick for the same event. So in the network modes the step length is the project's fixed timestep and nothing else, no time is dropped (a clock too far behind is reported so the netcode can resync, rather than the loop deciding), and attachment happens at tick boundaries. timeScale is allowed, not refused: it still scales Update's delta and Time.time, so slow-motion effects, animation and UI keep working, but it cannot pause or stretch the simulation. The offline loop is untouched because a change there would alter every existing game (a paused game, a slow-motion game, the editor's play mode). Decided on #157 and the netcode runtime design (None keeps today's loop byte for byte).

What the network modes mean for game code. Anything that must be the same on every peer (spawns, despawns, gameplay changes to physics bodies) belongs in FixedUpdate: it runs once per tick with the fixed delta, and what it creates attaches at the next tick. Something created in Update attaches at the next tick boundary after the frame that made it, which depends on the frame timing; Update is for presentation. A scene that loads gets its first components attached at its first tick boundary, so a frame that runs no tick shows them unattached.

No network traffic exists yet: the clock decides ticks from the frame delta it is given, and the netcode that will feed it a network clock comes later.

Quitting

Application::Quit() (static; also Application.Quit() in Lua) is a request: it logs "Quit requested" and sets a flag. It returns normally, so the calling component or Lua callback finishes. Before PR #24 it called std::exit(0) from inside callbacks with the scene and the Lua stack still live.

  • Run() checks the flag at the top of each iteration, so the frame in which Quit() was called runs to completion (including destroy processing and a pending scene change).
  • IsQuitRequested() exposes the flag to hosts that do not use Run(); the editor host polls it.
  • Lua's Application.Quit() can be refused PR #159. Application::SetScriptQuitAllowed(false) makes the binding log one warning, "Application.Quit is ignored on an editor host", and do nothing; IsScriptQuitAllowed() reads it. It is on by default (a game, and the editor's --play child, which is a running game). Since PR #179 the binding also refuses, with one warning per call ("Application.Quit is refused: this host does not run scripts"), whenever LuaRuntime::GetExecutionPolicy() is not Run, whatever this flag says: the editor host that edits runs no scripts at all (Execution policy), so this is the guard for a path added later. N2EditorHost turns it off before any scene loads unless it was started with --play. C++ callers of Application::Quit() are not affected, and the flag is not cleared by Init. Setting it re-arms the warning. ResetQuitRequest() clears a pending request, for tests that share the process's one Application.
  • The flag is cleared only by Init (one that actually runs, so the first Init or one after Shutdown). It is not cleared by Run() or Shutdown(). A Quit() requested before Run() is honoured only if it comes after Init (for example from a scene script's file-scope code run while adding the first scene): Run() then exits before the first frame. A Quit() before Init is lost, because Init clears the flag.

When the loop ends, for either reason (window closed or quit requested), Run() calls OnApplicationQuit() on the current scene, if there is one, then Shutdown(). The editor host does the same after its own loop. Run()'s early return for an invalid window does not call OnApplicationQuit.

Design decision: Quit is a request

Quit() is almost always called from inside a component callback or a Lua function, with the scene, the component and the Lua stack live on the call stack. Exiting there (the old std::exit(0)) ran static destructors under that code and skipped OnApplicationQuit and Shutdown. Setting a flag instead gives one exit path for every reason the loop can end: the frame finishes with the usual end-of-frame work (destroy processing, a pending scene change), then OnApplicationQuit, then Shutdown in a fixed order. Teardown is the same whether the window closed or a script quit, and Quit() is safe to call from any callback. Hosts with their own loop, like the editor host, poll IsQuitRequested() and follow the same order. This is the same deferral the engine uses for destroy and scene switches.

Design decision: the edit host ignores a script's Quit, the play child honours it PR #159

A scene's scripts run on the edit host when the scene loads, and a scene comes from a client. A script that called Application.Quit() there made the host loop exit with code 0, which a service manager treats as a clean stop and does not restart, and it did so again on every restart if the scene was the startup scene. So the binding checks a flag the host sets. The flag is in Application rather than in the host so the Lua binding, which has no view of the host, can read it; it refuses the script's call only, and C++ code that calls Quit() is unaffected. The --play child is a game the editor launched and the user is playing, so a script that quits ends that session, as it would in a shipped game. Decided on the security audit of the editor host (finding F3, part a).

Warning

Because only Init clears the flag, a test binary that calls Quit() leaves it set for every later test. A later test that spins Run() or the editor loop would exit at once. See Testing conventions.

Shutdown order

Shutdown() tears subsystems down in reverse order of Init:

  1. SceneManager::UnloadScenes() PR #28: drops any pending scene change, runs Clear() on the loaded scene (so components get OnDestroy) and frees it. Stored scene data is kept.
  2. AudioSystem::Instance().Shutdown(): stops and deletes one-shot and pooled sources, deletes sources still held by AudioSource components (and makes them forget the ids), destroys the OpenAL context.
  3. Destroy the physics backend (~PhysXBackend releases the PhysX SDK; ~JoltBackend destroys its bodies and releases Jolt's process-wide state if it was the last backend).
  4. Window::Shutdown(): input system, renderer, GLFW window, glfwTerminate.
  5. SetSimulationMode(None) PR #199: the network preset's tick loop ends with its project (Who sets the mode).

Scenes go first so the audio sources and physics bodies their components hold are released while those subsystems still exist. Before PR #28 the loaded scene was only freed during static destruction, after audio and PhysX were gone.

Shutdown is safe without Init and safe to call more than once. Run() calls it; hosts that do not use Run() must call it themselves before returning from main, so teardown does not depend on static destruction order.

Note

Shutdown does not tear down the Lua runtime, the main camera, ResourceLoader/Resources caches or stored scene data; those live until static destruction. The health report also keeps its last values.

The thirteen steps above are Application::Tick(const TickOptions &options = {}); Run() does while (!window.ShouldClose() && !quitRequested) Tick(); after zeroing the fixed-step accumulator (which is now a member, so it carries over between calls). RenderEditorFrame

RenderEditorFrame() renders one frame for a host that drives the engine itself (the editor server's RenderFrame command). It returns immediately if the window is invalid; otherwise it runs PollEvents, Time::Update, AudioSystem::Update and Render.

It does not run the attach queue, fixed steps, Update, coroutines, LateUpdate, destroy processing or pending scene changes: the scene is drawn, not simulated.

PR #98 RenderEditorFrame(const Camera &camera) does the same from a camera the caller owns: the view and projection matrices, the position the lit shaders see and the transparent objects' depth sorting come from camera, and the game's main camera is not used or changed. It also differs from the plain overload in two ways that suit a scene view: it draws no screen-space UI (world-space canvases are scene objects and still draw), and it doesn't call Window::PollEvents or read input (why). The editor server calls it with its editor camera, so a scene with no camera of its own, or an application with no main camera yet, can be drawn. Without a camera argument it draws the main camera (a default camera before Init has made one). Phase E7a, #79.

Rendering at a fixed size PR #85

A host that reads frames back instead of showing them (the editor server) renders them at its own size, not the window's. Window::SetRenderSize(width, height):

  • calls IRenderer::SetRenderTargetSize(width, height). OpenGL renders every later frame into an offscreen framebuffer of that size (RGBA8 colour, D24S8 depth and stencil), bound with its viewport in BeginFrame; ReadFramebuffer reads it; the window shows nothing new. The same size again keeps the target, another replaces it, and Shutdown frees it. It returns false when the framebuffer is incomplete: it logs, the old target is gone, and frames render to the window. Software (the default body, true for any non-zero size) calls Resize: its frame is already the offscreen CPU buffer, and ReadFramebuffer at that size is an exact copy. Vulkan recreates its offscreen colour and depth targets at that size (it always renders offscreen) and ignores Resize and OnResize from then on; false for a size over the device's limit or when allocation fails, which leaves no target (frames are skipped) until a later call succeeds PR #136.
  • updates the main camera's aspect (Application::OnWindowResize);
  • from then on, ignores the window's framebuffer-size callback, so a window resize reaches neither the renderer nor the camera;
  • makes Window::GetRenderDimensions() return that size. Everything that maps screen positions onto the frame uses it rather than the window's size, so drawing, hit testing and picking agree PR #85: the UI pass in Render, the application's UI hit provider (UISystem::MakeApplicationHitProvider), the world pick (PointerDispatcher::PickWithMainCamera) and the default viewport of Lua's Camera:ScreenPointToRay. Without a render size it is the window's size, so games are unaffected. Lua's Window.GetDimensions, GetWidth and GetHeight stay the window's size (in the editor host, the hidden window).

It returns false, changing nothing, without a renderer or for a size that isn't positive; the same size again does nothing. It also returns false when SetRenderTargetSize fails PR #85: then no render size is stored (any earlier one is cleared, as OpenGL has dropped its target), so the next call, even with the same size, tries again. Shutdown and InitWindow clear it. Window::AdoptRenderer(std::unique_ptr<IRenderer>) PR #85 replaces the renderer without a window (shutting the old one down and clearing the render size), for tests and tools; the editor server's tests use it to drive SetViewportSize and RenderFrame with a fake renderer. Every backend's ReadFramebuffer gives RGBA8 with the bottom row first; Renderer::Common::FlipRows (renderer/common/FrameRows.hpp) reverses the rows in place for a caller that wants the top row first. The editor server uses both for RenderFrame: see Viewport frames and why OpenGL uses an offscreen framebuffer. Issue #69.

Using Application in tests and tools

Init needs a window, so tests never call it. The pieces a test needs are installed directly:

  • Set3DPhysicsBackend(std::unique_ptr<IPhysicsBackend>) installs a backend without Init. It replaces and destroys any existing backend; nullptr removes it. Unload or replace scenes holding bodies first, because the old backend is destroyed immediately.
  • Fixed steps are driven by hand the way PhysicsUpdate does (PhysicsUpdate itself is private), or with Application::StepTicks(n), which runs exactly n fixed ticks of the current scene, or Tick with deltaSeconds for whole frames PR #186 (the simulation clock).
  • GetHealth() is empty and healthy; Shutdown() is a safe no-op.
static void SetUpTestSuite()
{
    auto backend = std::make_unique<N2Engine::Physics::PhysXBackend>();
    ASSERT_TRUE(backend->Initialize());
    N2Engine::Application::GetInstance().Set3DPhysicsBackend(std::move(backend));
}

static void TearDownTestSuite()
{
    // Leave no loaded scene holding bodies of the backend that's about to go away
    N2Engine::SceneManager::AddScene(N2Engine::Scene::Create("Teardown"), true);
    N2Engine::SceneManager::ProcessAnyPendingSceneChange();
    N2Engine::Application::GetInstance().Set3DPhysicsBackend(nullptr);
}

Singletons and static destruction

The engine relies on several process-wide singletons. Function-local statics are destroyed in reverse order of construction at exit, which is why teardown is done explicitly in Shutdown() and why some instances are deliberately never destroyed.
