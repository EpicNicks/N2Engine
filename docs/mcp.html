MCP bridge (n2-mcp)

n2-mcp is a program, kept in the frontend repository (N2Engine-Electron-Frontend, folder mcp/), that lets an AI agent such as Claude Code inspect and change an N2Engine project. It speaks the Model Context Protocol (MCP) on stdio to the agent and the editor protocol to an N2EditorHost. This page covers how to run it, the safety model, the tools that exist today, and how it shares a host with a person, including the engine's yield Hello flag (protocol 1.22.0), what CI now runs against a real host (Verified in CI) and what only a person can check (Checklist for a person).

Where the code is

The bridge is not part of this repository. This page was written from its source on the frontend repository's master (mcp/src/cli.ts, main.ts, bridge.ts, host.ts, policy.ts, limits.ts, scrub.ts, server.ts, tools.ts, tools-write.ts, play.ts, resources.ts, prompts.ts, session.ts) and its README. The bridge is version 0.1.0. When the two disagree, the frontend code is right; check n2-mcp --help for the options of the build you have.

What it is

The bridge is an ordinary editor protocol client with its own token. It adds no power of its own: the host's roles, --read-only mode, single-session rule and audit lines apply to the agent exactly as to a person's editor (Per-user tokens and roles). What it adds is the translation: MCP tools (typed, bounded, described for a model) on one side, protocol commands on the other, with the project's text treated as untrusted data on the way back.

It is a separate Node program (Node 22 or later, no Electron), built from the frontend repository into one file, dist/n2-mcp.mjs, with npm run build:mcp (npm run build does it too). It reuses that repository's protocol client and host launcher. It serves MCP over stdio, in both the 2026-07-28 and the handshake-based 2025-11-25 revisions of the specification (the SDK picks per connection how the client opens it). It talks to the host lazily: nothing is started or connected until a tool call (or, to list the write tools correctly, the first tools/list when writes are not turned off), so a client that only probes the server neither starts a host nor holds the host's one session.

Running it

Exactly one of two backends:

node dist/n2-mcp.mjs --launch <projectPath> [--host-path <N2EditorHost>] [--renderer opengl|software] [options]
node dist/n2-mcp.mjs --connect <host:port> --fingerprint <sha256> (--token-env <VAR> | --token-file <path>) [--user <name>] [options]

--launch: a host of the bridge's own

  • Starts N2EditorHost --project <dir> --port 0 --tokens-file <temp file> --exit-on-stdin-eof on loopback. The host binary comes from --host-path, else from the N2ENGINE_HOST environment variable (the editor's own name for it); with neither, the bridge refuses to start.
  • The host has one user, n2-mcp, with the editor role and a fresh random 256-bit token. The bridge writes only the token's SHA-256 to a 0600 file in a new temp folder (the tokens file is hashes only: Per-user tokens), keeps the token in its own memory, and never puts it in the host's arguments or environment. It removes the file and ends the host when it exits. The host also ends by itself when the bridge's stdin pipe to it closes. A host built without TLS support cannot hash tokens, so --launch needs a TLS build.
  • The host is started on the first tool call. It is not started with --exit-on-disconnect, so an idle disconnect leaves it up and the next call reconnects.
  • Only this backend has the play tools.
  • --renderer opengl|software and --ready-timeout <ms> (default 30000) belong to this backend, as does --host-path.

--connect: a running host

  • Connects over TLS with a pinned certificate fingerprint. --fingerprint is required (the certificate's SHA-256, 64 hex digits, colons allowed): there is no trust on first use, because nobody is at the prompt. The host prints it in its ready line (N2EditorHost ready port=... tls=1 fingerprint=...). Plaintext is not offered.
  • The token comes from exactly one of --token-env <VARIABLE> (the variable is read and then removed from the bridge's environment) or --token-file <path> (on POSIX the file must not be readable by group or others). A token is never accepted as an argument: --token and --password are errors, since arguments show up in process listings, shell history and client configs.
  • --user <name> is the token's user in the host's tokens file (1 to 64 characters of A-Z a-z 0-9 . _ @ -); it is sent in Hello (protocol 1.12.0).
  • host:port may be [::1]:9999 or localhost:9999.

Registering it with Claude Code and Claude Desktop

For Claude Code, claude mcp add [options] <name> -- <command> [args...] adds a stdio server (scopes local, project or user), or a project's .mcp.json can be committed because it holds no secret (${VAR} and ${VAR:-default} are expanded in command, args and env):

{
  "mcpServers": {
    "n2engine": {
      "command": "node",
      "args": ["tools/n2-mcp.mjs", "--launch", "${CLAUDE_PROJECT_DIR:-.}", "--renderer", "software"],
      "env": { "N2ENGINE_HOST": "${N2ENGINE_HOST}" }
    },
    "n2engine-staging": {
      "command": "node",
      "args": ["tools/n2-mcp.mjs", "--connect", "editor.example.net:9999", "--fingerprint", "<64 hex digits>", "--user", "agent-claude", "--token-env", "N2_AGENT_TOKEN"],
      "env": { "N2_AGENT_TOKEN": "${N2_AGENT_TOKEN}" }
    }
  }
}

The same with the command line: claude mcp add --transport stdio --scope project n2engine -- node tools/n2-mcp.mjs --launch . --renderer software. Claude Desktop takes the same mcpServers shape in claude_desktop_config.json with absolute paths; prefer --token-file there, since that file is plain text. The syntax is as the frontend README gives it; the bridge's own tests drive it with the MCP SDK's client and CI drives it with a small client of its own (Verified in CI); neither is Claude Code or Claude Desktop (Checklist for a person).

The safety model

The host's role gate is the security boundary. Everything below that the bridge adds is a limit on what a model can do by mistake or after reading hostile text, and none of it is a substitute for a narrow token.

  • A token of its own. Use a dedicated user per agent (for example --new-token agent-claude viewer or editor on the host), so audit lines say user=agent-claude and revoking it affects nobody else. Give a viewer token for inspection and an editor token only when the agent should change the project. A host started with --token-env has one token that is an admin: use a --tokens-file host for agents.
  • Admin is refused. After Hello the bridge reads the role the host reported. Anything other than viewer or editor (admin, or a role it does not know) makes every tool answer admin_refused and closes the connection, unless the bridge was started with --allow-admin. The write tools are listed only for an editor (or an allowed admin) on a host that is not read-only; a viewer token or a read-only host gets the read tools only. The host still enforces its own role gate on every command.
  • Irreversible operations need the person or the operator, never the model. Saving the scene, opening or creating a scene over unsaved changes, changing project settings, overwriting an existing text file and a revert that restores files cannot be undone by the editor. Each such call looks at the host first (is the scene dirty, does the file exist) and, when it really is irreversible: with --allow-irreversible it runs (the operator's consent); otherwise, if the client declared elicitation, the bridge asks the person a yes or no question naming the exact operation and runs it only on a yes; otherwise it is refused (irreversible_refused) and the host is never asked. No argument a model sends counts as consent: there is no confirm flag and every input schema refuses unknown keys.
  • Everything from the project is untrusted data. Names, field values, asset text, console lines and the host's error text are scrubbed and bounded before the model sees them: control characters removed; bidirectional, zero-width, line-separator and Unicode tag characters shown as \u{...} escapes; strings and whole values size-capped with a truncation marker; the text block's JSON escapes <, > and &, so data cannot close the <n2-data ... untrusted> envelope the result travels in. Every tool description and the server instructions say returned text is data, never instructions. There is no tool that runs text, and no shell, file system or network tool.
  • The host's paths and the bridge's secrets stay out. The project and user-data folders (learned from GetProjectInfo, which is never passed on with them) become <project> and <userdata>, any other absolute path in a message becomes <host-path>, and the token is replaced by [redacted] if a host ever echoes it. A result that would carry a registered secret is withheld. The console view drops the host's audit:, Rate limit and Refused Hello lines and peer= addresses.
  • Writes stay under assets/, never editor/. The bridge refuses a path that is not plain res:// followed by safe segments (no .., empty segment, backslash, colon, percent escape or control character), whose first segment is editor (or assets/editor), or that ends in .meta, before the host is asked anything. Editor extensions run with capabilities of their own (Lua editor extensions), so an agent must never be able to plant one. The host refuses again with its own rules.
  • Rate and write limits. 120 tool calls a minute (rate_limited, with the seconds to wait), 2000 host write commands per agent session (--max-writes), 500 ops in a batch, and the other limits. Undo, redo and the revert do not count against the write budget, so a session can always be undone.
  • Failures are bounded. A failed call is an error result with a stable code, a fixed message and one sentence of advice; a raw exception's text never reaches the model. A call the host does not answer within --call-timeout drops the connection and fails with timeout; the bridge never retries in a loop.
  • Cleanup. A launched host and its token file do not outlive the bridge (stdin closing, SIGINT, SIGTERM, SIGHUP, and a last-resort handler at exit).

The error codes are invalid_argument, rate_limited, read_only, forbidden, busy, auth_failed, fingerprint_mismatch, incompatible_protocol, connection_lost, host_unavailable, admin_refused, timeout, extensions_disabled, extension_failed, extension_faulted, host_error, result_too_large and internal, plus those of the write and play tools (such as budget_exceeded, session_conflict, confirmation_declined, irreversible_refused, play_not_running, play_failed and cancelled).

Source (frontend repository): mcp/src/bridge.ts — ensureLink (the admin check); mcp/src/policy.ts; mcp/src/server.ts — callTool; mcp/src/scrub.ts; mcp/src/errors.ts; mcp/src/write-core.ts.

The tools that exist today

These are the tools registered on the frontend's master, from mcp/tool-schemas.golden.json and the tool sources. Every result has the same shape ({source, untrusted, truncated, nextCursor?, notes?, data}) as structured content plus a text block holding a one-line summary and the same data in the envelope. Large results are paged (nextCursor).

Write tools (22)

Listed only when the host lets this token change the project: an editor (or an allowed admin) on a host that is not read-only, and not hidden by --read-only, --write-tools or --disable-tools. The bridge asks the host once and sends tools/list_changed if the answer changes; a host that cannot be reached at that moment lists the read tools only. Every edit call runs inside one edit group labelled AI: <tool> #<n> (it appears in the editor's Edit menu), opened and closed inside the call and never held between calls; if a command fails the group is closed and its step undone, so a failed call leaves nothing.

ToolWhat it does
n2_create_entityAn entity with name, parent and place, a preset (empty, cube, sphere, quad, lights), local transform, tag, layer, active flag and components with initial values: one step.
n2_destroy_entityDeletes an entity and its children (undoable).
n2_set_transformPart or all of the local transform; parts left out keep their values.
n2_set_parentReparents (parentId null for the root), at a sibling index, keeping the world transform unless told otherwise.
n2_set_propertiesName (this is the rename), active flag, tag, layer.
n2_add_componentAdds a component of a type from n2_get_component_types, optionally with field values.
n2_remove_componentRemoves a component by its UUID.
n2_set_component_fieldsSets fields of a component, all or nothing; the host's clamped values are echoed.
n2_duplicate_entityA copy with children and components, next to the original.
n2_apply_batchUp to 500 ops of the kinds above as one undo step, all or nothing; ops can refer to an earlier op's result.
n2_undo, n2_redoMove the agent's own steps only (at most 20 per call); they refuse and change nothing if a person edited after the agent or the history was cleared.
n2_create_scene, n2_open_scene, n2_save_sceneNew scene (optionally written to a new file), open a scene file, save. Opening or creating clears the host's undo history; opening over unsaved changes and saving are irreversible operations.

Every write tool except n2_begin_session takes an optional sessionId; without one the call is journaled in an implicit session. The annotations (readOnlyHint, destructiveHint, idempotentHint, openWorldHint) are hints that clients treat as untrusted; the safety above does not rely on them.

Play tools (6, --launch only)

A --connect bridge has no play tools at all: they are not registered, listed or callable. A --launch bridge lists them with the write tools (the same conditions). The game is a second N2EditorHost that the bridge starts with --play <snapshot>, the same project and renderer, and a fresh token in that child's environment only; the edit host writes a snapshot of the open scene as it is in memory (unsaved edits included, nothing saved), so nothing done in the game changes the scene or the project.

ToolWhat it does
n2_play_startStarts the game from the open scene and answers its state. A second call answers the running game.
n2_play_stopEnds the game (Shutdown, then a kill after a grace period). Not an error when none runs.
n2_play_controlpause, resume, or step 1 to 600 frames of a paused game (fixed timestep, so a test repeats), in chunks of 100 frames with progress and a cancellation check between them.
n2_play_inputUp to 256 input events (key, mouse button, pointer, scroll, release all), applied all or none.
n2_play_observeThe game's state, its log lines since the previous observe, up to 8 live entities by id, and optionally a PNG of the main camera.
n2_play_scriptA whole playtest in one call: up to 50 ops (input, step, screenshot, expectLog), the game paused first and left paused. Stops at a failed expectLog unless told to continue; a script that ends early releases every key it held.

Play budgets per agent session: 20,000 stepped frames and 50 game pictures; the step, pause, input and snapshot commands also count against --max-writes.

Agent sessions, undo and revert

n2_begin_session({label}) answers a sessionId that later calls pass. A session keeps a journal (per write: the tool, a scrubbed one-line summary, the undo step's label, the entities touched, the file written with its hash, and how an irreversible operation was confirmed), the labels of its own steps, a write counter, and the backups of text files it overwrote (a 0600 file in a private temp folder, deleted at exit unless --keep-journal). Sixteen sessions at most; one idle for 24 hours is dropped.

n2_session_summary says what changed so far; n2_end_session answers the final summary and forgets the session (the journal and backups go, so a revert is no longer possible). n2_session_revert undoes the session's steps in reverse and then restores overwritten files from the backups. It works only while the host's newest undo steps are exactly the session's own, in order; otherwise it refuses and changes nothing. It restores a file only if it still holds what the agent wrote, and leaves files the agent created in place (the host cannot delete files), listing them. Restoring files is irreversible-gated; restoreFiles: false reverts the steps only. Text-asset writes are not undone by the host's own undo: only a revert restores them, from the backup.

The person sees the agent's steps in the editor's Edit menu as AI: ... and can undo them there like any step.

Source (frontend repository): mcp/src/session.ts, mcp/src/write-core.ts, mcp/src/tools-write.ts.

Sharing the host with a person, and the yield flag

A host serves one session at a time (A second authenticated client). The bridge's connection is a session like an editor's, so an agent and a person contend for the same host. What happens depends on who arrives second:

  • The bridge finds the host busy (a person's editor, or another agent, holds it): the host answers busy; the bridge waits --busy-wait and tries once more, then answers the tool call with its own busy error. It never loops. A dropped or idle-closed session is reopened by the next call. A bridge that yields (the default) is never served by a host that is in use, whoever holds it and with whatever role.
  • A person arrives while the agent holds the host: with the default (the bridge yields), the host closes the bridge's session for any client that does not yield, whatever the roles (below). With --no-yield, or against a host before 1.22.0, the host's usual rules apply (above): the person's editor preempts the agent only with a strictly higher role, and the same user with the same role takes the session over; a person with the same role as the agent, as another user, is turned away with busy until the agent's session ends. That is the gap the yield flag closes. Give the agent a user of its own either way.
  • The agent must never take a person's session: the arbiter's same-user takeover would let an agent that shares a person's token and user replace the person's session. Use a per-agent user and token.

The Hello yield flag (protocol 1.22.0)

Since protocol 1.22.0 the engine's Hello request has a trailing yield bool (false when absent; after errorCodes and user). A client that sets it says: I am an agent, give way to people. The host applies these rules in SessionArbiter::Decide, in this order (details and tests: The yield flag):

  1. No session is active: Accept (a yielding client too).
  2. The candidate yields: Busy. It never takes over or preempts, not even from the same user, not even with a higher role, not even on a host with no token.
  3. The active session yields and the candidate does not: Preempt, whatever the roles. A viewer preempts a yielding admin; the same user preempts its own yielding session; a host with no token preempts it too.
  4. Otherwise the existing rules.

So an agent that sets yield gets an idle host, and as soon as any person's editor connects (with a token that is valid and does not itself yield) the agent's session is closed and the person's is served. The flag belongs to the connection (a later Hello on it replaces it), ServerInfo is unchanged, and the host logs yield=1 on the line that says the client said Hello.

The bridge yields by default

Since the frontend syncs to protocol 1.22.0 (frontend PR #64), the bridge sends yield: true in its Hello, for both --launch and --connect; --no-yield leaves it out. A bridge that finds the host in use answers busy saying it yields to people, and waits longer after each consecutive busy answer (up to the 10 second cap). If a person takes the host while the bridge holds it, the bridge's next call fails with a busy error saying the host ended its session, and the bridge reconnects only when the host accepts it. The Hello goes out before the bridge knows the host's version, so it always sends the field; a host before 1.22.0 does not read it. The frontend's own tests use a fake host that models the arbiter rules; the engine's CI smoke test runs the same rules against a real host built from the engine under test (protocol 1.23.0 at the time of writing) with the bridge at the pinned commit (Verified in CI): a client that does not yield preempts the bridge, the bridge's next call is busy with a message that begins "The host ended the bridge's", and the bridge does not take the host back while the person holds it.

Beside an open editor (--electron)

An --electron backend, which lets the agent work through the running Electron editor instead of contending for the host, has since been merged in the frontend repository (its PR #65). This page does not describe the backend itself: it was written from the code before that PR. What this repository runs of it is only the part that needs no Electron, in the smoke test (Verified in CI): the bridge's start-up with --electron --user-data, and what it says when the editor's discovery file is missing, says the editor is read-only, or names an endpoint nobody listens on. An --electron call that reaches a live editor endpoint (Electron's main process, a named pipe or Unix socket) is not run anywhere here. See the frontend README, whose tests (mcp/test/electron-backend.test.ts) run the bridge against the real endpoint code in front of a fake host.

What is not built yet

  • Documenting and testing the --electron backend (working beside an open editor; the engine's MCP proposal calls it MCP6): merged in the frontend as its PR #65 after this page was written, so it is not described here; the smoke test pins a bridge that has it but runs only its no-endpoint paths (Verified in CI).
  • Streamable HTTP transport: not built; the proposal defers it (MCP7), loopback only with a bearer token when it comes.
  • Known gaps listed by the frontend README: n2_screenshot does not restore the host's viewport size afterwards.

Verified in CI

Since MCP4 the engine's CI drives the bridge against a real N2EditorHost: python3 tests/smoke/editor_host_smoke.py --scenario mcp --config Release --exe build/bin/N2EditorHost, a step of the linux (Release, x86_64, Clang) job only (actions/setup-node@v5, Node 22, 15 minute timeout; the other legs are not slowed). Nothing is mocked on the host side: it is the host the job just built, started with --tls --tokens-file on a project made with --create, on the software renderer. The script:

  1. Fetches the frontend commit named in tests/smoke/mcp-bridge-ref.txt, runs npm ci --ignore-scripts and npm run build:mcp there, and checks that the checked-out commit is the pinned one. The bridge it tests is therefore a known commit, not whatever master is today.
  2. Makes three tokens with the host's own --new-token (an editor for the agent, a viewer, and an editor standing in for a person) and drives the bridge with --connect over stdio as an MCP client (tests/smoke/n2_mcp_client.py: newline-delimited JSON-RPC, protocol revision 2025-11-25, no client capabilities).

What it asserts, each against the real host:

  • Refusals. A wrong token gives auth_failed; an absent token variable stops the bridge at start (exit code 2); a wrong certificate fingerprint gives fingerprint_mismatch.
  • Tool lists. A viewer's tools/list is exactly the eleven read tools of the table above; an editor's over --connect is those plus the twenty-two write tools and none of the play tools; --launch lists all thirty-nine. The expected names are read from this page's own tables (the first cell of each row), so a tool added to or removed from the bridge without this page fails the step when the pin is bumped.
  • Read flow. n2_status (role, project name, open scene), n2_get_hierarchy, n2_get_project_info and n2_get_entity.
  • Write flow with undo. n2_create_entity (a cube), n2_set_properties (a rename), the hierarchy and n2_status (dirty) after the edits, then n2_undo twice: the name comes back, then the entity is gone, the scene is clean again, and the scene file on disk never held the entity.
  • Irreversible tier. With no --allow-irreversible and a client that declared no elicitation, n2_save_scene over unsaved changes and n2_set_project_settings are refused with irreversible_refused, and the scene file and project.n2proj on disk are unchanged.
  • Yield. The default bridge holds the host; a second client that does not yield (a plain editor protocol Hello from Python, with another user's token) takes the session; the bridge's next call is a busy error that begins "The host ended the bridge's"; while that client holds the host the bridge's calls stay busy ("does not take the host") and the client's session keeps working; a second bridge started meanwhile gets busy too; and once the client has left, the first bridge's call succeeds again.
  • --launch. A bridge that starts a host of its own (--host-path the host under test, on a second project) lists the thirty-nine tools, answers n2_status, creates an entity and undoes it, and exits with code 0 when its stdin closes.
  • --electron, without Electron. A bridge started with --electron --user-data pointing at a folder of the script's own lists only the eleven read tools (it does not know the editor's role before it connects). With no discovery file in agent/, n2_status fails with host_unavailable and advice naming the "Allow AI agent for this project" switch; with a file that has a reason and no endpoint (the editor is read-only), it fails with read_only; with a file naming an endpoint that does not exist, written for a process id that has exited, it fails with host_unavailable saying the endpoint file is left over from a crash. --electron with --connect exits with code 2. The made-up secret in that file is added to the no-leak check.
  • No token leaks. None of the three tokens appears in any bridge's stderr or in any tool result the script saw.

When an assertion fails the script prints which one, the bridge's stderr and the hosts' logs.

What the smoke test does not run

  • An --electron connection to a live editor endpoint: the script has no stand-in for the endpoint (it is a named pipe on Windows and a Unix socket elsewhere, with the editor's own role, undo labelling and confirmation dialog behind it), so what the bridge does once connected, and the editor's side, are not run. The frontend's own tests cover them against the real endpoint code and a fake host.
  • The elicitation prompt (the client declares none), and the --allow-irreversible path.
  • The play tools (they are only listed), resources, subscriptions, prompts, screenshots, n2_apply_batch, text asset writes, n2_session_revert, --token-file, --allow-admin and the admin refusal, and --read-only (the bridge's flag or the host's).
  • The 2026-07-28 revision of MCP (the script opens the connection the 2025-11-25 way).
  • Any host but the Linux x86_64 Clang one in CI, the Docker image, a person's Electron editor, Claude Code and Claude Desktop (below).

The pinned bridge, and how to bump it

tests/smoke/mcp-bridge-ref.txt holds two lines, repo= (the frontend repository's clone URL) and commit= (a full 40-digit sha). To move to a newer bridge: take the sha of the frontend's master (git rev-parse origin/master there), put it in commit=, run the scenario locally (below) and open a PR that changes that file; CI runs it on the Linux leg. Bump it when the frontend changes the tools, the yield behaviour or the protocol sync, and in the PR that changes host behaviour a bridge relies on. A tool list that no longer matches this page, or a changed message, fails the step: fix the page or the assertion in the same PR.

Running it locally

You need a host built with TLS support (-DN2ENGINE_EDITOR_TLS=ON: --tokens-file hashes tokens with SHA-256), git, Node 22 or later and npm, and network access to GitHub and the npm registry:

python tests/smoke/editor_host_smoke.py --scenario mcp --exe build/bin/Release/N2EditorHost.exe
python3 tests/smoke/editor_host_smoke.py --scenario mcp --exe build/bin/N2EditorHost

Options: --bridge <path to n2-mcp.mjs> tests a bundle you built yourself instead of the pinned commit, --no-launch skips the --launch part, --node names the Node executable and --work-dir says where the project and logs go. The scenario was also run on Windows (MSVC, Visual Studio generator, PhysX off, TLS on) while it was written, and passed there, --launch included; CI runs it on Linux only.

Source: tests/smoke/editor_host_smoke.py — scenario_mcp, build_bridge, docs_tool_lists; tests/smoke/n2_mcp_client.py; tests/smoke/mcp-bridge-ref.txt; .github/workflows/tests.yml (the step n2-mcp bridge smoke test). See also Testing.

Checklist for a person

These are what no CI job can check: they need Claude Code, Claude Desktop or the Electron editor, and a person to read the prompts. Do them once per bridge release and note the client's version beside each result. None of them has been done.

  1. A real Claude Code session against --launch. Register the bridge exactly as the frontend README says (above: claude mcp add --transport stdio --scope project n2engine -- node tools/n2-mcp.mjs --launch . --renderer software, with N2ENGINE_HOST set to a host built with TLS). In a session, ask it to list the hierarchy, create an entity, undo it, and end its session (n2_end_session). Check that Claude Code's own tool approval appears for the write tools, that the entity shows in the hierarchy and disappears on undo, and that the launched host ends when the session ends. Then make the scene dirty and ask it to save, and look at what Claude Code does for the irreversible tool: either it asks you a yes or no question that names the operation (a no gives confirmation_declined, a yes runs it), or the call is refused with irreversible_refused. Record which: only a client that declares elicitation is asked.
  2. --connect against the Docker image. Start the image as Running the host on Linux describes, with a tokens file that has an editor user for the agent, take the fingerprint from the ready line, and register a --connect bridge with --fingerprint, --user and --token-env. Ask Claude Code for n2_status and a hierarchy listing; check the role it reports and that it lists no play tools. CI does this against a host built in the job, not against the image.
  3. A person's editor taking the host from the bridge. With the bridge connected and a call made, connect the Electron editor to the same host with another user's token. Check that the editor connects and is not refused, that the bridge's next call answers busy with the message that the host ended its session, what Claude Code does with that message (it should stop and tell you, not loop), and that the agent does not take the host back while the editor is connected. CI does this with a Python stand-in for the editor, not with the editor.
  4. Claude Desktop, if you use it. Add the bridge to claude_desktop_config.json as above (absolute paths, --token-file rather than --token-env), restart it and repeat the read and write steps of the first item. Note whether it shows resources, prompts and the approval prompts, which the frontend README records as unknown.
