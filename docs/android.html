Android

The android target builds a game into an APK: the engine and the game's module list compiled with the NDK into libn2game.so, the game's pack in the APK's assets, and a small GameActivity around them. n2build drives Gradle; the editor's Build Settings panel drives n2build. Building an APK

node tools/n2build/n2build.mjs doctor --target android --project path/to/game
node tools/n2build/n2build.mjs build  --target android --project path/to/game [--config debug|release] [--out DIR] [--pack zip|stored|7z]

The build runs in the target's build tree (.n2/build/android-<config>-<hash>, one per configuration, module list and ABI list), in four steps:

  1. Cook: the game's pack, game.n2pack (zip by default; see Packs), into <tree>/assets.
  2. The Gradle project: players/android is copied into <tree>/gradle, over what is there, so Gradle's own output stays and the next build is incremental. n2build writes local.properties with the SDK folder and cmake.dir: the CMake that n2build found, because the SDK's own CMake (3.22) is older than the 3.25 the engine needs.
  3. Gradle: gradle -p <tree>/gradle assembleDebug (or assembleRelease), with the game's settings as properties (-Pn2.appId, -Pn2.project, -Pn2.assetsDir, -Pn2.abis and so on). Gradle's CMake step configures the engine repository itself with the NDK's toolchain and the GameActivity prefab and builds libn2game.so once per ABI, in <tree>/native.
  4. Package: the APK goes into the package folder as <Game>.apk (<Game>-unsigned.apk for a release build), with n2build's marker. The marker also records the app id and the ABIs.

A debug APK is signed with the SDK's debug key and installs on any device with USB debugging on. A release build is signed with a signing profile and also gives an AAB. Without a profile, the release APK is unsigned, and Android does not install an unsigned APK.

Source: tools/n2build/lib/android.mjs — planAndroid, prepareGradleTree, packageAndroid; targets/android/target.json; players/android

Gradle on Windows

Gradle is gradle.bat on Windows, which only cmd.exe can start. n2build passes it a quoted command line and refuses to start it when a path or setting holds a character cmd.exe would interpret (" % ! ^ & | < >). The error names the setting, so you can rename the folder or change the setting.

Signing and the AAB PR #TBD

A project names a signing profile and nothing more: build.targets.android.signing is {"profile": "release"}, and the editor refuses anything else there, because project files are committed and shared. The profile itself lives in your own n2build.json, beside the engine's user data (%APPDATA%\N2Engine\n2build.json, or ~/.local/share/n2engine/n2build.json):

{
  "signingProfiles": {
    "release": {
      "android": {
        "keystore": "C:/Users/me/keys/game.jks",
        "keyAlias": "upload",
        "storePassword": { "env": "GAME_STORE_PASSWORD" },
        "keyPassword": { "file": "C:/Users/me/keys/key.pass" }
      }
    }
  }
}
  • A password is {"env": "NAME"} (an environment variable), {"file": "/absolute/path"} (the file's first line) or plain text. Prefer the first two: then n2build.json holds no password at all. keyPassword defaults to the store password.
  • --signing NAME picks a profile for one build instead of the project's.
  • The profile is read only when a release build runs, never by --dry-run. A missing profile, keystore or variable fails the build before anything is compiled, with a message that names the key and never a password.

Where the secrets go

The keystore path, alias and passwords reach Gradle only in the environment of its process (N2_SIGNING_STORE_FILE, N2_SIGNING_STORE_PASSWORD, N2_SIGNING_KEY_ALIAS, N2_SIGNING_KEY_PASSWORD). They are never on a command line, in a file in the build tree, in the project, in the package marker (it records the profile's name) or in an editor protocol message. n2build replaces both passwords with **** in every line it prints, JSON events included. No other tool gets the variables, and a debug build never does. Tests: n2build.test.mjs, the signing and reporter tests.

A signed release build runs assembleRelease bundleRelease and puts <Game>.apk and <Game>.aab in the package folder. The AAB is what Google Play takes; the APK installs directly.

Running on a device PR #TBD

node tools/n2build/n2build.mjs run --target android --project path/to/game [--config debug] [--device SERIAL] [--seconds N] [--no-build]
  1. The device: adb devices -l (the SDK's platform-tools/adb). With one device attached, that one; with several, name it with --device. An unauthorized device says so: accept the USB debugging prompt on it.
  2. Install and start: adb install -r, then am start -W on the game's activity. An unsigned APK is refused before adb is asked.
  3. The log: adb logcat --pid=<the game's process>, each line a log event with "stream": "logcat" (JSON events), so the editor shows the game's log as it shows a build's. The run ends when the game's process ends, or after --seconds (then the game is stopped).

Source: tools/n2build/lib/adb.mjs — pickDevice, runOnDevice; tools/n2build/lib/signing.mjs

The player

players/android/native holds the platform backend (AndroidHost, an IPlatformHost; see the platform layer) and android_main. The OS owns the loop: the engine starts when the first window arrives and runs one frame per pass of the activity's event loop while the app is in the foreground.

  • Drawing: the software renderer draws each frame, and the backend copies it into the window's buffer (ANativeWindow_lock), so no EGL context is needed. The window can go away (the app goes to the background, or the screen turns off) and come back: the engine gets SurfaceLost and SurfaceRecreated, and frames are dropped while there is no window.
  • Lifecycle: Paused, Resumed, LowMemory and QuitRequested reach the engine as lifecycle events. The loop blocks while the app is paused.
  • Input: touches go to the Touchscreen (the first finger also moves the mouse, as on the web). Keys and gamepad buttons arrive in engine codes; sticks and triggers come from joystick motion events. Back is Escape and also raises BackRequested.
  • Safe area: Insets() combines the system bars and the display cutout. The activity is immersive: the bars hide until the player swipes them in.
  • Files: the game's pack is copied out of the APK into the app's files folder the first time the game starts, because an APK asset cannot be read at random positions. It is copied again when the APK's pack differs from the copy: a different size, or a different index at the pack's end, where a zip lists every file's CRC. The APK stores the pack uncompressed, so this check is a cheap seek. The pack is mounted where the game's folder would be. user:// is files/user.

Source: players/android/native/src/AndroidMain.cpp, AndroidHost.cpp; players/android/app (N2Activity)

What is not there yet

  • Rendering: the software renderer only. Vulkan on Android is stage 12.
  • Audio: OpenAL Soft plays through its OpenSL ES backend. AAudio through Oboe is a follow-up.
  • Rumble: does nothing yet. The manifest asks for VIBRATE, so adding it later does not change the APK's permissions.

CI

The android job in .github/workflows/tests.yml builds lua_project into a debug APK through n2build, for the emulator's ABI only (x86_64). It checks that the APK holds the pack and the native libraries. It then installs the APK on an API 30 emulator with no GPU, where scripts/android-emulator-smoke.sh passes when the game logs its first frame and a frame-rate line and is still running.
