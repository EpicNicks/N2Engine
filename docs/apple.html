iOS and macOS

The ios target builds a game into an app for the iOS simulator; the macos target builds the desktop player for Apple-silicon Macs. On a Mac, n2build builds both with Xcode and CMake. Anywhere else, it builds them in GitHub Actions, on a macOS runner, and downloads the result (decision D7: no Mac is needed). This is stage 10 of the build targets plan PR #345.

Building on a Mac

node tools/n2build/n2build.mjs doctor --target ios --project path/to/game
node tools/n2build/n2build.mjs build  --target ios --project path/to/game [--config debug|release]
node tools/n2build/n2build.mjs run    --target ios --project path/to/game [--no-build] [--seconds N]
node tools/n2build/n2build.mjs build  --target macos --project path/to/game

For iOS:

  1. Cook: the game's pack goes into the build tree first.
  2. Configure and build: CMake's Xcode generator configures the engine with CMAKE_SYSTEM_NAME=iOS, the simulator SDK and arm64. players/ios puts the pack into the app bundle and the game's settings into its Info.plist. cmake --build --config Release builds the app.
  3. Package: the app goes into the package folder as <Game>.app.

run works like this:

  1. It picks the booted simulator, else the newest iPhone (booting it), and installs the app.
  2. It waits for the simulator to finish booting, then launches the app and follows its log through the simulator's log stream (the app's process, its N2Engine lines), sending each line as a log event with "stream": "console". The player writes its log to the system log as well as stdout. On CI runners, neither simctl launch --console-pty nor --stdout delivered the output while the app ran. Whether the app still runs is checked on its process: a simulator app is a process of the Mac.
  3. It ends when the app exits, or after --seconds.

The doctor checks Xcode (xcodebuild -version) and CMake. For macOS it checks the compiler, CMake and Ninja, as on Linux.

The oldest systems: iOS 16.3 and macOS 13.3 (CMAKE_OSX_DEPLOYMENT_TARGET in the targets). They are the first where Apple's C++ library formats floating-point numbers (std::format uses std::to_chars).

Source: tools/n2build/lib/apple.mjs; targets/ios, targets/macos; players/ios; cmake/N2EngineApple.cmake

Building in GitHub Actions

When the machine is not a Mac, the ios and macos targets build in a workflow of the game's own GitHub repository:

  1. Once: n2build apple-workflow --project path/to/game writes .github/workflows/n2build-apple.yml into the game's repository. Commit and push it.
  2. The doctor checks only the GitHub CLI and its login (gh auth status). Xcode is the runner's.
  3. build refuses a project with uncommitted or unpushed changes, because the workflow builds what is on GitHub. It then runs gh workflow run n2build-apple.yml with four plain inputs: the target, the configuration, the project's folder in the repository, and the engine revision.
  4. It follows the run (gh run watch, its output as log events), then downloads the package artifact into the package folder. The package holds the marker that the workflow's own n2build wrote.

The workflow runs on a pinned macos-15 runner. It checks out the game and the engine at the requested revision, runs n2build build, and for iOS also runs the app in the simulator for 30 seconds, as a smoke test. build --dry-run prints the gh command without running it.

Source: tools/n2build/lib/remote.mjs — gitState, checkPushed, dispatchAndFollow, workflowTemplate

The iOS player

  • The app: one window and one view. The engine starts when the view appears; a CADisplayLink runs one frame per screen refresh while the app is active. The OS owns the loop.
  • Drawing: the software renderer's frame becomes the view's layer contents (a CGImage, flipped to top-down rows). No GPU API is needed, so this works on the simulator and on a device alike. An app built with MoltenVK draws with the Vulkan renderer instead (below).
  • Input: every touch goes to the Touchscreen, in pixels; the first finger is also the mouse. A hardware keyboard and game controllers are follow-ups.
  • Lifecycle: Paused, Resumed, LowMemory and QuitRequested. The display link pauses in the background.
  • Safe area and scale: Insets() is the view's safe area, in pixels; ContentScale() is the screen's scale.
  • Files: the pack is read where it is in the app bundle (bundle files are ordinary files, so there is no copy, unlike Android). user:// is Application Support/user.
  • Audio: OpenAL Soft on Core Audio, with the ambient audio session (it mixes with other apps and follows the silent switch).
  • Log: the engine's log goes to stdout. The player logs first frame (with the renderer) and then N frames, X fps every five seconds.

Source: players/ios/src/IosMain.mm, IosHost.hpp

macOS

macOS uses the desktop player (players/desktop), with GLFW, the OpenGL and software renderers, and AppleClang. The libc++ <generator> stand-in is the web build's. The package is a folder: the executable, which finds its libraries beside it (@executable_path), and game.n2pack. An .app bundle for macOS is a follow-up.

The Vulkan renderer on MoltenVK PR #352

macOS's GPU renderer is the engine's Vulkan renderer running on MoltenVK, Khronos's Vulkan on Metal. This was the user's pick after the stage 13 spike (orchestrator/proposals/metal-spike.md):

  • The build: when MoltenVK is found (brew install molten-vk, or the Vulkan SDK), the macOS build includes the Vulkan renderer. The player links libMoltenVK.dylib itself, without the Vulkan loader. n2build ships the library beside the player, and the player loads it from there (@executable_path), so a package needs nothing installed. Without MoltenVK, the player has the OpenGL and software renderers as before.
  • Running it: --renderer vulkan. GLFW makes the window's Metal surface (VK_EXT_metal_surface) through MoltenVK's entry point (glfwInitVulkanLoader).
  • A portability device: MoltenVK cannot swizzle image views (imageViewFormatSwizzle). The renderer then stores one- and two-channel textures, the text atlas among them, as RGBA holding (r, 0, 0, 1) and (r, g, 0, 1). It samples them exactly as a swizzled view would. Every other device keeps R8 and RG8.
  • Signing: rewriting the player's and MoltenVK's library paths breaks their code signatures, so both are signed again ad hoc. A release for distribution is signed with its own identity (a follow-up with the developer account, D7).
  • iOS: below.

Guarantee

Without image view swizzles, one- and two-channel textures are stored as RGBA holding what the swizzle would give (VulkanResourceTest.WithoutImageViewSwizzlesSmallTexturesAreStoredAsRgbaHoldingWhatTheSwizzleWouldGive, forced on any driver).

iOS on MoltenVK PR #353

The iOS app can draw with the Vulkan renderer too, on MoltenVK's static library (an app links its code in; it loads no library of its own from elsewhere):

  • Where MoltenVK comes from: Homebrew's MoltenVK is macOS-only. Take MoltenVK's own release from Khronos (MoltenVK-all.tar, unpacked: the folder MoltenVK/MoltenVK, holding include/ and static/MoltenVK.xcframework) or the Vulkan SDK's iOS folder. Name it with the environment variable N2_MOLTENVK_IOS (or the CMake option N2ENGINE_IOS_MOLTENVK) before n2build build --target ios.
  • The build: the xcframework's slice is chosen by the SDK the tree builds for: ios-arm64_x86_64-simulator for the simulator, ios-arm64 for a device. The shader compiler (glslangValidator, brew install glslang) runs on the Mac. Without MoltenVK named, the app is built as before, with the software renderer only.
  • At run time: the app asks MoltenVK for a GPU when it starts, before the view is made. With one, the view's layer is a CAMetalLayer and the renderer makes its surface on it (VK_EXT_metal_surface). Without one, the app keeps the software renderer. The log says which, at the start and again in the first-frame line: first frame, the Vulkan renderer (MoltenVK) or first frame, the software renderer.
  • The simulator: Apple's simulator draws through a Metal service on the Mac (SimMetalHost), which crashes on MoltenVK's Metal argument buffers when the first pipelines are made (seen on the CI's macOS 15 runner). In a simulator build the app therefore sets MVK_CONFIG_USE_METAL_ARGUMENT_BUFFERS=0 before its first Vulkan call, unless it is set already, and MoltenVK binds resources by discrete indexes instead. A device build keeps argument buffers. In the simulator a Release app draws at about 21 fps with MoltenVK and 55 with the software renderer (measured); the CI's Debug apps draw at about 3 fps either way.
  • The CI: the apple job builds the iOS app twice, as n2build builds it by default and with MoltenVK v1.4.2 (downloaded and checked against its SHA-256), and runs both in the simulator.
  • Not yet: the n2build-apple workflow for a game's own repository does not fetch MoltenVK; a game that wants it sets N2_MOLTENVK_IOS in its workflow. A device run is a checklist item.

MoltenVK's size and speed, measured PR #366

The Apple measurements workflow (.github/workflows/apple-measure.yml, with scripts/apple-measure.py) builds lua_project in Release on macos-15 runners, without and with MoltenVK v1.4.2, and times it. It runs on demand (workflow_dispatch) and on a pull request that changes the workflow or its script; it gates nothing. One run takes about 46 macOS runner minutes. The numbers below are from its first run, 43525490291 (2026-11-13).

How: on macOS, the wall time of a 330-frame run less that of a 30-frame run, divided by 300 (start-up cancels out), the median of three. In the simulator, the player's five-second frame-rate lines over 60 seconds, the first left out, the median.

  • The macOS rows are not a race. The Vulkan window ran at about the display's 60 Hz even with vsync off in two of three repeats (the third ran at 4.45 ms), so presenting through the VM's window server paces it. The software renderer presents nothing offscreen, and the runner has no OpenGL context, so OpenGL and the software renderer's window cannot run there. Both are well inside a 60 Hz frame for this scene.
  • In the simulator MoltenVK is slower than the software renderer. The simulator forwards Metal to the Mac's GPU and runs MoltenVK without argument buffers (above); neither is so on a device. Only a device run can say how MoltenVK does on an iPhone (checklist item 6).

Devices and signing

The app is built for the simulator and is not signed. A device build needs an Apple Developer account, which the plan defers (D7). When it comes, signing happens only inside the workflow, from the repository's own secrets. Nothing is read on this machine and nothing goes into the project.

CI and what was verified

The apple jobs in .github/workflows/tests.yml run on macos-15, with the same commands as the game workflow:

  • macOS: builds lua_project's package (Debug) and runs it for 60 frames with --headless, then 60 frames with --renderer vulkan in a window on MoltenVK, loaded from beside the player. The runner is a virtual machine: its paravirtual GPU runs MoltenVK, but it has no OpenGL context. The OpenGL window on a Mac is checklist item 5.
  • iOS: builds the simulator app (Debug), checks its bundle (the pack and the bundle identifier), and runs it in the simulator. The run must log a first frame and a frame rate.

The Apple measurements workflow is separate and on demand (above).

Verified only in CI

This machine has no Mac, so every Apple build and run on this page was verified only in CI. n2build's Apple and GitHub Actions logic is unit tested anywhere (n2build.test.mjs): the descriptors, the doctor off and on a Mac, the configure options, finding and packaging the app, the simulator choice and run, and the git checks and the gh flow against a fake gh.
