Scenes & SceneManager

A Scene owns a hierarchy of root GameObjects and drives their components through the frame. SceneManager stores scenes as JSON snapshots, loads one at a time, and switches scenes at the end of a frame. This page covers what each operation guarantees, in what order things happen, and what happens to objects that outlive their scene.

The Scene object

A Scene is created only through Scene::Create(name), which returns a std::unique_ptr<Scene> (the constructor is private). It is also an Asset, so it has a UUID and a GetResourceType() of "Scene"; see Resources.

What a scene holds:

  • Root objects: std::vector<std::shared_ptr<GameObject>>. The scene co-owns its roots; children are owned by their parents.
  • Component views: raw Component* lists for attached components (_components, lights included), components waiting for OnAttach (_attachQueue), and attached lights again (_sceneLights, for rendering). Components themselves are owned by their GameObject (unique_ptr).
  • A coroutine scheduler, one per scene (see Coroutines).
  • A destruction queue of objects passed to DestroyGameObject.
  • sceneName, a public string. It is what Serialize writes as "name" and what SceneManager keys stored scenes by.

Copy and move are deleted. GameObjects and the coroutine scheduler keep a Scene*, which a move would leave pointing at the moved-from object, so scenes always live behind unique_ptr. (The move operations used to be defaulted; issue #16 flagged this.)

Each scene owns a Base::LifetimeToken (GetLifetimeToken()) that expires when the Scene object is freed PR #31. Lua reaches scenes only through checked Scene handles built on it (SceneManager.GetCurrentScene() returns one, or nil): a handle stays valid while the scene is being cleared, so scripts can use it in OnDestroy during their own scene's unload, and raises a Lua error once the scene is freed after a switch. See Lua scripting.

Templates such as FindObjectByType<T> are defined in Scene.inl. Include engine/GameObjectScene.hpp, which pulls in GameObject.hpp, Scene.hpp and both .inl files, when you need them.

Traversal

  • TraverseAll(cb): pre-order, depth-first over every root's subtree. Inactive objects are visited.
  • TraverseAllActive(cb): the same walk, but it skips any object that is not IsActiveInHierarchy(), together with its whole subtree.
  • TraverseUntil(cb): pre-order. It stops the whole traversal as soon as cb returns true, and returns whether that happened.

The traversals iterate the live root vector and each object's live children vector. Don't add or remove roots or children from inside the callback.

Source: engine/src/sceneManagement/Scene.cpp — Scene::TraverseAll, Scene::TraverseAllActive, Scene::TraverseUntil, Scene::TraverseGameObjectRecursive

Attach queue and per-frame callbacks

A component enters a scene's attach queue when its GameObject joins the scene (SetScene with a different scene) or when it is added to an object that is already in a scene. ProcessAttachQueue runs at the start of each frame, in Application::Run. It:

  1. Takes the front entry off the live queue, one at a time. OnAttach can queue more components, which are processed in the same call. It can also remove pending ones, which DetachComponent erases from the queue, so no stale pointer is left.
  2. Calls OnAttach(). While it runs, the component is on a stack of components being attached. If OnAttach removes the component or moves its object to another scene, DetachComponent clears its stack entry and the component is skipped from here on, never registered or touched again. A stack, not a single slot, so an OnAttach that drains the queue again (nested attach) does not lose track of the outer component PR #34.
  3. Registers the component in _components, without duplicates; a Light is also added to _sceneLights PR #39. A component re-queued after re-parenting is never registered twice.

Update, FixedUpdate, LateUpdate and OnApplicationQuit each call the matching component callback on every entry of _components that is non-null, whose GameObject is active in the hierarchy, and that is itself active. The rules for iterating:

  • The loop runs by index. A component added during the loop (appended) is visited in the same pass.
  • A component removed during the loop is nulled out rather than erased, so the loop skips it. The nulls are compacted when the outermost iteration ends.
  • Iteration depth is held by a scope guard, so an exception thrown by a callback still brings the depth back down and compacts. The exception itself propagates to the caller.

Order within one frame of Application::Run: ProcessAttachQueue, then zero or more fixed steps (FixedUpdate inside PhysicsUpdate), then Update, then AdvanceCoroutines, then LateUpdate. Audio update and render follow, then ProcessDestroyed, and finally SceneManager::ProcessAnyPendingSceneChange. See Application & frame loop for the full loop.

Source: engine/src/sceneManagement/Scene.cpp — Scene::ProcessAttachQueue, Scene::OnAllActiveComponents, Scene::Update/FixedUpdate/LateUpdate/OnApplicationQuit; engine/src/Application.cpp — Application::Run; tests: LifecycleTest.RemoveComponentDuringUpdateSkipsIt, LifecycleTest.ThrowingComponentDoesNotWedgeIteration, LifecycleTest.RemoveComponentBeforeAttachLeavesNothingQueued, LifecycleTest.ReparentingWithinSceneDoesNotAttachTwice

Guarantee

Removing a component (or destroying its object) during Update never leaves the running loop with a dangling pointer, and the removed component is not called again that pass. A component removed before its first ProcessAttachQueue never gets OnAttach, and one that removes itself in OnAttach is never registered PR #34. Re-parenting within the same scene does not attach or update a component twice.

Deferred destruction (ProcessDestroyed)

ProcessDestroyed runs once per frame, after render. It works in three phases, so every OnDestroy can still use the other objects being destroyed in the same batch:

  1. Mark: each queued object is popped. Null entries and objects already marked are skipped, so destroying an object twice, or a parent and its child, tears it down once. An object that has moved to another scene since it was queued is skipped too PR #34. Each object's subtree is marked and collected, parent before children.
  2. Destroy callbacks: for every collected object, each component runs RunDestroyCallbacks(wasActive). OnDisable runs first, if the component was enabled and its object was active before marking, then OnDestroy. Each component runs these at most once, whichever teardown path gets to it first, even if its own callbacks remove it again; the loop walks a snapshot of the object's components and skips any a callback already freed PR #34 (see changes made by teardown callbacks). RunDestroyCallbacks does not check that the component was ever attached: a component added and destroyed in the same frame, or one in a scene that is switched away before its first frame, gets OnDisable/OnDestroy without ever having had OnAttach. Then the object's coroutines are stopped on this scene's scheduler.
  3. Purge: each object is removed from its parent (unless the parent is also being destroyed) or from the root list, SetScene(nullptr) detaches its components, and GameObject::Purge releases its components, children and Positionable (and marks it torn down PR #29).

An object destroyed from inside an OnDestroy in this pass is queued again and handled in the next frame's ProcessDestroyed, because the queue was already drained in phase 1.

Source: engine/src/sceneManagement/Scene.cpp — Scene::ProcessDestroyed, Scene::MarkHierarchyForDestruction, Scene::CallOnDestroyForGameObject, Scene::PurgeMarkedGameObject; engine/src/gameobject/Component.cpp — Component::RunDestroyCallbacks; tests: LifecycleTest.DestroyTwiceRunsOnDestroyOnce, LifecycleTest.DestroyingParentDestroysChildrenOnce, LifecycleTest.DestroyRunsOnDisableThenOnDestroy, LifecycleTest.DestroyOfInactiveOrDisabledSkipsOnDisable

DetachComponent: the single "forget" hook

Scene::DetachComponent(c) (private) removes a component from _components, _attachQueue and _sceneLights. Every path where a component or object leaves a scene goes through it: RemoveComponent, RemoveAllComponents, GameObject::SetScene when the scene changes (including RemoveRootGameObject and purging a destroyed object), ~GameObject while still in a scene, and Scene::Clear through SetScene(nullptr). This is why the scene's raw-pointer lists never hold a freed component. Issue #16's main finding was that they used to.

While _components is being iterated, detaching sets the entry to null instead of erasing it (see above). Outside an iteration it erases.

Source: engine/src/sceneManagement/Scene.cpp — Scene::DetachComponent; engine/src/gameobject/GameObject.cpp — GameObject::SetScene, GameObject::~GameObject; tests: LifecycleTest.RemoveComponentDetachesFromScene, LifecycleTest.DestroyingObjectRemovesItsLight

Lights

  • A Rendering::Light is registered in both _components and _sceneLights when it attaches PR #39. It gets OnUpdate/OnFixedUpdate/OnLateUpdate/OnApplicationQuit like any component (before, it was kept out of _components and got none of them); rendering reads the light list.
  • CollectLighting() (called by Application::Render) skips null and inactive lights, and caps each kind at SceneLightingData::MAX_DIRECTIONAL_LIGHTS, MAX_POINT_LIGHTS and MAX_SPOT_LIGHTS, in attach order. Spot cone angles are converted from degrees to radians.
  • With no usable light at all, it adds a default directional light (direction (0.5, -1, 0.3), white, intensity 0.8) and logs a warning once per scene.
  • Destroying a light's object removes it from _sceneLights, so CollectLighting never reads a freed light.

Source: engine/src/sceneManagement/Scene.cpp — Scene::ProcessAttachQueue, Scene::CollectLighting; tests: LifecycleTest.DestroyingObjectRemovesItsLight, LightCallbacksTest.*

Scene::Clear

Clear() runs the same teardown as ProcessDestroyed, so leaving a scene releases what its components hold (physics bodies, audio sources, script state):

  1. Marks and collects every root's subtree.
  2. Runs OnDisable/OnDestroy for each collected object's components (once each, as in ProcessDestroyed), and stops their coroutines on this scene's scheduler.
  3. Only then marks every collected object as torn down (_isTornDown), so each OnDestroy above could still use the other objects. Lua handles become invalid at this point; see Lua scripting. PR #29
  4. SetScene(nullptr) on every root, which detaches every component in the hierarchy. Then SetScene(nullptr) on every collected object that still points at this scene, including one an OnDestroy unlinked from its parent. An object a callback moved to another scene keeps that scene PR #34.
  5. Empties the roots, _components, the attach queue, the light list and the destruction queue. Emptying the root vector releases the scene's references, so every root that nothing else holds is freed here, together with its children and components.

Unlike ProcessDestroyed, Clear does not call Purge. Objects that something else still holds (a script, a GameObject::Ptr in C++) survive as destroyed objects with no scene. Their components have already run OnDestroy.

Clear walks the roots, and every object in a scene is reachable from them: a child removed with GameObject::RemoveChild becomes a root PR #34.

Source: engine/src/sceneManagement/Scene.cpp — Scene::Clear; tests: LifecycleTest.SceneSwitchRunsOnDestroy, SceneSwitchTest.LeavingSceneWithComponentsDoesNotCrash, HierarchyLifetimeTest.RemovedChildIsTornDownBySceneSwitch

Guarantee

After a scene switch, every component that was in the old scene (children and removed children included) has had OnDestroy called once. Its GameObject reports IsDestroyed() and GetScene() == nullptr.

Scene lifetime and objects that outlive it

A GameObject can outlive its scene, for example when a script or C++ code holds a GameObject::Ptr to it. ~Scene therefore walks its roots and the owners of everything still in _components and _attachQueue, and sets _scene = nullptr on each one that still points at this scene. Before that, a scene that still has attached components runs the teardown described in Scenes dropped without being loaded; otherwise no callbacks run in the destructor. Without it, ~GameObject (which detaches its components from _scene and stops its coroutines) would use a freed scene.

Ownership, by how the scene ends:

  • Cleared first (every scene switch, and UnloadScenes): Clear already released the roots, so roots nobody else holds, with their children and components, were freed in Clear. Its lists are empty, so ~Scene has nothing left to walk.
  • Destroyed without Clear (a scene that is dropped without being loaded, or one you own yourself): if any component attached to it, ~Scene first runs the Clear teardown for the attached components PR #39. Roots are released when the root vector is destroyed. A root nobody else holds dies there, and with it all its children and components. ~Scene first clears _scene on the objects it finds.
  • Either way, an object held elsewhere keeps living, with GetScene() == nullptr (cleared by Clear through SetScene(nullptr), or by ~Scene). Starting a coroutine on it logs a warning and returns null.

Source: engine/src/sceneManagement/Scene.cpp — Scene::~Scene, Scene::Clear; engine/src/gameobject/GameObject.cpp — GameObject::~GameObject, GameObject::StartCoroutine, GameObject::RemoveChild

Guarantee PR #34

No object survives its scene with a dangling scene pointer. Every object in a scene is a root or under one, because RemoveChild makes the removed child a root of its scene (as SetParent(nullptr) does), and Clear clears the scene pointer of every object it tore down. A child removed before a switch is torn down with the scene and can be used and released safely afterwards. This also covers Lua: parent:RemoveChild(child) leaves the child owned by the scene, and the script's handle takes ownership only when the child is not a scene root afterwards PR #31.

Tests: HierarchyLifetimeTest.RemoveChildMakesTheChildARootOfItsScene, HierarchyLifetimeTest.RemovedChildIsTornDownBySceneSwitch, LuaHandleTest.RemoveChildInASceneTakesOwnershipOnlyWhenNoSceneRootOwnsIt. Design rationale: RemoveChild re-roots, as in Unity.

SceneManager storage model

SceneManager is a static facade over a function-local singleton. It holds:

  • Stored scenes: a vector of StoredScene{name, data} PR #28. data is the scene's JSON, the only thing a load rebuilds from. name is copied from data["name"] (empty if that is missing or not a string) and kept alongside, so looking a scene up by name never builds it.
  • The loaded scene: one std::unique_ptr<Scene>, plus _curSceneIndex (-1 when nothing is loaded). The loaded scene is live: it can contain objects that are not in its stored data.
  • A pending change: whether a load is requested, the requested index, and optionally the caller's own Scene instance from AddScene(scene, true) PR #28.

Scene indices are positions in the stored vector. They are stable, except that DeleteScene shifts every later index down by one.

Source: engine/include/engine/sceneManagement/SceneManager.hpp, engine/src/sceneManagement/SceneManager.cpp — SceneNameOf, SceneManager::StoreScene

Warning

SceneManager::GetCurSceneRef() dereferences the loaded scene without checking. With nothing loaded (before the first load, after UnloadScenes) it is undefined behaviour. Use GetCurScene(), which returns null, or check GetCurSceneIndex() != -1 first, as Application::Run does.

Adding scenes

AddScene(std::unique_ptr<Scene> scene, bool loadAdded = false) PR #28

  • Takes the pointer by value, so the scene is always consumed, even when it isn't loaded.
  • A null scene logs an error and returns.
  • Always stores a snapshot: scene->Serialize(). Later loads of this scene rebuild from that snapshot.
  • If a stored scene already has the same (non-empty) name, its data is replaced at the same index and a warning is logged. Before #28, a duplicate was appended that name lookups could never reach. If a load of that index is pending, its caller-supplied instance is dropped, so the load builds from the new data.
  • loadAdded = true: requests a load of that index, and the caller's own object becomes the pending scene. At the next ProcessAnyPendingSceneChange it becomes the loaded scene as-is, so every GameObject::Ptr the caller kept belongs to the live scene. Before #28, the object was dropped and a copy rebuilt from JSON, which left the caller's pointers in an orphaned scene.
  • loadAdded = false: only the snapshot is kept, and the Scene object is destroyed when the call returns.

Note

The snapshot is taken when you call AddScene. Objects added to the live scene afterwards are not part of the stored data, so they are gone the next time the scene is loaded from storage, unless you call UpdateScene with the scene's current Serialize() (the editor's Save does this). Re-adding the name of the currently loaded scene with loadAdded = false replaces only the stored data. The live scene keeps running unchanged.

AddScene(nlohmann::json &j)

  • Validates by building the scene once with Scene::FromJSON(j, true). That requires "name" and an array "rootGameObjects", and the full deserialization must not throw. If it fails, the error is logged by FromJSON, nothing is stored, and the caller is not told (the function returns void).
  • If it succeeds, the data is moved out of j into storage, so the caller's j is left in a moved-from state. Name replacement works the same as above, including dropping a pending instance for that index.
  • The validation build is a real build: component constructors and Deserialize run, including Lua script chunks, and the result is then thrown away.

Source: engine/src/sceneManagement/SceneManager.cpp — SceneManager::AddScene (both overloads), SceneManager::StoreScene; tests: SceneStorageTest.AddedAndLoadedSceneIsTheCallersObject, SceneStorageTest.LoadingAStoredSceneAgainRebuildsItFromItsSnapshot, SceneStorageTest.ReAddingASceneNameReplacesIt, SceneStorageTest.ReAddingTheLoadedSceneWithoutLoadingLeavesItRunning, SceneStorageTest.AddSceneJsonDropsAPendingInstance

Loading and the pending scene

LoadScene only requests a load. The switch happens in ProcessAnyPendingSceneChange, which Application::Run calls at the very end of each frame, after ProcessDestroyed. A load requested during Update therefore takes effect after this frame's render and destruction pass.

CallResult
LoadScene(index), index out of rangeError logged, request ignored. A previous pending request stays.
LoadScene(index), same index as an already pending requestRequest kept. The caller's instance from AddScene(scene, true) is kept PR #28.
LoadScene(index), different index from a pending requestThe new request supersedes the old one. A pending caller instance is destroyed (see dropped scenes), but its snapshot stays stored.
LoadScene(name), unknown nameErrors logged (by GetSceneIndex and by LoadScene), nothing requested.
LoadScene(GetCurSceneIndex())Reloads the current scene from its stored snapshot. The live state is discarded through Clear.
Several requests in one frameThe last valid one wins.

ProcessAnyPendingSceneChange

  • Returns immediately if no load is pending.
  • Consumes the request (it is cleared whether the load succeeds or not).
  • Build before clear: the next scene is built first. That is either the caller's pending instance or Scene::FromJSON(stored data).
  • If the build fails (FromJSON returned null because the data is malformed), it logs "Scene N could not be loaded; keeping the current scene" and returns. The current scene and index are untouched. Before #23, the current scene was cleared first, leaving no scene at all.
  • Otherwise it clears the current scene (if one is loaded), sets the index and replaces the loaded scene. The old Scene object is destroyed at that point.

Source: engine/src/sceneManagement/SceneManager.cpp — SceneManager::LoadScene (both overloads), SceneManager::ProcessAnyPendingSceneChange; engine/src/Application.cpp — Application::Run; tests: SceneStorageTest.SupersededAddedSceneIsStillStored, SceneStorageTest.LoadingThePendingSceneAgainKeepsTheInstance, SceneLoadingTest.MalformedSceneFailsWithoutLosingTheCurrentOne

Guarantee

A load whose stored data is malformed never leaves the engine without a scene. The current scene stays loaded and keeps its index, and no exception escapes ProcessAnyPendingSceneChange.

Scenes dropped without being loaded PR #39

Several paths destroy a Scene that was never the loaded scene, without calling Clear(): a pending instance superseded by another LoadScene or replaced by StoreScene/UpdateScene, the validation build in AddScene(json)/FromJSON(j, true), the scene given to AddScene(scene, false), the pending instance dropped by UnloadScenes, a GetScene copy the caller releases, and the editor's HandleLoadScene validation build. The rule for all of them is in ~Scene:

  • Components that never attached get no callbacks. They never had OnAttach, so they have no scene setup to undo; they are freed (with their constructor and Deserialize state, including a LuaComponent's file-scope chunk) by their destructors only. This is the normal case: nothing attaches a scene before it is loaded.
  • Components that did attach (the owner ran ProcessAttachQueue on the scene, for example on a GetScene copy or before handing a scene to AddScene) get the normal Clear teardown: OnDisable if enabled in an active hierarchy, then OnDestroy, once, so what their OnAttach acquired (physics bodies, audio sources, script subscriptions) is released. Objects with an attached component are marked destroyed and torn down, as on a scene switch. Objects with none are not: they leave the scene unmarked, exactly as in a dropped scene where nothing attached, so an object's state never depends on its siblings.
  • A callback that throws ends this teardown; the destructor logs the error (and ignores a failure to log) instead of letting it escape.
  • SceneManager frees a scene it drops only after its own state change is complete, so an OnDestroy that calls LoadScene or AddScene is simply a later request (the last request wins) and never sees a half-updated pending scene.
  • Scenes still held by SceneManager when it is destroyed at process exit (no Application::Shutdown, for example in tests) are freed without this teardown, since physics, audio and Lua may already be gone by then. Application::Shutdown unloads scenes first, so a running game never gets there.
  • Limit: that exit guard only covers scenes SceneManager owns. A scene held elsewhere in static storage (a global std::unique_ptr<Scene>, say) and attached is torn down by its destructor whenever that static is destroyed, possibly after the engine's subsystems. Free such scenes before shutdown.

Guarantee PR #39

No dropped scene leaves an attached component without OnDestroy, and dropping a scene never gives OnDestroy to a component that did not get OnAttach. A loaded scene's Clear on a switch is unchanged: it still tears down components waiting in the attach queue (see the teardown sequence).

Design decision: a dropped scene undoes only what attached

OnAttach is where a component acquires scene resources (physics bodies, audio sources, subscriptions), and OnDestroy is where it gives them back. A scene that is dropped unloaded normally attached nothing, so running OnDestroy there would hand components a teardown for setup that never happened, which is why no callbacks run for them. But a caller can attach a scene it owns, and freeing that silently would leak what OnAttach acquired. Tying the teardown to "attached to this scene" covers both, and needs no rule about what constructors or Lua chunks must release. The loaded scene's Clear keeps its older rule (every component, attached or queued) because components there routinely spend a frame in the queue, and scripts already rely on it.

UpdateScene and DeleteScene

UpdateScene(index or name, json &data)

  • Replaces the stored data and name of the entry (copied, so the caller's JSON is untouched). The data is not validated. Malformed data is stored, and the failure only shows when that scene is loaded, which then keeps the current scene.
  • Index out of range: silently ignored. Unknown name: GetSceneIndex logs an error, then it is ignored. Index 0 is accepted (it used to be rejected).
  • If the new data renames the entry to the name of another stored scene, the update is refused with an error PR #28. Two entries with one name would make the second unreachable by name.
  • If a load of this index is pending, the caller's pending instance is dropped, so the load builds from the new data PR #28.
  • Updating the data of the loaded scene does not touch the live scene. It keeps running as it is until it is loaded again. The editor's Save uses this to refresh the snapshot: UpdateScene(GetCurSceneIndex(), GetCurSceneRef().Serialize()).

DeleteScene(name)

  • Unknown name: an error is logged and it returns false.
  • Refuses (error, returns false) to delete the loaded scene or a scene with a pending load.
  • Otherwise erases the named entry and returns true. The loaded index and a pending index shift down by one if they were after it. Before #17 it erased the loaded scene's index instead (and with nothing loaded, begin() - 1).

Source: engine/src/sceneManagement/SceneManager.cpp — SceneManager::UpdateScene (both overloads), SceneManager::DeleteScene; editor-server/src/EditorServer.cpp — EditorServer::HandleSaveScene; tests: SceneStorageTest.UpdateSceneDropsAPendingInstance, SceneStorageTest.UpdateSceneRefusesADuplicateName, SceneManagerTest.DeleteSceneRemovesTheNamedScene, SceneManagerTest.DeleteSceneRefusesLoadedAndUnknown

Note

Scenes with an empty name (or data whose "name" isn't a string) are never matched for replacement. Each AddScene of one appends a new entry.

Scene switch teardown, step by step

This is what happens from LoadScene(next) during a frame up to the first frame of the next scene, under Application::Run:

  1. LoadScene(next) records the request. The current frame continues normally: the rest of Update, coroutines, LateUpdate, audio and render.
  2. The current scene's ProcessDestroyed runs this frame's queued destroys (their OnDisable/OnDestroy, then purge).
  3. ProcessAnyPendingSceneChange takes the request.
  4. The next scene is built, unless it is the caller's pending instance. Scene::FromJSON creates every GameObject and component, deserializes them, and resolves references. Component constructors and Deserialize run now, so a LuaComponent's script chunk (its file-scope code) executes before the old scene's OnDestroy handlers. This ordering was acknowledged in the #23 review and left as is. If a script comes to depend on the opposite order, the plan is to defer running chunks until after the old scene is cleared.
  5. If the build failed: log, keep the current scene, stop here.
  6. The old scene is cleared (Scene::Clear). Every component in its root hierarchy runs OnDisable (if it was enabled and active) and OnDestroy. This is where physics bodies, audio sources, input subscriptions and script state are released. Then coroutines are stopped, objects are marked torn down, roots are detached, and all lists are emptied. Emptying the root list releases the roots: roots that nobody else holds are freed here, with their children and components. Children removed with RemoveChild are roots, so they are part of this PR #34.
  7. The index and the loaded scene are replaced, and the old Scene object is destroyed. After Clear it holds nothing, so ~Scene has no objects left to free or update.
  8. The next frame starts. ProcessAttachQueue runs OnAttach for the new scene's components, which creates physics bodies, before any fixed step or Update of the new scene.

Source: engine/src/Application.cpp — Application::Run; engine/src/sceneManagement/SceneManager.cpp — SceneManager::ProcessAnyPendingSceneChange; engine/src/sceneManagement/Scene.cpp — Scene::Clear, Scene::FromJSON; tests: LifecycleTest.SceneSwitchRunsOnDestroy, SceneSwitchTest.LeavingSceneWithComponentsDoesNotCrash

Note

Building before clearing is safe for physics. The new scene's bodies are only created in OnAttach on the next frame, and the old scene's bodies are destroyed in its OnDestroy pass. The two sets never coexist in PhysX.

Unloading at shutdown

SceneManager::UnloadScenes() (private; called by Application::Shutdown) drops any pending change and its instance (see dropped scenes), runs Clear() on the loaded scene and destroys it, and sets the index to -1. Stored scene data is kept. Application::Shutdown calls it before shutting down audio and PhysX, so OnDestroy can still release sources and bodies PR #28. Before, scenes were only freed during static destruction, after those subsystems were gone.

When Run ends (window closed or Application::Quit()), the loaded scene first gets OnApplicationQuit on its active components, then Shutdown runs.

Editor create-scene rule

The editor server's HandleCreateScene rejects a name that is already stored (HasScene) with the error "Scene already exists: <name>" PR #28. Because AddScene now replaces by name, creating a scene with an existing name would otherwise wipe that scene's stored data. Otherwise it stores the new empty scene with AddScene(scene, false) (not loaded).

Two related editor paths: HandleLoadScene parses the incoming text without throwing (invalid JSON returns an Error response PR #33) and validates it with FromJSON(json, true). Then it calls UpdateScene plus LoadScene for a known name, or AddScene(json) plus LoadScene for a new one, and processes the change immediately. HandleSaveScene refreshes the loaded scene's snapshot with UpdateScene and returns the JSON text, or an Error when no scene is loaded PR #33. All handlers run on the host's main thread, not the network thread, so these scene switches happen on the same thread as everything else that touches the scene. See Logging, health & editor.

Source: editor-server/src/EditorServer.cpp — EditorServer::HandleCreateScene, EditorServer::HandleLoadScene, EditorServer::HandleSaveScene

Note

For a new scene, HandleLoadScene builds the JSON three times: once to validate in the handler, once more inside AddScene(json), and once for the actual load. For a known scene it builds twice. Each build runs component constructors and Lua chunks. This is a cost, not a correctness problem, but script authors should not rely on a chunk running once per editor load.
