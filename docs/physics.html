Backends and build configuration

Components never talk to PhysX directly. They call Application::GetInstance().Get3DPhysicsBackend(), which returns an IPhysicsBackend*, and every call site checks it for null. PhysXBackend and JoltBackend PR #205 are the implementations; this page describes PhysX unless a section says Jolt (the Jolt backend has its own section and says what differs). Bodies are identified by a PhysicsBodyHandle: an index into the backend's body table plus a generation.

  • A default-constructed handle (INVALID_PHYSICS_HANDLE) has index == UINT32_MAX; IsValid() only checks the index.
  • Destroying a body pushes its slot onto a free list. Reusing the slot increments its generation, so a stale handle held by a component resolves to nothing (GetBodyData compares generation and the active flag). Calls through a stale handle are silent no-ops; getters return zero, Identity or 0.0f.
  • Handles are hashable (std::hash<PhysicsBodyHandle>) and compare index and generation.

Source: engine/include/engine/physics/PhysicsHandle.hpp; engine/src/physics/physx/PhysXBackend.cpp — AllocateHandle, GetBodyData, DestroyBody

PhysX is optional

The CMake option N2ENGINE_USE_PHYSX (default ON) requests PhysX. It is forced off with a warning on MinGW/GCC on Windows, on a Linux architecture other than x86_64 and aarch64, and when the binary download fails or the archive's SHA256 is not the pinned one (on the web: when building PhysX for WebAssembly fails; Linux PR #120, Windows PR #127; on Windows also when the extracted tree lacks the debug or release PhysX_64.dll). On macOS no branch matches, so PhysX is silently absent: no warning, only the generic status line "PhysX disabled - no physics backend active". Only when the binaries are actually available does the engine target define N2ENGINE_PHYSX_ENABLED=1 (PUBLIC), add the PhysX include directory and link the libraries.

On Linux PR #120 CMake downloads physx-linux-<x86_64|aarch64>-5.6.1.tar.gz from this repository's physx-dependencies-linux-5.6.1 release, requires its SHA256 to match the one pinned in cmake/PhysXLinuxHashes.cmake, extracts it into external/PhysX/physx and links the eight static libraries (libPhysX_static_64.a, Common, Foundation, Cooking, Extensions, PvdSDK, CharacterKinematic, Vehicle2) inside one -Wl,--start-group ... --end-group, then -lpthread -ldl -lrt. The libraries are Release-only and static, so there are no DLLs to copy and the Docker runtime image needs nothing extra; Debug, RelWithDebInfo and Release builds all link them; the engine never defines PX_CHECKED or PX_DEBUG. The PhysX Visual Debugger is not used on Linux: PhysXBackend opens the PVD socket on Windows builds only, so a server never dials out to 127.0.0.1:5425.

On Windows PR #127 CMake downloads physx-windows-x86_64-5.6.1-slim.zip from the physx-dependencies-windows-5.6.1 release, requires its SHA256 to match the one pinned in cmake/PhysXWindowsHashes.cmake, and extracts it into external/PhysX/physx (bin/win.x86_64.vc143.mt/{debug,release}, plus MANIFEST.txt and the licences inside that folder). A failed download or a hash mismatch turns PhysX OFF with a warning. After a verified extraction CMake writes bin/win.x86_64.vc143.mt/.archive-sha256; a stamp naming another hash makes a changed pin re-download, and a tree without a stamp (extracted from the old bin.zip, same file names) is reused as is. To bump the archive: publish it as physx-windows-x86_64-<version>-slim.zip on a release tagged physx-dependencies-windows-<version>, then change the version, tag and hash in cmake/PhysXWindowsHashes.cmake; the Windows CI cache key hashes that file.

Design decision: slim, hash-pinned Windows archive

The slim zip was derived from the original bin.zip (the original build recipe is unknown, so it cannot be rebuilt from source); the Debug and Release PhysX test legs ran against exactly these files before it was pinned. The old bin.zip stays published for older commits.

Design decision: static, Release-only PhysX on Linux, pinned by SHA256 PR #120

Static libraries mean the host binary carries PhysX and the container image needs no extra shared library, with one configuration to build and publish (PhysX's debug and checked builds are not needed to run the engine). The archives live on this repository's releases and CMake refuses any file whose SHA256 differs from the one committed in cmake/PhysXLinuxHashes.cmake, turning PhysX OFF with a warning instead of linking an unverified binary. PVD stays off on servers so a headless host never opens a debugging socket. Not verified: physics behaviour under real gameplay on Linux (CI runs the unit tests and a health check) and the aarch64 NEON path under load.

On the web (Emscripten) PR #184 CMake builds PhysX instead of downloading it: cmake/PhysXWeb.cmake runs scripts/web-build-physx.sh, which compiles the pinned PhysX commit (cmake/PhysXWebPin.cmake) as static, CPU-only libraries (PhysX, PhysXCommon, PhysXFoundation, PhysXExtensions, PhysXPvdSDK; scalar math, no GPU, no PVD, no cooking) into external/PhysX/physx/bin/emscripten.wasm32, and the engine target links those five archives. The web backend differs from the native one in three ways: the CPU dispatcher always has 0 worker threads (there are no threads, so physics.deterministic changes nothing about it), PhysX's errors and warnings go to the engine log instead of PxDefaultErrorCallback's text, and the GPU probe is never compiled (physics.gpu auto or on gives the Linux outcome: CPU scene, one warning). Choosing the backend (physics.backend) and the backend interface PR #199

The project setting physics.backend (a string in the physics block) names the project's 3D physics backend: "physx" or "jolt", case-insensitive. It is stage J2 of the plan to add a deterministic backend (issue #156): the setting, the selection and the interface additions are here (PR #205 J3 added the backend: the Jolt backend); PhysX stays the default, and Jolt runs only in a build with N2ENGINE_USE_JOLT and for a project that asks for it. Application::Init reads it with ReadPhysicsBackend, next to physics.gpu and physics.deterministic, because the backend is created once there and lives across scene switches (one backend per project, not per scene). A change needs a restart: applying it later with ApplyProjectSettings only validates it.

Design decision: the project picks the backend; an unavailable one never degrades a Deterministic project PR #199

Decided by the user on 2026-10-20 (P1 to P11: Jolt as a second 3D backend, chosen per project by physics.backend read at Init, PhysX the default). Judgement calls the plan did not cover: (1) the plan has hosts pass AUTO and the project decide; all four hosts pass PHYSX today (three are outside this change's paths), so a project's own setting wins over the host's value and the host's value is only the default for a project that does not say (AUTO and PHYSX then behave alike); (2) a backend missing from the build refuses a Deterministic project (it can never keep its promise on another backend) and falls back to PhysX with a warning for the others (they only lose what the other backend would have added); (3) the unavailable-backend refusal reuses the existing physics-backend requirement of ValidateNetwork (new environment fields backendName, backendUnavailable, backendRequested) rather than a requirement of its own; (4) the snapshot hash is named HashState as in the design, not StateHash, and returns an optional so "unsupported" is not a hash value; (5) BackendId() is the bare setting value ("physx"), without the version suffix the design's determinism fingerprint will want later.

Design decision: PhysX claims set-state, not snapshot PR #199

Teleporting a dynamic body, setting its velocities and its sleep state is what client reconciliation needs, and PhysX can do all of it, so SupportsSetState() is true and tested; the Authoritative preset no longer warns about it. Restoring a whole PhysX scene (contact caches, warm starting) cannot be done through its API, so SupportsSnapshot() stays false. Judgement calls: a kinematic body takes a target pose and ignores velocity and sleep (PhysX has no velocity for a kinematic body and refuses the call), and a sleeping dynamic body loses its velocities (putToSleep clears them), which is also what a sleeping body is.

GPU physics (physics.gpu) PR #122

The project setting physics.gpu (in the physics block of project.n2proj, next to fixedTimestep and gravity) chooses whether the rigid-body scene may run on an NVIDIA GPU through PhysX GPU dynamics. It is the groundwork for GPU particles; on its own it adds no new feature.

ValueMeaning
"off" (default; also when the key is missing or null)The CPU scene, exactly as before. No CUDA call is made at all: nothing is probed, no GPU library is loaded.
"auto"Probe the GPU. If it works the scene is the GPU scene; if not, a single warning is logged and the unchanged CPU scene is built (GPU state Unavailable).
"on"Same probe, but a failed probe is an error in the health row (GPU state Failed). The host still starts, with the CPU scene.

Values are case-insensitive. Any other value is refused with a project-settings warning and means off. The value is read from the project file by Application::Init before the physics backend is created (ReadPhysicsGpuMode), because the scene's GPU flag is fixed when the scene is created. ApplyProjectSettings only validates it, so changing it in a running editor host takes effect at the next start.

The probe

Only with auto or on, and only in a Windows build with PhysX, PhysXBackend::Initialize calls PxGetSuggestedCudaDeviceOrdinal (negative means no usable GPU), PxCreateCudaContextManager and checks contextIsValid(). On success the scene is created with eENABLE_GPU_DYNAMICS, the GPU broad phase (PxBroadPhaseType::eGPU) and the CUDA context manager; if PhysX still does not keep GPU dynamics, or scene creation fails, the context is released and the CPU scene is built instead. The Windows package already contains PhysXGpu_64.dll; it is loaded by PhysX only inside these calls. The Linux PhysX libraries are CPU-only static libraries with no GPU library, so on Linux (and with PhysX OFF) auto and on both report Unavailable (never Failed) and never touch CUDA.

The result is IPhysicsBackend::GetGpuStatus(), a GpuStatus of Disabled | Unavailable | Ready | Failed plus a detail string: the status of the scene and its probe, and only that PR #138. It feeds the Particles and SoftBodies rows of the engine health (generic SubsystemStatus values, so the editor protocol is unchanged) once each has composed it with its own failure (GPU features): Disabled and Unavailable are Disabled with the reason as the detail, Ready is Running, Failed is Failed. Lua gets Physics.IsGpuAvailable(), true only when the GPU scene is up; it reads the scene status, so a feature that gave up does not turn it false.

The particle backend seam is IPhysicsBackend::GetParticleBackend() PR #125: it returns nullptr by default, and a ParticleSystem uses the backend it returns only when its backend is Auto or PhysX; otherwise it simulates on the CPU. PhysXBackend returns its PBD particle backend when the GPU scene is up PR #129 (GPU particles). When the scene is ready the status detail reads PhysX GPU: <device name> (CUDA device N).

Design decision: GPU physics is off by default, as in Unity PR #122

GPU dynamics is a whole-scene switch: when it is on, every rigid body moves to the GPU pipeline, with different performance and contact behaviour, reduced-coordinate articulations only, and more video memory. Because it cannot be changed after the scene exists and would make a project behave differently on a machine without an NVIDIA GPU, it is opt-in. Unity likewise runs rigid bodies on the CPU and keeps effect particles separate from the physics GPU path. A project with physics.gpu off behaves the same on every machine, including the headless host.

Not verified in CI: creating the real CUDA context and GPU scene (needs an NVIDIA GPU on Windows; CI has none and only exercises the disabled path and the CPU-only mapping). The maintainer ran the GPU test described under GPU particles on a Windows PC with an NVIDIA GPU on 2026-10-14, together with the checklist, and both passed; other GPUs, drivers and Linux were not verified.

Reproducible physics (physics.deterministic) PR #161

The project setting physics.deterministic (a boolean in the physics block, default false) asks the physics backend for its reproducible-replay configuration, for tests and replays that run the same binary twice. It is stage S1 of the determinism plan in issue #157. With it off (or absent, or null) nothing changes: every existing project, scene and test builds the scene it always did. Anything but a boolean is refused with a project-settings warning and means false. Like physics.gpu it is read from the project file by Application::Init before the backend is created (ReadPhysicsDeterministic, then IPhysicsBackend::SetDeterministic), because the scene's flags cannot change once it exists; applying it later only validates it, and a change needs a restart.

With physics.deterministic on, PhysXBackend::InitializeWhy
sets PxSceneFlag::eENABLE_ENHANCED_DETERMINISM on the sceneThe PhysX 5.6.1 header (PxSceneDesc.h) promises the same result only for the same actors created in the same order and stepped the same way; the flag adds independence from additional, non-interacting actors. It still needs a consistent insertion order in a new scene, costs performance, and is not supported on GPU.
creates the CPU dispatcher with 0 worker threads instead of 4Every task then runs on the thread that calls Update. The vendor headers do not say whether results depend on the worker-thread count, so this removes the question. (The web build has 0 workers always: no threads.)
skips the GPU probe when physics.gpu is auto or onThe flag is not supported by GPU dynamics. One warning is logged, no CUDA call is made, the GPU status is Disabled with the reason, and the scene is the CPU scene.

What it does not do: it does not make N2Engine deterministic (the other blockers in issue #157, such as Lua pairs() order, the engine Random API, timeScale-scaled steps and SIMD tiers, are separate items; the timeScale-scaled steps and the frame-timed attach queue are what the network simulation modes replace PR #186, and only there), it does not make results the same on Windows and Linux (they are different PhysX binaries), and it is not a network mode. What it is expected to give, and the test that checks it, are on the testing page.

Design decision: an opt-in setting; GPU physics yields to it PR #161

Enhanced determinism costs performance and 0 worker threads costs parallelism, so the setting is opt-in and off by default, and a project without it behaves exactly as before. When both physics.deterministic and physics.gpu auto/on are set, the explicit determinism request wins and the scene is the CPU scene, with a warning, rather than a GPU scene that silently is not deterministic. This is a judgement call the plan did not cover: the alternative, refusing to start, would have been stricter.

Source: engine/src/physics/physx/PhysXBackend.cpp - PhysXBackend::Initialize, PhysXBackend::ProbeGpu; engine/src/ProjectSettings.cpp - ReadPhysicsDeterministic; tests/engine/physics/PhysXDeterminismTests.cpp.

Network presets and the backend's determinism declarations PR #187

The project setting network chooses the project's network model. This is the first stage (A1) of the netcode runtime plan, and it is data, startup checks and the choice of the simulation mode: there is no transport, no replication and no prediction yet. A project that starts with authoritative or deterministic runs its fixed-step loop as the tick loop of that mode (Application::SetSimulationMode, the simulation clock, PR #186): no time dropped, a fixed dt independent of timeScale. With the default preset none the engine behaves exactly as it did before (Init does not touch the simulation mode); the only visible difference is one more row in the engine health. Three presets exist: none (offline), authoritative (server authoritative: PhysX, client prediction and reconciliation) and deterministic (lockstep or rollback, the same result on every platform).

The preset table

Network::PresetTable() (engine/include/engine/network/NetworkPresets.hpp) holds the design's preset bundles as data, so the editor and the engine apply the same rules: one row per governed setting, with a cell for each preset (its class, its value, the design's wording and, for a locked cell, the guarantee a change loses). It has 26 rows: the 18 rows of the design's preset bundles (physics backend, GPU physics, fixed timestep, tick driver, SIMD tier, floating-point profile, transcendental functions, snapshot/restore, input delay, prediction or rollback window, state sync rate, interpolation, reconciliation, authority rules, RNG policy, ordering rules, threads, the backend picker) and the 8 transport and runtime settings the bundles do not cover.

ClassMeaning

Layers on Jolt PR #213

The engine's 32 layers and the symmetric collision matrix (Layers) work on the Jolt backend as on PhysX: each collider is on the layer of its own GameObject (ColliderSpec::layer, read when the collider is added and changed by SetColliderLayer), and two colliders interact only if each side accepts the other's layer; triggers obey the matrix too. Three things carry it:

  • Object layers. A body's Jolt ObjectLayer is (class << 1) | moving: moving is 0 for a static body and 1 for a dynamic or kinematic one; the class is the engine layer when all of the body's colliders are on one layer, else 32 (mixed: colliders on different layers, or no collider yet). There are two broad-phase layers, static and moving. When Jolt looks for pairs (from the awake bodies) its ObjectLayerPairFilter says no for two static bodies, yes when one body is mixed, and otherwise asks the matrix.
  • The matrix copy. The filters run on worker threads during Update, so they read the backend's own copy of the 32 rows (LayerMatrix), loaded in Initialize and replaced by RefreshCollisionMatrix, never the registry (which is main-thread state). That replacement is the plan's "filter swap".
  • The collider pair filter. A SimShapeFilter (PairShapeFilter) is asked about every pair of leaf shapes, that is of colliders: no if the matrix rules the layers out (the case a mixed body needs), no for two trigger colliders. Jolt keeps a resting pair's contacts in a cache and does not ask the filter about them again, so a pair that the matrix now rules out can outlive the change in the cache; the contact listener catches it, makes that contact one without a collision response, and reports nothing (ContactBridge::Handle).

Changes at runtime. SetColliderLayer sets the collider's layer, recomputes the body's object layer (BodyInterface::SetObjectLayer, which leaves the contact cache alone), wakes the body and the bodies it touches, and ends every touch the matrix now rules out: the Exit is queued at once and delivered by the next ProcessCollisionCallbacks, the same dispatch that delivers it on PhysX (PhysX needs one more simulation step to see the loss). A change that keeps a touching pair allowed does nothing to the pair: its contact stays in Jolt's cache, no Exit and Enter appear, Stay continues, also when one side is asleep (Events on Jolt). A suppressed pair that still overlaps and is allowed again is found by Jolt in the next step, because the bodies on the changed layers were woken: Enter. RefreshCollisionMatrix compares the new rows with its copy and, if a row changed, visits the bodies that have a collider on a changed layer in handle order (the refilter observer, SetRefilterObserver, is called for each: the test seam of PhysicsOrderTests) and wakes them, wakes the two bodies of every touch that involves such a layer, then ends the touches the matrix now rules out. A matrix change wakes bodies, as on PhysX: it is for setup and occasional changes, not for every frame. A layer set while a body is disabled applies when it is enabled: the body's object layer is set at once, and its pairs start when it is added back.

Design decision: a trigger collider on Jolt is a sensor sub-shape of its body, not a second body PR #213

Events on Jolt PR #213

Events are delivered by the ContactTracker, as on PhysX; what follows is what feeds it. Jolt's contact listener runs on worker threads, in no fixed order, with all bodies locked, so the backend does as little as it can there and everything else on the main thread, after Update.

  1. The listener (ContactBridge) reads only the bodies and the backend's collider list (which does not change during Update), sets each contact's settings, and appends a RawContact to a vector under a mutex: every Added, the Persisted of trigger contacts, every Removed. The settings are per collider pair: the combined friction and restitution are the average of the two colliders' dynamicFriction and restitution (PhysX's default combine; Jolt has no static friction, so staticFriction still has no effect), and a trigger pair is a sensor contact.
  2. The fold (FoldContacts, called at the end of Update) swaps the vector out, maps each Jolt body id back to the engine's handle (an id that is not a live body is dropped), and sorts the reports by (lower handle, higher handle, sub-shape of the lower, sub-shape of the higher, kind). That order is total: Jolt reports a body and sub-shape pair once per step for the bodies the engine makes (EMotionQuality::Discrete). The reports of one contact are grouped, so a Removed that comes with an Added or Persisted for the same contact in one step is no loss, and every touch that starts is handed to the tracker before any that ends: a compound body that Jolt's manifold reduction moves from one of its sub-shapes to another in one step neither exits nor enters.
  3. Which body is A. For a collision pair side A is the body with the lower handle; for a trigger pair it is the body that holds the trigger collider (as on PhysX). The contact data, which Jolt gives from its body 1's point of view, is flipped when needed so that each side sees it from its own.
  4. Sleeping. Jolt only reports the contacts of awake bodies and reports a body's contacts removed when it falls asleep (ContactListener.h), while a pair with a sleeping body is still a pair in PhysX (a ball at rest on a floor still gets Stay). The backend remembers which bodies were awake as a step began (CaptureActivity, only while it knows a contact); a Removed in a step in which a non-static body of the pair went from awake to asleep keeps the pair touching ("dormant"): Stay goes on. A dormant pair ends, with an Exit, in the first step in which Jolt looked at all its bodies (each non-static one was awake as the step began) and found no contact for it; a pair Jolt finds again is simply not dormant any more, with no event. So an Exit for a pair that separated while a body slept is delivered when that body is awake again.
  5. Removal. Disabling or destroying a body, and removing or toggling a collider, end the touches themselves (the tracker's forgotten pairs: Exit for both sides, delivered first in the next dispatch), as on PhysX, and drop what the backend remembers of them, so Jolt's later Removed for those contacts finds nothing.

What an Enter carries. The contact points (up to 64, each the middle of the two surface points Jolt found), the separation (the negative of Jolt's penetration depth), the normal from the other body to the receiver, relativeVelocity and impulse, for solid contacts only, from the contact's first report. A Stay carries only the colliders, an Exit that the engine caused none of it, as on PhysX.

Design decision: the impulse of an Enter on Jolt is an estimate (open question Q3) PR #213

Jolt calls its contact listener before the solver ("when contacts are added, the constraint solver has not run yet, so the collision impulse is unknown at that point", ContactListener.h), and the vendored Jolt has no call that returns the impulse a contact constraint applied. So ContactPoint::normalImpulse is Jolt's own estimate (EstimateCollisionResponse, run on the pair alone from the velocities before the collision, with the combined friction and restitution of the contact), Collision::impulse is the sum of normal * normalImpulse as before, and relativeVelocity is the velocity before the solve, that is the impact velocity (PhysX samples it after the step, when a ball may be bouncing already). Jolt says the estimate is accurate for two bodies colliding and not when more than two collide at once. tangentImpulse stays 0 on both backends. A game that needs the exact applied impulse needs PhysX. For you to accept as a recorded difference.

The fixed physics step

Physics runs inside the fixed-step loop of Application::Run. Each frame adds the unscaled frame delta (clamped to 0.25 s) to an accumulator, processes the scene's attach queue once, then runs one fixed step per Time::GetFixedUnscaledDeltaTime() in the accumulator. Each fixed step with a backend is:

  1. ApplyPendingChanges(): deferred scene changes. Today only SetGravity is deferred.
  2. scene.FixedUpdate(): components' FixedUpdate.
  3. Update(Time::GetFixedDeltaTime()): simulate then fetchResults(true) (blocking). PhysX's contact and trigger callbacks run inside fetchResults and only queue events.
  4. SyncTransforms(): writes simulated dynamic bodies' poses back to their GameObjects.
  5. ProcessCollisionCallbacks(): dispatches the queued events to components.

Without a backend the step is just scene.FixedUpdate(). After the fixed steps the frame runs Update, coroutines and LateUpdate; destroyed objects are purged at the end of the frame (ProcessDestroyed), which is when their bodies are released.

  • Step length. Time::fixedDeltaTime defaults to 0.02 s and is the unscaled fixed delta multiplied by timeScale. The number of steps is driven by unscaled time; the simulated length of each step is scaled. In a network simulation mode the length is the unscaled one, so timeScale does not change what a peer simulates PR #186.
  • Paused. While Time::GetFixedDeltaTime() is 0 (timeScale 0) no fixed step runs at all: no FixedUpdate, no simulation, no events. The accumulator still drains. Stepping PhysX by 0 is an error, and this matches Unity. (A network simulation mode has no such pause: its steps do not depend on timeScale PR #186.)
  • Gravity. SetGravity is queued and applied by the next step's ApplyPendingChanges; GetGravity() returns the old value until then. Repeated calls before a step keep only the last one.

When bodies are created

Bodies and shapes are created in OnAttach, not in the constructor or in AddComponent. AddComponent on an object that is in a scene queues the component on that scene's attach queue; Scene::ProcessAttachQueue runs at the start of the next frame (before its fixed steps) and calls OnAttach. A component on an object that is not in a scene is attached when the object joins one.

  • Setters called before attach (SetMass, SetGravityEnabled, SetBodyType, SetIsTrigger, SetSize, SetOffset, SetMaterial) only store the value; it is applied when the body or shape is created.
  • Calls that need a body (AddForce, SetVelocity, raycasts against the new object) do nothing until then. GetVelocity returns zero and GetHandle() is invalid.
  • Rigidbody::OnAttach returns immediately if the Rigidbody is already initialised, so re-queuing it (for example after a scene change of its object) does not create a second body.
  • If the GameObject has no Positionable, Rigidbody::OnAttach and ICollider::OnAttach create one. The body starts at the object's world position and rotation.
  • Attaching happens whether or not the object is active. A Rigidbody attached while it is disabled or its object is inactive creates its body out of the scene, and such a collider registers with its body but adds no shapes, until they are enabled (see Inactive objects and disabled components) PR #37.

Scene switches

Unloading a scene destroys its components, which releases their bodies. A dynamic body from the previous scene stops simulating and its Rigidbody's handle becomes invalid.

Guarantee: Rigidbody survives scene loads PR #34

Every scene load or switch rebuilds the scene from its JSON snapshot (the only exception is the scene object itself passed to SceneManager::AddScene(scene, true), which is loaded as-is the first time). Deactivating an object is how games hide pooled or not-yet-used objects, so an inactive object must not keep falling, pushing things or firing triggers, and its scripts must not hear about it. Every GameObject is on one of 32 layers (GameObject::GetLayer/SetLayer, default 0; see GameObjects). The engine-wide N2Engine::Layers registry (engine/Layers.hpp) names the layers and holds a symmetric collision matrix. Indices and built-in names follow Unity, so masks ported from Unity line up:

How layers reach PhysX

When a collider's shape is created (AttachColliderShape, the one path for adding, re-adding and re-creating shapes) it gets the layer of the collider's own GameObject:

  • query filter data word0 = 1 << layer, which PhysX's fixed-function query filter ANDs with a query's mask;
  • simulation filter data word0 = 1 << layer and word1 = CollisionMaskFor(layer).

CollisionEventFilterShader returns eSUPPRESS for a pair unless (f0.word0 & f1.word1) && (f1.word0 & f0.word1), i.e. each side accepts the other's layer. The check comes before the trigger branch, so triggers obey the matrix too, as in Unity. A suppressed pair raises no contacts and no events. The shader reads only its filter-data arguments, never the registry, because PhysX may call it from worker threads.

A collider on a child object uses the child's layer, not its parent's: each collider's shapes carry their own GameObject's layer. Layers are not inherited; SetLayerRecursive sets a whole subtree.

Changing a layer or the matrix at runtime

  • GameObject::SetLayer rewrites the query and simulation filter data of every attached shape of the object's colliders (ICollider::OnLayerChanged → IPhysicsBackend::SetColliderLayer). Queries see the new layer straight away. Disabled colliders, and colliders not attached yet, take the layer when their shapes are created.
  • Layers::SetCollision, Deserialize and ResetToDefaults call IPhysicsBackend::RefreshCollisionMatrix when the matrix changed; it rewrites word1 on every shape whose row changed.
  • Both then call PxScene::resetFiltering for the changed shapes (only for actors in the scene; an inactive body is filtered afresh when it is added back, with the filter data it has by then). Existing pairs are filtered again in the next step.
  • resetFiltering wakes the actor it is called on; the backend also wakes every sleeping dynamic body touching the re-filtered shapes, so PhysX re-finds those pairs promptly. A matrix change therefore wakes the bodies on the affected layers (and what they touch): it is meant for setup and occasional changes, not for every frame.

After resetFiltering, PhysX reports every pair of those shapes as lost, and the pairs the new data still allows as found again. The backend holds back the reports for re-filtered shapes during that step and settles each shape pair by its last report once the step is done (ReconcileRefilteredPairs), through the same per-shape touch lists as everything else:

Design decision: layers are Unity's, carried in PhysX filter data

Layers are 32 indices with Unity's built-in names at Unity's indices, so the existing uint32_t layerMask parameters and PhysX's 32-bit filter words fit without new APIs, and masks ported from Unity mean the same thing. The layer is a field on the GameObject saved as an index, so renaming a layer doesn't break scenes. The matrix lives in each shape's filter data rather than in a table the shader reads: that is the standard PhysX approach, costs nothing per pair and is safe on PhysX's worker threads; a change is applied with resetFiltering. Pairs are suppressed rather than killed so a later change can re-admit them, and re-filtering is settled per shape pair so a change that keeps a pair allowed is invisible to scripts, while one that rules it out still ends it with an Exit.

Triggers

Jolt: implemented in J4 PR #213: a trigger collider is a sensor sub-shape of its body's shape, see Triggers on Jolt. The rest of this section describes PhysX's shape flags.

A trigger is a per-collider setting: ICollider::SetIsTrigger(true) clears eSIMULATION_SHAPE and sets eTRIGGER_SHAPE on that collider's shapes only. Other colliders on the same body keep their own setting, so a solid box and a trigger sphere can share one Rigidbody. Toggling a trigger recomputes mass properties, because trigger shapes do not count towards inertia or centre of mass.

  • Trigger pairs raise OnTriggerEnter/Stay/Exit, never OnCollision*; triggers are not solid.
  • The setting is stored and applied when the collider attaches, so it can be set before or after the body exists.
  • Trigger shapes keep PhysX's scene-query flag, so raycasts hit them.
  • Triggers obey the collision matrix: a trigger and a collider on layers that don't collide raise no trigger events PR #44.

Collision and trigger events

Jolt: implemented in J4 PR #213 through the same ContactTracker; what feeds it is described in Events on Jolt, and what the two backends report differently is in the differences table.

Every Component has six virtual callbacks: OnCollisionEnter/Stay/Exit(const Collision&) and OnTriggerEnter/Stay/Exit(Trigger) (the trigger data is passed by value). Events are delivered to every component on the GameObject that owns each body, not only to physics components. The owner of a body is its Rigidbody's GameObject, otherwise its first registered collider's.

Components of an object that is inactive in the hierarchy receive none of them PR #37; a disabled component on an active object still does, as in Unity. An inactive object's body and shapes are out of the simulation altogether; see Inactive objects and disabled components.

The filter shader requests touch-found, touch-lost and contact-point notifications for solid pairs and the default trigger notifications for trigger pairs. PhysX's own default shader never reported solid contacts, which is why OnCollision* once never fired. Before that, it suppresses every pair the collision matrix rules out, triggers included PR #44.

Per-shape tracking, per-body-pair events

PhysX reports touches per shape pair, but events are per body pair. The ContactTracker (engine/src/physics/ContactTracker.cpp), which both backends use since J4 PR #213 (the PhysX backend kept its own copy of this logic until then, with no change of behaviour: its tests pass unchanged), keeps, for each body pair, the list of shape pairs currently touching (one map for solid contacts, one for triggers); a "shape" is whatever key the backend chooses (a PxShape on PhysX, the collider on Jolt):

  • Enter fires when the first shape pair of a body pair starts touching.
  • Stay fires once per fixed step for every body pair that has at least one touching shape pair, including the step in which it entered.
  • Exit fires when the last touching shape pair stops. A compound body that still touches through another shape does not exit.

When a shape is removed (its collider removed or disabled, or its body re-created) or a body is destroyed or taken out of the scene, the backend drops it from the touch lists itself. PhysX's later "touch lost" for a removed shape or a released or removed actor is flagged and ignored, since its pointers may no longer be valid. If that leaves a body pair with nothing touching, an Exit is queued on a separate "forgotten" list, together with the GameObject that owned each body at that moment.

Design decision: a re-created body's own object gets its Exit too

Re-creating a body (changing its type, adding or removing a Rigidbody) is an implementation detail: the object never stopped existing, so its scripts must see a balanced Enter/Exit sequence like everyone else. The alternative, keeping one pair identity across the re-creation, would hide that the old contact ended even though the new body may not touch at all (a kinematic body no longer pairs with static ones, for example). So the old pair ends for both sides, Exit(old) is delivered before Enter(new), and the side whose body is gone is reached through the GameObject recorded when the pair ended. Only an object that is being destroyed gets nothing, as before.

Dispatch order and handler safety

ProcessCollisionCallbacks dispatches in this fixed order every step:

  1. Forgotten collision Exits (pairs ended by removing a body or collider).
  2. Forgotten trigger Exits.
  3. OnCollisionEnter for each new pair.
  4. OnCollisionStay for each pair still touching.
  5. OnCollisionExit for pairs PhysX reported as lost.
  6. OnTriggerEnter.
  7. OnTriggerStay.
  8. OnTriggerExit.

For each event, body A's GameObject is dispatched first, then body B's. For trigger events body A is the trigger's body. Within a GameObject, components are called in GetAllComponents() order.

Guarantee PR #160

The order of re-filtering and of the Exit events for removed bodies and shapes does not depend on addresses or hashing. RefreshCollisionMatrix visits bodies by handle index and each body's colliders in attach order. The touching-pair maps are ordered by the two bodies' handles (smaller handle first), so waking the partners of re-filtered shapes and dispatching forgotten Exits go in body creation order. Handle indices come from a deterministic free list: a reused slot keeps its place, so after a body is destroyed and another created the order follows the slot, not the age. The same sequence of creates and destroys therefore gives the same order on every run.

Design decision: ordered maps for pairs and re-filtering PR #160

These loops used unordered_map keyed by actor pointer or by a hash of the pair, so their order varied between runs (pointers) or between standard libraries (hashes). The touch maps are now std::maps (lookup O(log n) in the number of currently touching body pairs), and the matrix refresh needs no grouping map. Collision events from PhysX itself still arrive in the order PhysX reports them; only the engine's own iteration order is pinned here. Stage S1 of the determinism plan (issue #157).

  • Queues are swapped out before iterating, and the Stay loops iterate a copy of the active pair keys and re-check each pair, so a handler that ends a pair or destroys a body cannot invalidate the iteration. A pair ended by a handler gets no further Stay this step.
  • Component snapshot. DispatchToBody snapshots the component list. Before each call it re-checks that the body still has the same owner (otherwise the rest of that side is skipped), that the component is still on the object, that it is not destroyed, and that the object is active in the hierarchy PR #37. The component's own enabled flag is not checked, as in Unity. Components added by a handler are not called for the current event.
  • Gone bodies. A side whose body no longer resolves gets nothing, except for a forgotten pair's Exit: that goes to the GameObject recorded when the pair was forgotten, if it still exists and is not being destroyed (a re-created body) PR #37.
  • Colliders are re-validated. collider/otherCollider are checked against the body's live collider list at dispatch (LiveCollider), so a collider removed by an earlier handler is reported as nullptr, never as a dangling pointer.

class Pickup final : public Component
{
public:
    explicit Pickup(GameObject &gameObject) : Component(gameObject) {}
    std::string GetTypeName() const override { return "Pickup"; }

    void OnTriggerEnter(const Physics::Trigger trigger) override
    {
        // Destroy() is deferred: until the end-of-frame purge this object still receives
        // Stay this step and Enter/Stay in later fixed steps of the frame, so guard with a flag
        if (_collected)
            return;

        // otherRigidbody is null when the other side has no Rigidbody
        if (trigger.otherGameObject != nullptr && trigger.otherRigidbody != nullptr)
        {
            _collected = true;
            GetGameObject().Destroy(); // safe: purged at end of frame, the other side then gets Exit
        }
    }

private:
    bool _collected = false;
};

Design decision: every directional value is from the receiver's point of view

A handler only ever asks "what happened to me": which way was I pushed, how fast did I hit. So collider, the contact normals, impulse and relativeVelocity are all given from the receiving body's side, and the two sides of one contact see opposite vectors. Before, normals and colliders were flipped for body B but impulse and relative velocity were not, so body B's handler saw the force on the other body. Which body PhysX calls A is arbitrary, so anything left in A's frame would make a handler's result depend on creation order.

The default maxDistance in Raycast.hpp is std::numeric_limits<float>::infinity(), but PhysX documents a raycast's distance as being in the range [0, inf) (sweeps are clamped to PX_MAX_SWEEP_DISTANCE). Mass, inertia and centre of mass PR #26

The Rigidbody's mass is authoritative, as in Unity (see the design decision below). The backend stores it per body. Inertia tensor and centre of mass come from the body's simulation shapes at uniform density, rescaled to that mass, via PxRigidBodyExt::setMassAndUpdateInertia(actor, mass, nullptr, false). Trigger shapes are excluded (includeNonSimShapes = false), so a sensor does not make its body heavier or lopsided.

  • Fallback. With no simulation shapes (or if PhysX's call fails), the body keeps its mass, its centre of mass is the actor origin, and its inertia is PxVec3(mass) (a unit radius of gyration, so it scales with mass; PhysX's own default would be (1, 1, 1) whatever the mass).
  • Invalid mass. Rigidbody::SetMass clamps values <= 0 to 0.001 with a warning. A value that bypasses it (deserialised _mass, or NaN, which fails the <= 0 test) is sanitised in the backend: a zero, negative or non-finite mass becomes 1, with the warning "Invalid Rigidbody mass {m}, using 1".
  • When it is recomputed. Only on change, never per frame: CreateDynamicBody, every Add*Collider, RemoveColliderShapes (including via UnregisterCollider), every Update*Collider (size, offset or material), SetIsTrigger and SetMass. SetBodyType re-creates the body, so the same paths cover it. Static actors are skipped; kinematic actors are updated too. A body with N colliders recomputes N times as they attach.
  • Reading it back. Rigidbody::GetMass() returns the backend's mass for a live Dynamic body and the stored value otherwise. PhysXBackend::GetInertiaTensor returns the principal moments in the mass frame (their axes follow the mass pose's rotation, not necessarily the actor's) and GetCenterOfMass the actor-local centre of mass. Both are diagnostics on PhysXBackend, not on IPhysicsBackend, and return zero for static or unknown bodies.
auto *box = go->AddComponent<BoxCollider>();
box->SetSize(Vector3(1.0f, 2.0f, 3.0f));
auto *body = go->AddComponent<Rigidbody>();
body->SetMass(2.0f);
// After the next attach: mass 2, inertia = 2/12 * (2^2 + 3^2, 1^2 + 3^2, 1^2 + 2^2)
box->SetOffset(Vector3(0.0f, 1.0f, 0.0f)); // centre of mass moves to (0, 1, 0); mass stays 2

Design decision: mass is authoritative, inertia comes from the shapes

The mass is the number a user sets and tunes on the Rigidbody, so the engine never replaces it with a value derived from collider volume and density: resizing a collider must not make an object heavier and change how it reacts to forces and impulses. Inertia and centre of mass, on the other hand, are hard to author by hand and depend on shape, so they are derived from the simulation shapes and rescaled to the chosen mass. A long box then spins more easily about its long axis and an offset collider moves the centre of mass, as in Unity's default behaviour. Trigger shapes are left out because they are sensors, not matter.

Guarantee PR #26

A collider's volume never overrides the Rigidbody's mass; adding, resizing, offsetting, removing or toggling the trigger flag of a collider moves the inertia and centre of mass and leaves the mass unchanged. An invalid deserialised mass of 0 behaves as mass 1 and the body still responds to impulses.

PhysicsMaterial

PhysicsMaterial holds staticFriction, dynamicFriction and restitution. Each collider has its own (default PhysicsMaterial::Default(): 0.5, 0.5, 0.3). Presets: Default, Ice (0.05, 0.05, 0.1), Rubber (0.9, 0.8, 0.8), Bouncy (0.5, 0.5, 0.95), Metal (0.4, 0.3, 0.5).

  • ICollider::SetMaterial updates the collider's live shapes. The backend caches one PxMaterial per exact (static, dynamic, restitution) triple and falls back to its own default material if creation fails. That fallback is (0.5, 0.5, 0.6), created in PhysXBackend::Initialize, not PhysicsMaterial::Default() (restitution 0.3).
  • Friction and restitution combine with the other shape's material using PhysX's default combine modes; the engine does not set them.
  • When deserialised, a missing field becomes 0, not the Default() value.

Forces, velocity and gravity

  • AddForce uses PhysX's default force mode (a continuous force applied over the next simulate); AddImpulse uses eIMPULSE. Both apply at the centre of mass.
  • SetVelocity/SetAngularVelocity set the linear and angular velocity directly.
