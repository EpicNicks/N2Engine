Backends and build configuration

Components never talk to PhysX directly. They call Application::GetInstance().Get3DPhysicsBackend(), which returns an IPhysicsBackend*, and every call site checks it for null. PhysXBackend is the only implementation. Bodies are identified by a PhysicsBodyHandle: an index into the backend's body table plus a generation.

  • A default-constructed handle (INVALID_PHYSICS_HANDLE) has index == UINT32_MAX; IsValid() only checks the index.
  • Destroying a body pushes its slot onto a free list. Reusing the slot increments its generation, so a stale handle held by a component resolves to nothing (GetBodyData compares generation and the active flag). Calls through a stale handle are silent no-ops; getters return zero, Identity or 0.0f.
  • Handles are hashable (std::hash<PhysicsBodyHandle>) and compare index and generation.

Source: engine/include/engine/physics/PhysicsHandle.hpp; engine/src/physics/physx/PhysXBackend.cpp — AllocateHandle, GetBodyData, DestroyBody

PhysX is optional

The CMake option N2ENGINE_USE_PHYSX (default ON) requests PhysX. It is forced off with a warning on MinGW/GCC on Windows, on Linux (binaries not configured), and when the Windows binary download fails. On macOS no branch matches, so PhysX is silently absent: no warning, only the generic status line "PhysX disabled - no physics backend active". Only when the binaries are actually available does the engine target define N2ENGINE_PHYSX_ENABLED=1 (PUBLIC), add the PhysX include directory and link the libraries.

The fixed physics step

Physics runs inside the fixed-step loop of Application::Run. Each frame adds the unscaled frame delta (clamped to 0.25 s) to an accumulator, processes the scene's attach queue once, then runs one fixed step per Time::GetFixedUnscaledDeltaTime() in the accumulator. Each fixed step with a backend is:

  1. ApplyPendingChanges(): deferred scene changes. Today only SetGravity is deferred.
  2. scene.FixedUpdate(): components' FixedUpdate.
  3. Update(Time::GetFixedDeltaTime()): simulate then fetchResults(true) (blocking). PhysX's contact and trigger callbacks run inside fetchResults and only queue events.
  4. SyncTransforms(): writes simulated dynamic bodies' poses back to their GameObjects.
  5. ProcessCollisionCallbacks(): dispatches the queued events to components.

Without a backend the step is just scene.FixedUpdate(). After the fixed steps the frame runs Update, coroutines and LateUpdate; destroyed objects are purged at the end of the frame (ProcessDestroyed), which is when their bodies are released.

  • Step length. Time::fixedDeltaTime defaults to 0.02 s and is the unscaled fixed delta multiplied by timeScale. The number of steps is driven by unscaled time; the simulated length of each step is scaled.
  • Paused. While Time::GetFixedDeltaTime() is 0 (timeScale 0) no fixed step runs at all: no FixedUpdate, no simulation, no events. The accumulator still drains. Stepping PhysX by 0 is an error, and this matches Unity.
  • Gravity. SetGravity is queued and applied by the next step's ApplyPendingChanges; GetGravity() returns the old value until then. Repeated calls before a step keep only the last one.

Source: engine/src/Application.cpp — Application::Run, Application::PhysicsUpdate; engine/src/Time.cpp; PhysXBackend::Update, PhysXBackend::SetGravity, PhysXBackend::ApplyPendingChanges. See Application & frame loop.

When bodies are created

Bodies and shapes are created in OnAttach, not in the constructor or in AddComponent. AddComponent on an object that is in a scene queues the component on that scene's attach queue; Scene::ProcessAttachQueue runs at the start of the next frame (before its fixed steps) and calls OnAttach. A component on an object that is not in a scene is attached when the object joins one.

  • Setters called before attach (SetMass, SetGravityEnabled, SetBodyType, SetIsTrigger, SetSize, SetOffset, SetMaterial) only store the value; it is applied when the body or shape is created.
  • Calls that need a body (AddForce, SetVelocity, raycasts against the new object) do nothing until then. GetVelocity returns zero and GetHandle() is invalid.
  • Rigidbody::OnAttach returns immediately if the Rigidbody is already initialised, so re-queuing it (for example after a scene change of its object) does not create a second body.
  • If the GameObject has no Positionable, Rigidbody::OnAttach and ICollider::OnAttach create one. The body starts at the object's world position and rotation.
  • Attaching happens whether or not the object is active. A Rigidbody attached while it is disabled or its object is inactive creates its body out of the scene, and such a collider registers with its body but adds no shapes, until they are enabled (see Inactive objects and disabled components) PR #37.
auto ball = GameObject::Create("Ball");
ball->CreatePositionable();
ball->GetPositionable()->SetPosition(Vector3(0.0f, 2.0f, 0.0f));
scene->AddRootGameObject(ball);

ball->AddComponent<SphereCollider>()->SetRadius(0.5f);
auto *body = ball->AddComponent<Rigidbody>();
body->SetMass(2.0f);          // stored; applied when the body is created
body->AddImpulse(Vector3::Up); // no effect: there is no body yet
// Next frame: ProcessAttachQueue -> OnAttach creates the body and the shape

Source: engine/include/engine/GameObject.inl — GameObject::AddComponent; engine/src/sceneManagement/Scene.cpp — Scene::ProcessAttachQueue; Rigidbody::OnAttach, ICollider::OnAttach; tests: PhysicsMassTest fixture (AddFloatingBody relies on creation at the next step)

Bodies, colliders and shapes

A physics body is one PhysX actor. A collider component (BoxCollider, SphereCollider, CapsuleCollider, all derived from ICollider) owns the shapes it put on a body. The Rigidbody is optional:

Components on the GameObjectResulting bodies
Colliders onlyEach collider creates and owns its own static body (CreateStaticBody with a null Rigidbody). Two colliders on one object are two static actors.
Rigidbody onlyOne body with no shapes. A dynamic one still simulates (falls under gravity) and uses the fallback mass properties; it collides with nothing.
Rigidbody and collidersOne body owned by the Rigidbody. Every collider on the same GameObject attaches its shapes to it, which makes a compound body.
Two RigidbodiesNothing prevents it. Colliders attach to the first one (GetComponent<Rigidbody>()); the second creates its own body with no shapes, which simulates separately and collides with nothing.
  • A collider only looks for a Rigidbody on its own GameObject (GetComponent<Rigidbody>()). Colliders on child objects do not join a parent's body; they get their own static bodies.
  • Attach order does not matter. When the Rigidbody attaches it calls OnAttach on every collider of its object. ICollider::OnAttach first unregisters from its previous body (destroying it if the collider owned it), then attaches to the Rigidbody's body. Collider-then-Rigidbody and Rigidbody-then-collider in the same frame both end with exactly one shape per collider.
  • Shapes are recorded per owning collider. Removing a collider (OnDestroy) calls UnregisterCollider, which detaches only that collider's shapes from the shared actor and, if the collider owned a static body, destroys it.
  • Each shape's userData is its collider, which is how events and the touch tracking know which collider touched.

Source: engine/src/physics/ICollider.cpp — ICollider::OnAttach, ICollider::OnDestroy; Rigidbody::OnAttach; PhysXBackend::AttachColliderShape, PhysXBackend::UnregisterCollider, PhysXBackend::RemoveColliderShapes; tests: ColliderThenRigidbodyGivesOneShape, RigidbodyThenColliderGivesOneShape, RemovingColliderRemovesItsShape

Guarantee

A collider contributes exactly one shape to exactly one body, whatever order the Rigidbody and colliders were added in, and a removed collider leaves no shape behind on a shared actor. Resizing a collider after it was re-attached updates the live shape (ColliderThenRigidbodyGivesOneShape).

Removing a Rigidbody

Like Unity, colliders that remain after their Rigidbody is removed become static colliders: Rigidbody::OnDestroy destroys the body, then calls OnAttach on every remaining, non-destroyed collider, and each gets its own static body. This is skipped when the Rigidbody never had a body, and when the whole GameObject is being destroyed (its colliders are about to go too).

Source: Rigidbody::OnDestroy; tests: RemovingRigidbodyLeavesStaticCollider, HandlerRemovingRigidbodyDuringDispatchIsSafe

Scene switches

Unloading a scene destroys its components, which releases their bodies. A dynamic body from the previous scene stops simulating and its Rigidbody's handle becomes invalid.

Guarantee: Rigidbody survives scene loads PR #34

Every scene load or switch rebuilds the scene from its JSON snapshot (the only exception is the scene object itself passed to SceneManager::AddScene(scene, true), which is loaded as-is the first time). Rigidbody and the three colliders are registered with the component registry as built-in components, so a reloaded physics object gets its Rigidbody back with its body type, mass and gravity flag, and a new body is created at the next attach. Before PR #34 the Rigidbody was not registered and was silently dropped, leaving collider-only static bodies.

Source: engine/src/serialization/BuiltinComponents.cpp — RegisterBuiltinComponents; tests: SceneSwitchReleasesDynamicBodies, RigidbodyAndItsSettingsSurviveASceneLoad. See Scenes & SceneManager and Serialization.

Inactive objects and disabled components PR #37

Physics follows the component's IsActive(): its own flag, and its GameObject active in the hierarchy.

What becomes inactiveEffect
The GameObject or an ancestor (SetActive(false), or reparenting under an inactive object)The Rigidbody's OnDisable takes its body out of the PhysX scene (IPhysicsBackend::SetBodyEnabled(handle, false), a removeActor), and each collider's OnDisable removes its shapes. The object neither simulates nor collides, triggers or shows up in queries.
The Rigidbody alone (Component::SetActive(false))The whole body, with every collider on it, leaves the scene. The colliders do not fall back to static bodies (Unity has no disabled Rigidbody; this is the engine's choice).
One collider (Component::SetActive(false))Only that collider's shapes are removed; the body and its other colliders carry on.
Any other componentNothing changes: as in Unity, a disabled component on an active object still receives its physics callbacks (see Dispatch), so a script that disables itself inside a zone still hears that it left.
  • Pairs end with an Exit. Pairs that end because a body or shapes left are queued on the forgotten list, like a removed collider's, and their Exit is delivered in the next step to every side whose object is still active in the hierarchy. The deactivated object's own components get OnDisable instead of an Exit; the components of an object that is still active (for example when only a collider was disabled) get the Exit, whether they are enabled or not.
  • Coming back. Re-enabling re-adds the body (first moved to the GameObject's current pose, since the object may have been moved meanwhile) and re-creates the collider's shapes with its current size, offset, material and trigger flag. Pairs that still overlap start again with an Enter in the next step. Velocities and the gravity flag are kept.
  • While out of the scene SyncTransforms does not touch the body, AddForce/AddImpulse and kinematic targets are ignored (PhysX rejects them for an actor outside a scene), and transform changes to a static body just move it.
  • The engine fires OnEnable/OnDisable only for changes of the object's effective state; for a component's own flag the physics components use the Component::OnActiveFlagChanged hook (see Active state).

Source: Rigidbody::OnEnable, OnDisable, OnActiveFlagChanged; ICollider::OnEnable, OnDisable, OnActiveFlagChanged, SetShapesAttached; PhysXBackend::SetBodyEnabled, SyncTransforms; tests: DeactivatingAnObjectTakesItOutOfPhysicsUntilReactivated, InactiveBodyDoesNotSimulateAndResumesAtItsObjectsPose, ObjectAttachedWhileInactiveStaysOutOfPhysics, DisablingAColliderEndsItsPairsAndEnablingRestoresThem, DisabledScriptComponentStillGetsPhysicsCallbacks

Design decision: inactive objects leave physics, as in Unity

Deactivating an object is how games hide pooled or not-yet-used objects, so an inactive object must not keep falling, pushing things or firing triggers, and its scripts must not hear about it. The rule is about the object: as in Unity, a disabled script on an active object still gets physics messages, so its Enter/Exit count stays balanced however it toggles itself. Only the physics components' own flags change physics, because a collider's flag is its participation. The body is removed from the scene rather than destroyed, so nothing about it (type, mass, velocity, shapes) is lost and re-enabling is cheap. The pairs it was in still end properly for the objects that remain, which is what the other side's scripts rely on to track who is inside a zone. The deactivated object itself gets OnDisable rather than an Exit: components of an inactive object get no callbacks, and OnDisable is the place to drop per-contact state. When it comes back, overlaps are reported again with Enter.

Warning

Teleporting a Dynamic body with Positionable::SetPosition does nothing to the physics body: Rigidbody::OnTransformChanged returns early for dynamic bodies, and the next SyncTransforms writes the simulated pose back over your change. Switch the body to Kinematic to drive it from the transform, or move it with forces and velocities.

Changing the body type

SetBodyType with the current type does nothing. Before the body exists it only stores the type. Afterwards it logs a warning ("Changing body type requires recreating physics body"), destroys the body through the private DestroyPhysicsBody (not OnDestroy), stores the new type and runs OnAttach again, which creates the new body immediately and re-attaches every collider to it. The colliders are not bounced through temporary static bodies on the way. Mass properties are recomputed for the new body.

Source: Rigidbody::SetBodyType, Rigidbody::DestroyPhysicsBody; tests: ChangingBodyTypeKeepsOneShape, ChangingBodyTypeKeepsMassProperties

Transform synchronisation

  • Physics to transform. SyncTransforms runs after every simulate and visits every active body that has a Rigidbody and is a non-kinematic PxRigidDynamic. It calls Positionable::SetPositionAndRotation with the actor's global pose. Kinematic bodies are skipped, so a script's move is not overwritten before PhysX consumes it; static bodies, collider-only bodies and disabled bodies (out of the scene) are skipped.
  • Transform to physics. Every change to a Positionable (and to any ancestor, because children are walked on every change) calls NotifyPhysicsComponents. If the object has a live Rigidbody, Rigidbody::OnTransformChanged pushes the world pose to a Kinematic (SetBodyTransform) or Static (SetStaticBodyTransform) body. Otherwise each collider's OnTransformChanged moves the static body it owns.
  • The notification fires on every change, so two moves in one frame both reach physics and the last one wins.
  • Moving collider-only static bodies logs "Static collider being moved frequently" on every tenth move. The counter is a single function-local static shared by all colliders.

Source: PhysXBackend::SyncTransforms, PhysXBackend::SetBodyTransform, PhysXBackend::SetStaticBodyTransform; engine/src/Positionable.cpp — MarkGlobalTransformDirty, NotifyPhysicsComponents; Rigidbody::OnTransformChanged, ICollider::OnTransformChanged; tests: KinematicBodyFollowsLatestTransform

  • SetOffset moves the shape in the body's local space (translation only; shapes cannot be rotated relative to the body).
  • Geometry, offset and material changes update the collider's existing shapes in place and recompute the body's mass properties. Before the shape exists they are just stored. Note: collider size ignores transform scale, by design

Shapes are sized only by the collider's own parameters. The GameObject's scale is never applied to them (decided in PR #20: coupling them would force users to compensate when they do not want scaled collision). Renderers do apply scale, so a scaled object's visuals and collider can differ; size the collider to match. An opt-in per-collider flag may come later.

Layers and the collision matrix PR #44

Every GameObject is on one of 32 layers (GameObject::GetLayer/SetLayer, default 0; see GameObjects). The engine-wide N2Engine::Layers registry (engine/Layers.hpp) names the layers and holds a symmetric collision matrix. Indices and built-in names follow Unity, so masks ported from Unity line up:

IndexNameNotes
0DefaultEvery object starts here
1TransparentFXReserved, unused
2Ignore RaycastLeft out of queries by default (Layers::DefaultRaycastMask)
4WaterReserved, unused
5UIReserved for UI objects
3, 6–31(unnamed)User layers: Layers::SetName(layer, name)
  • Names. NameToLayer(name) returns the index or -1 (exact, case-sensitive match); LayerToName(layer) returns "" for an unnamed or out-of-range layer. SetName refuses, with a warning and false, a built-in layer, an out-of-range one, or a name another layer already has, so a name always maps to one layer. GetMask("Player", "Enemy") builds a mask; unknown names are skipped, as in Unity.
  • Masks. A mask has bit 1u << layer set for each layer it includes (Layers::MaskOf).
  • Matrix. SetCollision(a, b, collide) sets both (a, b) and (b, a); GetCollision(a, b) reads it; CollisionMaskFor(layer) is the layer's row as a mask. Everything collides by default, a layer with itself included. Out-of-range indices are ignored with a warning.
  • Saving. Layers::Serialize() writes {"layers": [32 names], "collisionMatrix": [32 row masks]} and Deserialize reads it back; see Serialization. Nothing saves the block yet (that waits for the project file, #6), so a game sets its layers up from code or Lua at startup, as it does action maps. ResetToDefaults() restores the built-in names and an all-colliding matrix.
  • The registry is main-thread only. The physics backend copies what it needs into each shape, so the filter shader never reads it.

How layers reach PhysX

When a collider's shape is created (AttachColliderShape, the one path for adding, re-adding and re-creating shapes) it gets the layer of the collider's own GameObject:

  • query filter data word0 = 1 << layer, which PhysX's fixed-function query filter ANDs with a query's mask;
  • simulation filter data word0 = 1 << layer and word1 = CollisionMaskFor(layer).

CollisionEventFilterShader returns eSUPPRESS for a pair unless (f0.word0 & f1.word1) && (f1.word0 & f0.word1), i.e. each side accepts the other's layer. The check comes before the trigger branch, so triggers obey the matrix too, as in Unity. A suppressed pair raises no contacts and no events. The shader reads only its filter-data arguments, never the registry, because PhysX may call it from worker threads.

A collider on a child object uses the child's layer, not its parent's: each collider's shapes carry their own GameObject's layer. Layers are not inherited; SetLayerRecursive sets a whole subtree.

Changing a layer or the matrix at runtime

  • GameObject::SetLayer rewrites the query and simulation filter data of every attached shape of the object's colliders (ICollider::OnLayerChanged → IPhysicsBackend::SetColliderLayer). Queries see the new layer straight away. Disabled colliders, and colliders not attached yet, take the layer when their shapes are created.
  • Layers::SetCollision, Deserialize and ResetToDefaults call IPhysicsBackend::RefreshCollisionMatrix when the matrix changed; it rewrites word1 on every shape whose row changed.
  • Both then call PxScene::resetFiltering for the changed shapes (only for actors in the scene; an inactive body is filtered afresh when it is added back, with the filter data it has by then). Existing pairs are filtered again in the next step.
  • resetFiltering wakes the actor it is called on; the backend also wakes every sleeping dynamic body touching the re-filtered shapes, so PhysX re-finds those pairs promptly. A matrix change therefore wakes the bodies on the affected layers (and what they touch): it is meant for setup and occasional changes, not for every frame.

After resetFiltering, PhysX reports every pair of those shapes as lost, and the pairs the new data still allows as found again. The backend holds back the reports for re-filtered shapes during that step and settles each shape pair by its last report once the step is done (ReconcileRefilteredPairs), through the same per-shape touch lists as everything else:

Change while two shapes touchEventsBacked by
The pair is ruled out (matrix turned off, or an object moved to a layer the other doesn't collide with)Exit on both sides in the next step (if no other shape pair of the two bodies still touches); Stay stopsTurningCollisionOffMidContactEndsThePair, MatrixChangesEndAndRestartOverlappingTriggers, ChangingAnObjectsLayerAtRuntimeRefilters
The pair stays allowed (an object moved to another layer that still collides, or a matrix change that doesn't affect this pair)Nothing: lost-then-found nets out, Stay continues, also when one side was asleepChangingAnObjectsLayerAtRuntimeRefilters, LayerPhysicsRestingTest.*

PhysX may report a pair lost in one step and found again only in the next. So when a shape pair's last report is "lost" but the new filter data still allows the pair, its Exit is deferred by one step. The pair stays touching (Stay continues) and both bodies are woken. If "found" arrives in that step, nothing is reported. If no report arrives, the Exit is delivered then, one step late. The same one-step delay applies to a real separation of an allowed pair that happens in the step its shapes are re-filtered.

As a fallback, after that step any touch of a re-filtered shape that the new filter data rules out is ended with an Exit even if PhysX never reported it lost, so a ruled-out pair always gets its Exit and Enter/Exit stay balanced.

Source: engine/src/Layers.cpp; GameObject::SetLayer, ICollider::OnLayerChanged; PhysXBackend.cpp — CollisionEventFilterShader, AttachColliderShape, SetColliderLayer, RefreshCollisionMatrix, RefilterShapes, ReconcileRefilteredPairs; tests: LayersTests.cpp, LayerPhysicsTests.cpp (NonCollidingLayersPassThroughEachOther, TriggersObeyTheMatrix, ChildColliderUsesItsOwnLayer, CollidersAttachedAfterAMatrixChangeUseTheNewMatrix)

Design decision: layers are Unity's, carried in PhysX filter data

Layers are 32 indices with Unity's built-in names at Unity's indices, so the existing uint32_t layerMask parameters and PhysX's 32-bit filter words fit without new APIs, and masks ported from Unity mean the same thing. The layer is a field on the GameObject saved as an index, so renaming a layer doesn't break scenes. The matrix lives in each shape's filter data rather than in a table the shader reads: that is the standard PhysX approach, costs nothing per pair and is safe on PhysX's worker threads; a change is applied with resetFiltering. Pairs are suppressed rather than killed so a later change can re-admit them, and re-filtering is settled per shape pair so a change that keeps a pair allowed is invisible to scripts, while one that rules it out still ends it with an Exit.

Triggers

A trigger is a per-collider setting: ICollider::SetIsTrigger(true) clears eSIMULATION_SHAPE and sets eTRIGGER_SHAPE on that collider's shapes only. Other colliders on the same body keep their own setting, so a solid box and a trigger sphere can share one Rigidbody. Toggling a trigger recomputes mass properties, because trigger shapes do not count towards inertia or centre of mass.

  • Trigger pairs raise OnTriggerEnter/Stay/Exit, never OnCollision*; triggers are not solid.
  • The setting is stored and applied when the collider attaches, so it can be set before or after the body exists.
  • Trigger shapes keep PhysX's scene-query flag, so raycasts hit them.
  • Triggers obey the collision matrix: a trigger and a collider on layers that don't collide raise no trigger events PR #44.

Source: ICollider::SetIsTrigger, PhysXBackend::SetIsTrigger; tests: TriggerEventsFireOnBothBodies, TriggerOnlyAffectsItsOwnCollider, TriggerColliderDoesNotAffectMassProperties

Collision and trigger events

Every Component has six virtual callbacks: OnCollisionEnter/Stay/Exit(const Collision&) and OnTriggerEnter/Stay/Exit(Trigger) (the trigger data is passed by value). Events are delivered to every component on the GameObject that owns each body, not only to physics components. The owner of a body is its Rigidbody's GameObject, otherwise its first registered collider's.

Components of an object that is inactive in the hierarchy receive none of them PR #37; a disabled component on an active object still does, as in Unity. An inactive object's body and shapes are out of the simulation altogether; see Inactive objects and disabled components.

The filter shader requests touch-found, touch-lost and contact-point notifications for solid pairs and the default trigger notifications for trigger pairs. PhysX's own default shader never reported solid contacts, which is why OnCollision* once never fired. Before that, it suppresses every pair the collision matrix rules out, triggers included PR #44.

Per-shape tracking, per-body-pair events

PhysX reports touches per shape pair, but events are per body pair. The backend keeps, for each body pair, the list of shape pairs currently touching (one map for solid contacts, one for triggers):

  • Enter fires when the first shape pair of a body pair starts touching.
  • Stay fires once per fixed step for every body pair that has at least one touching shape pair, including the step in which it entered.
  • Exit fires when the last touching shape pair stops. A compound body that still touches through another shape does not exit.

When a shape is removed (its collider removed or disabled, or its body re-created) or a body is destroyed or taken out of the scene, the backend drops it from the touch lists itself. PhysX's later "touch lost" for a removed shape or a released or removed actor is flagged and ignored, since its pointers may no longer be valid. If that leaves a body pair with nothing touching, an Exit is queued on a separate "forgotten" list, together with the GameObject that owned each body at that moment.

Source: PhysXBackend.cpp — CollisionEventFilterShader, onContact, onTrigger, AddTouch, RemoveTouch, ForgetShape, ForgetPairsWithBody; tests: CollisionEventsFireOnBothBodies, CompoundTriggerExitsOnlyWhenFullyOutside

Guarantee

Both bodies of a pair receive each event, each from its own point of view: gameObject is the receiver and otherGameObject the other side (CollisionEventsFireOnBothBodies, TriggerEventsFireOnBothBodies). Enter and Exit stay balanced when a touching collider is removed and re-created in the same frame: Exit(old) is delivered before Enter(new) (RecreatingATouchingColliderKeepsEnterAndExitBalanced). They also stay balanced on both sides when a body is re-created while touching PR #37 (RecreatingABodyKeepsEnterAndExitBalancedOnBothSides).

Note

To make a kinematic mover detect a static zone, give one side a dynamic body (with gravity disabled if it must stay put). The physics tests do exactly that for their trigger "visitors".

Design decision: a re-created body's own object gets its Exit too

Re-creating a body (changing its type, adding or removing a Rigidbody) is an implementation detail: the object never stopped existing, so its scripts must see a balanced Enter/Exit sequence like everyone else. The alternative, keeping one pair identity across the re-creation, would hide that the old contact ended even though the new body may not touch at all (a kinematic body no longer pairs with static ones, for example). So the old pair ends for both sides, Exit(old) is delivered before Enter(new), and the side whose body is gone is reached through the GameObject recorded when the pair ended. Only an object that is being destroyed gets nothing, as before.

Dispatch order and handler safety

ProcessCollisionCallbacks dispatches in this fixed order every step:

  1. Forgotten collision Exits (pairs ended by removing a body or collider).
  2. Forgotten trigger Exits.
  3. OnCollisionEnter for each new pair.
  4. OnCollisionStay for each pair still touching.
  5. OnCollisionExit for pairs PhysX reported as lost.
  6. OnTriggerEnter.
  7. OnTriggerStay.
  8. OnTriggerExit.

For each event, body A's GameObject is dispatched first, then body B's. For trigger events body A is the trigger's body. Within a GameObject, components are called in GetAllComponents() order.

  • Queues are swapped out before iterating, and the Stay loops iterate a copy of the active pair keys and re-check each pair, so a handler that ends a pair or destroys a body cannot invalidate the iteration. A pair ended by a handler gets no further Stay this step.
  • Component snapshot. DispatchToBody snapshots the component list. Before each call it re-checks that the body still has the same owner (otherwise the rest of that side is skipped), that the component is still on the object, that it is not destroyed, and that the object is active in the hierarchy PR #37. The component's own enabled flag is not checked, as in Unity. Components added by a handler are not called for the current event.
  • Gone bodies. A side whose body no longer resolves gets nothing, except for a forgotten pair's Exit: that goes to the GameObject recorded when the pair was forgotten, if it still exists and is not being destroyed (a re-created body) PR #37.
  • Colliders are re-validated. collider/otherCollider are checked against the body's live collider list at dispatch (LiveCollider), so a collider removed by an earlier handler is reported as nullptr, never as a dangling pointer.

Source: PhysXBackend::ProcessCollisionCallbacks, DispatchCollisionExits, DispatchTriggerExits, DispatchToBody, LiveCollider, GetBodyOwner; tests: HandlerRemovingRigidbodyDuringDispatchIsSafe, RecreatingATouchingColliderKeepsEnterAndExitBalanced

class Pickup final : public Component
{
public:
    explicit Pickup(GameObject &gameObject) : Component(gameObject) {}
    std::string GetTypeName() const override { return "Pickup"; }

    void OnTriggerEnter(const Physics::Trigger trigger) override
    {
        // Destroy() is deferred: until the end-of-frame purge this object still receives
        // Stay this step and Enter/Stay in later fixed steps of the frame, so guard with a flag
        if (_collected)
            return;

        // otherRigidbody is null when the other side has no Rigidbody
        if (trigger.otherGameObject != nullptr && trigger.otherRigidbody != nullptr)
        {
            _collected = true;
            GetGameObject().Destroy(); // safe: purged at end of frame, the other side then gets Exit
        }
    }

private:
    bool _collected = false;
};

Design decision: every directional value is from the receiver's point of view

A handler only ever asks "what happened to me": which way was I pushed, how fast did I hit. So collider, the contact normals, impulse and relativeVelocity are all given from the receiving body's side, and the two sides of one contact see opposite vectors. Before, normals and colliders were flipped for body B but impulse and relative velocity were not, so body B's handler saw the force on the other body. Which body PhysX calls A is arbitrary, so anything left in A's frame would make a handler's result depend on creation order.

Raycasts and sweeps

The static Physics::Raycast class wraps the backend. The direction is normalised internally. Without a backend every query reports no hit.

CallResult
Raycast::Single(origin, dir, hit, maxDistance, layerMask)true and the closest hit in hit; otherwise false with hit.hit = false

  • Layer masks pick the layers a query can hit: a shape is hit only if its layer's bit is in the mask (its query word0 is 1 << layer) PR #44. Build masks with Layers::MaskOf or Layers::GetMask.
  • The default mask is Layers::DefaultRaycastMask, every layer except 2 (Ignore Raycast), as in Unity PR #44. It was 0xFFFFFFFF; pass Layers::AllLayers to include Ignore Raycast. The backend's query functions take the mask explicitly.
  • A mask of 0 hits nothing: every query returns no hit straight away PR #44. (PhysX treats all-zero query filter data as "no filter", so 0 used to hit everything.)
  • RaycastHit carries hit, point, normal, distance, bodyHandle and gameObject (the body's owner). rigidbody is set when the body has one. collider is the collider whose shape was hit (from the shape's userData, as in contact events), with or without a Rigidbody PR #37. All three queries fill hits the same way.
  • A query resets the hit. Every field of the RaycastHit passed in is cleared first, on a hit, a miss or without a backend, so a variable reused across queries never keeps a pointer from an earlier hit PR #37.
  • Inactive objects and disabled colliders are not hit (their bodies or shapes are out of the scene).
  • Queries hit trigger shapes as well as solid ones.
  • Objects are only hittable once their bodies exist, i.e. after the attach queue has run.
  • Picking (OnMouse*) is built on Raycast::Single; see Input Picking.

Raycasts from Lua Picking

The global Physics table wraps Raycast::Single and Raycast::All:

Open question

The default maxDistance in Raycast.hpp is std::numeric_limits<float>::infinity(), but PhysX documents a raycast's distance as being in the range [0, inf) (sweeps are clamped to PX_MAX_SWEEP_DISTANCE). Every test passes a finite distance; whether the default works for Raycast::Single/All/Any is unverified. Pass a finite distance.

Mass, inertia and centre of mass PR #26

The Rigidbody's mass is authoritative, as in Unity (see the design decision below). The backend stores it per body. Inertia tensor and centre of mass come from the body's simulation shapes at uniform density, rescaled to that mass, via PxRigidBodyExt::setMassAndUpdateInertia(actor, mass, nullptr, false). Trigger shapes are excluded (includeNonSimShapes = false), so a sensor does not make its body heavier or lopsided.

  • Fallback. With no simulation shapes (or if PhysX's call fails), the body keeps its mass, its centre of mass is the actor origin, and its inertia is PxVec3(mass) (a unit radius of gyration, so it scales with mass; PhysX's own default would be (1, 1, 1) whatever the mass).
  • Invalid mass. Rigidbody::SetMass clamps values <= 0 to 0.001 with a warning. A value that bypasses it (deserialised _mass, or NaN, which fails the <= 0 test) is sanitised in the backend: a zero, negative or non-finite mass becomes 1, with the warning "Invalid Rigidbody mass {m}, using 1".
  • When it is recomputed. Only on change, never per frame: CreateDynamicBody, every Add*Collider, RemoveColliderShapes (including via UnregisterCollider), every Update*Collider (size, offset or material), SetIsTrigger and SetMass. SetBodyType re-creates the body, so the same paths cover it. Static actors are skipped; kinematic actors are updated too. A body with N colliders recomputes N times as they attach.
  • Reading it back. Rigidbody::GetMass() returns the backend's mass for a live Dynamic body and the stored value otherwise. PhysXBackend::GetInertiaTensor returns the principal moments in the mass frame (their axes follow the mass pose's rotation, not necessarily the actor's) and GetCenterOfMass the actor-local centre of mass. Both are diagnostics on PhysXBackend, not on IPhysicsBackend, and return zero for static or unknown bodies.
auto *box = go->AddComponent<BoxCollider>();
box->SetSize(Vector3(1.0f, 2.0f, 3.0f));
auto *body = go->AddComponent<Rigidbody>();
body->SetMass(2.0f);
// After the next attach: mass 2, inertia = 2/12 * (2^2 + 3^2, 1^2 + 3^2, 1^2 + 2^2)
box->SetOffset(Vector3(0.0f, 1.0f, 0.0f)); // centre of mass moves to (0, 1, 0); mass stays 2

Design decision: mass is authoritative, inertia comes from the shapes

The mass is the number a user sets and tunes on the Rigidbody, so the engine never replaces it with a value derived from collider volume and density: resizing a collider must not make an object heavier and change how it reacts to forces and impulses. Inertia and centre of mass, on the other hand, are hard to author by hand and depend on shape, so they are derived from the simulation shapes and rescaled to the chosen mass. A long box then spins more easily about its long axis and an offset collider moves the centre of mass, as in Unity's default behaviour. Trigger shapes are left out because they are sensors, not matter.

Guarantee PR #26

A collider's volume never overrides the Rigidbody's mass; adding, resizing, offsetting, removing or toggling the trigger flag of a collider moves the inertia and centre of mass and leaves the mass unchanged. An invalid deserialised mass of 0 behaves as mass 1 and the body still responds to impulses.

PhysicsMaterial

PhysicsMaterial holds staticFriction, dynamicFriction and restitution. Each collider has its own (default PhysicsMaterial::Default(): 0.5, 0.5, 0.3). Presets: Default, Ice (0.05, 0.05, 0.1), Rubber (0.9, 0.8, 0.8), Bouncy (0.5, 0.5, 0.95), Metal (0.4, 0.3, 0.5).

  • ICollider::SetMaterial updates the collider's live shapes. The backend caches one PxMaterial per exact (static, dynamic, restitution) triple and falls back to its own default material if creation fails. That fallback is (0.5, 0.5, 0.6), created in PhysXBackend::Initialize, not PhysicsMaterial::Default() (restitution 0.3).
  • Friction and restitution combine with the other shape's material using PhysX's default combine modes; the engine does not set them.
  • When deserialised, a missing field becomes 0, not the Default() value.

Forces, velocity and gravity

  • AddForce uses PhysX's default force mode (a continuous force applied over the next simulate); AddImpulse uses eIMPULSE. Both apply at the centre of mass.
  • SetVelocity/SetAngularVelocity set the linear and angular velocity directly.
  • All of these require a live Dynamic body; see the body type table for what happens otherwise.
  • SetGravityEnabled toggles PhysX's per-actor gravity on a live Dynamic body and is otherwise applied at creation. World gravity defaults to (0, -9.81, 0); IPhysicsBackend::SetGravity is applied at the start of the next step.
