Lua scripting

N2Engine embeds Lua 5.4 through sol2. One process-wide LuaRuntime owns a single Lua state with the engine bindings; LuaComponent runs a behaviour script on a GameObject. This page covers the runtime, the script shape and lifecycle, serializable fields, the checked handles scripts receive instead of raw engine pointers, subscriptions, and the engine-api.lua annotation file.

LuaRuntime

LuaRuntime is a lazily created singleton (LuaRuntime::Instance()). Its constructor opens the standard libraries base, package, math, string and table only. io, os, debug, utf8 and coroutine are not opened, so coroutine.create is unavailable to scripts (engine coroutines are C++-only; see Coroutines).

All scripts share this one Lua state. Globals written by one script (or by a scene setup script) are visible to every other script.

Initialize

Initialize() registers every binding group in a fixed order (math, core, utility, physics, audio, input, events, time, debug, application, window, camera, components), then installs the module system and finally aliases T.new to the call constructor for Vector2, Vector3, Vector4, Quaternion, Color, PhysicsMaterial and BoundingBox, so both Vector3(1, 2, 3) and Vector3.new(1, 2, 3) work.

SituationResult
First call, all bindings registerLogs "LuaRuntime initialized with all bindings", returns true
First call, a binding throwsLogs "LuaRuntime failed to initialize: ...", returns false
Any later callReturns the first result without re-registering anything

Application::Init calls Initialize() and records the result as the "Scripting" subsystem status (Failed with "Lua bindings failed to register (see log)"). Tests and tools that do not run Application::Init call it themselves.

Guarantee

Calling Initialize() again is safe: values created before the second call keep working. Re-registering a usertype in the same state would strip the metatables of existing values, which is why later calls are no-ops.

Open question

LuaTest.OpensOnlySafeStandardLibraries says scripts "can't touch the filesystem", but the test only checks that io and os are nil. Whether the following is meant to be allowed is not stated.

Warning

The Lua state is not a sandbox. Do not run untrusted scripts.

  • The package library is opened in full. package.loadlib can load a native DLL or shared library and call into it, and the C searcher in package.searchers is reachable, so native code can be loaded even though the engine replaces the global require.
  • The base library is opened in full, including dofile, loadfile and load. Nothing in LuaRuntime::LuaRuntime removes them, so scripts can read and run files.
  • load and loadfile accept precompiled binary bytecode by default (mode "bt"). Malformed bytecode can crash the process or corrupt memory.

RunFile

RunFile(path) loads a .lua file through ResourceLoader and runs it once in the shared state, for example a scene setup script. It returns false and logs "Lua script not found: ..." or "Error running <path>: ..." on failure. The chunk is named after the path, so error messages point at the file.

Source: engine/src/scripting/LuaRuntime.cpp — LuaRuntime::RunFile; lua_project/src/Main.cpp; tests: LuaProjectSceneTest.RunFileReportsMissingScripts

Lifetime and Destroy

The runtime lives for the whole process. LuaRuntime::Destroy() is private and nothing calls it: destroying the state while components still hold sol::table/sol::function references into it would leave them dangling (made private in PR #24).

Source: engine/include/engine/scripting/LuaRuntime.hpp — LuaRuntime::Destroy

sol2 safety checks PR #29

engine/CMakeLists.txt defines SOL_ALL_SAFETIES_ON=1 as a PUBLIC compile definition on the engine target. sol therefore type-checks arguments in every build configuration, not only Debug. A wrong argument (nil where a GameObject is expected, a handle of the wrong type, rb.SetMass(5) with . instead of :) becomes a Lua error at the call site rather than undefined behaviour in Release builds.

Modules and require

Initialize replaces the global require with an engine version:

  1. If the module name is already in the runtime's module cache, the cached table is returned.
  2. Otherwise dots become slashes and .lua is appended: require("util.helpers") loads res://util/helpers.lua through ResourceLoader.
  3. If the file cannot be loaded, it logs "Failed to require module: ..." and returns nil.
  4. Otherwise the file runs (LoadScriptAsModule). If it returns a table, that table is the module; any other return value gives an empty table. The module is cached under its module name.
  5. If the module raises an error while loading, it logs "Failed to load module ...: ..." and returns a new empty table, which is not cached, so the next require runs the file again.

The global _loaded_modules() returns the names of the cached modules. LuaRuntime::GetModule(name) reads the cache from C++.

Source: engine/src/scripting/LuaRuntime.cpp — LuaRuntime::SetupModuleSystem, LuaRuntime::LoadScriptAsModule, LuaRuntime::PathToModuleName; tests: LuaScriptTest.RequireLoadsModulesFromAssets, LuaScriptTest.RequireOfMissingModuleReturnsNil

Note

Behaviour scripts attached with LuaComponent:SetScript do not go through the module cache. Each SetScript runs the whole file again, so every component gets its own class table and its own file-scope locals. Shared state belongs in a required module.

LuaComponent and the script table

A behaviour script is a file that returns a table, the script's "class". SetScript(path) does the following:

  1. Records the path and drops the component's reference to any previous instance. The old instance is not released: its self.component/self.gameObject are not cleared and the subscriptions it made keep firing, because they share the component's lifetime flag. Calling SetScript repeatedly therefore leaks old instances and their subscriptions.
  2. Loads the file through ResourceLoader. If it is missing, it logs a warning, sets HasMissingScript() and stops.
  3. Runs the file. If it raises an error or does not return a table, it logs an error and sets HasMissingScript().
  4. Creates a fresh instance table whose metatable is the class table, and sets self.component (this LuaComponent) and self.gameObject (its GameObject) on it. Both are checked handles PR #29.
  5. Reads SerializableFields and injects field values into the instance (see Serializable fields).
  6. Caches which per-frame and physics callbacks exist.
  7. Registers a reload callback for the module name, replacing any it registered before.

The instance's metatable is the class table itself, not a table with __index set for you. The class must set Class.__index = Class, or method lookups on self find nothing and the callbacks are never called. No error is reported in that case.

local Mover = {}
Mover.__index = Mover          -- required: the instance's metatable is this table

function Mover:OnUpdate()
    local p = self.gameObject:GetPositionable()
    if p ~= nil then
        p:SetPosition(p:GetPosition() + Vector3.Up * Time.deltaTime)
    end
end

return Mover                   -- anything other than a table: "Script must return a table"

From Lua, a component is added and given a script like this. Do it before the object joins the scene, or in the same frame (see Lifecycle):

local go = GameObject.Create("Mover")
go:AddComponent("LuaComponent"):SetScript("res://scripts/Mover.lua")
SceneManager.GetCurrentScene():AddRootGameObject(go)

The LuaComponent Lua type has SetScript(path), GetScriptPath(), HasMissingScript() and the methods every component handle has (below).

ReleaseScript

ReleaseScript() cuts the script off from its component. It runs at the end of OnDestroy and again in ~LuaComponent (for components freed without OnDestroy), and is safe to call twice. It:

  • sets the component's lifetime flag to false, so subscriptions the script made stop firing (see Subscriptions);
  • removes the component's reload callbacks;
  • sets self.component and self.gameObject to nil on the instance. A closure that kept self then gets an "attempt to index a nil value" error instead of touching freed memory.

Copies of those handles the script made earlier (local go = self.gameObject) are not cleared, but they are checked handles and fail cleanly (see Checked handles).

Source: engine/src/scripting/LuaComponent.cpp — LuaComponent::ReleaseScript, LuaComponent::OnDestroy, LuaComponent::~LuaComponent; tests: LuaLifetimeTest.DestroyedScriptLosesComponentReferences, LuaHandleTest.CopiesOfSelfErrorAfterDestroy

Lifecycle callbacks and their order

LuaComponent forwards these engine callbacks to methods of the same name on the script instance. Every call receives self. Each method is optional.

Script methodArgumentWhen it runs
OnAttachIn the first Scene::ProcessAttachQueue after the component joins a scene: at the start of the next frame, before the fixed steps. This happens whether or not the object is active. The component joins the update list only after this. Re-parenting within the same scene does not queue it again, but OnAttach runs each time the object joins a scene (GameObject::SetScene re-queues every component), for example after RemoveRootGameObject and a later AddRootGameObject. Subscriptions made in OnAttach are then duplicated.
OnFixedUpdateOnce per fixed step (0 to n per frame), before the physics step. No fixed steps while timeScale is 0.
OnCollisionEnter/Stay/ExitCollisionAfter the physics step of each fixed step (see Physics)
OnTriggerEnter/Stay/ExitTriggerSame as collisions
OnUpdateOnce per frame, after the fixed steps
OnLateUpdateOnce per frame, after OnUpdate and coroutines
OnEnable / OnDisableWhen the GameObject's effective active state changes (GameObject:SetActive on it or an ancestor), only for components whose own enable flag is on
OnDestroyFor an object in a scene: once, during teardown (destroy, RemoveComponent, scene switch), preceded by OnDisable if the component was enabled in an active hierarchy. Objects outside a scene get neither.

Per-frame callbacks (OnUpdate, OnFixedUpdate, OnLateUpdate) only reach components that are active: enabled, not marked for destruction, and active in the hierarchy. Destroys requested during a frame are processed after rendering, at the end of that frame. See Application & frame loop for the full frame order and GameObjects & components for the teardown sequence.

Guarantee

For an object in a scene, OnDestroy runs once, preceded by OnDisable if the component was enabled in an active hierarchy. Objects outside a scene get neither. During both callbacks self.gameObject, its Positionable and sibling components are still usable PR #29. This holds for all three teardown paths (destroy, scene switch, RemoveComponent).

Re-entry is not guarded: Component::RunDestroyCallbacks sets the "destroyed" flag only after OnDestroy returns, so a script that triggers teardown of its own component again from OnDisable or OnDestroy (for example by removing that component) runs the callbacks again.

Source: engine/src/scripting/LuaComponent.cpp — LuaComponent::OnAttach … LuaComponent::OnTriggerExit; engine/src/sceneManagement/Scene.cpp — Scene::ProcessAttachQueue; engine/src/gameobject/Component.cpp — Component::RunDestroyCallbacks; engine/src/gameobject/GameObject.cpp — GameObject::NotifyActiveChanged; engine/src/Application.cpp — Application::Run, Application::PhysicsUpdate; tests: LuaLifetimeTest.ScriptSeesOnDisableThenOnDestroy, LuaHandleTest.HandlesWorkDuringTeardownOfADestroyedObject, LuaHandleTest.HandlesWorkDuringTeardownOnSceneSwitch, LuaHandleTest.HandlesWorkDuringTeardownOfARemovedComponent

Note

  • No initial OnEnable. OnEnable is not called when a component first attaches, only on a later inactive-to-active transition.
  • Component:SetActive fires nothing. It only flips the component's own flag. OnEnable/OnDisable follow the GameObject's hierarchy state.
  • SetScript does not call OnAttach. If SetScript runs after the component's OnAttach pass, the new script's OnAttach never runs. The shipped scene.lua sets scripts before adding the objects to the scene.
  • File scope runs at SetScript time. The script's file-scope code runs inside SetScript, before OnAttach, and once per component.

Open question

OnApplicationQuit is never forwarded to scripts. Scene::OnApplicationQuit calls Component::OnApplicationQuit on active components when the run ends, but LuaComponent (engine/include/engine/scripting/LuaComponent.hpp) does not override it. A script method named OnApplicationQuit is never called. It is not stated whether this is deliberate.

Errors and how they are reported

Every call into a script is a protected call. A Lua error is logged and never propagates into the engine loop. The component keeps running, and the same callback is called again next frame.

File does not return a tableError "Script must return a table"; HasMissingScript() true
Error inside a callbackError "Lua <Method> error in <script path>: <message>"; no exception
Error inside a subscribed callbackError "<EventName> callback error: <message>", e.g. "InputAction callback error"

Serializable fields

A script declares editable, saved values in a SerializableFields table on its class. Each entry is either a shorthand value or a table with a default (and optionally a type):

local Fields = {}
Fields.__index = Fields
Fields.SerializableFields = {
    count   = 3,                                   -- shorthand, stored as an integer
    ratio   = 0.5,                                 -- shorthand, stored as a float
    enabled = true,
    label   = { type = "string", default = "hi" }, -- full form
    offset  = { default = Vector3(0, 1, 0) },      -- stored as {"x":0,"y":1,"z":0}
    target  = { type = "GameObject" },             -- reference field (see below)
    body    = { type = "Rigidbody" },              -- reference to a component
}

function Fields:OnAttach()
    Debug.Log(self.label .. " x" .. self.count)    -- values are fields on self
end
return Fields

Defaults and the scriptData store

The component keeps field values as JSON in scriptData. On SetScript:

  1. Extract: for each entry of SerializableFields that is not already in scriptData, the default (the shorthand value, or the table's default) is stored. Only numbers, booleans, strings and Vector3 defaults are stored. A Lua integer is stored as a JSON integer and a float as a JSON float. A Vector3 is stored as {"x", "y", "z"}.
  2. Inject: every scriptData entry is written onto the instance table as self.<name>. JSON floats become Lua numbers (via float), integers become Lua integers (via int), booleans and strings unchanged. An object with an "x" key becomes a Vector3. Missing or non-numeric axes become 0, so {"x": 1} gives Vector3(1, 0, 0).

Values already in scriptData win over defaults. A scene file's saved values therefore override the script's defaults, because Deserialize reads scriptData before it calls SetScript. SetScriptData(json) replaces the store and re-injects it. SetField<T>/GetField<T> (instantiated for int, float, bool, std::string) write and read the store from C++. SetField also writes the live instance.

Source: engine/src/scripting/LuaComponent.cpp — LuaComponent::ExtractSerializableFields, LuaComponent::InjectFieldsIntoScript, LuaComponent::SetScriptData, LuaComponent::GetField, LuaComponent::SetField; tests: LuaScriptTest.SerializableFieldDefaultsAndOverrides, LuaRobustnessTest.ShorthandFieldDefaultsAreRead, LuaRobustnessTest.PartialVectorFieldDefaultsMissingAxesToZero

Note

  • Unsupported defaults: a default of another type (Vector2, Color, Quaternion, a table) is not stored and not injected. self.<name> is then nil unless the class table defines it.
  • Script changes are not saved: the store is not updated when the script assigns self.speed = 10. Serialize writes scriptData, so runtime changes made in Lua are not saved.
  • Precision on injection: floats go through float (0.1 arrives as 0.100000001…), and integers go through int.
  • Extra keys: every key in scriptData is injected, including keys the script does not declare.

Before PR #24, a shorthand entry aborted the process (it was cast to a table without checks), integer defaults became floats, and a partial vector threw out of scene loading.

How a LuaComponent serializes

{
  "uuid": "…", "isActive": true,
  "scriptUUID": "…",                       // or "scriptPath" when the script has no meta UUID
  "scriptData": {
    "count": 3, "ratio": 0.5, "label": "hi",
    "offset": { "x": 0.0, "y": 1.0, "z": 0.0 },
    "target": { "$ref": "…uuid…" },         // reference field
    "body":   { "$ref": null }              // null reference: self.body = nil
  }
}

Deserialize resolves scriptUUID through ResourceLoader metadata. An unknown UUID logs "Script UUID not found" and marks the script missing. A scriptUUID string that is not a valid UUID is silently ignored: nothing is logged, the script is not marked missing, no script is loaded, and scriptPath is not tried. scriptPath is the fallback for older files that have no scriptUUID key. See Serialization.

Source: engine/src/scripting/LuaComponent.cpp — LuaComponent::Serialize, LuaComponent::Deserialize

Reference fields

A scriptData entry of the form {"$ref": "<uuid>"} is a reference. References are resolved after the whole scene has loaded, through the ReferenceResolver's pending references (only when Deserialize got a resolver). The field's type in SerializableFields decides what is looked up:

Field typeLookupValue on self
"GameObject"FindGameObject(uuid)A GameObject handle, or nil if not found
A scriptable component name ("Rigidbody", "BoxCollider", "LuaComponent", …), or any name longer than 9 characters ending in "Component"FindComponent(uuid)A component handle of its concrete Lua type (e.g. Rigidbody), or Component for types without one; nil if not found
Anything else, or a shorthand field (no table, no type)noneNot set

A null $ref sets the field to nil. An invalid UUID string logs an error and skips the field. A $ref that is neither null nor a string (a number, say) throws nlohmann::json::type_error from ResolveReferences, which fails the whole scene load. A reference that is not found logs a warning, sets the field to nil and sets HasUnresolvedReferences(). Before PR #24 only names ending in "Component" counted, so type = "Rigidbody" fields were silently skipped.

Checked handles PR #29

Lua never receives a raw pointer to a GameObject, component or Positionable. It receives small handle types, defined in engine/include/engine/scripting/LuaHandles.hpp. A script may keep a handle anywhere (in self, a global, a closure, a stored collision). Using it after its object is gone raises a Lua error instead of touching freed memory.

Handle (C++)Lua typeHolds

PositionableRefPositionableA GameObjectRef to its owner (a Positionable lives exactly as long as its GameObject)

When a handle is valid

A handle is valid from creation until its object's teardown has finished (GameObject::IsTornDown()). IsTornDown becomes true:

  • in Scene::ProcessDestroyed, after the OnDisable/OnDestroy pass over everything being destroyed;
  • in Scene::Clear (scene switch), after the OnDestroy pass over the scene's roots and their descendants. Scene::Clear walks only the roots, so an object detached with RemoveChild and not re-added is not torn down (see the warning below);
  • immediately, when Destroy() is called on an object that is in no scene.

Handles to the object, its components and to other objects torn down in the same pass therefore all keep working inside OnDisable/OnDestroy, and all fail afterwards. A component handle also becomes invalid when that component alone is freed (RemoveComponent), while the GameObject and its other components stay valid.

Warning

A RemoveChild-detached object is still in its scene and survives a scene switch with a dangling scene pointer; re-parent, AddRootGameObject or Destroy it before switching. GameObject::RemoveChild never calls SetScene(nullptr): the detached object's components stay in the scene's component list and keep getting OnUpdate, and Scene::Clear, which walks only the roots, does not tear it down. After the switch its handles stay valid, and a later AddComponent on it, or freeing it (~GameObject), uses the freed scene.

Validity checks and errors

  • IsValid() works on any handle, live or dead. Every component type also has IsDestroyed(), which is exactly not IsValid().
  • Every other method raises "attempt to use a destroyed <Type>" once the object is gone, for example "attempt to use a destroyed Rigidbody" or "attempt to use a destroyed GameObject". A Positionable raises "attempt to use the Positionable of a destroyed GameObject". This includes IsActive(), which used to answer false.
  • GameObject:Destroy() on an object that is already destroyed, or freed, does nothing.
  • A dead handle is not == nil. Lua does not call __eq when comparing userdata with nil, so if self.target == nil does not detect a destroyed target. Use IsValid().
-- A cached reference may outlive its object
if self.target ~= nil and self.target:IsValid() then
    self.target:GetPositionable():SetPosition(Vector3.Zero)
end

Note

Lua's Component:IsDestroyed() is not the C++ Component::IsDestroyed(). In C++ it reads the "marked for destruction" flag, which Component::RunDestroyCallbacks sets only after OnDestroy returns, so it stays false during OnDisable and OnDestroy. In Lua it is true only once the handle is invalid. Inside OnDisable/OnDestroy, both report false. Do not use IsActive() to detect teardown either: it can still be true inside OnDestroy on the RemoveComponent path (component enabled, object active in its hierarchy).

Equality

Each push to Lua creates a separate userdata, so == is implemented by __eq. It compares ownership (weak_ptr::owner_before), not addresses. As a result:

  • two handles to the same object are equal, for example go:GetComponent("SphereRenderer") == renderer or scene:FindGameObject("A") == a;
  • equality still holds after the object is freed, and a reused address never makes two different objects equal;
  • component equality works across handle types: a concrete SphereRenderer handle equals a plain Component handle to the same component;
  • a GameObject handle never equals a component handle.

Source: engine/include/engine/scripting/LuaHandles.hpp — GameObjectRef, ComponentRefBase, ComponentRef, PositionableRef, SameRef; engine/src/scripting/bindings/LuaComponentBindings.cpp — SameComponent; engine/src/sceneManagement/Scene.cpp — Scene::Clear; engine/src/gameobject/GameObject.cpp — GameObject::Destroy; tests: LuaHandleTest.LiveHandlesKeepWorking, LuaHandleTest.CachedComponentErrorsAfterRemoveComponent, LuaHandleTest.CachedHandlesErrorAfterDestroy, LuaHandleTest.CachedHandlesErrorAfterSceneSwitch, LuaHandleTest.HandlesToTheSameObjectAreEqual, LuaHandleTest.ConcreteAndPlainComponentHandlesAreEqual

How bindings use handles: Forward and BindComponentType

Bindings expose engine methods on handles with Forward<Handle, &Class::Method>(). The generated function pins the object, calls the method and returns the result:

  • Pinning: Pin() throws (which becomes the Lua error above) if the object is gone. Otherwise it holds a shared_ptr to the owning GameObject for the duration of the call, so a call that re-enters Lua (e.g. SetScript, SetActive) and triggers a GC cannot free the object mid-call.
  • Copies: a method returning an lvalue reference returns a copy to Lua. CubeRenderer:GetColor() or BoxCollider:GetSize() give values that stay valid after the object dies.
  • Compile-time check: a static_assert rejects forwarding any method that returns a raw or smart pointer, a Component, a GameObject or a Positionable. Such methods must be bound by hand and return a handle.

BindComponentType<T>(lua, name, members...) registers a component's Lua type on ComponentRef<T>. It sets the type's name used in error messages, has no constructor, and adds IsValid, IsDestroyed, IsActive, SetActive, GetGameObject and == to the given members. A Component type registered the same way is what ComponentToLua returns for components with no Lua type of their own.

using RigidbodyRef = ComponentRef<Physics::Rigidbody>;
BindComponentType<Physics::Rigidbody>(lua, "Rigidbody",
    "SetMass", Forward<RigidbodyRef, &Physics::Rigidbody::SetMass>(),
    "GetMass", Forward<RigidbodyRef, &Physics::Rigidbody::GetMass>());

Source: engine/include/engine/scripting/LuaHandles.hpp — Forward, Detail::CallPinned, Detail::IsEngineObjectReturn; engine/include/engine/scripting/bindings/LuaBindings.hpp — BindComponentType; tests: LuaHandleTest.ComponentCallKeepsItsGameObjectAlive

Ownership and garbage collection PR #29

A handle does not keep its object alive, with one exception. A handle is owning when the script may be the object's only owner:

OperationEffect on the handle
GameObject.Create(name) / GameObject(name)The returned handle owns the new object
parent:RemoveChild(child)If child was a child and is now detached from the parent, the child handle takes ownership. The object is not removed from the scene: it stays in the scene's component list, keeps updating, and is not torn down by a scene switch (see the warning above). Re-parent it, add it as a root or destroy it.
scene:RemoveRootGameObject(go)If it was a root and was removed, the go handle takes ownership
parent:AddChild(child)If the parent now holds it, the child handle releases ownership
scene:AddRootGameObject(go)If it is now one of the scene's roots, the go handle releases ownership

Ownership belongs to that handle (that userdata). A Lua variable that aliases it shares it. A separately obtained handle to the same object, for example from another FindChild, stays weak. When the last reference to an owning handle is collected, the Lua-owned object is freed (unless something else, such as a parent, still holds it).

Warning

A Lua-owned object that never joins a scene, and whose own script keeps the owning handle (for example in self), forms a reference cycle through the Lua registry. Lua's GC cannot collect it, so it is never freed. Add created objects to a scene or parent, or drop the owning handle.

Subscriptions and script lifetime

Scripts subscribe to C++ events through Subscribe(callback) on InputAction, InputActionEvent, Event, WindowResizeEvent and GameObjectEvent. Each returns an id for Unsubscribe(id). All five wrap the Lua function with MakeScriptCallback.

ScriptLifetimeScope

LuaComponent::CallLuaMethod opens a ScriptLifetimeScope around every call into its script. The scope makes the component's lifetime flag "current" (thread-local) and restores the previous one on exit, so nested calls into another component's script are handled. MakeScriptCallback captures ScriptLifetimeScope::Current() when the subscription is made:

Where Subscribe is calledCaptured ownerAfter the component is destroyed
Inside a lifecycle callback (OnAttach, OnUpdate, OnCollisionEnter, …)That componentCallback skipped
Scene setup script (RunFile), any code outside a component callNoneKeeps firing (nothing cancels it)
File scope of a behaviour script (runs inside SetScript)Whatever is current: none, or the component whose callback called SetScriptNot tied to the script's own component
Inside another subscription's callback (dispatched from C++)NoneKeeps firing

Subscribe from OnAttach (or another lifecycle method) so the subscription is tied to the component. OnAttach runs again each time the object rejoins a scene, so an object that can leave and rejoin should keep the subscription id and unsubscribe before subscribing again.

Rules

  • Skipped, not unsubscribed. A destroyed component's callbacks stay registered and are skipped at dispatch. The event they are registered on may already be gone (for example an action map replaced by Input.CreateActionMap), and unsubscribing from a stale event would be unsafe. A skipped callback stays registered until its event is destroyed, and still counts in Event:GetSubscriberCount().
  • Errors are contained. A failing callback logs "<EventName> callback error: ..." and the dispatch continues.
  • Unsubscribing inside a handler is safe (PR #22), including a handler removing itself. It is not called again. Subscribing during dispatch is also safe, and the new subscriber first runs on the next dispatch.
  • Arguments: a GameObject& argument (GameObjectEvent) arrives as a GameObject handle PR #29. Other class-type arguments, such as the InputAction, arrive by reference to the live object, not as a copy.
-- Fire once: unsubscribe from inside the handler
function Opener:OnAttach()
    local map = Input.LoadActionMap("Main Controls")
    if map == nil then return end
    local action = map:Get("Quit")
    local id
    id = action:Subscribe(function(a)
        if a:GetPhase() == ActionPhase.Started then
            a:Unsubscribe(id)
            Debug.Log("first press")
        end
    end)
end

Value types, constants and JSON

Immutable constants

Vector2, Vector3, Vector4 and Quaternion constants (Vector3.Zero, Vector3.Up, Quaternion.Identity, …) and the Color constants (Color.Red, …) are read-only properties that return a new copy on each access. Before PR #24 they were one shared object, so local v = Vector3.Zero; v.y = 5 changed Vector3.Zero for every script. Math values are plain values: assigning one copies it. See Math & SIMD.

local v = Vector3.Zero
v.y = 5
assert(Vector3.Zero.y == 0)   -- the constant is unchanged

The engine's Math table (Math.PI, Math.DEG_TO_RAD, …) is a plain table of numbers. It is separate from Lua's standard math library.

LuaToJson and ActionMapJsonFromLua

LuaToJson(value) (engine/include/engine/scripting/LuaJson.hpp) converts a Lua value for C++:

  • booleans and strings map directly;
  • numbers with an integral value below 253 become JSON integers (so 3.0 becomes 3), others become floats;
  • a table whose keys are exactly 1..n becomes an array; any other table, including an empty one, becomes an object. Non-string keys are converted to their JSON text;
  • functions, userdata (including vectors and handles) and nil become null;
  • a table that contains itself, directly or indirectly, becomes null at the point it recurs, instead of overflowing the stack (PR #24). A table referenced twice without a cycle is converted twice.

ActionMapJsonFromLua(actions) builds the JSON ActionMap::Deserialize expects from { ["Action"] = { binding, ... } }. It is what Input.CreateActionMap uses. Bindings keep their written order, and entries with a non-string key or a non-table value are skipped.

Reloading scripts

LuaRuntime::ReloadModule(path, script) drops the cached module, reloads it, and then calls every reload callback registered for that module name. It iterates a copy, because a callback may itself call SetScript and so re-register. Reload callbacks are keyed by owner (PR #18):

  • RegisterReloadCallback(module, fn, owner) adds a callback;
  • UnregisterReloadCallbacks(owner) removes all callbacks of that owner, for any module (a null owner is ignored);
  • ClearReloadCallbacks(module) removes all callbacks for one module.

LuaComponent::SetScript replaces its own callback, so calling it twice does not duplicate it, and ReleaseScript removes it. The component's callback runs ReloadScript(). If the script was missing, that retries SetScript. Otherwise it re-runs the file into a new instance, restores the saved scriptData, re-injects it and re-caches the callbacks.

Source: engine/src/scripting/LuaRuntime.cpp — LuaRuntime::ReloadModule, RegisterReloadCallback, UnregisterReloadCallbacks, ClearReloadCallbacks; engine/src/scripting/LuaComponent.cpp — LuaComponent::ReloadScript; tests: LuaLifetimeTest.ReloadCallbacksAreReplacedAndRemoved

Open question

Nothing in engine/, editor/ or editor-server/ calls LuaRuntime::ReloadModule; only tests do. Hot reload is therefore not wired to a file watcher. In addition, LuaComponent::ReloadScript leaves these semantics unstated:

  • It does not call OnAttach on the new instance.
  • It does not release the old instance. Closures the old instance subscribed keep firing, because they share the same lifetime flag.
  • It overwrites scriptData with the saved copy after extraction, so fields added by the new version get no default.
  • It does not re-resolve $ref reference fields, so they become nil.

The engine-api.lua annotation file

engine/src/scripting/bindings/engine-api.lua is a definition file for the Lua Language Server (LuaLS). It starts with ---@meta and describes the bound API with ---@class, ---@field, ---@param and ---@return annotations over empty function stubs. The engine never loads it. Nothing in the build or runtime references it, and the bindings themselves are registered in C++. It exists only for editor completion, hover documentation and type checking.

To use it, point LuaLS at the file or its folder as a library. In VS Code with the Lua extension, add the folder to Lua.workspace.library in the workspace settings, or in a .luarc.json at the project root. The repository ships neither.

{
  "workspace.library": ["../engine/src/scripting/bindings"],
  "runtime.version": "Lua 5.4"
}

Its "CORE OBJECTS" header documents the handle rules described above: validity through teardown, the "attempt to use a destroyed ..." error, == identity and ownership PR #29.

Where the file and the bindings differ

  • Mouse.Get() and the Mouse methods (GetScrollDelta, GetPosition, GetPositionDelta) are bound but not documented.
  • The engine require and the _loaded_modules() helper are not documented.
  • SceneManager.LoadScene is documented with an index only. The binding also accepts a scene name.
  • The Window instance returned by Window.Get() has GetTitle, SetTitle, GetDimensions, SetWindowMode and a clearColor field. Only the global functions are documented.
  • Camera.Main() and Application.GetCamera() are annotated as returning Camera, but return nil when there is no camera.
  • Script-side conventions are described only in prose on LuaComponent: the lifecycle methods, SerializableFields and the OnCollision*/OnTrigger* argument types have no annotations.

Subscriptions made directly in a scene script have no owning component and are never cancelled.

Behaviour script

The shipped assets/scripts/QuitHandler.lua. It subscribes in OnAttach, so the subscription stops when the component is destroyed:

local QuitHandler = {}
QuitHandler.__index = QuitHandler

function QuitHandler:OnAttach()
    local controls = Input.LoadActionMap("Main Controls")
    if controls == nil then
        Debug.Warn("QuitHandler: 'Main Controls' action map not found")
        return
    end

    controls:Get("Quit"):Subscribe(function(action)
        if action:GetPhase() == ActionPhase.Started then
            Application.Quit()
        end
    end)
end

return QuitHandler

CameraController.lua follows the same pattern. It stores input values from two subscriptions in self, and in OnUpdate moves Camera.Main() by Time.deltaTime, fetching the camera each frame rather than caching it.

Fields, cached handles and collisions

A script written against the rules on this page:

local Bouncer = {}
Bouncer.__index = Bouncer

Bouncer.SerializableFields = {
    jumpImpulse = 5.0,                          -- float
    maxJumps = 3,                               -- stays an integer
    label = { type = "string", default = "bouncer" },
}

function Bouncer:OnAttach()
    self.jumps = 0
    self.body = self.gameObject:GetComponent("Rigidbody")   -- handle or nil
end

function Bouncer:OnCollisionEnter(collision)
    local other = collision.otherGameObject
    if other ~= nil and other:IsValid() then
        Debug.Log(self.label .. " hit " .. other:GetName())
    end

    -- The cached handle may outlive the Rigidbody (RemoveComponent): check, don't compare to nil
    if self.body ~= nil and self.body:IsValid() and self.jumps < self.maxJumps then
        self.body:AddImpulse(Vector3.Up * self.jumpImpulse)
        self.jumps = self.jumps + 1
    end
end

return Bouncer
