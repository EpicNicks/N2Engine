Lua scripting

N2Engine embeds Lua 5.4 through sol2. One process-wide LuaRuntime owns a single Lua state with the engine bindings; LuaComponent runs a behaviour script on a GameObject. This page covers the runtime, the script shape and lifecycle, serializable fields, the checked handles scripts receive instead of raw engine pointers, subscriptions, and the engine-api.lua annotation file.

LuaRuntime

LuaRuntime is a lazily created singleton (LuaRuntime::Instance()). Its constructor opens the standard libraries base, math, string and table only, and then restricts base (see What scripts cannot reach). package, io, os, debug, utf8 and coroutine are not opened, so coroutine.create is unavailable to scripts (engine coroutines are C++-only; see Coroutines).

All scripts share this one Lua state. Globals written by one script (or by a scene setup script) are visible to every other script.

Initialize

Initialize() registers every binding group in a fixed order (math, core, utility, physics, audio, input, events, time, debug, application, window, camera, components), then installs the module system and finally aliases T.new to the call constructor for Vector2, Vector3, Vector4, Quaternion, Color, PhysicsMaterial and BoundingBox, so both Vector3(1, 2, 3) and Vector3.new(1, 2, 3) work.

SituationResult
First call, all bindings registerLogs "LuaRuntime initialized with all bindings", returns true
First call, a binding throwsLogs "LuaRuntime failed to initialize: ...", returns false
Any later callReturns the first result without re-registering anything

Application::Init calls Initialize() and records the result as the "Scripting" subsystem status (Failed with "Lua bindings failed to register (see log)"). Tests and tools that do not run Application::Init call it themselves.

Guarantee

Calling Initialize() again is safe: values created before the second call keep working. Re-registering a usertype in the same state would strip the metatables of existing values, which is why later calls are no-ops.

What scripts cannot reach PR #34

Scripts are project content, so they get no way around the asset pipeline. The constructor enforces this:

  • No package library. That removes package.loadlib, package.searchpath and the C and file searchers, so scripts cannot load native code or open arbitrary paths. The engine's own require (below) still works.
  • No dofile or loadfile. Both are set to nil after base is opened.
  • load takes source text only. It is wrapped so the underlying call always uses mode "t". A binary chunk returns nil plus an error, whatever mode is asked for, and a mode without "t" (for example "b") loads nothing, as in standard Lua. An explicit env argument is passed through; an omitted one keeps the globals.
  • The engine's own loading is text-only too. LuaRuntime::RunSource runs source with sol::load_mode::text, and RunFile, require and LuaComponent::SetScript all go through it. A .lua asset that contains precompiled bytecode is rejected with a load error instead of running. Crafted bytecode could otherwise corrupt the VM.

Guarantee

io, os, package, dofile and loadfile are nil; require is the engine's function; load runs text with or without an environment and returns nil for any binary chunk; RunSource rejects bytecode.

Note

This closes the file-system and native-code routes. It is not a security boundary for untrusted code: every script shares one state and the full engine API. CPU time and memory are bounded (next section), but only by the limits listed there. A game and the editor's --play child therefore still run whatever scripts the project holds. The editor host that edits does not run them at all (Execution policy, below); it still listens on loopback by default (see Logging, health & editor).

Execution policy: the editor host that edits never runs project Lua PR #179

Loading a scene deserialises its components, and deserialising a LuaComponent used to run its script's top-level chunk in the shared state with every engine binding. LuaRuntime::SetExecutionPolicy changes that for a whole process. It is process-wide because an edit-mode scene is marked as such only after it is built, and building it is what ran the script: a per-scene switch comes too late.

PolicySet byWhat the process does with project Lua
Run (the default)Nothing: a game, the editor's --play child and every test that does not ask otherwiseEverything on this page, unchanged: the chunk runs, a LuaComponent has an instance, callbacks run.
DeclarationsOnlyN2EditorHost when it has no --play scene (Host.cpp, next to Application::SetScriptQuitAllowed), before any scene loadsNo project script runs in the engine's state, ever. A LuaComponent reads the fields its script declares (below). LuaRuntime::GetExecutionPolicy() and RunsScripts() read the setting; nothing changes it back.

Under DeclarationsOnly:

  • A component reads declarations. LuaComponent::SetScript and ReloadScript do not touch the engine's Lua state. They ask the ScriptDeclarationCache for the DeclarationResult of the script's source text (DeclarationEvaluator) and fill from it what the instance used to give: the defaults a component's scriptData lacks (saved values win), the "keep only the fields the new script declares" rule when the script is a different one, and DescribeFields (so GetLuaFields and the inspector), through the same MakeLuaFieldInfo a running instance uses. There is no instance, so $ref fields stay as saved in scriptData and are never resolved, and a scriptData edit changes only the data.
  • Nothing else runs. LuaRuntime::RunSource, the one door through which the engine runs script text (RunChunk, RunFile, require and module loading all come through it), answers a load error ("Lua is not run on this host: it reads script declarations only") without compiling anything. LuaComponent lifecycle, collision and pointer calls return at once, and HasMethod answers false, so a deleted object or a scene switch runs no script's OnDisable or OnDestroy (C++ components' callbacks are unaffected). Application.Quit is a logged refusal ("Application.Quit is refused: this host does not run scripts"); no script can reach it, so it guards a future path. The engine's Lua state and its bindings still exist on such a host (Application::Init makes them); only project code does not run in it.
  • A script whose declarations cannot be read keeps its data. A syntax error, a script that returns no table, a budget or time-out, an unreadable file contents, or a list of fields that only the engine could give (SerializableFields = Config.Fields) leaves scriptData exactly as it is, skips the "keep only declared fields" step, sets HasMissingScript() (as a script that fails to run does), and makes DescribeFields list scriptUUID and then every key of scriptData, sorted, each of the kind its value has: an integer is Int, another number Float, a boolean Bool, a string String, an object with an x key Vector3, anything else (a {"$ref": ...} too) Json. Nothing is hidden or dropped. The reason is a log line, once per evaluation, not silence. A script that simply declares no fields (no SerializableFields) is not a failure: it has no script fields and keeps nothing it does not declare, as a running one does. A script whose file is missing is a missing script with no script fields, as before. A refusal (below: no worker free, the command's evaluation budget spent, shutdown, a thread that could not start) is not the script's answer and is not kept as one: the component shows the same shape meanwhile, logs "The declarations of <path> are not read now (...)" once, and reads the script again (with the same arguments) the next time it is described (DescribeFields, so GetLuaFields and GetComponent) or asked HasMissingScript(); a reload that is refused keeps the previous declarations meanwhile.
  • A field whose default came from the engine (speed = Config.Speed) is listed, with the kind a declared type = ... gives, otherwise Json, and gets no default in scriptData; the log line says it is unknown here. Declare a type = for a computed default that needs the engine. The other differences from a real run (stubs, branches on an engine value) are in the evaluator's list.
  • Hot reload runs nothing. LuaRuntime::ReloadModule drops the cache's entries of the path whose source differs from the new one, and tells every component that read declarations from that module to read them again (ScriptDeclarationCache::NotifyReloaded); no module table is made, no chunk runs. A new version whose declarations cannot be read leaves the component on the previous declarations ("Keeping the declarations of the running version of ...", as a running instance is kept); the next write that fixes the script reloads cleanly. The same text read again is a cache hit.

ScriptDeclarationCache. One entry per resource path, valid for the hash of the source text (two independent 64-bit hashes and the length), never a file time: a write within the file system's time granularity must not serve an old declaration. The same text read by two components, or again by an undo, a snapshot restore or a second LoadScene, is evaluated once. The cache holds at most 1024 paths and starts over if a project has more. It logs once per evaluation, as Script <path>: <reason>. Components subscribe to reloads through it instead of through LuaRuntime::RegisterReloadCallback, and a component's destructor unsubscribes without making the runtime (LuaRuntime::HasInstance).

Evaluation is off the command thread. A script can make Lua's own garbage collector do quadratic work inside one C call (tables with weak keys, __mode = "k"), which neither the instruction hook nor the allocator cap can interrupt; the evaluator's own deadline cannot either. So the cache never evaluates on the thread that asks:

  • Each evaluation runs on a worker thread. The caller waits at most DefaultDeadlineMillis (2000 ms, also the evaluator's own wall-clock limit) plus 250 ms of grace, so an evaluator that stops by itself at the deadline reports it first. Past that the caller abandons the call and gets a failed declaration (declared false, timedOut and budgetExceeded set, an error saying it was abandoned).
  • The worker owns what it uses: a copy of the source, its own throwaway state and a shared result slot. After abandonment it never reads or writes the cache or any host data, and its late result is dropped.
  • The timeout is recorded under that source's hash, so the same text is not evaluated again in a loop; an edit is a new text and a new attempt.
  • At most MaxWorkers (4) workers exist at once, abandoned ones included. A further evaluation answers a failed declaration at once ("... script evaluations are still running ...") and is not recorded, since a later attempt may succeed; so do an evaluation after Shutdown and one whose thread cannot be started (any exception from starting it, std::bad_alloc included, gives the slot back).
  • The deadline bounds one evaluation, and a command can need many (a scene of several scripts). So the editor host opens a ScriptDeclarationCache::CommandBudget for every command (EditorServer::ExecuteCommand), for the asset watcher's poll and for the startup scene: every evaluation started on that thread while it is open shares one wall-clock allowance, DefaultCommandBudgetMillis (3000 ms). The caller waits at most what is left of it; once it is spent a further evaluation answers at once ("The evaluation budget for this command is exhausted: ...") without starting a worker, and a wait it cuts short is given up the same way. Both are refusals: not recorded (the script is not at fault), so the next command reads the script again. A worker whose wait was cut short keeps running and keeps its slot, and the next read of the same text (same path, same hash) waits for that worker instead of starting another: its answer, even one that arrives after the command that started it, is taken and recorded as usual; past its own deadline and grace (counted from its start) it is a recorded timeout. So one stalling text holds one slot however often it is asked. One stalling script still gets its whole deadline and grace; a second only what is left. Budgets nest without an inner one extending the outer one. Without one (a library caller, a test) only the per-evaluation deadline holds.
  • ScriptDeclarationCache::Shutdown(maxWait) stops new evaluations and waits up to maxWait (1 s by default; the host calls it after the server stops) for the running workers, and returns how many are still running. A thread cannot be interrupted, so one stuck in a long collection is left and the process exits around it. That is safe because everything it touches is heap state that is never destroyed (the cache and the worker bookkeeping are made on first use and leaked on purpose) and it holds no host data. The vendored Lua is not patched to bound the collector.
  • A build with no threads (N2ENGINE_SINGLE_THREADED, the default web artifact) evaluates on the calling thread, where only the evaluator's own wall-clock check bounds it, and cannot abandon anything. The editor host is not a web target (it is not built there), so this fallback is only for the engine library.

The deadline, the command budget, the evaluator and the clock-free parts are test hooks of the cache (SetDeadlineMillis, SetCommandBudgetMillis, SetEvaluatorForTest, ResetForTest, GetStats, LiveWorkers).

Guarantee

With DeclarationsOnly, loading, opening, snapshotting, undoing and reloading a scene or script, and deleting an object that has a LuaComponent, run no project Lua in the engine's state: no global is set, Application.Quit does not end the host, and the state is not used for it. A script that loops forever, quits or sets a global gives the same editor answers as one that does nothing. A script that stalls the evaluator's thread is abandoned at its deadline, and a command's evaluations together never hold it longer than its evaluation budget (3 s by default; one deadline plus the grace fits inside it), however many slow scripts its scene has: past that the rest are refused for that command and read by a later one. The command's other work (building the scene, answering) is not part of that bound.

Design decision: the editor host that edits never runs project Lua, instead of running it with limits PR #179

Budgets (above) stop a loop and a memory bomb but leave every binding reachable from a script that runs while a scene is being built: GameObject.Create, SceneManager.LoadScene, globals shared by every script, and OnDisable/OnDestroy running with full bindings when an object is deleted or a scene replaced. Running chunks also happened two or three times per LoadScene and once more per component on a reload. The editor needs only a script's declarations, so the host reads them in a throwaway state with no bindings and caches them by content. The cost: a field whose default comes from the engine is unknown in the editor (declare type =), a script that branches on an engine value may declare differently than at play, and Lua OnDisable/OnDestroy no longer run when the editor deletes an object (nothing was ever attached, so there was nothing to undo). The play host and the game run scripts as before. Decided on the security audit of the editor host (finding F3, part b; the plan's option B, approved 2026-10-15, including the loss of those two callbacks).

Design decision: a worker that is abandoned at its deadline, not the command thread and not a patched Lua PR #179

The weak-key collector stall cannot be stopped from Lua or from the evaluator, and the host runs commands on one thread, so evaluating there would let a scene stall the host. Bounding the collector would mean changing the vendored Lua, which the engine keeps to one small patch (Reproducible Lua). A worker with a deadline needs no change to Lua: the stuck thread is left alone (it owns its own state and result, and the cap on workers bounds how many can be stuck), and the host answers the command with the failed-declaration shape. The thread is detached with shared ownership and a leaked bookkeeping object, rather than joined, because a join on a thread stuck in the collector would hang the host's exit; Shutdown waits a bounded time instead. A deadline per evaluation alone would let a scene of N slow scripts hold one command N deadlines long, so each command also has one evaluation budget; what it refuses is retried by a later command rather than recorded, because the script is not at fault, and a component does not keep a refusal as its script's answer. A shorter deadline was not chosen instead: it would fail a script that is merely slow to read even when it is the only one.

Instruction budget and memory cap PR #159 PR #173

The Lua state has two limits, applied in every build (a game, the editor's --play child, the editor host that edits). Without them a script that loops forever, or builds strings until the machine is out of memory, ends the process; on the editor host a client could put such a script in a scene and set it as the startup scene. Since PR #179 the editor host that edits runs no project script at all (Execution policy), so there the limits are a second line of defence; the game and the play host rely on them.

LimitDefaultWhat happens at the limit
Instructions per entry50,000,000 Lua VM instructions (about 0.1 to 0.5 s of PUC Lua)The running script gets a Lua error, "script exceeded its instruction budget of 50000000".
Memory of the state256 MiB, for all scripts togetherThe allocation that would pass the cap fails, and Lua raises its ordinary "not enough memory" error.
  • The budget is per outermost entry. It is refilled each time C++ calls into Lua from outside Lua: RunSource (so RunFile, require, LoadScriptAsModule and ReloadModule), each lifecycle, collision, trigger and pointer call into a LuaComponent, the script instance's creation, field extraction and injection (they can run the script's __index and __newindex), and each event, input and UI callback (MakeScriptCallback). These are all LuaBudgetScopes. An entry made while a script is already running (a binding that calls back into Lua, require inside a chunk, an event raised from Lua) shares the budget that is running and does not refill it, so a script cannot get more by calling out and back.
  • pcall and xpcall do not catch it. Once the budget is spent the count hook fires on every instruction and raises again, until the outermost entry ends; and the sandbox's pcall and xpcall re-raise a budget error they are handed. The script's xpcall message handler is never handed the budget error: Lua calls a message handler where the error is raised, and the budget error is raised inside the count hook, where the VM runs with hooks off, so the handler's instructions would not be counted and a looping handler would never end. The sandbox's xpcall passes the script's handler through a small wrapper that hands a budget error on unchanged and every other error to the script's handler, which then runs with the budget counting as usual (a handler that loops after an ordinary error is aborted like any loop).
  • A faulted component stays off. A LuaComponent whose call ran out of instructions or memory is logged once ("Lua OnUpdate in ... aborted: ... The script is switched off until it is set again or reloaded.") and skips every later lifecycle call, so a looping OnUpdate does not burn the whole budget each frame. Setting its script again or reloading it clears the fault. A script callback (an event, input action or button listener) that runs out is logged once and switched off. A chunk that runs outside a component (RunFile, require) logs its limit error once per chunk name. The engine and the editor host keep running and keep answering commands.
  • One state. All scripts share the one Lua state, so the 256 MiB cap is shared too: one script that holds a lot leaves less for the others. Registering the engine's bindings uses a small fraction of it (checked by LuaBudgetTest.TheDefaultsAreGenerousAndTheStateStartsSmall).
  • Changing them. LuaRuntime::Instance().SetLimits({instructionsPerEntry, maxBytes}) and GetLimits(); a value of 0 means unlimited, for tools. The cap takes effect at once and the budget at the next entry. GetMemoryUsed() reports what the cap counts. Tests lower the limits through this API; the defaults are not changed for them.

What is not limited

The count hook sees Lua instructions, not work done inside one C function. A single call can take long and use no budget: a pathological string.find or string.gsub pattern, string.rep or table.concat just under the memory cap (the copy itself takes time), a very large table.sort (its Lua comparator is counted, a built-in comparison is not), and anything the engine's own bindings do (a physics step, a model load). Memory held outside the Lua state (meshes, textures, audio) is not counted by the cap. The limits make a runaway script stop; they do not make the sandbox safe for hostile code.

Design decision: a count hook and a counting allocator, per entry

The Lua state is PUC Lua built from source, and the sandbox opens no coroutine library, so a count hook on the one state sees every script instruction, with one exception the sandbox closes: the VM runs a __gc finalizer with its debug hooks off, so setmetatable refuses a metatable that has __gc and a script class that defines it fails to load. Reading the script's tables from C++ (its __index, SerializableFields) runs inside a Lua protected call, so a budget or memory error there is an ordinary logged error. A reload (ReloadModule) is one entry: the module run and every component's reload callback share a budget, while each component deserialised by a scene load is its own entry. An instruction count is cheaper and steadier than a wall clock (no timer calls, the same result on a slow CI machine) and the budget is generous (50 million; the repository's demo and test scripts have no loop near that size, which was checked by reading them, not by measuring), so a normal script is not expected to meet it. It is reset per outermost entry rather than per frame, so a long load and a short update each get a full budget, and not per call, so nesting cannot be used to multiply it. The memory cap is a lua_Alloc that returns NULL past the cap: Lua then runs a full collection, retries, and raises its own memory error, which every protected call already handles.

Engine reads of script tables run in a protected call, so a script's __index error does not reach the panic function. When the budget is spent or the memory cap is hit, LuaRuntime::ProtectedCall reports the budget or memory error from the runtime's own state instead of reading the error object off the stack (LuaRuntime::LimitAwareError; a component's lifecycle call and a script callback report it the same way, and take a memory error from the call's status, sol::call_status::memory, not from its text). The error unwinds the C++ frames of the engine code doing the read, and where those frames pop the stack while they unwind (MSVC runs C++ destructors on Lua's longjmp), Lua takes the wrong stack slot as the error object: in the MSVC Debug build the reported error was the key being read. Known limitation: an ordinary error (not the budget, not memory) raised inside such a read is still taken from the stack, so on MSVC Debug and on the web build its logged text can be wrong (both run C++ cleanups on Lua's longjmp: MSVC by design, the web build because its longjmp is a WebAssembly exception; the web job runs these tests and passes with the weaker check); and on Linux Lua's longjmp skips the destructors of the C++ objects in the read (sol references, JSON values, strings), so each such error leaks them. The leaked sol references hold registry slots and memory that count against the cap: a script whose metamethod errors on every read, in a scene loaded over and over or a tight loop of reads, leaks until the memory cap trips, which then faults the component like any memory error. An error raised outside every protected call (an allocation outside one) still reaches Lua's panic function, which sol turns into a C++ exception. Lua resets the thread before it calls the panic function but leaves three of its fields as the error found them, so the engine's panic function repairs them before the exception leaves (engine/src/scripting/LuaPanicRepair.cpp, the one file that reads Lua's internal thread state): the hook flag, which is off when the error came from the count hook and would otherwise leave the instruction budget switched off for good; the thread status; and the call counter (nCcalls), set back to what a fresh main thread has: its C-call half would otherwise leave the state failing every call with "C stack overflow" after about two hundred such errors, and its non-yieldable half would grow with every error too. A guard stops the build if the vendored Lua is not 5.4.8, so an upgrade re-checks these internals. The stack's values are not repaired: Lua's reset cuts the stack down to its base and the error object. The engine's panic function (in place of sol's default_at_panic, which would empty the stack) then pads it with nils up to 16 slots, within the slots the reset reserved, so nothing is allocated, before it throws the error as a sol::error. A C++ object that held Lua stack values across the unprotected operation that failed pops whatever is there when the exception destroys it; sol's own message-handler guard pops one slot while the exception leaves a protected function call whose arguments could not be pushed. A pop below the base makes Lua treat the base slot as a variable to close and call it: that raises a new error outside any protected call, a second panic inside a destructor, and std::terminate, whether or not the cap is reached. The padding keeps pops above the base only while the frames the exception unwinds pop 16 values or fewer. That is why the engine's loading (LuaRuntime::RunChunk, used by RunFile, require, hot reload and LuaComponent) keeps at most a chunk's first return value on the stack: a module that returns twenty values leaves one. The engine makes no unprotected Lua calls. The places where it can still allocate outside a protected call, and so panic at the memory cap, are: the arguments sol pushes before a component method's protected call (the instance and any argument; CallLuaMethod) and before a script callback's (an event's handle argument, such as the InputAction of Subscribe; MakeScriptCallback), including sol's stack-space checks while it pushes, which can grow the stack; the collision and trigger objects built for OnCollision* and OnTrigger* (CallLuaMethodWithArgument). The sol references the engine creates or copies outside a protected call (luaL_ref can grow the registry) are not on this list: each is made from a reserved registry slot, inside a protected call, or by a move (Registry references, below). CallLuaMethod, MakeScriptCallback and CallLuaMethodWithArgument catch every exception (std::exception and ...), reset the stack to its empty base (LuaRuntime::RecoverAfterPanic, when the panic count says the exception came down the panic path), and report the error like any limit error: logged once, the component or callback switched off; nothing leaves into the event dispatch or the physics step. A hot reload (LuaRuntime::ReloadModule) catches C++ exceptions around the module run and around each component's reload (one failing reload no longer stops the others) and logs "Reloading module ... failed" with the module name and the exception text sanitised (control characters replaced, cut at 100 bytes). Registry references PR #173 (the known limitation of PR #159, closed): in sol, creating or copying a Lua reference (a sol::table, sol::object or function, sol::make_object, a stack value turned into a reference) is noexcept and calls luaL_ref. If the registry has to grow for it at the memory cap, outside a protected call, the panic function's throw sol::error would meet that noexcept frame and the process would end with std::terminate, which no catch (including ReloadModule's) can handle. No path of the engine can do that now. LuaRuntime::ReserveReferences(count, error) checks the length of the registry's free list (the slots luaL_ref reuses before it allocates; CountFreeRegistrySlots, in LuaPanicRepair.cpp beside the 5.4.8 guard, because the list's index changed in 5.4.3) and, if it holds fewer than count, takes count references in a protected call and gives them back: the registry then holds that many free slots, and the luaL_ref that follows takes one and allocates nothing. A failure to grow is a returned error (the memory error, or the budget's), which the caller logs and gives up on; nothing throws. Each site reserves right before its unprotected references, with none in between (script code can take slots). The sites, as of this change: LuaComponent::CreateScriptInstance reserves before scriptClass = result[0] (a value on the outer stack cannot be read inside a protected call's body, so it cannot be copied there), and its __gc check, which used to make a sol::object outside any protected call whenever the class defined __gc (the script chooses the value), now reads the class with lua_rawget inside the protected call that builds the instance, so no reference is made for it; LoadScriptInstance moves the new instance into the component instead of copying it, and RetireScriptInstance moves the old one out (a move creates no reference); LuaComponent::DescribeFields (what the editor host's field listing and schema call) makes no sol reference at all: it pushes the instance on the stack (which keeps it alive while a metamethod runs) and reads SerializableFields with Lua's own API into plain C++ data, each definition's type and default in a protected call of its own; a read that fails leaves that field to its default (or, for the table itself, the listing holds only the script field) and is logged as a warning; LuaRuntime::LoadScriptAsModule reserves before the chunk's table and the module map's copy of it, and on a failure logs the error (once per chunk), stores nothing and answers an invalid table; LuaRuntime::GetModule reserves before its copy and answers nothing, with a warning, if it cannot; CallLuaMethodWithArgument reserves before it builds the collision or trigger object (CollisionToLua, TriggerToLua, sol::make_object), and a failure faults the component and is logged once like any limit error. LuaComponent::GuardedAccess, which every protected read or write of the instance goes through, reserves 16 slots first, because a body holds a few references at a time (a method read as a function, a field table, a key and a value) and a body that has them reserved never has to grow the registry. A protected call is not enough on its own where Lua's errors are C++ exceptions (the web build, and MSVC Debug): an error raised inside a noexcept sol constructor then ends the process even inside the call, so the reservation matters there too, and the web job's sweeps check it. LuaRuntime::RunSource no longer goes through sol's safe_script: that builds a sol::protected_function, whose constructor looks sol's default error handler up by pushing a string, an allocation that at the memory cap outside a protected call went down the panic path through a noexcept frame (the sweeps found it). It now loads with luaL_loadbufferx and calls with lua_pcall, using the same handler (the traceback function the state registered), and the string that names the handler's global is kept alive from the state's creation, so a lookup never allocates. Design decision: reserve free registry slots before unprotected references PR #173

The other way to make a reference unable to fail is to make it inside LuaRuntime::ProtectedCall. Where a reference was only being copied from one place to another (the instance into the component, out of it), the code moves it instead, which makes no reference at all. The state. Each call makes its own lua_State with its own allocator and instruction hook: the same LuaGuardState, LuaCappedAlloc and panic function the runtime's state uses (engine/src/scripting/LuaGuard.hpp), not a copy, but a different state with its own counters, so the runtime's limits, scopes and memory are not involved and LuaRuntime::Instance() is never created or used. The libraries are base, math, string and table only, with the engine's budget sandbox (pcall and xpcall hand the budget error on, setmetatable refuses a metatable with __gc). Where an evaluation differs from a real run

  • Control flow that depends on an engine value. A script that branches on a global (if Input then ... end, if Application.IsEditor() then ... end) takes the branch the placeholder gives (it is truthy), which a real run may not. The evaluation cannot tell; stubUses is the only hint. Declare type = for such fields.
  • A field whose default is an engine value reads as unevaluable (above) where a real run has the value. A Vector2, Quaternion or Color default is the placeholder here and so is unevaluable, where a real run classifies it as Json.
  • A script that fails only in the real runtime (it needs a global that a project sets, or an engine object) can succeed here, because every missing global is the placeholder. A script that the sandbox here refuses (load, a pattern function used for a default, a table library call over more than 65,536 elements) reads as unevaluable, as an error or as budgetExceeded where a real run has none.
  • The class is read like a real instance. The reader makes a table whose metatable is the returned class and reads SerializableFields from it, so an inherited declaration (through __index) is found and return { SerializableFields = ... } with no __index finds nothing, exactly as DescribeFields on a running script does.   • Randomness. math.random is the placeholder, so a declaration never depends on the clock or on determinism.luaSeed. Fields are sorted by name, so Lua's string-hash order does not show either.

Bounded, not a sandbox for hostile code

The evaluator still runs the script's Lua. The instruction hook sees Lua instructions, not time spent inside one C function: one C call that loops runs to its end, and neither the instruction budget nor the deadline can interrupt it. So every C loop the libraries here can reach is either bounded by the memory cap at memcpy speed, or removed, or redone in Lua (the audit below). On top of that a wall-clock limit (2 s by default, checked in the hook every 100 instructions) stays as defence in depth: one instruction can still do megabytes of C work (comparing or copying a long string, s:upper() on 8 MB), so the instruction budget alone does not bound time, but the deadline ends a loop of them within the time of about 100 such instructions after it passes (a result with timedOut). A wall-clock limit means a very slow machine can time out a script that a fast one finishes; declarations take microseconds. What the state removes is everything that touches the engine, the files and the clock; what it bounds is instructions, bytes and time. The same known limitation as the runtime's applies to error text on the web build and MSVC Debug: budgetExceeded and memoryExhausted come from the state's counters and the call status, and only an ordinary error's text is read off the stack.

The table library. A table's length is not bounded by its memory: a border can be 240 with 41 elements (keys 240 down to 1, all in the hash part), a __len metamethod can answer anything, and each access can walk a chain of up to 2000 __index tables. The stock table.insert(t, 1, v), remove, concat, unpack, move and sort loop in C over that length or over the range they are given, so one call could run for hours. Here they are redone in Lua with the stock semantics (metamethods included): the length is read once, every element is read and written by counted Lua code, and the C functions are handed only plain tables that this Lua code filled (concat and unpack of the collected values; sort of a copy, through a Lua comparator, the default order being a < b in Lua, so every comparison is counted). A length or range above 65,536 is refused before any loop, as budgetExceeded: never the placeholder, so a refused call cannot leave a silently wrong list behind. A position (table.insert(t, pos, v), table.remove(t, pos)) is only checked against the length, as stock Lua does: out of bounds raises the ordinary, catchable "position out of bounds". A first argument that is not a table never reaches a C table function (a string would pass the stock check through the strings' metatable and loop over missing keys in C): insert, remove, concat, move and sort raise the stock "table expected" error, and unpack of a string reads its elements in Lua like a table's. The strings' metatable is protected (getmetatable("") answers "protected"), so a script cannot give strings a __len, __newindex or another __index. Since every comparison of a sort runs Lua code (about 4 instructions with the default order, more through a comparator), a table.sort of more than roughly 15,000 elements already runs out of the 1,000,000-instruction budget (budgetExceeded), well below the 65,536 bound. Error texts for bad arguments are close to the stock ones but not guaranteed identical.

The shared sandbox builder: LuaSandbox and its two profiles PR #183

Scripting::LuaSandbox (engine/include/engine/scripting/LuaSandbox.hpp) builds a fresh, owned lua_State for code that is not the game's: its own allocator with a byte cap, its own instruction and wall-clock hook, the libraries of a SandboxProfile, and nothing else. It never touches the runtime's state (LuaRuntime::GetState()), an engine object or a singleton, so it can be made and used on any thread, several at once, with or without a LuaRuntime; one thread at a time uses one LuaSandbox. It is a library component with two users: the declaration evaluator (above), which builds its throwaway state through the Declarations profile, and, since PR #189, the editor host's ExtensionHost, which builds one state per editor extension file through the EditorExtension profile (below). The profile is for the Lua editor extensions of the design (lua-editor-extensions, stage E-X1); the Editor namespace is installed by that host, not by the builder.

Preconditions and what is not bounded

The hook runs between VM instructions, so one call into C that does not return cannot be interrupted. Known and not fixed here: (1) the collector's atomic phase over tables with weak keys (__mode = "k"), the same estimated quadratic stall described for the evaluator above, with no hook and no allocation to refuse; vendored Lua is not patched. A caller must therefore run a sandbox where it can be abandoned: on a worker with a deadline, as ScriptDeclarationCache does for the evaluator, never on a thread whose latency matters. (2) The EditorExtension profile's table library is the stock one (design 6.4) except table.move, insert and remove, which are redone in Lua with the stock semantics, so a huge range or border (even on a plain table) costs counted instructions and ends as a budget trip, with no size limit of their own. concat, unpack and sort over a huge range or length (a table whose __len lies, or whose border is huge) still loop in C where the hook cannot stop them. The Declarations evaluator redoes all six, with a bound of 65,536; the extension profile does not, so (1)'s precondition applies to (2) as well. (3) The strings' own growth is bounded by the allocator (string.rep('x', 1e9) and a table growth bomb end as memoryExhausted), but an empty string repeated costs no allocation: the profile answers it in Lua. A script can catch a memory error with pcall and carry on; only an error that leaves the entry is reported.

Design decision: one builder with profiles, the evaluator on top of it PR #183

The evaluator's state (allocator with a cap, count hook with a deadline, budget sandbox, panic repair) is the same machinery an editor extension needs; two copies would drift. The builder owns that, the evaluator keeps only what is its own (the environment script, the reader, the result) and runs on the state the Declarations profile makes, so the evaluator's behaviour did not change and its tests are the oracle. The allocator's bookkeeping (LuaGuardState) outlives the state inside the sandbox, so the counters (peak, leaked bytes, the trip flags) are read after the state is closed, as before. The extension profile is a different profile of the same builder and not a configuration of the evaluator, because it keeps its state alive across entries and has no placeholder environment.

Editor extension states: what the editor host makes of the EditorExtension profile PR #189

The editor host's ExtensionHost (Lua editor extensions) is the first host feature to use the EditorExtension profile. For each file of <project>/editor/**/*.lua it makes one state on a worker thread (LuaSandbox::Create(SandboxProfile::EditorExtension) with the load budget and a memory cap of the smaller of 64 MiB and what is left of the host's total budget of 256 MiB for all the states of one load, Lua editor extensions PR #194; the host reads Counters().peakBytes after the load to charge the state), runs three things in it, each under SandboxDefaults::LoadBudget (10 million instructions, 1 s of wall clock), and keeps the state: a prelude that defines the Editor global and returns a reader function; the file's chunk; and the reader function, which copies the declaration the file returned into plain data. These states are not the game's state and not the declaration evaluator's throwaway state. They are made at host start (with --editor-extensions) and in ReloadEditorExtensions, never by loading a scene, and are discarded at the next reload.

What a state has: the profile's libraries (the table above) and one global added by the host, Editor, whose only member is Editor.Extension(table). What it cannot do, in this stage:

  • Reach an engine object: there is no binding at all (Application and GameObject are nil), so no handle can dangle.
  • Reach the machine: no io, os, package, debug, require, load, loadfile, dofile or print, and no string pattern functions. Another extension's globals are not visible: one state per file.
  • Run again: after its file loaded, nothing calls it. A menu item's run function is never invoked in this stage, so a loaded state is idle. It has no Editor.Scene, no log function and no asset access either; the capabilities it declares are listed and nothing is installed for them yet.
  • Outlive a reload, escape a budget (an extension that loops, fills memory or would take the host past its total memory budget fails as data, the other files still load), or stall the host for good: a file that never returns from a C call is abandoned at a deadline (off the command thread), which is the precondition the builder's header names.

A test lists what is absent (io, os, package, debug, require, load, loadstring, dofile, loadfile, collectgarbage, print, coroutine, Application, GameObject, string.find, string.gsub), checks that Editor has exactly one member and that a global set by one file is not visible in the next (ExtensionHostTest.AStateHasNoWayToReachTheHostOrAnotherExtension).

Modules and require

Initialize replaces the global require with an engine version:

  1. If the module name is already in the runtime's module cache, the cached table is returned.
  2. Otherwise dots become slashes and .lua is appended: require("util.helpers") loads res://util/helpers.lua through ResourceLoader.
  3. If the file cannot be loaded, it logs "Failed to require module: ..." and returns nil.
  4. Otherwise the file runs as text (LoadScriptAsModule, through RunSource). If it returns a table, that table is the module; any other return value gives an empty table. The module is cached under its module name.
  5. If the module raises an error while loading, it logs "Failed to load module ...: ..." and returns a new empty table, which is not cached, so the next require runs the file again.

The global _loaded_modules() returns the names of the cached modules. LuaRuntime::GetModule(name) reads the cache from C++.

LuaComponent and the script table

A behaviour script is a file that returns a table, the script's "class". SetScript(path) does the following:

  1. Records the path and loads the file through ResourceLoader. If it is missing, it logs a warning, retires any previous instance (see Replacing a script instance), sets HasMissingScript() and stops.
  2. Runs the file. If it raises an error or does not return a table, it logs an error, retires any previous instance and sets HasMissingScript().
  3. Creates a fresh instance table whose metatable is the class table, and sets self.component (this LuaComponent) and self.gameObject (its GameObject) on it. Both are checked handles PR #29.
  4. Retires the previous instance, if there was one PR #37.
  5. Reads SerializableFields and injects field values into the instance (see Serializable fields), and carries resolved $ref fields over from the previous instance.
  6. Caches which per-frame, physics and quit callbacks exist.
  7. If the component has already been attached (its first OnAttach ran), calls the new instance's OnAttach straight away PR #37.
  8. Registers a reload callback for the module name, replacing any it registered before.

The instance's metatable is the class table itself, not a table with __index set for you. The class must set Class.__index = Class, or method lookups on self find nothing and the callbacks are never called. No error is reported in that case.

local Mover = {}
Mover.__index = Mover          -- required: the instance's metatable is this table

function Mover:OnUpdate()
    local p = self.gameObject:GetPositionable()
    if p ~= nil then
        p:SetPosition(p:GetPosition() + Vector3.Up * Time.deltaTime)
    end
end

return Mover                   -- anything other than a table: "Script must return a table"

From Lua, a component is added and given a script like this. Do it before the object joins the scene, or in the same frame (see Lifecycle):

local go = GameObject.Create("Mover")
go:AddComponent("LuaComponent"):SetScript("res://scripts/Mover.lua")
SceneManager.GetCurrentScene():AddRootGameObject(go)

The LuaComponent Lua type has SetScript(path), GetScriptPath(), HasMissingScript() and the methods every component handle has (below).

ReleaseScript

ReleaseScript() cuts the script off from its component. It runs at the end of OnDestroy and again in ~LuaComponent (for components freed without OnDestroy), and is safe to call twice. It:

  • sets the component's lifetime flag to false, so subscriptions the script made stop firing (see Subscriptions);
  • removes the component's reload callbacks;
  • sets self.component and self.gameObject to nil on the instance. A closure that kept self then gets an "attempt to index a nil value" error instead of touching freed memory.

Copies of those handles the script made earlier (local go = self.gameObject) are not cleared, but they are checked handles and fail cleanly (see Checked handles).

Serializable fields

A script declares editable, saved values in a SerializableFields table on its class. Each entry is either a shorthand value or a table with a default (and optionally a type). The editor host that edits does not run the script to learn them: it reads them with the DeclarationEvaluator (Execution policy), which gives the same fields for every form below, except that a default or type that comes from an engine call is unknown there (declare type =):

local Fields = {}
Fields.__index = Fields
Fields.SerializableFields = {
    count   = 3,                                   -- shorthand, stored as an integer
    ratio   = 0.5,                                 -- shorthand, stored as a float
    enabled = true,
    label   = { type = "string", default = "hi" }, -- full form
    offset  = { default = Vector3(0, 1, 0) },      -- stored as {"x":0,"y":1,"z":0}
    target  = { type = "GameObject" },             -- reference field (see below)
    body    = { type = "Rigidbody" },              -- reference to a component
}

function Fields:OnAttach()
    Debug.Log(self.label .. " x" .. self.count)    -- values are fields on self
end
return Fields

Defaults and the scriptData store

The component keeps field values as JSON in scriptData. On SetScript:

  1. Extract: for each entry of SerializableFields that is not already in scriptData, the default (the shorthand value, or the table's default) is stored. Only numbers, booleans, strings and Vector3 defaults are stored. A Lua integer is stored as a JSON integer and a float as a JSON float. A Vector3 is stored as {"x", "y", "z"}.
  2. Inject: every scriptData entry is written onto the instance table as self.<name>. JSON floats become Lua numbers (via float), integers become Lua integers (via int), booleans and strings unchanged. An object with an "x" key becomes a Vector3. Missing or non-numeric axes become 0, so {"x": 1} gives Vector3(1, 0, 0).

Values already in scriptData win over defaults. A scene file's saved values therefore override the script's defaults, because Deserialize reads scriptData before it calls SetScript. SetScriptData(json) replaces the store and re-injects it. SetField<T>/GetField<T> (instantiated for int, float, bool, std::string) write and read the store from C++. SetField also writes the live instance.

The editor reads these declarations: GetLuaFields lists them with their kinds (the declared type, else the default's type), and SetComponentFields sets them through scriptData PR #93. See Reflection: LuaComponent and Components and the inspector.

  • Unsupported defaults: a default of another type (Vector2, Color, Quaternion, a table) is not stored and not injected. self.<name> is then nil unless the class table defines it.
  • Script changes are not saved: the store is not updated when the script assigns self.speed = 10. Serialize writes scriptData, so runtime changes made in Lua are not saved.
  • Precision on injection: floats go through float (0.1 arrives as 0.100000001…), and integers go through int.
  • Extra keys: every key in scriptData is injected, including keys the script does not declare.

When a handle is valid

A handle is valid from creation until its object's teardown has finished (GameObject::IsTornDown()). IsTornDown becomes true:

  • in Scene::ProcessDestroyed, after the OnDisable/OnDestroy pass over everything being destroyed;
  • in Scene::Clear (scene switch), after the OnDestroy pass over the scene's roots and their descendants. A child removed with RemoveChild is one of those roots PR #34, so it is torn down too;
  • immediately, when Destroy() is called on an object that is in no scene.

Handles to the object, its components and to other objects torn down in the same pass therefore all keep working inside OnDisable/OnDestroy, and all fail afterwards. Validity checks and errors

  • IsValid() works on any handle, live or dead. Every component type also has IsDestroyed(), which is exactly not IsValid().
  • Every other method raises "attempt to use a destroyed <Type>" once the object is gone, for example "attempt to use a destroyed Rigidbody" or "attempt to use a destroyed GameObject". A Positionable raises "attempt to use the Positionable of a destroyed GameObject". This includes IsActive(), which used to answer false.
  • GameObject:Destroy() on an object that is already destroyed, or freed, does nothing.
  • A dead handle is not == nil. Lua does not call __eq when comparing userdata with nil, so if self.target == nil does not detect a destroyed target. Use IsValid().
-- A cached reference may outlive its object
if self.target ~= nil and self.target:IsValid() then
    self.target:GetPositionable():SetPosition(Vector3.Zero)
end

Note

Lua's Component:IsDestroyed() is not the C++ Component::IsDestroyed(). In C++ it reads the "marked for destruction" flag, which Component::RunDestroyCallbacks sets only after OnDestroy returns, so it stays false during OnDisable and OnDestroy. In Lua it is true only once the handle is invalid. Inside OnDisable/OnDestroy, both report false. Do not use IsActive() to detect teardown either: it can still be true inside OnDestroy on the RemoveComponent path (component enabled, object active in its hierarchy).

Equality

Each push to Lua creates a separate userdata, so == is implemented by __eq. It compares ownership (weak_ptr::owner_before), not addresses. As a result:

  • two handles to the same object are equal, for example go:GetComponent("SphereRenderer") == renderer or scene:FindGameObject("A") == a;
  • equality still holds after the object is freed, and a reused address never makes two different objects equal;
  • component equality works across handle types: a concrete SphereRenderer handle equals a plain Component handle to the same component;
  • a GameObject handle never equals a component handle.

Scene and input handles PR #31

Scene, ActionMap and InputAction are not part of a GameObject and are freed whenever their owner decides: a scene on a scene switch, a map when it is replaced or reloaded, an action when it is replaced, removed or its map is freed. Each owns a Base::LifetimeToken, a shared_ptr that expires when the object is freed. A copy of the object gets a fresh token, so a handle never follows an object's contents somewhere else; ActionMap and InputAction are also non-movable, and Scene was already non-copyable and non-movable.

  • Validity: a LifetimeRef is valid until its object is freed. There is no teardown window as for GameObjects; a scene handle still works inside the OnDestroy calls of that scene's own unload, because the scene is freed only afterwards.
  • Errors: Pin() throws "attempt to use a destroyed Scene", "... ActionMap" or "... InputAction", which reaches the script as a Lua error. This includes property reads and writes (scene.sceneName, map.disabled = true) and indexing (map["X"]).
  • API: each type has IsValid() and == (token identity, also after the object is freed). Scene has a read/write sceneName property. SceneManager.GetCurrentScene(), Input.GetActionMap, LoadActionMap and CreateActionMap return a handle or nil. Input callbacks receive an InputAction handle. See Input: Lua API.
  • Nil checks: as with every handle, a dead one is not == nil; use IsValid().

Design decision: handles are valid until teardown or free

Lua code can keep any value for as long as it likes, so a raw pointer handed to Lua turns every engine-side free into a potential use-after-free inside the VM. Checked handles turn that into a Lua error at the call site, which the engine already contains and logs (see Errors). The validity window is chosen so that scripts never see a half-dead object:

  • GameObjects and components stay valid until their teardown has finished, so OnDisable/OnDestroy can still use the object, its siblings and anything torn down with it, and every handle fails together afterwards.
  • Scenes, maps and actions stay valid until they are freed. A map or action replaced from inside an input callback is retired, not freed, until the outermost input update ends, so the callback that replaced it can finish.
  • Nothing a script can call on these objects frees them mid-call: scene switches and the end of the input update never run inside a script call. That is why LifetimeRef::Pin can return a plain pointer without holding a reference.
  • This reasoning assumes scripts and those frees all run on the main thread. The editor server now runs every command on the main thread for this reason (see Logging, health & editor).

Handles do not keep objects alive (except the ownership cases below), so a script cannot extend an object's life past the engine's own rules; it can only observe that the object is gone.

How bindings use handles: Forward and BindComponentType

Bindings expose engine methods on handles with Forward<Handle, &Class::Method>(). The generated function pins the object, calls the method and returns the result:

  • Pinning: Pin() throws (which becomes the Lua error above) if the object is gone. Otherwise it holds a shared_ptr to the owning GameObject for the duration of the call, so a call that re-enters Lua (e.g. SetScript, SetActive) and triggers a GC cannot free the object mid-call.
  • Copies: a method returning an lvalue reference returns a copy to Lua. CubeRenderer:GetColor() or BoxCollider:GetSize() give values that stay valid after the object dies.
  • Compile-time check: a static_assert rejects forwarding any method that returns a raw or smart pointer, a Component, a GameObject or a Positionable. Such methods must be bound by hand and return a handle.

Subscriptions and script lifetime

Scripts subscribe to C++ events through Subscribe(callback) on InputAction, Event, WindowResizeEvent and GameObjectEvent. Each returns an id for Unsubscribe(id). All four wrap the Lua function with MakeScriptCallback. (InputActionEvent was removed in PR #31; InputAction:OnStateChanged() now returns the action itself.)

ScriptLifetimeScope

LuaComponent::CallLuaMethod opens a ScriptLifetimeScope around every call into its script. The scope makes the component's lifetime flag (one per script instance: a replaced instance's flag is cleared and the new one gets its own PR #37) "current" (thread-local) and restores the previous one on exit, so nested calls into another component's script are handled. MakeScriptCallback captures ScriptLifetimeScope::Current() when the subscription is made:

Where Subscribe is calledCaptured ownerAfter the component is destroyed

Inside another subscription's callback (dispatched from C++)NoneKeeps firing

Subscribe from OnAttach (or another lifecycle method) so the subscription is tied to the component. OnAttach runs again each time the object rejoins a scene, so an object that can leave and rejoin should keep the subscription id and unsubscribe before subscribing again.

Rules

  • Skipped, not unsubscribed. A destroyed component's callbacks stay registered and are skipped at dispatch. The event they are registered on may already be gone (for example an action map replaced by Input.CreateActionMap), and unsubscribing from a stale event would be unsafe. A skipped callback stays registered until its event is destroyed, and still counts in Event:GetSubscriberCount().
  • Errors are contained. A failing callback logs "<EventName> callback error: ..." and the dispatch continues.
  • Unsubscribing inside a handler is safe (PR #22), including a handler removing itself. It is not called again. Subscribing during dispatch is also safe, and the new subscriber first runs on the next dispatch.
  • Arguments: a GameObject& argument (GameObjectEvent) arrives as a GameObject handle PR #29, and an InputAction& as an InputAction handle PR #31 (Detail::ToLuaArg overloads). Other class-type arguments arrive by reference to the live object, not as a copy.
-- Fire once: unsubscribe from inside the handler
function Opener:OnAttach()
    local map = Input.LoadActionMap("Main Controls")
    if map == nil then return end
    local action = map:Get("Quit")
    local id
    id = action:Subscribe(function(a)
        if a:GetPhase() == ActionPhase.Started then
            a:Unsubscribe(id)
            Debug.Log("first press")
        end
    end)
end

Reloading scripts

LuaRuntime::ReloadModule(path, script) drops the cached module, reloads it, and then calls every reload callback registered for that module name. It iterates a copy, because a callback may itself call SetScript and so re-register. Reload callbacks are keyed by owner (PR #18):

  • RegisterReloadCallback(module, fn, owner) adds a callback;
  • UnregisterReloadCallbacks(owner) removes all callbacks of that owner, for any module (a null owner is ignored);
  • ClearReloadCallbacks(module) removes all callbacks for one module.

Under the DeclarationsOnly policy (the editor host that edits) ReloadModule does none of this: it runs no module, replaces no instance and keeps no module table; it drops the declaration cache's older entries for the path and notifies the components that subscribed through ScriptDeclarationCache (Execution policy).

LuaComponent::SetScript replaces its own callback, so calling it twice does not duplicate it, and ReleaseScript removes it. The component's callback runs ReloadScript(). If the script was missing, that retries SetScript. Otherwise it re-runs the file into a new instance that replaces the running one, as below; if the new version fails to load, the running instance stays.

Replacing a script instance PR #37

A second SetScript (same path or another) and ReloadScript both replace the component's script instance. The new instance is created first; then:

  1. The old instance is retired as if its component were removed: once the component has been attached, it gets OnDisable (if the component is enabled in an active hierarchy) and then OnDestroy. Before it is attached, it gets neither.
  2. Its subscriptions stop firing (its lifetime flag is cleared and the new instance gets a new one), and its self.component/self.gameObject become nil, as after a destroy.
  3. The new instance gets the saved scriptData values; fields that a new version adds get their defaults. Resolved $ref fields (GameObject and component references) are copied from the old instance, since they are handles on the instance rather than values in scriptData. For a reload or a SetScript of the same path everything is kept, including fields the new version no longer declares. For a SetScript of a different path, only the fields (and references) that the new script declares in SerializableFields are kept; the rest are dropped from scriptData, so unrelated scripts never share values. The first SetScript of a component keeps everything, since Deserialize fills scriptData before it.
  4. If the component was already attached, the new instance gets OnAttach immediately. It does not get OnEnable, just as a first attach does not, so setup done only in OnEnable is not re-run after a hot reload; put it in OnAttach.

Source: engine/src/scripting/LuaComponent.cpp — LuaComponent::LoadScriptInstance, RetireScriptInstance, CopyReferenceFields, ExtractSerializableFields; tests: LuaLifetimeTest.ReloadRetiresTheOldInstanceAndAttachesTheNewOne, LuaLifetimeTest.SettingAnotherScriptRetiresTheFirstInstance, LuaLifetimeTest.ReloadKeepsSavedFieldsAndReferencesAndDefaultsNewOnes, LuaLifetimeTest.AnotherScriptKeepsOnlyTheFieldsItDeclares

Design decision: a replaced script instance is retired like a removed component

Replacing the script must not leave the old code running behind the new one. Before, the old instance kept its subscriptions (they shared the component's lifetime flag) and its self.component, so a reload doubled every input handler, and the new instance never got OnAttach, so it never subscribed or initialised at all. Treating a replacement as remove-then-add reuses rules scripts already follow: OnDestroy undoes what OnAttach set up, and OnAttach sets it up again. The component's data (scriptData and resolved references) is kept, because it belongs to the component and the scene, not to one version of the code. A different script only keeps the fields it declares, since a same-named field of another script is a coincidence, not shared data. The new instance gets OnAttach but not OnEnable: this engine never fires OnEnable on attach, and firing it only on replacement would make a reloaded script run code a freshly attached one never runs. A reload that fails to compile keeps the running version, so a typo during hot reload does not stop the game.

Where the file and the bindings differ

  • The engine require and the _loaded_modules() helper are not documented.
  • SceneManager.LoadScene is documented with an index only. The binding also accepts a scene name.
  • The Window instance returned by Window.Get() has GetTitle, SetTitle, GetDimensions, SetWindowMode and a clearColor field. Only the global functions are documented. GetDimensions, Window.GetWidth and Window.GetHeight are the window's size even when frames render at another size: in the editor host that is the hidden window, not the viewport PR #85 (Camera:ScreenPointToRay's default uses the viewport).
  • Camera.Main() and Application.GetCamera() are annotated as returning Camera, but return nil when there is no camera.
  • Script-side conventions are described only in prose on LuaComponent: the lifecycle methods (including OnMouse*), SerializableFields and the OnCollision*/OnTrigger* argument types have no annotations.

Scene setup script

lua_project builds its whole scene from assets/scene.lua, run with LuaRuntime::RunFile after a scene is loaded and ResourceLoader is initialized. Besides the falling cube and sphere below, it builds the GPU smoke test's stations PR #86. Trimmed:

    error("scene.lua needs a loaded scene")

-- Created before the behaviour scripts attach, since they subscribe to these actions
local controls = Input.CreateActionMap("Main Controls", {
    ["Camera Move"] = {
        { type = "Vector2Composite", up = "W", down = "S", left = "A", right = "D" },

local cube = GameObject.Create("TestCube")            -- owned by this handle for now
cube:AddComponent("CubeRenderer"):SetColor(Color.Blue)
cube:AddComponent("BoxCollider"):SetSize(Vector3.One)

Subscriptions made directly in a scene script have no owning component and are never cancelled.

Behaviour script

The shipped assets/scripts/QuitHandler.lua. It subscribes in OnAttach, so the subscription stops when the component is destroyed:

local QuitHandler = {}
QuitHandler.__index = QuitHandler

function QuitHandler:OnAttach()
    local controls = Input.LoadActionMap("Main Controls")
    if controls == nil then
        Debug.Warn("QuitHandler: 'Main Controls' action map not found")
        return
    end

    controls:Get("Quit"):Subscribe(function(action)
        if action:GetPhase() == ActionPhase.Started then
            Application.Quit()
        end
    end)
end

return QuitHandler

CameraController.lua follows the same pattern. It stores input values from two subscriptions in self, and in OnUpdate moves Camera.Main() by Time.deltaTime, fetching the camera each frame rather than caching it.

Fields, cached handles and collisions

A script written against the rules on this page:

local Bouncer = {}
Bouncer.__index = Bouncer

Bouncer.SerializableFields = {
    jumpImpulse = 5.0,                          -- float
    maxJumps = 3,                               -- stays an integer
    label = { type = "string", default = "bouncer" },
}

function Bouncer:OnAttach()
    self.jumps = 0
    self.body = self.gameObject:GetComponent("Rigidbody")   -- handle or nil
end

function Bouncer:OnCollisionEnter(collision)
    local other = collision.otherGameObject
    if other ~= nil and other:IsValid() then
        Debug.Log(self.label .. " hit " .. other:GetName())
    end

    -- The cached handle may outlive the Rigidbody (RemoveComponent): check, don't compare to nil
    if self.body ~= nil and self.body:IsValid() and self.jumps < self.maxJumps then
        self.body:AddImpulse(Vector3.Up * self.jumpImpulse)
        self.jumps = self.jumps + 1
    end
end

return Bouncer
