Resources & paths

How the engine names files (res://, user://), indexes a project's assets with stable UUIDs in .meta files, loads and caches them, and looks them up through one API. IO::ResourceLoader is the authority for project files. IO::Resources is the single lookup API, and it also holds assets registered at runtime.

Two registries, one lookup API

IO::ResourceLoaderIO::Resources
HoldsFiles under <project>/assets that have a registered loaderAssets registered at runtime, and files loaded from outside the project
UUIDsDeterministic, from the res:// path, recorded in .meta filesRandom per process (the Asset default)
KeysResourcePath and UUIDResolved filesystem path string and UUID
RoleAuthority for project files: scans, metadata, loads, cachesThe one place to look anything up PR #28. Lookups fall through to ResourceLoader.

Before #28, the two registries were not connected. An asset loaded through one couldn't be found through the other, and Resources::Load on a project file created a second copy with a random UUID. Now Resources delegates project files to ResourceLoader and checks its cache on every lookup. Each project asset has exactly one cache entry, under its .meta UUID.

ResourcePath: schemes and normalization

IO::ResourcePath is a value type made of a PathType and a relative (or absolute) path string. Parsing the string constructor:

InputTypeStored path
"res://scripts/a.lua"Resourcescripts/a.lua
"user://saves/1.json"Usersaves/1.json
an absolute filesystem pathAbsolutethe path, normalized, keeping its root
any other string, e.g. "scripts/a.lua"Resourcethe string, normalized
default constructorInvalidempty

Both constructors call Normalize(), which gives each file exactly one spelling:

  1. Backslashes become /.
  2. lexically_normal() removes . segments, collapses //, and resolves x/... A result of "." becomes empty.
  3. For Resource and User paths, leading slashes are stripped: they are relative to their root, so res:///a is a. An Absolute path keeps its root (/home/me/a.wav, a UNC //server/share/a.wav, C:/a.wav) PR #37.
  4. One trailing slash is removed, except from a bare root (/, C:/), which would otherwise change meaning.
  5. A leading .. is kept: res://../outside.txt stays ../outside.txt, so Resolve can see the escape and reject it.

Equality, ordering and hashing compare the type and the normalized string. So res://scripts/../scripts/thing.lua, res://scripts//./thing.lua and res://scripts\thing.lua are all equal to res://scripts/thing.lua, and they hit the same cache and metadata entries. Before this, Resolve accepted those spellings, but Load reported "Resource not found". The comparison is case-sensitive: on a case-insensitive filesystem, res://Scripts/a.lua and res://scripts/a.lua name the same file but are different keys, and only the spelling the scan produced has metadata.

IsValid() is true when the type isn't Invalid and the path is non-empty, so ResourcePath("res://") is not valid. ToString() puts the scheme back on. JSON serialization uses ToString(), and deserialization uses the string constructor.

Source: engine/include/engine/io/ResourcePath.hpp — ResourcePath::Normalize, ResourcePath::ResourcePath, operator==, ResourcePath::Hash; tests: ResourcePathTest.EquivalentSpellingsAreOnePath, ResourcePathTest.AbsolutePathsKeepTheirRoot

Guarantee PR #37

An Absolute path stays absolute: GetPath(), ToString() and Resolve return it with its root. Before, every leading slash was stripped, so on POSIX ResourcePath("/home/me/a.wav") (and the Absolute fallback of ResourceLoader::MakeResourcePath for files outside both roots) became the relative home/me/a.wav. res:// and user:// paths are unchanged.

Resolving to the filesystem

ResourceLoader::Resolve(path) turns a ResourcePath into a filesystem path:

  • Resource: joined under <project>/assets.
  • User: joined under the user data path.
  • Absolute: returned as stored, with no containment check.
  • Invalid: an empty path.

For res:// and user://, the joined path is lexically normalized and must still lie under its root. Otherwise Resolve logs "Resource path escapes its root and was rejected" and returns an empty path. This rejects .. escapes (res://../../x, res://scripts/../../x). It also rejects absolute paths smuggled in after the scheme: a Windows res://C:/x joins to C:/x, which is outside the root, and on POSIX res:///etc/x has its leading slash stripped and resolves under the root. Paths that leave the root and come back (res://scripts/../scripts/thing.lua) are accepted.

Source: engine/src/io/ResourceLoader.cpp — ResourceLoader::Resolve, ResolveUnder; tests: ResourceLoaderTest.ResourcePathsCannotEscapeTheAssetsRoot

Guarantee

No res:// or user:// path resolves to a file outside its root. Callers get an empty path instead and should treat it as "not found". Load does so: it reports the source file as missing.

User data path

The root that user:// resolves under is set by ResourceLoader::Initialize:

  • Windows: %APPDATA%\N2Engine (read with _dupenv_s).
  • Other platforms: $HOME/.n2engine (read with std::getenv; it used the MSVC-only _dupenv_s before #23).
  • If the variable is unset: ".", the current directory.

Initialize creates the directory. The name is the same for every project. GetUserDataPath is private.

Initializing ResourceLoader

A host initializes two things, in this order (from lua_project/src/Main.cpp):

// 1. The namespace that project UUIDs are derived from
IO::ResourceUUID::Initialize(Math::UUID::GenerateNameBased(Math::UUID::ZERO, projectDir.string()));
// 2. Scan <projectDir>/assets and load/create metadata
IO::ResourceLoader::Instance().Initialize(projectDir);

auto script = IO::ResourceLoader::Instance().Load<LuaScript>(IO::ResourcePath("res://scripts/CameraController.lua"));

ResourceLoader::Initialize(projectRoot):

  1. Sets the roots: assets in <projectRoot>/assets, metadata in <projectRoot>/.import, and user data as above. It creates the metadata and user-data directories.
  2. Clears all metadata, the UUID-to-path map, and both caches PR #28. Everything is keyed by root-relative res:// paths, so entries left over from a previous root, even a deleted one, would otherwise answer lookups for the new one. Registered loaders are kept.
  3. Scans the assets directory (RescanAssets). If it doesn't exist, a warning is logged and nothing is indexed.

The scan walks assets/ recursively. It skips non-regular files, .meta files, and any file whose lower-cased extension has no registered loader. For each remaining file it creates or updates the metadata inside its own try, so one bad asset logs "Skipping asset ..." and the scan continues. RescanAssets() can be called again later, for example by the editor's rescan command. It adds and updates entries but does not remove the entries of deleted files. Only Initialize starts from scratch.

The editor host does the same when started with --project <path>, right after Application::Init PR #84; without --project it initialises neither. See Editor host: project resources.

Source: engine/src/io/ResourceLoader.cpp — ResourceLoader::Initialize, ResourceLoader::RescanAssets, ResourceLoader::ScanDirectory; lua_project/src/Main.cpp; editor-server/src/Main.cpp

Warning

Call ResourceUUID::Initialize before ResourceLoader::Initialize. Without it, ResourceUUID::FromPath logs "ResourceUUID not initialized!" for each asset and returns UUID::ZERO. Every asset then gets the same UUID, and existing .meta files are rewritten with it.

.meta files

Metadata for assets/<dir>/<file> is stored at .import/<dir>/<file>.meta under the project root, in a parallel tree rather than next to the asset. The JSON written by AssetMetadata::SaveToFile:

{
  "uuid": "2c8d6e0a-4f1b-5a3c-9e7d-1b0f2a6c4d81",
  "resourcePath": "res://scripts/CameraController.lua",
  "resourceType": "LuaScript",
  "lastModified": 1767700800,
  "fileSize": 2048
}

lastModified is the file's write time in Unix seconds. An optional customData object is written only when it is non-empty; asset types read their import settings from it (fonts, textures). For a new file, resourceType is chosen from the extension:

Extensions (any case)resourceType
.luaLuaScript
.wav, .ogg, .mp3, .flacAudioClip
.png, .jpg, .jpeg, .tga, .bmp PR #64Texture
.ttf, .otf PR #45Font
.mat PR #65Material
Anything elseUnknown

The extension is compared lower-cased, as loader matching is PR #64: Jump.WAV is an AudioClip and Logo.PNG a Texture. (It used to be case-sensitive, so Jump.WAV was scanned and loaded but its metadata said Unknown and GetAssetsByType("AudioClip") missed it.) An existing .meta that says Unknown is given its type, and saved, the next time its file is scanned.

For each scanned file:

  • No .meta: one is created with the deterministic UUID, then "New asset: ..." is logged.
  • Existing .meta: a resourceType of Unknown is replaced by the type the extension gives, if it gives one PR #64. Its UUID is checked against the deterministic one. On a mismatch it logs "UUID mismatch ... Regenerating.", rewrites the UUID and saves. If the timestamp or size changed, both are updated, saved, and "Asset modified" is logged. The stored resourcePath is not checked or corrected, and it becomes the key the asset is indexed under (metadata map and UUID-to-path map). A .meta whose resourcePath names a different file (for example one copied along with a renamed asset) indexes the asset under that other path, and Load of it resolves that other path.
  • Corrupt .meta (unparseable, missing keys, wrong types): logs "Corrupt metadata ...; regenerating" and recreates it as if it were new. Before #23 this threw out of Initialize. Because the UUID comes from the path, references to the asset still resolve.

That doesn't match what AssetMetadata reads and writes (uuid, resourcePath, resourceType, lastModified, fileSize, customData), and nothing in the code reads the file. UUID stability across runs

A project asset's UUID is UUID::GenerateNameBased(projectNamespace, "res://<path>"). The .meta file records it, but the path decides it: a stored UUID that differs is overwritten. As a result:

  • The same file under the same project namespace gets the same UUID in every run, on every machine, even with the .import folder deleted. This is what lets saved asset references (RegisterAssetRef) and LuaComponent's scriptUUID resolve in a later run.
  • Moving or renaming an asset changes its UUID, and references saved against the old UUID stop resolving. The .meta file doesn't carry a UUID across a move.
  • The namespace is whatever the host passes to ResourceUUID::Initialize. lua_project derives it from the project directory string, so running the same project from a different directory (or with a different spelling of its path) gives every asset a different UUID. The editor host (N2EditorHost --project) derives it from the canonical project path, so different spellings of the same folder agree, but moving the folder still changes every UUID PR #84. A per-project id is planned to replace both (#6, phase E3).

Source: engine/src/io/ResourceUUID.cpp — ResourceUUID::FromPath; engine/src/io/ResourceLoader.cpp — ResourceLoader::CreateOrUpdateMetadata; lua_project/src/Main.cpp; tests: AudioAssetReferenceTest.AudioSourceClipResolvesInALaterRun

Loading through ResourceLoader

CallBehaviour
Load<T>(path)Returns the cached asset if there is one. Otherwise: no metadata for path gives an error ("Resource not found") and null. A source file that is missing or rejected by Resolve gives an error and null. No loader for the extension gives an error and null. A loader that returns null gives null without a log. On success the asset's UUID is set to the meta UUID, its ResourcePath is set, it is cached by path and by UUID, and it is returned as T.
LoadByUUID<T>(uuid)Returns the cached asset by UUID. Otherwise looks up the path for that UUID and calls Load<T>. An unknown UUID gives null, silently.
GetCached<T>(path) / GetCachedByUUID<T>(uuid)The cache only. Never loads.
GetMetadata(path or uuid), GetUUID(path), Exists(path)Metadata lookups: nullptr, UUID::ZERO or false for unknown paths. Exists means "has metadata", not "is on disk".
GetAllAssets(), GetAssetsByType(type)Copies of the metadata, in unspecified order.
RegisterAsset(asset, path)Puts an existing asset into both caches. It doesn't create metadata, so Exists(path) stays false.

Note

The type is checked with dynamic_pointer_cast after loading and caching. Load<AudioClip> on a .lua file loads and caches the LuaScript, then returns null without logging. The cache check (GetCached<T>) is typed too, so a wrong-type Load<T> on a path that is already cached misses the cache, re-reads the file and replaces the cached object with a new one. A later Load<LuaScript> returns that new object, not the one earlier callers hold.

Change detection and Reload

  • HasSourceChanged(path) returns true when the file's current write time (Unix seconds) differs from the recorded lastModified. It returns false for unknown paths and for missing files. Size is not compared.
  • Reload(path) evicts the cached asset (by path and by UUID), then re-reads the file's timestamp and size and stores the refreshed metadata. Before #23 the metadata was discarded, so HasSourceChanged stayed true forever. It returns false if the file is missing or rejected by Resolve, in which case the cache entry has still been evicted.
  • Reload does not load anything. The next Load reads the file again and creates a new asset object. Code that still holds the old shared_ptr keeps the old object. Script reloading is covered in Lua scripting.

Source: engine/src/io/ResourceLoader.cpp — ResourceLoader::HasSourceChanged, ResourceLoader::Reload; tests: ResourceLoaderTest.ReloadRefreshesMetadata

Note

Write times are converted from the filesystem clock to the system clock by subtracting the two clocks' now() values, and then truncated to whole seconds. The conversion is approximate, so a timestamp that lands right on a second boundary could compare differently between two reads.

Loaders

A loader is a function std::shared_ptr<Base::Asset>(const std::filesystem::path&) registered for a file extension. Register it through IO::Resources (RegisterLoader, RegisterSimpleLoader<T>, or the Resources::LoaderRegistrar helper). This also registers it with ResourceLoader PR #28, so the scan indexes project files with that extension and they load there with their meta UUIDs.

  • RegisterSimpleLoader<T>(ext) creates a T with its default constructor and calls T::Load(path). It returns null if that returns false.
  • ResourceLoader::RegisterLoader rescans the project if the extension is new and Initialize has already run PR #28. Without the rescan, files of that type would have no metadata and would fall back to random UUIDs. Static registrars run before main, before any root is set, so they don't trigger a scan.
  • Registering an extension again replaces its loader (no rescan).
  • Extensions are matched against the file's lower-cased extension, but the registered key is used as given. Register extensions in lower case, with the dot (".wav").

IO::Resources: the lookup API PR #28

CallOrder of lookupLoads?
GetAsset<T>(uuid)Resources' own UUID map, then ResourceLoader::GetCachedByUUIDNo
LoadByUUID<T>(uuid)GetAsset<T>(uuid), then ResourceLoader::LoadByUUID (loads the project file with that meta UUID)Yes, project files only
GetAsset<T>(path)Resources' own path map (key: ResolvePath(path)), then, if the path is a project file, ResourceLoader::GetCachedNo
Load<T>(path)Resources' own path map, then for a project file ResourceLoader::Load, otherwise its own loadersYes

What counts as a project file (FindProjectPath): a res:// or user:// string that ResourceLoader has metadata for, or a filesystem path under ResourceLoader's assets root that maps to a tracked res:// path. A cheap lexical check against the assets root runs first, so lookups of files elsewhere never touch the filesystem. A file spelled with a different 8.3 short or long form from the root isn't recognised. If ResourceLoader hasn't been initialized, nothing is a project file.

Load<T> for a non-project file: the path is resolved (relative paths are joined to SetResourcePath's directory if that is an existing directory, otherwise used as-is). It returns null, without logging, if the file doesn't exist, has no extension, or has no loader. The asset keeps its random UUID and is registered here under that UUID and the resolved path. If the loaded asset isn't a T, it is discarded and null is returned.

This includes a res:// or user:// string that ResourceLoader has no metadata for (a typo, a file added after the last scan, or ResourceLoader not initialized): it is not a project file, so it is treated as a plain filesystem path, which doesn't exist, and Resources::Load returns null silently. ResourceLoader::Load on the same path would have logged "Resource not found".

RegisterAsset(asset, path = {}) registers under the asset's UUID and, if a path is given, under ResolvePath(path). It does nothing for an asset that ResourceLoader already holds under its UUID: caching it in both registries would keep each one's reference count above the other's eviction threshold.

Source: engine/include/engine/io/Resources.hpp — Resources::GetAsset, LoadByUUID, Load, RegisterAsset; engine/src/io/Resources.cpp — Resources::FindProjectPath, Resources::ResolvePath; tests: ResourceLoaderTest.ProjectAssetLoadedThroughResourceLoaderIsFoundThroughResources, ResourceLoaderTest.ProjectAssetLoadedThroughResourcesHasItsMetaUUID, ResourcesTest.AssetRefResolvesAnAssetRegisteredAtRuntime

Guarantee

A project asset loaded through either registry is the same object when looked up through the other, by UUID, by res:// path or by absolute path. It always carries its .meta UUID.

auto &res = N2Engine::IO::Resources::Instance();

// Project file: delegated to ResourceLoader, gets its stable meta UUID
auto clip = res.Load<N2Engine::Audio::AudioClip>("res://sfx/beep.wav");

// Same object, found again by UUID (e.g. when resolving a saved reference)
auto same = res.GetAsset<N2Engine::Audio::AudioClip>(clip->GetUUID());

// Runtime asset: random UUID, valid for this run only
auto generated = std::make_shared<N2Engine::LuaScript>("return {}");
res.RegisterAsset(generated);

Warning

Resources::RegisterAsset(nullptr) dereferences the null pointer: the "already in ResourceLoader" check is guarded, but the next line isn't. Path keys in Resources' own map are not normalized (ResolvePath(path).string()), so a/./b.x and a/b.x are different entries there. Project files are unaffected, because they go through ResourcePath.

Resources::UnregisterAsset still removes only the first path entry for the asset (it breaks after one match). RemoveUnused was fixed in #23 to erase all of them. Unregistering an asset that was registered under two paths leaves the second path entry, which keeps the asset alive and findable by that path. The Asset base class

Base::Asset is the base of every loadable or identifiable thing: AudioClip, LuaScript, and also Scene, GameObject and Component.

  • The default constructor assigns UUID::Random(), which is different on every run. Asset(uuid) takes an explicit UUID.
  • ResourceLoader::Load overwrites the UUID with the meta UUID and sets the ResourcePath after the loader returns. Assets created at runtime or loaded by Resources from outside the project keep their random UUID and an Invalid resource path.
  • Serialize() writes uuid and resourcePath. Deserialize() restores whichever of them is present. Subclasses extend both (for example, LuaScript adds sourceCode).
  • Load(path) returns false by default. RegisterSimpleLoader<T> relies on T overriding it.
  • GetResourceType() is pure virtual (for example "LuaScript" or "Scene").

Source: engine/include/engine/base/Asset.hpp, engine/src/base/Asset.cpp — Asset::Asset, Asset::SetUUID; engine/include/engine/scripting/LuaScript.hpp
