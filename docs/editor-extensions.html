Lua editor extensions

An editor extension is a Lua file in a project's editor/ folder that adds menu items, inspector sections and hooks to the editor. The editor host runs it in a sandbox of its own and the editor only draws what it declares. This page is the guide: the model, how to turn extensions on, the whole Editor API, who may do what, the limits, what to look at when a file does not load, and a worked example. The command-level detail (every gate, every error code, the registry, the watcher) is in Editor projects, and the function-by-function reference with its argument shapes is in Lua scripting. Everything here was checked against the host's code; the files it was checked against are named in the source lines.

The model

Three facts hold everything else together.

  • The Lua runs in the editor host, not in the editor. The host (N2EditorHost) is the process that has the scene. Each extension file runs in one Lua state of its own, made by the shared sandbox builder with the EditorExtension profile (below), and that state has no engine bindings: there is no GameObject, no Vector3, no Application. It has the Editor namespace and nothing that reaches the machine. These states are not the game's state and not the declaration evaluator's throwaway state (Lua scripting).
  • The UI is data. A file declares menu items, parameter forms and inspector sections as Lua tables. The host checks them when the file loads and lists them (GetEditorUi) as plain data: the functions stay in the host's state and are never sent. The editor draws the data with its own widgets, so no project code runs in the Electron editor. The Electron editor's source treats every string that comes from an extension as untrusted text and shows it as text, never as HTML.
  • Every change is a command. When a client runs an item, the host runs the item's function on a worker thread, and each Editor.Scene or Editor.Assets call of the script is a request to the host's command thread, which answers it by sending the command a client would send (SetLocalTransform, AddComponent, ...) with the role of the user who ran the item. So the read-only gate, the role gate and the audit line apply to the script as to a person, and a script can never do what the user who ran it could not. The whole call is one undo step labelled with the item's title, and a failure takes every change back (Running a menu item).

Extensions load at host start, on ReloadEditorExtensions and, with --editor-extensions-watch, for a single file when it changes. Opening, creating or loading a scene never loads or reloads one. A scene open does call the OnSceneOpened hooks of the extensions that are already loaded, after the scene is loaded (Hooks).

Guarantee

A host that was not started with --editor-extensions has no extension host at all: it never reads editor/, ListEditorExtensions answers enabled: false with nothing listed, and InvokeMenuItem is refused (EditorExtensionCommandsTest.*, AlignToolsOffByDefaultTest.AHostThatWasNotGivenTheFlagHasNoExtensionHostAndListsNothing).

Turning extensions on, and trusting a project PR #222

Extension code is project code that runs on the host, and a host cannot tell a project it should trust from one it should not. So extensions are off unless whoever starts the host asks for them, with two flags of N2EditorHost (--help lists both):

FlagWhat it doesRefused when the arguments are parsed (a line on stderr, exit code 1)
(neither)No extension host. editor/ is never read.-
--editor-extensionsLoads the project's editor/**/*.lua at host start, and again only on ReloadEditorExtensions (or, with the watch flag, for the one file that changed). Works with --read-only (the extensions are listed; nothing can run or reload them there). Without --project the host warns that there is no project folder to find extensions in, and has none.With --play ("a play host never loads editor extensions"). With a --bind address outside 127.0.0.0/8 and no --tokens-file: a single --token-env token is one admin and no roles, and --insecure-bind does not lift this, because who may run extension code on a host other machines reach has to be a role.
--editor-extensions-watchChecks editor/ about once a second (modification time and size, then a hash of the content) and loads again only the file that changed, loads a file that was added and drops one that was removed (the watcher). It does not wait for a client to be connected.Without --editor-extensions.

In the Electron editor (the separate N2Engine-Electron-Frontend repository) the flag is passed by one place, the project trust in its main process. A local project gets --editor-extensions only when its own editor/ folder holds at least one .lua file and the user answered Trust for that folder. The question is a native dialog the page cannot answer for the user: "This project contains N editor extensions. Trust this project?", listing the files and saying they run code on this computer's editor host and that what each may do (its capabilities) is not known until the host loads it. The buttons are Trust and Not now; Not now is the default button and is what closing the dialog does. The answer is kept per folder, by the folder's real path, in a file in the editor's user data folder: a moved, renamed or copied project asks again, and nothing inside a project can say it is trusted. Not now opens the project without the flag, and the page's banner offers to enable the extensions later (the same question, then a restart of the host). A remote host is never asked about: its flag is its operator's. The launcher passes --editor-extensions and does not pass --editor-extensions-watch, and it passes neither to a --play host.

The Electron editor draws the items of GetEditorUi as a Tools menu (a path's leading Tools segment is dropped, since the whole menu is Tools), asks the item's confirm question and shows its form before sending InvokeMenuItem, shows inspector sections under components of their type, shows each extensionOutput event in its console as an "extension" line, and has an Extensions section in the project settings with Reload for admins (its frontend PRs #47 and #54). How these look in the real application is not verified here.

At host start the host writes one log line per file (Troubleshooting). Only an admin can make the host reload: ReloadEditorExtensions is an Admin command.

Where the files are

The files are <project>/editor/**/*.lua, in a folder beside assets/, not inside it. That is the point: every protocol write (WriteTextAsset, CreateScriptAsset, CreateFolder) is confined to assets/, require and the play host resolve only under assets/, the web player packs only assets/ and project.n2proj, and ListAssets does not show the folder. So an editor-role user cannot create or change an extension, no game or play host loads one, and extensions arrive with the project (git, a deploy), never through the protocol. Even Editor.Assets cannot reach them: its paths are res:// paths inside assets/, so res://editor/x.lua is assets/editor/x.lua.

  • A file is found when its extension is .lua in any letter case. Its id is its path inside editor/ with / separators (tools/Align.lua); the registry is in id order, in byte order.
  • The walk goes 8 directory levels down and looks at no more than 4096 entries. Symbolic links, files and folders alike, are skipped and never followed, and a file whose real path is outside editor/ is left out; if editor/ itself is a link, nothing is loaded from it.
  • At most the first 64 files (in id order) are loaded. A file over 1 MiB fails without being read. A byte order mark at the start is dropped. A precompiled chunk is refused (text only).

What a file declares

A file calls Editor.Extension with a table and returns what it gave back. The host reads the table after the file ran and checks its shape; a wrong shape fails that file alone (its state becomes failed, with the reason), and so does a key this API version does not know, so a typo is found at once.

return Editor.Extension {
  name = "Snap Tools",
  apiVersion = 1,
  capabilities = { "scene.read", "scene.write" },
  menu = {
    {
      id = "snap.toGrid",
      path = "Tools/Snap/Snap selection to grid",
      params = { grid = { type = "number", default = 1, min = 0.01, max = 100 } },
      run = function(ctx, p)
        -- ctx.selection: the ids the user had selected; p.grid: the checked form value
        return { message = "done" }
      end,
    },
  },
}
KeyRule
nameRequired. 1 to 64 bytes of text with no path characters (/ \ : < > " | ? *, ..) and no space or . at either end: it ends up in logs, audit lines and menus. Several files may share a name; the id identifies a file.
apiVersionRequired, an integer, and it must be 1: that is the one version this host speaks.
capabilitiesOptional list of at most 8 of scene.read, scene.write, assets.read, assets.write, none twice. What each installs.
menuOptional list of at most 64 items: id, path, title, minRole, enabledWhen, confirm, params and run (Menu items).
hooksOptional table of hook name = function (Hooks).

Inspector sections are not a key of this table: they are registered with Editor.Inspector.Register while the file loads (Inspector sections). The whole declaration is also bounded: nested at most 8 levels, at most 4000 entries, a string at most 4096 bytes, a key at most 128 bytes; a number that is NaN or infinite, a table with a list and named entries mixed, and a list with a gap are errors. The exact limit of every key is in Editor projects.

Forms and field kinds

A menu item's (or an inspector button's) params is a form: a table of name = spec with at most 32 entries, each name letters, digits and _, not starting with a digit, at most 64 bytes. The host builds from it the protocol's FieldSchema list (sorted by name) and an object of defaults, the client draws the fields, and the host checks the values it gets back before any Lua runs: every name must be a field of the form, each value passes ValidateFieldValue (the check that guards a component's fields) and is clamped to the field's min and max with ClampFieldValue, and a field left out takes its default. An item without a form takes no parameters. The script's params therefore has every field of the form.

typeField kindThe script getsSpec keys
"number"Floata numberdefault, min, max, tooltip, displayName
"int"Intan integerthe same; min, max and default must be whole numbers (finite, at most 9e15)
"string"Stringa stringdefault (at most 1024 bytes), tooltip, displayName
"bool"Boola booleandefault, tooltip, displayName
"Vector3"Vector3{ x, y, z }default (a table with exactly x, y, z), tooltip, displayName
"GameObject"GameObjectRefan object id (a string), or nil when none was chosenno default; tooltip, displayName
"enum"Enumone of the options (a string)options (required: 1 to 64 distinct strings of at most 64 bytes), default (one of them; the first when absent), tooltip, displayName

Another type is an error of the file (component and asset types are not form fields). min and max go only with number and int, options only with enum, min may not be above max, and a default outside them is an error. A number or int with no default takes its min when that is above zero, else its max when that is below zero, else zero; the other kinds start at false, the empty string, a zero vector or the first option. A tooltip is at most 200 bytes and a displayName at most 64 (the name spaced out when absent).

Menu items

An item is one entry of the editor's Tools menu.

KeyRule
idRequired. Letters, digits, ., _, -, starting with a letter or digit, at most 64 bytes. Unique across the whole host (a client names an item by its id and nothing else): the first file in id order keeps an id and a later file that uses it fails.
pathRequired. Segments separated by /, at most 6 and 200 bytes, each 1 to 64 bytes, not . or .., no backslash, no space at either end. The last segment is the item's title unless title is given.
titleOptional, at most 100 bytes. It is also the label of the undo step.
minRole"editor" (the default) or "admin". A viewer never runs an item. The host enforces it (roles).
enabledWhenOptional { selection = "any" | "nonEmpty" | "one" | "none", componentType = "Name" }. For the client only: the host does not check it, so a script must cope with any selection it is given.
confirmOptional question (at most 200 bytes) the client asks first. Also client-only.
paramsThe form (above).
runRequired, a function run(ctx, params). ctx is { itemId, selection }, where selection is the list of the UUID strings the client had selected (at most 4096; the host does not check that the objects exist).

The item runs when a client sends InvokeMenuItem. Before any Lua runs, the host checks, in this order: the command gates every command has, that extensions are enabled, that the client's uiRevision is the current one (staleUiRevision otherwise), that the item exists, minRole, that the extension is not faulted, that the client has no edit group open (editGroupOpen), and then the selection and the form values (the list, with the codes). Then it opens one edit group and runs run on a worker thread under the invocation budget (Budgets).

What run returns is nothing, or a table of { message = "...", select = { ids }, warnings = { "..." } } and no other key: anything else (another key, a number as the message) fails the call. message and each warning are cut to 1024 bytes (control characters other than line breaks and tabs replaced), select holds at most 4096 UUID strings that the client selects, and warnings at most 100. When the item returns, the group ends: changes are one undo step labelled with the title, writes that left the scene as it was make no step, and an item that changed nothing makes nothing. When it fails (a Lua error, a budget trip, the memory cap, a result of the wrong shape) every change is taken back, no step is made, the redo steps are kept, and the client gets extensionFailed with the reason. A command the host refuses is a Lua error at the call, which pcall can catch: an item that catches it and returns normally keeps what it did before that call. (Asset writes are the exception: they are files, not scene edits, so a failed call leaves them. See Editor.Assets.)

Inspector sections

Editor.Inspector.Register(componentType, { sections = { ... } }) adds sections to the inspector of one component type. It can be called only while the file loads (before or after Editor.Extension, at most 64 times); a call from a running item, button or hook is a Lua error. The file must declare scene.read. A section is { label, fields?, buttons? } and needs fields or buttons. fields has the shape of a form without default (the client shows the component's own value). buttons is a list of at most 16 of { id, label, minRole?, params?, run }: a button's id is unique among the inspector buttons of the whole host (in a namespace of its own, so a button and a menu item may share an id), its label is the undo step's label, and its run(ctx, params) gets ctx = { actionId, componentId, entityId }. A file has at most 32 sections.

The client sends InvokeInspectorAction with a component id and a button id. The host finds the component in the open scene and refuses one that is not of the section's componentType (the host does not check that a type of that name exists, so a section for an unknown type matches nothing), so a button only ever runs on a component its section is shown for; the script gets the object's id from the host. Everything else is as for a menu item: the same gates, one undo step, the same budgets, the same rollback, the same result shape. A section for LuaComponent applies to every Lua script component, since they share that type name.

Editor.Inspector.Register("Light", {
  sections = {
    {
      label = "Light tools",
      buttons = {
        {
          id = "light.double",
          label = "Double the intensity",
          run = function(ctx, p)
            local light = Editor.Scene.GetComponent(ctx.entityId, ctx.componentId)
            Editor.Scene.SetFields(ctx.entityId, ctx.componentId, { intensity = light.intensity * 2 })
            return { message = "Doubled" }
          end,
        },
      },
    },
  },
})
return Editor.Extension { name = "Light Tools", apiVersion = 1, capabilities = { "scene.read", "scene.write" } }

Hooks

A file may declare hooks = { OnSceneSaved = function(info) ... end }. The four names below are the only ones; another name, or a value that is not a function, fails the file. A hook needs the capability of what it reads, checked when the file loads: scene.read for the three scene hooks, assets.read for OnAssetsChanged.

HookCalledArgumentReturn value
OnSceneOpened(info)After OpenScene or NewScene made a scene the open one{ scene = "res://..." }, "" for a new scene with no file yetignored
OnSceneSaved(info)After SaveSceneToFile wrote the file and marked the history saved; not after a save that failed{ scene = "res://..." }ignored
OnBeforePlay(info)In the handler of WritePlaySnapshot, after the request was accepted and the snapshot written, before the response; a request that is refused (a path outside the project, no scene, a play host) calls no hook{ scene = "res://..." }: the scene the client asked to play, or the open scene's path when it named nonenothing, or { warnings = {...}, message = "..." } and no other key
OnAssetsChanged(added, removed, modified)After the host reloaded the assets that changed and pushed assetsChanged: after RescanAssets, a client's asset write and the asset watcher's pollthree lists of res:// paths, each cut to 1000ignored
  • A hook is read-only. It may call the readers of Editor.Scene, Editor.Assets.List and ReadText (for the capabilities it declared), Editor.Log and print. A write is a Lua error that says the hook is read-only. Three checks each hold that alone: the worker refuses every operation that is not a read, the host lets only Read-class commands through for a hook, and a hook's commands run as a viewer, whoever is connected. A hook opens no edit group and makes no undo step.
  • A hook is a small, separate call. It runs after the work that caused it, on a worker, under the hook budget (20 million instructions, 0.5 s), sending at most 1000 requests. The hooks of one trigger, all extensions together, share 2 s: once they are spent the rest are skipped and the host logs it.
  • A hook never fails the work that called it. A hook that errors, runs out of budget or returns a bad result is logged and counted against its extension like a failed item (the fault flag); the save, the open, the snapshot or the asset change goes on.
  • OnBeforePlay never blocks play. Each warning (and the message) becomes an extensionOutput event of level warn, at most 1024 bytes each, and an Admin log line. Unlike Editor.Log output, these events are not Admin-tagged: every role receives them.
  • The host opens its startup scene before it loads the extensions, so OnSceneOpened is not called for that scene. No hook is called in a play host, nor while another extension call is running: an asset that an extension writes itself does not call OnAssetsChanged, so a hook cannot start another run of itself. A failed or faulted extension's hooks are not called.

Capabilities and roles

Capabilities

A file asks for what it needs in capabilities, and a function of a capability the file did not declare does not exist in its state (it is nil, not refused); the host checks the capability again on every request, in case one reaches it anyway.

CapabilityInstallsAlso needed by
scene.readthe six readers of Editor.Scenethe hooks OnSceneOpened, OnSceneSaved, OnBeforePlay, and any inspector section

A name that is not in this table (project.write and import.hooks are reserved for later, not granted) fails the file. Every capability is also capped by the role of whoever runs the item: scene.write lets the script send the write commands, and each of them is refused if that user's role may not send it.

Roles

The roles exist only on a host that has access tokens: a --tokens-file gives each user a role (admin, editor or viewer), and a single --token-env token is one admin identity. A host with no token has no roles: the one local user may do everything in this table. A host that is bound to a non-loopback address must have a tokens file to load extensions at all (above).

Budgets, workers and the fault flag

Extension code is bounded in instructions, wall-clock time and memory, and a stalled call cannot stall the host.

  • A whole load (host start or a reload) waits for its workers for at most about 10 s of wall clock; a file it did not reach in time fails as data and is tried again at the next reload. At most 64 files of at most 1 MiB are loaded.
  • Workers. Each file's load and each call runs on a worker thread, and the command thread waits for it. At most 4 workers exist at once, abandoned ones included. A worker that neither asks the host for something nor finishes within the silence limit above is abandoned: it owns copies of what it touches, never reads or writes the registry again, and closes its state when it ends. This is what bounds a call into C that the instruction hook cannot interrupt (Lua scripting says which).
  • The fault flag. A failed call counts against its extension: a Lua error or a result of the wrong shape counts one, and 3 failures within 10 minutes make the extension faulted; a budget trip, the state's memory cap or an abandoned worker faults it at once. A faulted extension stays listed with its items (so a client can show them disabled with the reason), refuses InvokeMenuItem and InvokeInspectorAction with extensionFaulted, and its hooks are not called, until the next reload. Hook failures count the same way.

The sandbox

A state is made by LuaSandbox::Create(SandboxProfile::EditorExtension) (the shared builder). What it has and lacks:

  • Has: the base library without load, loadstring, loadfile, dofile, collectgarbage and warn; math; table; utf8; string without find, match, gmatch, gsub (patterns: their cost in C is invisible to the instruction budget) and dump; print, which the host replaces so that it writes to Editor.Log.Info; and the Editor table described above.
  • Lacks: io, os, debug, package, coroutine, require and load (so no file, no process, no network, no way to turn text into code), and every engine binding. Another extension's globals are not visible (one state per file), and the one C function that reaches the host is taken into a local by the host's prelude and removed from the globals before the file's first line runs.
  • Is idle between calls. After its file loaded, a state runs only when a client runs one of its items or buttons, or the host calls one of its hooks. It is discarded at the next reload (or when its file changes, with the watcher).

Security notes

  • It is project code, and the sandbox bounds what it can do, not whether it is yours. The state reaches no file, process or network, and only the 17 commands above, but it reads the whole scene (and, with assets.read, the text assets) and changes whatever the user who runs it may change. The control that matters is who may put a file in editor/ and whether the host loads it: the folder is outside the protocol's reach, the flag is off by default, and the Electron editor passes it for a local project only after the user trusts the folder.
  • Trust is per folder, not per file. A project folder that was trusted and later gets a new .lua file in editor/ (a git pull, say) loads it at the next host start without a new question. Review the folder, not only the first version.
  • Admin-only things. ReloadEditorExtensions; an item or button with minRole = "admin" (on a host with tokens); the host's audit and log lines, which include extension=<name>@<first 8 hex digits of the file's sha256>; and Editor.Log output, which is Admin-tagged. Only an admin (or the one user of a host without tokens) receives them. The one extension output every role receives is OnBeforePlay's warnings.
  • The role of the user who runs an item applies to everything the item does. A viewer runs nothing. A hook is a viewer.
  • No host path in an error. A chunk's name is its id, and an error text that reaches a client has the project's folder and its parent replaced by <project>.
  • What is never available to an extension: an engine object, the game's Lua state, another extension's state, any file or process, load, the editor/ folder (not even as an asset path), the commands that open, save or load a scene, undo or redo, group edits, play, Shutdown, the extension commands themselves, and the viewport. An extension cannot call into the Electron editor or put code in it.
  • What the budgets do not cover. A call into a C function that never returns (a table.concat, unpack or sort over a huge range) cannot be interrupted by the instruction hook; the worker is abandoned at its deadline instead, which leaves a thread running until the call ends, and at most 4 such threads can exist before the host refuses to start more extension work until they end. An asset write by Editor.Assets is a real write to the project, and a failed invocation does not take it back.

Troubleshooting: states and messages

An extension is in one of three states, shown by ListEditorExtensions with an error text for the last two. There is no separate "refused" or "incompatible" state: every way a file does not load is failed, and the reason says which.

StateMeaning
loadedThe file ran and returned a valid declaration, and its state is kept. Its items, sections and hooks are live.
failedAnything else: it could not be read or loaded, or its declaration is wrong. It has no state, no items, no sections and no hooks, and the other files are not affected. It is tried again at the next reload (with the watcher, when the file changes; a file that failed on an id clash is also tried again when the extension that held the id changes or goes).
faultedLoaded, then failed too often or ran out of a budget (above): disabled until the next reload. Its items stay listed.

The host writes one line per file when it loads: Editor extension: <name>@<sha8> capabilities=[...] menu items=N inspector sections=N (<id>) (with hooks=[...] when it declared some) for a file that loaded, Editor extension <id> did not load: <reason> for one that did not, and Editor extensions: N of M loaded. The reason is also the error of ListEditorExtensions, with no host path in it.

A worked example: AlignTools PR #222

lua_project/editor/AlignTools.lua is a small extension that is safe to read, copy and run. It adds three items to Tools > Align, which work on the local positions of the selected objects, and one hook:

  • Align selection (align.align): a form with an axis (x, y or z) and a mode (min, center or max); every selected object moves to the lowest, the middle or the highest position on that axis and keeps its other two coordinates.
  • Distribute selection evenly (align.distribute): the same axis; the two end objects stay and the ones between are spread evenly in their order along the axis. It needs three objects and says so in its message otherwise.
  • Snap selection to grid (align.snapToGrid): a grid size (0.01 to 100, default 1) and a boolean per axis (snapX and snapZ on, snapY off by default).
  • An OnSceneSaved hook that writes one line to Editor.Log, which shows that a hook is declared in the same table and reads info.scene.

It declares only scene.read and scene.write, so it has no Editor.Assets. Each item refuses a selection of more than 2000 objects with a warning, because one call may send at most 10,000 commands and reading an object costs one and moving it two. An abridged copy of the file follows (its comments and the other two items are left out):

local MAX_OBJECTS = 2000

local function tooMany(ctx)
  if #ctx.selection > MAX_OBJECTS then
    return {
      warnings = { string.format("Select at most %d objects (this selection has %d).", MAX_OBJECTS, #ctx.selection) },
    }
  end
  return nil
end

-- The selected objects as { id, index, position }, in selection order
local function readPositions(ids)
  local entries = {}
  for i, id in ipairs(ids) do
    entries[i] = { id = id, index = i, position = Editor.Scene.GetLocalTransform(id).position }
  end
  return entries
end

-- Moves one object along one axis; a transform names only what it changes, so the rest of it stays
local function moveAlong(entry, axis, value)
  local p = entry.position
  local moved = { x = p.x, y = p.y, z = p.z }
  moved[axis] = value
  Editor.Scene.SetLocalTransform(entry.id, { position = moved })
end

local AXIS = { type = "enum", options = { "x", "y", "z" }, default = "x", tooltip = "The axis to work along" }

return Editor.Extension {
  name = "Align Tools",
  apiVersion = 1,
  capabilities = { "scene.read", "scene.write" },
  menu = {
    {
      id = "align.align",
      path = "Tools/Align/Align selection",
      enabledWhen = { selection = "nonEmpty" },
      params = {
        axis = AXIS,
        mode = {
          type = "enum",
          options = { "min", "center", "max" },
          default = "center",
          tooltip = "Move every object to the lowest, the middle or the highest position on the axis",
        },
      },
      run = function(ctx, p)
        local refused = tooMany(ctx)
        if refused then
          return refused
        end
        local entries = readPositions(ctx.selection)
        if #entries < 2 then
          return { message = "Select two or more objects to align." }
        end
        local low = entries[1].position[p.axis]
        local high = low
        for _, entry in ipairs(entries) do
          local value = entry.position[p.axis]
          if value < low then
            low = value
          end
          if value > high then
            high = value
          end
        end
        local target = low
        if p.mode == "max" then
          target = high
        elseif p.mode == "center" then
          target = (low + high) / 2
        end
        for _, entry in ipairs(entries) do
          moveAlong(entry, p.axis, target)
        end
        return {
          message = string.format("Aligned %d objects on %s (%s).", #entries, p.axis, p.mode),
          select = ctx.selection,
        }
      end,
    },
  },
  hooks = {
    OnSceneSaved = function(info)
      Editor.Log.Info("Align Tools: saved " .. info.scene)
    end,
  },
}

What happens when a user runs it, in the terms of this page: the editor asks GetEditorUi for the items (the host answers from what it captured when the file loaded and runs no Lua); the user selects objects, picks Align selection and fills the form; the editor sends InvokeMenuItem with the item's id, the selection, the form values and the uiRevision it built the request from; the host checks the gates and the form (an axis that is not an option is refused before the file runs), opens an edit group labelled "Align selection", and runs run on a worker; each GetLocalTransform and SetLocalTransform goes to the host as a command with the user's role; the result's message is shown and its select reselects the same objects; and one undo takes every object back. A selection id that is not an object makes GetLocalTransform raise a Lua error, and the whole call is taken back.

It is off by default in every way that can be checked: it is not an asset, so no game, no play host and no lua_project run loads it; the web player packs only assets/ and project.n2proj; and the editor host loads it only when it is started with --editor-extensions for lua_project as its project (in the Electron editor, after the user trusts that folder). In this repository only the editor host's ExtensionHost looks in an editor/ folder at all. AlignToolsTest.* (in tests/editor-server/project/EditorExtensionAlignToolsTests.cpp) points an EditorServer at lua_project itself, so the file the test loads is the file in the repository, and runs each item through InvokeMenuItem against a scene: one undo step each, the form checked by the host, an invalid axis refused, a too-large selection refused with a warning, and the hook run. AlignToolsOffByDefaultTest shows a server without the flag has no extension host.

Design decision: the example lives in lua_project/editor/ and is loaded where it lies PR #222

lua_project is a real project folder (project.n2proj, assets/), and an extension belongs in the editor/ folder of a project, so that is where the example is: a reader can open the project and see an extension in its place. Nothing else changes for the project: editor/ is beside assets/, so the resource loader, the scene tests that read lua_project/assets, the web package (which packs assets/ and the project file) and the lua_project executable never see it. The test does not copy the file into a temporary project: it enables the extension host on lua_project, so a change to the file that breaks it breaks the test. Judgement call of this PR: the plan names the path and asks for a project test using the existing fixtures; reading the real file in place is how this one uses them.

Editor completion: editor-api.lua PR #222

editor-server/editor-api.lua is a definition file for the Lua Language Server (LuaLS) that describes the Editor API of this page: ---@class, ---@field, ---@param and ---@return annotations over empty function stubs, the capability and hook names as aliases and classes, and the shape of a declaration, a form field, a result and every value Editor.Scene and Editor.Assets return. It is separate from engine-api.lua because it describes a different state: an extension has no GameObject or Vector3, and a scene script has no Editor. Nothing loads it; it exists for completion, hover text and type checking. To use it, add the folder to LuaLS as a library for the files under editor/ (in VS Code with the Lua extension, Lua.workspace.library in the workspace settings or a .luarc.json; the repository ships neither), with the path adjusted to where the engine is:

{
  "workspace.library": ["path/to/N2Engine/editor-server"],
  "runtime.version": "Lua 5.4"
}

ExtensionApiAnnotationTest.* keeps the file honest. It reads the file, makes a state of an extension that declares every capability, and lists the functions in its Editor table: a function the host registers that has no stub fails the test, so does a stub for a function the host does not register, so does a stub whose number of parameters or ... differs from the host's function, and so does a stub whose ---@param lines do not name its parameters in order. It compares the file's hook names (the On... fields of EditorHooks) with ExtensionHost::HookNames and its capability names with ExtensionHost::CapabilityNames, and checks that the file is plain ASCII, starts with ---@meta and holds no code but the namespace tables and the empty stubs. What it cannot check is the types and the descriptions: they are as accurate as this page and Lua scripting, which were checked by reading.

Design decision: editor-api.lua is a separate file, checked against the live Editor table PR #222

engine-api.lua has no check: nothing in the build or the tests reads it, so it can drift from the bindings and its docs section lists where it already does. The editor API is small and stable enough to do better cheaply, and an annotation file that names a function the host does not have, or misses one it has, gives wrong completion exactly where an extension author needs it right. The test enumerates what the host really registers by making a state, not by reading ExtensionHost.cpp as text, so a function added to the prelude without a stub fails at once. Parameter counts are read from the functions themselves (lua_getinfo), which needs no debug library in the state. The file sits in editor-server/, next to the host that registers the API, and is found by the test through a compile definition. Judgement call of this PR: the plan says to extend a check if one exists and otherwise add a cheap one; none exists for engine-api.lua, and this PR does not add one for it.
