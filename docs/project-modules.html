Project modules

A game can leave out the engine modules it does not use, so its build is smaller. The project lists its modules, a scan checks the list against what the project uses, and the build compiles the rest out. So far the list covers physics, particles, soft bodies, audio, UI, scripting, network and the Vulkan and WebGPU renderer backends.

The list

A project lists its modules in project.n2proj. The editor keeps the key when it saves the file.

"build": {
  "modules": {
    "physics3d": "none",
    "physics2d": true,
    "particles": true,
    "softbodies": false
  }
}
ModuleValuesSets
physics3dnone, physx, jolt, bothN2ENGINE_USE_PHYSX, N2ENGINE_USE_JOLT
physics2dtrue, falseN2ENGINE_USE_BOX2D
particlestrue, falseN2ENGINE_USE_PARTICLES
softbodiestrue, falseN2ENGINE_USE_SOFTBODIES
audiotrue, falseN2ENGINE_USE_AUDIO
uitrue, falseN2ENGINE_USE_UI
scriptingtrue, falseN2ENGINE_USE_SCRIPTING
networktrue, falseN2ENGINE_USE_NETWORK
vulkantrue, falseN2ENGINE_RENDERER_VULKAN (only ever off; see Renderer backends)
webgputrue, falseN2ENGINE_RENDERER_WEBGPU (the web build's; only ever off)

A module the list does not name keeps its usual option. A project with no list builds everything. Unknown modules and values stop the configure with a message.

Design decision: the list is explicit, and the scan only checks it

Lua can reach a component through a computed name, as in AddComponent(kinds[i]), and no scan can resolve that. Stripping from the scan alone could remove something a script needs, and the game would break only when that line ran. So a person writes the list, and the scan suggests one and checks it.

Renderer backends

vulkan and webgpu leave a renderer backend out of the player. They follow one rule: the build target's own setting is the ceiling. A key can turn a backend off that the target would build, and can never turn one on that the target does not build (no Vulkan on the web, no WebGPU natively). true is the same as no key: the target keeps what it builds, and a true for a backend the target lacks prints a configure note. A target that forces a backend on (Android with build.targets.android.renderer vulkan, macOS and iOS with MoltenVK) keeps it unless the key is false; then it builds without it.

  • The software renderer is always built (and OpenGL in the desktop build), so a list can never leave a game with no renderer, and no configure fails for that. Besides the checks described under The scan, it refuses this contradiction: build.targets.<T>.renderer naming a backend that the list leaves out.
  • Vulkan off needs no Vulkan headers, loader or glslc. n2player --renderer vulkan then stops at once with this player was built without the Vulkan renderer; the engine's window code says the same for any other host.
  • WebGPU off (web) leaves out the emdawnwebgpu port and the page's device probe: the shell's n2-webgpu tag is no, so the canvas stays free for the software renderer, and the player refuses --renderer webgpu. Natively WebGPU is a CI-only backend that is off by default, so the key changes nothing there.
  • Games pick a renderer at run time (--renderer, or the target's renderer setting); the list decides only which ones the build contains.
  • OpenGL and the software renderer are not keys: they are small, share the window and presentation code, and the software renderer is the fallback for everything else.

Test project: tests/projects/no_vulkan. The Linux CI job builds its player, checks that --renderer vulkan is refused and that the game runs on the software renderer, and prints the size against the full player as [MODULES-SIZE-NATIVE] lines. The web job builds it too (the WebGPU half) and prints [MODULES-SIZE].

Building a game with its list

cmake -S . -B build-mygame -DN2ENGINE_PROJECT=path/to/game

The engine is one static library, so the list applies to the whole build tree, and a game gets a tree of its own. An editor's tree never sets it, because a project can use anything while it is being edited.

  • Web: N2ENGINE_PROJECT also picks the project the player packs, in place of N2_WEB_PROJECT_DIR. Build the web-package target as usual (Web build).
  • Native: a native game is its own executable linking engine, as lua_project is. It can call n2_check_project_modules(<target>) in its CMakeLists.txt to check again each time it links.

Strict floating point for a networked game

build.strictFp (true or false, beside modules) sets N2ENGINE_STRICT_FP, the strict floating-point profile (Math), for the game's build tree. Left out, n2build turns it on for a game that uses networking (a NetworkObject, NetworkTransform or LagCompensatedHitbox in a scene or prefab, the Network Lua table, or a network preset) and leaves the build's own default for any other game. A direct cmake configure reads only the key, so it must be set there. When the project sets it to false and some object has a networking component and a 3D or 2D physics component together, n2build build (and so the editor's Build) reports a warning: peers built without the profile can compute different physics floats and desync. Components added from Lua are in no scene: a Lua file that names a networking component and a physics component (AddComponent("NetworkObject") and AddComponent("Rigidbody")) raises the same warning as a nearest match, since the scan cannot tell whether one object gets both. The Android target passes the answer to Gradle (-Pn2.strictFp, so the automatic "on" reaches its CMake step too), and a GitHub Actions build (iOS, macOS) runs n2build on the runner, which resolves the key from the pushed project; the warning is also shown on the machine that starts it.

Source: scripts/project-modules.mjs — resolveStrictFp, strictFpWarning; tools/n2build/n2build.mjs; cmake/N2EngineModules.cmake; tests: scripts/project-strict-fp.test.mjs, tools/n2build/n2build.test.mjs

A list per build target build targets stage 3

A project can give one build target its own modules in build.targets.<target>.modules (Per-target settings). They are laid over build.modules key by key, so a target names only what it changes:

"build": {
  "modules": { "physics3d": "physx", "physics2d": true },
  "targets": { "android": { "modules": { "physics3d": "jolt" } } }
}

Android then builds Jolt and Box2D; every other target builds PhysX and Box2D. -DN2ENGINE_TARGET=android on the configure picks the target's list (n2build passes it), and node scripts/project-modules.mjs path/to/game --target android checks that list. Without N2ENGINE_TARGET only build.modules counts, as before.

The scan

node scripts/project-modules.mjs path/to/game             # what it uses against its list
node scripts/project-modules.mjs path/to/game --suggest   # the smallest list the scan can justify
node scripts/project-modules.mjs path/to/game --target android   # the list a build for that target uses

It reads the component types in scenes and prefabs, and in Lua the module's globals, its event handlers and component names in quotes. Particles and soft bodies have no Lua global of their own, so for them it is the component name alone: "ParticleSystem" and "SoftBody". Comments do not count. It also reads the project settings: physics.backend, and the deterministic network preset, which needs Jolt.

  • A conflict stops the build. It names the file and line, and runs at configure time, so before anything compiles, and again when the game links.
  • A computed name is reported as "could not be checked". It does not stop the build. Check those by hand.
  • Without node the check is skipped with a warning at configure time.

What a stripped module does at run time

The components stay registered, so a scene that names one still loads and saves without losing data, and the editor still lists it. The registry, and so the network fingerprint, does not depend on the list.

  • 3D physics: no backend, as when physics fails to start. Components warn and do nothing (Application), and Physics queries find nothing.
  • 2D physics: see Leaving it out of a game.
  • Particles: a ParticleSystem keeps its settings, plays and stops, and emits and draws nothing (Leaving it out).
  • Soft bodies: a SoftBody keeps its settings and never starts, so its MeshRenderer draws the mesh as it is (Leaving it out).
  • Network: the server and client sessions, lockstep, rollback, replication, prediction and the Network Lua table are not in the build, and N2Server is not built (Leaving it out). The network components, the settings and the fingerprint registry stay, so the fingerprint does not change.

Particles and soft bodies do not depend on physics: each has a CPU backend, so a game can keep them with "physics3d": "none". Leaving one out removes all of its backends, the PhysX GPU one included, from a build that keeps PhysX.

Scripting

"scripting": false leaves out the Lua runtime, sol2 and every Lua binding: LuaRuntime, the sandbox, the coroutine support and the bindings of every other module. It is for a game with no Lua scripts at all.

  • How such a game starts. Without Lua there is no assets/scene.lua to run, so the game must name a startupScene. The desktop, Android and iOS players load it whenever a project names one, and the web player does when it is built without scripting (with scripting it still runs assets/scene.lua); the scan reports a project with no startupScene as a conflict. The dedicated server (N2Server) is built only with both the network and the scripting module: it builds on the editor host's library, which needs Lua.
  • A scene saved with scripts still loads. LuaComponent stays registered and keeps its script reference (scriptUUID or scriptPath) and its scriptData, saves them again as it read them, and runs nothing. The first one read logs one warning (N2ENGINE_USE_SCRIPTING is OFF); there is one per process, not one per component. .lua files are still assets of type LuaScript.
  • The scan. Any .lua file under assets or scenes, and any LuaComponent in a scene or prefab, is a use of the module, so the list cannot leave it out while the project has scripts: the build refuses a list that would make them silently not run. A scene with LuaComponents still loads in a tree configured with -DN2ENGINE_USE_SCRIPTING=OFF directly, as above. A project with no startupScene counts as using it too (the players run assets/scene.lua), so --suggest does not suggest leaving it out.
  • Health. The Scripting row is Disabled: "Not in this build". The Deterministic network preset still requires determinism.luaSeed, as in every build (the requirement is checked from the project settings; it changes nothing here, because no Lua state exists).
  • The editor. The editor host runs project scripts and editor extensions in Lua, so a tree with N2ENGINE_USE_SCRIPTING=OFF does not build editor-server, the dedicated server (n2server, which is built on the editor host's library), lua_project or their tests. An editor's tree never sets the option (see above), so the editor keeps Lua. The golden replay's two Lua scenes (lua_sim, lua_driven) are not in a build without the module; transforms is.
  • Tests. A build without the module leaves out every test of the Lua runtime and its bindings (tests/engine/scripting and the other files that run Lua), skips the cases of other files that run a script, and runs tests/engine/modules/LeftOutScriptingTests.cpp. The size numbers are in the PR that added it.
