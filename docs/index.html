N2Engine behaviour reference

N2Engine is a C++23 game engine with a GameObject/Component model, PhysX physics, OpenAL audio, an action-based input system, Lua scripting and a headless editor host. These pages describe how the engine behaves: what is guaranteed, in which order things happen, how long objects live, and what counts as an error.

What these docs cover

These pages describe the engine as it is on master. Behaviour that a specific pull request introduced or changed carries a badge such as PR #34, so you can find the PR description and review thread that explain it. Much of the baseline was settled by the fixes for the engine code review (#16) in PRs #17–#24; later work added PhysX mass properties (#26), SIMD correctness and dispatch (#27, #30), scene storage and asset registries (#28), Lua checked handles (#29, #31), editor-server hardening (#33) and core lifetime fixes (#34).

The pages are written from the source code, cross-checked against the PR descriptions and review threads. Where the code and the prose disagree, the code wins. Where behaviour is unclear or looks inconsistent, the page says so in an Open question callout instead of guessing.

Out of scope for this version: the renderers (OpenGL, Vulkan, software) beyond where they appear in the frame, the example projects, and full API listings. The headers remain the API reference.

How to read a page

Each page starts with a short summary and an "On this page" list, then goes through behavioural contracts one topic at a time. Four kinds of callout are used consistently:

Guarantee

Something the engine enforces, usually pinned by a named test. Code may rely on it.

Note

Rationale, context, or a consequence that is easy to miss.

Warning

A footgun: behaviour that is intended but surprising, or a pattern that is not supported.

Open question

Behaviour that is unclear, undecided, or inconsistent in the code. These are candidates for issues.

Modules

The CMake project (CMakeLists.txt) builds these targets:

math/Vectors, matrices, quaternions, UUIDs, random numbers, with SIMD dispatch. No engine dependencies. See Math & SIMD.

Two build options change behaviour: N2ENGINE_USE_PHYSX (default ON; when OFF the engine has no physics backend and reports physics as Disabled) and N2ENGINE_BUILD_TESTS. The math target requires AVX (/arch:AVX, a PUBLIC flag on the math target); see why SIMD tiers still exist.

Architecture map

Application

Singleton. Initializes subsystems, reports their health, runs the frame loop, owns the window, camera and physics backend.

SceneManager & Scene

SceneManager stores scene snapshots by name and switches scenes at the end of a frame. A Scene owns its root GameObjects and drives their updates.

GameObject & Component

Hierarchy of objects; components get lifecycle callbacks (attach, enable, update, disable, destroy).

Transforms

Positionable: local and world position, rotation, scale; tells physics when it moves.

Coroutines

Per-scene scheduler for std::generator-based coroutines with Unity-style waits.

Physics

IPhysicsBackend with a PhysX implementation; Rigidbody and collider components; collision and trigger events; raycasts.

Input

Action maps with typed actions and bindings; owned by the window, updated as events are polled. Mouse picking and the OnMouse* callbacks.

Audio

OpenAL-based AudioSystem: sources, one-shots, mixer groups and a listener.

UI

Screen-space overlay UI as GameObjects: Canvas, RectTransform anchors, Image, UIText and Button PR #54; drawn in a canvas pass after the scene and hit-tested before world picking.

Text & fonts

Font assets with SDF atlases built at load time, and UTF-8 layout with kerning, wrapping and alignment, and the TextRenderer component for world-space text (OpenGL, and alpha-tested on the software renderer); UI text shares its drawing code.

Meshes, models & textures

Texture assets decoded from PNG, JPEG, TGA and BMP with import settings, the UV convention, and the GPU cache that shares textures per renderer PR #64; Mesh and Material assets, .mat files, MeshRenderer and the built-in shapes on shared meshes PR #65; glTF models with sub-assets, Model::Instantiate and the Blender export guide PR #68.

Resources

res:// and user:// paths, the project asset scan with stable meta UUIDs, and one lookup API.

Serialization

Scenes and components to and from JSON, including references between objects and to assets.

Lua scripting

LuaComponent runs scripts with lifecycle callbacks, serializable fields and checked handles.

Logging, health, editor

Logger with backlog and subscribers; EngineHealth; the TCP editor host.

Who owns what

Most lifetime rules in the engine follow from this ownership graph:

  • Application (function-local singleton) owns the Window (which owns the InputSystem and the renderer), the main Camera, and the 3D physics backend.
  • SceneManager (singleton) owns the stored scene snapshots (StoredScene{name, data} JSON), the loaded Scene, and a pending scene, each behind std::unique_ptr.
  • Scene owns its root GameObjects (std::shared_ptr<GameObject>) and its coroutine scheduler. It also keeps non-owning lists of components and lights for iteration, which every removal path updates through Scene::DetachComponent. Scenes cannot be moved, because objects point back at them.
  • GameObject owns its children (shared_ptr) and its components (std::unique_ptr<Component>). Anything else that refers to a component, including Lua, holds a raw pointer or a checked handle.
  • Subsystem singletons (AudioSystem, LuaRuntime, Logger) are process-wide. AudioSystem is deliberately never destroyed, so components can unregister from it during static destruction.

Note

A GameObject can outlive its scene, for example when C++ code or a Lua handle still holds the shared_ptr. When a scene is torn down it clears the scene pointer of every torn-down object that still belongs to it, so they are inert rather than dangling. RemoveChild no longer leaves objects behind: a child removed inside a scene becomes a root of that scene; see Hierarchy.

How a frame runs

Application::Run repeats the following until the window closes or Application::Quit() has been requested. The full contract, including edge cases, is on the Application page.

  1. Input. Window::PollEvents: GLFW events, then InputSystem::Update (actions fire their callbacks here). See Input.
  2. Time. Time::Update; the unscaled frame delta, clamped to 0.25 s, is added to the fixed-step accumulator.
  3. Attach. Scene::ProcessAttachQueue: components added since the last frame get OnAttach.
  4. Fixed steps. While the accumulator holds a full fixed step: apply pending physics changes, FixedUpdate, simulate, sync transforms, dispatch collision and trigger events. No steps run while timeScale is 0. See Physics.
  5. Pointer. OnMouse* callbacks on the object under the cursor (PointerDispatcher): a UI element if one is there, otherwise the world. See Input and UI.
  6. Update. Scene::Update, then coroutines (Scene::AdvanceCoroutines), then Scene::LateUpdate. See Coroutines.
  7. Audio. AudioSystem::Update, after LateUpdate so listener and source positions are current. See Audio.
  8. Render. Camera matrices, scene lighting, then each renderable: opaque in hierarchy order, then transparent back to front (render queues), then the UI canvases over the scene (UI pass).
  9. Destroy. Scene::ProcessDestroyed: objects destroyed this frame get OnDisable/OnDestroy and are removed. See GameObjects & components.
  10. Scene change. SceneManager::ProcessAnyPendingSceneChange: if a load was requested, the next scene is built, and only then is the current one torn down. See Scenes.

When the loop ends, for whatever reason, the current scene gets OnApplicationQuit, then Application::Shutdown unloads scenes and shuts down audio, physics and the window, in that order.

Cross-cutting rules

A few rules recur on almost every page:

  • Structural changes are deferred. Destroying an object, switching scenes and quitting take effect at the end of the frame. New components are attached at the start of the next frame.
  • One teardown sequence. Every way a component is destroyed (Destroy, RemoveComponent, scene switch, shutdown) runs OnDisable (if it was enabled in an active hierarchy) and then OnDestroy, exactly once unless a callback throws (the component is marked destroyed only after OnDestroy returns, so a later teardown path runs its callbacks again); a component that removes or destroys itself from those callbacks does not re-enter teardown. The editor's DestroyEntity runs the same sequence. Releasing an object with RemoveRootGameObject, or a scene dropped by SceneManager without being loaded, runs no callbacks. RemoveChild is not a release: inside a scene the child becomes a root and keeps running. See GameObjects & components.
  • Safe modification during iteration. Component updates, event dispatch, input action updates, coroutine updates and physics event dispatch all tolerate handlers that add or remove things while they run. Removals take effect immediately for lookup and are compacted after the loop.
  • Errors are logged, not fatal. Bad scene JSON, corrupt asset metadata, unknown input binding names and throwing scripts or coroutines are reported through the Logger, and the engine keeps running with the previous valid state. The editor server follows the same rule for its clients: a failing command is logged and answered with an Error response instead of terminating the host (see Logging, health & editor).
  • Headless is a first-class mode. The engine runs without a window, renderer or audio device. Tests and the editor host rely on this, and Application::Init reports what is missing in its EngineHealth.

Design decisions

Some behaviour is a deliberate choice rather than an accident of the code. Each decision is explained once, on the page it belongs to:

DecisionIn short
RemoveChild works like UnityRemoving a child inside a scene makes it a root of that scene, the same as SetParent(nullptr); it never leaves a child in a scene but unreachable from its roots. Outside a scene it just detaches.
GetComponent returns the first of a typeThe first component of the exact type added; stable as more are added and across save/load, and an O(1) lookup.
Quit is a requestApplication::Quit() sets a flag; the frame finishes and teardown runs in its usual order.
Two render queues, state per drawOpaque renderables draw in hierarchy order, then Transparent ones by sort key and back to front without writing depth; depth, cull and blend state travel with each draw, because the software renderer reorders draws.
Lua handles are valid until teardownScripts get checked handles that stay valid until teardown (or until freed, for scenes, action maps and actions); using a freed object is a Lua error, never a crash.
The editor server is loopback-onlyThe protocol has no authentication, so it listens on 127.0.0.1 unless --bind says otherwise, and runs every command on the main thread.
Rigidbody mass is authoritativeThe mass you set is the body's mass; inertia and centre of mass come from the collider shapes.
Inactive objects leave physicsA disabled Rigidbody or collider, or an inactive object, is taken out of the simulation and queries; its pairs end with an Exit for the other side, while its own components get OnDisable instead. Re-enabling restores it, with Enter for what still overlaps.
A re-created body's object gets its ExitWhen a body is re-created while touching, both sides get Exit for the old body before Enter for the new one, so Enter/Exit stay balanced.
Layers are Unity's, carried in filter data32 layers at Unity's indices, saved on each GameObject as an index; the collision matrix is copied into each shape's PhysX filter data, and a change re-filters existing pairs so a ruled-out pair still ends with an Exit.
Clicks are Unity's OnMouse* callbacksThe object under the cursor gets OnMouse* before Update, picked by a physics ray from the main camera; the object that got Down captures Drag and Up. Delivery follows the physics rule, and a destroyed or deactivated target is dropped without Exit.
Collision data is from the receiver's sideColliders, normals, impulse and relative velocity are all given from the receiving body's point of view; the two sides see opposite vectors.
Logs are delivered on the logging threadAny thread may log; one recursive lock delivers each message whole and in order, on the thread that logged it.
Polled commands never log per call PR #83Frames, audio and the read-only queries an editor refreshes on a timer (EditorServer::IsPolledCommand) skip the "Command Issued" line; their failures are still logged.
A replaced script instance is retiredSetScript or a reload tears the old instance down like a removed component and attaches the new one, keeping the component's field data and references.
Play restarts, UnPause resumesAudioSource::Play always starts from the beginning; resuming a paused source is UnPause.
UI is GameObjects in a canvas passCanvases, RectTransforms and graphics are components on GameObjects with Unity's anchor model; they draw after the scene in hierarchy and sort order with depth and culling off, and a rect hit test gives UI the pointer before the world through the OnMouse* callbacks.
Fonts are CPU-only assetsA Font holds its face and SDF atlas in memory and never touches a renderer, so it loads headless; renderers make their own textures from it.
One cached mesh per textA TextRenderer lays out and rewrites its mesh (in place, through UpdateMesh) only when a layout input changes; the atlas is one texture per font and renderer, and the colour is a uniform.
World and UI text share one drawing helper PR #53TextRenderer and UIText use the same layout cache, glyph mesh and per-(renderer, font) atlas cache (Rendering::TextDrawing); UI text is sized in canvas pixels per em, wraps at its rect, and is not a raycast target by default.
A button tints its graphic at draw time PR #54Button sets a separate, unsaved tint on its target graphic, multiplied into the graphic's colour when it draws, so the colour itself is never overwritten.
OnClick is an EventHandler fired on OnMouseUpAsButton PR #54The button reuses the dispatcher's callbacks and capture rules and the engine's EventHandler, adding a per-listener exception guard and an event that survives the button being destroyed by a listener.
Button listeners are not serialized PR #54Scenes save a button's colours, multiplier, fade and interactable flag; code or scripts add the OnClick listeners after building or loading the scene.
A button needs a raycast target on its own object PR #54Pointer callbacks go to the hit graphic's object without bubbling, so the button sits on its Image's object and its label is not a raycast target.
Asset import is its own CPU-only library PR #64Image decoding (and later model parsing) lives in assetimport/, which depends only on math and exposes no third-party types, so every parser is tested without the engine or a GPU.
Textures are stored bottom row first PR #64v = 0 is the first row of pixel data and imported images are flipped on load (flipY), so images show upright on the existing v-up primitives and UI quad; importers of v-down formats flip v instead.
One GPU cache for shared resources PR #64GpuCache holds one GPU resource per (renderer, asset), refcounted and guarded by the renderer's lifetime token; text atlases, UI sprites, meshes and materials use it.
Images are size-capped before decoding PR #64Only PNG, JPEG, TGA and BMP decode; an image over 16384 pixels a side or 256 MiB decoded is rejected from its header, and bad data is an error, never a crash.
sRGB is recorded, not applied PR #64A texture's srgb setting is read and kept but changes nothing until the engine gets a linear-lighting option, because switching to sRGB textures changes every colour on screen.
One MeshRenderer, no MeshFilter PR #65MeshRenderer holds the mesh and one material per submesh itself; nothing needs a separate filter component yet.
Submeshes are index ranges PR #65A mesh is one vertex and index buffer; each submesh is drawn with DrawMesh(..., IndexRange), whose default body never draws the whole mesh for a part.
A renderable can draw in both queues PR #65IRenderable::DrawsInQueue lets a mesh with opaque and blended parts draw each in its own pass; RenderInQueue is told the queue.
Blending follows the alpha mode PR #65The Opaque queue no longer blends; only Blend materials, in the Transparent queue, do. Mask materials cut out with an alpha test.
Built-in shapes are shared meshes PR #65Cube, Sphere and Quad are built-in Mesh assets with fixed UUIDs, one GPU mesh per renderer; the shape components draw them unchanged.
The standard shaders read vertex colour PR #65Unlit and lit multiply by the vertex colour on both backends; existing meshes are white per vertex, so nothing changes.
Sub-asset UUIDs come from their own namespace, keyed by name PR #68A model's meshes, materials and textures get ResourceUUID::FromSubAsset(model, key), so scenes reference them like files; keys use names when every name of a kind is unique, and indices for the whole kind otherwise.
The sub-asset index is written on load, never by the scan PR #68ResourceLoader records a model's sub-assets in its .meta when it loads; the scan only reads indexes back, so the core never parses models.
Unsupported glTF features warn once PR #68Cameras, lights, skins, morphs, animations, extra UV sets and unknown extensions are ignored with one warning each; Draco and meshopt compression are errors.
Software text is alpha-tested and writes depthThe software renderer can't blend, so its SDF text shader keeps or rejects each pixel at the 0.5 edge and writes depth where it draws, even in the Transparent queue; text keeps its submitted position in the draw order.
A headless software renderer for pixel testsSoftwareRenderer::Initialize(nullptr, w, h) skips only the GL parts (loading GL, the blit), so tests render real frames through the same render thread and shaders on a GPU-less CI runner.
Golden images compare structurePixel tests assert counts, bounding boxes, flat colours and separated shapes within tolerances, never exact images or hashes, because Debug and Release round floats differently.
No audio clips without a contextClips are OpenAL buffers, so they fail to load (with a warning) while the AudioSystem is not initialized, and a clip from an earlier context is never treated as loaded.
A dropped scene undoes only what attachedA scene destroyed without being loaded tears down the components that attached to it, and gives no callbacks to those that never did.
A prefab instance is a new object treeInstantiating resolves references inside the prefab to the new objects, then gives every object and component a fresh UUID; references leaving the prefab become null.
SIMD tiers are an algorithm choiceThe build already requires AVX; tiers select which implementation runs so each can be tested against scalar, under a written per-operation contract.

Extending these docs

The site is plain HTML and CSS: no build step, no JavaScript, no external fonts or scripts. It works when opened from the filesystem and on GitHub Pages. docs/README.md explains the conventions in full. In short:

  • Start a new page from docs/_template.html. It contains the sidebar, the callout markup and the footer.
  • Add the page to the sidebar of every page, since there is no JavaScript to generate it, and mark the current page with aria-current="page".
  • Describe behaviour, not just signatures, and cite the source file, the function and any test that pins the behaviour down.
  • Use the callouts as defined above. When something is unclear, write an Open question rather than guessing.
  • When a PR changes behaviour, update the affected page in the same PR.
