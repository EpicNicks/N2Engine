N2Engine behaviour reference

N2Engine is a C++23 game engine with a GameObject/Component model, PhysX physics, OpenAL audio, an action-based input system, Lua scripting and a headless editor host. These pages describe how the engine behaves: what is guaranteed, in which order things happen, how long objects live, and what counts as an error.

How to read a page

Each page starts with a short summary and an "On this page" list, then goes through behavioural contracts one topic at a time. Four kinds of callout are used consistently:

Guarantee

Something the engine enforces, usually pinned by a named test. Code may rely on it.

Note

Rationale, context, or a consequence that is easy to miss.

Warning

A footgun: behaviour that is intended but surprising, or a pattern that is not supported.

Open question

Behaviour that is unclear, undecided, or inconsistent in the code. These are candidates for issues.

Source citations look like this:

Source: engine/src/Application.cpp — Application::Run; tests: CoreRobustnessTests

Paths are relative to the repository root. Line numbers are left out on purpose, because they drift; search for the function name.

Modules

The CMake project (CMakeLists.txt) builds these targets:

DirectoryWhat it is
math/Vectors, matrices, quaternions, UUIDs, random numbers, with SIMD dispatch. No engine dependencies. See Math & SIMD.
renderer/Rendering backends behind Renderer::Common::Renderer: OpenGL (default), Vulkan and a software renderer.
engine/The engine proper: application loop, GameObjects, scenes, physics, audio, input, resources, serialization, coroutines and Lua scripting.
editor-server/N2EditorHost, a headless engine host that editors talk to over TCP. See Logging, health & editor.
test_project/, lua_project/Example games, in C++ and in Lua.
tests/GoogleTest suites per module (built when N2ENGINE_BUILD_TESTS=ON). See Testing & CI.

Two build options change behaviour: N2ENGINE_USE_PHYSX (default ON; when OFF the engine has no physics backend and reports physics as Disabled) and N2ENGINE_BUILD_TESTS. The math target requires AVX (/arch:AVX, a PUBLIC flag on the math target).

Architecture map

Application

Singleton. Initializes subsystems, reports their health, runs the frame loop, owns the window, camera and physics backend.

SceneManager & Scene

SceneManager stores scene snapshots by name and switches scenes at the end of a frame. A Scene owns its root GameObjects and drives their updates.

GameObject & Component

Hierarchy of objects; components get lifecycle callbacks (attach, enable, update, disable, destroy).

Transforms

Positionable: local and world position, rotation, scale; tells physics when it moves.

Coroutines

Per-scene scheduler for std::generator-based coroutines with Unity-style waits.

Physics

IPhysicsBackend with a PhysX implementation; Rigidbody and collider components; collision and trigger events; raycasts.

Input

Action maps with typed actions and bindings; owned by the window, updated as events are polled.

Audio

OpenAL-based AudioSystem: sources, one-shots, mixer groups and a listener.

Resources

res:// and user:// paths, the project asset scan with stable meta UUIDs, and one lookup API.

Serialization

Scenes and components to and from JSON, including references between objects and to assets.

Lua scripting

LuaComponent runs scripts with lifecycle callbacks, serializable fields and checked handles.

Logging, health, editor

Logger with backlog and subscribers; EngineHealth; the TCP editor host.

Who owns what

Most lifetime rules in the engine follow from this ownership graph:

  • Application (function-local singleton) owns the Window (which owns the InputSystem and the renderer), the main Camera, and the 3D physics backend.
  • SceneManager (singleton) owns the stored scene snapshots (StoredScene{name, data} JSON) PR #28, the loaded Scene, and a pending scene, each behind std::unique_ptr.
  • Scene owns its root GameObjects (std::shared_ptr<GameObject>) and its coroutine scheduler. It also keeps non-owning lists of components and lights for iteration, which every removal path updates through Scene::DetachComponent. Scenes cannot be moved, because objects point back at them.
  • GameObject owns its children (shared_ptr) and its components (std::unique_ptr<Component>). Anything else that refers to a component, including Lua, holds a raw pointer or a checked handle.
  • Subsystem singletons (AudioSystem, LuaRuntime, Logger) are process-wide. AudioSystem is deliberately never destroyed, so components can unregister from it during static destruction.

Note

A GameObject can outlive its scene, for example when C++ code or a Lua handle still holds the shared_ptr. When a scene is destroyed it clears the scene pointer of the objects it can still find, so they are inert rather than dangling. Objects detached with RemoveChild can be missed; see the open question under Purge and ~GameObject.

How a frame runs

Application::Run repeats the following until the window closes or Application::Quit() has been requested. The full contract, including edge cases, is on the Application page.

  1. Input. Window::PollEvents: GLFW events, then InputSystem::Update (actions fire their callbacks here). See Input.
  2. Time. Time::Update; the unscaled frame delta, clamped to 0.25 s, is added to the fixed-step accumulator.
  3. Attach. Scene::ProcessAttachQueue: components added since the last frame get OnAttach.
  4. Fixed steps. While the accumulator holds a full fixed step: apply pending physics changes, FixedUpdate, simulate, sync transforms, dispatch collision and trigger events. No steps run while timeScale is 0. See Physics.
  5. Update. Scene::Update, then coroutines (Scene::AdvanceCoroutines), then Scene::LateUpdate. See Coroutines.
  6. Audio. AudioSystem::Update, after LateUpdate so listener and source positions are current. See Audio.
  7. Render. Camera matrices, scene lighting, then each renderable.
  8. Destroy. Scene::ProcessDestroyed: objects destroyed this frame get OnDisable/OnDestroy and are removed. See GameObjects & components.
  9. Scene change. SceneManager::ProcessAnyPendingSceneChange: if a load was requested, the next scene is built, and only then is the current one torn down. See Scenes.

When the loop ends, for whatever reason, the current scene gets OnApplicationQuit, then Application::Shutdown unloads scenes and shuts down audio, physics and the window, in that order.

Cross-cutting rules

A few rules recur on almost every page:

  • Structural changes are deferred. Destroying an object, switching scenes and quitting take effect at the end of the frame. New components are attached at the start of the next frame.
  • One teardown sequence. Every way a component is destroyed (Destroy, RemoveComponent, scene switch, shutdown) runs OnDisable (if it was enabled in an active hierarchy) and then OnDestroy, once, unless a callback re-enters teardown (the destroyed flag is set only after OnDestroy returns). Detaching and releasing an object (RemoveChild, RemoveRootGameObject, the editor's DestroyEntity), or a scene dropped by SceneManager without being loaded, runs no callbacks. See GameObjects & components.
  • Safe modification during iteration. Component updates, event dispatch, input action updates, coroutine updates and physics event dispatch all tolerate handlers that add or remove things while they run. Removals take effect immediately for lookup and are compacted after the loop.
  • Errors are logged, not fatal. Bad scene JSON, corrupt asset metadata, unknown input binding names and throwing scripts or coroutines are reported through the Logger, and the engine keeps running with the previous valid state. The exception is the editor server, where an exception in a command handler terminates the host (see Logging, health & editor).
  • Headless is a first-class mode. The engine runs without a window, renderer or audio device. Tests and the editor host rely on this, and Application::Init reports what is missing in its EngineHealth.

Extending these docs

The site is plain HTML and CSS: no build step, no JavaScript, no external fonts or scripts. It works when opened from the filesystem and on GitHub Pages. docs/README.md explains the conventions in full. In short:

  • Start a new page from docs/_template.html. It contains the sidebar, the callout markup and the footer.
  • Add the page to the sidebar of every page, since there is no JavaScript to generate it, and mark the current page with aria-current="page".
  • Describe behaviour, not just signatures, and cite the source file, the function and any test that pins the behaviour down.
  • Use the callouts as defined above. When something is unclear, write an Open question rather than guessing.
  • When a PR changes behaviour, update the affected page in the same PR.
