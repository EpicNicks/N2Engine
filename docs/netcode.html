Netcode: the n2net library

n2net is the netcode's lowest layer: a transport interface, an in-memory network simulator, and a packet layer on top of datagrams (acknowledgements, a reliable-ordered channel, an unreliable-sequenced channel, fragmentation of large reliable messages). This page describes what exists in master now. Its one real network transport is UdpTransport (native UDP sockets, Windows and Linux), and SecureTransport puts a connection handshake, join tokens and authenticated encryption of every packet over it (The secure layer), and N2Server runs that stack in a headless process of its own PR #216 (The dedicated server); above them is the network world PR #224 (The network world): NetworkObject, net ids, prefab spawns and despawns replicated to clients, and the join check of the scene and build. Above that is field replication PR #226 (Field replication): the server sends the fields a component marks replicated to every client, as the difference to what that client acknowledged, and NetworkTransform replicates an object's transform. RPCs PR #241 (RPCs) let a component call across the connection with per-client budgets. Prediction of the character controller B6 (Client prediction) is there; the rest of prediction is not (see What is not there yet).

What exists and where it lives PR #197

The library is the CMake target n2net (alias N2Engine::n2net), a static library defined in engine/CMakeLists.txt. Its headers are under engine/include/engine/network/n2net/ and its sources under engine/src/network/n2net/. The engine target excludes that source directory from its glob and links n2net publicly PR #224 (the network world layer runs its Connections; below). Apart from UdpTransport, SecureTransport and the join tokens (which use n2security, below) it uses the standard library only: no sockets, no threads, no platform headers, no engine types, no global state, no exceptions across its API (errors are return codes), and it reads no clock (every time is passed in as microseconds). UdpTransport is the one exception: it includes the BSD socket or Winsock headers (ws2_32 is linked on Windows), still starts no thread, and reads the steady clock only to age out idle peers. Its whole class is compiled out under Emscripten (N2NET_HAS_UDP is 0), so the library, apart from that class, still builds the same on Windows, Linux x86_64 and arm64, and in the single-threaded web build.

The caller moves bytes: a datagram from ITransport::Poll goes into Connection::OnPacket, and each datagram Connection::Update produces goes to ITransport::Send (the example in Using it in a test does exactly that). Everything is single-threaded and polled.

Design decision: our own small reliability layer, not a networking dependency PR #197

The netcode design (decision N2) chose to write the packet layer here rather than adopt ENet, GameNetworkingSockets or yojimbo. The browser transports, the security model and the simulator all have to be ours anyway, and the reliability layer is the small part. No new third-party dependency is added by this library.

The packet format PR #197

One datagram is a 17-byte header followed by blocks, at most 1200 bytes in all. All integers are little-endian, read and written byte by byte, so the format does not depend on the host's endianness or alignment.

Header (17 bytes)

OffsetSizeFieldMeaning
0u32protocol idWhat the receiver expects (a protocol version and game build identifier chosen by the caller); any other value drops the packet.
4u32connection idThe receiver's connection; any other value drops the packet. Configured, the same on both sides (a later handshake will agree it).
8u16sequenceThis packet's number: +1 per packet sent, wrapping at 65536. The first one is ConnectionConfig::initialSequence.
10u16ackThe newest packet number received from the other side. Valid only if flags bit 0 is set (written as 0 otherwise).
12u32ack bitsBit i set: packet ack - 1 - i (modulo 65536) was received too. Written as 0 when there is no ack.
16u8flagsBit 0: ack and ack bits are valid. Bits 1 to 7 are reserved and must be zero.

After the header come blocks, back to back to the end of the datagram. A datagram may have none (an ack-only or keep-alive packet).

Guarantee: a malformed packet changes nothing

A datagram is parsed completely before anything in it is applied. An unknown block type, a length of 0, a length past the end of the datagram or past the block's cap, a reserved bit set (in the header flags or the unit flags), a truncated header or block, or bytes left over after the last block makes the whole packet malformed: it is dropped without effect (no acknowledgement, no delivery, no state change other than the rejection counters). The connection: acknowledgements and channels PR #197

A Connection is one end of a connection. It is built from a ConnectionConfig and the current time, and has four calls: SendReliable and SendUnreliable queue a message (copied); OnPacket(now, datagram, handler) processes one received datagram and delivers any messages it completes to the handler (which may send, but not call OnPacket or Update); Update(now, sender) resends what is due, sends what the window allows, acknowledges, sends keep-alives, and calls sender once per packet (the span is valid only during the call). Update produces at most maxPacketsPerUpdate (default 64) packets per call. The configuration is sanitised on construction: sizes, windows and times are clamped into safe ranges whatever the caller passed.

Packet numbers and acknowledgements

Every packet carries a 16-bit sequence number. Ordering uses wraparound arithmetic: a is more recent than b when it is 1 to 32767 steps ahead modulo 65536; a difference of exactly 32768 counts as neither. The receiver remembers the last 256 packet numbers in a ring and answers every packet with the newest number it has seen (ack) and a 32-bit mask of the 32 numbers before it (ack bits), Gaffer-on-Games style.

  • A packet number already seen is dropped as a duplicate (DuplicatePacket); one 256 or more behind the newest is dropped as TooOld. A jump forward of 256 or more clears the ring, so stale entries cannot be mistaken for new packets.
  • A packet that carries blocks makes the receiver send an acknowledgement on its next Update; a duplicate of such a packet does too (the peer is resending, so the ack was probably lost). Packets with no blocks (keep-alives, ack-only packets) are not themselves acknowledged and are not counted in the loss figures.
  • A packet is declared lost when its deadline passes (the RTO, below), when it is three or more sequences behind the newest acknowledged one (a single ack of a later packet suffices), or when its slot in the sender's 128-entry ring is needed again. A packet declared lost and acknowledged later is reclassified (counted in packetsAckedLate), and any pending resend of its units is cancelled.
  • Because the ack bits reach back only 32 packets, a sender never leaves more than 32 data packets unanswered: while the oldest unanswered packet is 32 or more behind, packets go out with no blocks. That is at most 32 data packets per round trip.

The RTT estimate follows RFC 6298 in integer microseconds: smoothed RTT and variance, RTO = smoothed + max(1 ms, 4 × variance), clamped to [minRtoMicros, maxRtoMicros] (defaults 50 ms and 2 s); before the first sample the RTO is initialRtoMicros (200 ms). A sample is taken from the packet named by each received ack field, never from the ack bits. A resend's deadline backs off by doubling per retry up to 16 times the RTO, capped at the maximum RTO.

The reliable-ordered channel

Reliable messages are cut into units (see Fragmentation). The units form one numbered stream (16-bit unit ids, starting at initialUnitId, which must be the same on both sides). Each unit is resent until acknowledged and delivered in order, so a message reaches the handler whole, exactly once, in the order it was sent, whatever the link does short of ending the connection.

  • Resends happen when the packet that carried a unit is declared lost; they go out oldest first, before new units, at the next Update.
  • Window. At most reliableWindow units are in flight (sender) and the receiver buffers units only up to that many ahead of the next one it expects; a unit further ahead is dropped (unitsOutOfWindow). With equal windows on both sides an honest peer never sends one; the window is not negotiated yet, so both peers must be configured with the same reliableWindow, because the packet carrying a dropped unit is still acknowledged and the unit is not resent. The configured window is clamped to 1 to 1024 and rounded down to a power of two (default 256), so unit ids map to slots without collisions across the 65536 wrap.
  • Queue. SendReliable fails with QueueFull when the bytes queued and not yet packetised would pass maxSendQueueBytes (default 256 KiB); the caller retries later. Other results: Empty, TooLarge (over maxMessageSize), ConnectionFailed.
  • Congestion. There is no congestion control. The unit window and the 32-packets-per-round-trip rule are the only things that slow a sender.

Guarantee: exactly once, in order

Over a link that loses 30% of datagrams and also reorders and duplicates them, every reliable message queued is delivered exactly once and in the order it was sent, and the connection ends idle. Tests: ReliableUnderThirtyPercentLossWithReorderingAndDuplication, TenThousandMessagesEachWayOverALossyLink, AWindowOfOneStillDeliversUnderLoss.

Fragmentation and its limits

A reliable message larger than one unit is cut into units of up to 1177 bytes (with a smaller ConnectionConfig::maxPacketSize PR #210, up to that size less 23: 1152 over SecureTransport, whose packets have 25 bytes of their own; an unreliable message may then be up to that size less 22, MaxUnreliableMessageSize(), and the setting is clamped to 128 - 1200 bytes); the first carries the "first" flag, the last the "last" flag, and a message that fits in one unit has both (the smallest message, 1 byte, is a 24-byte packet: 17 + 6 + 1). Units are numbered in sequence, so the receiver reassembles by delivering them in order; units that arrive out of order wait in the window until the gap fills. Every limit below is enforced, and a configuration that asks for more is clamped.

The unreliable-sequenced channel

SendUnreliable queues a message of 1 to 1178 bytes (never fragmented). Each one is sent once, in a later Update, with a 16-bit message sequence number that increments per message and is never resent. The receiver delivers a message only if its sequence is more recent (wraparound rules, as above) than the newest it has delivered; an older or equal one is dropped and counted in unreliableStale. So the stream the handler sees only ever moves forward: newest wins, stale is dropped, and a lost message is simply never delivered.

The send queue holds at most maxQueuedUnreliableMessages (default 64) messages and maxQueuedUnreliableBytes (default 64 KiB); beyond either the oldest queued message is dropped (unreliableDropped). Unreliable messages share packets with reliable units, after them, only if they fit.

Stream transports

With ConnectionConfig::reliableStream set (what ITransport::IsReliableStream() reports), the connection never resends and keeps no copy of sent units, and has no unit window. Packet numbers and acks are still sent and received (for RTT and ordering checks); a packet unanswered past its deadline is not counted as lost. Units must arrive exactly in order: any other unit id ends the connection with ProtocolViolation.

Failure, timeouts and statistics

A connection can fail, and then stays failed: IsFailed() and Failure() report why, every buffer it held is released, Update produces nothing, sends return ConnectionFailed and OnPacket returns ConnectionFailed. There is no recovery; the owner ends it and starts a new connection.

FailureReasonWhen
TimeoutNothing was received for idleTimeoutMicros (default 10 s), checked in Update.
ReassemblyStallPartly received reliable data made no progress for reassemblyTimeoutMicros (default 5 s).
MessageTooLargeA received message grew past maxMessageSize.
ProtocolViolationThe peer sent reliable units that cannot be a legal stream.

To keep the link alive, Update sends an empty packet when nothing else was sent for keepAliveMicros (default 1 s), and an acknowledgement-only packet when blocks were received. OnPacket returns a PacketStatus naming what it did with the datagram: Ok, TooLarge, BadHeader, WrongProtocol, WrongConnection, Malformed, DuplicatePacket, TooOld or ConnectionFailed; only Ok means it was processed.

Connection::Stats() counts, among others: packets and bytes sent and received; packets rejected, malformed, duplicate; packets acked, acked late and lost; units sent and resent; reliable and unreliable messages delivered; stale and dropped unreliable messages; duplicate and out-of-window units. Rtt() gives the smoothed, latest, minimum and variance of the round trip and the current RTO. LossRatePpm() is packets lost over packets settled (acked or lost), in parts per million. ReliableBacklogBytes() and ReliableIdle() report what reliable data is still unacknowledged.

Untrusted input and bounded memory PR #197

This layer will face the internet, so every byte that arrives is treated as hostile.

  • Every length is checked before data is taken. ByteReader never reads past the end whatever lengths the bytes claim: a failed read returns 0 or an empty view and sets a flag. ByteWriter never writes past its buffer. A block's length is checked against the bytes that remain and against its cap before the data is viewed.
  • Validate, then apply. OnPacket checks size (at most 1200), header, protocol id, connection id and the whole block structure before it touches any state. A packet has at most 197 blocks (the smallest, an unreliable message of one byte, takes 6 bytes of the 1183 after the header), so the work per datagram is bounded.
  • No unbounded allocation. What a peer can make a connection hold is bounded by the configuration, not by what the peer sends: the receive window (units), the message size cap, the send queue, and the unreliable queue. MemoryInUseBytes() reports the payload buffers held now and MemoryBoundBytes() what that can never exceed under the configuration (1,664,000 bytes with the defaults); the tests assert the first never passes the second, including while a peer floods maximum-size units at every unit id.
  • No loops driven by input. There are no length-prefixed repeat counts: loops run over the bytes of one datagram, over fixed-size rings (32 ack bits, 128 sent packets, 256 received numbers), or over the window.
  • Time arithmetic cannot wrap. Configured times are clamped to about 12 days and RTT samples to the same order, so no deadline or backoff shift overflows.
  • Errors are values. Nothing throws on bad input. A bad datagram is a PacketStatus; a peer that breaks the stream rules ends its connection with a FailureReason.

The ids are not secrets: authentication is the secure layer's job

The protocol id and connection id only filter out stray traffic; they are not keys. Over a plain transport, anyone who can send datagrams to a connection and knows or guesses the two ids and a plausible sequence number can inject packets. Over SecureTransport PR #210 every datagram the Connection sees has passed an authentication tag (The secure layer); over a plain one this layer is for tests and loopback development, not for an exposed port. The handshake does not agree the connection id yet: both sides still configure it.

The network simulator PR #197

SimNetwork is a deterministic in-memory network for tests; it is what every later netcode test runs on. It creates endpoints (SimTransport, an ITransport) with ids 1, 2, 3 in creation order; Link(a, b, config) connects two of them (each side then gets a PeerConnected event) with a separate SimLinkConfig per direction if wanted. Time is the network's virtual clock: NowMicros() starts at 0 and only Advance(micros) moves it. A datagram is scheduled when sent and handed out by SimTransport::Poll once the clock has reached its delivery time; Poll never moves time. Nothing sleeps and nothing reads a wall clock.

What a link can do

All times are virtual microseconds and all probabilities are parts per million (1,000,000 = always), so the simulation is integer-only. The default SimLinkConfig is a perfect link.

FieldEffect
latencyMicros, jitterMicrosFixed one-way delay, plus a uniform extra delay in [0, jitter].
lossPpmIndependent loss.
burstEnterPpm, burstExitPpm, burstLossPpmBurst loss, a two-state model: in the good state a datagram moves the link to the burst state with probability burstEnterPpm; in the burst state it moves back with probability burstExitPpm, and a datagram is lost with probability burstLossPpm (default 100%) instead of lossPpm. burstEnterPpm 0 never bursts.
reorderPpm, reorderDelayMicrosWith probability reorderPpm a datagram is delayed by a further 1 to reorderDelayMicros, so later datagrams overtake it. A reorderDelayMicros of 0 never reorders this way (jitter can still reorder).
duplicatePpmWith this probability a second copy is delivered, with its own jitter.
bandwidthBytesPerSecond0 is unlimited. Otherwise datagrams are serialised at this rate: each waits for the ones before it and takes bytes × 106 / rate microseconds (rounded up).
queueLimitBytesWith a bandwidth cap: a datagram that would find more than this many bytes already waiting is dropped (tail drop). 0 is unlimited.

SetLinkConfig changes one direction's config while it runs (its burst state and random stream continue); Unlink removes a link without telling the other side (datagrams in flight on it are dropped when due, even if the pair is linked again before then), whereas SimTransport::Disconnect removes it and gives the other side a PeerDisconnected; GetLinkStats(from, to) returns per-direction counters (submitted, dropped by loss, by queue limit, or because the link was removed, duplicated, reordered, delivered).

Determinism

Guarantee: the same seed and the same calls give the same bytes on every platform

The simulator's random numbers come from SimRandom, xoshiro256** seeded through SplitMix64, written out in the library with integer arithmetic only (not std::random_device or the standard distributions, whose output differs between standard libraries). Each link direction has its own stream derived from the seed and the two endpoint ids, so adding a link does not change what another link does. Every datagram consumes the same seven random draws in the same order whatever the configuration and whatever its fate, so changing one impairment does not change what another decides for the same datagram. Delivery order is fully determined: events are keyed by delivery time and then by the order the datagrams were sent. Tests: SameSeedSameBytesDifferentSeedDifferent, AnotherLinkDoesNotDisturbThisOne, AnImpairmentDoesNotShiftAnothersDecisions, StreamIsFixedAcrossPlatforms, and the two golden traces under Tests.

Using it in a test

Create a network with a seed, add endpoints, link them, and give each side a Connection. Each step: advance the clock, poll each endpoint into its connection, then update each connection into its endpoint. This is a complete, compiling example:

SimNetwork network(1234);
SimTransport &a = network.AddEndpoint();
SimTransport &b = network.AddEndpoint();

SimLinkConfig link;
link.latencyMicros = 40'000;
link.jitterMicros = 10'000;
link.lossPpm = 300'000; // 30%
link.duplicatePpm = 50'000;
network.Link(a.Id(), b.Id(), link);

ConnectionConfig config;
config.protocolId = 0x4E32'4E54;
config.connectionId = 7;
Connection connA(config, network.NowMicros());
Connection connB(config, network.NowMicros());

const std::vector<std::uint8_t> hello = {'h', 'i'};
connA.SendReliable(hello);

const auto onMessage = [&](MessageChannel, std::span<const std::uint8_t> message) { /* use it now: copy what you keep */ };
for (int step = 0; step < 2000; ++step)
{
    network.Advance(1'000); // the only thing that moves time
    const std::uint64_t now = network.NowMicros();

    });

}

Design decision: the simulator is integer-only with its own random number generator PR #197

The simulator is the CI proof for all later netcode, and the same trace has to come out on Windows, Linux, arm64 and wasm. The native UDP transport PR #203

UdpTransport is the ITransport for real networks on Windows (Winsock) and Linux (BSD sockets): one non-blocking UDP socket, polled on the calling thread, no thread of its own, no blocking call anywhere. It carries datagrams exactly as given (no framing of its own) up to MaxPacketSize(), 1200 bytes, and IsReliableStream() is false. It is not built for the web: there is no UdpTransport class when __EMSCRIPTEN__ is defined (N2NET_HAS_UDP is 0), and UdpTransport.cpp then compiles to nothing. A UdpTransport is made with UdpTransport::Open(options, encryptionAvailable), which returns a UdpOpenResult (a transport, or an UdpError with the system error code and a one-line message); it never throws.

Binding, and the fail-closed rule

options.bindAddress is a numeric IPv4 or IPv6 address (default 127.0.0.1) and options.port a port (0 picks a free one; read it back with LocalPort()). A host name, an empty string, a zone (fe80::1%eth0) and anything else inet_pton does not accept is InvalidAddress: a name could resolve to anything, so a loopback check on it would mean nothing. An IPv6 bind address makes an IPv6 socket; bound to the wildcard :: with options.dualStack (default true), the socket also reaches IPv4 peers, shown as IPv4 addresses, if the system accepts turning IPV6_V6ONLY off. DualStack() reports what happened, and is false for any other IPv6 bind address: a socket bound to one address such as ::1 can never exchange IPv4 traffic, so Connect to an IPv4 address on it returns FamilyMismatch (with a message naming the bound address) instead of making a peer every Send to which is silently lost PR #207. dualStack = false sets IPV6_V6ONLY. An IPv4 address makes an IPv4 socket.

Fail closed: a non-loopback bind needs encryption or an explicit override PR #203

Open refuses (NonLoopbackRefused, before any socket is created) every address that is not loopback unless the caller passes encryptionAvailable = true or sets options.insecureBind. Loopback means an IPv4 address in 127.0.0.0/8, ::1, or an IPv4-mapped 127/8 address (IsLoopbackAddressText is the same test); 0.0.0.0 and :: (all interfaces) are not loopback, and neither is any text that is not an exact numeric address. insecureBind is the transport-level form of the editor host's --insecure-bind: when it actually overrides the rule, the transport reports InsecureOverrideUsed() and sends one warning line (about the address, port and the missing encryption) to options.warningSink, or to stderr when none is set; a loopback bind with the flag set is quiet. Connect to a non-loopback address is held to the same rule.

Since PR #210 the only caller that passes encryptionAvailable = true is SecureTransport::OpenUdp, which puts the handshake and the sealed packets over every datagram the transport carries (Over UDP). So a game listens on, or talks to, a non-loopback address only through the secure layer, or by opting in loudly with insecureBind.

Peers, caps and unknown sources

A peer is a remote address and port, and its PeerId is a counter (from 1; 0 and ids still in use are skipped if it ever wraps). A peer comes from Connect(address, port) (numeric addresses only; PeerConnected is delivered by the next Poll, and nothing is sent) or, when options.acceptUnknownPeers is true (the default, for a server), from the first datagram of an unknown source (PeerConnected, then the Datagram). A client sets it false: everything not from a connected peer is dropped and counted. Sources that are not usable endpoints (port 0; IPv4 0.0.0.0/8 and 224.0.0.0 upward, which covers multicast, reserved and broadcast; IPv6 :: and ff00::/8; the same ranges inside an IPv4-mapped address) are dropped before they can make a peer, and Connect refuses them as InvalidAddress.

  • The peer table is bounded. maxPeers (default 256, clamped to 1 to 4096) counts peers from Connect and from unknown sources together; a new source beyond it is dropped (droppedPeerLimit), and peers already in keep working. A peer from which nothing is received for peerIdleTimeoutMs (default 30,000; 0 never) is removed and reported as PeerDisconnected, so spoofed sources cannot fill the table forever. The check runs after Poll has read the socket (see below). PR #207 Per-peer state is a fixed-size record: the address, the last-receive time and the counters of UdpPeerInfo.
  • The transport never speaks first. It sends only what Send is given, only to a known peer. An unknown or spoofed source cannot make it transmit anything, so there is no amplification at this layer. A peer made by an unknown source's first datagram is not vetted: GetPeerInfo returns its address and byte and datagram counters, so a layer above can check what it sends to an unauthenticated address against what it received (the secure layer's handshake keeps every such reply no larger than its request by construction, The handshake).
  • Peers are attributed by source address and port only. A datagram that merely claims to belong to a connection is another peer if it comes from another source. Nothing here proves a source address is genuine (UDP source addresses can be forged); that is what the handshake is for.
  • Disconnect is local. It forgets the peer and sends no packet, so the other side finds out through its own idle timeout (or the Connection's). Unlike SimTransport, whose Disconnect gives the other side PeerDisconnected, nothing tells it. A later datagram from the same address makes a new peer with a new PeerId. Called from inside the Poll handler, which the interface forbids, Disconnect does nothing and Connect returns Busy.

Datagrams, errors and platform notes

  • Socket errors are data, never exceptions. Stats() counts what was dropped and why (droppedEmpty, droppedOversize, droppedBadSource, droppedUnknownSource, droppedPeerLimit), the ignored resets, receiveErrors, sendWouldBlock, sendErrors, and keeps the system error code of the last real failure in lastErrorCode. A zero-length datagram, or one longer than 1200 bytes, is dropped and counted: the transport reads into a buffer one byte over the maximum to tell a 1200-byte datagram from a longer one (Windows reports a longer one as WSAEMSGSIZE, also counted as oversize).
  • Send never blocks and reports like a datagram network. After the checks (unknown peer, empty, over 1200 bytes) it returns Sent even when the system could not take the datagram: a full send buffer (sendWouldBlock) or another error (sendErrors) means a lost datagram, which the reliable channel exists to repair. EINTR is retried a bounded number of times.
  • Poll is bounded. It delivers the peers Connect made, then reads at most maxDatagramsPerPoll (default 1024) datagrams, stopping at EWOULDBLOCK, then the idle expiries PR #207; the rest wait in the socket (receiveBufferBytes, default 1 MiB, and sendBufferBytes, default 256 KiB, are requested and the system may grant less). A flood therefore cannot keep a caller inside Poll.
  • Windows: connection resets are ignored. By default a Windows UDP socket that sent to a closed port gets an ICMP port unreachable that makes a later recvfrom fail with WSAECONNRESET, which would hide the datagrams behind it. Open turns off SIO_UDP_CONNRESET and SIO_UDP_NETRESET, and Poll and Send also skip reset-type errors (connectionResetsIgnored; on Linux ECONNREFUSED and similar are treated the same). Winsock is started per transport (WSAStartup, reference counted) and released with it.
  • The port cannot be shared or taken. SO_REUSEADDR is never set, and Windows sets SO_EXCLUSIVEADDRUSE, so a second Open on a port in use fails with BindFailed; after the first transport is destroyed the port can be bound again at once (UDP has no TIME_WAIT).

Design decision: drain the socket, then sweep idle peers PR #207

A caller can stall between two Polls (a long frame, a breakpoint, a suspended process) for longer than peerIdleTimeoutMs while its peers keep sending. Sweeping first would drop every one of them although their datagrams sit in the receive buffer, and the next datagram would then make a new peer with a new PeerId (or, on a client that accepts no unknown sources, be dropped). So Poll reads first and sweeps after, judging idleness against the time the Poll began: a peer heard from during this read has a last-receive time at or after that and is kept, a peer that sent nothing is still removed in the same Poll. The read stays bounded by maxDatagramsPerPoll, so a peer whose datagram is queued behind that many others can still expire; the bound is what keeps a flood from holding the caller in Poll.

Limits

  • IPv4 and IPv6 sockets only; no multicast, no host-name resolution, no IPv6 zones. A datagram over 1200 bytes is dropped, never reassembled by this layer.
  • One socket, used from one thread. There is no I/O thread, no send queue (a datagram goes straight to sendto) and no pacing.
  • A flood of spoofed sources can fill the peer table (maxPeers) until they idle out, and then new genuine sources are dropped. The secure layer's per-address and global limits bound the work and the state such sources cause above this transport, not this table.
  • Dual stack needs a :: bind and depends on the system: on any other IPv6 bind address, or where it cannot be enabled, DualStack() is false and an IPv4 Connect on that socket returns FamilyMismatch. That includes an IPv4-mapped bind address such as ::ffff:127.0.0.1; bind 127.0.0.1 for IPv4.
  • Nothing is encrypted or authenticated by this class itself (that is SecureTransport, see the fail-closed rule above); a NAT, a firewall or a path that drops UDP is not handled.

The secure layer: handshake, sealed packets, join tokens PR #210

SecureTransport is an ITransport that runs over another ITransport (a UdpTransport, or a SimTransport in the tests) and adds the connection handshake and per-packet authenticated encryption. The layers above it (a Connection and its channels) see only authenticated peers: PeerConnected only after a handshake has completed, Datagram only for packets whose tag verified, PeerDisconnected when a session ends. Its MaxPacketSize() is the inner transport's less 25 bytes (1175 over UDP); pass it to ConnectionConfig::maxPacketSize so the packet layer builds packets that still fit once sealed. It is native only: the class exists when n2security has its crypto library (N2NET_HAS_SECURE is 1), which the web build does not have. Like every transport here it is single-threaded and polled, never throws and never logs; its Stats() counters are the only record of what it dropped and why.

  • Stateless until the echo. A ConnectRequest costs the server a rate-limit token and one HMAC, and it keeps nothing: no session, no slot, no table entry (the inner UdpTransport does keep its own record of the source, bounded by its peer cap and idle timeout, see Peers, caps and unknown sources). The cookie is a MAC of everything the server needs to check the echo, so the echo carries the state. The cookie secret is 32 random bytes per process, replaced every cookieSecretRotationMicros (default 60 s, never less than twice the cookie lifetime); the secret of the epoch just ended still verifies, any older one is gone. The cookie time is inside the MAC, so it cannot be moved.
  • No amplification. Both client handshake packets are exactly 256 bytes, and the server drops any other size before doing anything else. The only replies a peer without a session can get are the 41-byte Challenge and the 82-byte Accept (sent again, byte for byte and at most 8 times, when a repeated ConnectResponse shows the first was lost). Static assertions in the header pin this, SendPreAuthReply refuses a reply larger than its request, and Stats() keeps the largest reply and the smallest request answered.
  • Silent refusal. A wrong size, a nonzero padding byte, another version or protocol id, a backed-off address, a spent rate limit, a bad or expired cookie, no free slot, a token that matches nothing: each is dropped without a reply and counted. There is no "denied" packet: it could not be authenticated (a server that does not recognise the token has no key in common with the client), so anyone could forge one to abort other people's handshakes. A client with a wrong token therefore sees exactly what it sees when the server is unreachable: ClientState() becomes Failed with HandshakeTimeout after handshakeTimeoutMicros (5 s).

Once it has echoed a cookie it ignores any further Challenge (on a round trip longer than 250 ms the resent ConnectRequest brings a second one, with another cookie, and the server's Accept is for the cookie echoed first). It goes back to a ConnectRequest when it has had no Accept for a cookie lifetime, and gives up after 5 s. A pending session (between the Accept and the client's first sealed packet) is dropped after the same 5 s, and a non-loopback address is charged one failure for it.

Sealed packets

After the handshake every datagram is u8 type | u64 sequence | ciphertext | 16-byte tag: type 0x10 carries data for the layer above, 0x11 is a keep-alive (empty) and 0x12 a disconnect (empty). The cipher is ChaCha20-Poly1305 (RFC 8439) with the session key of the sending direction. The 12-byte nonce is one direction byte (0x43 client to server, 0x53 server to client), three zero bytes and the 64-bit sequence; the associated data is the type, the version, the protocol id and the sequence, so none of them can be changed without failing the tag.

Guarantee: a nonce is never used twice with one key PR #210

Each session derives two fresh keys from its own ephemeral X25519 exchange, one per direction, so no key is ever shared by two sessions or two directions. Within a direction the sequence is taken and incremented before sealing, whatever happens to the packet afterwards, and it only ever rises: the server's Accept is sequence 0 of its key and its data starts at 1, the client starts at 0. At the last value (264 - 1) the layer refuses to seal instead of wrapping (and a keep-alive due then ends the session). The one packet that is sent twice, a lost Accept, is the same bytes, not a new plaintext under the same nonce.

On receipt the sequence is checked against a 256-packet replay window (ReplayWindow: the newest authenticated sequence and a bitmap of the 255 before it) before the packet is opened, and recorded only after its tag verified, so a forged packet can never move the window. A sequence seen before is dropped (droppedReplay), one 256 or more behind the newest is dropped as too old (droppedTooOld), a tag that does not verify is dropped (droppedAuthFailed), and a sealed packet from a peer with no keys is dropped (droppedNoSession); none of these ends the session or gets a reply. Only an authenticated packet refreshes the session's idle clock. A side sends a keep-alive when it has sent nothing for keepAliveMicros (1 s) and drops a session that has authenticated nothing for idleTimeoutMicros (10 s). Poll drains the inner transport first, authenticating what is queued, and only then runs these timers against the time the Poll began, so a caller that stalled for longer than the idle timeout keeps a session whose authenticated packets the inner Poll drained (it is bounded, for UDP by maxDatagramsPerPoll, so a longer backlog is finished by later polls) and still loses one that sent nothing PR #214. Disconnect(peer) sends a sealed disconnect (best effort) and forgets the session.

Design decision: our own AEAD layer on Mbed TLS primitives, after netcode.io, with an ECDHE handshake PR #210

The netcode design (2.1.3) weighed DTLS 1.2 through Mbed TLS against a small layer of our own and chose the latter, reviewed against the netcode.io standard. What is the same as netcode.io: a padded connect request no smaller than any reply, a challenge before any server state, ChaCha20-Poly1305 per packet with the packet sequence in the nonce, per-direction keys, a 256-entry replay window, silent drops. What differs, and why: netcode.io's keys and identity come from a connect token that a web backend encrypts with a key it shares with the server; v1 has no backend, only a static tokens file, so the keys come from an ephemeral X25519 exchange and the token is proved with HMACs instead of carried. netcode.io's challenge token is encrypted; ours is an HMAC cookie, because the echo carries the request fields themselves and nothing in it is secret. netcode.io has a connection-denied packet; ours has none (above). netcode.io writes sequences in 1 to 8 bytes; ours are always 8. ChaCha20-Poly1305 rather than AES-GCM (both are in the vendored configuration) because it is constant-time in software on every leg, with no dependence on AES instructions.

Not covered: the proofs are MACs of public data keyed with K, so an eavesdropper can test guesses of a low-entropy token offline. Tokens must be long random strings (the editor host's --new-token makes 256-bit ones); a short password is not safe here. Whoever has the tokens file can impersonate any user and the server.
Expensive messages (CPU)The costly steps (X25519, two HMACs per token entry) run only after a valid cookie, inside the connect rate and a slot.
Denial by an attacker on the path, or one who can spoof the server's addressNot covered: such an attacker can drop packets, or send forged Challenges that make a handshake fail (a forged Challenge that arrives before the real one is the cookie the client echoes, since it takes only the first Challenge, and its responses then fail the cookie check until it times out); it cannot make the client accept a forged Accept.
Traffic analysisNot covered: packet sizes, timing, types and sequences are visible.

Over UDP, and the fail-closed rule

SecureTransport::OpenUdp(udpOptions, options) opens a UdpTransport with encryptionAvailable = true and puts this layer over it, owning it (result.udp points at it, for Connect, LocalPort and its counters). It is the only caller that passes true, so the A4 rule now reads: a non-loopback bind (or Connect) is allowed when the secure layer is on; without it, insecureBind is still required (Fail closed).

The dedicated server: N2Server PR #216

N2Server is a headless executable that runs a project's scene and listens for clients on a SecureTransport over a UdpTransport: the stack of the sections above in a process of its own, with no window, no renderer and no audio. It is the CMake target N2Server (sources in n2server/; RunServer and the argument parser are in the static library N2ServerCore, so the tests can link them). Like UdpTransport it is not part of the web build. It is a new executable, not a mode of N2EditorHost or lua_project.

What it does: it loads the project and the scene, runs the engine's fixed-tick loop, accepts authenticated connections up to --max-clients, enforces the pre-auth slots and rate limits the secure layer already has, and logs each connect and disconnect. PR #224 It also hosts the scene's network world: it gives the scene's NetworkObjects their net ids, sends each client that connects the server's fingerprint, and replicates spawns and despawns to the clients that join (The network world). What it does not do: it spawns nothing by itself (a host built over RunServer does, through its hooks), and it replicates values only for the fields a component marks replicated (Field replication PR #226, at the project's network.authoritative.snapshotRate): the netcode's later stages add interpolation, inputs, RPCs and prediction.

What starts, in order

  1. --help prints the usage; --new-token runs the generator; --relay on a project that is not deterministic is refused. None of these refusals starts the engine.
  2. The log sink starts on stderr (and --log-file), using the editor host's LogSink (the host log): one timestamped line per Logger line at or above --log-level, control characters escaped. SIGPIPE is ignored on POSIX.
  3. The crypto library must work (Security::CryptoAvailable), or the server exits 1: it could not authenticate anyone.
  4. The tokens file is loaded with JoinTokenTable::Load, so every check the secure layer's table makes applies (a regular file, at most 1 MiB, private to its owner on POSIX, well formed). A file that fails ends the server with one line on stderr that never repeats a hash or the file's text.
  5. The project folder and project.n2proj are checked, and the scene path is determined.
  6. Application::Init runs with RenderBackend::NONE, isHeadless = true, audio = false and physicsGpu = false (Init and ApplicationOptions), and PhysicsBackend::AUTO (the project's own physics.backend wins when present, as for every host). The project's Lua runs (LuaExecutionPolicy::Run): this is the game, not an editor. A project whose network.preset is refused (the Network row is Failed) ends the server with exit code 1 and a line on stderr.
  7. The project's id, resources and settings are applied, and the scene is built from its file, made current as a running game (not edit mode), so its components attach at the first tick. A scene that cannot be loaded ends the server with exit code 1.
  8. PR #224 The scene's NetworkObjects are matched (NetworkWorld::BindScene; a scene that cannot be matched, such as one that uses a UUID twice, ends the server with exit code 1 and a line on stderr), the host's beforeListening hook runs if there is one (it registers prefabs), and the prefab table is captured. Both counts are logged.
  9. SecureTransport::OpenUdp binds --bind and --port. A failure (the address is not numeric, the port is in use) ends the server with exit code 1.
  10. The ready line is printed (below), then the loop starts.

The ready line

Once the server is listening, and not before, it prints one line to stdout, flushed (the C stream, as the editor host does, so a pipe sees it at once): N2Server ready port=<port> bind=<address>, where the port is the one bound (the system's pick with --port 0) and the address is the bound address. A launcher matches a whole line starting with N2Server ready followed by space-separated key=value fields (values never hold a space) and ignores keys it does not know; port is always present. This is the format of the editor host's ready line. The line holds no secret. It is not the only thing on stdout, so a launcher reads line by line and matches the prefix, as it does for the editor host: Math::InitializeSIMD prints its start-up report (the lines between ----------INITIALIZE SIMD BEGIN---------- and ----------INITIALIZE SIMD END------------) through std::cout in every build type, and in a Debug build (N2ENGINE_DEBUG) Application::Init also calls Logger::InitializeDebugConsoleHelper, which echoes every log line to stdout as [INFO] ..., [WARN] ... or [ERROR] .... The server's own log goes to stderr (and --log-file) in every build type. The SIMD report comes out at start-up, before the ready line (in a Debug build as [INFO] ... lines, since the helper also redirects std::cout into the logger); the Debug echo continues for the whole run, so lines such as client connections follow the ready line. Join tokens: --new-token

N2Server --new-token alice player --tokens-file tokens.json makes a token for alice with the role player (or spectator or admin), adds the entry to the file and prints:

New join token for alice (player). It is shown once: the tokens file keeps only its SHA-256, so store the token now.
token: <64 lowercase hex digits>
Added alice to tokens.json. A running server reads the file again on SIGHUP (POSIX); a server that is started reads it at start.

The token is 256 random bits from Security::RandomBytes (the operating system's entropy source, through Mbed TLS), written as 64 lowercase hex digits. The entry added is {"user", "role", "hash"} with the hash "sha256:" and the SHA-256 of the token's text (HashJoinToken), the format JoinTokenTable reads; the hash needs no salt because there is nothing to guess. The generator does not start the engine, installs no log sink and logs nothing; the token goes to stdout once and is never written to the file, a log or an error (a launcher takes it from the line that starts token: ). On failure it prints one line, N2Server --new-token: <reason>, to stderr, prints no token and exits 1.

  • The file is checked as the server checks it. An existing file is read with JoinTokenTable::Load (so one that is too large, malformed, or readable by group or others on POSIX is refused, and left unchanged); a symbolic link is followed and the target is replaced, the link kept. A file that does not exist is created (its folder must exist).
  • A user already in the file is an error and the file is untouched: to revoke or replace a user, edit the file.
  • The file is rewritten whole, atomically. It is written from the parsed table plus the new entry (one entry per line), to a new file beside it and moved over it, so a reader never sees half a file. On POSIX the new file is created with mode 0600 (O_EXCL), flushed to disk, then renamed. On Windows it inherits its folder's ACL (Windows ACLs are not checked by the server either). What is about to be written is parsed again before it is written, so the generator never writes a file the server would refuse.
  • Run it one at a time. Two runs at once read the same file and the later write wins: one entry can be lost.
  • The user name is 1 to 64 characters of A-Z a-z 0-9 . _ @ -; the role is spelled exactly player, spectator or admin.

Security

  • Fail closed. ParseServerArguments refuses a non-loopback --bind unless --tokens-file or --insecure-bind is given, before anything starts (exit code 1, a message naming the address and both ways out). Loopback is IsLoopbackAddressText: an IPv4 address in 127.0.0.0/8, ::1 and an IPv4-mapped 127/8 address; a host name or any odd spelling counts as non-loopback. The default bind is 127.0.0.1, and no other option changes it, so a server never listens on 0.0.0.0 unless asked to. This mirrors the editor host's rule (which needs a token and --tls, or --insecure-bind); here every session is encrypted and authenticated by the secure layer whatever the flags are, so the rule is about whether anyone can authenticate. A server with no tokens file admits nobody (SecureTransportOptions::tokens is null), and logs "No --tokens-file: nobody can join this server"; --insecure-bind only lets such a server start on a non-loopback address, and the server then logs a warning that it did.
  • Tokens. The server holds hashes only (the file's). A presented token is never compared as text: the handshake proves knowledge of the token's hash with HMACs and SecureTransport checks the proofs against every entry of the tokens file in constant time: SecureTransport::OnConnectResponse runs its own loop over the table's entries (JoinTokenTable, the file's parsed and checked records), computes both HMACs with each entry's hash as the key, compares them with Security::ConstantTimeEqual, never exits early and selects the matching entry with a mask, so the time depends on the number of entries and not on which one matched (it does not call BasicTokenTable::Authenticate; The handshake). Nothing the server writes (the log, the ready line, an error) contains a token or a hash: the log names the tokens file's path and the number of users in it, and a user's name once connected. No secret is taken from a command line or the environment: --new-token prints a token and nothing reads one. The test client of the smoke test reads its token from stdin.
  • Limits are the secure layer's. N2Server sets no flag for them and keeps the defaults of SecureTransportOptions: 16 pre-auth slots in all and 2 per non-loopback address, 200 challenges per second in all and 10 per non-loopback address, 50 connect responses per second in all and 5 per non-loopback address, and the backoff of addresses whose handshakes failed (Admission). --max-clients bounds the sessions. Handshakes the server drops are counted and, when any were, reported in one line every 60 seconds ("Handshakes dropped since the server started: bad token 3, ...") and in the line it logs at shutdown; the line holds counts, no addresses.
  • What a world-facing bind exposes. The UDP port: anything that can send to it can start a handshake, which costs the server a bounded amount of work per source (the cookie step keeps no state; limits above). Only a token in the tokens file gets a session. The server logs a warning at start when it is bound to a non-loopback address. Firewall the port to the clients' addresses where you can.
  • No session without an identity. A session is made from the token entry that matched, so it always carries the entry's user and role and GetPeerIdentity finds it. If a PeerConnected ever came without one, the server would log one warning (no secret in it) and disconnect that peer right after the current Poll returns, never keep it as a client: SecureTransport::Disconnect does nothing inside Poll's handler, so the peer is queued in the handler and disconnected by the loop (a sealed Disconnect, the session forgotten) before the next engine tick PR #218.
  • Revoking. A reload (SIGHUP) swaps the table for new handshakes only; a client already connected stays until it leaves or goes idle (Limits). To remove one at once, restart the server.
  • The project's Lua runs on the server with the engine's usual sandbox and limits (Scripting); a project is trusted code of whoever deploys it. The server never loads a scene or a script a client names: --scene is the operator's.

Token handling is security-critical and this stage has had no review beyond its tests and its author. The points to review are the fail-closed bind rule, the tokens file's handling and permissions (checks on load, the 0600 atomic write of the generator), that no secret is printed or logged outside --new-token's one line, the shutdown paths, and the defaults above on a world-facing bind.

While it runs, and stopping it

Each pass of the main loop (every 2 ms): reload the tokens file if SIGHUP asked; NetworkServer::Update (it polls the SecureTransport, handles the world messages and sends what is due) PR #224; Application::Tick with window events off and rendering off (the fixed ticks that are due run as in any host: the simulation mode follows the project's network.preset); the host's onTick hook if there is one; report dropped handshakes if a minute has passed and some were dropped; sleep 2 ms. Events:

  • Connect: PeerConnected comes once the client's first sealed packet arrived (step 5). The log line is Client connected: user=alice role=player peer=1 address=127.0.0.1:50321 (1/16): the user and role the handshake proved, the transport's peer id, the source address and the count out of --max-clients. These lines are tagged Logger::LogSensitivity::Admin, as the editor host tags lines about its clients.
  • Disconnect: Client disconnected: user=alice role=player peer=1 (0/16), when the client sent its sealed Disconnect or its session went idle (10 s without an authenticated packet, SecureTransportOptions::idleTimeoutMicros).
  • Data: an authenticated client's datagrams go to its world Connection (The join, step by step) PR #224; the world's own log lines (Network client joined the world, Network client left the world, a drop with its reason) come with them, and the shutdown line reports how many clients joined the world.

Stopping. The loop ends on SIGINT or SIGTERM, on Application::Quit (a script's Application.Quit()), and, with --exit-on-stdin-eof, when stdin closes. On Windows a console's Ctrl+C and Ctrl+Break do the same, and so do closing the console, logoff and shutdown: the console handler asks the loop to stop and waits up to 4.5 seconds for the clean shutdown before it lets Windows end the process. The handlers only set a flag, so no logging happens inside a signal handler. Then: a sealed Disconnect to every connected client, one line of counters ("Stopping: N session(s) established, ..."), the transport closed, OnApplicationQuit on the scene, Application::Shutdown. The exit code is 0 after a clean stop, 1 for a setup failure above or a std::exception that escaped (logged as "Fatal error: ..."); that last path runs the same OnApplicationQuit and Application::Shutdown as the clean stop, each guarded so that neither can throw (a failure in one is logged and the other still runs), so scenes, physics and audio are not left to static destruction PR #218. The signal handlers are put back as they were when RunServer returns.

SIGHUP (POSIX, only with --tokens-file) reads the file again: a table that loads replaces the one used for new handshakes ("Reloaded the tokens file: N user(s)"); one that fails its checks is logged ("The tokens file was not reloaded (the previous one stays in force): ...") and the old table stays. Without --tokens-file the server leaves SIGHUP at its default, which ends the process.

Design decision: a new executable that borrows the editor host's helpers, with stricter arguments PR #216

The netcode design (decisions N5, N11 and N12) asks for N2Server as its own executable, not a mode of N2EditorHost or lua_project: a game server has a different trust model (clients are untrusted players, not editors), a different loop and no editor protocol. It links N2EditorServer for what is generic there (the log sink with its escaping, the port and number parsers, the stdin watcher, scene path resolution) rather than copy it; the editor protocol and server are not started. It departs from the editor host's argument conventions in one way: unknown arguments are errors, not ignored (above). It has two flags the plan did not list, --protocol-id (the secure layer needs an id and a game must be able to set its own; the default is the one this page's examples use) and the default port 7777, both easy to change.

Design decision: the engine learns "no renderer", "no audio" and "no physics GPU" PR #216

The headless paths that existed were the editor's: a hidden window or the software renderer (still a renderer object), and a loopback audio device for the editor's audio stream. A server wants neither, so ApplicationOptions gained RenderBackend::NONE (no GLFW, no window, no renderer: Window::IsValid() stays false, IsWindowless() is true, ShouldClose() is false), audio (false opens no device at all and reports Audio Disabled) and physicsGpu (false forces the physics GPU off whatever physics.gpu says, also for the checks of a Deterministic project). All three default to what every host did before, so no existing host changes. Resources::LoadShader returns null with no renderer instead of dereferencing it.

NetworkObject and net ids PR #224

NetworkObject is a component registered under the name NetworkObject with the engine's own types, one per object (IsSingleton). It saves nothing beyond the base keys (uuid, isActive) and has no editable fields: the id, the owner and the prefab are the session's, set by a NetworkWorld, and are never written into a scene or a prefab. While no world has the object it has no id (GetNetworkId() is 0, IsRegistered() false) and replicates nothing. When the object's GameObject is destroyed, or the component freed, the object leaves its world and the world's destroyed handler is told (a server turns that into a despawn).

  • Net ids. The scene's NetworkObjects get 1, 2, 3 … (below); every object spawned afterwards gets the next number up (NetworkWorld::AllocateId). The counter only rises: an id is never given out twice in a session, so a message that arrives late can never name a different object than the one it was about. When the 32-bit counter would run out (id 4,294,967,295 is never used), the server refuses to spawn.
  • Owner. A spawned object has the client id of its owner (NetworkServer::Spawn(prefab, owner); the owner must be a client that has joined) or 0, the server. Scene objects belong to the server. Client ids start at 1 for each server run and are never reused. The owner is fixed at spawn. Nothing acts on it yet: sending inputs and RPCs for an owned object is later work. An object whose owner has left keeps naming that client, which no longer exists; what to do with it is the game's choice (NetworkServer::Despawn).
  • At most 4096 objects are registered at once, scene and spawned together: more fails a scene bind, and a spawn at the cap fails.

Scene objects: matching by UUID PR #224

NetworkWorld::BindScene(scene) walks every GameObject of the scene (active or not, attached to the scene's update or not: it walks the hierarchy, not the list of attached components, so it works right after the scene is built; an object already marked for destruction is skipped), takes those that have a NetworkObject, sorts them by the 16 bytes of their GameObject UUID and gives them ids 1, 2, 3 … in that order. The server and every client load the same scene file, so each computes the same ids and nothing about scene objects travels on the wire: the fingerprint (below) proves the files are the same. Objects created in a different order, or in a different tree shape, still get the same ids, since only the UUIDs count.

The bind fails, leaving the world empty and the objects as they were, when two objects share a UUID (scene objects are matched by UUID, so each needs its own), when there are more than 4096, or when an object already belongs to another world. N2Server ends with exit code 1 on such a scene, before it listens. The world is tied to the scene it was given: when that scene is freed (a scene change) the world is lost (HasScene() is false) and a server ends every client's session; scene changes are not replicated yet.

Prefabs and the prefab table PR #224

A spawned object is made from a prefab registered with PrefabManager::RegisterPrefab (Serialization: prefabs). PrefabTable::Capture() takes the registered prefabs at that moment, sorted by name, at most 1024 (the first by name, with a warning, when more are registered), and the session uses that table from then on: a spawn names its prefab by the prefab's index in it (a u16). A prefab registered after the capture is not in the table, and NetworkServer::Spawn refuses it. Both ends build their table from their own registrations, and the fingerprint's registry hash covers it, so a client whose table differs refuses to join.

The prefab hash is of the prefab's shape (PrefabShapeHash): for every object in pre-order its name, its component type names in order and its number of children. It does not include UUIDs (a project that builds its prefabs in code gives every object a new random UUID in every process, and two peers must still agree), and it does not include component values (replicated values travel in state updates after the spawn, below). A prefab of more than 100,000 objects hashes as that fact.

A spawnable prefab must have exactly one NetworkObject, on its root object. NetworkWorld::SpawnInstance instantiates it with InstantiateRegisteredPrefab (fresh UUIDs), checks that, and only then adds it to the scene as a root object and registers it; a prefab that fails the check leaves nothing in the scene. The instance's components attach at the scene's next attach pass, like any object added to a scene.

The messages PR #224

One message per reliable message of an n2net Connection (the reliable-ordered channel; the state updates of field replication use the unreliable one and are decoded apart). Little-endian. A message is a type byte and a body; the type byte also says who may send it. kWireVersion is 3 (state replication, PR #226, raised it from 1 to 2; player input, PR #TBD, to 3); any change to a layout, or a new message, bumps it. The current value is 6 (the RPC messages, PR #241, are new; their layout is below).

TypeNameSent byBody
0x01ServerHelloserveru16 wire version, fingerprint, u32 client id (not 0)
0x02Spawnserveru32 net id (not 0), u16 prefab index (under 1024), u32 owner client id (0: the server)
0x03Despawnserveru32 net id (not 0)
0x04WorldReadyserveru32 spawned objects sent in the join state, u32 destroyed scene objects sent (each at most 4096)
0x81ClientAcceptclientu16 wire version, fingerprint
0x82ClientRejectclientu8 reason, 1 to 5 (JoinRefusal: wire-version, engine-version, scene-content, registry, object-count)

A fingerprint on the wire is: u8 length and the engine version, u64 scene hash, u64 registry hash, u8 length and the scene path, u32 scene object count (at most 4096), u16 prefab count (at most 1024). The largest message is a hello with the longest fingerprint, 318 bytes; no message is over kMaxMessageBytes, 512, and both ends set their Connection's maxMessageSize to it, so a peer that sends more fails its own connection (MessageTooLarge).

Guarantee: the decoder reads only what it is given and allocates nothing a peer asks for

Every length is checked against the bytes that remain and against its cap before anything is taken. The only allocations are the two texts of a fingerprint, at most 32 and 255 bytes; every count is a plain integer, checked against its cap and never used to size anything. A text must be printable ASCII (0x20 to 0x7E), so it can go into a log line or an error as it is. Bytes after the end of the message, an unknown type, a type of the other direction, a wire version that is not this one, an id or client id of 0 and a count over its cap are each rejected with a reason (DecodeError) and have no effect. What decodes re-encodes to the same bytes.

The join, step by step PR #224

  1. The link. The transport reports a peer. Over N2Server that is a SecureTransport peer, which exists once its handshake succeeded (step 5), so everything below happens to authenticated clients only.
  2. The server makes a Connection for the peer (protocol id: the server's --protocol-id; connection id the constant 0x4E324E42 on both ends; the reliable window and first unit id at their defaults, as the client has them), gives the client the next client id and sends a ServerHello at once. A peer beyond maxClients is dropped without a hello.
  3. The client (state AwaitingHello from its own link) decodes the hello: a wire version it does not know, or any difference in the fingerprint, makes it Refused (above). Otherwise it sends a ClientAccept with its own fingerprint and is Joining.
  4. The server compares the accept's fingerprint with its own (a mismatch drops the client), marks the client joined and sends the join state: a Despawn for each scene object destroyed since the start (ascending ids), a Spawn for each live spawned object (ascending ids, with its prefab index and owner), then WorldReady with the two counts.
  5. The client applies each message as it comes (a despawn destroys the object it matched, a spawn instantiates its own copy of the prefab). At WorldReady the counts must equal what it received; then it is Joined and follows every later spawn and despawn in order.

A server that spawns or despawns tells every client that has joined; a client still joining gets it from the join state, which is made when it accepts. A client that joins later gets the objects that were spawned and not despawned and the scene objects that are gone, not the history. NetworkClient's states: Connecting (no link yet), AwaitingHello, Joining, Joined, Refused, Closed (the server closed the connection, or Leave() was called) and Failed (the server broke the protocol, or sent no hello within 10 seconds of the link). The client checks every spawn: it must carry an id that is above every scene object's and above the last spawn's, name a prefab that is in the client's own table, pass SpawnInstance's checks, and not take the world past 4096 objects; anything else fails the client, which disconnects. A despawn of an object the client does not have (it destroyed it itself) is counted and ignored.

Authority and limits PR #224

Guarantee: a client can never spawn or despawn anything

Only NetworkServer::Spawn and NetworkServer::Despawn, called by the server's own code, create or destroy a networked object. There is no message a client can send for either: the decoder the server uses on client input accepts two types, the accept and the reject, and answers every server type with WrongDirection (the state acknowledgement of field replication is decoded apart: it carries sequence numbers and no value). A client that sends a Spawn, a Despawn, a hello, a WorldReady or anything else is dropped (the log says so) and nothing it sent has any effect.

Hosting it: NetworkServer, NetworkClient and N2Server PR #224

Both ends run over any ITransport (a simulator endpoint in the tests, a SecureTransport over UDP in N2Server) and are polled: call Update(nowMicros) every frame with a monotonic microsecond clock; it polls the transport, handles what arrived, runs the timers and lets each connection send. They are single-threaded, take the transport and the NetworkWorld by reference and must not outlive either. A server in a host of your own:

Network::NetworkWorld world;
auto matched = world.BindScene(scene);                        // ids 1..N for the scene's NetworkObjects
Network::NetworkServerOptions options;
options.protocolId = protocolId;                               // the same on every client
options.scenePath = "res://scenes/main.scene";
options.sceneHash = Network::HashSceneJson(sceneJson);         // of the file's parsed JSON
options.prefabs = Network::PrefabTable::Capture();             // frozen now
Network::NetworkServer server(transport, world, std::move(options));

server.Update(nowMicros);                                      // every frame
std::expected<Network::NetworkId, std::string> id = server.Spawn("Crate", ownerClientId);
server.Despawn(*id);

A client does the same with a NetworkClient (NetworkClientOptions: the protocol id, its scene path and hash, its prefab table) after it has loaded the scene and bound the world, and watches State(), Error() and the events its observer gets (Joined, Spawned, Despawned, Refused, Closed, Failed). It needs no window, renderer or engine tick: only a scene to put objects into. A despawn destroys the object's GameObject (the scene frees it at its next destroy pass, which Application::Tick runs); the object has left the world at once.

When the game's own code destroys a networked object on the server (Destroy() on its GameObject), the server hears of it when the scene's destroy pass runs the component's OnDestroy and replicates it as a despawn at its next Update. An object that is added to the scene at runtime without Spawn has no id and is not replicated.

N2Server does the server's part: after the scene is loaded it binds the world (a scene it cannot match ends the server with exit code 1), captures the prefab table, opens the transport, and runs a NetworkServer over it in its loop (NetworkServer::Update replaces the transport's own poll; each pass: update, tick, sleep). It logs Network world: N scene object(s) with a NetworkObject and Network world: M prefab(s) in the prefab table at start, Network client joined the world: client=1 peer=3 and Network client left the world: client=1 peer=3 joined=yes (disconnected) (Admin lines like the connect lines), a warning Network client 1 (peer 3) is dropped: … for each drop (an info line for a refusal), and the number of clients that joined the world in its shutdown line. N2Server itself spawns nothing; a host built over RunServer(options, hooks) (ServerHooks) registers prefabs in beforeListening (after the world is bound, before the table is captured) and spawns and despawns from onTick, which also may end the loop. The scene is loaded by LoadSceneForRun (n2server/include/n2server/SceneLoading.hpp), which also returns the scene's content hash; a test client loads its scene with the same function.

What is not replicated, and the limits PR #224

  • Only replicated fields. A spawned object appears as its prefab made it, and the server's state updates then bring its replicated fields (Field replication, PR #226); nothing else about a component is sent.
  • Prefabs come from code. There is no prefab file in a project: prefabs are registered with PrefabManager::RegisterPrefab in C++, so a plain N2Server has an empty prefab table until a host registers prefabs (ServerHooks::beforeListening), and a client must register the same ones. Loading prefabs from project files is later work.
  • One scene. A scene change on the server ends every session and is not replicated; a client does not reconnect by itself, and a client that reconnects is a new client with a new id.
  • No interest management or priorities: every spawn, and every replicated field of every object, goes to every client that joined.
  • Limits: 4096 objects, 1024 prefabs, 512-byte messages, 32 client messages a second, a 10-second join timeout, --max-clients (at most 1024) clients.

Design decision: scene objects are matched by UUID and numbered in UUID order, with nothing on the wire PR #224

The netcode design (section 2.5) matches scene-placed objects by their scene-file UUID and gives them ids in sorted UUID order, because both sides load the same file and the fingerprint proves it. That keeps the join state to what changed since the start (the objects spawned, the scene objects destroyed) instead of a table of the whole scene, and makes the ids of the scene identical on both sides without an exchange. The cost: every scene object that is networked needs a unique UUID (a scene that reuses one is refused), and a scene file that differs in any way is refused at the join rather than matched approximately.

Design decision: the client checks the fingerprint, with a small non-cryptographic hash of the scene's parsed content PR #224

The design says the client refuses on a mismatch, so the check is the client's; the server only repeats it on the accept. The scene hash is taken over the parsed JSON, not the file's bytes, so a Windows checkout with CRLF line endings, a re-indented file or another key order joins a Linux server (the loopback test joins a reformatted copy). It is FNV-1a 64: a fingerprint has to tell two builds apart, not resist an attacker, and a hash with no dependency builds in the web build, which has no crypto library. The prefab hash covers structure and not UUIDs or values for the reason above. Lua sources and assets are not in it.

Design decision: prefabs are registered in code and frozen into a table per session PR #224

The design names a prefab by its index in a registered-prefab table sorted by name. The engine's prefab registry is in memory and filled from C++, with no prefab asset type in a project, so the table is whatever is registered when the session starts (PrefabTable::Capture), and a prefab registered later is not spawnable until the next session. Making prefabs files of the project, so that N2Server and a client load the same set from disk, is left to the stage that adds them.

Design decision: an owner that leaves does not change the object PR #224

Ownership has no behaviour yet (inputs and RPCs for an owned object are later stages), so the owner of a spawned object is its client id for good, and client ids are never reused: an object whose owner left cannot be mistaken for another client's. Whether it should be despawned, handed to the server or to another client is the game's call until those stages say otherwise; the server's observer tells the host when a client leaves.

Design decision: the engine target links n2net PR #224

n2net stays free of engine types, but the world layer is engine code that runs its Connections and takes its ITransport, so engine links n2net publicly. The web build links it too: the parts it uses have no sockets and no crypto, and the new tests run on the web leg.

Not verified

The layer has run only in CI: over the simulator in engine_tests, and over real loopback UDP with the secure handshake in n2server_net. Behaviour across a real network, with real loss and latency, and with many clients is untested. The web client has no transport yet, so the web build only compiles and unit-tests this layer. Bandwidth was not measured: every spawn is 11 bytes plus packet overhead, a join state is one message for each object spawned and each scene object destroyed, at most 8192 messages of at most 11 bytes each. The security-relevant paths (the codec, the authority checks, the limits above) have had no review beyond their tests and their author.

What an object replicates: the layout PR #226

An object's layout (BuildObjectLayout) lists the replicated fields of its components, the components that have any in the order of the object's components and in each the fields DescribeFields lists with replicated set. The field mask of a state entry has one bit per entry of that list, so both ends must derive the same list from the same scene (they load the same file). Three things keep a difference from being misread:

  • The registry hash of the join fingerprint covers, for every registered component type, the replicated fields of its schema and everything that decides their bytes (HashFieldFormat: name, container, kind, type name, step, range, enum options). A client that replicates other fields, or the same fields another way, refuses to join (registry).
  • The layout hash. Every state entry carries 16 bits of a hash over the layout (component positions and type names and every field's format). A reader whose layout for that object differs skips the entry, counts it (entriesLayoutMismatch) and does acknowledge the message (a layout that differs stays different, and a message held back would keep every object that shares it from getting a baseline). This is also the only check for a Lua script's fields, which belong to an object and not to a type, so the registry hash cannot know them.
  • Limits. At most 64 replicated fields per object (kMaxReplicatedFieldsPerObject; the rest are ignored, with a warning), and the fields of an object at their longest, with the mask, must fit 900 bytes (kMaxReplicatedEntryBytes; an object over it replicates nothing, and an error is logged). A layout is cached per net id and rebuilt when the object's list of components changes; DescribeFields is not asked again otherwise (a script reloaded in place keeps its layout until the components change).

Delta against the acknowledged baseline PR #226

The server reads and encodes every replicated object once per send tick (objects in net id order, fields in layout order), then builds each joined client's messages (ServerReplicator::BuildForClient). Per client and per object it keeps, for each field, the bytes the client has acknowledged (the value of the newest acknowledged message that carried the field) and how many unacknowledged messages carry it. A tick sends a field when

  1. the client has acknowledged none yet (a new object, or a baseline that was lost: the first message holds every field of the object that could be encoded), or
  2. its current bytes differ from the acknowledged ones, or
  3. an unacknowledged message carries it: the client may already have that newer value or may not, and sending the field again is the only way the receiver's state is certain.

The client applies each entry on top of what it has. There are no per-packet guarantees: a lost message is simply not acknowledged, and the next message is computed against the baseline as it was, so nothing needs a resend queue. The unreliable channel delivers a message at most once and never one older than a message already delivered, so a field that is absent from a message is one both ends agree on, and the receiver ends with the server's value whatever was lost, reordered or duplicated. A client sends one StateAck per update in which it applied a message (the newest sequence and the 32 before it, so a lost acknowledgement is covered by the next); the server applies each message's acknowledgement once, and an acknowledgement of an older message that arrives after a newer one's does not take a baseline back (each field remembers the sequence its baseline came from).

  • A message is acknowledged only if every entry in it was applied or permanently unusable. An entry for an object the client does not have yet (the reliable spawn is still on its way) or one that refers to an unknown object leaves the message unacknowledged, and the server, which treats an unacknowledged message as not received, keeps those fields in what it sends. A client in the state Joining ignores state updates entirely and acknowledges none; it gets everything once Joined. An entry with another layout is counted and skipped but does not hold the acknowledgement back.
  • The history is bounded. A client's unacknowledged messages are kept at most maxInFlightMessages (64; 8 to 256) and at most recordTimeoutMicros (2 s). A message that falls out of either is given up on: every object it named loses its baseline and goes out in full, so a late arrival of the old message cannot leave a stale value behind (the full state overwrites it). Each message is at most 1100 bytes; each baseline is at most 64 fields of at most MaxEncodedBytes bytes; an object's baselines are dropped when it is despawned and a client's when it leaves.
  • Rate and budget. NetworkServerOptions::stateSendRateHz (30; at most 240; 0 turns replication off) sets how often a tick runs (N2Server: the project's network.authoritative.snapshotRate); a tick builds at most maxMessagesPerTick (4) messages per client, and the objects that did not fit are the first of the next tick, so none starves. With nothing changed since the acknowledgement a tick sends nothing.
  • Everything goes to everyone: interest management is a later stage.

Bandwidth in a scripted scenario (ServerReplicatorTest.ADeltaIsMuchSmallerThanSendingEverythingEveryTick): 50 objects with a 60-byte label each, one object's score changing every tick for 300 ticks, every tick acknowledged: the deltas total under a twentieth of what sending the whole state every tick would.

What is not there, and the limits PR #226

  • No owner-written fields; prediction only for the character controller. A client sees the server's values; remote NetworkTransforms are shown interpolated PR #236 (Clock sync and interpolation), every other replicated field as it arrives, at the send rate.
  • No interest management or priorities: every client gets every replicated field of every object, within the per-tick budget of 4 messages.
  • Not replicated: lists of references, component references, Json fields, a Lua field that is a reference or a table, and anything a component does not mark.
  • Limits: 64 replicated fields and 900 bytes per object, 128 bytes per string, 1100 bytes per message, 64 unacknowledged messages and 2 seconds of them per client, 1024 acknowledgements a second per client, 240 sends a second at most. A network latency over the 2-second record timeout cannot be tolerated: a message that arrives after the server gave up on it could leave a stale value until the next change.
  • Sequence numbers are 32 bits per client. When one client has been sent 4,294,967,294 messages the server stops sending it state (sequencesExhausted counts what it did not send) rather than let the number wrap, since a wrapped sequence would look stale to the client; it rejoins to start again. That is 51 days at the extreme of 4 messages per tick at 240 ticks a second, and 4.5 years at 30 ticks a second with one message each.

Design decision: the baseline is the newest acknowledged value of each field, and an unacknowledged field is sent again PR #226

The design says to compare each object with the last acknowledged state. A client that applies entries on top of what it has needs more than that: a message that was received but not yet acknowledged may already have changed a field the next message leaves out. So the baseline is kept per field, with the sequence it came from, and a field that any unacknowledged message carries is sent again until one is acknowledged. The cost is that a changed field is sent about once per round trip's worth of ticks (until its acknowledgement arrives) rather than once; a field that never changes costs nothing after the first acknowledgement. The alternative, keeping a history of whole snapshots on the client and naming the baseline in each message, costs client memory and a baseline-not-found case for every object.

Design decision: values are read through the component's JSON and compared as encoded bytes PR #226

The design's first version reads fields through the existing serialize functions (a JSON value per member) and encodes that; a raw-pointer path for plain types is left for later. Comparing the encoded bytes, not the JSON, means a quantised field that moved by less than a step is not resent, and the comparison is exact and cheap. A component that keeps its live state somewhere other than its members (a LuaComponent) overrides SerializeReplicated and ApplyReplicated.

Design decision: a layout hash in every entry, not field ids on the wire PR #226

Entries name no field: the mask has a bit per field of the layout both ends derive. A 16-bit hash of the layout in each entry (2 bytes per object per message) turns a layout that differs, which a Lua script's per-object fields make possible and the registry hash cannot see, into a skipped and counted entry instead of garbage. The wire version rose from 1 to 2 because the state messages are new.

Design decision: where the codecs differ from the design's sketch PR #226

A Bool is a byte, not a bit (the field mask already says whether it is present, and a byte keeps every codec byte-aligned). An AssetRef is the asset's 16-byte UUID, not an index into a per-session table or a hash of its path: there is no session asset table yet, and a UUID resolves exactly the way a scene's reference does (Resources::LoadByUUID). A ComponentRef is not replicable (it would need a component id on the wire). Quantisation is chosen per field (a step, or a range), not by a global setting, and NetworkTransform has its own position step as a saved member.

Design decision: a teleport is a replicated counter PR #226

NetworkTransform::Teleport raises an integer that replicates like any field, rather than adding a flag to the wire format: the client sees "the serial changed" exactly when it has the new position, the delta machinery needs no special case, and a lost message cannot lose the jump (the counter is resent until acknowledged).

The input layout PR #TBD

A game declares which controls its players' input holds, once, and the same on the server and every client (InputLayout, engine/include/engine/network/InputLayout.hpp). A control is a button (one bit), an axis (one number), a vector2 or a vector3 (two or three numbers with the same bits and range). Controls are held in the byte order of their names, so the order they were declared in does not matter. From C++:

Network::InputControlSpec move; move.name = "move"; move.kind = Network::InputControlKind::Vector2; move.bits = 8; move.range = 1.0f;
Network::InputControlSpec jump; jump.name = "jump"; jump.kind = Network::InputControlKind::Button;
auto layout = Network::InputLayout::Create({move, jump});      // std::expected: the error names the first problem
Network::SetDeclaredInputLayout(std::move(*layout));           // what a host copies into its server or client options

From a Lua script, at the top level of a script that loads with the scene (the dedicated server reads the declared layout once the scene has loaded):

Network.DeclareInputLayout({
    { name = "jump", kind = "button" },
    { name = "move", kind = "vector2", bits = 8, range = 1 },
    { name = "throttle", kind = "axis", bits = 6, range = 1, signed = false },
})

The bounds, which Create checks and the Lua call checks field by field (a field of the wrong type, an unknown field, a missing name or kind, or a list with other keys is an error, and a refused declaration changes nothing):

  • At most 32 controls; a name of 1 to 32 characters of A-Z a-z 0-9 _ that does not start with a digit; no two the same.
  • bits per component 1 to 16 (2 to 16 for a signed one); range in (0, 1,000,000]; signed defaults to true, bits to 8 and range to 1. A button ignores all three.
  • At most 256 bits in all, so a payload is at most 32 bytes.

Quantisation. A component is a whole number of steps, packed lowest bit first, controls in name order, padded with zero bits to whole bytes. Signed: 2^(bits-1) - 1 steps each side of zero, so zero is exact; unsigned: 2^bits - 1 steps from zero to range. A value outside the range clamps to the nearest end, NaN is 0, a button is pressed from 0.5 up. The value a payload decodes to uses only IEEE division and multiplication on small whole numbers, so it is the same on every machine; a value packed and unpacked comes back rounded to the nearest step (a tie up), and packing that again gives the same bytes.

The fingerprint. InputLayout::Hash() (FNV-1a over each control's name, kind, bits, signedness and range) is folded into registryHash (HashRegistry(prefabs, layout), registry format tag 3), so a client whose layout differs in any control or any quantisation is refused with JoinRefusal::Registry and an error that names "input layout". The fingerprint's wire fields did not change.

The client: sampling, redundancy and the ring PR #TBD

Once Joined, the game calls NetworkClient::QueueInput(tick, values) once per fixed tick with the layout's values (ValueCount() numbers, ValueOffset(i) says where control i starts). It packs them into an InputFrame with the next sequence (1, 2, 3 ...; the tick must rise from one call to the next) and keeps it in a ring of unacknowledged frames, at most 64: beyond that the oldest is dropped and counted (framesDroppedFull). Design decision: the input delay is applied on the server, as stamp plus delay PR #TBD

The design sketches an adaptive buffer of 1 to 3 ticks. This stage has no clock sync, so there is nothing yet to adapt to: the target is a fixed number of ticks (delayTicks) that shifts the tick a frame is applied on. It costs that many ticks of added latency and makes a frame that arrives up to that many ticks late still count; an adaptive target, and the client running ahead of the server by the measured delay, belong with clock sync.

Design decision: acknowledge like the state acks, but not a frame that is too far ahead PR #TBD

The acknowledgement is the latest sequence plus 32 bits, the same shape as the state acknowledgement, so a lost ack costs nothing. Clock sync and interpolation of remote objects PR #236

This is stage B3. It does two things for a client: it estimates the server's tick (so the client knows when a state it received was true), and it uses that to show every object it does not control a little in the past, interpolated between the states the server sent, so that movement is smooth although the states arrive 30 times a second, late, out of order or not at all. The clock estimate PR #236

Once joined the client pings at most once per Update: every 100 ms until it has eight samples, then every 500 ms (clockBurstIntervalMicros, clockIntervalMicros, each at least 20 ms). It keeps the send time of the last 8 pings by sequence; a pong whose sequence has no record (answered already, too late, never sent) is counted (pongsUnmatched) and ignored. A matched pong becomes a sample in ClockSync (no I/O, no clock of its own, testable on its own):

  • One sample is the round trip (receive minus send on the client's monotonic clock) and an offset: the server's time when the pong arrived (the pong's tick, plus the fraction of the tick, plus half the round trip) minus the client's clock. A sample with the pong before the ping, a round trip over 5 s, a bad tick or a tick rate that differs from the first sample's is refused and changes nothing.
  • The estimate comes from the newest 16 samples (sampleCount, 3 to 64): the median offset of the half with the shortest round trips (best of N: a sample delayed by queueing has its offset wrong by up to half the delay, so a few spikes of jitter or loss move nothing). The round trip it reports is the median of all 16 and the jitter their mean absolute deviation from it.
  • It never goes backwards and has no jumps it does not have to make. What the game reads (ServerTick) follows the estimate at a bounded rate: at most 5 % faster or slower than real time (maxSlewRate, 0.001 to 0.5), which is how drift is followed. The first estimate is taken as it is. An estimate more than 250 ms away from the running one replaces it at once (snapThresholdMicros; counted in Stats().snaps) and, as always, the answer is never smaller than one already given, so time stands still until the new estimate catches up. A client clock that steps back is tolerated the same way.
  • Ticks are 32 bits on the wire and are unwrapped against the first sample's into a 64-bit count (the tests start the server 16 ticks before the wrap). Everything is in ticks of the server's tick rate as a double, exact far beyond any session. Before the first sample the clock reads 0, and nothing divides by anything that can be 0 (the tick rate is 1 to 1000, the sample count at least 1).

On the simulator (80 ms round trip, 10 ms jitter, 3 % loss, 5 % reordering) the estimate stays within one tick (16.7 ms) on average and 2.5 ticks at worst; the test pins both. That bound is for the simulator's impairments, which are a model (limits).

Snapshot interpolation PR #236

When a state update applies an entry to an object with a NetworkTransform, the client takes the transform's replicated values (GetReplicatedPosition, GetReplicatedRotation, GetReplicatedScale: the server's latest, whatever the object is showing) and the teleport serial, and gives them to the SnapshotInterpolator as a sample stamped with the message's tick. Every Update then shows each such object at (estimated server time - interpolation delay). The delay is NetworkClientOptions::interpolation.delayMicros (the network setting authoritative.interpolationDelayMs, 100 ms by default; 0 to 2 s; a host copies the setting into the option). Only the parts NetworkTransform replicates (replicatePosition, replicateRotation, replicateScale) are written to the transform.

  • Between two samples position and scale are linear and the rotation is a slerp along the shorter arc, normalised. A rotation that is not finite or has no length, or a position or scale that is not finite, is refused when it arrives (samplesInvalid); one that is merely not unit length is normalised.
  • Before the first sample the first is shown. After the newest the newest is held, as long as the stream has reached the render time (the newest tick of any state update or stream tick is at or after it): the server sends nothing for an object that did not change, so silence is not lateness.
  • A late snapshot (the render time is past everything the server has said) is extrapolated: from the newest sample by the velocity of the last two, for the time past the stream and at most maxExtrapolationMicros (250 ms), and then held at that point. Only the position is extrapolated. It is a guess: the next message with the object's real state replaces it, and it can jump. A jump (teleport) as the newest sample, or a single sample, has no velocity and is held.
  • A teleport (the sample's teleportSerial differs from the one before it) is never interpolated across: the object stays at the earlier sample until the time of the jump, then is at the jump.
  • When a move starts. If messages arrived after an object's last sample and before its next one without the object in them, the object was where it was until at least then: a "still here" sample is put at the last such message's tick, so the move spans the last interval and not all of the silence. A run of identical samples is two samples long whatever its length (the end of the run slides forward).
  • Out of order and repeated. Samples are kept in tick order; one out of order is put in its place; a second sample for a tick already held (from a later message) replaces the first; one older than the newest by more than 256 ticks is refused (samplesStale). Ticks are compared modulo 232 and the render time is reduced the same way, so a wrap of the counter changes nothing.
  • Bounded. At most 32 samples per object (maxSamplesPerObject, 4 to 64; the oldest is dropped, samplesDropped), samples nobody can need again are dropped as the render time passes them, and only objects of the client's own world get samples. A message tick more than 3600 ticks ahead of the newest, or more than 256 behind it, is a break in the server's tick count: every buffer is dropped and starts again (resyncs), so a hostile or restarted server cannot park a sample at the end of time. A render time or tick rate that is not a finite number shows the newest state.

On the client, and the hook for locally controlled objects PR #236

Bounds, limits and what is not verified PR #236

  • Rates. A client sends at most one ping per Update and no more often than every 20 ms (10 a second by default, then 2); the server drops a client above 32 a second. The server holds at most 8 unsent pongs per client and the client 8 pings awaiting an answer. All memory is fixed by the options: 64 samples in the estimator, 64 samples per object.
  • The delay has to cover the latency. The newest tick a client has heard trails the server by the network latency, up to one send interval (33 ms at 30 Hz) and up to one tick of truncation. With the default 100 ms delay a link whose one-way latency is over about 50 ms regularly has snapshots later than the render time, and those objects are extrapolated (guessed) for a moment. Raise authoritative.interpolationDelayMs for such links; there is no adaptive delay yet.
  • Extrapolation can be wrong. An object that was moving and whose snapshot is late is shown moving on for up to 250 ms; if it had stopped, it snaps back when the stream catches up.
  • Only NetworkTransform is interpolated. Other replicated fields are applied as they arrive. No Hermite interpolation with a replicated velocity (the design allows one; the transform carries none).
  • The clock does not run the client ahead of the server. Making an authoritative client simulate ahead by half the round trip plus input jitter, with time dilation, is not done by B6 either (prediction shows the owner's input at once without it). QueueInput still takes the tick from the game, which can now use ServerTick().

Design decision: a stream tick instead of a heartbeat entry, and a per-object "still here" sample PR #236

The delta replication of B2 sends nothing for an object that did not change, which means a client cannot tell "stopped" from "late" and would either extrapolate every stopped object or never extrapolate. The server now says how far its stream has got, in every state tick that has no state update for a client (5 bytes), and the client extrapolates only when the render time is past that. The alternatives were a state update with no entries (it would be acknowledged and change B2's accounting) and a longer interval of silence as the sign of lateness (it cannot be told from a world at rest). The cost is a small constant stream. The same ticks let the client know when a move really started (the "still here" sample), which keeps a start from being smeared over the whole silence before it.

Design decision: best-half median of 16, slewed, never backwards PR #236

The design asks for a median of the last N pings, a bounded correction and no jumps. A plain median of offsets is biased by every delayed sample, because a delay in one direction shifts the offset by half of it; keeping the half with the shortest round trips removes that. The estimate is slewed at up to 5 % instead of applied, so a changed estimate is never a visible jump; a large error (over 250 ms) is the exception and takes effect at once, with time standing still instead of going back. The sizes (16 samples, 5 %, 250 ms) are judgement calls for the simulator's links and are options.

Client prediction, reconciliation and smoothing B6

This is stage B6. A client that owns an object with a CharacterController moves it at once from its own input instead of waiting a round trip for the server, then corrects it when the server's state disagrees. Only the engine-owned character controller is predicted (design 3.3): its step is a pure function of (state, input, dt, scene queries), so a correction is "set the state to the server's, run the same step over the inputs the server has not applied yet". Dynamic rigid bodies are not predicted. The server stays the authority: the client's state is a guess that the next state update overwrites, and nothing the client computes is ever sent. Off by default (NetworkClientOptions::prediction.enabled).

What changed on the wire B6

kWireVersion rose from 6 to 7. This is the version of the world messages, not the editor protocol: the editor/engine protocol (1.x) is unchanged. The StateUpdate header grew from 11 to 16 bytes (kStateUpdateHeaderBytes): after the server tick come a u8 flags (bit 0: the next field is valid; the other bits must be 0) and a u32 input tick, the stamp (InputFrame::tick) of the newest input frame the server applied to the objects of the client the message is for. The states in the message include that input and none after it. The decoder refuses unknown flag bits and an input tick named without its flag (BadValue); the tick is 0 and ignored when the flag is clear. The server learns the stamp from NetworkServer::InputFor (ControlledInput::frameTick; a repeated input names the frame it repeats, neutral input names none) and keeps the newest one applied per client.

The replicated state of a controller B6

CharacterController registers three hidden, read-only replicated fields: the position (1 mm quantisation), the vertical speed and the grounded flag. SerializeReplicated refreshes them from the state before each send; on a client they hold the newest state the server sent (GetReplicatedState()). Horizontal velocity and the ground normal are results of a step and are not sent: a reconciliation starts from them at rest. Because the position is quantised, the comparison tolerance (positionEpsilon, 0.01) must stay above a millimetre.

The server's step B6

StepServerCharacter(server, object, map, tick, dt), called by the host once per fixed tick after SetCurrentTick and before Update sends, reads the owner's input for the tick (InputFor, so a missing frame is repeated or neutral by the server's policy), maps it with CharacterInputMap and steps the controller. An object the server owns, or whose owner left, steps with no input (gravity still acts). The mapping reads the layout's controls by name: a move Vector2 (world x and z, as a fraction of moveSpeed, cut to length 1 so a hostile client cannot exceed it) and a jump Button. The controller is marked externally driven so its own fixed update does not step it a second time.

The client: predict, compare, replay B6

  • Predict. QueueInput(tick, values) also steps every CharacterController of an object this client owns (at most 8), with the input after the layout's quantisation (the input the server will read), and records (stamp, input, state) in a ring of at most 128 ticks (PredictionHistory, fixed array). An object is not predicted until the server has sent its first state: that state sets the controller (an instance spawned by the client is not placed where the server's is, and stepping it from there would only be corrected away); the inputs of the ticks before are sent but not predicted, and the first comparison after that may show a small correction while the server's neutral start-up steps are caught up.
  • Compare. A state update carries the input tick; for each owned predicted entry the client keeps the newest by input tick. In Update, PredictionHistory::Reconcile compares the server's state with the history at that stamp: positions within positionEpsilon, vertical speed within velocityEpsilon, same grounded flag. Agreement drops the history up to the stamp.
  • Replay. Otherwise the controller is set to the server's state and the later inputs are run through CharacterController::Simulate (the same CharacterMotor::Step), at most one reconciliation per object per Update, at most 128 steps. The replayed states replace the history's.
  • Cases that are not a plain compare. A stamp the client never made, a tick between two samples, a non-finite state or one older than what was already confirmed is ignored and counted (statesIgnored). A stamp older than the history holds (the window overflowed) snaps to the server's state and drops the history. The same stamp twice (the server repeated a frame) replays from the state without a comparison. Ticks are compared modulo 232.

Smoothing B6

When a correction moves the state, the client records the difference between what was shown and the new state as an offset that falls linearly to zero over smoothingMicros (default 100 ms; the project setting network.authoritative.smoothingMs). With applySmoothing (default) every Update and every QueueInput puts the object at state + offset; otherwise the game reads PredictionOffset(id). A correction over snapDistance (default 1.0; snapThreshold) or a window overflow is a jump with no offset. A host copies the three project settings into PredictionOptions (smoothingMs, snapThreshold, and the tick rate for stepSeconds); nothing does it for it. predictionMaxMs is not used: the window is historyTicks (8 to 128).

Limits and what is not verified B6

  • The client does not run ahead by the clock. The game picks the stamps; the server applies a frame on stamp + its input delay. The prediction shows input at once whatever the stamps are.
  • A repeated frame is a correction. When a frame is lost the server repeats the last one, the client's prediction (which used the real input) differs, and the client is corrected and replays; this is by design and visible in PredictionStats::corrections.
  • The step must be identical. Client and server must use the same stepSeconds/dt, mapping and controller settings, and the client's physics scene must contain the same static colliders. RPCs: declared in C++ and Lua, with budgets and rate limits PR #241

An RPC is a named call on a component of a NetworkObject that runs on the other side of the connection. The declaration says who may call it, whether it is reliable and what its arguments are; the wire carries no names or types. The wire version rose from 5 to 6 because the RPC messages are new. Everything below is checked on the receiving side: the sending side's checks only save bandwidth.

Declaring an RPC PR #241

C++, next to the component's registration, with RegisterRpc<T, Args...>(typeName, name, &T::Method, RpcOptions{direction, reliable, cosmetic}). The method takes a const RpcContext & (the sender's client id, the object's net id, and whether the handler runs on the server) and then the arguments. Each argument type must map to a replicable kind (FieldTraits): bool, an integer, a float, a string, a vector, a quaternion, a colour or an enum registered with N2_SERIALIZE_ENUM. References (GameObjectRef, AssetRef) are refused: an RPC takes plain values. The declaration is checked (ValidateRpcDescriptor): a name of 1 to 32 letters, digits and underscores, at most 8 arguments, at most 32 RPCs per component type, and an encoded size under kMaxRpcMessageBytes (480). An invalid or duplicate declaration is refused and logged.

Lua, in a table next to SerializableFields:

local Gun = {}
Gun.__index = Gun
Gun.Rpcs = {
    Fire  = { target = "server", reliable = true,
              args = { "Vector3", { type = "float", min = 0, max = 10 } } },
    Shout = { target = "client", cosmetic = true, args = { "string" } },
}
function Gun:OnRpc_Fire(sender, dir, power) ... end   -- runs on the server
function Gun:OnRpc_Shout(sender, text) ... end        -- runs on the clients
-- calling:  self:Rpc("Fire", dir, power)   or   self:RpcTo(clientId, "Shout", "hi")

target is "server" (clients call, the server runs), "client" (the server calls, every client runs) or "owner" (the server calls, only the owner runs). reliable defaults to true, cosmetic to false. An argument type is one of bool, int, float, string, Vector3, or a table with type and, for an int or a float, min and max together (the value is clamped to them on both sides; a float with a range travels as 16 bits across it). The table is read from the script instance when first needed and again after the script is replaced; a malformed entry is logged and only that entry is left out. The handler gets the sender's client id (0 when the server called) and the arguments. self:Rpc and self:RpcTo raise a Lua error for an unknown name, a wrong number of arguments or a wrong type, and return whether the call was sent. A client calls only "server" RPCs, the server only the others.

What the receiver checks PR #241

In this order, the first failure ends it; every refusal is a counter in RpcStats and a throttled log line (the first five of a kind, then one in 1024), and none drops the client except a header that cannot be decoded:

  1. The header decodes (length at most 480, a known type byte, a net id that is not 0); otherwise the client is dropped as malformed. An RPC before the client has joined drops it as a protocol violation.
  2. Budget. The client's windows (below) admit it; otherwise droppedRate. The pending queue of the client has room (maxQueued); otherwise droppedQueueFull.
  3. Object and authority. The object exists (rejectedUnknown) and its owner is the sending client (rejectedAuthority). Objects the server owns have owner 0, which no client is, so a client can call nothing on them.
  4. The component index, the RPC index and the table hash match (rejectedUnknown).
  5. Direction. The server runs only ClientToServer RPCs (rejectedDirection for the others: the server never executes a server-to-client RPC a client sent), and the message arrived on the channel the RPC is declared for. A client runs only ServerToClient and, if it owns the object, ServerToOwner RPCs.
  6. Preset. Where cosmeticRpcsOnly is set, a non-cosmetic RPC is refused (rejectedSimulation).
  7. Arguments. Decoded with the field codecs (a string over 128 bytes, invalid UTF-8, a non-finite float, a truncated or over-long argument list are refused: rejectedArguments), then each value is checked with ValidateFieldValue and clamped with ClampFieldValue. Nothing is allocated from a count the message gives: at most 8 values of bounded size.

A call that passes is queued, not run. NetworkServer::Update and NetworkClient::Update run the queue right after the transport poll: the server's by client id ascending and, within a client, in arrival order, so the order does not depend on how the peers happen to be listed. The object, component and table are looked up again at that moment (any of them may be gone), and the handler runs under a guard: a C++ handler that throws, or returns false, is counted in handlerFailed; a Lua handler runs through the component's ordinary guarded call, in its own instruction budget, so an error is logged and a loop is stopped by the budget (the component is then switched off like any script that ran out) and neither reaches the server or the other calls.

Calling PR #241

NetworkServer::CallRpc(component, name, args, target, client) and NetworkClient::CallRpc(component, name, args) take one JSON value per argument and return an RpcSendResult: Sent, or why not (UnknownObject, UnknownRpc, WrongDirection, NotOwner, NoTarget, BadArguments, NotSimulationSafe, OverBudget). Design decision: the Deterministic preset allows cosmetic RPCs only PR #241

The design says an RPC that changes simulation state does not belong in a deterministic session: every peer must apply a command at the same tick, which is what the input stream is for. An RPC declares cosmetic (chat, an emote, a sound); with cosmeticRpcsOnly set on the server and client options, any other RPC is refused on send and on receipt and counted. The option is the host's to set from the preset. N2Server does not run the Deterministic preset yet and leaves it off.

Design decision: an RPC is addressed by position, not by a global id PR #241

The wire names an RPC by its component's position in the object and its own position in the component's name-sorted list, plus a 16-bit hash of that list, in the way a state entry is addressed by the object layout and its hash. A global id table would have to be agreed at join time and could not cover Lua RPCs, which are declared by a script instance. The cost is 4 to 6 bytes of header per call and a table hash that is 16 bits, not a proof.

What is not there, and what is not verified PR #241

  • No return values and no acknowledgement of an RPC; a reliable one arrives or the connection fails.
  • No client-to-client RPC: a client calls only the server, on objects it owns.
  • Lua arguments are bool, int, float, string and Vector3. C++ may use any replicable kind except the references.
  • The Lua RPC declarations are not in the join fingerprint (only the table hash of each message guards them).
  • The per-RPC and total windows are fixed windows, so a client can send up to twice a limit across a window boundary.

Lockstep relay, client runtime and the desync flow C3

The Deterministic preset (lockstep mode) runs as a star: every client has one n2net Connection to N2Server --relay and none to another client. Nothing of the world protocol is used; the session has its own small protocol (engine/include/engine/network/LockstepProtocol.hpp, wire version 2 since the rollback runtime and spectators added Spectate 0x63, SnapshotRequest 0x46, SnapshotData 0x64, SnapshotPart 0x47 and the NoSnapshot refusal; a version 1 client is refused at its Join; its own connection id) next to the n2net kinds the peers already had (input bundle 1, root 2, bisect request 3 and reply 4).

The relay (LockstepRelay)

  • Join and refusal. A client sends Join (protocol version, input payload size, layout hash). The relay answers Welcome (its slot, the slot count, input delay, tick rate, hash interval, drop fill, the neutral input) or Refuse (wrong version, layout mismatch, session full, session already running, protocol error). When every slot has joined it sends Start. N2Server reads input delay and hash interval from network.deterministic.* and the tick rate from the engine's real fixed step, round(1 / Time::GetFixedDeltaTime()). The same startup check that refuses a Deterministic project (physics.backend jolt in a strict-FP build, scalar SIMD, a Lua seed, ...) applies before the relay listens; in the normal (non-relay) mode N2Server now also sets cosmeticRpcsOnly for the Deterministic preset.
  • Forwarding and confirming. A client sends only its own slot's frames (an unreliable InputBundle, redundant like between peers). The relay feeds them into a LockstepScheduler of its own, so it knows which tick is confirmed (every alive slot's input has arrived), forwards every slot's frames to every other client from that client's acknowledged tick on, and acknowledges a client's own frames with its confirmed tick. It does not simulate: it compares the roots the clients report.
  • Drop. A slot the others have waited for longer than --relay-stall-ms, or whose client left or broke the rules, is handled per --relay-stall. drop: the relay runs DropSlot(slot, NextNeeded(slot)) (the first tick the slot has not delivered), broadcasts DropSlot on the reliable channel and disconnects the client. Every peer applies it before it can pass that tick, because it cannot pass it without the slot's input, and the relay forwards nothing from the slot at or after it; from that tick on the slot's input is neutral (or its last, per drop fill) on every peer. stop: Stop for everyone.
  • Hidden tab. A client may send Pause; a paused client's slot is not stalled before pausedGraceMicros (30 s). The runtime exposes SetPaused; nothing in the web build calls it yet.
  • Authority and bounds. A client can send inputs for its own slot only: a bundle for another slot, under another layout, with a payload the layout cannot produce, or two different inputs for one tick drops the client. Rate limits: bundles and reliable messages per second per client; at most 16 connections by default (--max-clients, at most 64); 16 checkpoint records; join timeout; the per-connection memory is the Connection's. Bisect messages are forwarded only after a desync stop, only between the two peers it names, at most 1024 per session, and only if they decode as a bisect request or reply.
  • After a session (everyone gone, or the linger over) the relay returns to waiting for the next one.
  • Spectators C6. A client may send Spectate (the body of a Join) before or after the start; it gets a Welcome whose slot is kSpectatorSlot (255), owns no slot, is never waited for or dropped as a stall, and its roots and inputs are not taken (a spectator bundle with frames drops it). Once the session runs, the relay sends SnapshotRequest to the lowest live player slot; the player answers with SnapshotData parts (at most 3584 bytes each) of a serialised snapshot of a confirmed tick; the relay checks them (in order, at most maxSnapshotBytes, 16 MiB by default, a tick still in its history and at most 128 ticks past its own confirmed tick, since a player may be ahead of the relay by its own frames in flight) and passes them to the spectator as SnapshotPart, paced by the spectator's reliable backlog (64 KiB). Awaited parts do not count against the message rate. From the snapshot's tick on, the spectator is sent every slot's confirmed input out of a history of 1024 ticks, a dropped slot's synthesised input included, so it needs no DropSlot; its ack-only bundles move it on, and one that falls 1024 ticks behind is dropped. If the source leaves before the snapshot is whole, the request goes to the next player; no snapshot begun within snapshotTimeoutMicros (10 s), or not whole within twice that, refuses the spectator with NoSnapshot. At most maxSpectators (4) at once; a spectator gets the Stop too. N2Server does not expose these options as flags (the defaults apply).

The client runtime (LockstepRuntime)

Transport-agnostic, so the same class runs over SimTransport in tests and a SecureTransport in the headless test client. Each Update pumps the connection and runs the SimulationClock (network mode Deterministic, the A2 accumulator) for the ticks that are due: it samples the local input (the values of an InputLayout, packed as a B4 payload) at most inputDelay ticks ahead of the simulation, submits it, and runs a tick only when TryAdvance says every slot's input is known; when it is not, the accumulator is reset so a stall is not caught up in a burst. After every tick whose number is a multiple of hashInterval it builds the host's state-hash tree (BuildStateHashTree for a NetworkWorld, or the host's own), keeps it in a HashTreeHistory and sends the root. Every confirmed tick is also recorded as an n2replay version 2 row.

Rollback mode C5 (LockstepRuntimeOptions::rollbackWindow 1 to 15, with the save and restore hooks): the same connection, relay, bundles, drop and stop, and a RollbackSession runs the ticks (below). Spectating C6 (spectate): the client sends Spectate, applies the player's snapshot through its join hook, starts its scheduler at the snapshot's tick (nothing pre-filled) and runs every confirmed tick the relay sends; it sends ack-only bundles and no roots. A player answers a SnapshotRequest through its save hook (without one it does not answer), with SerializeWorldSnapshot of a confirmed tick: in lockstep the world as it is after the ticks run so far, under rollback the ring's snapshot of the confirmed tick, or the world when nothing past the confirmed tick has run; the parts go out while its reliable backlog is under 64 KiB.

The desync flow (design N14: stop, never continue)

  1. Roots arrive at the relay; two different roots for one tick make the relay send Stop (reason desync, the tick, the two slots and their roots) to everyone and nothing else is simulated after it.
  2. The two named peers bisect against each other. Bisect is a synchronous loop, so it runs on a helper thread that is handed control one slice per Update (the caller never blocks and the two never run at the same time); the BisectClient sends through a sender function that wraps each request in a To envelope, the relay forwards it as From, and a BisectResponder on the other side answers from its history. On the web build (no threads) the bisection is skipped.
  3. Each of the two writes the n2desync report (peer, tick, both roots, build fingerprint, the first divergent object and field, the input log from tick 0 as an inline n2replay, the last K trees), keeps answering for desyncLingerMicros (the relay waits longer than that), and leaves. A third peer writes the report without a bisection.

Not verified

Rollback: world snapshots, parked spawns, events and input prediction C5

Rollback is lockstep that does not wait: a tick runs on the confirmed inputs it has and on a guess for the ones it does not, and when a late input turns out different from the guess, the world is put back to the state before that tick and the ticks since are run again with the real inputs. This first part of C5 is the whole engine-side mechanism, with no transport of its own: the world snapshot (RollbackWorld), parked spawns and despawns (NetworkWorld::Park), rollback-aware events (RollbackEventQueue) and the session state machine with prediction, the ring of snapshots and the bounded window (RollbackSession). The second part carries a session over the lockstep relay, selects it by network.deterministic.mode, detects desyncs over confirmed ticks, lets spectators join late from a serialised snapshot and drives Application's fixed loop (The relay-connected runtime). Design: 4.2 and 4.4 of orchestrator/proposals/netcode-runtime-design.md.

What a snapshot holds (RollbackWorld::Save / Restore)

A WorldSnapshot is the state before a tick runs. It holds:

  • The net object set in ascending id order, with each object's owner, spawned flag, prefab name and the GameObject's own active flag (the flag decides whether a Rigidbody's body is in the simulation), and the id counter (NetworkWorld::NextId), so a resimulation hands out the ids the first run did.
  • Every replicated field of every object, unquantised (CaptureObjectValues, ApplyObjectValues in ReplicationLayout.hpp): the JSON the component's SerializeReplicated writes, not the wire bytes, which are rounded by the codecs (a quantised field would come back rounded and the resimulation would drift from a run that never rolled back). A NetworkTransform is such a field set, so object poses are covered. Values go back through Component::ApplyReplicated.
  • The physics world as IPhysicsBackend::SaveState bytes (the Jolt backend, J6), when the backend supports snapshots; Restore then calls RestoreState and SyncTransforms. With no backend, or one without SupportsSnapshot, the snapshot has no physics part.
  • Random streams: the global seeded stream (Random::Seed; Random::SeededState and RestoreSeededState were added to read and set it, DeterministicRandom::State likewise), and any game-owned DeterministicRandom registered with RollbackWorld::AddRandomStream.

Lua state (the scope decision). A Lua script is part of the snapshot only through its declared replicated fields (replicated = true, written and read by LuaComponent::SerializeReplicated and ApplyReplicated), which is exactly rule 2 of the design's rollback contract. Locals, closures, upvalues and coroutines are not captured; a script that carries simulation state across ticks outside its declared fields will diverge after a rollback, and nothing but the desync detector will say so (design N7). The Lua interpreter's own state (its table hash seed, its RNG) is not saved either. Everything that is not a replicated field, a body or a random stream (audio, particles, UI, a component's non-replicated fields) is presentation and is left alone by Restore.

Restore checks everything that can be refused before it changes anything (an object of the snapshot that is neither registered nor parked, a replicated layout that changed since the snapshot, a random-stream count mismatch, a physics part without a capable backend) and then returns an error naming the cause. A failure inside the physics restore, or a component that refuses a value, is reported after the objects were already rewound: the session treats any error as fatal and stops.

Parked spawns and despawns

Inside the rollback window nothing is destroyed. Simulation code spawns with RollbackWorld::Spawn(prefab, owner, tick) (the next net id, then NetworkWorld::SpawnInstance) and despawns with RollbackWorld::Despawn(id, tick):

  • A despawn parks the object (NetworkWorld::Park): it leaves the registry (Find, Objects and Count no longer see it, so it is not replicated or hashed), its GameObject is made inactive (so a Rigidbody's body is disabled, not destroyed, which is what the physics parked-body contract asks for) and no OnDestroy runs. It keeps its id, owner and prefab. ReleaseConfirmed(oldestSnapshotTick) destroys it for good once no snapshot at or after its despawn tick is retained; the session calls it through the host's confirmed hook.
  • A restore parks every object that did not exist in the snapshot (the spawn is undone) and unparks every object of the snapshot that is not registered (the despawn is undone), then sets the active flags, then writes the fields, then restores the physics. The enabled bodies are therefore exactly the ones at save time, which is the contract RestoreState checks.
  • The pool: when the resimulation spawns, the id counter (restored) gives the id the first run used; if a parked object has that id and the same prefab and owner, it is taken back instead of instantiating a new one. Its transform, the local transforms of its whole hierarchy and its replicated fields are reset to what they were right after instantiation (captured at the first spawn), and every Rigidbody in it, on the root or on a child, is put back at its pose with no velocity. Because each body keeps its handle, the handle numbering (and so the physics state hash) stays equal to a run that never rolled back. A pooled object with a Rigidbody is handed out inactive and activated by CommitSpawns(), which the host calls where the scene's attach queue runs (end of tick, before Save), because the game sets the pose after Spawn returns and a fresh instance only gets its body at that point too. ReleasePool() destroys the parked spawns the resimulation did not claim (the session calls it through the host's resimulated hook). A spawned prefab with a Rigidbody on a child is pooled the same way (it was destroyed and recreated before the C5 follow-up); a parked object whose hierarchy changed shape since it was instantiated (children added or removed) is not reused: it is destroyed and a fresh instance is made, whose bodies' handles can then differ from a run that never rolled back.

Rollback-aware events

Effects the simulation triggers (a sound, a particle burst) go through RollbackSession::Events() (a RollbackEventQueue): Emit(netId, eventId, payload) inside the tick. An event is identified by its key (tick, net id, event id, occurrence among identical emissions in that tick). Two policies (RollbackConfig::eventPolicy):

  • Immediate (default): played the moment it is emitted, once. A resimulation that emits the same key with the same payload is recognised and not played again; one it does not emit again is cancelled (the cancel handler runs); a new one is played; the same key with another payload cancels the old and plays the new. An event becomes final, and can never be cancelled, when its tick is confirmed.
  • OnConfirm: played only when its tick is confirmed, in key order. Never cancelled, a few ticks late; the choice for effects that cannot be taken back.

The log holds an event only from its tick until the tick is confirmed, so it is bounded by the window.

The session: input, prediction, misprediction, resimulation

RollbackSession has no transport and no clock. The host submits the local player's input with SubmitLocal (for tick current + inputDelay, as in lockstep; the first inputDelay ticks are neutral for every slot) and the other slots' with SubmitRemote(slot, tick, input) (from InputBundles, or anything else), and calls Advance() for each tick that is due. It reports SubmitResult like the lockstep scheduler (Accepted, Duplicate, Conflict (the first stays), TooOld, TooFar, BadSlot, BadPayload).

  • Prediction. A tick whose input from some slot is not confirmed runs on that slot's last confirmed input (the design's default), or the layout's neutral input if it has none; RollbackHost::predict replaces the guess. The input a tick actually ran with is remembered per slot.
  • Misprediction detection. When a confirmed input arrives for a tick that already ran, it is compared with the one used; if they differ, a rollback is scheduled for the oldest such tick. An input equal to the guess costs nothing.
  • Resimulation. The next Advance restores the snapshot taken before that tick, resimulates up to the present (confirmed input where known now, a fresh guess elsewhere), saving the snapshots of the resimulated ticks again, and then runs the new tick. Events and the pool are finalised around it (BeginResimulation/EndResimulation, resimulated).
  • The ring and the window. A snapshot is saved before every tick that could still be rolled back to, in a ring of rollbackWindow + 2. At most rollbackWindow (0 to 15, design 4.2) ticks may run past the confirmed tick (the first tick whose inputs are not all confirmed and used); beyond that Advance returns WindowFull and the session waits, so a rollback never resimulates more than the window. A tick run on fully confirmed input right behind the confirmed tick takes no snapshot (it can never be rolled back to).
  • Window 0 is lockstep: it never guesses (WaitingForInput until every input is in), saves nothing and cannot roll back.

The result after all inputs are in is the state a lockstep session reaches with the same inputs; the test checks that with the state-hash tree root and every replicated field, exactly.

What the host and the game must do

  • The step must be a pure function of the state and the inputs (lockstep's rules, section 4.3 of the design), and must put all simulation state in what a snapshot holds (replicated fields, bodies, random streams, the object set). Spawn and despawn through RollbackWorld.
  • Save and Restore run at a tick boundary, after a complete step: the scene's attach and destroy queues processed, CommitSpawns called, and (physics) ProcessCollisionCallbacks done, because the Jolt backend refuses to save with an undelivered Exit. Anything pending in the backend that is not state it saves (queued gravity, for one) is the host's to apply before Save.
  • Ticks are plain 32-bit counters from 0; the rollback session does not duplicate the lockstep scheduler's wrap-around handling.

The relay-connected runtime, the mode switch, desync detection, spectators and the fixed loop C5 C6

  • Over the relay. LockstepRuntime with rollbackWindow 1 to 15 and the save and restore hooks (optional: confirmed, resimulated, predict, eventPolicy) is the rollback client of the same LockstepRelay: the join, the welcome, the bundles, the acknowledgements, DropSlot, Stop and the desync flow are lockstep's, and the relay does not know which mode a client runs, so rollback and lockstep peers can share one session. The lockstep scheduler still collects every confirmed input (it drives the bundles and acknowledgements, applies DropSlot and feeds the n2replay recorder, so a rollback peer's replay is the confirmed input stream). Each remote frame is also given to the RollbackSession as it arrives, and every tick the scheduler confirms is given to it again with every slot's input (a dropped slot's synthesised input arrives this way). The session runs the due ticks: on a guess where an input is missing, at most the window past the confirmed tick; WindowFull waits like a lockstep stall (the accumulator is reset).
  • The mode switch. RollbackWindowFor(settings) (NetworkSettings.hpp) is network.deterministic.rollbackWindow (clamped to 0 to 15) for the Deterministic preset with deterministic.mode rollback, and 0 (lockstep) for lockstep mode and every other preset. RollbackRuntime takes it from the project's NetworkSettings; with a physics backend whose SupportsSnapshot() is false it runs lockstep and logs a warning (the startup check already refuses such a Deterministic rollback project).
  • Desync detection over confirmed ticks. Under rollback the tree of checkpoint tick C is built every time the world reaches C (again after each resimulation), kept aside, and its root is sent, and the tree put in the history the bisection answers from, only once every tick before C is confirmed and was run with the confirmed inputs. That is the state a lockstep peer hashes at C, so a rollback peer reports confirmed state only and agrees with lockstep peers. RollbackRuntime builds BuildStateHashTree(world, layouts, tick, physics): the replicated fields plus a physics leaf (object 0, field kPhysicsFieldId 0xFFFD) holding IPhysicsBackend::HashSimulatedState(), which on Jolt hashes each body in the simulation on its own (kind, pose, velocities, awake flag; parked, disabled bodies are skipped, handle numbers are not hashed) and combines them by an order-free sum with the body count. A rollback peer that keeps despawned bodies parked, or took a pooled body back, therefore hashes like a lockstep peer that destroyed and recreated them. HashState itself is unchanged (it still counts parked bodies, in handle order). Every peer of a session must build the same tree: a plain LockstepRuntime host that uses the three-argument BuildStateHashTree (no physics leaf) does not agree with a RollbackRuntime peer.
  • The serialised snapshot. SerializeWorldSnapshot / DeserializeWorldSnapshot (RollbackWorld.hpp): magic N2WS, format 1, tick, id counter, random streams, each object (id, owner, spawned and active flags, prefab, layout hash, the replicated fields as CBOR with a written value as [value] and an absent one as null, and the root Rigidbody's body state, now also captured by Save), the physics bytes and an FNV-1a 64-bit checksum, little-endian; at most 64 MiB, 4096 objects; every length is checked before it is taken. The physics part is still the backend's own bytes (same build, same bodies).
  • Late join and spectators. RollbackWorld::RestoreForJoin takes another peer's snapshot into a world bound to the same scene: registered objects the snapshot does not hold are despawned, spawned objects it holds are instantiated under their ids, the scene's attach and destroy queues run, then the objects, fields, id counter and random streams are restored as by Restore. The physics part goes to RestoreState; when the backend refuses it (its bodies are not the snapshot's: other slots, generations or Jolt ids, as after bodies were destroyed and recreated on the other peer) the root Rigidbodies are set from the snapshot's body states instead and exactPhysics is false (RollbackRuntime then warns: such a view may drift, and a spectator reports no roots, so nothing would stop it). Late joining is for spectators only: a client cannot take a player slot after the start, nor rejoin a dropped one.
  • Application's fixed loop. RollbackRuntime (RollbackRuntime.hpp) puts it together: a LockstepRuntime in the mode the settings select, a RollbackWorld over the scene's NetworkWorld and its physics backend, and Application::SetFixedTickDriver: while a driver is set, Application::Tick calls it with the frame's unscaled delta in place of its own fixed steps and clears the clock's accumulator after it. Each tick (confirmed, predicted or resimulated) sets the tick counter to the tick (SimulationClock::SetTick, so Time::GetTick() inside a resimulated tick's FixedUpdate is what the first run saw), runs the host's applyTick (where the game takes the tick's inputs), Application::StepTicks(1), then the end of tick a snapshot needs: the attach queue, CommitSpawns, the destroy queue. Save, restore, ReleaseConfirmed, ReleasePool, the tree and RestoreForJoin are wired to the RollbackWorld. With SimulationMode::None the constructor switches the Application to Deterministic; the destructor gives the loop back. The game must step only in applyTick and in components' FixedUpdate, and spawn and despawn through RollbackRuntime::World().

The editor's Network panel (B11, host side)

The editor chooses a project's network model through three presets, none, authoritative (Server authoritative) and deterministic (lockstep or rollback), stored as network.preset (the preset table and the startup checks). Protocol 1.21.0 gives the editor host three commands for a panel over it (Editor protocol): GetNetworkSettings (the settings, the three bundles row by row with locked, tunable, the value and its source, the customised state, whether the Deterministic card can be chosen and the reason if not, and the nudge), SetNetworkSettings (the preset and the tunable network settings, through the SetProjectSettings write path, taking effect at the next start) and GetNetworkValidation (the requirements of the Deterministic preset with met or unmet and the reason, mechanical fixes as settings patches, and the warnings of Server authoritative). The report is the engine's own ValidateNetwork run without starting anything, so what it calls unmet is what Application::Init would refuse to start on (design decision D4). The Deterministic card stays disabled with the reason until the project's physics backend declares what the preset needs (decisions D1 to D3; the backend picker, protocol 1.20.0).

The nudge is a hint, never a block: when the preset is none and the open scene has NetworkObject components, or the project's network block holds settings, GetNetworkSettings says so and the frontend may show the non-blocking "this project has no network model" panel of the design. The editor does not run a networked session; nothing in this host starts a server or a client. Historical hit queries (B8)

The server records opt-in LagCompensatedHitbox components once per simulation tick. The component's shape is sphere, capsule or box; centre, endpoint (capsule end-sphere centre), halfExtents and radius are local geometry. World position, rotation and scale are captured, with the object's layer. Nonuniform scale uses the largest absolute axis for sphere/capsule radius. Invalid or inactive hitboxes are omitted. These are query shapes, independent of physical colliders.

Physics::RaycastLagCompensated(server, clientId, renderTimeMicros, origin, direction, maxDistance) and SphereCastLagCompensated(..., maxDistance, radius) return an optional hit with net id, hitbox index, distance, point, normal and query time. The time is an absolute value on the monotonic microsecond clock passed to NetworkServer::Update. Convert the client's estimated render time to that clock; it is not a wall-clock timestamp or a duration. The requester must be a joined client with a measured RTT. The server clamps rewind to both its measured RTT and lagCompMaxMicros (default 200 ms, hard maximum 1 s); it never trusts a client-supplied latency.

Positions, extents and radii interpolate; rotations slerp. A changed NetworkTransform teleport serial holds the earlier pose until the teleport sample. The latest pose is held between simulation samples, for at most the history window. History is bounded to 256 frames on a server and 4096 shapes per frame. Despawn erases an object's history. A query without history at its bounded time misses. Casts solve sphere/capsule quadratics and box face intersections analytically. Sphere sweeps use the rounded box (face patches and edge capsules), rather than an inflated box approximation. Live physics actors are never moved.

For custom hitboxes, disable NetworkServerOptions::autoCaptureHitboxes and call CaptureHitboxes after each tick. Shapes must name registered net ids. BindPhysicsQueries selects the server used by Lua (N2Server does this); destruction clears the binding. Game server code must use the authenticated RPC sender as requester, and must validate shot origin/direction and game rules.

Source: LagCompensation.cpp, LagCompensatedHitbox.cpp, NetworkServer.cpp; tests: LagCompensationTests.cpp.

Relevance, priority and snapshot budgets (B9)

NetworkObject::SetInterestPolicy({Relevance::Radius, 100, 1}) chooses relevance, radius and priority. Defaults are Always, radius 100 and priority 1. OwnerOnly sends state only to the owner; Radius also sends to observers inside that object's radius. Owners always receive their own state. NetworkServer::SetObserver(clientId, netId) assigns an observer owned by that joined client; a missing, destroyed, unpositioned or foreign observer grants no radius visibility. Always objects need no observer.

A uniform grid is rebuilt each snapshot tick. Large radii use a scan of the bounded object list rather than an unbounded grid walk. Each client has an independent accumulator: priority is added each snapshot and reset when an entry is selected. Higher accumulators go first, with ascending net ids breaking ties. Deferred entries retain their accumulated priority. ServerReplicationOptions::maxBytesPerTick limits total StateUpdate bytes, including every header; zero uses the message-count/size bounds. An entry larger than the budget cannot be sent until the host raises it. This budget covers field snapshots, not reliable lifecycle/visibility traffic.

Reliable Visibility messages hide irrelevant objects and restore their server active flag on re-entry. Hidden objects keep their client instances; existence, prefab identity and shared scene data are not secret. Their new fields are withheld, references to hidden objects encode as null, and their acknowledged baselines and outstanding baseline entries are removed. Re-entry sends full fields. Already delivered data cannot be revoked. World wire version 3 adds Visibility (type 0x20, u32 net id, u8 visible, u8 active; booleans must be 0 or 1).

Lua server scripts use Network.SetInterestPolicy(gameObject, "radius", radius, priority), Network.SetObserver(clientId, gameObject) and Network.ClearObserver(clientId). Calls return false without a bound server or a valid server-world object. A bad policy name raises a Lua error.

Browser WebSocket transport (B10)

WebSocketTransport::Connect(url, token, protocolId, error) is the Emscripten client API. It requires wss, except ws on localhost/127.0.0.1 for development. The token goes in the first binary message, never the URL. The native listener authenticates it against the join-token table before emitting PeerConnected. Browser transport security is TLS through the browser, rather than the native UDP secure packet format.

Start N2Server with --websocket-port 7778 --websocket-origin https://game.example. The TCP listener binds only 127.0.0.1, independently of the UDP bind. A TLS-terminating reverse proxy exposes the public wss endpoint and forwards WebSocket upgrade headers to it. The exact browser Origin must match the configured value; default empty permits only requests with no Origin (tools). The ready line appends websocketPort=<port>. Port zero selects a free port; omitting the flag disables the listener.

UDP and WebSocket peers share one NetworkServer via MultiplexTransport, with separate authenticated peer ids. Stream peers skip the packet layer's resends while keeping its sequence and acknowledgement checks. Each WebSocket binary message is one datagram (1 to 1200 bytes). The listener accepts masked frames only, supports binary fragmentation and ping/pong, and refuses text and oversized messages and negotiates no extensions. HTTP headers are capped at 4 KiB, input at 8 KiB per peer, queued output at 300 KiB, authentication at 5 s, idle connections at 30 s, and accept work at 64 connections/s and 16 per poll. Peer and frame-processing caps also bound each poll. Saturating a stream queue disconnects it instead of silently dropping a reliable packet. Browser receive queues are capped at 256 events and outgoing browser buffering at 300 KiB.

TCP loss stalls subsequent traffic, including snapshots and inputs. The Node smoke and an actual Emscripten client run against the native listener in CI. The optional scripts/websocket-browser-smoke.mjs runs the same client in an isolated Chrome/Edge profile; the desktop Chrome loopback check has passed. Public certificates, proxy configuration and real-browser behavior still require deployment checks; no certificate is generated automatically.

Source: WebSocketTransport.cpp, MultiplexTransport.cpp, n2server/src/Server.cpp; tests: N2NetWebSocketTransportTests.cpp, scripts/websocket-smoke.mjs, tests/web/WebSocketClient.cpp. Protocol: RFC 6455; browser API: Emscripten websocket.h.

What is not there yet

  • Browser networking uses the WebSocket transport; UDP uses SecureTransport. WebRTC/WebTransport remain later work.
  • The handshake agrees no connection id and no settings. ConnectionConfig's ids and window are still configured on both sides (the world layer uses a constant connection id and the defaults, above). See also the secure layer's limits.
  • Not there yet: general prediction and lockstep. C5 The rollback mechanism (snapshots, parked spawns, events, input prediction with resimulation) runs over the lockstep relay, with spectators that join late from a snapshot and a runtime that drives Application's fixed loop, but no shipped host starts one (Rollback). PR #241 RPCs are there (RPCs). PR #232 Player input is (Player input), but nothing samples a real keyboard or gamepad into it, and B6 the character controller of an owned object can be predicted and reconciled (Client prediction); PR #236 the client now has a clock estimate (Clock sync and interpolation), but QueueInput still takes the tick from the game: nothing runs the client ahead of the server yet. PR #224 The network world replicates that objects exist (The network world) and, PR #226, the server-owned fields they mark replicated (Field replication); the rest are the netcode's later stages.   • No prefab files. Prefabs are registered in code; a project has no prefab asset, so a plain N2Server has an empty prefab table (above).
  • No congestion control and no flow control beyond the unit window.

Not verified

The secure layer has had no review beyond its tests and its author yet. Whether the window, the 32-packets-per-round-trip rule and the timeouts are good defaults for real games is untested.
