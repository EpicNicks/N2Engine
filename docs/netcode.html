Netcode: the n2net library

n2net is the netcode's lowest layer: a transport interface, an in-memory network simulator, and a packet layer on top of datagrams (acknowledgements, a reliable-ordered channel, an unreliable-sequenced channel, fragmentation of large reliable messages). This page describes what exists in master now. Its one real network transport is UdpTransport (native UDP sockets, Windows and Linux), and SecureTransport puts a connection handshake, join tokens and authenticated encryption of every packet over it (The secure layer), and N2Server runs that stack in a headless process of its own PR #PRNUM (The dedicated server); the packet layer is not wired to the engine's objects yet (see What is not there yet).

What exists and where it lives PR #197

The library is the CMake target n2net (alias N2Engine::n2net), a static library defined in engine/CMakeLists.txt. Its headers are under engine/include/engine/network/n2net/ and its sources under engine/src/network/n2net/. The engine target excludes that source directory from its glob and does not link n2net; only engine_tests does. Apart from UdpTransport, SecureTransport and the join tokens (which use n2security, below) it uses the standard library only: no sockets, no threads, no platform headers, no engine types, no global state, no exceptions across its API (errors are return codes), and it reads no clock (every time is passed in as microseconds). UdpTransport is the one exception: it includes the BSD socket or Winsock headers (ws2_32 is linked on Windows), still starts no thread, and reads the steady clock only to age out idle peers. Its whole class is compiled out under Emscripten (N2NET_HAS_UDP is 0), so the library, apart from that class, still builds the same on Windows, Linux x86_64 and arm64, and in the single-threaded web build.

Everything is single-threaded and polled.

Design decision: our own small reliability layer, not a networking dependency PR #197

The netcode design (decision N2) chose to write the packet layer here rather than adopt ENet, GameNetworkingSockets or yojimbo. The browser transports, the security model and the simulator all have to be ours anyway, and the reliability layer is the small part. No new third-party dependency is added by this library.

The packet format PR #197

One datagram is a 17-byte header followed by blocks, at most 1200 bytes in all. All integers are little-endian, read and written byte by byte, so the format does not depend on the host's endianness or alignment.

Header (17 bytes)

OffsetSizeFieldMeaning
0u32protocol idWhat the receiver expects (a protocol version and game build identifier chosen by the caller); any other value drops the packet.
4u32connection idThe receiver's connection; any other value drops the packet. Configured, the same on both sides (a later handshake will agree it).
8u16sequenceThis packet's number: +1 per packet sent, wrapping at 65536. The first one is ConnectionConfig::initialSequence.
10u16ackThe newest packet number received from the other side. Valid only if flags bit 0 is set (written as 0 otherwise).
12u32ack bitsBit i set: packet ack - 1 - i (modulo 65536) was received too. Written as 0 when there is no ack.
16u8flagsBit 0: ack and ack bits are valid. Bits 1 to 7 are reserved and must be zero.

Blocks

After the header come blocks, back to back to the end of the datagram. A datagram may have none (an ack-only or keep-alive packet).

Guarantee: a malformed packet changes nothing

A datagram is parsed completely before anything in it is applied. An unknown block type, a length of 0, a length past the end of the datagram or past the block's cap, a reserved bit set (in the header flags or the unit flags), a truncated header or block, or bytes left over after the last block makes the whole packet malformed: it is dropped without effect (no acknowledgement, no delivery, no state change other than the rejection counters). The connection: acknowledgements and channels PR #197

A Connection is one end of a connection. It is built from a ConnectionConfig and the current time, and has four calls: SendReliable and SendUnreliable queue a message (copied); OnPacket(now, datagram, handler) processes one received datagram and delivers any messages it completes to the handler (which may send, but not call OnPacket or Update); Update(now, sender) resends what is due, sends what the window allows, acknowledges, sends keep-alives, and calls sender once per packet (the span is valid only during the call). Update produces at most maxPacketsPerUpdate (default 64) packets per call. The configuration is sanitised on construction: sizes, windows and times are clamped into safe ranges whatever the caller passed.

Packet numbers and acknowledgements

Every packet carries a 16-bit sequence number. Ordering uses wraparound arithmetic: a is more recent than b when it is 1 to 32767 steps ahead modulo 65536; a difference of exactly 32768 counts as neither. The receiver remembers the last 256 packet numbers in a ring and answers every packet with the newest number it has seen (ack) and a 32-bit mask of the 32 numbers before it (ack bits), Gaffer-on-Games style.

  • A packet number already seen is dropped as a duplicate (DuplicatePacket); one 256 or more behind the newest is dropped as TooOld. A jump forward of 256 or more clears the ring, so stale entries cannot be mistaken for new packets.
  • A packet that carries blocks makes the receiver send an acknowledgement on its next Update; a duplicate of such a packet does too (the peer is resending, so the ack was probably lost). Packets with no blocks (keep-alives, ack-only packets) are not themselves acknowledged and are not counted in the loss figures.
  • A packet is declared lost when its deadline passes (the RTO, below), when it is three or more sequences behind the newest acknowledged one (a single ack of a later packet suffices), or when its slot in the sender's 128-entry ring is needed again. A packet declared lost and acknowledged later is reclassified (counted in packetsAckedLate), and any pending resend of its units is cancelled.
  • Because the ack bits reach back only 32 packets, a sender never leaves more than 32 data packets unanswered: while the oldest unanswered packet is 32 or more behind, packets go out with no blocks. That is at most 32 data packets per round trip.

The RTT estimate follows RFC 6298 in integer microseconds: smoothed RTT and variance, RTO = smoothed + max(1 ms, 4 × variance), clamped to [minRtoMicros, maxRtoMicros] (defaults 50 ms and 2 s); before the first sample the RTO is initialRtoMicros (200 ms). A sample is taken from the packet named by each received ack field, never from the ack bits. A resend's deadline backs off by doubling per retry up to 16 times the RTO, capped at the maximum RTO.

The reliable-ordered channel

Reliable messages are cut into units (see Fragmentation). The units form one numbered stream (16-bit unit ids, starting at initialUnitId, which must be the same on both sides). Each unit is resent until acknowledged and delivered in order, so a message reaches the handler whole, exactly once, in the order it was sent, whatever the link does short of ending the connection.

  • Resends happen when the packet that carried a unit is declared lost; they go out oldest first, before new units, at the next Update.
  • Window. At most reliableWindow units are in flight (sender) and the receiver buffers units only up to that many ahead of the next one it expects; a unit further ahead is dropped (unitsOutOfWindow). With equal windows on both sides an honest peer never sends one; the window is not negotiated yet, so both peers must be configured with the same reliableWindow, because the packet carrying a dropped unit is still acknowledged and the unit is not resent. The configured window is clamped to 1 to 1024 and rounded down to a power of two (default 256), so unit ids map to slots without collisions across the 65536 wrap.
  • Queue. SendReliable fails with QueueFull when the bytes queued and not yet packetised would pass maxSendQueueBytes (default 256 KiB); the caller retries later. Other results: Empty, TooLarge (over maxMessageSize), ConnectionFailed.
  • Congestion. There is no congestion control. The unit window and the 32-packets-per-round-trip rule are the only things that slow a sender.

Guarantee: exactly once, in order

Over a link that loses 30% of datagrams and also reorders and duplicates them, every reliable message queued is delivered exactly once and in the order it was sent, and the connection ends idle. Tests: ReliableUnderThirtyPercentLossWithReorderingAndDuplication, TenThousandMessagesEachWayOverALossyLink, AWindowOfOneStillDeliversUnderLoss.

Fragmentation and its limits

A reliable message larger than one unit is cut into units of up to 1177 bytes (with a smaller ConnectionConfig::maxPacketSize PR #210, up to that size less 23: 1152 over SecureTransport, whose packets have 25 bytes of their own; an unreliable message may then be up to that size less 22, MaxUnreliableMessageSize(), and the setting is clamped to 128 - 1200 bytes); the first carries the "first" flag, the last the "last" flag, and a message that fits in one unit has both (the smallest message, 1 byte, is a 24-byte packet: 17 + 6 + 1). Units are numbered in sequence, so the receiver reassembles by delivering them in order; units that arrive out of order wait in the window until the gap fills. Every limit below is enforced, and a configuration that asks for more is clamped.

The unreliable-sequenced channel

SendUnreliable queues a message of 1 to 1178 bytes (never fragmented). Each one is sent once, in a later Update, with a 16-bit message sequence number that increments per message and is never resent. The receiver delivers a message only if its sequence is more recent (wraparound rules, as above) than the newest it has delivered; an older or equal one is dropped and counted in unreliableStale. So the stream the handler sees only ever moves forward: newest wins, stale is dropped, and a lost message is simply never delivered.

The send queue holds at most maxQueuedUnreliableMessages (default 64) messages and maxQueuedUnreliableBytes (default 64 KiB); beyond either the oldest queued message is dropped (unreliableDropped). Unreliable messages share packets with reliable units, after them, only if they fit.

Stream transports

With ConnectionConfig::reliableStream set (what ITransport::IsReliableStream() reports), the connection never resends and keeps no copy of sent units, and has no unit window. Packet numbers and acks are still sent and received (for RTT and ordering checks); a packet unanswered past its deadline is not counted as lost. Units must arrive exactly in order: any other unit id ends the connection with ProtocolViolation.

Failure, timeouts and statistics

A connection can fail, and then stays failed: IsFailed() and Failure() report why, every buffer it held is released, Update produces nothing, sends return ConnectionFailed and OnPacket returns ConnectionFailed. There is no recovery; the owner ends it and starts a new connection.

FailureReasonWhen
TimeoutNothing was received for idleTimeoutMicros (default 10 s), checked in Update.
ReassemblyStallPartly received reliable data made no progress for reassemblyTimeoutMicros (default 5 s).
MessageTooLargeA received message grew past maxMessageSize.
ProtocolViolationThe peer sent reliable units that cannot be a legal stream.

To keep the link alive, Update sends an empty packet when nothing else was sent for keepAliveMicros (default 1 s), and an acknowledgement-only packet when blocks were received. OnPacket returns a PacketStatus naming what it did with the datagram: Ok, TooLarge, BadHeader, WrongProtocol, WrongConnection, Malformed, DuplicatePacket, TooOld or ConnectionFailed; only Ok means it was processed.

Connection::Stats() counts, among others: packets and bytes sent and received; packets rejected, malformed, duplicate; packets acked, acked late and lost; units sent and resent; reliable and unreliable messages delivered; stale and dropped unreliable messages; duplicate and out-of-window units. Rtt() gives the smoothed, latest, minimum and variance of the round trip and the current RTO. LossRatePpm() is packets lost over packets settled (acked or lost), in parts per million. ReliableBacklogBytes() and ReliableIdle() report what reliable data is still unacknowledged.

Untrusted input and bounded memory PR #197

This layer will face the internet, so every byte that arrives is treated as hostile.

  • Every length is checked before data is taken. ByteReader never reads past the end whatever lengths the bytes claim: a failed read returns 0 or an empty view and sets a flag. ByteWriter never writes past its buffer. A block's length is checked against the bytes that remain and against its cap before the data is viewed.
  • Validate, then apply. OnPacket checks size (at most 1200), header, protocol id, connection id and the whole block structure before it touches any state. A packet has at most 197 blocks (the smallest, an unreliable message of one byte, takes 6 bytes of the 1183 after the header), so the work per datagram is bounded.
  • No unbounded allocation. What a peer can make a connection hold is bounded by the configuration, not by what the peer sends: the receive window (units), the message size cap, the send queue, and the unreliable queue. MemoryInUseBytes() reports the payload buffers held now and MemoryBoundBytes() what that can never exceed under the configuration (1,664,000 bytes with the defaults); the tests assert the first never passes the second, including while a peer floods maximum-size units at every unit id.
  • No loops driven by input. There are no length-prefixed repeat counts: loops run over the bytes of one datagram, over fixed-size rings (32 ack bits, 128 sent packets, 256 received numbers), or over the window.
  • Time arithmetic cannot wrap. Configured times are clamped to about 12 days and RTT samples to the same order, so no deadline or backoff shift overflows.
  • Errors are values. Nothing throws on bad input. A bad datagram is a PacketStatus; a peer that breaks the stream rules ends its connection with a FailureReason.

The ids are not secrets: authentication is the secure layer's job

The protocol id and connection id only filter out stray traffic; they are not keys. Over a plain transport, anyone who can send datagrams to a connection and knows or guesses the two ids and a plausible sequence number can inject packets. Over SecureTransport PR #210 every datagram the Connection sees has passed an authentication tag (The secure layer); over a plain one this layer is for tests and loopback development, not for an exposed port. The handshake does not agree the connection id yet: both sides still configure it.

The network simulator PR #197

SimNetwork is a deterministic in-memory network for tests; it is what every later netcode test runs on. It creates endpoints (SimTransport, an ITransport) with ids 1, 2, 3 in creation order; Link(a, b, config) connects two of them (each side then gets a PeerConnected event) with a separate SimLinkConfig per direction if wanted. Time is the network's virtual clock: NowMicros() starts at 0 and only Advance(micros) moves it. A datagram is scheduled when sent and handed out by SimTransport::Poll once the clock has reached its delivery time; Poll never moves time. Nothing sleeps and nothing reads a wall clock.

What a link can do

All times are virtual microseconds and all probabilities are parts per million (1,000,000 = always), so the simulation is integer-only. The default SimLinkConfig is a perfect link.

FieldEffect
latencyMicros, jitterMicrosFixed one-way delay, plus a uniform extra delay in [0, jitter].
lossPpmIndependent loss.
burstEnterPpm, burstExitPpm, burstLossPpmBurst loss, a two-state model: in the good state a datagram moves the link to the burst state with probability burstEnterPpm; in the burst state it moves back with probability burstExitPpm, and a datagram is lost with probability burstLossPpm (default 100%) instead of lossPpm. burstEnterPpm 0 never bursts.
reorderPpm, reorderDelayMicrosWith probability reorderPpm a datagram is delayed by a further 1 to reorderDelayMicros, so later datagrams overtake it. A reorderDelayMicros of 0 never reorders this way (jitter can still reorder).

bandwidthBytesPerSecond0 is unlimited. Otherwise datagrams are serialised at this rate: each waits for the ones before it and takes bytes × 106 / rate microseconds (rounded up).

SetLinkConfig changes one direction's config while it runs (its burst state and random stream continue); Unlink removes a link without telling the other side (datagrams in flight on it are dropped when due, even if the pair is linked again before then), whereas SimTransport::Disconnect removes it and gives the other side a PeerDisconnected; GetLinkStats(from, to) returns per-direction counters (submitted, dropped by loss, by queue limit, or because the link was removed, duplicated, reordered, delivered).

Determinism

Guarantee: the same seed and the same calls give the same bytes on every platform

The simulator's random numbers come from SimRandom, xoshiro256** seeded through SplitMix64, written out in the library with integer arithmetic only (not std::random_device or the standard distributions, whose output differs between standard libraries). Each link direction has its own stream derived from the seed and the two endpoint ids, so adding a link does not change what another link does. Every datagram consumes the same seven random draws in the same order whatever the configuration and whatever its fate, so changing one impairment does not change what another decides for the same datagram. Delivery order is fully determined: events are keyed by delivery time and then by the order the datagrams were sent. Tests: SameSeedSameBytesDifferentSeedDifferent, AnotherLinkDoesNotDisturbThisOne, AnImpairmentDoesNotShiftAnothersDecisions, StreamIsFixedAcrossPlatforms, and the two golden traces under Tests.

Using it in a test

Create a network with a seed, add endpoints, link them, and give each side a Connection. Each step: advance the clock, poll each endpoint into its connection, then update each connection into its endpoint. This is a complete, compiling example:

SimNetwork network(1234);
SimTransport &a = network.AddEndpoint();
SimTransport &b = network.AddEndpoint();

SimLinkConfig link;
link.latencyMicros = 40'000;
link.jitterMicros = 10'000;
link.lossPpm = 300'000; // 30%
link.duplicatePpm = 50'000;
network.Link(a.Id(), b.Id(), link);

ConnectionConfig config;
config.protocolId = 0x4E32'4E54;
config.connectionId = 7;
Connection connA(config, network.NowMicros());
Connection connB(config, network.NowMicros());

const std::vector<std::uint8_t> hello = {'h', 'i'};
connA.SendReliable(hello);

const auto onMessage = [&](MessageChannel, std::span<const std::uint8_t> message) { /* use it now: copy what you keep */ };
for (int step = 0; step < 2000; ++step)
{
    network.Advance(1'000); // the only thing that moves time
    const std::uint64_t now = network.NowMicros();
    a.Poll([&](const TransportEvent &event) {
        if (event.type == TransportEventType::Datagram) connA.OnPacket(now, event.data, onMessage);
    });
    b.Poll([&](const TransportEvent &event) {
        if (event.type == TransportEventType::Datagram) connB.OnPacket(now, event.data, onMessage);
    });
    connA.Update(now, [&](std::span<const std::uint8_t> packet) { a.Send(b.Id(), packet); });
    connB.Update(now, [&](std::span<const std::uint8_t> packet) { b.Send(a.Id(), packet); });
}

Includes are engine/network/n2net/Connection.hpp and engine/network/n2net/SimTransport.hpp; everything is in N2Engine::N2Net. The tests' TwoPeers helper (tests/engine/network/n2net/N2NetTestUtil.hpp) wraps this loop for two connections over one link.

Design decision: the simulator is integer-only with its own random number generator PR #197

The simulator is the CI proof for all later netcode, and the same trace has to come out on Windows, Linux, arm64 and wasm. Floating-point probabilities, std::uniform_*_distribution and std::random_device all risk differing between compilers and standard libraries, so probabilities are parts per million compared against a multiply-shift of a 64-bit generator written out in the library. The multiply-shift has a tiny bias that is irrelevant to a network simulator.

The native UDP transport PR #203

UdpTransport is the ITransport for real networks on Windows (Winsock) and Linux (BSD sockets): one non-blocking UDP socket, polled on the calling thread, no thread of its own, no blocking call anywhere. It carries datagrams exactly as given (no framing of its own) up to MaxPacketSize(), 1200 bytes, and IsReliableStream() is false. It is not built for the web: there is no UdpTransport class when __EMSCRIPTEN__ is defined (N2NET_HAS_UDP is 0), and UdpTransport.cpp then compiles to nothing. A UdpTransport is made with UdpTransport::Open(options, encryptionAvailable), which returns a UdpOpenResult (a transport, or an UdpError with the system error code and a one-line message); it never throws.

Binding, and the fail-closed rule

options.bindAddress is a numeric IPv4 or IPv6 address (default 127.0.0.1) and options.port a port (0 picks a free one; read it back with LocalPort()). A host name, an empty string, a zone (fe80::1%eth0) and anything else inet_pton does not accept is InvalidAddress: a name could resolve to anything, so a loopback check on it would mean nothing. An IPv6 bind address makes an IPv6 socket; bound to the wildcard :: with options.dualStack (default true), the socket also reaches IPv4 peers, shown as IPv4 addresses, if the system accepts turning IPV6_V6ONLY off. DualStack() reports what happened, and is false for any other IPv6 bind address: a socket bound to one address such as ::1 can never exchange IPv4 traffic, so Connect to an IPv4 address on it returns FamilyMismatch (with a message naming the bound address) instead of making a peer every Send to which is silently lost PR #207. dualStack = false sets IPV6_V6ONLY. An IPv4 address makes an IPv4 socket.

Fail closed: a non-loopback bind needs encryption or an explicit override PR #203

Open refuses (NonLoopbackRefused, before any socket is created) every address that is not loopback unless the caller passes encryptionAvailable = true or sets options.insecureBind. Loopback means an IPv4 address in 127.0.0.0/8, ::1, or an IPv4-mapped 127/8 address (IsLoopbackAddressText is the same test); 0.0.0.0 and :: (all interfaces) are not loopback, and neither is any text that is not an exact numeric address. insecureBind is the transport-level form of the editor host's --insecure-bind: when it actually overrides the rule, the transport reports InsecureOverrideUsed() and sends one warning line (about the address, port and the missing encryption) to options.warningSink, or to stderr when none is set; a loopback bind with the flag set is quiet. Connect to a non-loopback address is held to the same rule.

Since PR #210 the only caller that passes encryptionAvailable = true is SecureTransport::OpenUdp, which puts the handshake and the sealed packets over every datagram the transport carries (Over UDP). So a game listens on, or talks to, a non-loopback address only through the secure layer, or by opting in loudly with insecureBind.

Peers, caps and unknown sources

A peer is a remote address and port, and its PeerId is a counter (from 1; 0 and ids still in use are skipped if it ever wraps). A peer comes from Connect(address, port) (numeric addresses only; PeerConnected is delivered by the next Poll, and nothing is sent) or, when options.acceptUnknownPeers is true (the default, for a server), from the first datagram of an unknown source (PeerConnected, then the Datagram). A client sets it false: everything not from a connected peer is dropped and counted. Sources that are not usable endpoints (port 0; IPv4 0.0.0.0/8 and 224.0.0.0 upward, which covers multicast, reserved and broadcast; IPv6 :: and ff00::/8; the same ranges inside an IPv4-mapped address) are dropped before they can make a peer, and Connect refuses them as InvalidAddress.

  • The peer table is bounded. maxPeers (default 256, clamped to 1 to 4096) counts peers from Connect and from unknown sources together; a new source beyond it is dropped (droppedPeerLimit), and peers already in keep working. A peer from which nothing is received for peerIdleTimeoutMs (default 30,000; 0 never) is removed and reported as PeerDisconnected, so spoofed sources cannot fill the table forever. The check runs after Poll has read the socket (see below). PR #207 Per-peer state is a fixed-size record: the address, the last-receive time and the counters of UdpPeerInfo.
  • The transport never speaks first. It sends only what Send is given, only to a known peer. An unknown or spoofed source cannot make it transmit anything, so there is no amplification at this layer. A peer made by an unknown source's first datagram is not vetted: GetPeerInfo returns its address and byte and datagram counters, so a layer above can check what it sends to an unauthenticated address against what it received (the secure layer's handshake keeps every such reply no larger than its request by construction, The handshake).
  • Peers are attributed by source address and port only. A datagram that merely claims to belong to a connection is another peer if it comes from another source. Nothing here proves a source address is genuine (UDP source addresses can be forged); that is what the handshake is for.
  • Disconnect is local. It forgets the peer and sends no packet, so the other side finds out through its own idle timeout (or the Connection's). This differs from the interface's wording for SimTransport. A later datagram from the same address makes a new peer with a new PeerId. Called from inside the Poll handler, which the interface forbids, Disconnect does nothing and Connect returns Busy.

Datagrams, errors and platform notes

  • Socket errors are data, never exceptions. Stats() counts what was dropped and why (droppedEmpty, droppedOversize, droppedBadSource, droppedUnknownSource, droppedPeerLimit), the ignored resets, receiveErrors, sendWouldBlock, sendErrors, and keeps the system error code of the last real failure in lastErrorCode. A zero-length datagram, or one longer than 1200 bytes, is dropped and counted: the transport reads into a buffer one byte over the maximum to tell a 1200-byte datagram from a longer one (Windows reports a longer one as WSAEMSGSIZE, also counted as oversize).
  • Send never blocks and reports like a datagram network. After the checks (unknown peer, empty, over 1200 bytes) it returns Sent even when the system could not take the datagram: a full send buffer (sendWouldBlock) or another error (sendErrors) means a lost datagram, which the reliable channel exists to repair. EINTR is retried a bounded number of times.
  • Poll is bounded. It delivers the peers Connect made, then reads at most maxDatagramsPerPoll (default 1024) datagrams, stopping at EWOULDBLOCK, then the idle expiries PR #207; the rest wait in the socket (receiveBufferBytes, default 1 MiB, and sendBufferBytes, default 256 KiB, are requested and the system may grant less). A flood therefore cannot keep a caller inside Poll.
  • Windows: connection resets are ignored. By default a Windows UDP socket that sent to a closed port gets an ICMP port unreachable that makes a later recvfrom fail with WSAECONNRESET, which would hide the datagrams behind it. Open turns off SIO_UDP_CONNRESET and SIO_UDP_NETRESET, and Poll and Send also skip reset-type errors (connectionResetsIgnored; on Linux ECONNREFUSED and similar are treated the same). Winsock is started per transport (WSAStartup, reference counted) and released with it.
  • The port cannot be shared or taken. SO_REUSEADDR is never set, and Windows sets SO_EXCLUSIVEADDRUSE, so a second Open on a port in use fails with BindFailed; after the first transport is destroyed the port can be bound again at once (UDP has no TIME_WAIT).

Design decision: drain the socket, then sweep idle peers PR #207

A caller can stall between two Polls (a long frame, a breakpoint, a suspended process) for longer than peerIdleTimeoutMs while its peers keep sending. Sweeping first would drop every one of them although their datagrams sit in the receive buffer, and the next datagram would then make a new peer with a new PeerId (or, on a client that accepts no unknown sources, be dropped). So Poll reads first and sweeps after, judging idleness against the time the Poll began: a peer heard from during this read has a last-receive time at or after that and is kept, a peer that sent nothing is still removed in the same Poll. The read stays bounded by maxDatagramsPerPoll, so a peer whose datagram is queued behind that many others can still expire; the bound is what keeps a flood from holding the caller in Poll.

Limits

  • IPv4 and IPv6 sockets only; no multicast, no host-name resolution, no IPv6 zones. A datagram over 1200 bytes is dropped, never reassembled by this layer.
  • One socket, used from one thread. There is no I/O thread, no send queue (a datagram goes straight to sendto) and no pacing.
  • A flood of spoofed sources can fill the peer table (maxPeers) until they idle out, and then new genuine sources are dropped. The secure layer's per-address and global limits bound the work and the state such sources cause above this transport, not this table.
  • Dual stack needs a :: bind and depends on the system: on any other IPv6 bind address, or where it cannot be enabled, DualStack() is false and an IPv4 Connect on that socket returns FamilyMismatch. That includes an IPv4-mapped bind address such as ::ffff:127.0.0.1; bind 127.0.0.1 for IPv4.
  • Nothing is encrypted or authenticated by this class itself (that is SecureTransport, see the fail-closed rule above); a NAT, a firewall or a path that drops UDP is not handled.

The secure layer: handshake, sealed packets, join tokens PR #210

SecureTransport is an ITransport that runs over another ITransport (a UdpTransport, or a SimTransport in the tests) and adds the connection handshake and per-packet authenticated encryption. The layers above it (a Connection and its channels) see only authenticated peers: PeerConnected only after a handshake has completed, Datagram only for packets whose tag verified, PeerDisconnected when a session ends. Its MaxPacketSize() is the inner transport's less 25 bytes (1175 over UDP); pass it to ConnectionConfig::maxPacketSize so the packet layer builds packets that still fit once sealed. It is native only: the class exists when n2security has its crypto library (N2NET_HAS_SECURE is 1), which the web build does not have. Like every transport here it is single-threaded and polled, never throws and never logs; its Stats() counters are the only record of what it dropped and why.

The cookie secret is 32 random bytes per process, replaced every cookieSecretRotationMicros (default 60 s, never less than twice the cookie lifetime); the secret of the epoch just ended still verifies, any older one is gone. The cookie time is inside the MAC, so it cannot be moved.
  • No amplification. Both client handshake packets are exactly 256 bytes, and the server drops any other size before doing anything else. The only replies a peer without a session can get are the 41-byte Challenge and the 82-byte Accept (sent again, byte for byte and at most 8 times, when a repeated ConnectResponse shows the first was lost). Static assertions in the header pin this, SendPreAuthReply refuses a reply larger than its request, and Stats() keeps the largest reply and the smallest request answered.
  • Silent refusal. A client with a wrong token therefore sees exactly what it sees when the server is unreachable: ClientState() becomes Failed with HandshakeTimeout after handshakeTimeoutMicros (5 s).

It goes back to a ConnectRequest when it has had no Accept for a cookie lifetime, and gives up after 5 s. A pending session (between the Accept and the client's first sealed packet) is dropped after the same 5 s, and a non-loopback address is charged one failure for it.

Sealed packets

After the handshake every datagram is u8 type | u64 sequence | ciphertext | 16-byte tag: type 0x10 carries data for the layer above, 0x11 is a keep-alive (empty) and 0x12 a disconnect (empty). The cipher is ChaCha20-Poly1305 (RFC 8439) with the session key of the sending direction. The 12-byte nonce is one direction byte (0x43 client to server, 0x53 server to client), three zero bytes and the 64-bit sequence; the associated data is the type, the version, the protocol id and the sequence, so none of them can be changed without failing the tag.

Guarantee: a nonce is never used twice with one key PR #210

Each session derives two fresh keys from its own ephemeral X25519 exchange, one per direction, so no key is ever shared by two sessions or two directions. Within a direction the sequence is taken and incremented before sealing, whatever happens to the packet afterwards, and it only ever rises: the server's Accept is sequence 0 of its key and its data starts at 1, the client starts at 0. At the last value (264 - 1) the layer refuses to seal instead of wrapping (and a keep-alive due then ends the session). The one packet that is sent twice, a lost Accept, is the same bytes, not a new plaintext under the same nonce.

On receipt the sequence is checked against a 256-packet replay window (ReplayWindow: the newest authenticated sequence and a bitmap of the 255 before it) before the packet is opened, and recorded only after its tag verified, so a forged packet can never move the window. A sequence seen before is dropped (droppedReplay), one 256 or more behind the newest is dropped as too old (droppedTooOld), a tag that does not verify is dropped (droppedAuthFailed), and a sealed packet from a peer with no keys is dropped (droppedNoSession); none of these ends the session or gets a reply. Only an authenticated packet refreshes the session's idle clock. A side sends a keep-alive when it has sent nothing for keepAliveMicros (1 s) and drops a session that has authenticated nothing for idleTimeoutMicros (10 s). Disconnect(peer) sends a sealed disconnect (best effort) and forgets the session.

Design decision: our own AEAD layer on Mbed TLS primitives, after netcode.io, with an ECDHE handshake PR #210

The netcode design (2.1.3) weighed DTLS 1.2 through Mbed TLS against a small layer of our own and chose the latter, reviewed against the netcode.io standard. What is the same as netcode.io: a padded connect request no smaller than any reply, a challenge before any server state, ChaCha20-Poly1305 per packet with the packet sequence in the nonce, per-direction keys, a 256-entry replay window, silent drops. What differs, and why: netcode.io's keys and identity come from a connect token that a web backend encrypts with a key it shares with the server; v1 has no backend, only a static tokens file, so the keys come from an ephemeral X25519 exchange and the token is proved with HMACs instead of carried. netcode.io's challenge token is encrypted; ours is an HMAC cookie, because the echo carries the request fields themselves and nothing in it is secret. netcode.io has a connection-denied packet; ours has none (above). netcode.io writes sequences in 1 to 8 bytes; ours are always 8. ChaCha20-Poly1305 rather than AES-GCM (both are in the vendored configuration) because it is constant-time in software on every leg, with no dependence on AES instructions.

Both use one configuration: the library's default plus cmake/mbedtls/config/n2_mbedtls_user_config.h (threading on, with std::mutex callbacks that Security::InitializeCrypto installs once per process). The web build adds neither: there N2SECURITY_HAS_CRYPTO is 0, CryptoAvailable() is false, every crypto function reports failure, and SecureTransport does not exist.

Limits

  • No server identity beyond K, no certificates, no re-keying, no address migration, and no ending of an established session when its token is revoked (SetTokens affects new handshakes only).
  • The browser build has no secure layer: a browser transport (B10) gets its security from the browser's TLS.
  • Reviewed so far only by its tests and its author: the user's security review is required before merge.

The dedicated server: N2Server PR #PRNUM

N2Server is a headless executable that runs a project's scene and listens for clients on a SecureTransport over a UdpTransport: the stack of the sections above in a process of its own, with no window, no renderer and no audio. It is the CMake target N2Server (sources in n2server/; RunServer and the argument parser are in the static library N2ServerCore, so the tests can link them). Like UdpTransport it is not part of the web build. It is a new executable, not a mode of N2EditorHost or lua_project.

What it does so far: it loads the project and the scene, runs the engine's fixed-tick loop, accepts authenticated connections up to --max-clients, enforces the pre-auth slots and rate limits the secure layer already has, and logs each connect and disconnect. What it does not do: it replicates nothing and runs no gameplay networking (that is the netcode's track B); the datagrams an authenticated client sends are counted and dropped, and nothing is sent to a client but the handshake, keep-alives and a final disconnect.

Command line

Unlike N2EditorHost, an unknown option or a stray argument is an error (the message names it, with control characters written out) rather than ignored: a typo such as --tokens-flie must not leave a server running with settings the operator thought they had set. -h or --help anywhere prints the usage and exits 0, whatever else is there.

What starts, in order

  1. --help prints the usage; --new-token runs the generator; --relay is refused. None of them starts the engine.
  2. The log sink starts on stderr (and --log-file), using the editor host's LogSink (the host log): one timestamped line per Logger line at or above --log-level, control characters escaped. SIGPIPE is ignored on POSIX.
  3. The crypto library must work (Security::CryptoAvailable), or the server exits 1: it could not authenticate anyone.
  4. The tokens file is loaded with JoinTokenTable::Load, so every check the secure layer's table makes applies (a regular file, at most 1 MiB, private to its owner on POSIX, well formed). A file that fails ends the server with one line on stderr that never repeats a hash or the file's text.
  5. The project folder and project.n2proj are checked, and the scene path is determined.
  6. Application::Init runs with RenderBackend::NONE, isHeadless = true, audio = false and physicsGpu = false (Init and ApplicationOptions), and PhysicsBackend::AUTO (the project's own physics.backend wins when present, as for every host). The project's Lua runs (LuaExecutionPolicy::Run): this is the game, not an editor. A project whose network.preset is refused (the Network row is Failed) ends the server with exit code 1 and a line on stderr.
  7. The project's id, resources and settings are applied, and the scene is built from its file, made current as a running game (not edit mode), so its components attach at the first tick. A scene that cannot be loaded ends the server with exit code 1.
  8. SecureTransport::OpenUdp binds --bind and --port. A failure (the address is not numeric, the port is in use) ends the server with exit code 1.
  9. The ready line is printed (below), then the loop starts.

The ready line

Once the server is listening, and not before, it prints one line to stdout, flushed (the C stream, as the editor host does, so a pipe sees it at once): N2Server ready port=<port> bind=<address>, where the port is the one bound (the system's pick with --port 0) and the address is the bound address. A launcher matches a whole line starting with N2Server ready followed by space-separated key=value fields (values never hold a space) and ignores keys it does not know; port is always present. This is the format of the editor host's ready line. Nothing else is written to stdout, and the line holds no secret.

Join tokens: --new-token

N2Server --new-token alice player --tokens-file tokens.json makes a token for alice with the role player (or spectator or admin), adds the entry to the file and prints:

New join token for alice (player). It is shown once: the tokens file keeps only its SHA-256, so store the token now.
token: <64 lowercase hex digits>
Added alice to tokens.json. A running server reads the file again on SIGHUP (POSIX); a server that is started reads it at start.

The token is 256 random bits from Security::RandomBytes (the operating system's entropy source, through Mbed TLS), written as 64 lowercase hex digits. The entry added is {"user", "role", "hash"} with the hash "sha256:" and the SHA-256 of the token's text (HashJoinToken), the format JoinTokenTable reads; the hash needs no salt because there is nothing to guess. The generator does not start the engine, installs no log sink and logs nothing; the token goes to stdout once and is never written to the file, a log or an error (a launcher takes it from the line that starts token: ). On failure it prints one line, N2Server --new-token: <reason>, to stderr, prints no token and exits 1.

  • The file is checked as the server checks it. An existing file is read with JoinTokenTable::Load (so one that is too large, malformed, or readable by group or others on POSIX is refused, and left unchanged); a symbolic link is followed and the target is replaced, the link kept. A file that does not exist is created (its folder must exist).
  • A user already in the file is an error and the file is untouched: to revoke or replace a user, edit the file.
  • The file is rewritten whole, atomically. It is written from the parsed table plus the new entry (one entry per line), to a new file beside it and moved over it, so a reader never sees half a file. On POSIX the new file is created with mode 0600 (O_EXCL), flushed to disk, then renamed. On Windows it inherits its folder's ACL (Windows ACLs are not checked by the server either). What is about to be written is parsed again before it is written, so the generator never writes a file the server would refuse.
  • Run it one at a time. Two runs at once read the same file and the later write wins: one entry can be lost.
  • The user name is 1 to 64 characters of A-Z a-z 0-9 . _ @ -; the role is spelled exactly player, spectator or admin.

Security

  • Fail closed. ParseServerArguments refuses a non-loopback --bind unless --tokens-file or --insecure-bind is given, before anything starts (exit code 1, a message naming the address and both ways out). Loopback is IsLoopbackAddressText: an IPv4 address in 127.0.0.0/8, ::1 and an IPv4-mapped 127/8 address; a host name or any odd spelling counts as non-loopback. The default bind is 127.0.0.1, and no other option changes it, so a server never listens on 0.0.0.0 unless asked to. This mirrors the editor host's rule (which needs a token and --tls, or --insecure-bind); here every session is encrypted and authenticated by the secure layer whatever the flags are, so the rule is about whether anyone can authenticate. A server with no tokens file admits nobody (SecureTransportOptions::tokens is null), and logs "No --tokens-file: nobody can join this server"; --insecure-bind only lets such a server start on a non-loopback address, and the server then logs a warning that it did.
  • Tokens. The server holds hashes only (the file's). A presented token is never compared as text: the handshake proves knowledge of the token's hash with HMACs and SecureTransport matches the proofs against every entry in constant time (BasicTokenTable::Authenticate, The handshake). Nothing the server writes (the log, the ready line, an error) contains a token or a hash: the log names the tokens file's path and the number of users in it, and a user's name once connected. No secret is taken from a command line or the environment: --new-token prints a token and nothing reads one. The test client of the smoke test reads its token from stdin.
  • Limits are the secure layer's. N2Server sets no flag for them and keeps the defaults of SecureTransportOptions: 16 pre-auth slots in all and 2 per non-loopback address, 200 challenges per second in all and 10 per non-loopback address, 50 connect responses per second in all and 5 per non-loopback address, and the backoff of addresses whose handshakes failed (Admission). --max-clients bounds the sessions. Handshakes the server drops are counted and, when any were, reported in one line every 60 seconds ("Handshakes dropped since the server started: bad token 3, ...") and in the line it logs at shutdown; the line holds counts, no addresses.
  • What a world-facing bind exposes. The UDP port: anything that can send to it can start a handshake, which costs the server a bounded amount of work per source (the cookie step keeps no state; limits above). Only a token in the tokens file gets a session. The server logs a warning at start when it is bound to a non-loopback address. Firewall the port to the clients' addresses where you can.
  • Revoking. A reload (SIGHUP) swaps the table for new handshakes only; a client already connected stays until it leaves or goes idle (Limits). To remove one at once, restart the server.
  • The project's Lua runs on the server with the engine's usual sandbox and limits (Scripting); a project is trusted code of whoever deploys it. The server never loads a scene or a script a client names: --scene is the operator's.

Needs the security review

Token handling is security-critical and this stage has had no review beyond its tests and its author. The points to review are the fail-closed bind rule, the tokens file's handling and permissions (checks on load, the 0600 atomic write of the generator), that no secret is printed or logged outside --new-token's one line, the shutdown paths, and the defaults above on a world-facing bind.

While it runs, and stopping it

Each pass of the main loop (every 2 ms): reload the tokens file if SIGHUP asked; SecureTransport::Poll; Application::Tick with window events off and rendering off (the fixed ticks that are due run as in any host: the simulation mode follows the project's network.preset); report dropped handshakes if a minute has passed and some were dropped; sleep 2 ms. Events:

  • Connect: PeerConnected comes once the client's first sealed packet arrived (step 5). The log line is Client connected: user=alice role=player peer=1 address=127.0.0.1:50321 (1/16): the user and role the handshake proved, the transport's peer id, the source address and the count out of --max-clients. These lines are tagged Logger::LogSensitivity::Admin, as the editor host tags lines about its clients.
  • Disconnect: Client disconnected: user=alice role=player peer=1 (0/16), when the client sent its sealed Disconnect or its session went idle (10 s without an authenticated packet, SecureTransportOptions::idleTimeoutMicros).
  • Data: an authenticated client's datagram is counted and dropped; the shutdown line reports how many.

Stopping. The loop ends on SIGINT or SIGTERM, on Application::Quit (a script's Application.Quit()), and, with --exit-on-stdin-eof, when stdin closes. On Windows a console's Ctrl+C and Ctrl+Break do the same, and so do closing the console, logoff and shutdown: the console handler asks the loop to stop and waits up to 4.5 seconds for the clean shutdown before it lets Windows end the process. The handlers only set a flag, so no logging happens inside a signal handler. Then: a sealed Disconnect to every connected client, one line of counters ("Stopping: N session(s) established, ..."), the transport closed, OnApplicationQuit on the scene, Application::Shutdown. The exit code is 0 after a clean stop, 1 for a setup failure above or a std::exception that escaped (logged as "Fatal error: ..."). The signal handlers are put back as they were when RunServer returns.

SIGHUP (POSIX, only with --tokens-file) reads the file again: a table that loads replaces the one used for new handshakes ("Reloaded the tokens file: N user(s)"); one that fails its checks is logged ("The tokens file was not reloaded (the previous one stays in force): ...") and the old table stays. Without --tokens-file the server leaves SIGHUP at its default, which ends the process.

Running it as a service

Nothing here is new for a service: the editor host's recipes apply (the Linux host, the host log), with these differences. The logs are on stderr, so journalctl -u n2server -f and docker logs show them. The server needs the shared OpenAL library its build links, as the editor host does (LD_LIBRARY_PATH in the unit below). The tokens file must be mode 0600 and owned by the user the service runs as (the server refuses any other mode, at start and on reload), so use a static user, as the editor host's per-user-tokens unit does. Make tokens with sudo -u n2server /opt/n2engine/bin/N2Server --new-token alice player --tokens-file /etc/n2server/tokens.json and reload with systemctl reload n2server. ReadWritePaths=/srv/game is there because N2Server does not open the project's resource loader read-only (the editor's play host does), so the loader may write its asset metadata (.meta files, .import/, .n2/asset-state.json) into the project folder. Do not add --exit-on-stdin-eof.

In Docker the same binary needs the same shared libraries as the editor host image (deploy/Dockerfile), which builds only N2EditorHost: add N2Server to its --target list and copy build/bin/N2Server into the runtime image. Publish the UDP port (-p 7777:7777/udp) and run with --bind 0.0.0.0, a tokens file mounted at mode 0400 or 0600 and owned by the container user (a Docker secret's default 0444 is refused), and docker kill -s HUP to reload it. Whether the server sees a client's own address or the Docker network's depends on the network mode: the address= in the connect line shows what it sees, and the per-address limits apply to that address.

Design decision: a new executable that borrows the editor host's helpers, with stricter arguments PR #PRNUM

The netcode design (decisions N5, N11 and N12) asks for N2Server as its own executable, not a mode of N2EditorHost or lua_project: a game server has a different trust model (clients are untrusted players, not editors), a different loop and no editor protocol. It links N2EditorServer for what is generic there (the log sink with its escaping, the port and number parsers, the stdin watcher, scene path resolution) rather than copy it; the editor protocol and server are not started. It departs from the editor host's argument conventions in one way: unknown arguments are errors, not ignored (above). It has two flags the plan did not list, --protocol-id (the secure layer needs an id and a game must be able to set its own; the default is the one this page's examples use) and the default port 7777, both easy to change.

Design decision: the engine learns "no renderer", "no audio" and "no physics GPU" PR #PRNUM

The headless paths that existed were the editor's: a hidden window or the software renderer (still a renderer object), and a loopback audio device for the editor's audio stream. A server wants neither, so ApplicationOptions gained RenderBackend::NONE (no GLFW, no window, no renderer: Window::IsValid() stays false, IsWindowless() is true, ShouldClose() is false), audio (false opens no device at all and reports Audio Disabled) and physicsGpu (false forces the physics GPU off whatever physics.gpu says, also for the checks of a Deterministic project). All three default to what every host did before, so no existing host changes. Resources::LoadShader returns null with no renderer instead of dereferencing it.

What is not there yet

  • No browser transport. The implementations are SimTransport and the native UdpTransport (with SecureTransport over it); the browser WebSocket transport is later (B10), and the web build has no secure layer.
  • The handshake agrees no connection id and no settings. ConnectionConfig's ids and window are still configured on both sides; the scene and build fingerprint check is later (B1). See also the secure layer's limits.
  • No engine integration. The engine target does not link n2net. Sessions, replication, NetworkObject, RPCs, prediction and lockstep are the netcode's later tracks.
  • No transport-to-connection glue. There is no class that owns a Connection per PeerId and pumps an ITransport into it; the example above is the pattern, and the tests' TwoPeers and the UDP tests' Side are its only implementations. N2Server (stage A6) runs a SecureTransport in a process of its own but pumps no Connection: it ignores the datagrams its authenticated clients send.
  • No congestion control and no flow control beyond the unit window.

Not verified

Real network behaviour and performance on real links: the packet layer has run over the simulator, whose impairments are a model, and UdpTransport (with and without SecureTransport) only over loopback (with a seeded loss shim), never across machines, a NAT or a congested path. The secure layer has had no review beyond its tests and its author yet. Whether the window, the 32-packets-per-round-trip rule and the timeouts are good defaults for real games is untested.
