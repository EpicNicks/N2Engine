Editor projects

A project is a folder with a project.n2proj file at its root. This page covers the file, creating a project (N2EditorHost --create), what the editor host does when it opens one (--project), scenes as .scene files the host opens and saves, unsaved-change tracking, the hierarchy and entity commands, the project commands, and each project's own user:// folder. The host process, the wire format and every other command are on Logging, health & editor. Part of the editor plan #6, phase E3 (#75) PR #90.

A project's folder

My Game/
  project.n2proj        the project file (commit it)
  assets/               res:// is this folder; every file here is an asset
    scenes/Main.scene   scenes are assets: JSON, as Scene::Serialize writes it
    scripts/Example.lua
  .import/              one .meta per asset (UUID, type, import settings)
  .gitignore            ".n2/": the editor's per-machine folder

.import/ is written by ResourceLoader (see Resources). .n2/ is reserved for per-machine editor state (later phases of #6: caches, autosaves, play-mode scenes); nothing writes it yet. <project>/scenes/*.json, the folder the deprecated DeleteScene works in, is not part of this layout.

project.n2proj

One JSON object. IO::ProjectFile (engine/include/engine/io/ProjectFile.hpp) parses, validates and saves it. It is CPU only: it touches nothing but files, so tools and tests use it without starting the engine.

{
  "engineVersion": "1.0.0",
  "formatVersion": 1,
  "name": "My Game",
  "projectId": "8e0c3a8e-0b1f-4f5e-9d0e-3f6f1c7d2a10",
  "scenes": ["res://scenes/Main.scene"],
  "settings": {
    "layers": { "layers": ["Default", "TransparentFX", "..."], "collisionMatrix": [4294967295, "..."] },
    "physics": { "fixedTimestep": 0.02, "gravity": { "x": 0, "y": -9.81, "z": 0 } }
  },
  "startupScene": "res://scenes/Main.scene"
}
KeyRule
formatVersionRequired integer, 1. A newer format is refused ("... is newer than this engine reads; open it with a newer engine").
nameRequired, not empty or only whitespace. Shown by editors; names the user:// folder.
projectIdRequired UUID, not all zeros; written in lower case. Made once when the project is created. It is the namespace of every asset UUID (why).
engineVersionRequired major.minor.patch: the engine version that created the project. Opening it with another major version is refused; another minor version is a warning (IO::CompareEngineVersions). It is not rewritten when the project is saved by a newer engine.
startupSceneOptional: "", or a scene path (res://, inside the assets folder, ending in .scene in any case; ProjectFile::IsScenePath). The host opens it first.
scenesOptional array of scene paths: the project's scene list. SetStartupScene adds to it; nothing else edits it yet.
settingsOptional object of blocks, each owned by a subsystem (below). ProjectFile stores them without reading them.
  • Errors name the key: FromJson, Parse and Load return std::expected, with messages such as projectId: 'x' is not a UUID. Load of a folder without the file says "project.n2proj not found: ... is not a project (create one with N2EditorHost --create)", and a corrupt file names the file.
  • Unknown keys are kept. Top-level keys this version doesn't know are kept in unknownKeys and written back by ToJson/Save; anything inside settings is kept as it is. A file edited by a newer editor survives an older one.
  • Saving validates first (an invalid project is never written), then writes the file indented by two spaces, keys sorted, ending in a newline, through a temporary file beside it (<file>.<8 hex digits>.tmp) renamed over the old file (IO::WriteTextFileAtomically; why).

Source: engine/src/io/ProjectFile.cpp — ProjectFile::FromJson, Validate, ToJson, Save, IsScenePath, CompareEngineVersions, WriteTextFileAtomically; tests: ProjectFileParseTest.*, ProjectFileTest.SaveThenLoadRoundTrips, ProjectFileTest.AnInvalidProjectIsNotSaved

Design decision: one JSON project file, whose settings blocks belong to their subsystems PR #90

The project file is what a project is: the editor finds projects by it, the host refuses a folder without it, and it is committed. JSON, because the engine already reads and writes JSON everywhere and a person can review a diff of it. Each settings block is whatever its subsystem's own Serialize writes (Layers, InputSystem), so ProjectFile doesn't duplicate their formats or validate them twice; the subsystem decides at apply time. Unknown keys are kept, top-level and in settings, because a project moves between engine versions and between tools: a key one doesn't understand is not one it may delete. The C# client and other tools can add keys of their own the same way. Decided on #6 (decision 1); #75.

Design decision: the projectId is the asset UUID namespace PR #90

Asset UUIDs are name-based, from a namespace and the asset's res:// path, so .import/ can be deleted and regenerated with the same UUIDs. The namespace used to be a hash of the project folder's path (PR #84), so moving, renaming or cloning the folder changed every asset UUID and broke every reference in every scene. A random id made once when the project is created and kept in the committed project file doesn't depend on where the folder is: two clones, or a folder moved, give the same UUIDs (ResourceLoaderProjectTest.TheNamespaceIsTheProjectIdSoUuidsDontDependOnTheFolder). The id is the namespace itself, not hashed again, so a folder can adopt the namespace it already had. Moving or renaming an asset still changes its UUID (#6, decision 6: a later move command will rewrite references). Decided on #6 (decision 3); #75.

Settings

ApplyProjectSettings(settings) (engine/ProjectSettings.hpp) applies the blocks it knows to the running engine, each through its subsystem:

BlockApplied by
layersLayers::Deserialize: layer names and the collision matrix (#4). Malformed input changes nothing.
inputMust be {"actionMaps": {...}}, checked even when there is no input system (an editor host without a window), so a block that could never load is refused PR #90; then the window's InputSystem::Deserialize reads it, when there is one.
physicsfixedTimestep (seconds, positive) through Time::SetFixedTimestep PR #90; gravity ({x, y, z}) through the physics backend, when there is one.
window, rendering, anything elseNot applied: an editor host has no window to size. Kept in the file for a player (or a later version) to read.

It returns one message per block that was refused (empty when everything given was applied); other blocks are still applied. A missing or null block changes nothing. It runs after Application::Init, which resets the fixed timestep.

Creating a project: --create

A launcher creates a project by running the host once with --create. It makes the files and exits; the engine is never started.

N2EditorHost --create <folder> [--name <name>] [--project-id <uuid> | --project-id from-path]
OptionMeaning
--create <folder>The folder to make a project. It is created (with its parents) if it doesn't exist; an existing folder is adopted (its files are kept).
--name <name>The project's name. Default: the folder's name (Project for a drive root). Spaces are fine (quote the argument).
--project-id <uuid>The project's id, any case, not all zeros. Default: a new random UUID.
--project-id from-pathThe id is the namespace the folder's assets had before projects had ids (ResourceUUID::NamespaceForProjectDir(<folder>)), so a folder an older host or lua_project opened keeps every asset UUID. See adopting a folder.

What it writes. IO::CreateProject: assets/scenes/Main.scene (an empty scene named Main), assets/scripts/Example.lua (a behaviour script in the engine's script model, the same template CreateScript returns, class Example), .gitignore (.n2/), then project.n2proj last, with startupScene res://scenes/Main.scene, scenes ["res://scenes/Main.scene"], settings {} and engineVersion the running engine's. A file that already exists (adopting a folder) is kept, never overwritten, even Main.scene. Options are checked before anything is created, and the project file is written last, so a failure never leaves a folder that looks like a project.

The contract a launcher relies on (the Electron editor's F2 launcher; tested by HostOptionsTest.TheCreatedLineHasTheDocumentedFormat, EditorCreateTest.RunCreateMakesAProjectAndRefusesToMakeItTwice and the CI smoke test):

Exit codestdoutstderrMeaning
0Exactly one line: the created line (below)NothingThe project exists now.
2NothingOne line: N2EditorHost --create: <folder> already has a project.n2proj; nothing was changedThe folder already is a project. Nothing was written; open it with --project.
1NothingOne line: N2EditorHost --create: <reason>, or an argument error (below)Anything else: the path is a file, a file can't be written, a bad option.
 
N2EditorHost created projectId=8e0c3a8e-0b1f-4f5e-9d0e-3f6f1c7d2a10 startupScene=res://scenes/Main.scene
  • The created line starts with N2EditorHost created , then space-separated key=value fields, as the ready line does: projectId (lower case) is always present, startupScene when the project has one. A value never contains a space (a startup scene path with one would be left out). Later versions may add fields: ignore keys you don't know and don't depend on their order. Regex: ^N2EditorHost created (?:.* )?projectId=([0-9a-f-]{36})(?: |$). Strip a trailing \r first (on Windows the line ends in \r\n).
  • The folder and the name are not in the line: the launcher passed them, and they may contain spaces. Read project.n2proj for the rest.
  • Argument errors are checked before anything else and exit 1 with one stderr line: --create, --name or --project-id without a value ("--name is missing a value"; a value starting with -- counts as missing, so a name can't start with --), "Invalid --project-id: <value> (expected a non-zero UUID, or from-path)", "--create and --project can't be combined: ...", and --name or --project-id without --create ("--name only goes with --create"). Other host options (--port, --renderer, ...) are parsed as usual but unused. --help wins over everything.
  • No engine subsystem starts, so no log lines, renderer or audio messages reach stdout, and it works on a machine without a GPU. It takes a few milliseconds.
  • Then start the host on it: N2EditorHost --project <folder> --port 0 --renderer software --token-env <VAR> --exit-on-disconnect and wait for the ready line.

Source: editor-server/src/Host.cpp — Editor::RunCreate; editor-server/src/HostOptions.cpp — ParseHostArguments, FormatCreatedLine; engine/src/io/ProjectFile.cpp — IO::CreateProject; tests: ProjectFileTest.CreateProject*, HostOptionsTest.Create*, HostOptionsTest.ProjectIdFromPathAsksForTheFoldersOldNamespace, HostOptionsTest.AnInvalidProjectIdIsAnError, HostOptionsTest.NameAndProjectIdOnlyGoWithCreate

Design decision: --create never starts the engine PR #90

Creating a project is writing a few files. Starting the engine for it would initialise PhysX, a GPU context and audio, take seconds, fail on a machine without a GPU, and print subsystem lines into the stdout the launcher reads. So --create runs IO::CreateProject, which uses nothing but the filesystem, and exits. The host is the tool that creates projects, rather than the launcher writing the files itself, so the layout, the id and the script template are the engine's and stay in step with what the host reads. One line on stdout, in the ready line's key=value form, gives the launcher the id without parsing JSON; exit code 2 for "already a project" lets it offer to open the folder instead of showing an error, without matching message text. Decided on #6 (decisions 2 and D); #75.

Design decision: adopting a folder can keep its asset UUIDs (--project-id from-path) PR #90

Scenes store asset references as UUIDs. A folder opened before projects had ids (by lua_project, or a host before this change) has UUIDs made in the namespace of its path; a fresh random id would change all of them once and break every reference. Since the id is the namespace, the folder can adopt the namespace it already had. The launcher can't compute it (a UUIDv5 of the path spelled exactly as ResourceUUID::NormalizeProjectDir spells it), so the host does: from-path asks for it, and --project-id <uuid> takes any id a tool already knows. From then on the id is fixed in the file, so moving the folder no longer changes anything. Decided on #6 (decision 1, review §2.6); #75.

Opening a project: --project

N2EditorHost --project <folder> opens the project in that folder. Before the engine starts, RunHost checks the folder exists, reads project.n2proj (ProjectFile::Load) and compares its engineVersion with the engine's. Each failure prints one line to stderr and exits with code 1 before anything starts, so a launcher pointed at the wrong folder gets a quick, clean answer:

  • "Project folder not found or not a folder: ..."
  • "project.n2proj not found: ... is not a project (create one with N2EditorHost --create)", or the file's validation error. When the folder has no project file but has .import/ (an older host or lua_project opened it, so its .meta UUIDs come from its path), a second line says how to keep them: "It has asset metadata (.import/): to keep its asset UUIDs, make it a project with N2EditorHost --create "<folder>" --project-id from-path" PR #90.
  • "project.n2proj was made with engine X; this is engine Y, a different major version"

Then, after Application::Init (so the lines reach the console and the event ring):

  1. Log "Opening project '<name>' (<id>)", and a warning when the project's minor engine version differs.
  2. ResourceUUID::Initialize(projectId): the asset UUID namespace.
  3. ResourceLoader::Initialize(folder, project.UserDataPath()): res:// is <folder>/assets, user:// the project's own folder, and every asset gets its .meta.
  4. ApplyProjectSettings(settings); each refused block is logged as a warning ("Project settings: ...") and the host carries on.
  5. EditorServer::SetProject(folder, project), and the deprecated DeleteScene folder, <folder>/scenes.
  6. Open the startup scene (EditorServer::OpenSceneFile). If there is none, or it can't be opened (logged as "Couldn't open the startup scene: ...", an exception included PR #90), an empty scene named Untitled with no file is loaded instead, so a host with a project always has a scene.

Without --project the host has no project and no scene, as before: the project and scene-file commands answer Error "No project: ...". Hello's projectLoaded is now whether the server has a project (EditorServer::HasProject), rather than whether ResourceLoader was initialised.

Source: editor-server/src/Host.cpp — Editor::RunHost; editor-server/src/EditorServer.cpp — EditorServer::SetProject, HandleHello; tests: EditorProjectTest.HelloReportsTheProject, EditorSessionTest.HelloAnswersWithTheServersVersionsAndCapabilities, the CI smoke test

Design decision: --project needs a project file; there is no plain-folder fallback PR #90

Before, --project took any folder and named its UUIDs after its path (PR #84). Falling back to that for a folder without a project file would give the same folder different UUIDs depending on whether the file exists yet, and a typo in the path would silently open an empty "project". So the host refuses, before starting the engine, and says how to make one. Adopting a folder is one --create --project-id from-path away and keeps its UUIDs. lua_project, which runs folders that aren't editor projects, keeps the fallback, with a warning (below). Decided for #75.

Scene files

A scene is a .scene file under assets/: the JSON Scene::Serialize writes ({"name", "rootGameObjects"}). ResourceLoader scans .scene files like any asset, with resource type "Scene", the type Scene itself already reports, and loads them as SceneFile (the scene's JSON; engine/sceneManagement/SceneFile.hpp). So a scene has a path-derived UUID in its .meta, and a project file names its scenes by res:// path.

The host owns scene files: a client opens, saves and creates them with commands, never by writing files itself (#6, decision 7). All four answer SceneInfo (0x0D): path (the scene's file as a res:// path, or empty when it has none), name, uuid, revision and savedRevision (uint32s, below).

IdCommandRequestBehaviour
0x25OpenScenestring pathReads the file, builds it (Scene::FromJSON, validated) in edit mode (components are deserialised, never attached; a LuaComponent's script chunk does run, see security) and makes it the loaded scene, replacing the loaded one: a client asks before discarding unsaved changes. The scene's UUID becomes its file's asset UUID (ResourceUUID::FromPath, the same as its .meta), so it is the same every run. A file added since the last scan is indexed first. The revision moves on, and the scene counts as saved. Errors: no project, a path that isn't a scene path of the project, a missing file, invalid JSON, or JSON that isn't a valid scene ("Not a valid scene (see the log)"); the loaded scene is kept then.
0x26SaveSceneToFilestring pathWrites the loaded scene's JSON, indented by two spaces and ending in a newline, atomically (a temporary file beside it, renamed over the file), creating folders as needed, and stores it in the host as SaveScene does. Empty path: the scene's own file ("The open scene has no file yet: pass the path ..." when it has none). Another path is "save as": the file is overwritten if it exists, becomes the scene's file, and the scene takes that file's UUID. The file is indexed (its .meta written or updated, a cached copy dropped). savedRevision becomes revision.
0x27NewScenestring path, string nameAn empty scene named name (empty: the file's name without .scene, or Untitled without a path) becomes the loaded scene. With a path, the scene is written there first; a file that already exists is an Error ("A file already exists at ... (open it with OpenScene)"), never overwritten. With an empty path it has no file until SaveSceneToFile names one (and needs no project). It starts saved.
0x29GetOpenScene—The loaded scene, as the others report it. Error "No scene loaded" without one. (The scene's objects are GetHierarchy's, below.)

Scene paths. res://, then a path that stays inside the assets folder, whose file name ends in .scene (any case): res://scenes/Main.scene, res://levels/../scenes/Main.scene (normalised). Rejected: no scheme (scenes/Main.scene), user://, absolute paths, a drive or other root name, a : anywhere (on NTFS name.scene:x would be an alternate data stream), .. escapes, other extensions (ProjectFile::IsScenePath). Then the folders that exist are resolved with symlinks followed, and so is the file itself when it exists; each must stay inside the assets folder, so a symlinked folder or file under assets/ can't send a read or a write elsewhere (EditorServer::ResolveScenePath) PR #90. The scene's res:// path is then rebuilt from the resolved file, relative to the assets folder: the spelling the file system has. So on Windows, where file names are case-insensitive, res://Scenes/main.scene is the same scene as res://scenes/Main.scene, with the same UUID and .meta, and saving through either spelling saves the scene's own file. The path in SceneInfo is that form. Paths are UTF-8 on the wire and in .meta files, whatever the Windows code page (IO::PathFromUtf8, IO::PathToUtf8), so a file named with characters outside it is a scene like any other.

Other scene commands. LoadScene (a scene sent as JSON) still works: the scene it loads has no file (path empty) and is unsaved. SaveScene still only stores the scene in the host's memory; GetCurrentScene and CreateScene are unchanged. DeleteScene's <project>/scenes/*.json rule is deprecated: scene files are .scene assets now, and deleting assets will be an asset command (#6, E8).

Source: editor-server/src/EditorServer.cpp — EditorServer::OpenSceneFile, NewSceneFile, SaveSceneFile, GetOpenSceneInfo, ResolveScenePath, LoadOpenedScene; engine/src/sceneManagement/SceneFile.cpp; tests: EditorProjectTest.OpenScene*, EditorProjectTest.SaveAsMakesTheNewFileTheScenesFile, EditorProjectTest.SavingAndOpeningRoundTripsTheScene, EditorProjectTest.NewScene*, EditorProjectTest.AnUntitledSceneHasNoFileUntilSavedWithAPath, EditorScenePathTest.OnlyScenePathsInsideTheAssetsFolderResolve, ResourceLoaderProjectTest.SceneFilesAreSceneAssetsWithPathDerivedUuids

Design decision: .scene files use Scene's own resource type; the scene takes its file's UUID PR #90

Scene already is an asset (Scene : Base::Asset, resource type "Scene"), with a random UUID per instance; what was missing was a file extension and a stable UUID. Adding a second "scene asset" type would give one scene two types and two UUIDs. So .scene files have resource type "Scene", and opening one gives the live Scene the file's path-derived UUID (Asset::SetUUID), which is what the .meta and any reference to the file hold. The loader still needs a product of its own, because ResourceLoader caches shared_ptrs while SceneManager owns live scenes as unique_ptrs; that product is SceneFile, the file's JSON, named so there aren't two classes called "Scene". OpenScene reads the file itself rather than through the loader's cache, so it always opens what is on disk. Decided on #6 (decision 4); #75.

Design decision: files are written to a temporary file, then renamed PR #90

Writing a scene or the project file in place truncates it first, so a crash, a full disk or a killed host halfway through leaves a broken file where a good one was, and the project file is the one file a project can't lose. Writing a temporary file and renaming it over the old file replaces it in one step (MoveFileExW with MOVEFILE_REPLACE_EXISTING on Windows, rename on POSIX): a reader sees the old file or the new one. The temporary file has a random name of its own (<file>.<8 hex digits>.tmp), created exclusively where the library supports it (std::ios::noreplace), so two writers or a stale file left by a crash never collide. On Windows, another process that has the file open (an editor, a virus scanner, the search indexer) makes the rename fail for a moment with an access or sharing violation, so the rename is retried up to 10 times, 10 to 50 ms apart PR #90. This protects against the host crashing or a write failing, not against losing power: the data is handed to the operating system but not forced to the disk (no FlushFileBuffers/fsync). A failed write removes the temporary file and leaves the old one. NewScene refuses to overwrite and SaveSceneToFile overwrites, because "new" never means replacing work, while "save as" over a file is what the user asked for after the client confirmed it. Decided for #75.

Unsaved changes: revision and savedRevision

  • revision (EditorServer::GetSceneRevision) is 0 until a scene is loaded. Every command that changes the loaded scene, or loads another, moves it on by one: OpenScene, NewScene, LoadScene, CreateEntity, DestroyEntity (when something was destroyed) and SetEntityTransform (when applied), and, since PR #92, CreateEntityEx, SetEntityParent, SetEntityProperties (each when something changed), DuplicateEntity and SetLocalTransform. Failures and reads don't. It only grows, across scenes too, so a client refetches what it shows whenever it changes. Later phases add their commands to this list.
  • savedRevision is the revision the loaded scene was last opened or saved at (OpenScene, NewScene, SaveSceneToFile).
  • The scene has unsaved changes exactly when revision != savedRevision: an editor shows its "unsaved" marker and asks before closing, opening another scene or quitting.
  • Every change and every save pushes a sceneChanged event: {"kind": "sceneChanged", "revision", "savedRevision", "path"}, path being the loaded scene's file (empty for none), and, for a change, which objects it touched (entityIds, or full when another scene was loaded; below PR #92). A client that polls events sees the state change without asking; GetOpenScene gives it on demand, for example right after connecting, when the host has already opened the startup scene.
{"kind":"sceneChanged","path":"res://scenes/Main.scene","revision":5,"savedRevision":4,"seq":31}

Source: editor-server/src/EditorServer.cpp — EditorServer::MarkSceneChanged, PushSceneChanged, HandleCreateEntity, HandleDestroyEntity, HandleSetEntityTransform, HandleLoadScene; tests: EditorProjectTest.EditsLeaveTheSceneUnsavedUntilItIsSaved, EditorProjectTest.EveryMutatingCommandMovesTheRevision, EditorProjectTest.SceneChangesAndSavesPushSceneChangedEvents, EditorProjectTest.ASceneSentWithLoadSceneHasNoFileAndIsUnsaved

Design decision: dirty is a revision compared with a saved revision PR #90

A "dirty" flag would have to be cleared by a save and set by every change, and couldn't tell a client which change it last saw; it also stops being right once undo arrives (#6, E6), where undoing back to the saved state should make the scene clean again. A counter that every change moves on, plus the value it had when last saved, answers both: the scene is dirty when they differ, the client refetches when the revision moves, and undo can later restore an earlier revision number. The revision never resets, even on opening another scene, so a client can't mistake a new scene's revision 1 for an old one it already showed. E4's hierarchy commands use the same revision. Decided on #6 (additional decision C); #75.

Design decision: a host with a project always has a scene PR #90

Entity commands need a loaded scene, and an editor shouldn't have to create one before it can show anything. So a host that opens a project loads its startup scene, and when there is none, or it can't be opened, an empty Untitled scene with no file, logging why. A broken startup scene doesn't stop the host: the user can still open another scene or fix the file. Decided for #75, following #6 §(a) ("loads the startup scene, or an empty one").

Hierarchy and entities

PR #92 The scene's objects (GameObjects, called entities on the wire) are read and edited with the commands below. An object is named by its UUID string (entityId, parentId; an empty parentId is "no parent": a root of the scene). Which object is selected is the client's own state: the host learns about a selection only through the ids in the commands that use it. Every command needs a loaded scene (Error "No scene loaded"), and an object that isn't in it is Error "Entity not found: ...". The older commands (CreateEntity, DestroyEntity, GetAllEntities, the world-space Get/SetEntityTransform) are unchanged.

IdCommandRequestResponseBehaviour
0x28GetHierarchy—Hierarchy {uint32 revision, json nodes}Every object, as a flat list in depth-first order: a parent comes right before its children, siblings in their order. Each node is {id, parentId, index, name, active, activeInHierarchy, layer, tag, components}: parentId empty for a root; index the object's place among its siblings; active its own flag and activeInHierarchy whether it and every ancestor are active; components the component type names, in order. revision is the scene revision the list was read at: a client refetches it when sceneChanged says the revision moved.
0x35CreateEntityExstring name, parentId; int32 siblingIndex; string presetEntityCreatedMakes an object with a transform (CreateEntity's has none), under parentId (empty: a root), at siblingIndex among its siblings (-1, or past the last: the last). The preset adds components: empty or Empty (none), Cube, Sphere, Quad (the built-in renderers), Light or DirectionalLight, PointLight, SpotLight (a Light of that type). An empty name is the preset's: GameObject, Cube, Sphere, Quad, Light, Directional Light, Point Light, Spot Light. An unknown parent or preset is an Error (the preset error lists the presets), and nothing is made.
0x36SetEntityParentstring entityId, parentId; int32 siblingIndex; bool keepWorldTransformOkMoves the object under parentId (empty: to the roots) at siblingIndex among its new siblings (-1, or past the last: the last), also within the one parent it has: that reorders. keepWorldTransform true keeps where the object is in the world (its local transform changes to match); false keeps its local transform (it moves with its new parent). A parent that is the object itself or one of its descendants is an Error. Moving the object to the place it already has changes nothing, and doesn't move the revision.
0x37SetEntityPropertiesstring entityId; json propertiesOkproperties is an object with any of name (string), active (bool, the object's own flag), tag (string), layer (integer 0 to 31; not clamped). Everything is checked before anything is applied: an unknown key, a value of the wrong type or a layer out of range is an Error and nothing changes. A property that already has the value changes nothing, and if none changes the revision doesn't move.
0x38DuplicateEntitystring entityIdEntityCreated (the copy's id)Copies the object and everything under it, right after the original among its siblings and under the same parent. The copy is named as Unity names one: Cube and Cube (3) both give Cube (1), then Cube (2), the first number no sibling has. Every object and component has a new UUID. See Duplicating.
0x39GetEntitystring entityIdEntityData {json entity, mat4 worldMatrix}One object in full: entity is {header, transform, components} (below), and worldMatrix its local-to-world matrix (column-major, the translation in elements 12 to 14; the identity for an object with no transform), so a client draws a gizmo without walking the parent chain.
0x3ASetLocalTransformstring entityId; vec3 position; quat rotation; vec3 scaleOkSets the transform relative to the object's parent (to the scene, for a root). The rotation is a quaternion, normalised by the host; a zero quaternion, or any value that isn't a finite number, is an Error. An object that has none (CreateEntity makes such objects) gets a transform.

What GetEntity returns

entity is the JSON shape EntityDetails in protocol.json:

{"header": {"id": "6b0e...", "parentId": "", "index": 0, "name": "Lamp", "active": true,
            "activeInHierarchy": true, "layer": 0, "tag": "Untagged"},
 "transform": {"position": {"x": 0, "y": 2, "z": 0}, "rotation": {"x": 0, "y": 0, "z": 0, "w": 1},
               "scale": {"x": 1, "y": 1, "z": 1}},
 "components": [{"type": "Light", "uuid": "c41f...", "values": {"type": "Point", "intensity": 1, "range": 10}}]}

header has the fields a hierarchy node has (without components); transform is the local transform, the rotation a quaternion (x, y, z, w), and is absent for an object that has none; each component is its type name, its UUID and values: what the scene saves for it (Component::Serialize), in component order. Reading changes nothing, and neither it nor GetHierarchy logs per call.

sceneChanged says what changed

Every change of the scene pushes sceneChanged (above), which since this phase also carries what the change touched, so a client doesn't refetch everything for every edit:

  • entityIds: the UUIDs of the objects the change touched: every object whose GetEntity data changed: the one created, renamed, re-tagged or moved to another layer, and, with everything under it (their world matrices or activeInHierarchy changed too), the one reparented, given a transform or switched on or off; the copy and everything under it for DuplicateEntity, the destroyed object and everything under it for DestroyEntity. A client that shows one of them (the inspector) refetches it. The siblings whose index shifted are not listed: header.index is only guaranteed fresh in a GetHierarchy read, which a client that shows the tree refetches when the revision moved. At most 256 ids go into one event: a change that touched more carries none, which reads as "anything may have changed".
  • full (true): another scene was loaded (OpenScene, NewScene, LoadScene), so every id a client holds is invalid: it drops its selection and refetches everything. A later phase uses the same flag after an undo that restored a snapshot (#6, decision 9).
  • A save, which changes no object, carries neither; so does a change that touched more than 256 objects.
{"kind":"sceneChanged","entityIds":["6b0e..."],"path":"res://scenes/Main.scene","revision":9,"savedRevision":4,"seq":52}
{"kind":"sceneChanged","full":true,"path":"","revision":10,"savedRevision":10,"seq":53}

Edit mode

The host never runs a game loop, so the components of a scene it opened never attach (OnAttach, which adds a Light to the scene's light list and creates physics bodies, only runs from Scene::ProcessAttachQueue). Every scene the host loads (OpenScene, NewScene, LoadScene) is marked with Scene::SetEditMode(true), and two engine paths act on it:

  • Lighting. Scene::CollectLighting() takes the lights of an edit-mode scene from the hierarchy, as Scene::Render finds renderables: every active Light on an object that is active in the hierarchy, in traversal order, with the usual caps and the default light when there is none (LightingSource::Hierarchy). A scene's lights now light the editor's viewport; before, none was ever registered and every scene was lit by the default light. A scene that runs keeps the attached lights (LightingSource::Attached). The built-in shapes are unlit; a lit MeshRenderer shows the effect.
  • Active state. Changing an object's active flag (SetEntityProperties), or moving it under an inactive parent (SetEntityParent), runs no OnEnable/OnDisable on its components. They were never enabled, and a script's OnEnable must not run because someone toggled a checkbox. The flags and cached states change as usual.

Not yet changed: DestroyEntity still runs OnDisable/OnDestroy (Lua included) on what it destroys, as before; physics bodies are still not created, so picking by a physics ray finds nothing in edit mode (#6, E7 picks by bounds instead). A copy made by DuplicateEntity is built by deserialising, which for a LuaComponent runs its script chunk and may log warnings about its reference fields; a reference the scene doesn't know is null.

Duplicating

DuplicateEntity serialises the subtree and builds it again with PrefabManager::InstantiatePrefab(json, outside), an overload of the prefab instantiation that takes a ReferenceResolver for the rest of the scene (SceneReferences: every object and component of the scene by UUID). References between objects inside the copy point at the copy's own; a reference to anything outside it (a script's target that isn't part of the subtree, a component reference) keeps pointing at that object, instead of becoming null as in a prefab instance; a reference the scene doesn't know is still null. The copy has fresh UUIDs for every object and component, so two objects never share one.

Design decision: the hierarchy is a flat list, and a client refetches it when the revision moves PR #92

A nested tree answers one question; a flat, depth-first list with parentId and index on every node answers it just as well (a client builds the tree in one pass), is the same shape a database or a table view takes, and keeps one node small enough to log or diff. The list carries the revision it was read at, so a client compares it with the sceneChanged it holds and refetches only when they differ. A hierarchy is about 100 bytes an object, so a 10 000-object scene is about 1 MB, fetched only on a change; incremental hierarchy events are a later optimisation if that ever matters. Decided on #6 (§(b), "Flat, in depth-first order"); #76.

Design decision: sceneChanged lists the touched objects, only when it is cheap, and says when everything is new PR #92

An edit that touches one object shouldn't cost a refetch of everything, so the event names the objects it touched (entityIds). A deleted or duplicated subtree can be huge, and an event that held 100 000 ids would be bigger than the hierarchy it saves refetching, so past 256 the event carries none: for the client that is simply "anything may have changed", the same as an event from a host that never sent ids, so the contract has only one fallback to implement. Loading another scene is different in kind: every id a client holds is now invalid, and listing none would look like "unknown", so it says full: true. The same flag is used after an undo restores a snapshot, which recreates every object (#6, decision 9). Decided on #6 (§(c) "sceneChanged{revision, entityIds?} (entityIds only when cheap)", decision 9, and the E3 addendum); #76.

Design decision: a scene opened for editing is marked, rather than the engine guessing PR #92

An edit-mode scene differs from a running one in what never happened (OnAttach), not in anything the engine could test cheaply: "has any component attached" is also true of a scene that simply hasn't had its first frame yet. A flag the host sets for the scenes it loads (Scene::SetEditMode) says what the host knows, and costs nothing for a running game. It decides two things that would otherwise be wrong in the editor: the lights are found in the hierarchy (the Light list is filled by OnAttach, so edit mode was lit by the default light only; #6 proposed exactly this edit-mode path in CollectLighting), and toggling an object's active state doesn't call OnEnable/OnDisable on components that were never enabled (a script's callback ran, a sound played, a button's state changed, all in the editor). Lighting also keeps an explicit source (LightingSource), so a test can ask for either. Decided on #6 (§(f), "Scene::CollectLighting gets an edit-mode path that walks the hierarchy"); the active-state half is this phase's choice, because the hierarchy commands are the first to change it in edit mode; #76.

Design decision: a duplicate keeps its references to objects outside the copy PR #92

Instantiating a prefab nulls every reference to anything outside it, because the prefab may be instantiated where those objects aren't. A copy made in the scene is different: the objects its references point at are right there, and a duplicate of a turret that aims at a target, or a button that calls a manager, should still aim and call. Unity keeps such references, and silently nulling them would break a scene with no sign why. So the copy is built with the scene's own references as a fallback (ReferenceResolver::SetFallback, and an InstantiatePrefab overload that takes the scene's resolver and keeps outside $refs of Lua fields instead of nulling them). References inside the copy still go to the copy. Decided on #6 (additional decision B); #76.

Design decision: GetEntity returns the world matrix, and the rotation is a quaternion PR #92

A gizmo is drawn at the object's world position, orientation and scale, which depend on every ancestor's transform. A client that had to compute them would fetch the parent chain (one round trip per ancestor, refetched whenever any of them changes) and reimplement the engine's transform maths; the host already has the matrix. worldMatrix comes with the entity in one response, as a mat4 field rather than inside the JSON, so it is 64 bytes the codecs read as numbers, not text. The local transform travels as position, quaternion and scale: converting to Euler angles and back on every edit drifts (and has several answers for one rotation), so the inspector shows Euler angles but sends the quaternion, and SetLocalTransform normalises it. The world-space, Euler Get/SetEntityTransform stay for existing clients. Decided on #6 (review point 9, §(b) SetLocalTransform); #76.

Design decision: an edit that changes nothing doesn't move the revision PR #92

The revision decides whether the scene has unsaved changes and when a client refetches. A drag that ends where it started, a rename to the same name, or an apply of a value that was already set would otherwise mark the scene unsaved and make every client refetch for nothing. SetEntityParent compares the place the object would take with the one it has, and SetEntityProperties each property with its value. (SetLocalTransform compares the position, the normalised rotation and the scale with the stored ones exactly: a gizmo drag that sends the same values again changes nothing, and a value that differs by a rounding error counts. SetEntityTransform still always counts.) Undo (#6, E6) can then restore the revision exactly. Decided for #76, following the revision decision.

Project commands

All three answer ProjectInfo (0x0E): rootPath and userDataPath (strings: the project folder and its user:// folder, absolute, UTF-8) and project (json:ProjectFile: the project file as saved, unknown keys included). Without a project each is Error "No project: the host wasn't started with --project". A successful change saves project.n2proj (atomically) and pushes a projectChanged event ({"kind": "projectChanged"}).

IdCommandRequestBehaviour
0x70GetProjectInfo—The project.
0x71SetProjectSettingsjson settingsA JSON merge patch (RFC 7386) for the settings object: a key set to null is removed, objects merge key by key, anything else replaces. The patch must be an object. The blocks the patch touches (its top-level keys) are applied to the running engine (ApplyProjectSettings), after the live state they change is captured (ProjectSettingsSnapshot: the layers, the input maps, the fixed timestep and gravity). If any block is refused, or the file can't be saved, that captured state is put back, so the engine runs exactly as before, even for a block the old settings didn't have; nothing is saved, and the Error lists the refused blocks ("Project settings refused: physics.fixedTimestep: -1 is not a positive number of seconds"). Source: editor-server/src/EditorServer.cpp — EditorServer::HandleGetProjectInfo, HandleSetProjectSettings, HandleSetStartupScene, SaveProject; tests: EditorProjectTest.GetProjectInfoDescribesTheProject, EditorProjectTest.SetProjectSettings*, EditorProjectTest.SetStartupScene*, EditorNoProjectTest.ProjectAndSceneFileCommandsNeedAProject

Design decision: settings change by merge patch, applied before they are saved PR #90

An inspector edits one value at a time, and the client shouldn't have to send (or even know) every block to change one, nor risk overwriting a block another tool added. A merge patch is a standard, one-line way to say "these keys, these values, remove these", which nlohmann::json implements. Applying before saving means the file never holds settings the engine refused, so the next start doesn't fail on them. Undoing a refused patch by applying the previous settings again isn't enough: a block the previous settings didn't have (a fresh project has none) would apply nothing and leave the new value running. So the live state the blocks change is captured before applying and put back exactly, keeping the running engine and the file in agreement. Only the blocks the patch touches are applied, so changing the gravity doesn't reload the input maps. The response is the saved project, so the client shows what was stored without a second request. Decided on #6 §(b) ("a partial object, merged ... applied live and saved"); #75.

user:// per project

user:// paths (saves, settings a game writes at run time) resolve under the folder ResourceLoader::Initialize is given. A project's is ProjectFile::UserDataPath():

%APPDATA%\N2Engine\<sanitised name>-<first 8 hex digits of projectId>     (Windows)
$HOME/.n2engine/<sanitised name>-<first 8 hex digits of projectId>       (elsewhere)

For example %APPDATA%\N2Engine\My_Game-8e0c3a8e. The name is sanitised to one safe folder name (ProjectFile::SanitizeFolderName): ASCII letters, digits, -, _ and . are kept, anything else becomes _, leading and trailing . and _ are dropped, at most 48 characters, Project when nothing is left. Initialize creates the folder. Without a folder (Initialize(root), as tests and plain folders do) user:// is the shared %APPDATA%\N2Engine as before (ProjectFile::UserDataBase()). GetProjectInfo reports the folder, and ResourceLoader::GetUserDataRoot() returns it.

Source: engine/src/io/ProjectFile.cpp — ProjectFile::UserDataPath, UserDataBase, SanitizeFolderName; engine/src/io/ResourceLoader.cpp — ResourceLoader::Initialize; tests: ProjectFileParseTest.TheUserDataFolderIsTheSanitisedNameAndTheIdsFirstEightDigits, ProjectFileParseTest.FolderNamesKeepOnlySafeCharacters, ResourceLoaderProjectTest.UserPathsResolveUnderTheProjectsOwnFolder, ResourceLoaderProjectTest.TwoProjectsGetTwoUserFolders

Design decision: each project's user:// is named after it and its id PR #90

One shared user:// folder meant two games on a machine read and overwrote each other's saves. The id makes the folder the project's own (two projects with the same name don't collide), and keeping it under the user's application data, not in the project folder, keeps run-time files out of the committed tree and matches where a shipped game writes. The readable name prefix lets a person find a game's saves; only 8 digits of the id are used because the name already separates almost every project. The cost: renaming the project starts a new folder (the old one is left alone), and a project copied without changing its id shares the original's saves, which a "duplicate project" command would avoid by giving the copy a new id. Decided on #6 §(a); #75.

Rescanning assets

RescanAssets (0x41, ResourceLoader::RescanAssets) indexes new and changed files and now also forgets deleted ones: their metadata, their UUID mapping and their cache entries are dropped, so they no longer load by path or UUID and no longer appear in GetAllAssets. Whoever still holds a loaded copy keeps it. The deleted file's .meta stays in .import/, so a file put back (a branch switch, an undo) gets its import settings and UUID back. A file counts as modified when its size or its modification time (whole Unix seconds, converted exactly with clock_cast, so an unchanged file never looks modified) changed PR #90. RescanAssets returns what changed (RescanResult: added, removed, modified, each sorted), and the host pushes it as an assetsChanged event when anything did:

{"added":[],"kind":"assetsChanged","modified":["res://scripts/Player.lua"],"removed":["res://scenes/Old.scene"],"seq":42}

Source: engine/src/io/ResourceLoader.cpp — ResourceLoader::RescanAssets, ScanDirectory; editor-server/src/EditorServer.cpp — HandleRescanAssets; tests: ResourceLoaderProjectTest.ARescanForgetsDeletedFilesAndReportsThem, ResourceLoaderProjectTest.ARescanReportsAddedAndModifiedFilesSorted, ResourceLoaderProjectTest.ADeletedLoadedAssetIsDroppedFromTheCache, EditorProjectTest.RescanAssetsReportsADeletedAssetAndForgetsIt

Design decision: a rescan forgets deleted files but keeps their .meta PR #90

A rescan that only ever added entries left deleted files listed, loadable by UUID until the load failed, and an asset browser would show files that aren't there. Forgetting them makes the index match the folder. The .meta is a different matter: it holds import settings (customData) a person chose, and a file can disappear for a moment (a branch switch, an editor's save-by-rename, an undo in a file manager); deleting its .meta would lose those settings for good. Path-derived UUIDs mean keeping it costs nothing: the file put back gets the same UUID either way. Cleaning up orphaned .meta files belongs with the asset commands (#6, E8). Decided for #75.

lua_project

lua_project has a project.n2proj of its own (name lua_project, no startup scene: its scene is built by assets/scene.lua). Its Main.cpp opens a folder the way the host does: with a project file, the projectId is the namespace, user:// is the project's own folder and its settings apply. A folder without one still runs, as before projects had files: the namespace comes from its path (NamespaceForProjectDir), user:// is the shared folder, and it logs a warning. The new id changed lua_project's asset UUIDs once, which is harmless: its scene is built from Lua and stores none.
