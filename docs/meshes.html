Meshes, models & textures

How the engine imports and draws content made outside it: images today, and meshes, materials and glTF models in the next phases of issue #3. This page covers the CPU-only assetimport library, the Texture asset and its import settings, the UV convention every textured thing follows, the GpuCache that shares GPU resources between components, and texture sampling on the software renderer. Textures reach the screen through the UI Image sprite PR #TBD.

The assetimport library PR #TBD

assetimport/ is a static library (N2Engine::assetimport) that turns file bytes into plain CPU structs. Today it decodes images (assetimport/include/assetimport/ImageDecoder.hpp); model parsing joins it in P3. It depends only on math and its vendored decoders, never on the engine, the renderer, GLFW, PhysX or nlohmann. The engine links it privately: no assetimport type appears in an engine header, and no stb type appears in an assetimport header.

stb_image 2.30 (external/stb_image/, see THIRD_PARTY_NOTICES.md) is compiled once, in assetimport/src/assetimport/ImageDecoder.cpp, with STB_IMAGE_STATIC so its symbols stay in that file. It is configured there: STBI_ONLY_PNG, STBI_ONLY_JPEG, STBI_ONLY_TGA, STBI_ONLY_BMP (PSD, GIF, HDR, PIC and PNM are left out), STBI_NO_STDIO (the engine reads files itself and decodes from memory), STBI_NO_LINEAR, STBI_MAX_DIMENSIONS 16384, and STBI_ASSERT a no-op in Release builds (stb's own assert in Debug).

Source: assetimport/CMakeLists.txt; assetimport/src/assetimport/ImageDecoder.cpp; external/stb_image/README.md

Design decision: asset import is its own CPU-only library PR #TBD

Parsers are where untrusted bytes meet the engine, so they need the most tests, and those tests should run anywhere. Putting image decoding (and later glTF and FBX parsing) in a library that depends only on math, as text/ does for fonts, lets assetimport_tests run every decoder without the engine, a window, a GPU or PhysX. Its output is library-neutral structs (ImportedImage), so a decoder can be swapped or a second one added (ufbx beside cgltf) without touching the engine. Decided on #3 (decision 3).

Image decoding PR #TBD

AssetImport::DecodeImage(std::span<const std::uint8_t> bytes, const ImageDecodeOptions &options) returns std::expected<ImportedImage, ImageDecodeError>.

  • Formats. PNG (1 to 16 bits per channel, every colour type, palette with or without tRNS, interlaced), JPEG (baseline and progressive), TGA (with or without RLE) and BMP (bottom-up and top-down, 1 to 32 bits per pixel). The decoder goes by the content, not the file name.
  • Always 8-bit RGBA. ImportedImage has width, height, channels (always 4), sourceChannels (what the file held: 1 grey, 2 grey + alpha, 3 RGB, 4 RGBA) and pixels, width × height × 4 bytes, rows tightly packed. Grey becomes (g, g, g, 255), so a grey PNG shows grey rather than red as an R8 texture would. Missing alpha is 255. 16-bit channels keep their high byte.
  • Row order. With options.flipY (the default) the bottom row of the picture comes first; without it the top row does. See the UV convention.
  • Size caps. The header is read first (stbi_info_from_memory), and nothing is decoded or allocated for an image wider or taller than kMaxImageDimension (16384), or whose RGBA pixels would exceed kMaxDecodedImageBytes (256 MiB: an 8192 × 8192 image fits, 8192 × 8193 doesn't). ImageDecodeOptions::maxDimension and maxDecodedBytes lower the caps for one call; values above the built-in caps are lowered to them. Decoding can briefly need more memory than the cap (stb's working buffers, about twice it for a 16-bit PNG). Input over 2 GiB is refused, since the decoder takes an int length.
  • Errors. An error has a code and a message for the log: EmptyInput; InputTooLarge; UnrecognizedFormat (not one of the four formats, or a corrupt or truncated header; stb's reason is in the message); DimensionsTooLarge (a side over the cap, or zero); DecodedSizeTooLarge; DecodeFailed (a readable header but corrupt, truncated or unsupported pixel data). A PNG or JPEG header over 16384 a side is refused by stb itself while it reads the header, so it reports UnrecognizedFormat with stb's "too large"; oversized TGA and BMP headers report DimensionsTooLarge. Either way nothing is decoded.
  • Thread-safe. No global decoder state is set (stb's failure reason is thread-local, and the flip is done here, not with stb's global flag).

Source: assetimport/include/assetimport/ImageDecoder.hpp; assetimport/src/assetimport/ImageDecoder.cpp — DecodeImage; tests: ImageDecoderTest.* (tests/assetimport/ImageDecoderTests.cpp)

Guarantee

Truncated or corrupt image data is an error, never a crash or an abort: every prefix of a stored and of a deflate-compressed PNG is decoded in ImageDecoderTest.EveryTruncationOfAPngIsAnErrorNotACrash (the only prefixes that decode are those missing just the final IEND chunk's CRC, which stb doesn't check; they give the whole image). Oversized headers are rejected before any pixel memory is allocated (OversizedDimensionsAreRejectedFromTheHeader, OversizedDecodedBytesAreRejectedFromTheHeader, with crafted BMP headers that carry no pixel data at all).

Design decision: fixed size caps, checked before decoding PR #TBD

stb_image is small and fast but not hardened; it has a history of CVEs, mostly in formats and paths the engine doesn't need. So only four formats are compiled in, and an image is measured from its header before anything is decoded: a malicious or broken file claiming 100000 × 100000 pixels costs a header read, not a 40 GB allocation. 16384 a side matches what GPUs commonly accept for a texture; 256 MiB decoded allows any 8192 × 8192 image, far beyond what a game texture needs, while a single bad file can't ask for gigabytes. The caps are compile-time constants, so a project can't raise them by accident; a caller can only lower them. Images are still trusted project assets: don't load downloaded images at runtime. Decided on #3 (decisions 2 and C).

The Texture asset PR #TBD

N2Engine::Rendering::Texture (engine/include/engine/rendering/Texture.hpp) is a Base::Asset with resource type "Texture". It holds CPU data only: GetWidth(), GetHeight(), GetPixels() (8-bit RGBA, the first row being v = 0) and GetSettings(). It never holds a GPU handle, so it loads headless and one texture can serve several renderers; each renderer gets its own GPU copy through GpuCache. A texture never changes after it is made; a reload makes a new object.

  • Files. .png, .jpg, .jpeg, .tga and .bmp, in any case, load as textures. Texture::RegisterLoader() registers the loader with Resources (and so ResourceLoader, which then scans and indexes those files). It is called by a static registrar in Texture.cpp and, because the linker can drop that file from a program that never names Texture, by ResourceLoader::Initialize too, as for fonts. See Loaders.
  • Loading. Texture::Load(path) reads the file, takes the settings from its .meta when ResourceLoader tracks it (defaults otherwise), and decodes it with DecodeImage. A file that can't be read, or doesn't decode, logs an error ("Cannot load texture <path>: <reason>") and the load returns null. GetSourcePath() is the file it came from.
  • From memory. Texture::CreateFromEncoded(bytes, settings, debugName) decodes image file bytes with the given settings; null and an error on failure.
  • At runtime. Texture::Create(width, height, rgbaPixels, options) makes a procedural texture from width × height × 4 bytes, the first row being v = 0, with TextureOptions for its filter, wrap and mipmaps (the defaults are TextureOptions::Default()). A zero size or a pixel count that doesn't match logs an error and returns null. Its UUID is random, so to be found by UUID (a saved Image sprite, say) it must be registered with Resources::RegisterAsset, and only resolves in that run.
auto icon = IO::Resources::Instance().Load<Rendering::Texture>("res://ui/icon.png");
image->SetSprite(icon); // UI::Image

std::vector<std::uint8_t> rgba = MakeNoise(64, 64);
auto noise = Rendering::Texture::Create(64, 64, rgba); // linear, repeat, mipmaps

Source: engine/include/engine/rendering/Texture.hpp; engine/src/rendering/Texture.cpp — Texture::Load, Texture::Create, Texture::CreateFromEncoded, Texture::RegisterLoader; engine/src/io/ResourceLoader.cpp — ResourceLoader::Initialize; tests: TextureCreateTest.*, TextureAssetTest.*

Texture import settings PR #TBD

A project texture takes its settings from its .meta file's customData (see .meta files), in a "texture" object. Every key is optional:

{"texture": {"srgb": true, "filter": "linear", "wrap": "repeat", "mipmaps": true, "flipY": true}}
KeyValuesDefaultEffect
srgbtrue, falsetrueWhether the colours are sRGB-encoded. Recorded only: nothing reads it yet (why).
filter"linear", "nearest""linear"TextureOptions::filter. On the software renderer, bilinear or nearest sampling (below).
wrap"repeat", "clamp""repeat"TextureOptions::wrap (Repeat or ClampToEdge). One value for both axes.
mipmapstrue, falsetrueTextureOptions::mipmaps: OpenGL generates a mip chain (trilinear with linear). The software renderer has none.
flipYtrue, falsetrueStore the rows bottom first, so the image shows upright (the UV convention). Turn it off only for data meant to be read top row first.

filter, wrap and mipmaps map one to one onto TextureOptions, and their defaults are TextureOptions::Default(), what CreateTexture did before options existed. Texture::ParseSettings(customData, defaults) does the parsing exactly as Font::ParseAtlasSettings does: a missing key keeps the default; a key with the wrong type or an unknown value is ignored with a warning (Texture settings: ignoring "filter": "cubic" (expected "linear" or "nearest")); a "texture" member that isn't an object is ignored with one warning; unknown keys are ignored silently. The settings are read when the texture loads, so after editing a .meta the texture must be loaded again (rescan, then Reload or a new run).

Source: engine/src/rendering/Texture.cpp — Texture::ParseSettings, TextureSettings::ToTextureOptions; tests: TextureSettingsTest.*, TextureAssetTest.LoadsWithTheSettingsFromItsMeta, TextureAssetTest.BadSettingsInTheMetaWarnAndKeepTheDefaults

Design decision: sRGB is recorded, not applied PR #TBD

Image files are almost always sRGB, and correct lighting would decode them to linear (an SRGB8_ALPHA8 texture on OpenGL, a lookup table on the software renderer) and encode the result for display. Neither backend has sRGB textures or an sRGB framebuffer today, and the engine lights in gamma space. Turning sRGB on for textures alone would darken every textured surface, and doing it properly changes every colour the engine draws, UI included. So P1 reads and keeps the setting, defaulting to true to describe typical files, and it changes nothing until the engine-wide linear-lighting option arrives in P4a, which will default to off. Projects can set the flag correctly now and it will take effect then. Decided on #3 (decision A).

The UV convention PR #TBD

The engine's texture coordinates are v-up: v = 0 is the first row of pixel data, and that row is the bottom of the picture. u = 0 is the left edge. This is what the existing geometry already assumes:

  • the UI Image quad has uv (0, 0) at the bottom-left of its rect (Image);
  • the CubeRenderer's bottom vertices have v = 0 and the QuadRenderer's top-left has v = 1;
  • OpenGL samples v = 0 from the first row uploaded.

Image files store the top row first, so texture assets are decoded with flipY on by default: the stored rows go bottom to top and the image shows upright everywhere above. SoftwareImageGoldenTest.ASpriteFromAnImageFileShowsUpright pins this: a 2 × 2 BMP whose top-left pixel is red shows red in the top-left quadrant of the screen. A raw texture given to IRenderer::CreateTexture is uploaded as given, so its first row is v = 0.

Two exceptions keep their own conventions: the SDF glyph atlas uses y-down uvs internally, because the text code produces and consumes them (TextRenderer's mesh); and formats whose UVs are v-down, such as glTF, are converted by their importer with v' = 1 − v (P3), never by the renderer.

Design decision: textures are stored bottom row first PR #TBD

Something has to flip: image files are top row first, and the engine's existing geometry (the UI quad, the cube, sphere and quad primitives) and OpenGL's upload are v-up. Flipping the images once, at import, changes nothing that exists and costs one row copy per load. The alternative, top row first with v-down UVs everywhere, would mean changing every primitive and the Image quad, and every future importer still has to agree with one or the other. Unity makes the same choice. The flip lives in the importer, not the renderer, so a texture's pixels mean the same thing to every backend, and a format with v-down UVs (glTF) flips its UVs instead. Decided on #3 (decision 4).

GpuCache: shared GPU resources PR #TBD

Rendering::GpuCache (engine/include/engine/rendering/GpuCache.hpp, engine-internal) holds one GPU resource per (renderer, source asset, kind), created on first use, shared by every component that asks for it, and destroyed when the last one lets go. Today it holds textures: AcquireTexture(renderer, texture) for Texture assets (uploaded as RGBA8 with the texture's filter, wrap and mipmaps) and AcquireFontAtlas(renderer, font) for fonts' SDF atlases (single channel, TextureOptions::SdfAtlas()). Meshes and materials join it in P2. Users are the UI Image (its sprite) and every TextRenderer and UIText (their font's atlas, through TextDrawing::DrawResources), which share one atlas per font and renderer as before.

An acquire returns a move-only GpuCache::Handle: one user's share. It is false when there is nothing to upload (a null or unloaded asset, an empty atlas) or the renderer couldn't create the resource, and then no entry is made. The rules, the ones the text atlas cache had:

  1. Refcounted. Each handle is one user. Release(true), or a move assignment over a handle, gives the share up; the last share destroys the resource on its renderer, if that renderer is still alive.
  2. The asset stays alive. An entry holds its asset's shared_ptr, so the asset's address, half the key, can't be reused by another asset while the entry exists.
  3. Renderers are told apart by their lifetime token. Each entry keeps its renderer's lifetime token. An entry whose renderer has been destroyed or shut down is never handed out and its resource is never destroyed (the renderer freed it); the next acquire with that key replaces it.
  4. A stale handle can't touch a new entry. A release names the token its handle was acquired with, so a handle from a destroyed renderer never releases, or destroys, the entry that a new renderer at the same address has made since.
  5. Destructors don't call the renderer. A handle destroyed without Release gives up its share without calling the renderer, which may be gone or mid-destruction; a resource whose last share went that way stays with the renderer until it shuts down.
  6. Leaked on purpose. The cache is never destroyed, so a component that Lua keeps alive until exit can still release its share after function-local statics are gone.

GetEntryCount() and GetUserCount(renderer, source) report the cache's state for tests and diagnostics. The cache is used on the main thread only, like the components that draw.

Source: engine/include/engine/rendering/GpuCache.hpp; engine/src/rendering/GpuCache.cpp; engine/src/rendering/TextDrawing.cpp — DrawResources::EnsureAtlasTexture; engine/src/ui/Image.cpp — Image::EnsureSpriteTexture; tests: GpuCacheTest.*, ImageSpriteTest.* (tests/engine/rendering/GpuCacheTests.cpp), and unchanged, TextRendererTest.*, UITextTest.*, SoftwareTextGoldenTest.*

Design decision: one GPU cache for every shared resource PR #TBD

Textures, and soon meshes and materials, are CPU assets that many components draw. Uploading one copy per component wastes memory and upload time, and each kind of resource would otherwise need its own copy of the subtle rules for renderers that are destroyed or re-created at the same address. Text already had those rules, privately, for font atlases. GpuCache is that cache generalised: keyed by renderer, source asset and kind, refcounted, guarded by the lifetime token, and leaked for static-destruction order, with the text atlas moved onto it so there is one implementation, tested once. A component keeps only handles, so the lifetime scenarios (a new renderer, one re-created at the same address, release after the renderer is gone) behave the same for every user. Decided on #3 (decision B).

Sampling on the software renderer PR #TBD

The software renderer's unlit and lit shaders sample a texture through SWTexture::SampleFiltered, following its filter:

  • Linear (the default for texture assets and for CreateTexture without options): SampleBilinear, every channel filtered as OpenGL's GL_LINEAR without mipmaps. Texel centres are at (i + 0.5) / size; the four texels around the sample point are weighted by distance; neighbours outside the texture are clamped or wrapped as wrap says. It shares its footprint code with the text shader's SampleFirstChannelBilinear. Each channel is rounded to 8 bits.
  • Nearest: Sample, picking the texel as GL_NEAREST does: texel i covers i / size to (i + 1) / size, and a clamped u = 1 is the last texel. (It used to scale by size − 1, so a texture two texels wide showed its second texel only at u = 1 exactly.)

Both read missing channels as OpenGL reads R8/RG8/RGB8 textures (green and blue 0, alpha 255), and read a NaN or infinite coordinate as 0. There are no mipmaps on this backend, so distant textures alias. The text shader is unchanged. SoftwareImageGoldenTest.ALinearSpriteIsFilteredIntoAGradient checks a Linear 2 × 1 texture draws a gradient between its texel centres and the Nearest one two flat halves.

Source: renderer/include/renderer/software/SWTexture.hpp — SWTexture::Sample, SampleBilinear, SampleFiltered; renderer/src/software/SoftwareRenderer.cpp — ShadeUnlitPx, ShadeLitPx; tests: TextureOptionsTest.SoftwareNearestSamplingPicksTexelsAsGLNearestDoes, TextureOptionsTest.SoftwareBilinearRgbaSamplingMatchesGLLinear

Meshes (planned)

The CPU Mesh asset with submeshes as index ranges and bounds, the built-in Cube, Sphere and Quad meshes, and the MeshRenderer component come in P2 (#59). Their GPU meshes will be shared through GpuCache.

Materials (planned)

The Material asset (base colour and texture, vertex colour, alpha mode and cutoff, double-sided, smoothness) comes in P2; emissive, normal maps, sRGB and PBR in P4 (#61).

Models and glTF import (planned)

glTF 2.0 import through cgltf, the Model asset, sub-asset UUIDs, Model::Instantiate and the Blender export workflow come in P3 (#60); optional FBX and OBJ through ufbx in P5 (#62). Embedded and external model images will load as Textures through the same decoder.

Axes, winding and units (planned)

The engine renders right-handed and Y-up, with front faces counter-clockwise and units in metres; objects face +Z and the camera looks down −Z. This section will document how imported models map onto that (P3), alongside the UV convention above.

Lua PR #TBD

Scripts reach textures through the UI Image: image:SetSprite("res://ui/icon.png") loads the file through Resources (an error, keeping the current sprite, if it doesn't load), image:SetSprite(nil) clears it, and image:GetSprite() returns the path or nil. See UI from Lua. There is no Texture table yet.

local icon = UI.CreateElement("Icon")
local image = icon:AddComponent("Image")
image:SetSprite("res://ui/coin.png")
print(image:GetSprite()) -- res://ui/coin.png
