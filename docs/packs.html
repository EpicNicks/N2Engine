Packs & the virtual filesystem

A packaged game is one file, game.n2pack: the project folder's project.n2proj, assets/ and .import/ in a zip or 7z pack. The engine reads every game file through a virtual filesystem, so a player mounts the pack where the game's folder would be and opens that folder as it opens any project. This is stage 4 of the build targets plan PR #338.

The virtual filesystem

IO::Vfs (engine/include/engine/io/Vfs.hpp) is the one door through which the engine reads a game's files. A path inside a mount is served by that mount; any other path by the disk, exactly as before. Paths stay ordinary std::filesystem paths, so nothing above this layer changes its spelling.

MountWhat it serves
none (the disk)Every path not inside a mount: the editor, development runs, user://
folder (MakeFolderMount)A folder on disk at another path (a platform bundle's assets). Reads are confined to it: a path that leaves the folder is not found.
zip (Pack::OpenZip)A zip, stored or deflate (miniz's inflate). ZIP64 is read.
7z (Pack::OpenSevenZip)A 7z archive, read with the LZMA SDK's decoder: LZMA, LZMA2 and the branch filters; PPMd is not compiled in.
  • Vfs::Mount(at, mount) makes a mount's files appear at at, an absolute path that need not exist. The deepest mount wins for its own paths; a sibling whose name only starts the same (game and gamex) is not inside.
  • Stat, Exists, IsDirectory, IsRegularFile, ReadBytes, ReadText, ReadBytesCapped (refused before reading when larger than a limit) and ListFiles. Times are milliseconds since the Unix epoch, the unit the asset index keeps.
  • Pack::Open tells the two formats apart by their first bytes.

What goes through it

Every read of game data: project.n2proj (ProjectFile::Load), the asset scan and its .meta files (ResourceLoader), scripts (LuaScript, so require too), scenes, prefabs, materials, textures, models and the buffers and images a glTF names (the importer takes a reader, ModelImportSettings::readFile), fonts, the four audio formats (decoded from memory now: WAV, OGG, MP3, FLAC) and shader files. On disk each reads the same bytes it read before; a project opened from its folder behaves exactly as it did.

A project whose root is inside a mount is packed (ResourceLoader::IsPacked): it is scanned from the pack's directory and is always read-only, so no .meta, no .import folder and no .n2/asset-state.json is ever written. user:// is still the game's own folder on disk.

Guarantee: a pack cannot reach outside itself, and a damaged pack is refused

An entry name with a .., . or empty segment, a leading /, a drive, a backslash or a control character (zip slip) refuses the whole pack when it opens (Pack::NormalizeEntryName). Every offset and size is checked against the file before anything is read; an entry may hold at most 1 GiB uncompressed and a pack at most 1 000 000 entries; a name twice, a stored entry whose sizes differ, damaged deflate data and a CRC that does not match are errors that name the file. Encrypted zip entries and other compression methods are refused with the reason. Tests: VfsPackTest.EntryNamesThatCouldLeaveThePackAreRefused, VfsPackTest.DamagedPacksAreRefusedWithTheReason.

Pack formats

Decision D6: zip by default, 7z as an option. A target's build.targets.<target>.pack or n2build's --pack chooses.

packWhat it isDefault for
zipDeflate where it saves bytes, stored where it does not (an image or a sound that is already compressed)Desktop
storedA zip with nothing compressed: reading is a copyWeb: the web server compresses the download, and inflating twice would only cost the player time
7zNon-solid (7z -ms=off): every file is its own block, so a player decodes only the file it reads. Written by 7-Zip's command line, which n2build looks for on PATH and in 7-Zip's folder on WindowsNone yet (the mobile targets may)
folderNo pack: the project folder copied as it is (game/ beside the player)None: for a developer who wants to look inside a package

A solid 7z still reads: its block is decoded once and kept until another block is asked for, only slower and with more memory. The web player reads zip packs only, so the 7z decoder is never in the web binary; n2build refuses --pack 7z for the web target.

The cook step

node tools/n2build/n2build.mjs cook --target linux --project path/to/game [--out game.n2pack] [--pack zip|stored|7z] [--strip-shader-sources]
  1. The module-list check for the target (the target's own list): a game that uses a module its list leaves out is refused, naming the file and line.
  2. The files a game needs: project.n2proj, assets/ and .import/. Not .n2/, editor/ (editor extensions), sources or tools.
  3. A manifest of every file's size and SHA-256, n2pack-manifest.json inside the pack and <pack>.manifest.json beside it.
  4. The shaders: each .n2shader is cooked into .import/shaders/<uuid>/ for the target's renderers.
  5. The pack. A zip is written by n2build itself, in name order with a fixed time, so the same project always makes the same bytes.

n2build build cooks as part of packaging, with the same command line as before: a desktop package holds the player, its libraries and game.n2pack; the web package's index.data holds /game.n2pack instead of the project folder (n2build passes -DN2ENGINE_WEB_PACK; a CMake build without it preloads the folder as before).

Shaders in a pack user shaders, stage 6

A project's .n2shader files (user shaders, orchestrator/proposals/user-shaders.md) are cooked by the same step. For each one under assets/ n2build runs tools/n2shader and writes .import/shaders/<uuid>/, the folder the engine's Shader::MakeBlob reads: manifest.json and one payload per renderer the target uses, byte for byte what node tools/n2shader/n2shader.mjs cook writes. The <uuid> is the asset's, from its .meta (a shader that was never opened in the editor has none: n2build says so and stops). Names are sorted and nothing is time-stamped, so the same project and tools make the same pack. Whatever .import/shaders/ held on disk (the editor's cook is for the editor's own renderer) is replaced by what is cooked for the target.

Package kindPayloads
desktop (Windows, Linux, macOS)vulkan (SPIR-V) and gl (GLSL 330 text)
webwebgpu (WGSL, through Tint) only
android, iosvulkan only

A target descriptor may name its own list with shaderTargets. A --pack folder build copies the project folder as it is, so it holds whatever the editor cooked.

  • Tools. The cook needs glslangValidator, spirv-val, spirv-dis and spirv-cross (the Vulkan SDK, or glslang-tools, spirv-tools and spirv-cross from apt); a project with shaders and a missing tool is refused with what to install. The web target also needs Tint. n2build finds it through TINT, PATH, then its own copy, and otherwise downloads it once: the pinned Dawn release (the one the CI job takes Tint from), read as a stream, keeping only bin/tint (the Windows archive is 119 MB for a 7.6 MB tint.exe), and used only when its SHA-256 is the pinned one. It is kept in %APPDATA%\N2Engine\tools (or ~/.local/share/n2engine/tools). It is a build tool: it is never in a pack, a player or the editor (THIRD_PARTY_NOTICES.md, "Not shipped").
  • Strip sources. n2build cook --strip-shader-sources (or "stripShaderSources": true in build.targets.<target> of project.n2proj) leaves each .n2shader's header in the pack but not its GLSL, and leaves out the OpenGL payload (it is readable source), for a studio that does not want its shader code shipped. Such a pack cannot recompile a shader, and an OpenGL player draws the fallback for it (the built-in unlit shader, with one logged error naming the shader).
  • Nothing about shaders is game state. The cooked data is render-only: it is not in rollback snapshots, replication or the golden-replay hashes.

Tests: tools/n2build/shaders.test.mjs (the pack's shader files and their order, the same bytes as n2shader cook, the strip option, the Tint pin and download against a fake server).

Compiling shaders on the device user shaders, stage 7

A shipped game always carries the cooked payloads (and its sources, unless stripped). When a payload is missing, stale (the header or the contract changed since the cook) or is for another backend, the engine can build it from the .n2shader itself, once, and keep the result. Shader::MakeBlob tries the cooked data first (MakeCookedBlob) and then this:

BackendOn the device
OpenGL (desktop)Always. The payload is the generated text (the prelude, the Material block, the author's stage behind a #line); the driver compiles it. No compiler of ours is involved, so no option is needed.
Vulkan (desktop)With glslang linked and the setting on. Build with -DN2ENGINE_RUNTIME_SHADER_COMPILER=ON (off by default; it pulls the pinned glslang 15.3.0 from cmake/Glslang.cmake, SHA-256 checked, and adds about 4–5 MB to a binary) and turn on RenderSettings::SetRuntimeShaderCompile (the editor host does; a player's project setting is rendering.runtimeShaderCompile, false by default). The result is what glslangValidator -V --target-env vulkan1.1 makes: the same flags, so the same SPIR-V bytes when the glslang is the same version.
WebGPU, Android, iOSNever: the web ships cooked WGSL (the browser compiles it), and the mobile players ship cooked SPIR-V.
  • Same text as the cook. UserShaderCompiler::BuildSource is the C++ twin of tools/n2shader/lib/prelude.mjs: the prelude templates of renderer/shaders/user/prelude are embedded at configure time (engine/CMakeLists.txt), the Material block is laid out as std140 the same way, and glslang's own reflection of the compiled Material block (size and each member's offset) is checked against that layout before the module is used. UserShaderCompilerTest compares the OpenGL text and, in a build with glslang, the SPIR-V with the cook's committed output (tests/renderer/fixtures/user-shaders).
  • Not done on the device: the cook's lint (an authoring aid; what protects a player is the size limits and ValidateUserShaderBlob's SPIR-V allow-list) and WGSL (Tint is not linked). A compile error is a refusal with the cook's form of diagnostic, file:line: ..., logged once with the Material's fallback; it never stops a frame. A pack made with stripped sources has nothing to compile.
  • The shader cache. user://cache/shaders/<key>/ holds the manifest and the payload; the key is the SHA-256 of the file's text, the prelude templates, the contract, the compiler (Glslang Version: 11:15.3.0) and the target, so a changed engine, prelude or glslang is a different key. An entry is used only when its payload is the one its manifest hashed, written through a temporary file and renamed, and the folder is pruned past 256 entries (oldest first). A missing or damaged entry only means compiling again.
  • The Vulkan pipeline cache. The renderer keeps one VkPipelineCache, made on the first pipeline, so a pipeline is built once per driver rather than every run: saved at shutdown to user://cache/vk-pipelines-<vendor>-<device>.bin and read back only when the header names this vendor, device and driver build (pipelineCacheUUID), at most 64 MiB. Pipelines are still made on first use; pre-warming a Material's likely states at load is not done yet.
  • Not isolated. glslang runs on the calling thread (the first draw of a Material), not in a worker or another process, and has no time limit: it is the opt-in, hostile-input surface of proposal section 8, which is why it is off in players. Untrusted mods should ship cooked payloads.

How a player finds its game

The desktop player (players/desktop, Player::ResolveGame):

  • a folder argument, or the default game folder beside the player, that exists: the folder, from disk;
  • a pack named directly (n2player path/to/game.n2pack): mounted at path/to/game;
  • a folder that does not exist with <folder>.n2pack beside it: that pack, mounted at the folder. A packaged game is this case.

A folder that exists wins over a pack beside it (a developer's unpacked game). The web player mounts /game.n2pack at /project when the package holds one. The Android player copies game.n2pack out of the APK's assets into the app's files folder (an APK asset cannot be read at random positions) and mounts that copy (Android: the player); the iOS player mounts game.n2pack where it is in the app bundle (iOS & macOS).

Not done yet

  • Persistent web saves. user:// on the web is in memory (Emscripten's MEMFS): a game's saves are lost when the page closes. Mounting IDBFS there and syncing after each write is the next step for the web; until then, this is the gap.
  • Streaming reads. A file is read whole; a mount that streams (large audio, video) can come later behind the same interface.
