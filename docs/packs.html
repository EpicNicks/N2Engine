Packs & the virtual filesystem

A packaged game is one file, game.n2pack: the project folder's project.n2proj, assets/ and .import/ in a zip or 7z pack. The engine reads every game file through a virtual filesystem, so a player mounts the pack where the game's folder would be and opens that folder as it opens any project. This is stage 4 of the build targets plan PR #TBD.

The virtual filesystem

IO::Vfs (engine/include/engine/io/Vfs.hpp) is the one door through which the engine reads a game's files. A path inside a mount is served by that mount; any other path by the disk, exactly as before. Paths stay ordinary std::filesystem paths, so nothing above this layer changes its spelling.

MountWhat it serves
none (the disk)Every path not inside a mount: the editor, development runs, user://
folder (MakeFolderMount)A folder on disk at another path (a platform bundle's assets). Reads are confined to it: a path that leaves the folder is not found.
zip (Pack::OpenZip)A zip, stored or deflate (miniz's inflate). ZIP64 is read.
7z (Pack::OpenSevenZip)A 7z archive, read with the LZMA SDK's decoder: LZMA, LZMA2 and the branch filters; PPMd is not compiled in.
  • Vfs::Mount(at, mount) makes a mount's files appear at at, an absolute path that need not exist. The deepest mount wins for its own paths; a sibling whose name only starts the same (game and gamex) is not inside.
  • Stat, Exists, IsDirectory, IsRegularFile, ReadBytes, ReadText, ReadBytesCapped (refused before reading when larger than a limit) and ListFiles. Times are milliseconds since the Unix epoch, the unit the asset index keeps.
  • Pack::Open tells the two formats apart by their first bytes.

What goes through it

Every read of game data: project.n2proj (ProjectFile::Load), the asset scan and its .meta files (ResourceLoader), scripts (LuaScript, so require too), scenes, prefabs, materials, textures, models and the buffers and images a glTF names (the importer takes a reader, ModelImportSettings::readFile), fonts, the four audio formats (decoded from memory now: WAV, OGG, MP3, FLAC) and shader files. On disk each reads the same bytes it read before; a project opened from its folder behaves exactly as it did.

A project whose root is inside a mount is packed (ResourceLoader::IsPacked): it is scanned from the pack's directory and is always read-only, so no .meta, no .import folder and no .n2/asset-state.json is ever written. user:// is still the game's own folder on disk.

Guarantee: a pack cannot reach outside itself, and a damaged pack is refused

An entry name with a .., . or empty segment, a leading /, a drive, a backslash or a control character (zip slip) refuses the whole pack when it opens (Pack::NormalizeEntryName). Every offset and size is checked against the file before anything is read; an entry may hold at most 1 GiB uncompressed and a pack at most 1 000 000 entries; a name twice, a stored entry whose sizes differ, damaged deflate data and a CRC that does not match are errors that name the file. Encrypted zip entries and other compression methods are refused with the reason. Tests: VfsPackTest.EntryNamesThatCouldLeaveThePackAreRefused, VfsPackTest.DamagedPacksAreRefusedWithTheReason.

Pack formats

Decision D6: zip by default, 7z as an option. A target's build.targets.<target>.pack or n2build's --pack chooses.

packWhat it isDefault for
zipDeflate where it saves bytes, stored where it does not (an image or a sound that is already compressed)Desktop
storedA zip with nothing compressed: reading is a copyWeb: the web server compresses the download, and inflating twice would only cost the player time
7zNon-solid (7z -ms=off): every file is its own block, so a player decodes only the file it reads. Written by 7-Zip's command line, which n2build looks for on PATH and in 7-Zip's folder on WindowsNone yet (the mobile targets may)
folderNo pack: the project folder copied as it is (game/ beside the player)None: for a developer who wants to look inside a package

A solid 7z still reads: its block is decoded once and kept until another block is asked for, only slower and with more memory. The web player reads zip packs only, so the 7z decoder is never in the web binary; n2build refuses --pack 7z for the web target.

The cook step

node tools/n2build/n2build.mjs cook --target linux --project path/to/game [--out game.n2pack] [--pack zip|stored|7z]
  1. The module-list check for the target (the target's own list): a game that uses a module its list leaves out is refused, naming the file and line.
  2. The files a game needs: project.n2proj, assets/ and .import/. Not .n2/, editor/ (editor extensions), sources or tools.
  3. A manifest of every file's size and SHA-256, n2pack-manifest.json inside the pack and <pack>.manifest.json beside it.
  4. The pack. A zip is written by n2build itself, in name order with a fixed time, so the same project always makes the same bytes.

n2build build cooks as part of packaging, with the same command line as before: a desktop package holds the player, its libraries and game.n2pack; the web package's index.data holds /game.n2pack instead of the project folder (n2build passes -DN2ENGINE_WEB_PACK; a CMake build without it preloads the folder as before).

How a player finds its game

The desktop player (players/desktop, Player::ResolveGame):

  • a folder argument, or the default game folder beside the player, that exists: the folder, from disk;
  • a pack named directly (n2player path/to/game.n2pack): mounted at path/to/game;
  • a folder that does not exist with <folder>.n2pack beside it: that pack, mounted at the folder. A packaged game is this case.

A folder that exists wins over a pack beside it (a developer's unpacked game). The web player mounts /game.n2pack at /project when the package holds one.

Tests

  • tests/engine/io/VfsPackTests.cpp: the three committed packs (tests/assets/packs, made by make_packs.py: a zip with deflate and stored entries, a non-solid and a solid 7z) read the same bytes; folders, listing, names that leave the pack, damaged packs, mount precedence and confinement.
  • tests/engine/io/PackedProjectTests.cpp: lua_project run from its folder and from a pack of it indexes the same assets with the same UUIDs and types and loads each to the same thing, and nothing is written where the pack is mounted; a glTF in a pack reads its .bin from the pack.
  • tests/players/PlayerOptionsTests.cpp: AGameIsAFolderOrAPack.
  • tools/n2build/n2build.test.mjs: the files a pack holds, reproducible zips that CMake's own archiver extracts, the manifest, the module check, a non-solid 7z (when 7-Zip is installed), the pack format's precedence, a desktop package with game.n2pack, the web plan's N2ENGINE_WEB_PACK.

Not done yet

  • Persistent web saves. user:// on the web is in memory (Emscripten's MEMFS): a game's saves are lost when the page closes. Mounting IDBFS there and syncing after each write is the next step for the web; until then, this is the gap.
  • Platform bundles. Android's APK assets and iOS's app bundle are mounts the mobile stages add (an IMount over AAssetManager, a folder mount over the bundle).
  • Streaming reads. A file is read whole; a mount that streams (large audio, video) can come later behind the same interface.
