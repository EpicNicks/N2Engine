Design decisions

Why the engine is built the way it is: the product and architecture choices, and the low-level mechanisms and trade-offs, each with the reasoning the repository records and the alternatives it rejected.

  4. Web build and WebGPU strategy
    • The web player started as the software renderer drawing to a canvas
    • The baseline web build is single-threaded
    • Run() is split into BeginRun, RunFrame and EndRun
    • Stand-ins for GLFW and OpenAL first, the real thing in its own stage
    • The software player renders at most 1280 wide and the browser scales
    • The web player has its own wasm loader and fetches the pack asynchronously, not lazily
    • Web audio links Emscripten's OpenAL port and drops, not queues, sounds asked for before the unlock
    • PhysX for the web is built from the pinned source in the web job, scalar, no WebAssembly SIMD
    • Size budgets are the measured size plus about 15 percent, raised on purpose
    • One wasm carries software and WebGPU renderers; WebGPU is automatic, software is the permanent fallback
    • The web build uses the same Dawn release as the native test harness
    • GPU particles and soft bodies in the browser use WebGPU compute, resolved at runtime
  5. Rendering
    • Why there are four renderers
    • Vulkan was rewritten on the existing renderer interface; it always renders offscreen
    • Shaders are compiled to SPIR-V at build time
    • Vulkan is tested on a software driver, with the validation layer failing tests
    • WebGPU shaders are hand-written WGSL tied to the Vulkan interface by a parity test
    • Dawn is a pinned prebuilt release, and the native WebGPU renderer exists only as a CI harness
    • Every WebGPU device error fails the tests
    • Matrices are row-major in the engine; each backend adapts at the edge (copied as is on Vulkan, transposed on upload on WebGPU)
    • Materials are a shared, fixed std140 block written by name (BlockMaterial)
    • Per-draw data goes through a ring of uniform chunks, with the lighting block copied once per chunk per version
    • A buffer a frame may still read is never written or freed at once; handles carry a generation
    • Blending copies OpenGL exactly, and the renderer never sorts
    • Linear lighting is off by default and applies to the lit shader only
    • The camera looks down -Z while objects face +Z
    • Textures are stored bottom row first (flipY on import)
    • Built-in shaders only: no user shaders in v1; effects are fixed uniforms
    • User shaders (.n2shader): proposed, not merged
    • Apple GPU rendering uses MoltenVK; native Metal is not planned
    • The software renderer cannot blend, so it cuts out and alpha-tests; it copies uniforms per draw
    • One Sprite2D component, always in the Transparent queue
    • Text is an SDF atlas with one cached mesh per text, shared by world and UI
  6. Physics backends
    • Gameplay code reaches physics only through a small backend interface
    • Jolt is the deterministic 3D backend; PhysX cannot be
    • PhysX stays the default and the server-authoritative backend
    • A custom physics engine was rejected; Jolt and Box2D were integrated instead
    • Jolt is vendored, pinned and always built deterministic
    • The backend is chosen per project, and an unavailable one never degrades a Deterministic project
    • GPU physics is off by default
    • physics.deterministic is the same-build repeatability option, separate from the Deterministic preset
    • The Deterministic preset stays single-threaded Jolt
    • The Jolt adapter avoids every nondeterministic Jolt API
    • A trigger on Jolt is a sensor sub-shape of its body, not a second body
    • What a Jolt snapshot holds, and what it refuses
    • One rule set for scene queries on both 3D backends (and 2D)
    • Contact impulses on Jolt are an estimate
    • The character controller is engine-owned, built from backend capsule queries
    • Joints are an optional feature bit, reported by Jolt only
    • Box2D is a separate 2D module with a concrete world and no backend interface
    • 2D event names carry a 2D suffix; changes inside a handler run immediately
    • 2D is in rollback snapshots and the state hash; a 2D world created after a rollback session began cannot be rewound past its creation
    • Physics iteration is ordered by handle and gameplay data is ordered by net id
    • 3D rigidbody mass is authoritative; 2D mass comes from shapes unless set
    • Inactive objects leave physics; Enter and Exit stay balanced
    • A feature failure is the feature's, not the scene's
    • Particles and soft bodies each have a real CPU backend
    • PhysX on Linux and the Windows slim package are pinned by hash
  7. Determinism and math
    • Strict floating point, not fixed point
    • N2ENGINE_STRICT_FP is a build profile on every target, on by default
    • Engine-owned sin, cos, atan, exp and log, written as short series
    • Flush-to-zero off everywhere, with a guard on every network tick
    • SIMD tiers are an algorithm choice; the default is scalar; determinism requires scalar
    • No fused multiply-add on aarch64; NEON is a separate enum value
    • Lua gets Ordered.pairs, a seed switch and a small Lua patch; the seed stays off by default
    • Seeding Random is opt-in
    • In network modes the netcode owns the tick; timeScale becomes presentation-only
    • Determinism is proved by CI, not argued
  8. Netcode
    • Two presets, and a Deterministic project is refused when its requirements are unmet
    • Lockstep first, rollback second
    • The rollback contract: only declared state rolls back; spawns are parked
    • The packet layer is our own library, not ENet or GameNetworkingSockets
    • The network simulator is integer-only with its own random generator
    • Encryption is our own AEAD layer on Mbed TLS primitives, not DTLS
    • The UDP transport drains the socket, then sweeps idle peers
    • Browsers connect over WebSocket first
    • Deterministic sessions use a star through the server in relay mode; no matchmaking or NAT traversal
    • N2Server is its own executable with strict arguments
    • Replication is opt-in per field, with deltas against the newest acknowledged value
    • The join fingerprint, and what is in it
    • Scene objects are matched by UUID and numbered in UUID order, with nothing on the wire
    • Inputs: a fixed layout sampled per tick, redundant sends, a server-side delay, and a pull model
    • Clock sync: best-half median of 16, slewed, never backwards; a stream tick instead of a heartbeat
    • Prediction covers only the owner's kinematic character; riding platforms is predicted in the platform's frame
    • Lag compensation uses the engine's own hitbox history, capped at 200 ms
    • On a desync the session ends with a report and a replay
    • Deterministic sessions allow only cosmetic RPCs; RPCs are addressed by position
    • No late join in lockstep v1; spectators can later be promoted to a player
    • Wire versions rise on any change; refusals name the reason
  9. Lua scripting and its sandbox
    • Five libraries, an instruction budget and a memory cap per entry
    • The editor host that edits never runs project Lua
    • One sandbox builder with profiles serves declarations and editor extensions
    • Free registry slots are reserved before unprotected references
    • A marked patch in vendored sol2 instead of rewriting binding lambdas
    • Script data is declared in a table the editor can read
  10. Editor host, frontend and MCP bridge
    • A headless host plus a separate Electron frontend, joined by a binary protocol
    • One protocol.json is the spec; clients and vectors are generated from it
    • Protocol versions are additive: new fields are trailing, a minor bump never breaks an older client
    • Play mode runs in a separate child process started by the launcher
    • The editor camera, hierarchy order and dirty state belong to the server
    • One JSON project file; the project id is the asset UUID namespace; saves are atomic
    • Picking is a CPU ray against bounds and shapes, not a physics query
    • The asset watcher polls the directory listing, gated on a client
    • Moving an asset keeps its UUID (the .meta is the identity)
    • Prefabs: self-contained instances with a stored override list; the stage swaps the loaded scene
    • Editor extensions are host-side Lua with declarative UI, in editor/, opt-in twice
    • The MCP bridge is a separate stdio process, an ordinary protocol client
    • The host mixes audio on a loopback device paced by elapsed time, and serves it by a separate request
    • Engine stats are polled at a low rate with timers off until someone asks
    • The frontend uses its own panel registry and CodeMirror, not a docking library or Monaco
  11. Security posture
    • The host listens on loopback only, and a non-loopback bind fails closed
    • Per-user tokens (hashed) and three roles; a viewer may not play
    • A read-only host runs an allow list of reads, default deny, with a test that every command is classified
    • Per-connection cost is bounded before and after authentication
    • Log lines carry a sensitivity, and viewers read a public, scrubbed view
    • Scene, prefab and snapshot data is treated as untrusted and size-capped
    • TLS in the host is optional, vendored Mbed TLS, with pinned fingerprints on the client
    • Third-party code is vendored and pinned, with notices; OpenAL Soft stays dynamically linked
  12. Assets, serialization and import
    • Field registration returns a builder holding an index, not a reference
    • An asset's type name is declared once, as a static
    • Mesh import: one MeshRenderer, submeshes as index ranges, sub-assets with stable UUIDs
    • UI is GameObjects in a canvas pass with Unity's anchor model
  13. Testing and CI strategy
    • Eight checks, one required; docs-only changes skip with a job-level condition
    • Compiler caches: ccache saved only on master; Windows uses Ninja Multi-Config
    • Golden images compare structure, not pixels or hashes
    • Backend tests are typed tests run on every backend; fake drivers for GPU-only code
    • Host smoke tests are one Python script for both operating systems
    • The demo stations are a second list, not stations 8 to 10
  14. Documentation, versioning and process
    • The docs describe behaviour, the code wins, and a PR updates its page
    • The site is plain HTML with a prebuilt search index and a stale-index check
    • Each page explains its own design decisions in "Design decision" callouts
    • Large changes start as a design proposal with numbered decisions for the owner
    • Required check and branch discipline

How to read this page

This page collects 158 decisions in 13 areas. It is an index of reasoning, not a behaviour reference: for what the engine does, follow the links to the other pages. Every entry has the same parts:

  • Decision: what was chosen.
  • Context: the situation or constraint.
  • Why: the reasoning, with the alternatives that were rejected and why.
  • Consequences and trade-offs: what it costs.
  • Where to look: pages, source paths, proposals and PR numbers.

Each entry carries a badge that says how well its reason is sourced:

  • stated (142 entries): the repository states the reason, in a docs page, a design proposal, a code comment or a PR description. The text of the Why paragraph follows that source.
  • mixed (13): part of the reason is stated; the rest is marked in the text as Inference or as not recorded.
  • inferred (0): the repository does not state the reason and the Why paragraph is an inference, labelled as one.
  • not-recorded (3): the repository does not record the reason, and the entry says so.

Decided, recommended, proposed

Many sources are design proposals that end with numbered "Decisions for the user" and a recommendation for each. A recommendation is not a decision. Entries here say when the user decided ("Decided by the user on ...", "accepted") and when something is only proposed, such as the user-shader design in the open PR #397. Numbers such as D3, N6, P4 or W8 refer to those lists in the proposal named in "Where to look".

Dates and numbers

Sizes, timings and counts are the ones the sources give at the time they were written (the PR or document date). They drift; the linked page or test is the current truth. Where this page and the code disagree, the code wins, as on every page of these docs.

Product and architecture

The overall shape of the engine and the habits that hold it together.

Unity-compatible behaviour where there is a choice mixed

Decision. Where Unity has an answer, the engine follows it: RemoveChild, layers and the collision matrix, the OnMouse* picking callbacks, the UI anchor model, Quit semantics, event names.

Context. The engine is a C++23 GameObject/Component engine with Lua scripting and an editor host. A game that is being ported to it comes from Unity.

Why. Stated: the 2D physics design says the component set "mirrors 3D, and the game being ported comes from Unity", and the Sprite2D design keeps "the converter from Unity simple". Inference: the same reasoning covers the other Unity-shaped choices (layers, anchors, mouse callbacks), but the pages only state "like Unity", not why that was the goal for the engine as a whole. The repository does not record the original reason for modelling the engine on Unity.

Consequences and trade-offs. Unity quirks come along (for example the camera/object forward-axis split, see the camera looks down -Z). Where the engine deliberately differs (3D mass is authoritative, 2D mass comes from shapes) the difference is documented.

Where to look: Design decisions table on the overview; gameobjects-components.html#design-removechild; physics.html#design-layers; input.html#design-picking; orchestrator/proposals/physics2d-box2d-design.md; orchestrator/proposals/sprite2d-design.md

Math, text and asset import are CPU-only libraries that depend on almost nothing stated

Decision. math/, text/ and assetimport/ are separate libraries with no renderer, window or engine dependency. assetimport exposes no third-party types; a Font holds its face and SDF atlas in memory and never touches a renderer.

Context. Fonts, images and models have to load in the editor host, in tests and on CI runners with no GPU.

Why. Stated: "every parser is tested without the engine or a GPU", and a font "loads headless; renderers make their own textures from it".

Consequences and trade-offs. A renderer has to build its own texture from a CPU atlas, so there is a GPU cache layer (GpuCache) that holds one GPU resource per (renderer, asset).

Where to look: meshes.html#design-assetimport; text.html#design-cpu-fonts; meshes.html#design-gpu-cache

The engine can start with no window, no renderer, no audio and no physics GPU stated

Decision. ApplicationOptions has RenderBackend::NONE, audio and physicsGpu switches, and a software renderer can run with no window at all.

Context. The editor host, the dedicated server and CI all run on machines with no display or GPU.

Why. Stated: a server "wants neither the editor's loopback audio stream nor a renderer object nobody draws with"; the windowless software renderer lets tests render real frames "on a GPU-less CI runner". All switches default to what every host did before, so nothing changed for existing users.

Consequences and trade-offs. More configurations to test (the headless path is its own set of tests).

Where to look: netcode.html#design-n2server-headless; application.html#design-windowless; application.html#design-sw-headless

Process singletons stay, so multi-peer tests use several processes stated

Decision. The engine keeps its process-wide singletons (Application, SceneManager, LuaRuntime). Netcode is therefore tested with pure-logic tests in one process on a simulator, plus multi-process tests on loopback.

Context. Two network peers cannot share one process while these singletons exist.

Why. Stated in the netcode design: the engine "is a set of process singletons", so "two peers cannot share one process". The design takes this as a fact to work around, not a thing to change first.

Consequences and trade-offs. Slower integration tests (real processes) and a pure-logic layer, n2net, that has to be engine-independent so it can be tested alone.

Where to look: orchestrator/proposals/netcode-runtime-design.md (Executive summary, section 6); netcode.html

The editor host is a library function, not a plugin loader stated

Decision. Editor::RunHost holds the host's whole body, so a game with its own C++ components builds its own host executable.

Context. The editor needs a host process that links the game's components.

Why. Stated: "so a game with its own C++ components builds its own host instead of loading plugin DLLs".

Consequences and trade-offs. A game that wants editor support with custom C++ components must build its own host binary.

Where to look: logging-and-editor.html#design-run-host

Two render queues, with state carried per draw stated

Decision. Opaque renderables draw in hierarchy order, then Transparent ones by sort key, back to front, without writing depth. Depth, cull and blend state travel with each draw.

Context. There are four renderers and one of them (software) reorders draws.

Why. Stated: state travels with each draw "because the software renderer reorders draws". Related: the renderer never sorts; the engine's Scene::Render sorts the Transparent queue (see blending follows OpenGL).

Consequences and trade-offs. Every backend must accept per-draw state; there is no state set once per pass.

Where to look: application.html#design-render-queue; application.html#design-webgpu-blend-order

Scripts get checked handles, never raw pointers stated

Decision. Lua handles stay valid until teardown (or until freed, for scenes, action maps and actions). Using a freed object is a Lua error, never a crash.

Context. Scripts hold references to engine objects across frames.

Why. Stated in the Design decisions table: "using a freed object is a Lua error, never a crash".

Consequences and trade-offs. Handle bookkeeping on every binding; the same generation-counted idea is reused for backend handles (see generation-counted handles).

Where to look: scripting-lua.html#design-handles

Coroutines run in start order, never in pointer-hash order stated

Decision. An object's coroutines run in the order the first coroutine started; ordered maps (by body handle) are used for physics pair and re-filtering iteration.

Context. Iterating a container keyed by pointer gives an order that changes from run to run.

Why. Stated: "so the execution order is reproducible". This is one of the determinism blockers found in the PhysX investigation (coroutine order keyed by GameObject* in an unordered_map).

Consequences and trade-offs. Slightly more bookkeeping than a hash map.

Where to look: coroutines.html#design-coroutine-order; physics.html#design-physx-ordered-containers; orchestrator/proposals/physx-limitations-and-determinism.md

Quit is a request; the edit host ignores a script's Quit stated

Decision. Application::Quit() sets a flag and teardown runs in its usual order. On the edit host, the Lua binding ignores a script's Application.Quit(); the play child honours it.

Context. A scene arrives from a client and its scripts run on the edit host when it loads.

Why. Stated: a script that quit the host made it exit with code 0, "which a service manager treats as a clean stop and does not restart", and again after every restart if the scene was the startup scene.

Consequences and trade-offs. A script's Quit behaves differently in the editor than in a game; C++ calls to Quit are unaffected.

Where to look: application.html#design-quit; application.html#design-script-quit

Modules, build targets and packaging

How a game becomes a shipped program, and why the engine can shrink to what a game uses.

A game lists its engine modules explicitly; the scan only suggests and checks stated

Decision. build.modules in project.n2proj names the modules (physics3d none/physx/jolt/both, physics2d, particles, softbodies, audio, ui, replay, network, scripting, renderer backends). A scan tool reports usage and verifies the list.

Context. A smaller engine matters most for the web build, where size is budgeted.

Why. Stated: Lua can reach a component through a computed name such as AddComponent(kinds[i]) that no scan can resolve, so a purely automatic strip "could remove something a script needs, and the game would break only when that line ran".

Consequences and trade-offs. A person maintains a list.

Where to look: project-modules.html#design-explicit-list; orchestrator/proposals/engine-stripping-design.md

Stripping happens at compile time, not with the linker stated

Decision. Each module is a CMake option (N2ENGINE_USE_PHYSX, _JOLT, _BOX2D, _PARTICLES, _SOFTBODIES, _AUDIO, _UI, _SCRIPTING, _NETWORK, N2ENGINE_RENDERER_VULKAN) and a game gets its own build tree.

Context. Link-time dead-code removal was the obvious alternative.

Why. Stated: RegisterBuiltinComponents names every component type and Application.cpp references the backends directly, so LTO cannot remove an unused module.

Consequences and trade-offs. A build tree per (target, configuration, module list); ccache is used where available.

Where to look: CMakeLists.txt (options and comments); cmake/N2EngineModules.cmake; orchestrator/proposals/engine-stripping-design.md section 3

Stripped components stay registered as thin data holders stated

Decision. With a module off, its component types (Rigidbody2D, AudioSource, LuaComponent, NetworkObject and so on) remain registered, keep their data and do nothing; a scene that needs a stripped component fails at package time naming the scene and module.

Context. A scene file should load the same way in the editor and in a stripped game.

Why. Stated: scene data survives a round trip, the editor lists the components, and the network registry hash (a fingerprint over component type names and replicated fields) must not change.

Consequences and trade-offs. A leftover component at run time logs one error and does nothing, instead of failing to link.

Where to look: orchestrator/proposals/engine-stripping-design.md section 4.4-4.5; CMakeLists.txt (N2ENGINE_USE_BOX2D comment); project-modules.html

The editor and host always build every module; physics was stripped first stated

Decision. Stripping applies only to shipped game builds. Physics came first.

Context. A project may use anything while it is being edited. Measured on the web size profile, PhysX is about 41 percent of the brotli size, Jolt 14, Box2D 3.

Why. Stated: "a project may use anything while edited; the 3D backends are where the benefit is". PR #315 measured that all physics off cut the size-profile wasm (brotli) from 1,995,743 to 866,077 bytes (57 percent).

Consequences and trade-offs. CI builds one configuration per module with only that module off, plus a minimal all-off one, because stripped configurations rot if untested.

Where to look: orchestrator/proposals/engine-stripping-design.md sections 1, 4.6, 4.7; project-modules.html

Builds run on the user's machine through n2build stated

Decision. The Electron main process runs n2build locally. Remote hosts (Docker, SSH) show targets and settings but have no Build button until a host-side build command exists. Apple targets are the exception (GitHub Actions).

Context. Decision D1 of the build-targets design.

Why. Stated: toolchains and devices are on the user's machine, and a remote host keeps the project on the host, so there is nothing local to build. The user answered "run the builds locally".

Consequences and trade-offs. Remote hosts cannot build from the editor yet.

Where to look: orchestrator/proposals/build-targets-design.md sections 3.5, 6 (D1); build-targets.html

The final game is always a full build from source stated

Decision. A shipped build compiles the player with the game's module list. Prebuilt players may come later as a fast option for test builds, never as the only path.

Context. The design recommended prebuilt players by default; the user chose otherwise.

Why. Stated: the editor's play mode is the everyday "player", and a full build is what makes stripping possible. Decided by the user on 2026-11-10.

Consequences and trade-offs. Every target's compiler must be on the building machine; doctor checks this.

Where to look: build-targets.html#design-full-build; orchestrator/proposals/build-targets-design.md D3

A separate desktop player; lua_project stays a demo stated

Decision. A new players/desktop reuses what lua_project solved (project folder argument, --renderer parsing).

Context. Converting lua_project into the player was the recommended option.

Why. Stated: the user said "lua project is a demo project right? Write a separate one"; engine_tests and the web player's default package also use its assets.

Consequences and trade-offs. Two programs with some shared logic.

Where to look: orchestrator/proposals/build-targets-design.md D4; players/

A platform layer confines GLFW to one backend; input uses engine codes first stated

Decision. Platform::IPlatformHost (surface, window, lifecycle, loop, input, paths) with backends desktop-glfw, headless, web, android, ios and private. Input moved to engine-owned codes (InputDevice) before the platform layer; saved bindings store keys by name, so no migration was needed.

Context. GLFW was referenced about 60 times in Window.cpp, 144 times as key codes in InputMapping.hpp, and by every native renderer.

Why. Stated: the web build's fake-GLFW stub "works for one extra platform and will not scale to four", and CI, the editor host and N2Server already run windowless. Doing input first made the larger window change mechanical.

Consequences and trade-offs. Stage 6 was the largest regression risk, since it touches every window and input path.

Where to look: platform.html; orchestrator/proposals/build-targets-design.md sections 3.1, 5, 8

Build-target stages ordered to ship the Build button before the riskiest refactor stated

Decision. Stages 1 to 3 (n2build, settings, editor panel for Windows, Linux and web) come before the platform layer (stages 5 to 7).

Context. The first draft put the platform layer first.

Why. Stated: that order "delayed the Build button behind the riskiest stage" (amended 2026-11-10). The doc also asks to "stop and compare" after stage 3.

Consequences and trade-offs. None recorded.

Where to look: orchestrator/proposals/build-targets-design.md section 5

New platforms start on the software renderer; GPU renderers follow stated

Decision. Android and iOS shipped first with the software renderer (the frame is copied to the surface); Vulkan on Android came in stage 12 and MoltenVK on Apple in stage 13. WebGPU-on-Dawn as a shipped native renderer and GLES3 were not chosen.

Context. The user wanted native mobile rendering "at some point but we can make that a later goal".

Why. Stated: it gets games running on every target without a per-platform GPU port; "Dawn never a shipped renderer" (W8) stands.

Consequences and trade-offs. Phone frame rate is unverified (the CI emulator manages roughly 4 to 8 fps); real-device GPU behaviour is unmeasured.

Where to look: android.html; apple.html; orchestrator/proposals/build-targets-design.md D2

Mobile targets get Jolt and Box2D, not PhysX stated

Decision. A project that needs PhysX on Android or Apple fails at doctor or build time with a clear message instead of a link error.

Context. Decision D8.

Why. Stated: both libraries build from source, while PhysX for the NDK and Apple would be "a large extra build to maintain"; revisit if a game needs it.

Consequences and trade-offs. PhysX-only features (GPU particles, GPU soft bodies) are not available there.

Where to look: orchestrator/proposals/build-targets-design.md D8; android.html

Apple builds go through GitHub Actions macOS runners stated

Decision. iOS and macOS are built by a workflow the game repository owns; n2build starts, follows and downloads it with gh. Tests run on the iOS simulator in CI; device signing waits for a developer account.

Context. The maintainer has no Mac.

Why. Stated: no Mac is available and the repository is public, so standard runners are free.

Consequences and trade-offs. No real device or real-Mac GPU verification; the gaps are listed under "not verified".

Where to look: apple.html; orchestrator/proposals/build-targets-design.md D5, D7

Console targets live outside the repository stated

Decision. A private target folder supplies its own CMake source and toolchain and brings its own renderer through the platform host; only a neutral sample ships.

Context. Console SDKs are under NDA.

Why. Stated: that is the constraint. Whether a console vendor's SDK terms permit this plugin shape is recorded as unverified.

Web build and WebGPU strategy

The web player is a baseline that works from any static host; WebGPU is an upgrade on top.

The web player started as the software renderer drawing to a canvas mixed

Decision. The first web milestone was the CPU renderer's windowless mode feeding a canvas. The player uses that path, not Emscripten's GLFW port.

Context. An early issue draft listed WebGL2, software-to-canvas, WebGPU and pixel streaming and suggested software first as a milestone with WebGL2 after it.

Why. Stated: the software renderer already had a windowless mode, a canvas "is exactly a consumer of that buffer", it avoids "a WebGL context the decisions of #155 rule out" and avoids calling GLFW functions Emscripten's port lacks. The repository docs do not repeat why #155 rules out WebGL; the repository does not record that reason in the pages read here. The issue draft's WebGL2 step was superseded by WebGPU.

Consequences and trade-offs. No window modes on the web (GLFW is still a no-op stand-in).

Where to look: web-build.html#design-web-windowless-player; orchestrator/proposals/issue-draft-web-build.md; orchestrator/proposals/webgpu-backend-design.md

The baseline web build is single-threaded stated

Decision. A submitted frame runs inline inside SubmitFrame; a threaded artifact is an optional later second file.

Context. Static hosts do not send the headers threads need.

Why. Stated: issue #155 makes the single-threaded build the baseline; running the frame inline keeps every call site and the command order identical to the threaded path.

Consequences and trade-offs. No overlap of rendering with the next frame's scene update.

Where to look: web-build.html#design-web-single-thread

Run() is split into BeginRun, RunFrame and EndRun stated

Decision. The same statements in the same order, so the browser driver is the same code as native.

Context. A browser cannot run a blocking loop.

Why. Stated: copying the loop into the player would let "the fixed-step handling and the end-of-run sequence" drift.

Consequences and trade-offs. None recorded.

Where to look: web-build.html#design-web-run-split

Stand-ins for GLFW and OpenAL first, the real thing in its own stage stated

Decision. The web link uses stand-ins that give the linker its symbols and make the "no window, no sound card" paths the ones that run; later stages replaced them.

Context. Emscripten ports exist but do not cover what the engine calls (gamepad functions, glfwSetWindowAttrib, OpenAL Soft's loopback extension).

Why. Stated: stage 1 only needed the core to link and run headless; a window and WebAudio have their own decisions (a canvas, the user-gesture rule).

Consequences and trade-offs. A new GLFW call needs a no-op added or the web link fails.

Where to look: web-build.html#design-web-stand-ins

The software player renders at most 1280 wide and the browser scales stated

Decision. Render size follows the canvas at device resolution, capped at 1280 pixels wide and 1280 by 800 in all.

Context. The software renderer's cost is its pixel count; a browser window can be 4K.

Why. Stated: sharpness is traded for a frame rate the software renderer can hold; whether 1280 is the right number is called out as open.

Consequences and trade-offs. A HiDPI canvas costs more pixels than before.

Where to look: web-build.html#design-web-render-cap

The web player has its own wasm loader and fetches the pack asynchronously, not lazily stated

Decision. The loader uses two documented Emscripten hooks to show one progress figure, version the URLs and report a missing file. The whole asset pack is one fetched file with no custom format.

Context. Emscripten's generated loader cannot do those things.

Why. Stated: fetching assets while the game runs would need a pack format, a request path through the engine's synchronous file API and a loading state for scenes, which is "a separate piece of work and is not done".

Consequences and trade-offs. The wasm download starts only after the pack arrives, and the Emscripten pin (4.0.10) is now also a pin on the loader's assumptions.

Web audio links Emscripten's OpenAL port and drops, not queues, sounds asked for before the unlock stated

Decision. No WebAudio shim; the loopback device reports itself absent. A sound requested while the AudioContext is suspended is dropped.

Context. Browsers suspend audio until a user gesture.

Why. Stated: a suspended context's clock does not advance, so a "queued" sound would hold a pooled source and then all start at once, late, when resumed. Dropping needs no timers and behaves the same in every browser.

Consequences and trade-offs. A sound requested before the first input is lost; a short queue with an expiry is a later option.

PhysX for the web is built from the pinned source in the web job, scalar, no WebAssembly SIMD stated

Decision. No prebuilt wasm archive; the web job builds the pinned PhysX commit (about two minutes cold). The baseline uses scalar PhysX.

Context. Options were a prebuilt archive on a release or a source build in CI.

Why. Stated: a prebuilt archive needs a publishing workflow and a manual hash bump for every flag change and says nothing about what it was built from; the baseline contract (any host, no browser requirement beyond stages 1 to 4) decides for scalar. SIMD stays an option for a separate artifact.

Consequences and trade-offs. Cold-cache minutes in CI; a possibly slower physics frame on big stacks (not measured).

Context. Size is a product requirement for a browser download.

Why. Stated: the limits are measurements, not guesses, and a raise is a visible decision in the PR that causes it.

Consequences and trade-offs. Every feature that grows the wasm needs a budget edit and a reviewer's agreement.

One wasm carries software and WebGPU renderers; WebGPU is automatic, software is the permanent fallback stated

Decision. The loader acquires a WebGPU device when the browser offers one (secure context, adapter, device within a four-second deadline) and otherwise starts the software renderer; ?renderer= overrides. Device loss offers a "continue with the software renderer" button, with no automatic reload.

Context. Maintainer answers on #155 (W3, W4, W5).

Why. Stated: the fallback is a working game, plain-http hosting never gets WebGPU, some browsers will keep software for a long time, and an automatic reload could loop. WebGL2 is "revisit only if browser coverage demands it".

Consequences and trade-offs. A third shader copy to keep in step; one canvas cannot have both a WebGPU and a 2D context, so a mid-game fallback needs a fresh canvas.

The web build uses the same Dawn release as the native test harness stated

Context. Emscripten 4.0.10's built-in port pins a Dawn more than a year older.

Why. Stated: otherwise the backend would compile against two C API versions and "what the harness tests would not be what the browser runs". A device only arrives asynchronously and the web build has no ASYNCIFY or JSPI (ASYNCIFY costs code size, JSPI is not in every browser).

Consequences and trade-offs. A pinned toolchain coupling; failure to get a device selects software.

GPU particles and soft bodies in the browser use WebGPU compute, resolved at runtime stated

Decision. Auto resolves to PhysX GPU, then WebGPU compute, then CPU, gated by physics.gpu. Positions are read back asynchronously.

Context. The browser has no CUDA; the web PhysX is CPU-only. Decided by the user on 2026-11-08.

Why. Stated: the WebGPU renderer offers general-purpose compute, so the components and drawing stay unchanged; the compute API is renderer-neutral (no graphics-API types in it).

Consequences and trade-offs. Only the WebGPU renderer implements compute; every other renderer returns null.

Rendering

Four renderers sit behind one interface: OpenGL (the default on desktop), Vulkan, WebGPU and a CPU software renderer. Most decisions here are about keeping them equal and testable.

Why there are four renderers mixed

Decision. OpenGL is the default; the software renderer is the baseline for headless, CI and the web fallback; Vulkan exists for modern desktop and Android (and Apple through MoltenVK); WebGPU is the browser GPU path.

Context. renderer/ holds OpenGL, Vulkan, WebGPU and software behind Renderer::Common::Renderer.

Why. Stated, per renderer: software for pixel tests on GPU-less runners and as the always-works web player; Vulkan because the old one did not work and CI can run it on a software driver; WebGPU because browsers have no OpenGL-class desktop API. Inference: OpenGL remains the default simply because it was first and the Vulkan docs keep it the Linux default until verified on real hardware ("OpenGL stays the Linux default until the final present PR passes on the user's real GPU", stated).

Consequences and trade-offs. Every rendering feature must be implemented four times, or one backend must refuse it; this is the main reason for the choices below (fixed built-in shaders, cross-backend diff tests).

Where to look: application.html; orchestrator/proposals/vulkan-backend.md; orchestrator/proposals/webgpu-backend-design.md

Vulkan was rewritten on the existing renderer interface; it always renders offscreen stated

Decision. Every frame goes to the renderer's own colour and depth images, and a window gets a blit at Present. The swapchain is a UNORM format, never sRGB while a UNORM one is offered. Vsync defaults on (FIFO); recreation waits for the device to go idle.

Context. At the time of the rewrite, the Vulkan renderer's Initialize returned false at its first step.

Why. Stated: the editor viewport and tests need the frame as pixels anyway, so a second "window" path would leave untested the code the window uses. With one path, CI on a software driver exercises everything except the final blit. The swapchain rule exists because the offscreen image already holds the final, encoded bytes and an sRGB swapchain would encode twice. Waiting for idle on recreation is chosen because it is rare and guarantees nothing still uses the old swapchain.

Consequences and trade-offs. An extra blit per frame; real swapchain and present behaviour can only be checked on a real GPU (a manual checklist exists).

Where to look: application.html#design-vulkan-offscreen; application.html#design-vulkan-swapchain-format; application.html#design-vulkan-present-policy; gpu-vulkan-checklist.html

Shaders are compiled to SPIR-V at build time stated

Decision. GLSL is compiled with glslangValidator or glslc when the renderer is built and embedded. Vulkan memory comes from a vendored VMA. The Vulkan backend has a build option (N2ENGINE_RENDERER_VULKAN). Custom GLSL is not supported in v1 (it returns null with a warning).

Context. Three places a compiler could live: committed SPIR-V, a runtime compiler, or the build.

Why. Stated: committed SPIR-V differs between glslang versions so a regeneration check would be flaky unless the tool were pinned, cannot be reviewed and compiles even when stale; a runtime glslang or shaderc adds tens of megabytes and notices and would only serve custom shaders. VMA over a hand-rolled allocator because a sub-allocator is risk and per-buffer allocation can hit maxMemoryAllocationCount (4096 on many drivers).

Consequences and trade-offs. Linux and Docker builds need glslang-tools; no user shaders (see built-in shaders only).

Where to look: application.html#design-vulkan-spirv-build-time; orchestrator/proposals/vulkan-backend.md section 8 and "Decisions (user, 2026-10-14)"

Vulkan is tested on a software driver, with the validation layer failing tests stated

Decision. CI runs the real Vulkan backend on Mesa lavapipe; any validation error or leak fails the test.

Context. CI runners have no GPU.

Why. Stated: OpenGL pixels are untestable on the runners for that reason, but Vulkan does not have to be; lavapipe is a conformant CPU driver. It checks initialisation, synchronisation, layouts and shutdown on every PR.

Consequences and trade-offs. It cannot show format support, memory types, timing, or the swapchain and present path; those need a GPU PC.

Where to look: testing.html#design-vulkan-lavapipe; gpu-vulkan-checklist.html

WebGPU shaders are hand-written WGSL tied to the Vulkan interface by a parity test stated

Decision. WGSL ports of the three built-in shaders (unlit, lit, text) are written by hand; a text parity test ties them to the shared interface table, and Tint and naga validate them in a small non-required CI job from pinned, hash-checked tools.

Context. Browsers accept WGSL only. Options: translate the Vulkan GLSL at build time (Tint or naga), translate at run time, or write WGSL by hand.

Why. Stated: build-time translation would need a translator in every web build and the current GLSL uses the constructs translators handle worst (row_major blocks, combined samplers, inverse(), discard), so it would be rewritten anyway; run-time translation ships a compiler of megabytes into a size-budgeted wasm.

Consequences and trade-offs. A third copy of each shader (GLSL 330, GLSL 450, WGSL); drift is held back by the parity test and the golden scenes. (Note: a later proposal found row_major and inverse() do translate; see user shaders.)

Where to look: application.html#design-webgpu-wgsl-handwritten; application.html#design-webgpu-wgsl-validation; orchestrator/proposals/webgpu-backend-design.md W1

Dawn is a pinned prebuilt release, and the native WebGPU renderer exists only as a CI harness stated

Decision. The native harness links Dawn's published archive, not a source build; N2ENGINE_RENDERER_WEBGPU is OFF by default, Linux x86_64 only, and not selectable from the editor host, lua_project or project settings. It is always ON for the web build.

Context. Decision W8. A source build of Dawn needs about a dozen dependency repositories and was estimated at 15 to 30 minutes on a cold cache.

Why. Stated: the prebuilt archive is one 36 MB file with the library and headers; the harness exists to test what the browser runs; reaffirmed in the build-targets design where WebGPU-on-Dawn for mobile was considered and not chosen ("Dawn never a shipped renderer").

Consequences and trade-offs. The harness runs on lavapipe, which hides real-GPU and Safari or Firefox differences.

Where to look: application.html#design-webgpu-dawn-prebuilt; CMakeLists.txt (N2ENGINE_RENDERER_WEBGPU comment); orchestrator/proposals/webgpu-backend-design.md W2, W8

Every WebGPU device error fails the tests stated

Decision. The renderer counts uncaptured errors and unexpected device losses in the callbacks it creates the device with, and the test fixture fails any test whose count is not zero; negative controls keep that honest.

Context. The Vulkan tests fail on any validation message. WebGPU has no validation layer.

Why. Stated: a program that ignores an uncaptured error "renders wrong or nothing".

Consequences and trade-offs. Asynchronous delivery means the count has to be flushed before reading.

Where to look: application.html#design-webgpu-error-count

Matrices are row-major in the engine; each backend adapts at the edge (copied as is on Vulkan, transposed on upload on WebGPU) stated

Decision. The engine passes row-major matrices. The Vulkan GLSL block says row_major, the counterpart of OpenGL's transposed upload, so they are copied unchanged. WGSL has only column-major matrices, so the WebGPU backend transposes the three matrices once when it fills each draw's block (3 x 64 bytes of CPU work), and the WGSL then multiplies exactly as the GLSL does.

Context. Three shader languages with different matrix conventions.

Why. Stated: the alternative, writing the WGSL with row-vector products, "needs no CPU work but makes every product read backwards against the GLSL and the table". Tests move a quad by a translation in the model, the view, the projection and in combinations to catch a missing or doubled transpose.

Consequences and trade-offs. A small per-draw CPU transpose on WebGPU.

Where to look: application.html (WebGPU "Matrices" paragraph; Vulkan ring paragraph); renderer/include/renderer/common/GpuShaderInterface.hpp

Materials are a shared, fixed std140 block written by name (BlockMaterial) mixed

Decision. A built-in shader's material values live in a CPU copy of a fixed std140 block, written through a name-to-offset table (GpuShaderInterface.hpp); an unknown name or wrong type logs once and is ignored. BlockMaterial (renderer/common/BlockMaterial.hpp) is the shared class that Vulkan and WebGPU both return from CreateMaterial. The values are snapshotted at each DrawMesh.

Context. OpenGL sets uniforms by name; Vulkan and WebGPU need a binary block.

Why. Stated: materials set uniforms by a fixed name set "so no SPIR-V reflection needed"; the pieces that hold no Vulkan were moved to renderer/common in PR #188 "so another GPU backend can use them"; the table's defaults are checked against OpenGL's by a parity test. Snapshotting at draw time gives OpenGL's semantics (a change after a draw does not affect that draw). The material block is sized to fit within 128 bytes for every shader. Inference for the "fixed-size" part: a fixed layout is what makes the name table and the WGSL parity test possible; the repository states the table and the parity test but does not state "fixed size" as a goal in itself.

Consequences and trade-offs. Custom shaders cannot have their own material layout (see user shaders).

Where to look: application.html (Shared by GPU backends, PR #188); renderer/include/renderer/common/BlockMaterial.hpp; renderer/include/renderer/common/GpuShaderInterface.hpp

Per-draw data goes through a ring of uniform chunks, with the lighting block copied once per chunk per version stated

Decision. Vulkan: a chain of persistently mapped uniform buffers per frame slot, dynamic offsets, chunks that double in size when full. WebGPU: a CPU-staged ring with one queue write per chunk and dynamic offsets into immutable bind groups. In both, UpdateSceneLighting builds a CPU copy and bumps a version; the first lit draw after an update copies the block into the ring.

Context. Per-draw data of 192 bytes exceeds the 128-byte push-constant minimum; two frames are in flight on Vulkan; a WebGPU queue write lands before the frame's commands are submitted.

Why. Stated: a single lighting buffer bound by both frame slots would be rewritten while the other slot may still read it ("a race the validation layer does not always catch"); on WebGPU a queue write per update would make every draw see the last update, wrong when lighting changes mid-frame as the engine does before the scene pass. A draw must see the lighting of its time, as on OpenGL.

Consequences and trade-offs. A lighting copy per chunk per version.

Where to look: application.html#design-vulkan-lighting-ring; application.html#design-webgpu-uniform-ring; application.html#design-webgpu-lighting-copies

A buffer a frame may still read is never written or freed at once; handles carry a generation stated

Decision. Vulkan UpdateMesh uploads to new buffers and retires the old ones onto a per-frame deletion list, freed after that frame slot's fence. WebGPU writes in place unless the mesh was drawn in the open frame (a per-mesh flag). Physics feature handles (particles, soft bodies) pack the issuing backend's generation into the upper 32 bits so a backend recreated at the same address cannot honour an old handle.

Context. Text and particles call UpdateMesh every frame; backends can be recreated.

Why. Stated: with two frames in flight the GPU may be reading what the CPU wants to change. WebGPU chose the flag over "always allocate new" (an allocation per text change) and over splitting the frame. For handles, an address comparison (PR #125) could be fooled by a backend recreated at the same address.

Consequences and trade-offs. A deletion list and a generation counter per feature.

Where to look: application.html#design-vulkan-deferred-deletion; application.html#design-webgpu-in-frame-update; particles.html#design-particles-generation; physics.html#design-softbody-handles

Blending copies OpenGL exactly, and the renderer never sorts stated

Decision. WebGPU's blend state is set to OpenGL's factors, the same for colour and alpha. Ordering belongs to the engine: Scene::Render sorts the Transparent queue back to front for every backend. In linear lighting, a blended lit draw blends encoded values on Vulkan (about 128,0,128 for half-alpha red over blue) where OpenGL blends in linear space (about 188,0,188); this is a recorded difference.

Context. The software renderer cannot blend, so OpenGL is the reference.

Why. Stated: a separate alpha equation would change the stored alpha the readback shows; and the Vulkan target is UNORM with the lit shader encoding in the shader, so the blend sees encoded values for that one case.

Consequences and trade-offs. A known cross-backend pixel difference for blended lit draws in linear lighting.

Where to look: application.html#design-webgpu-blend-order; application.html#design-vulkan-blend-linear

Linear lighting is off by default and applies to the lit shader only stated

Decision. sRGB textures and the framebuffer encode apply only for lit draws (GL_FRAMEBUFFER_SRGB on only for lit draws; a table on the software renderer). Numeric colours (factors, vertex colours) are taken as linear, as in glTF; only textures marked sRGB are decoded. The sRGB flag of a texture is recorded but changes nothing until linear lighting is on.

Context. Issue #3 planned linear lighting.

Why. Stated: the UI, text and unlit draws must be identical in both colour spaces; switching textures to sRGB changes every colour on screen, so it is opt-in. The numeric-colour rule is described as "the choice made in PR #94" because the plan on #3 did not say.

Consequences and trade-offs. Two lighting modes to test everywhere.

Where to look: meshes.html#design-linear-lit-shader-only; meshes.html#design-numeric-colours-linear; meshes.html#design-srgb-recorded

The camera looks down -Z while objects face +Z stated

Decision. Objects follow Unity (forward is +Z), while the camera's view and projection follow OpenGL (the eye looks down its local -Z).

Context. Both renderers, ScreenPointToRay, frustum culling and transparent sorting are built on the OpenGL form.

Why. Stated: making the camera look down +Z would mean a different projection, a mirrored image or a handedness flip and changes to all of those.

Consequences and trade-offs. Two forward conventions that a script author must know.

Where to look: math.html#design-camera-forward

Textures are stored bottom row first (flipY on import) stated

Decision. v = 0 is the first row of pixel data; imported images are flipped on load, and v-down model formats flip v instead.

Context. The existing primitives and UI quad are v-up.

Why. Stated: images then show upright on the existing geometry.

Consequences and trade-offs. Importers of v-down formats must convert.

Where to look: meshes.html#design-uv-flipy

Built-in shaders only: no user shaders in v1; effects are fixed uniforms stated

Decision. Vulkan and WebGPU return null for custom shaders. Visual effects are added as fixed built-in uniforms instead: saturation and a flash colour on Sprite2D and UI Image, a per-draw screen tint (saturation inside a screen circle), a CPU-made texture outline (Texture::MakeOutline), glow as a blended gradient sprite (skipped on the software renderer through Graphics.CanBlend()), and glitch in Lua. Screen tint does not reach the UI.

Context. A game being ported needs time-stop greys, hit flashes and outlines.

Why. Stated (effects design): each custom shader would need GLSL 330, Vulkan GLSL, WGSL and C++ versions, and the software renderer ignores shader source. A tint per draw equals tinting the finished frame because saturation is a linear colour map and alpha blending is linear, with no render target; a real pass waits for blur or bloom. Glow is skipped on software because hard-edged glow "looks worse than none". Tint skips the UI because in Unity overlay UI draws after full-screen effects so the HUD stays coloured.

Consequences and trade-offs. Only the effects built in are available; custom OpenGL shaders ignore the tint.

Where to look: orchestrator/proposals/effects-design.md; sprite2d.html; orchestrator/proposals/vulkan-backend.md section 8

User shaders (.n2shader): proposed, not merged stated

Decision. Open PR #397 proposes one .n2shader asset, cooked offline to SPIR-V, WGSL (through Tint) and GLSL 330 against a fixed engine interface, with the material block generated from declared parameters (std140, 256 bytes maximum, five texture slots), the software renderer falling back to built-in unlit with a warning, and compile-on-device only for OpenGL and (opt-in) desktop Vulkan.

Context. This is a proposal only: it is unmerged and nothing described here exists in the engine.

Why. Stated in the PR: a spike showed row_major and inverse() translate fine, naga cannot be the translator (it stays a validator), and the real gaps are combined samplers, textureSample after discard, and isnan/isinf; the web cannot take GLSL because browsers compile WGSL only. It would need the Vulkan material block range raised from 128 to 256 bytes.

Consequences and trade-offs. If accepted, a cook tool and more shader paths to test.

Where to look: PR #397 (open); orchestrator/proposals/user-shaders.md (on that PR's branch only)

Apple GPU rendering uses MoltenVK; native Metal is not planned stated

Decision. The Vulkan renderer is the GPU renderer on macOS and iOS through MoltenVK (a static framework on iOS, a dylib beside the macOS player). Picked by the user on 2026-11-12.

Context. A spike compared MoltenVK, native Metal, and both in order.

Why. Stated: a native Metal backend "would roughly double the GPU renderer code that has to stay in step" before it was shown to be needed. The spike ran 309 Vulkan tests on MoltenVK: 262 passed and all 46 failures had one cause (no image view swizzle), fixed by storing one- and two-channel textures as RGBA where the device cannot swizzle.

Consequences and trade-offs. About 5 MiB added to the macOS package and about 3 MiB on iOS; the iOS simulator ran 20.7 fps against 54.8 for software (a simulator lacking Metal argument buffers; no real-device numbers).

Where to look: orchestrator/proposals/metal-spike.md; apple.html

The software renderer cannot blend, so it cuts out and alpha-tests; it copies uniforms per draw stated

Decision. Software text keeps or rejects each pixel at the 0.5 SDF edge and writes depth; textured sprites and UI images are cut out at alpha 0.5; material values are copied into each draw and destroys wait for any frame in flight.

Context. Adding blending to the software renderer was the alternative.

Why. Stated: adding blending "is a renderer project of its own"; copying material values per draw gives OpenGL's semantics and removes the render thread's only read of an object the main thread changes freely. Textures stay pointers because copying pixels per draw would cost far more and a software texture's pixels never change after creation.

Consequences and trade-offs. Edges are not antialiased in software; a destroy can wait on a frame.

Where to look: text.html#design-sw-text-alpha-test; application.html#design-sw-frame-in-flight; orchestrator/proposals/sprite2d-design.md

One Sprite2D component, always in the Transparent queue stated

Decision. A single component with a shape field (rect, triangle, circle, regular polygon, convex polygon), an integer sortingOrder and no named sorting layers; CPU-generated shape meshes cached by description.

Context. The game's art is mostly coloured shapes with an occasional texture.

Why. Stated: one type keeps scenes, Lua and the Unity converter simple; only the Transparent queue has a draw order a component can set, and an opaque sprite would be ordered by depth alone ("two sprites at the same z would fight"). Integer-only sorting can later map named layers onto ranges without changing scenes.

Consequences and trade-offs. No early depth rejection for sprites, "which does not matter at 2D scale".

Context. Rollback and cross-platform lockstep need bit-identical results on Windows, Linux x86_64, Linux arm64 and the web.

Determinism and math

The Deterministic network preset needs every peer to compute identical floats. The engine gets there with a strict floating-point build, its own transcendental functions and a lot of small rules, and then proves it in CI.

Strict floating point, not fixed point stated

Decision. The engine keeps float Vector3 and Quaternion and relies on IEEE arithmetic with no contraction, engine-owned trig and a per-tick guard.

Context. Decision P7. Strict float costs weeks; fixed point costs months.

Why. Stated: both candidate physics engines are strict-float; Lua numbers are doubles; the renderer, math library and serialization are float; fixed point would force a custom physics engine and a parallel math stack (new fixed types, a 64x64-to-128 multiply, new serialization field kinds).

Consequences and trade-offs. The guarantee depends on compilers honouring IEEE without contraction. Risks named: NaN payloads, denormal modes set by any library, libm differences and constant folding of transcendental calls; they are guarded by cross-leg hashes on every toolchain bump.

Where to look: orchestrator/proposals/netcode-runtime-design.md section 4.8; orchestrator/proposals/physics-backend-investigation-156.md section 3; math.html#design-strict-fp

N2ENGINE_STRICT_FP is a build profile on every target, on by default stated

Decision. The option builds all targets with no FP contraction and no fast-math. It is ON by default in every build (issue #381; it was ON only for the web size and speed profiles before), -DN2ENGINE_STRICT_FP=OFF turns it off, and build.strictFp in the project turns it on for a game's own tree (n2build turns it on for a game that uses networking).

Context. The same source must compile to the same float operations.

Why. Stated: it applies to all targets, not only math, "because the inline math in the headers is compiled into every target that includes them, and they must all be the same code"; it is a profile, not a guarantee (C libraries, SIMD tiers, Debug versus Release and the prebuilt PhysX still differ). It defaults ON for web because Jolt declares cross-platform determinism only with it and WebAssembly has no fused multiply-add, so it changes no instruction there. Elsewhere it stayed OFF "so existing builds are unchanged" until issue #381, when networked games became the common case and the default moved to ON (x86_64 and WebAssembly lose no instruction; arm64 may lose some speed in float-heavy code).

Consequences and trade-offs. One cold compile per leg when turned on; a warning if a networked game turns it off while using physics (PR #384).

Where to look: CMakeLists.txt (N2ENGINE_STRICT_FP); math.html#design-strict-fp; project-modules.html; PR #384

Engine-owned sin, cos, atan, exp and log, written as short series stated

Decision. Sin, Cos, Tan, Asin, Acos, Atan, Atan2, Exp and Log are truncated Taylor series with Cody-Waite reduction (fdlibm reduction points for atan, fdlibm summation order for log), compiled without contraction; the float versions round the double result once. A source-scan test fails on new std::sin style calls outside a short audited list.

Context. Library trig differs between C libraries.

Why. Stated: "a few dozen lines that can be reviewed against the maths", no third-party licence, no Jolt dependency in the math library. Minimax polynomials would need fewer terms but must be generated by a tool; the extra multiply-adds are irrelevant at game rates. Rounding the double result once makes a float and a Lua number agree.

Consequences and trade-offs. Slower than the library functions; the engine owns the accuracy.

Where to look: math.html#design-engine-trig; math/include/math/DeterministicMath.hpp

Flush-to-zero off everywhere, with a guard on every network tick stated

Decision. Round to nearest, flush-to-zero off, exceptions masked, set and verified at the start of each fixed tick in the network modes and restored after; no guard in None mode.

Context. FP environment settings are per thread and a library may change them.

Why. Stated: WebAssembly cannot turn flush-to-zero on, so any other choice would make the web a different game; the guard is per tick because settings are per thread; it runs only in network modes so non-network projects pay nothing.

Consequences and trade-offs. Two register accesses per tick.

Where to look: math.html#design-fp-guard

SIMD tiers are an algorithm choice; the default is scalar; determinism requires scalar stated

Decision. The build targets AVX once for every target. Runtime tiers (scalar, SSE2, SSE4.1, AVX, NEON) select which implementation runs so each can be tested against scalar in one process. A tier the machine lacks is lowered with a warning. The Deterministic preset requires scalar. Only elementwise operations are asserted bit-identical to scalar; dot, length, normalize and cross stay tolerance-only.

Context. The alternative was per-CPU binaries or per-function target attributes.

Why. Stated: tiers exist so implementations can be selected, tested and benchmarked; they are bit-exact only for rounding, sign and min/max; making dot and length bit-exact would mean giving up the speed the tiers exist for. A project must never fail to start because of the setting, so a missing tier is lowered with a warning.

Consequences and trade-offs. Binaries need an AVX CPU whatever tier is chosen; a deterministic mode must check the tier in use, not trust the setting.

Where to look: math.html#design-simd-tiers; math.html#design-simd-tier-clamp; orchestrator/proposals/physics-bench-381.md

No fused multiply-add on aarch64; NEON is a separate enum value stated

Decision. -ffp-contract=off is added PUBLIC on aarch64 non-MSVC targets, and the NEON tier is appended to the enum instead of placed above AVX.

Context. Clang contracts a*b+c into one fused instruction on aarch64 by default; x86 never does here.

Why. Stated: otherwise scalar and NEON would round differently from each other and from x86 and break bit-exact comparisons; PUBLIC because the scalar functions are inline in headers compiled into every target. Existing enum values keep their meaning.

Consequences and trade-offs. Scalar code on aarch64 loses the fused instruction.

Where to look: math.html#design-neon-fma; math.html#design-neon-enum

Lua gets Ordered.pairs, a seed switch and a small Lua patch; the seed stays off by default stated

Decision. An Ordered.pairs iterator (array part, then numbers, strings, booleans ascending; an error for keys with no order) is in every Lua state; setting determinism.luaSeed fixes Lua's string-hash seed and math.random seed through two small marked patches in the vendored Lua (external/lua/n2seed.{h,c}) that fall through to upstream when unset.

Context. Lua's pairs() order over string keys differs from run to run.

Why. Stated: banning pairs() would break scripts, so an ordered alternative is offered; Lua takes both seeds in code, not in a setting, and a macro cannot reach randseed. A constant hash seed makes hash flooding possible (anyone who knows it and controls table keys can make inserts quadratic), so it stays off by default.

Consequences and trade-offs. A patched vendored Lua; scripts that need reproducible order should still use sorted key lists.

Where to look: scripting-lua.html#design-ordered-pairs; scripting-lua.html#design-lua-seed-security; scripting-lua.html#design-lua-seed-patch

Seeding Random is opt-in stated

Decision. Nothing seeds the global Random on its own; one explicit Seed call (script or C++) switches the whole global Random, and independent simulations get their own seeded streams (Random.NewStream).

Context. A replay or netcode session seeds from its own session value.

Why. Stated: with no seed call every project and test behaves as before; the right moment to seed is the game's; the rejection loop has no fixed number of draws, so interleaving simulations on one stream is a reason to give each its own stream.

Consequences and trade-offs. Randomness that must not be reproducible should not draw from Random.* in a seeded game.

Where to look: math.html#design-random-seed

In network modes the netcode owns the tick; timeScale becomes presentation-only stated

Decision. A SimulationClock decides how many fixed ticks run per frame; a 64-bit tick counter (Time::GetTick()) exists; the fixed step ignores timeScale; the attach queue runs at each tick boundary; no frame time is dropped. A frame more than 1 second behind tells a behind handler or drops the owed time with a logged warning. None, the default, keeps today's loop and only gains the tick counter. In OnFixedUpdate of a networked mode Time.time is tick times the fixed step (PR #387).

Context. The old loop is a wall-clock accumulator clamped at 0.25 s that drops time and scales the step by timeScale (zero means no step); the attach queue ran once per frame, so a component created in Update joined at a frame-timing-dependent tick.

Why. Stated: those are exactly the things that make two peers diverge. The None preset must stay "byte for byte" unchanged (a golden test pins it).

Consequences and trade-offs. Slow-motion effects must be done in presentation; time dilation for catching up uses a bounded rate change (about 5 percent) instead of jumps.

Where to look: application.html#design-sim-clock; application.html#design-owed-limit; orchestrator/proposals/netcode-runtime-design.md section 2.4; PR #387

Determinism is proved by CI, not argued stated

Decision. A corpus of scenes (10 in the Jolt job, 600 ticks, hashed every 60) is replayed on Windows MSVC, Linux clang x86_64, Linux clang arm64, Linux GCC 14 and the web (node), and compared with each other and with committed goldens (tests/golden/physics-determinism.json) with no tolerance. A replay hash job does the same for physics-free netcode scenes. Goldens change only in PRs that say why. The comparer has a self-test.

Context. Strict-FP determinism "depends on compilers honouring IEEE".

Why. Stated: "Proof is CI, not argument"; PhysX is also run as a negative control. The job was first non-required (for about two weeks) and was to become required.

Consequences and trade-offs. More CI legs and goldens to update on toolchain bumps.

Netcode

There are two real presets beside "None": Server authoritative (PhysX, prediction and reconciliation) and Deterministic (lockstep, then rollback). The design was accepted in the netcode runtime design document and built in stages (n2net, world, replication, input, clock, prediction, lockstep, rollback).

Two presets, and a Deterministic project is refused when its requirements are unmet stated

Decision. Presets: None, Server authoritative and Deterministic. Deterministic refuses to start unless the backend is cross-platform deterministic with snapshots, every feature group, a strict-FP build, scalar tier, fixed Lua seed, engine trig, GPU physics off and others. One data table of Locked, Tunable and Startup-checked rows is read by both engine and editor, and only a Locked cell can make a project Customised.

Context. User decisions of 2026-10-20 (D2 cross-platform determinism, D3 show the Deterministic card disabled with a reason while no backend qualifies, D4 refuse to start).

Why. Stated: refuse, "never silently degrade"; the table is data in the engine so the engine and editor "cannot disagree about what a preset locks"; the check happens right after the project file is read and names every unmet requirement.

Consequences and trade-offs. A project that cannot meet the bar cannot start in that preset.

Where to look: physics.html#design-network-refusal; physics.html#design-network-presets-data; orchestrator/proposals/netcode-runtime-design.md section 5

Lockstep first, rollback second stated

Decision. Lockstep with an input delay (default 2 ticks) came first; rollback (maximum window 8 ticks by default, up to 15, 0 means lockstep) came next on a constrained "rollback world".

Context. Decision N6.

Why. Stated: rollback is the hardest part "not mainly because of physics": the simulation state is spread over heap GameObjects with side-effecting lifecycles (OnAttach creates bodies), Lua tables, upvalues and coroutines, and Scene::Serialize is JSON, so a restore by reload would rebuild bodies cold in milliseconds.

Consequences and trade-offs. A rollback world contract restricts how a game is written (see next item).

Where to look: orchestrator/proposals/netcode-runtime-design.md sections 4.2, 4.4; netcode.html

The rollback contract: only declared state rolls back; spawns are parked stated

Decision. Simulation state is replicated fields, NetworkTransform, physics body state, RNG state and the net id set. Lua simulation scripts keep cross-tick state only in declared (replicated = true) fields. Despawned objects are deactivated and parked until their tick is confirmed; sim-triggered effects are rollback-aware events keyed by (tick, net id, event id). The runtime lints tick callbacks' bytecode at construction.

Context. The engine cannot snapshot arbitrary Lua state.

Why. Stated: a snapshot interpreter was rejected as infeasible with the vendored Lua and the lua_State pointers held by bindings; snapshotting a table graph was rejected as "high cost and fragile (functions, userdata, coroutines are not serialisable)". The desync detector, not static analysis, enforces the rest. A restricted simulation-Lua profile is kept as a follow-up only if a game needs it.

Consequences and trade-offs. The lint is static and incomplete (an inherent limit documented in the netcode page).

Where to look: orchestrator/proposals/netcode-runtime-design.md sections 4.4, 4.7, 9.2; orchestrator/proposals/lua-state-and-joints-381.md; netcode.html

The packet layer is our own library, not ENet or GameNetworkingSockets stated

Decision. n2net (ITransport, a deterministic in-memory SimTransport, 1200-byte packets, 16-bit sequence plus 32 ack bits, reliable-ordered and unreliable-sequenced channels, fragmentation) is a standalone static library using only the standard library apart from the UDP and secure transports.

Context. Decision N2.

Why. Stated: "The browser transports, the security model and the simulator have to be ours anyway, and the reliability layer is the small part" (about 1500 lines estimated). Rejected: ENet (no encryption), Valve GameNetworkingSockets (heavy dependencies), yojimbo or netcode (needs libsodium).

Consequences and trade-offs. The project owns its reliability code and its bugs.

Where to look: netcode.html#design-n2net-own-layer; engine/include/engine/network/n2net/

The network simulator is integer-only with its own random generator stated

Decision. SimTransport uses integers and its own RNG so golden traces are identical everywhere.

Context. The simulator drives most network tests.

Why. Stated: its traces "must be identical on every compiler, standard library and architecture, which floating point and the standard distributions do not promise".

Consequences and trade-offs. None recorded.

Where to look: netcode.html#design-n2net-integer-sim

Encryption is our own AEAD layer on Mbed TLS primitives, not DTLS stated

Decision. A cookie handshake (padded connect request carrying a join token, a stateless challenge cookie, a reply never larger than the request), X25519 and HKDF keys, ChaCha20-Poly1305 per packet with the sequence in the nonce, per-direction keys and a 256-entry replay window, with silent drops. A non-loopback bind fails closed unless --insecure-bind.

Context. The design compared DTLS 1.2 through Mbed TLS with a small layer of its own, "reviewed against the netcode.io standard".

Why. Stated: DTLS is heavier with per-peer session objects; Mbed TLS 3.6.7 is already vendored; the pre-auth slots, token buckets, rate limiter and token table are reused from the editor host. The risk is acknowledged: it is "our responsibility to get right" and DTLS stays the conservative fallback. It differs from netcode.io because keys and identity come from an ECDHE handshake rather than a connect token encrypted by a web backend.

Consequences and trade-offs. A security-sensitive layer that needs its own review.

Where to look: netcode.html#design-secure-own-layer; orchestrator/proposals/netcode-runtime-design.md section 2.1.3

The UDP transport drains the socket, then sweeps idle peers stated

Decision. Poll reads first and sweeps after, judging idleness against the time the poll began.

Context. A caller can stall between two polls longer than the idle timeout.

Why. Stated: sweeping first would drop every peer whose datagrams sit in the receive buffer, and the next datagram would create a new peer id.

Consequences and trade-offs. None recorded.

Where to look: netcode.html#design-udp-drain-then-sweep

Browsers connect over WebSocket first stated

Decision. A WebSocket transport (a native listener in N2Server, Emscripten client) comes first; WebRTC or WebTransport come later, if measurement justifies one.

Context. A static host cannot be a game server and a browser cannot accept connections.

Why. Stated: WebSocket works in every browser but is TCP, so loss stalls everything behind it; WebRTC needs a native stack, signalling and STUN or TURN; WebTransport needs an HTTP/3 server and Safari support is uncertain; wss:// needs a CA-trusted certificate, so the editor's self-signed trust-on-first-use does not carry over.

Consequences and trade-offs. Worse behaviour under packet loss in browsers.

Where to look: orchestrator/proposals/netcode-runtime-design.md section 2.1.2, N3

Deterministic sessions use a star through the server in relay mode; no matchmaking or NAT traversal stated

Decision. N2Server --relay forwards and timestamps inputs; v1 is direct connect with a join token.

Context. Decisions N5 and N12.

Why. Stated: peer-to-peer would expose peer IP addresses; NAT punch-through, TURN and matchmaking are out of scope for v1.

Consequences and trade-offs. The server must be reachable.

Where to look: orchestrator/proposals/netcode-runtime-design.md sections 1.2, 2.1.4

N2Server is its own executable with strict arguments mixed

Decision. A separate headless executable (project, scene, bind, port, tokens file, max clients, relay) that links the host's log sink, parsers and scene-path resolution; an unknown argument is an error.

Context. Decision N11.

Why. Stated: a game server has a different trust model, loop and protocol from the editor host; sharing code avoids copies; strict arguments so "a typo cannot leave it running with the wrong settings". The design doc itself recommends a new executable without a detailed reason; inference: security separation and no editor dependencies.

Consequences and trade-offs. Another executable to build and deploy.

Where to look: netcode.html#design-n2server-exe; n2server/

Replication is opt-in per field, with deltas against the newest acknowledged value stated

Decision. .Replicated() (or Lua replicated = true) marks fields; a Json field is not replicable; the server keeps, per client and field, the newest acknowledged bytes and resends a field until acknowledged; every state entry carries a 16-bit layout hash instead of field ids; a teleport is a replicated counter.

Context. Decision N10.

Why. Stated: no JSON on the wire; a client applies entries on top of what it has, so a received but unacknowledged message may already have changed a field the next one omits, which is why an unacknowledged field is resent; a differing layout (a Lua script's per-object fields) is then a skipped, counted entry rather than garbage; a counter "needs no special case and a lost message cannot lose the jump".

Consequences and trade-offs. A changed field is sent about once per round trip of ticks; the wire version rose to 2 for the layout hash.

Where to look: netcode.html#design-replication-baseline; netcode.html#design-replication-layout-hash; netcode.html#design-replication-teleport; netcode.html#design-replication-codec-choices

The join fingerprint, and what is in it stated

Decision. A hash of the scene's parsed JSON (FNV-1a 64) plus a registry hash over every registered component type's replicated fields and everything that decides their bytes (name, container, kind, type name, step, range, enum options), the input layout hash, prefab hashes (structure, not UUIDs), counts (at most 4096 scene objects and 1024 prefabs), a packed build profile (compiler id and major, strict FP, contraction-free, Debug or Release, pointer width, architecture) and a flag saying whether the server enforces it. Lua sources and assets are not covered.

Context. The client checks that it loaded the same project as the server.

Why. Stated: FNV-1a over the parsed JSON means line endings and key order do not matter and the web build needs no crypto library; "a fingerprint has to tell two builds apart, not resist an attacker", and the client's own check is the protecting one. The build profile was added (PR #388, wire 8 to 9, largest hello 318 to 323 bytes) and is compared only when the server enforces it (set from the Deterministic preset), so Authoritative sessions still accept mixed builds.

Consequences and trade-offs. A client that modifies itself can lie; Lua sources and assets are not verified at join.

Where to look: netcode.html#design-world-fingerprint; netcode.html#design-input-layout-hash; PR #388

Scene objects are matched by UUID and numbered in UUID order, with nothing on the wire stated

Decision. Both sides load the same file; net ids for scene objects are assigned in UUID order; the join state is only what changed since the start. Prefabs are registered in code and frozen into a name-sorted table per session. An owner who leaves does not change the object.

Context. World matching.

Why. Stated: "Both sides load the same file and the fingerprint proves it"; the prefab registry is in memory with no prefab file type in a project, so the table is what is registered at session start; ownership has no behaviour yet and client ids are never reused.

Consequences and trade-offs. Every networked scene object needs a unique UUID and a scene that differs is refused.

Where to look: netcode.html#design-world-matching; netcode.html#design-world-prefabs-code; netcode.html#design-world-owner

Inputs: a fixed layout sampled per tick, redundant sends, a server-side delay, and a pull model stated

Decision. A project-declared input layout is sampled once per tick into an InputFrame (signed axes cover [-range, range], unsigned [0, range], so neutral is exactly zero); the client sends the last few unacknowledged frames; the server applies a fixed delayTicks and a jitter buffer; the game pulls InputFor(object, tick) and the server remembers the last 64 ticks.

Context. Simulation must read frames, not live devices.

Why. Stated: action maps are unordered maps; one update can run several fixed ticks so the server cannot know which tick the game is on, hence pull; a frame refused as too far ahead is deliberately not acknowledged so the client resends it; an adaptive delay waits for clock sync.

Consequences and trade-offs. The host must call SetCurrentTick; fixed delay adds latency.

Where to look: netcode.html#design-input-delay; netcode.html#design-input-ack; netcode.html#design-input-pull; netcode.html#design-input-layout-hash

Clock sync: best-half median of 16, slewed, never backwards; a stream tick instead of a heartbeat stated

Decision. The client estimates server time from the shortest-round-trip half of the last 16 pings, slewing at up to 5 percent (a jump over 250 ms takes effect at once with time standing still). The server sends a 5-byte stream tick when it has no state for a client, so a client can tell a stopped object from a late one.

Context. Delta replication sends nothing for an unchanged object.

Why. Stated: a plain median is biased by delayed samples; without the stream tick a client would extrapolate every stopped object or never extrapolate. The sizes (16, 5 percent, 250 ms) are "judgement calls for the simulator's links".

Consequences and trade-offs. Tuned on the simulator, not on real networks.

Where to look: netcode.html#design-clock-best-of-n; netcode.html#design-clock-stream-tick

Prediction covers only the owner's kinematic character; riding platforms is predicted in the platform's frame stated

Decision. Predicted rigid bodies are rejected for v1; the engine-owned controller is predicted and reconciled (smoothing about 100 ms, snap above 1 m). A character on a moving kinematic platform is kept as (ground net id, offset in the platform's local frame) (wire version 8).

Context. Decisions N8 and N9; B6.

Why. Stated: replaying a dynamic PhysX body resimulates the whole scene per correction and is not bit-exact on replay; predicting from replicated platform state needs an exact server pose the client never has; predicting kinematic bodies would extend prediction to a second object kind.

Consequences and trade-offs. Dynamic bodies are not ridden and rotating platforms agree only approximately.

Where to look: orchestrator/proposals/netcode-runtime-design.md sections 3.3, 3.5; netcode.html; PR #271

Lag compensation uses the engine's own hitbox history, capped at 200 ms stated

Decision. A ring of hitbox poses with ray and sphere tests, server only; the client's claimed latency is clamped to the server's measured round trip.

Context. Rewinding live PhysX actors was the alternative.

Why. Stated: it avoids moving live PhysX actors; the cap defeats fake-latency abuse.

Consequences and trade-offs. Only simple hitboxes.

Where to look: orchestrator/proposals/netcode-runtime-design.md section 3.6

On a desync the session ends with a report and a replay stated

Decision. A 64-bit hash tree (tick, net id, field) every 30 ticks reuses the replication codecs; peers compare roots; on mismatch the session ends and a desync report with fingerprints, input log from tick 0, recent trees and the first divergent net id and field is written. No automatic resync in v1.

Context. Decision N14.

Why. Stated: hashing reuses the replication code; the input log is a replay, so re-running it headless per platform pinpoints the tick; replays double as CI goldens.

Consequences and trade-offs. A desync ends the match.

Where to look: orchestrator/proposals/netcode-runtime-design.md section 4.5; netcode.html

Deterministic sessions allow only cosmetic RPCs; RPCs are addressed by position stated

Decision. An RPC declares itself cosmetic or not; with cosmeticRpcsOnly any other RPC is refused on send and receipt and counted. Simulation-changing commands travel in the input frame. RPCs are addressed by (component position, name-sorted position, 16-bit list hash), not a global id.

Context. Every peer must apply a command at the same tick.

Why. Stated: that is what the input stream is for; a global id table "would have to be agreed at join time and could not cover Lua RPCs".

Consequences and trade-offs. 4 to 6 header bytes per call; the 16-bit hash is "not a proof".

Where to look: netcode.html#design-rpc-preset; netcode.html#design-rpc-ids

No late join in lockstep v1; spectators can later be promoted to a player stated

Decision. Spectators join from the start; a spectator can be promoted to a dropped slot (lockstep wire 3) with a slot rejoin at a join tick. The design proposes that a joiner whose physics bytes are refused fails unless the host sets allowInexactPhysics (PR #302 is titled "physics-refusal fallback"; the exact shipped behaviour is on the netcode page).

Context. Decision N13 and the C5 follow-up notes.

Why. Stated: a spectator already in step removes the snapshot-transfer problem; joining only at hash checkpoints was rejected as a longer wait; failing is chosen over silent drift.

Consequences and trade-offs. Late join needs a spectator first.

Where to look: orchestrator/proposals/netcode-runtime-design.md section 9; PR #299

Wire versions rise on any change; refusals name the reason stated

Decision. The n2net world wire version, the lockstep wire version and the editor protocol version are separate counters; a joining peer of another version is refused with a reason (the reject-reason range grew to 1 to 6). Bounded decoders read only what they are given, with every count capped.

Context. Peers must run the same build (cross-version play is a non-goal).

Why. Stated in PR descriptions (wire 8 to 9, 2 to 3) and in the decoder guarantee. The design lists cross-version play as a non-goal.

Consequences and trade-offs. No compatibility across builds.

Where to look: netcode.html; PR #299; PR #388

Lua scripting and its sandbox

Scripts are Lua 5.4 built from source and share one state. The sandbox exists to stop runaway scripts, not to contain hostile code.

Five libraries, an instruction budget and a memory cap per entry stated

Decision. Only base, math, string, table and coroutine are opened (no io, os, package, debug or utf8). A count hook limits instructions per entry and a counting allocator caps memory; coroutines are run under the budget of the call that resumed them; a faulted component stays off; setmetatable refuses __gc.

Context. The state is PUC Lua built from source and debug hooks are per thread.

Why. Stated: a coroutine would otherwise run without the hook; a __gc finalizer runs with hooks off. The docs are explicit: "The limits make a runaway script stop; they do not make the sandbox safe for hostile code" (a pathological pattern match inside one C call uses no budget).

Consequences and trade-offs. A single C call can still take long; xpcall needs a wrapper so a budget error is never handed to a script handler.

Where to look: scripting-lua.html#design-lua-limits; scripting-lua.html

The editor host that edits never runs project Lua stated

Decision. A process-wide execution policy: a LuaComponent on the edit host reads its script's declarations from a cache keyed by the source text and runs nothing. Declarations are evaluated once in a throwaway budgeted state (1,000,000 instructions, 16 MiB, no engine bindings, load, dofile, print and string patterns removed, a stub environment) on a worker that is abandoned at its deadline (at most four).

Context. Security audit finding F3: a script's top-level chunk ran in the one global state with every binding and no budget, two to three times per scene load.

Why. Stated: three options were weighed. A static parser of untrusted text is attack surface and loses computed defaults; keeping execution with budgets leaves the bindings, re-runs and destroy callbacks; the chosen throwaway evaluation keeps computed defaults. A script can stall Lua in one uninterruptible C call and the host has one command thread, hence the abandonable worker; the vendored Lua is not patched for it.

Consequences and trade-offs. Lua OnDisable and OnDestroy no longer run on the edit host; engine-derived defaults are unknown (shown as placeholders); a script that branches on a stub can take a different path than at play.

Where to look: scripting-lua.html#design-lua-execution-policy; scripting-lua.html#design-declaration-evaluator; scripting-lua.html#design-declaration-worker; orchestrator/proposals/security-design-lua-editmode-and-preauth-slots.md

One sandbox builder with profiles serves declarations and editor extensions stated

Decision. The allocator cap, count hook with a deadline, budget sandbox and panic repair live in one builder; the declaration evaluator and the extension host are profiles on top of it.

Context. Editor extensions need the same machinery.

Why. Stated: "two copies would drift"; the evaluator's existing tests act as the oracle.

Consequences and trade-offs. None recorded.

Where to look: scripting-lua.html#design-lua-sandbox-builder

Free registry slots are reserved before unprotected references stated

Decision. Rather than making references inside the protected call, the runtime reserves registry slots first.

Context. A returned value sits on the outer frame's stack, which a protected call's new C frame cannot read.

Why. Stated: sol's reference constructors are noexcept, so a failure inside one ends the process even in a protected call on builds where Lua errors are C++ exceptions (web, MSVC Debug).

Consequences and trade-offs. None recorded.

Where to look: scripting-lua.html#design-lua-registry-reserve

A marked patch in vendored sol2 instead of rewriting binding lambdas stated

Decision. Under real GCC only, a type name that mentions a lambda gets the compiler's unique mangled name appended.

Context. GCC prints every lambda of one signature in one function as the same name, so two lambdas shared a metatable and Lua called the wrong function.

Why. Stated: sol2 3.2.3 has no upstream fix; changing the many binding lambdas into named functors would also have worked but was not chosen.

Consequences and trade-offs. A patch to carry across sol2 upgrades.

Where to look: testing.html#design-sol2-lambda-names; external/sol2/include/sol/sol.hpp

Script data is declared in a table the editor can read not-recorded

Decision. Scripts declare serializable fields (and, for networking, replicated = true, Rpcs, input layouts).

Context. Editor inspector and replication both need field schemas.

Why. The repository does not record the reason for the declaration-table form in the pages read here. Inference: the same schema serves the inspector, serialization and the network codecs.

Consequences and trade-offs. Computed defaults need explicit types in the editor's evaluator.

Where to look: scripting-lua.html; serialization.html

Editor host, frontend and MCP bridge

The editor is split in two: a C++ headless host that owns the engine and the project, and an Electron frontend in a separate repository (EpicNicks/N2Engine-Electron-Frontend) that talks to it over a binary protocol. The MCP bridge is a third piece that is also an ordinary protocol client.

A headless host plus a separate Electron frontend, joined by a binary protocol mixed

Decision. The host (N2EditorHost, editor-server/) runs the engine, owns the scene and the project and serves a TCP request and response protocol; the Electron UI lives in its own repository and follows editor-server/protocol/protocol.json. The frontend is not in this repository.

Context. The editor plan (issue #6) was approved by the user on 2026-10-06 with its decisions, which include "Electron spawns the play-mode child process".

Why. Stated in the saved plan: the frontend is meant to follow the editor-server pattern; the host runs windowless, so it works over Docker or SSH, in CI and for remote projects; frames and audio are streamed to the client. The repository does not record why Electron was chosen over another UI toolkit; inference: a web UI stack that can also be tested with Node and jsdom in CI (the frontend repo has its own CI).

Consequences and trade-offs. Two repositories kept in step: the frontend pins an engine commit (engine-ref.txt) and regenerates its client from protocol.json; the engine pins the frontend for the MCP smoke test.

Where to look: editor.html; logging-and-editor.html; orchestrator/project-memory/editor-plan-issue6.md; orchestrator/project-memory/electron-editor-frontend.md; editor-server/protocol/protocol.json

One protocol.json is the spec; clients and vectors are generated from it stated

Decision. The protocol is a request and response pair per command (no server push); events are polled from a bounded ring (4096 events, about 2 MiB, 1024 per poll, messages cut at 16 KiB); a client keeps its place as an epoch and a sequence number; FrameUpdate is one response with a flag.

Context. The editor protocol is a binary protocol, one response per request, in order.

Why. Stated: "the spec, generators and vectors assume one response type per command"; a polled ring gives no per-client server state, so a reconnecting client neither loses nor repeats events; serving PollEvents logs nothing so polling never feeds the ring; the frame-changed event is sent once per rendered frame so a drag does not fill it.

Consequences and trade-offs. Polling instead of push; events beyond the ring are dropped and counted.

Where to look: logging-and-editor.html#design-poll-events; logging-and-editor.html#design-event-seq; logging-and-editor.html#design-event-limits; editor.html#design-frame-update-one-response

Protocol versions are additive: new fields are trailing, a minor bump never breaks an older client stated

Decision. Versions are major.minor.patch. A minor bump adds commands, or trailing optional fields: a server reads a trailing field only when the payload has bytes left and defaults it otherwise (ReadTrailing); a newer server's trailing response fields are ignored by older generated decoders. Hello refuses another major version and accepts any minor; capabilities covers optional features the version does not imply. New denial information goes in a new response (ErrorCoded) sent only to a client that asked in Hello, never in a field on Error.

Context. The protocol is at 1.30.0 in the frontend pin; clients ship on their own schedule.

Why. Stated: a client older than a field must not break (reading unconditionally would throw and answer Error); Error's payload is raw bytes with no room for a trailing field; when minors differ the server logs a warning because commands only one side knows fail with "Unknown command". Protocol numbers are reserved per planned change (for example 1.24.0 asset move, 1.25.0 prefab references, 1.26.0 prefab stage) and renumbered if the merge order flips.

Consequences and trade-offs. Every change to the protocol also needs a frontend sync PR; features cannot be removed within a major.

Where to look: logging-and-editor.html (protocol.json section); logging-and-editor.html#design-error-coded; orchestrator/proposals/next-work-plan-2026-10-31.md; editor-server/protocol/protocol.json

Play mode runs in a separate child process started by the launcher stated

Decision. The launcher starts the play child; the edit host only writes a snapshot of the scene in memory. The play host refuses commands that write the project or swap the scene, steps exactly one fixed timestep per step command, takes keys from an Input::KeySource instead of a window, and runs a frame then commands for the rest of a 16 ms budget.

Context. The child shares the project folder with the edit host.

Why. Stated: process management stays out of the portable, testable server; the snapshot is the scene in memory so unsaved edits play and nothing is saved; "one command sent to the wrong connection must not overwrite" the project; frames pace at 60 per second whatever the client does and a busy client is still answered.

Consequences and trade-offs. Two hosts to run and keep consistent.

Where to look: editor.html#design-play-child-launcher; editor.html#design-play-refuse-edits; editor.html#design-play-frame-pacing; editor.html#design-play-keysource

The editor camera, hierarchy order and dirty state belong to the server stated

Decision. The editor camera is server state (pose and projection only: not a scene object, not saved, not in undo); the client computes orbit, pan and fly. The hierarchy is a flat depth-first list with a revision. Dirty is a revision compared with a saved revision. One frame revision covers every cause of a changed frame.

Context. A scene with no camera should still be viewable.

Why. Stated: looking around must never mark a scene unsaved; one number tells a client its frame is current; an edit that changes nothing does not move the revision.

Consequences and trade-offs. The server holds view state.

Where to look: editor.html#design-editor-camera-server; editor.html#design-flat-hierarchy; editor.html#design-saved-revision; editor.html#design-frame-revision

One JSON project file; the project id is the asset UUID namespace; saves are atomic stated

Decision. project.n2proj holds the name, id, engine version, startup scene, scene list and per-subsystem settings blocks (unknown keys kept). A random projectId replaces a hash of the folder path as the UUID namespace. Files are written to a temporary file and renamed. Settings change by RFC 7386 merge patch, and a block a subsystem refuses is never saved. --create never starts the engine.

Context. Editor plan E2 and E3.

Why. Stated: moving or cloning a project keeps every asset UUID; scenes and the project file are never half-written; creating a project is a pure file operation. user:// is per project so two games stop sharing saves.

Picking is a CPU ray against bounds and shapes, not a physics query stated

Decision. Boxes order the candidates and the exact shape (triangles via a per-mesh BVH, text rectangle, topmost graphic of a world canvas) decides; objects with no shape get a 0.25-unit pick sphere; UI objects get none; the answer includes the hit point and normal.

Context. Edit-mode scenes have no physics bodies.

Why. Stated: edit-mode scenes have no bodies and most visual objects no collider, so the engine's own geometry decides; an ID-buffer pick can replace the exact step later. The BVH answers exactly as the linear scan does.

Consequences and trade-offs. A CPU cost per pick, bounded by the BVH.

The asset watcher polls the directory listing, gated on a client stated

Decision. Once a second, only while a client could be looking, with a fingerprint taken before the scan reads anything. File size and time live in .n2/asset-state.json, not in the .meta; times are Unix milliseconds. A script is reloaded in place; other assets are dropped from the cache.

Context. Asset changes need to reach the editor.

Why. Stated: polling is "portable, testable, no thread to coordinate with"; a committed .meta should not change with every edit; two saves of the same size in one second are two changes; textures are immutable and held by pointer so reload means drop.

Consequences and trade-offs. A one-time re-import of models when milliseconds were introduced.

Context. The proposal first recommended redirect aliases; the user accepted stable UUIDs on 2026-10-31.

The MCP bridge is a separate stdio process, an ordinary protocol client stated

Decision. n2-mcp is TypeScript on the official MCP SDK, speaks stdio, lives in the frontend repository, and uses its own per-user token. It has three backends: --launch (spawns its own host), --connect (TLS with a pinned fingerprint) and --electron (attach to the running app). Every mutating tool call is one undo step labelled AI:; irreversible operations need elicitation or an operator flag, never a model-supplied confirm argument; the bridge refuses the admin role by default, has no shell, file system or network tools, wraps untrusted text as data and strips host paths. A Hello yield flag (protocol 1.22.0) makes an agent never preempt a human.

Context. Decisions M1 to M12.

Why. Stated: no new network surface (the hardened host protocol, tokens, roles and audit stay the only exposure); a hijacked agent can do at most what its token's role allows; the official SDK tracks a fast-moving spec which would be "L+ and permanently behind" in C++; "a shell through MCP would erase the capability boundary"; an injected instruction can set confirm: true. Consequences and trade-offs. Node 22 on the agent's machine; HTTP transport deferred; the bridge pin in tests/smoke/mcp-bridge-ref.txt must be bumped when the frontend changes.

Consequences and trade-offs. The engine must keep rendering or audio time stops.

Security posture

Most of the exposure is the editor host and the game server. The stance is fail closed, bound everything before authentication, and give every role the least it needs. The security audit (2026-10-15) found the authentication core sound and the risk mostly availability.

The host listens on loopback only, and a non-loopback bind fails closed stated

Decision. The protocol has no authentication in the loopback case, so the host binds 127.0.0.1 unless --bind says otherwise; a non-loopback bind needs a token and --tls, or --insecure-bind, or the host refuses to start. Every command runs on the main thread.

Context. Audit finding F5: --bind 0.0.0.0 with no token gave an unauthenticated peer admin with only a warning.

Why. Stated in the audit and the loopback decision. The same stance was reused for the game server.

Consequences and trade-offs. Remote use needs TLS and tokens.

Where to look: logging-and-editor.html#design-loopback; orchestrator/proposals/editor-host-security-audit-2026-10-15.md

Per-user tokens (hashed) and three roles; a viewer may not play stated

Decision. A tokens file holds sha256: hashes of machine-made 256-bit tokens; roles are viewer (read class), editor (read and write) and admin. Play commands are writes because they run project Lua, so a viewer cannot play. The tokens file reloads on the next connection and on SIGHUP and keeps the old table if a reload fails. No trusted-proxy support.

Context. User decisions of 2026-10-13; protocol 1.11.0.

Why. Stated: a 256-bit random token has nothing to guess, so an unsalted SHA-256 is adequate; the hash comes from the TLS library so the tokens file needs the TLS build (the user chose Mbed TLS over a vendored SHA-256); a typo while revoking someone must not lock everyone out; behind a reverse proxy every peer is loopback, so per-address bans would lock out everyone and trusting a forwarded address can be spoofed.

Consequences and trade-offs. Rate-limit lockouts can hit the real user in the tunnel case.

Where to look: logging-and-editor.html#design-tokens-hash; logging-and-editor.html#design-tokens-roles; logging-and-editor.html#design-tokens-reload; orchestrator/proposals/exposed-host-hardening.md

A read-only host runs an allow list of reads, default deny, with a test that every command is classified stated

Decision. Every protocol command is classified Read, Write or Admin in a table; a test fails on any command that is not; an unclassified command or unknown id is refused.

Context. The play host already had a 13-command deny list.

Why. Stated: the old edit-only list covered file-writing commands only, so reusing it would leave in-memory mutation open; a new command must not be able to ship unclassified.

Consequences and trade-offs. Every new command needs a classification decision.

Where to look: logging-and-editor.html#design-read-allow-list; orchestrator/proposals/exposed-host-hardening.md

Per-connection cost is bounded before and after authentication stated

Decision. A 5 s TLS budget and a 2 s Hello budget, idle and write deadlines, pre-auth slots (default 4) with per-address and global rate limits, a session arbiter (accept, same-user takeover, higher-role preemption, else Busy), and the token checked before any per-user backoff. Loopback has no counter or backoff.

Context. Audit F1, F2 and F6: one silent peer could hold the only slot, an idle viewer could lock out admins, and a per-user backoff let anyone lock out a named user.

Why. Stated: goal "no unauthenticated connection delays an authenticated session". Alternatives rejected: a single event loop (new incremental parsing and TLS state machine) and a thread per connection (churn); queuing was rejected because queued connections hold pre-auth slots that token holders can fill.

Consequences and trade-offs. Same-user takeover lets anyone with a user's token kick that user (they could log in as them anyway).

Where to look: logging-and-editor.html#design-connection-deadlines; orchestrator/proposals/security-design-lua-editmode-and-preauth-slots.md

Log lines carry a sensitivity, and viewers read a public, scrubbed view stated

Decision. The host's own audit, Hello, rate-limit, peer and path lines are Admin; engine and script lines are Public. The public view omits Admin events, scrubs host paths, and is numbered on its own so a sequence gap does not reveal a hidden line. Remote clients get sanitised errors; determinism settings are admin-only.

Context. Audit F9 and F10: viewers could read users, roles, IPs and absolute paths.

Why. Stated: that exposure; a host with no authentication keeps the full log.

Consequences and trade-offs. Two views of the ring.

Where to look: logging-and-editor.html#design-event-sensitivity; PR #191; PR #192

Scene, prefab and snapshot data is treated as untrusted and size-capped stated

Decision. Hierarchy at most 512 levels deep, scene text at most 1088 JSON levels; images capped at 16384 pixels a side or 256 MiB decoded (rejected from the header); text assets limited to an allow-list of extensions, strict UTF-8 and 4 MiB; one path checker refuses names Windows cannot hold on every OS and resolves symbolic links; models and Lua sources have their own caps.

Context. A chain of children 100,000 deep overflowed the stack and a saved deep scene became a crash loop (audit F4).

Why. Stated for each: a client's LoadScene, a .scene written by an editor and a project from git are all untrusted input.

Consequences and trade-offs. A legitimately huge asset is refused.

Where to look: serialization.html#design-depth-caps; meshes.html#design-image-caps; editor.html#design-text-allowlist; editor.html#design-asset-paths

TLS in the host is optional, vendored Mbed TLS, with pinned fingerprints on the client mixed

Decision. N2ENGINE_EDITOR_TLS (default OFF) builds the host's TLS from the vendored Mbed TLS; the frontend pins a certificate fingerprint (trust on first use) for a direct remote connection.

Context. The Linux host work chose TLS on and PhysX off for the Linux container.

Why. Stated: Mbed TLS was already needed for hashing tokens and vendored in the tree; browsers cannot use the editor's self-signed trust model for the game server (see WebSocket first). The repository pages read here do not record why TLS is default OFF; inference: the extra vendored C code and build time for builds that only ever bind loopback.

Consequences and trade-offs. A build without it cannot use a tokens file.

Where to look: CMakeLists.txt (N2ENGINE_EDITOR_TLS); orchestrator/proposals/linux-host.md; logging-and-editor.html

Third-party code is vendored and pinned, with notices; OpenAL Soft stays dynamically linked stated

Decision. Libraries live under external/ with recorded versions; THIRD_PARTY_NOTICES.md carries notices, and binary artefacts must carry them too. FreeType is used under the FTL (chosen from the dual FTL or GPL-2.0 licence); OpenAL Soft stays dynamic because of its LGPL licence.

Context. A 2026-10-15 notices audit.

Why. Stated: switching OpenAL Soft to static linking would need the LGPL obligations revisited. The audit says it is not legal advice.

Consequences and trade-offs. Every vendored upgrade needs notice updates.

Where to look: THIRD_PARTY_NOTICES.md; orchestrator/proposals/third-party-notices-audit-2026-10-15.md; scripts/check-jolt-vendor.sh; scripts/check-box2d-vendor.sh

Assets, serialization and import

Small decisions that keep data loading safe, predictable and the same across platforms.

Field registration returns a builder holding an index, not a reference stated

Decision. FieldBuilder holds the member list and the member's index so .Range() chains stay valid however many members are registered after it. A set calls only the members whose keys are present and is checked on a copy from a second instance.

Context. The obvious design returns a reference into a list that may move.

Why. Stated: a builder kept in a variable would write through a dangling reference; some member deserialisers clear their list when a key is missing, so loading a whole component to set one field would empty reference lists.

Consequences and trade-offs. A slightly more indirect API.

Where to look: serialization.html#design-field-builder-index; serialization.html#design-partial-set

An asset's type name is declared once, as a static stated

Decision. The virtual GetResourceType() is implemented from the class's static name. Light::color stays a Vector3 marked as a colour for the inspector rather than becoming a Common::Color.

Context. A second spelling could drift ("Font" versus "font") with no compile error; a type change would break the JSON and C++ and Lua API.

Why. Stated for both: the hint "changes no type, so light.color keeps its API for C++ and Lua code, and keeps its JSON".

Consequences and trade-offs. An extra hint on the field.

Where to look: serialization.html#design-resource-type-name; serialization.html#design-light-color-hint

Mesh import: one MeshRenderer, submeshes as index ranges, sub-assets with stable UUIDs stated

Decision. MeshRenderer holds the mesh and one material per submesh (no MeshFilter); a mesh is one vertex and index buffer with submeshes drawn as index ranges; a model's sub-assets get UUIDs from their own namespace keyed by name when every name of a kind is unique and by index otherwise; unsupported glTF features warn once (Draco and meshopt are errors); FBX and OBJ support (ufbx) is vendored, optional and on in one CI leg.

Context. The mesh plan (issue #3).

Why. Stated: nothing needs a separate filter component yet; scenes can reference sub-assets like files; ufbx is off by default because it is about 1.2 MB and costs a manual upgrade and an opt-in. FBX and OBJ default to smooth normals and non-metallic, unlike glTF, and are documented as such.

Consequences and trade-offs. Two defaults for missing normals (smooth for FBX/OBJ, flat for glTF).

Where to look: meshes.html#design-one-mesh-renderer; meshes.html#design-index-ranges; meshes.html#design-sub-asset-uuids; meshes.html#design-ufbx-optional

UI is GameObjects in a canvas pass with Unity's anchor model stated

Decision. Canvases, RectTransforms and graphics are components that draw after the scene in hierarchy and sort order with depth and culling off; a rect hit test gives UI the pointer before the world through OnMouse*. A button tints its graphic at draw time, OnClick is an EventHandler fired on OnMouseUpAsButton and listeners are not serialized.

Context. UI needs the scene, serialization and scripting to work as for any object.

Why. Stated for the individual pieces: the tint is separate and unsaved so the colour is never overwritten; the button reuses the dispatcher's capture rules; scenes save colours and flags while code adds listeners after loading.

Consequences and trade-offs. A button needs a raycast target on its own object.

Where to look: ui.html#design-ui; ui.html#design-button-tint; ui.html#design-button-event; ui.html#design-button-listeners

Known gaps in this page

This page was written from the pages in docs/, the proposals in orchestrator/proposals/, code comments and CMake options, and merged PR descriptions. It does not claim to be complete.

  • The Electron frontend is a separate repository and is not in this tree; only what this repository records about it is covered.
  • Several proposals were read through their decision sections and summaries, not line by line (the electron UI roadmap, prefab overrides, the Lua extension design and the security audit findings F8 to F18). Their entries say "stated" only for what was read.
  • Decisions made only in conversation, in issue threads or in PR review comments (for example the reasons behind choosing Electron, default-off TLS, or which CI check is required) are not recorded in the repository, and the entries say so rather than guess.
  • A proposal's "recommendation" is not a decision. An entry that describes a recommendation says so; entries marked as decided cite where the user's choice is recorded.
  • The per-page "Design decision" callouts hold many more small decisions (for example every editor protocol command). Follow the "Where to look" links for the detail.
