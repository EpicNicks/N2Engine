User shaders

A .n2shader file is a fragment shader you write once and use on a Material, a Sprite2D, a UI Image or a particle system, on Vulkan, WebGPU (the browser) and OpenGL, with the editor cooking it when you save. This page is for the person writing one: the file, the names you can use, what is not available, and how to set its parameters. The engineering behind it is in orchestrator/proposals/user-shaders.md; how a pack and the editor handle it is in Packs and Editor projects.

The file

A .n2shader is one text file: a JSON header, then a line that is exactly #stage fragment, then GLSL (version 450 core, no #version line of your own). The engine writes the vertex stage, so a shader is fragment-only and the vertex input and the five varyings are fixed.

{ "n2shader": 1,
  "name": "Dissolve",
  "params": [
    { "name": "baseColor",        "type": "color",   "default": [1, 1, 1, 1] },
    { "name": "baseColorTexture", "type": "texture", "default": "white" },
    { "name": "u_Threshold",      "type": "float",   "default": 0.5, "min": 0, "max": 1, "label": "Threshold" },
    { "name": "u_Edge",           "type": "color",   "default": [1, 0.5, 0, 1] },
    { "name": "u_Noise",          "type": "texture", "default": "white" }
  ],
  "state": { "blend": "alpha", "cull": "none" }
}
#stage fragment
void main() {
    vec4 base  = baseColor * n2_texture(baseColorTexture, n2_UV) * n2_Color;
    float n    = n2_texture(u_Noise, n2_UV).r;
    if (n < u_Threshold) { discard; }
    float edge = 1.0 - smoothstep(0.0, 0.08, n - u_Threshold);
    n2_FragColor = mix(base, u_Edge, edge);
}
  • Header keys: n2shader (the format, 1), name, params, uses (optional, ["lighting"]), state (optional hints) and targets ({"webgpu": "generated"}, the only value). Any other key is an error that names it.
  • Errors cite your file. The generated GLSL is compiled behind a #line directive, so a message reads assets/dissolve.n2shader:14: error: ... with your line number, in the editor (GetShaderInfo, the host log), in n2build and in the engine's log.
  • Line endings may be LF or CRLF; a leading byte order mark is ignored.

  • Names are GLSL identifiers, unique, and do not start with n2_ or gl_ (those are the engine's). They are also the keys scripts and code use.
  • Editor hints label, min, max, step, tooltip and group are ignored by the shader; min and max also clamp a number that is set (it is clamped, not refused).
  • Reserved names bind to the standard fields so a custom shader tints and textures like the built-ins: a color named baseColor is the Material's base colour times the draw's colour (a Sprite2D's or Image's colour, a particle's), and a texture named baseColorTexture is the Material's base colour texture (the sprite's texture) and takes slot 0. Other textures take slots 1–4 in the order declared (or 0–3 without a baseColorTexture).
  • Limits: at most 64 parameters, 5 textures and a 256-byte block (std140 layout, in declaration order). No arrays as parameters (you may use arrays inside the shader); a mat4 takes 64 bytes of the block, so four of them and a few floats use it up.
  • Blend modes. alpha is SRC_ALPHA, ONE_MINUS_SRC_ALPHA; additive adds the colour (SRC_ALPHA, ONE); premultiplied is ONE, ONE_MINUS_SRC_ALPHA, so the shader writes colour that is already multiplied by its alpha (n2_FragColor = vec4(rgb * a, a)); multiply is DST_COLOR, ZERO: the target's colour times the shader's, so a pixel that should not change must write white, and the shader's alpha is not used (the target's alpha stays). Any of them makes the Material a Blend one. A .mat can set "blendMode": "alpha" | "additive" | "premultiplied" | "multiply" (written only when it is not alpha), and Material::SetBlendMode does the same from code; a component's own shader (Sprite2D, Image, ParticleSystem) follows the shader's hint. The software renderer cannot blend and ignores all of it.
  • state supplies defaults for a Material that does not set them: blend (none, alpha, additive, premultiplied, multiply: see blend modes), cull (none or back), depthWrite, queue (opaque, transparent). They are hints: a value the .mat sets wins, and queue has no effect unless the Material also blends.

What the fragment stage can use

NameWhat it is
n2_UV, n2_Color, n2_WorldPos, n2_Normal, n2_TangentThe vertex stage's outputs: texture coordinates (vec2), vertex colour (vec4; a particle's start-to-end colour, white on a sprite), world position, world normal, world tangent (vec4)
n2_FragColorThe one output, vec4
n2_texture(slot, uv), n2_textureLod(slot, uv, lod), n2_texelFetch(slot, texel, lod), n2_textureSize(slot, lod)Sampling. The slot is the texture parameter's name. Write these, never sampler2D: the spelling differs between backends and the prelude hides it
isnan(x), isinf(x)Work on a float and on a vec2, vec3 or vec4 (a bvec back), on every backend. WGSL has no NaN or infinity, so Tint refuses the built-ins; a shader whose stage names either gets engine functions (n2_isnan, n2_isinf) that test the IEEE bit pattern, and isnan and isinf are macros for them. A shader that uses neither is unchanged. A GPU compiler may assume a value is finite and fold the test away, so treat the result as a diagnostic, not as a guarantee
n2_FragCoord()The pixel position, origin top-left on every backend (raw gl_FragCoord differs, so it is refused)
n2_Model, n2_View, n2_ProjectionThe draw's matrices; n2_Model * v means the same everywhere
n2_StageDim, n2_TintSaturation, n2_TintInside, n2_TintCircleThe per-draw screen-tint values the built-in shaders read (the editor's and the game's screen tint)

Lighting is opt-in: with "uses": ["lighting"] the scene's lights are in the prelude (n2_CameraPos, n2_AmbientLight, n2_NumDirectionalLights and the light arrays) and so are three helpers: n2_LightDiffuse(normal, worldPos), the lit shader's Blinn-Phong diffuse part (ambient plus each light), n2_Attenuation(distance, range, attenuation), and n2_EncodeOutput(color), the sRGB encode for authors lighting in linear space (a no-op unless the project's linear lighting is on). There are no shadows. A shader without uses does not pay for any of it.

What is not available, and the limits

The cook refuses these with a message at your line, so you find out when you save, not when a player runs it:

  • gl_Position (the vertex stage is the engine's unless you write your own, which sets the position with n2_SetPosition); gl_FragCoord (use n2_FragCoord()), gl_FrontFacing, gl_FragDepth, gl_VertexID, gl_InstanceID and other gl_ inputs.
  • Any uniform, in, out, layout or buffer declaration of your own (parameters come from the header), #extension lines, and array, shadow and integer textures and images (a cube or 3D texture is a parameter type, not a sampler you declare).
  • Atomics, barriers and image access; textureGrad and textureGather.
  • Sample, then branch. Sampling after a discard or inside a non-uniform branch is an error on WebGPU (the browser's rule); sample first (as the example does) or use n2_textureLod / n2_texelFetch, which need no derivatives.
  • In the default (strict) mode, loops need an integer literal or const bound: while and do are refused (a shader that never ends cannot be ruled out in general, so a bounded for is the rule). The cook tool has a --relaxed option for your own use (node tools/n2shader/n2shader.mjs cook --relaxed).
  • Size limits: 256 KiB and 20,000 lines for the file, a 64 KiB header. Everything else that translates to all three backends (inverse, determinant, arrays, switch, fwidth) is allowed.

The conformance corpus in renderer/shaders/user/corpus has a working example of each of these and a refused one of the rest.

Cube and 3D textures

A cube or texture3d parameter is a normal 2D texture holding an atlas, read through a lookup function, so it needs no new descriptor, pipeline or backend support and works on every backend the same way. It takes one of the five texture slots.

  • cube: six square faces side by side in the image, in the order +X -X +Y -Y +Z -Z (OpenGL's and Vulkan's cube order), each stored as a cube map image is (the image is 6 * size wide and size tall). n2_textureCube(u_Sky, direction) picks the face by the largest component and reads it.
  • texture3d: depth slices side by side, slice 0 first (the image is depth * width wide). n2_texture3D(u_Lut, u_Lut_depth, uvw) blends the two nearest slices (trilinear); u_Lut_depth is the header's depth. A 16 x 16 x 16 colour-grading LUT is a 256 x 16 image.
  • Import the atlas with filter Bilinear or Point, wrap Clamp and mipmaps off (the lookups read level 0, and keep each tap half a texel inside its face or slice so filtering never bleeds into the neighbour). A cube's faces are not blended with each other at the edges (no seamless cube filtering).
  • Defaults: white, black or none (a 1 x 1 texture reads the same in every direction), like a texture. A .mat, Material::SetTexture and MaterialInstance:SetTexture take the atlas as for a texture.
  • Cooked only: the lookups live in the cook's prelude, which the runtime compiler does not embed, so a shader with one of these draws from cooked data (the project's build or the editor makes it), as the fallback without it.
  • Not done: true cube-map and 3D samplers (a texture of those kinds as a GPU resource, hardware seamless filtering, mip levels): that needs another descriptor type in the one layout every material shares, an ITexture creation API per backend and an asset format for the sources, and is left for when an atlas is not enough.

A custom vertex stage

By default the engine writes the vertex stage (so a shader cannot forget the depth remap), and your fragment stage reads what it writes. To move geometry (waves, wind, billboards, a squash), add a #stage vertex block after the fragment stage:

{ "n2shader": 1, "name": "Wave", "params": [ { "name": "u_Wave", "type": "float", "default": 0.1 } ] }
#stage fragment
void main() { n2_FragColor = n2_Color; }
#stage vertex
void n2_vertex() {
    n2_WorldPos.y += sin(n2_WorldPos.x * 4.0) * u_Wave;
}

You write void n2_vertex(), never main. The engine's main does three things: it runs its default maths (the world position, the normal matrix, the unit tangent with its mirror sign, the uv and the vertex colour), then calls your n2_vertex(), then writes the clip position from n2_WorldPos unless you called n2_SetPosition(vec4 clip) yourself (give it OpenGL clip space, z from -w to w; it applies the target's depth remap, which is why gl_Position stays unavailable).

  • What you can read: the five vertex attributes as n2_in_Position (vec3), n2_in_Normal (vec3), n2_in_UV (vec2), n2_in_Color (vec4) and n2_in_Tangent (vec4); n2_Model, n2_View, n2_Projection; and the shader's parameters (the same block as the fragment stage, so u_Wave above is one value in both).
  • What you can write: the five varyings the fragment stage reads, n2_UV, n2_Color, n2_WorldPos, n2_Normal, n2_Tangent, already filled by the default maths, and the clip position through n2_SetPosition. A normal you change is not renormalised for you.
  • Not in the vertex stage (v1): textures, n2_FragCoord(), n2_FragColor, discard, gl_VertexID/gl_InstanceID, the lighting block, and your own main. The same strict loop rules apply. isnan and isinf work as in the fragment stage.
  • Cooking: each target gets a vertex payload next to the fragment one (shader.vulkan.vert.spv, shader.webgpu.vertex.wgsl, shader.gl.vert), checked like the fragment stage (glslang, spirv-val, the reflection of the PerDraw and Material blocks and of the five inputs and outputs, Tint and naga for WGSL). The engine makes your fragment stage read all five varyings (it renames your main and wraps it), so no vertex output is left unread, which the Vulkan validation layer would report.
  • Only cooked: the runtime compiler (N2ENGINE_RUNTIME_SHADER_COMPILER) does not build vertex stages: a shader with one draws from the cooked data the project's build or the editor makes, and as the fallback without it. A stripped pack keeps the empty #stage vertex line so the engine knows the cooked data has a vertex stage.
  • Costs: one more shader module per such shader and its pipelines; shaders without a vertex stage use the engine's shared module, exactly as before.

Authored WGSL for the web

By default the WebGPU build runs the WGSL that Tint makes from your GLSL, so one source drives every backend. When that translation gets in the way (a feature WGSL has and GLSL does not, a hand-tuned loop), a shader can supply its own WGSL for the web only. Set "targets": { "webgpu": "authored" } in the header and add a #stage wgsl block after the fragment stage:

{ "n2shader": 1, "name": "Tint", "params": [ { "name": "u_Color", "type": "color", "default": [1, 0.5, 0, 1] } ],
  "targets": { "webgpu": "authored" } }
#stage fragment
void main() { n2_FragColor = u_Color * n2_Color; }     // Vulkan and OpenGL
#stage wgsl
struct Material { u_Color : vec4<f32>, }
@group(1) @binding(0) var<uniform> material : Material;
@fragment
fn main(@location(1) n2_Color : vec4<f32>) -> @location(0) vec4<f32> { return material.u_Color * n2_Color; }

The GLSL still feeds Vulkan and OpenGL (and the runtime compiler); keeping the two equal is yours. To start from the generated WGSL, cook the shader without the targets line and copy shader.webgpu.wgsl. The cook still holds the module to the contract, and tells you the file and line:

  • One @fragment fn main, its inputs written as parameters (@location(0) n2_UV vec2<f32>, 1 n2_Color vec4<f32>, 2 n2_WorldPos vec3<f32>, 3 n2_Normal vec3<f32>, 4 n2_Tangent vec4<f32>, any subset), returning @location(0) vec4<f32>. No @vertex, no @compute, no enable, requires or diagnostic directive.
  • Only the contract's resources: @group(0) @binding(0) the per-draw block with the contract's members in its order (only if you use it), @group(0) @binding(1) the lighting block with "uses": ["lighting"], @group(1) @binding(0) the Material struct laid out as the header says (same member names, order and offsets), and for each texture parameter texture_2d<f32> n2_texN at binding 1 + slot and sampler n2_sampN at 6 + slot.
  • Tint and naga both read it (and Tint writes it back to SPIR-V), as for a generated module. At most 256 KiB.

The player validates the module again with the browser's own WGSL compiler, so a module that slips past the cook makes the shader draw as the fallback, never crash. The manifest of an authored shader lists "authored": ["webgpu"].

Using a shader

  • On a Material: set "shader": "res://shaders/dissolve.n2shader" and "params": {...} in the .mat (or Material::SetShader and the typed setters), and every user of the Material draws with it. In Lua, Material.Load gives the shared asset and renderer:GetMaterialInstance(slot) a copy that is yours alone (Materials).
  • On a Sprite2D, a UI Image or a ParticleSystem (a component with no Material of its own): SetShader gives it a private Material, so one object's values never reach another's. 
    local fx = go:AddComponent('Sprite2D')
fx:SetTexture('res://art/hero.png')
fx:SetShader('res://shaders/dissolve.n2shader')
local m = fx:GetMaterialInstance()       -- the shader's parameters, on this sprite's own material
m:SetFloat('u_Threshold', 0.3)
m:SetColor('u_Edge', Color.Red)
m:SetTexture('u_Noise', 'res://art/noise.png')
    sprite->SetShader(shader);                 // a std::shared_ptr<Shader>, or nullptr for the built-in one
sprite->SetShaderParam("u_Threshold", 0.3f);
sprite->SetShaderParam("u_Edge", Common::Color::Red);
sprite->SetShaderInt("u_Steps", 4);

    The component's texture is the shader's baseColorTexture, its colour the baseColor, and on a renderer that cannot blend the cut-out of a texture's transparent pixels stays. Its saturation and flash are not applied (they are the built-in shaders'; a user shader declares what it reads). A UI Image shows only its sprite through a shader, not a raw texture set with SetTexture. Setting nil goes back to the built-in shader.

  • In scene and prefab files, per object. A Sprite2D, Image or ParticleSystem with a shader saves a shaderState key: {"shader": "<the .n2shader asset's UUID>", "params": {"u_Gain": 2.5, "u_Color": {...}}}, the same value spellings as a .mat's params (a texture as its path). The shader is named by UUID, so moving the asset keeps the link. A component without a shader writes no such key, so every file written before this is unchanged, and loading a file without it clears the slot. Each instance has its own values (a prefab's instances differ the way any component fields do). The key is in no schema and is never replicated, so rollback snapshots, replication and replay hashes do not hold it. An unusable shader or a value that does not fit its parameter is dropped with a warning, as in a .mat. There is no inspector widget yet (the editor frontend is separate): set values from a script, or write the key.
  • Per frame. Setting a number, vector or colour every frame costs nothing extra (they are uniforms); setting a texture makes a new GPU material, so do it when it changes.

When it cannot be drawn

A Material, sprite, image or particle system whose shader cannot be drawn is never skipped, and never stops a frame: it draws the built-in unlit shader with its base colour and texture, and logs one error naming the shader and the reason. In the editor host the fallback is flat magenta so the failure is obvious; in a player it looks like the object without the shader. The reasons: the shader was never cooked for this backend (or was cooked from an older header: stale), the cook failed (the diagnostics are in GetShaderInfo), the backend has no user shaders (the software renderer), or the compile on the device failed. A pack whose shader sources were stripped (Packs) cannot recompile and uses the fallback when its payload does not fit.

Shaders are not game state

Guarantee

A shader and its parameter values are render-only. Nothing a shader computes can reach the simulation, and no shader value, Material instance or component shader is part of a rollback snapshot, a replication payload or a golden-replay hash. A test sets a Material parameter every frame and checks the state hash does not move; a component's shader is not even a serialized field.
