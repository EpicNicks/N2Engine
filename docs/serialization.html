Serialization

Scenes, GameObjects and components serialize to JSON (nlohmann::json). Loading runs in two phases: first every object and component is created, then cross-references are resolved by UUID. This page covers the JSON shape, how components declare serializable fields, how object, component and asset references survive a round trip, and what happens when the data is malformed.

Scene JSON

Scene::Serialize() writes the scene name and its root objects, each serialized recursively. That's all: the scene's own UUID, the attach queue, coroutines and anything else at runtime are not saved. SceneManager stores scenes in exactly this form; see SceneManager storage model.

A trimmed example, put together from Scene::Serialize, GameObject::Serialize, Positionable::Serialize and Light's registered members. Some Light fields are left out, and the UUIDs are illustrative:

{
  "name": "Level1",
  "rootGameObjects": [
    {
      "uuid": "6f1c2a8e-0d7b-4c39-9a51-2b7e4f0c9d13",
      "name": "Lamp",
      "tag": "Untagged",
      "layer": 0,
      "isActive": true,
      "positionable": {
        "localPosition": { "x": 0.0, "y": 3.0, "z": 0.0 },
        "localRotation": { "w": 1.0, "x": 0.0, "y": 0.0, "z": 0.0 },
        "localScale":    { "x": 1.0, "y": 1.0, "z": 1.0 }
      },
      "components": [
        {
          "type": "Light",
          "data": {
            "uuid": "b3e9d1f0-5a62-4f8e-8c07-91d4a6e2f5b8",
            "isActive": true,
            "type": "Point",
            "color": { "x": 1.0, "y": 0.9, "z": 0.8 },
            "intensity": 1.5,
            "range": 10.0
          }
        }
      ],
      "children": []
    }
  ]
}

Scene::FromJSON(j, validate) builds a new scene from this data:

  • With validate = true, it first requires "name" and an array "rootGameObjects". If either is missing it logs an error (with the dumped JSON) and returns nullptr.
  • Without validation, a missing "name" leaves the name empty and a missing "rootGameObjects" gives an empty scene.
  • Any std::exception thrown while deserializing is caught, logged as "Failed to load scene: ...", and turned into a nullptr return.

GameObject JSON

KeyWrittenOn load
uuidAlways, as a stringRequired (.at()). Restored as the object's UUID. A string that isn't a valid UUID, or a non-string value, logs an error and becomes UUID::ZERO; it does not throw.
nameAlwaysRequired (.at()), must be a string.
tag PR #39Always ("Untagged" by default)Optional; missing or null keeps "Untagged", so data written before tags existed loads unchanged. Must be a string (anything else fails the load, like other malformed fields). See tags.
layer PR #44Always, as an index (0, Default, unless set)Optional; missing or null means 0, so data written before layers existed loads unchanged. An integer outside 0–31 is clamped into range with a warning. Anything other than an integer (a string, a fraction, a boolean) fails the load, like other malformed fields. See Layer.
isActiveAlwaysOptional. Defaults to active.
prefabReferenceOnly if setOptional UUID. It round-trips, but nothing else uses it yet.
positionableOnly if the object has a PositionableOptional. If present, a Positionable is created and localPosition, localRotation and localScale are each applied if present. See Transforms.
componentsAlways (possibly empty). Each entry is {"type": GetTypeName(), "data": Serialize()}.Optional. Each entry needs type and data (.at()). The component is created through the ComponentRegistry; see below for unknown types.
childrenAlways (possibly empty), recursiveOptional. Each child is deserialized and attached with AddChild(child, false), so local transforms are kept as stored.

Component order is preserved. If the data holds two components of the same type, the first one is the one GetComponent<T> finds. A component's data always starts with the base fields from Component::Serialize: uuid and isActive. Both are optional on load.

Loading creates the objects and components but does not attach them. When the deserialized roots join a scene (SetScene), every component is queued, and OnAttach runs at that scene's next ProcessAttachQueue. See Attach queue.

ComponentRegistry: type name to constructor

ComponentRegistry is a singleton map from a type-name string to a factory std::unique_ptr<Component>(GameObject&). The name a component writes (GetTypeName()) must match the name it is registered under, or it cannot be loaded.

  • Engine components are registered by RegisterBuiltinComponents (engine/src/serialization/BuiltinComponents.cpp), which the registry's constructor calls PR #34. Anything that creates components by name therefore links that file and every built-in type with it, whatever headers the program includes.
  • Game components use REGISTER_COMPONENT(ClassName), which registers #ClassName (the unqualified token) with a factory that calls std::make_unique<ClassName>(go), through a static ComponentRegistrar. test_project's Spin does this.
  • Register(name, factory) overwrites any earlier factory with the same name.
  • Create(name, go) returns nullptr for an unknown name.

Built-in types PR #34: Rigidbody, BoxCollider, SphereCollider, CapsuleCollider, Light, AudioSource, AudioListener, CubeRenderer, SphereRenderer, QuadRenderer, TextRenderer PR #49 and LuaComponent. (LuaComponent.cpp also keeps its own static registrar for the same name; registering twice just overwrites the factory.) Their already-declared fields now round-trip:

  • Rigidbody: body type, mass and gravity flag. See Physics.
  • AudioSource: its clip (as an asset reference), volume, pitch, loop, spatial, play-on-awake, min/max distance, rolloff and mixer group. See Audio.
  • AudioListener: the component itself (it has no fields beyond the base ones).
  • Renderers: colour and size, plus the sphere's latitude and longitude segment counts.
// MyComponent.cpp
namespace Game
{
    REGISTER_COMPONENT(Health)   // registers "Health"

    std::string Health::GetTypeName() const { return "Health"; } // must match
}

An unknown "type" is skipped with a warning PR #34: GameObject::Deserialize logs "Unknown component type '...' on '...' was not loaded" and the load continues without that component. Before PR #34 it was skipped silently.

Guarantee PR #34

Every engine component survives a scene load with its serialized fields, whether or not the program includes the component's header, and a component type the registry does not know is reported in the log rather than vanishing silently (ComponentRoundTripTest: RigidbodyAndItsSettingsSurviveASceneLoad, AudioSourceAndItsSettingsSurviveASceneLoad, AudioListenerSurvivesASceneLoad, ExampleRenderersAndTheirSettingsSurviveASceneLoad, BuiltinTypesAreRegisteredWithoutIncludingTheirHeaders, UnknownComponentTypeIsReportedNotSkippedSilently).

Note

This matters because SceneManager rebuilds every scene from its stored JSON on every load and every scene switch; the only scene object not rebuilt is the one passed to SceneManager::AddScene(scene, true), for its first load. Before PR #34, Rigidbody, AudioSource, AudioListener and the renderers were not registered, so they were dropped on every load.

Warning: REGISTER_COMPONENT and static libraries

REGISTER_COMPONENT registers from a static initializer. In a static library, the linker drops an object file that nothing references, together with its registrar; this is what happened to AudioClipLoader.cpp before #23, and why the engine's own components moved to BuiltinComponents.cpp. Put a game component's REGISTER_COMPONENT in a file the program references for other reasons, such as the component's own .cpp, or in its header.

SerializableComponent and RegisterMember

Derive from SerializableComponent and register fields in the constructor. Serialize() writes the base fields (uuid, isActive) and then every registered member, in registration order. Deserialize(j, resolver) reads the base fields, then runs each member's deserializer.

  • RegisterMember(name, member) works for any type nlohmann::json can convert both ways. Otherwise compilation fails on a static_assert. On load, a missing key leaves the member at its constructor default. A key whose value has the wrong type throws nlohmann::json::type_error (see failure handling).
  • The serializers capture references to the members. A component is never copied or moved after construction (it is owned through unique_ptr), so the references stay valid for its whole life. Do not register locals or temporaries.
  • Engine components use NAMEOF(_field) for the key, so the JSON key is the C++ member name, for example "_mass", "_halfExtents" or "intensity". Renaming a member therefore changes the file format.
class Health final : public N2Engine::SerializableComponent
{
public:
    explicit Health(N2Engine::GameObject &go) : SerializableComponent(go)
    {
        RegisterMember("maxHp", maxHp);
        RegisterGameObjectRef("respawnPoint", respawnPoint);
        RegisterComponentRef("shield", shield);
        RegisterAssetRef("hurtSound", hurtSound);
    }
    [[nodiscard]] std::string GetTypeName() const override { return "Health"; }

    float maxHp = 100.0f;
    N2Engine::GameObject *respawnPoint = nullptr;
    Shield *shield = nullptr;                                   // Shield : Component
    std::shared_ptr<N2Engine::Audio::AudioClip> hurtSound;
};

GameObject and component references

References are written as the target's UUID string, or JSON null. On load they are not looked up straight away. Each one adds a pending fix-up to the ReferenceResolver, which runs once every object in the scene exists.

RegistrationMember typeResolved with
RegisterGameObjectRef(name, ref)GameObject*&resolver->FindGameObject(uuid)
RegisterGameObjectRefVector(name, refs)std::vector<GameObject*>&Same, per index
RegisterComponentRef<T>(name, ref)T*&, T derived from Componentdynamic_cast<T*>(resolver->FindComponent(uuid))
RegisterComponentRefVector<T>(name, refs)std::vector<T*>&Same, per index

Behaviour on load:

  • A missing key or null sets a single reference to nullptr. RegisterComponentRef also logs an info line when this happens.
  • A vector is cleared, resized to the array length, and filled with nullptr. Each non-null element is then resolved by index, so null elements keep their positions. A missing key or a non-array value leaves the vector empty.
  • A UUID that the resolver does not know resolves to nullptr, silently. This covers a target in another scene or one that wasn't saved. A component of the wrong type also resolves to nullptr.
  • Without a resolver (Deserialize(j) or Deserialize(j, nullptr)), a single non-null reference is not touched: the member keeps its current value, and only null and missing references are written. A vector reference is still cleared and resized, but nothing fills it, so it becomes all nullptr (one per stored element).

History: RegisterGameObjectRef used to take the pointer by value, so loading wrote to a dead stack copy. The component variants took shared_ptr<T>& and could not be instantiated. Both were fixed in #23. Components are owned by unique_ptr, so references to them are raw pointers.

Source: engine/src/serialization/ComponentSerializer.cpp — SerializableComponent::RegisterGameObjectRef, SerializableComponent::RegisterGameObjectRefVector; engine/include/engine/serialization/ComponentSerializer.hpp — RegisterComponentRef, RegisterComponentRefVector; tests: SerializationReferencesTest.ReferencesRoundTripThroughTheResolver, SerializationReferencesTest.NullReferencesStayNull

Warning

A reference is a raw pointer that nothing tracks. If the target is destroyed or its scene is switched out, the member dangles, just like any other raw pointer to a component. Serialization only fixes the pointer at load time.

Asset references (RegisterAssetRef)

RegisterAssetRef<T>(name, std::shared_ptr<T>& ref) (T derived from Base::Asset) writes the asset's UUID, or null. It resolves immediately during Deserialize and does not use the reference resolver:

  1. A missing key or null gives nullptr.
  2. UUID::ZERO (including an unparseable UUID string, which becomes ZERO) gives nullptr and the warning "Invalid UUID for asset ...".
  3. Otherwise it calls IO::Resources::Instance().LoadByUUID<T>(uuid) PR #28. That checks Resources' own runtime assets, then ResourceLoader's cache, then loads the project file whose .meta UUID matches. If none of these finds it, the reference is nullptr and "Asset '...' not found: ..." is logged.

Cross-run stability. A project file under assets/ gets a deterministic UUID from its res:// path (see UUID stability). A reference saved in one run therefore loads the same file in a later run, even if nothing has loaded it yet. This holds whether the asset was first loaded through ResourceLoader or through Resources, because Resources::Load delegates project files to ResourceLoader PR #28. An asset registered at runtime (Resources::RegisterAsset) has a random UUID, so a reference to it resolves only within the same run.

Source: engine/include/engine/serialization/ComponentSerializer.hpp — SerializableComponent::RegisterAssetRef; engine/include/engine/io/Resources.hpp — Resources::LoadByUUID; tests: AudioAssetReferenceTest.AudioSourceClipResolvesInALaterRun, ResourceLoaderTest.AssetRefToAnAssetLoadedThroughResourcesResolvesInALaterRun, ResourcesTest.AssetRefResolvesAnAssetRegisteredAtRuntime

Note

Because asset references load on demand, deserializing a scene can perform file I/O and create backend resources. For example, an AudioClip needs an initialized OpenAL context; without one, the clip fails to load and the reference is null.

ReferenceResolver: create, then resolve

Scene::Deserialize creates one ReferenceResolver per load and runs two phases:

  1. Create: every root is deserialized recursively. Each GameObject is registered under its UUID as soon as it is created, before its components and children. Each component is registered under data["uuid"] (if present) before its own Deserialize runs. Reference members queue fix-up closures. Each root is appended to the scene and joins it with SetScene.
  2. Resolve: ResolveAll() runs every queued closure in the order queued, then clears the queue. Every UUID in the scene is known by then, so forward references (to objects later in the file, or to a parent's sibling) resolve.
  • Registration is last-wins per UUID. Two objects with the same UUID (for example several invalid UUIDs, all mapped to ZERO) make references to that UUID resolve to whichever was registered last.
  • The closures capture the resolver's address. The resolver must outlive ResolveAll(), which is why it is a local in Scene::Deserialize. If you drive a resolver yourself (as the tests do), keep it alive until you call ResolveAll().
  • Scope is a single load: references never resolve across scenes.
  • LuaComponent queues its script-field references through the same resolver; see Lua scripting.
// Manual two-phase load of a single component (what Scene::Deserialize does for a whole scene)
N2Engine::ReferenceResolver resolver;
resolver.RegisterGameObject(target->GetUUID(), target.get());
holder->Deserialize(savedJson, &resolver);   // queues fix-ups
resolver.ResolveAll();                        // fills holder's reference members

Guarantee

Malformed scene JSON (missing required keys, wrong value types) never aborts the process through Scene::FromJSON. It returns nullptr and logs the reason.

Note

A load that fails partway has already run constructors and Deserialize for the components created before the error, including Lua script chunks. The half-built scene is then destroyed without OnDestroy; see the open question on dropped scenes.

Prefabs

Prefab wraps a name and a root GameObject. Its JSON is {"name": ..., "rootObject": <GameObject JSON> | null}.

  • Prefab::Serialize() writes rootObject: null when the prefab has no root.
  • Prefab::Deserialize(j, resolver = nullptr) returns std::expected<std::unique_ptr<Prefab>, PrefabParseError>. A missing name gives MissingName, and a missing or null rootObject gives MissingRootObject. UUIDs of the whole hierarchy are preserved. PrefabParseErrorToString has a message for every error.
  • Prefab::Deserialize never throws PR #39: a root whose GameObject data is malformed (missing uuid or name, wrong types) gives InvalidRootObject (the cause is logged), and a name that is not a string gives the new InvalidName. Data that is not an object at all gives MissingName. With a caller's resolver, the caller runs ResolveAll; after an InvalidRootObject that resolver may hold entries for the partly built (already freed) objects, so discard it.

Instantiating and registering prefabs PR #39

PrefabManager::InstantiatePrefab(json) builds a new, independent object tree from prefab data:

  1. It accepts Prefab JSON ({"name", "rootObject"}, what Prefab::Serialize writes) or the bare GameObject JSON of the root (the rootObject value), which is what it used to require. An object with a rootObject key is treated as Prefab JSON.
  2. Renumber the data first. Every GameObject and component id in the prefab's JSON ("uuid" of each object and of each component's data) is mapped to a new random UUID. Then every string anywhere in that JSON that is one of those ids (compared as UUIDs, so case does not matter) is replaced by its new id: the ids themselves, RegisterGameObjectRef/RegisterComponentRef members and their vectors, and Lua {"$ref": ...} fields in a LuaComponent's scriptData. A Lua $ref to anything that is not an id of the prefab is set to null. Other UUID strings (assets, script UUIDs) are left alone.
  3. The renumbered root is deserialized with a fresh ReferenceResolver and ResolveAll runs. References inside the prefab therefore point at the objects of this instance, both as pointers and in the saved form (serializing the instance writes the new UUIDs, so a save and reload keeps the links). Pointer references to anything outside the prefab are not found and come back nullptr, and external Lua $refs are already null, so nothing re-links to the prefab's source objects after a reload.
  4. An object or component the data gave no valid id gets a random one instead of UUID::ZERO.
  5. The instance is in no scene. Add it with AddRootGameObject or AddChild; its components attach at that scene's next ProcessAttachQueue.
  6. Malformed data (a null rootObject, missing keys, wrong types) logs an error and returns nullptr; no exception escapes.

A registry keeps prefabs by name: RegisterPrefab(name, root) stores a snapshot of root (its Prefab JSON, as serialized at that moment; later edits to root do not change the prefab). Registering a name again replaces it with a warning; an empty name or a null root is refused (false, logged). HasPrefab(name), UnregisterPrefab(name) and InstantiateRegisteredPrefab(name) (which is InstantiatePrefab on the stored data, or nullptr with an error for an unknown name) complete it. The registry lives in memory only; nothing is written to disk.

#include "engine/prefabs/PrefabManager.hpp"

PrefabManager::RegisterPrefab("Turret", turretTemplate);           // snapshot
auto first = PrefabManager::InstantiateRegisteredPrefab("Turret");  // fresh UUIDs
auto second = PrefabManager::InstantiateRegisteredPrefab("Turret"); // different fresh UUIDs
scene.AddRootGameObjects({first, second});

Guarantee PR #39

Two instances of one prefab never share a UUID with each other or with the prefab, and each instance's internal references point at its own objects. Malformed prefab data is an error value (Prefab::Deserialize) or nullptr (InstantiatePrefab), never an exception. Before, instantiating kept the stored UUIDs (so two instances had the same ones), resolved no references, required bare GameObject JSON, and RegisterPrefab was an empty stub.

Tests: PrefabInstantiateTest.EveryObjectAndComponentGetsAFreshUUID, PrefabInstantiateTest.InternalReferencesPointIntoTheNewInstance, PrefabInstantiateTest.TwoInstancesReferenceTheirOwnObjects, PrefabInstantiateTest.ReferencesOutsideThePrefabAreNull, PrefabInstantiateTest.MalformedDataReturnsNullWithoutThrowing, PrefabRegistryTest.*, PrefabDeserializeErrorTest.*, LuaPrefabRefTest.RefFieldPointsAtTheInstancesOwnChild, LuaPrefabRefTest.TwoInstancesGetDifferentRefs, LuaPrefabRefTest.RefOutsideThePrefabBecomesNull.

Design decision: a prefab instance is a new object tree

A UUID identifies one object: it keys reference resolution, the editor's entity ids and FindGameObjectByUUID. An instance that kept the prefab's UUIDs would collide with every other instance in the same scene. References are stored as UUID strings, some of them (Lua $ref fields) never become pointers, so the instance is renumbered in its data, before it is built: then the live objects, their pointer references and their saved form all agree. References leaving the prefab cannot be kept: the prefab is a template that may be instantiated into any scene, and the objects it pointed at need not exist there. Prefab links (prefabReference, overrides, nested prefabs) are not implemented; prefabReference still only round-trips.

Input, layers and Lua data

  • Input bindings: InputSystem has its own JSON format for action maps and bindings, including how unknown binding names are rejected. See Input.
  • Lua components: a LuaComponent's data holds the base fields plus scriptUUID (the script's .meta UUID, preferred), or scriptPath if the script has no metadata, and scriptData (the script's serializable field values). On load, a scriptUUID that ResourceLoader doesn't know logs a warning and marks the script as missing; one that isn't a valid UUID string is ignored silently (no script, not marked missing). Field types, references from Lua fields, and validation are covered in Lua scripting.
  • Layers PR #44: Layers::Serialize() writes the layer names and collision matrix as {"layers": [32 names], "collisionMatrix": [32 row masks]} ("" for an unnamed layer; row i has bit j set if layers i and j collide). Layers::Deserialize validates the whole block first and never throws: anything malformed (not an object, layers not an array of at most 32 strings, a name used twice, collisionMatrix not exactly 32 integers in 0–0xFFFFFFFF) logs a warning, returns false and changes nothing. A missing key takes the defaults; built-in layer names are kept whatever the block says; an asymmetric matrix is made symmetric, with a warning, by keeping a pair colliding only if both rows say so. Nothing saves the block yet; the project file (#6) will. See Layers and the collision matrix.
  • Assets: Base::Asset::Serialize writes uuid and resourcePath. Asset files and .meta metadata are covered in Resources & paths.
