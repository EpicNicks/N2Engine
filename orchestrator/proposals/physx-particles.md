# Proposal: PhysX GPU particles (PBD) first, soft bodies later

Status: research only, N2Engine master a5e483c. Marks: [V] verified in the repo or in the PhysX source (clone of NVIDIA-Omniverse/PhysX tag `107.3-omni-and-physx-5.6.1`, paths below are relative to its `physx/`), [M] from memory / unverified until a GPU run.
Header paths: engine copy `external/PhysX/physx/include/` is the same 5.6.1 set [V: PxParticleSystem.h, PxPBDParticleSystem.h, PxParticleBuffer.h, gpu/PxGpu.h, cudamanager/*, extensions/PxParticleExt.h, extensions/PxCudaHelpersExt.h all present].

## 1. What PhysX 5.6.1 needs for PBD particles
1. **CUDA context**: `PxCreateCudaContextManager(foundation, PxCudaContextManagerDesc, profiler)` (`include/gpu/PxGpu.h:~95`) then check `contextIsValid()`, else release it. Pattern in `snippets/snippetpbf/SnippetPBF.cpp:230-238` [V]. Desc fields `ctx, graphicsDevice, deviceOrdinal(-1), appGUID` (`cudamanager/PxCudaContextManager.h:113-157`) [V]. `PxGetSuggestedCudaDeviceOrdinal(errorCb)` returns -1 with no usable GPU [V]. Env var `PHYSX_GPU_DEVICE` picks the ordinal (README_LINUX) [V].
2. **GPU library loading**: `PxCreateCudaContextManager` and friends call `PxLoadPhysxGPUModule` (`source/physx/src/gpu/PxGpu.cpp:69-124`) [V]. Windows: `LoadLibrary` of `PhysXGpu_64.dll` via `CmModuleUpdateLoader` (normal DLL search: exe dir), name from define `PX_PHYSX_GPU_SHARED_LIB_NAME` (`source/compiler/cmake/windows/PhysX.cmake:122`) [V]; `PxSetPhysXGpuLoadHook` can override the file name (`PxGpu.h:41-70`) [V]. Linux: first `dlopen("libcuda.so.1")`, then `dlopen("libPhysXGpu_64.so")` (`PxPhysXGpuModuleLoader.cpp:~205-215`, name `PhysX.cmake:96` in cmake/linux) [V]; found through rpath/LD_LIBRARY_PATH/ld.so cache, so the Linux host needs `$ORIGIN` rpath or a service env var. Failures only call `reportError` (no crash, no exception) [V] so a missing DLL/driver surfaces as "context invalid / NULL manager".
   Engine today: `CMakeLists.txt:72-76` appends `PhysXGpu_64` to PHYSX_LIBS and the DLL to the copy list if the file exists [V]. bin.zip has a 4.6 KB `PhysXGpu_64.lib` (release+debug) next to the 345 MB / 511 MB dlls [V, zip central directory read]; the import lib is tiny and unreferenced so the exe does not hard-depend on the DLL [M, confirm with `dumpbin /dependents` on the user's PC].
3. **Scene**: `sceneDesc.cudaContextManager = cm; flags |= PxSceneFlag::eENABLE_GPU_DYNAMICS; broadPhaseType = PxBroadPhaseType::eGPU` (`SnippetPBF.cpp:89-93`) [V]. The flag is immutable after creation (`include/PxSceneDesc.h:233-239`) [V]. If the manager is NULL, `Sc::Scene` only logs "GPU solver pipeline failed, switching to software" and runs CPU (`source/simulationcontroller/src/ScScene.cpp:777-791`; also requires `supportsArchSM30()`) [V]. Consequence: the WHOLE rigid scene moves to the GPU pipeline when the flag is on: reduced-coordinate articulations only (`NpScene.cpp:984`), aggregates need `maxNbShapes` (`NpScene.cpp:1919`), more VRAM (`PxGpuDynamicsMemoryConfig`, `PxSceneDesc.h:~460-471`), different perf/contact behaviour [V]. Engine scene creation: `PhysXBackend.cpp:202-216` sets only PCM + stabilization and no cuda manager [V].
4. **API**: `PxPhysics::createPBDMaterial(friction, damping, adhesion, viscosity, vorticityConfinement, surfaceTension, cohesion, lift, drag, cfl, gravityScale)` (`PxPhysics.h:980`), `createPBDParticleSystem(cudaCM, maxNeighborhood=96, neighborhoodScale)` (`:754`), `ps->createPhase(mat, PxParticlePhaseFlags(eParticlePhaseFluid|eParticlePhaseSelfCollide))`, buffers via `ExtGpu::PxCreateAndPopulateParticleBuffer / ...AndDiffuseBuffer` (`extensions/PxParticleExt.h:365-374`, pinned host staging with `PX_EXT_PINNED_MEMORY_ALLOC`, `SnippetPBF.cpp:155-204`), `ps->addParticleBuffer(buf)`, then `scene->addActor(*ps)` [V]. Buffer fields: `getPositionInvMasses()` (PxVec4), `getVelocities()`, `getPhases()`, `setNbActiveParticles`, `raiseFlags(eUPDATE_POSITION|eUPDATE_VELOCITY|eUPDATE_PHASE)` (`PxParticleSystemFlag.h:51-61`) [V]. There is NO emitter: spawning = write new entries into the pinned/device arrays, bump `setNbActiveParticles`, raise update flags [V by API absence]. Deprecated: cloth/rigid/volume buffers, rigid attachments.
5. **Read-back for rendering**: the buffer pointers are DEVICE pointers. The shipped snippets copy with `cudaContext->memcpyDtoH(hostVbo, CUdeviceptr(positions), n*sizeof(PxVec4))` (`snippetpbf/SnippetPBFRender.cpp:84-85`) under a `PxScopedCudaLock` [V]; only the GL snippet renderer shows CUDA-GL interop (`snippetrender/SnippetRender.cpp:1304-1355`, `cuGraphicsGLRegisterBuffer`) [V]. Recommendation: host copy (16 B/particle: 100k particles = 1.6 MB/frame) after `fetchResults`, because it works for OpenGL, software, and any future Vulkan renderer with no CUDA-graphics link and no extra driver libs. Interop is a later optimisation, OpenGL only.
6. **CPU fallback: none.** `NpScene::addParticleSystem` returns an error unless `isUsingGpuDynamicsAndBp()` ("Particle systems only currently supported with GPU-accelerated scenes!", `source/physx/src/NpScene.cpp:1623-1626`); the snippet says the same ("only supported on GPU", `SnippetPBF.cpp:237`); `NpPhysics::createPBDParticleSystem` returns NULL when `PX_SUPPORT_GPU_PHYSX` is 0 (`NpPhysics.cpp:585-595`) [V]. The CPU-only static libs we just published for Linux (`PX_SUPPORT_GPU_PHYSX`, `PX_GENERATE_GPU_PROJECTS` off) therefore cannot run particles at all [V logic, [M] that the cpu-only preset defines the macro to 0].
7. Requirements: NVIDIA GPU compute capability 7.0+ (Volta+), driver compatible with CUDA 12.8 (README_LINUX/README_WINDOWS "PhysX GPU Acceleration") [V]; the CHANGELOG says CUDA 11.8 -> 12.8 in this line and Pascal (6.0) dropped [V]. Exact min driver numbers ~570.x [M, check NVIDIA table]. AMD/Intel/Mac: no particles.

## 2. Building the GPU part
- Source IS in the tag: `source/gpu*/`, `source/cudamanager`, `source/physxgpu` and 61 `.cu` files [V]. The GPU projects live in `source/compiler/cmakegpu/{linux,windows}`; presets `linux-clang` and `linux-gcc` (and `-aarch64-*`) have `PX_GENERATE_GPU_PROJECTS=True`, the `*-cpu-only` ones do not (`buildtools/presets/public/linux-clang.xml`) [V]. So the Linux GPU `.so` is buildable from source, not binary-only. Output: shared `libPhysXGpu_64.so` (`PX_GENERATE_GPU_STATIC_LIBRARIES=False` in every preset; static variant exists but the engine side loads by name) [V].
- Toolchain: NVIDIA CUDA Toolkit 12.8 (README_LINUX:16), not on packman (`dependencies.xml` has no CUDA entry; the toolkit must be installed on the host, `CUDACXX` selects nvcc) [V]. `compiler/public/CMakeLists.txt:47-60` does `ENABLE_LANGUAGE(CUDA)` + `find_package(CUDAToolkit)`, default `CMAKE_CUDA_ARCHITECTURES 75` overridden by `cmakegpu/CMakeLists.txt:87-91`: full SASS `70,80,86,89,90,100,120` + PTX 120, or with `PX_GENERATE_GPU_REDUCED_ARCHITECTURES=True` SASS `80,86,89,90,100,120` + PTX 120 [V]. sm_120 (Blackwell) needs toolkit >= 12.8 [M]. Windows PhysXGpu_64.dll is 345 MB release / 511 MB debug for that reason [V]; expect a ~300 MB `.so` [M].
- x86_64 only for desktop: the aarch64 GPU presets exist but target NVIDIA Jetson/Grace-style hosts; there is no aarch64 desktop GPU box in scope [M]. CPU-only aarch64 stays as published.
- Build time [M]: 60-120+ min on a 4-core GitHub runner for full arch list (the .cu files x 7 archs); reduced arch list roughly halves it. Memory is fine.
- GitHub-hosted runners: no GPU, but CUDA toolkit installs for compile-only (apt `cuda-toolkit-12-8` from NVIDIA's repo, or `Jimver/cuda-toolkit` action; ~3-4 GB download; `nvcc` needs no driver) [M]. They can compile, link, and `ldd`/`nm`-check the `.so`, but cannot execute a CUDA context. Smoke test with a GPU must be the user's PC. A GPU `.so` plus its CPU static libs must come from the same build so the PxGpu ABI matches.
- Linux asset plan: extend `.github/workflows/physx-linux.yml` with a `gpu` job (matrix x86_64 only), upload `physx-linux-gpu-x86_64-5.6.1.tar.gz` containing `libPhysXGpu_64.so` (release), published to the same release `physx-dependencies-linux-5.6.1` or a sibling; never overwrite existing assets (rule already in the workflow). Runtime: host needs the NVIDIA driver (`libcuda.so.1`), nothing else; Docker needs `--gpus all` + nvidia-container-toolkit. Licence: BSD-3, ship PhysX LICENSE with it; the CUDA runtime is statically linked into the NVIDIA-built DLL on Windows [M, check `ldd` for libcudart on Linux].
- Windows needs nothing new: the DLLs are in bin.zip already [V]. SIDE NOTE: bin.zip is 1.4 GB compressed / 3.7 GB unpacked; PDBs (1.48 GB) + snippet exes (251 MB) + `.map` are not needed and can be dropped WITHOUT touching PhysXGpu_64.dll/.lib or the `*Gpu_static_64.lib` (those are 1+ GB themselves and the engine links none of the `*Gpu_static` libs, so they could also go, but keep them if soft bodies / static GPU link are wanted) [V sizes from zip listing].

## 3. Engine-side design
**Seam [V]**: `IPhysicsBackend` (`engine/include/engine/physics/IPhysicsBackend.hpp`) is rigid-body only (bodies, colliders, queries) and the single implementation is `PhysXBackend`; `Application.cpp:155-188` creates it and records `SubsystemStatus "Physics"`. Recommended seam: a new small interface `IParticleBackend` (engine/include/engine/physics/IParticleBackend.hpp) obtained from `IPhysicsBackend::GetParticleBackend()` (returns nullptr by default, PhysXBackend returns its GPU implementation when the scene is GPU). Calls: `CreateSystem(desc) -> handle`, `Spawn(handle, positions, velocities)`, `SetParams`, `Destroy`, and `CopyPositions(handle, std::vector<Vec4>&)` (host copy after fetchResults). Keeps PhysX/CUDA types out of components, same as bodies.
**Capability probe** (Application::Init, near `Application.cpp:155-188`): in `PhysXBackend::Initialize` (l.166-216) try, in order, `PxGetSuggestedCudaDeviceOrdinal`, `PxCreateCudaContextManager`, `contextIsValid()`; if OK set `eENABLE_GPU_DYNAMICS` + `eGPU` broadphase and `sceneDesc.cudaContextManager`; if anything fails, build today's CPU scene unchanged. Expose `GpuStatus {Unavailable|Ready|Failed, detail}`. Project setting `physics.gpu` = `off|auto|on` in ProjectSettings (`engine/src/ProjectSettings.cpp:160` already parses `physics`). Default `off`/auto-only-if-project-has-particles is a DECISION (section 5): GPU scene changes rigid-body behaviour for every project.
**Component** `ParticleSystem` (single component, emission params inside; split into emitter later if needed): `class ParticleSystem final : public SerializableComponent, IRenderable` modelled on `Light` (`engine/include/engine/rendering/Light.hpp`, `Light.cpp` `RegisterMember(NAMEOF(x), x)`, `.AsColor()`; `N2_SERIALIZE_ENUM`) and `TextRenderer` (`engine/include/engine/rendering/TextRenderer.hpp:42-64`: IRenderable, `GetRenderQueue`, `RenderInQueue`, Init/CleanupRenderResources) [V]. Registration: add `Add<Rendering::ParticleSystem>(registry, "ParticleSystem")` in `engine/src/serialization/BuiltinComponents.cpp:50-66` [V]. Fields: maxParticles, emissionRate, burst, lifetime, startSpeed, startSize, color (+end color), gravityScale, material preset (water/sand/smoke -> PBD material params: viscosity, cohesion, friction, damping, drag), simulate-in-world flag, playOnAwake, collideWithRigidbodies (layer mask later), `Play()/Stop()/Clear()`.
**Rendering**: renderers are `IRenderer` (`renderer/include/renderer/common/Renderer.hpp`) with OpenGL (1466 lines), Software (1604), Vulkan (stubs: `VulkanRenderer.cpp:815-847` CreateShader/CreateMaterial return nullptr) [V]. Minimal v1: reuse the existing path with NO new renderer API: one billboard-quad mesh, `IRenderer::UpdateMesh` (`Renderer.hpp:167`) rebuilding a camera-facing quad mesh per frame on the CPU from the host positions (`TextRenderer` already does exactly this with `UpdateMesh`) in the Transparent queue [V pattern]. Works on OpenGL and software today with zero renderer changes; Vulkan unsupported (as it is for text/meshes). 100k quads rebuilt on CPU per frame is the cost ceiling; v2 = `IRenderer::DrawInstanced`-style point sprite/instanced path in OpenGL + software [M].
**Health / headless [V]**: `EngineHealth` (`engine/include/engine/Health.hpp`) holds generic `SubsystemStatus{name,state,detail}` with `Disabled` meaning deliberately off and not counting as unhealthy. Add a `"Particles"` entry beside Physics at `Application.cpp:217` (`Running` with detail "PhysX GPU: <device>", `Disabled` with detail "No CUDA GPU / driver / PhysXGpu library", `Failed` only for a context that worked then died). A host without a GPU must log once, never throw: all PhysX GPU calls sit behind the probe and `ParticleSystem::OnAttach` just goes inert and logs a warning (as Rigidbody does when there is no backend). A project that depends on particles on a non-GPU host shows Disabled and invisible particles, not an error.
**Editor protocol [V]**: `SubsystemStatus` is `{name,state,detail}` strings (`editor-server/protocol/protocol.json:845-849`), so the Particles health row needs NO schema change and `GetEngineHealth` (`:552`) just returns one more row. Inspector fields come from `GetComponentTypes` (`:564`) via RegisterMember, so the component needs NO protocol change either. Optional: advertise `"particles-gpu"` in `ServerInfo.capabilities` (`:70-76`, `json:string[]`): data-only, but any addition should bump the minor (now 1.10.0) per the protocol rules; if bumped, regenerate `editor-server/clients/{cpp,csharp,web}` with `editor-server/protocol/generators/*` and update `test-vectors.json`. Editor (Electron client repo) only needs to show the row (already generic) plus an optional "GPU particles unavailable" hint on the component.
**Lua**: bindings via `MakeAccess<T>()` table in `engine/src/scripting/bindings/LuaComponentBindings.cpp:~109` (`TextRenderer`, `Light` entries) [V]; add `ParticleSystem` with fields + `Play/Stop/Clear/EmitBurst(n)`; plus `Physics.IsGpuAvailable()` in `LuaPhysicsBindings.cpp:191` (`Physics` table). Docs: `docs/physics.html`.
**Play mode**: physics runs from `Application::PhysicsUpdate` (`Application.cpp:420-436`) in the fixed-step loop; particles step with the scene `simulate`, then `ParticleSystem::Update` (frame) copies positions. Edit mode: scene is not stepped, so show a static preview only (nothing) or a cheap CPU "preview burst" (decision). Enter/exit play uses scene snapshots (`EditorServer::EnterPlayMode`, `EditorServer.hpp:442`): particle state is never serialized; exit destroys PhysX particle systems and resets. Pause (timeScale 0) already skips fixed steps (`Application.cpp:~285`) so particles freeze with it [V].
**Recommendation**: GPU-only PhysX v1 exactly as above (IParticleBackend seam, host copy, CPU-rebuilt billboards, Particles health row, no protocol change), with `physics.gpu=off` default and `auto` opt-in.

## 4. Option B: renderer-side compute particles (not PhysX)
| | PhysX PBD (chosen) | Renderer compute shaders |
|---|---|---|
| Hardware | NVIDIA CUDA GPU only; driver >= CUDA 12.8 class | any OpenGL 4.3+ / Vulkan GPU |
| Physics interaction | fluids, collision with rigid bodies/colliders in the same scene, rigid bodies pushed by fluid is limited | needs hand-written collision (planes, spheres, depth buffer); no two-way coupling |
| Fluid quality | real PBD fluid, viscosity, cohesion, diffuse foam/spray | simple ballistic/sprite effects (fire, smoke, sparks), fluids are a large extra project |
| Cost to build | moderate engine code (this plan); big binary dependency | new GPU compute path in each renderer (OpenGL compute now; Vulkan renderer is still stubs; software renderer would need CPU sim) |
| CI | compile only; run needs GPU PC | GL compute runs on Mesa llvmpipe in CI ok [M] |
| Headless editor host | Disabled (no GPU) | Disabled or CPU sim |
| Risk | binary size/asset churn, whole-scene GPU dynamics side effects | none NVIDIA-specific, but no rigid-body physics integration |
Honest take: Option B is what most games call "particles" (VFX); PhysX PBD is a physics feature (fluids/granular interacting with rigid bodies). If the user's goal is effects, B covers more users sooner; if it is fluids/sand that collide with the physics world, only PhysX does. A CPU/software particle path (billboards from a CPU simulation) would give the headless host and non-NVIDIA users something, and could share the same component and renderer path as v1 above.

## 5. Staged plan (PR-sized) and verification
1. **PR-A (CI-verifiable)** GPU capability probe + health: `PhysXBackend` probe (PxGetSuggestedCudaDeviceOrdinal, manager create guarded), `GpuStatus`, `Particles` health row (always Disabled in CI), `physics.gpu` setting, tests in `tests/engine/HealthTests.cpp` for the Disabled row on CPU-only builds. Windows CI links nothing new.
2. **PR-B (CI-verifiable)** `IParticleBackend` interface + null/CPU-less implementation, `ParticleSystem` component (serialize, inspector, Lua, registration, tests for round-trip and "inert without GPU"). No PhysX GPU calls yet.
3. **PR-C (needs GPU PC)** PhysX PBD implementation: GPU scene creation when probe OK, PBD material/system/buffer, spawn, read-back; billboard rendering via `UpdateMesh`; golden test only when `PxGetSuggestedCudaDeviceOrdinal() >= 0` (skipped in CI). Manual check on the Windows GPU PC; the committed Windows DLLs are enough.
4. **PR-D** Linux GPU asset: `physx-linux.yml` `gpu` job (CUDA 12.8, reduced archs, compile-only on a hosted runner), publish `libPhysXGpu_64.so`, CMake download + rpath, docs. Verified for link/ldd on CI, execution only on a Linux GPU host the user must provide (or skip Linux GPU until requested).
5. **PR-E (optional)** protocol capability string + minor bump + client regeneration; editor hint; instanced/point-sprite rendering; interop.
6. Later: soft bodies reuse the same GPU scene, probe, `PxCudaContextManager` and asset (`PxDeformableVolume`, `include/PxDeformableVolume.h`; needs tet meshes via cooking `PhysXCooking` which the engine already links) [V headers present].
**Unknowns**: (a) the exact bin.zip build recipe (was `PX_GENERATE_GPU_PROJECTS` on, which archs) [V that it has the GPU dll, not how]; (b) real behaviour change of rigid bodies under GPU dynamics (PCM/stabilization flags, aggregates, CCD) [M]; (c) VRAM use of default `PxGpuDynamicsMemoryConfig` on the user's card; (d) whether the exe has a hard import of PhysXGpu_64.dll (check dumpbin); (e) CUDA install size/time on hosted runners; (f) whether PhysX Linux CPU static libs and a separately built `.so` stay ABI-compatible (same tag, same build) [M].
**Decisions for the user**: 1) default `physics.gpu` off vs auto; 2) one component or separate Emitter; 3) v1 renders billboards on CPU path (simple) vs wait for instancing; 4) ship the Linux GPU asset now or Windows-only first; 5) any CPU fallback particle sim for headless/non-NVIDIA (recommend separate, later).

## Decisions (user, 2026-10-13)
- PhysX GPU particles first, soft bodies later; BOTH a PhysX PBD backend and a CPU simulation backend, selectable ("both as configurable"): the ParticleSystem component has `backend: Auto | PhysX | CPU` (Auto = PhysX when the GPU probe is Ready and the project enables GPU physics, else CPU), and the project setting `physics.gpu` = `off | auto | on` defaults to `off` (Unity runs rigid bodies on the CPU only and keeps effect particles separate from the physics GPU path). A project with `physics.gpu=off` therefore always uses the CPU backend, so it behaves the same on every machine and on the headless host.
- One ParticleSystem component (not a separate emitter). v1 renders CPU-built billboards through UpdateMesh (instancing and CUDA-GL interop later, optional). Windows first; the Linux GPU asset later (PR D waits). No protocol change for v1 (backend is an ordinary component field; a Particles health row uses the generic SubsystemStatus).
- Plan changes: PR-A probe/health/`physics.gpu`; PR-B IParticleBackend + ParticleSystem component + CPU backend + billboard rendering + Lua (fully CI-verifiable, runs headless); PR-C PhysX PBD backend (needs the user's Windows GPU PC); PR-D Linux GPU asset (deferred); PR-E optional. Soft bodies later reuse the GPU scene, probe and asset.
- Sequencing: wait for physx-linux-enable to merge (it edits CMake and PhysXBackend) before PR-A.
