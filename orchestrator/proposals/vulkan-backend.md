## 2. The contract a Vulkan backend must meet (from OpenGL and Software)
- **Immediate-mode, ordered draws** [V `Renderer.hpp:34-52,93-140`]: draws reach the target in submission order with a per-draw `RenderState` (depthTest, depthWrite, cull None/Back/Front, blend, additive; `RenderState.hpp`). `SetViewProjection` may change mid-frame (the UI pass after the scene, `Application.cpp:408-417`). Matrices are row-major, OpenGL clip conventions (GL uploads with transpose, `OpenGLRenderer.cpp:626-636`). So Vulkan records one command buffer per frame; per-draw data (model, view, proj) goes into a per-frame dynamic-offset UBO ring (192 B per draw exceeds the 128 B guaranteed push-constant size [M spec minimum]); pipelines are cached by (shader, RenderState, wireframe): at most 3 shaders x 2 x 2 x 3 x 3 = 108 variants, created lazily.
- **Clip space** [M]: GL depth -1..1 and y-up. Convert in the vertex shader (`z = (z + w) / 2`) plus a negative-height viewport (core 1.1) to keep y-up and CCW-front winding; the cull and upright-texture goldens (section 4) check this.
- **Meshes** [V `RenderTypes.hpp:15-30`]: 64-byte `Vertex` (pos, normal, uv, colour, tangent), uint32 indices, `IndexRange` submesh draws (out-of-range draws nothing, as GL `OpenGLRenderer.cpp:578-592`). `UpdateMesh` keeps the IMesh* and is called every frame by text (`TextDrawing.cpp:333`), particles (`ParticleSystem.cpp:509`) and GpuCache (`GpuCache.cpp:299`). With 2 frames in flight a buffer the GPU may still read must not be overwritten: allocate a new buffer per update and retire the old one to a per-frame deletion queue (also needed for Destroy* calls).
- **Textures** [V `TextureOptions.hpp`]: 1-4 channels (R8, RG8, RGB8, RGBA8), Nearest/Linear, Repeat/Clamp, mipmaps, srgb. A 1-channel texture samples (r,0,0,1) (docs/application.html:316). RGB8 is often not a sampled format on desktop GPUs [M]: expand to RGBA8 (alpha 1) at upload. Mipmaps by `vkCmdBlitImage`, only if the format has linear-blit support, else no mips.
- **Shaders/materials** [V]: three built-ins (unlit, lit, SDF text; GLSL 330 in `OpenGLRenderer.cpp:835-1358`). Materials set uniforms by name; the full set the engine uses is fixed: uAlbedo, uHasTexture, uAlphaCutoff, uMetallic, uSmoothness, uEmissive, uPbr, uHas{Emissive,Occlusion,Normal,MetallicRoughness}Texture, uOcclusionStrength, uNormalScale, uOutline, uOutlineColor, uSoftness, uShadowColor, uShadowOffset, uShadowSoftness; scene-level uCameraPos, uAmbientLight, uNum*Lights + arrays (2 dir / 8 point / 4 spot, `SceneLighting.hpp:86-88`), uEncodeOutput (grep of Set*("u...") in engine/src and renderer/src). So a fixed std140 block per shader with a name-to-offset table works without SPIR-V reflection. Five samplers (base + 4 AuxTexture, `IMaterial.hpp`), bound to 1x1 defaults when absent. **Custom GLSL** enters only through `Resources::LoadShader` -> `CreateShaderProgram` (`engine/src/io/Resources.cpp:92-125`), and nothing in the repo calls `LoadShader` [V grep]; the software renderer already ignores custom sources (returns an unlit shader, `SoftwareRenderer.cpp:1121-1127`). So v1 can ship built-ins only.
- **Colour space** [V `OpenGLRenderer.cpp:415-436,670-689,1390-1420`]: GL renders into an SRGB8_ALPHA8 target and enables FRAMEBUFFER_SRGB only for the lit shader in linear lighting, otherwise encodes in-shader (`uEncodeOutput`, `forceShaderEncode`). Proposed Vulkan: UNORM targets everywhere, lit shader always encodes in-shader when linear. Same bytes as GL for unlit/text/blended UI [M, checked by goldens].
- **Render target and readback** [V `Renderer.hpp:189-224`]: `ReadFramebuffer` returns RGBA8 bottom row first; `SetRenderTargetSize` renders later frames offscreen at a fixed size (editor viewport). Proposed design: Vulkan ALWAYS renders into its own offscreen colour+depth image; with a window, Present blits it to the swapchain image. Then CI exercises exactly the code a window uses, except the final blit/present. Readback copies to a host-visible buffer, waits on the frame fence, flips rows.
- **Headless**: Software is created with `Initialize(nullptr, w, h)` in every golden test [V `SoftwareMeshGoldenTests.cpp` Render()]. Vulkan should accept a null window the same way (no surface, no swapchain extensions, pick any device with a graphics queue). No engine change needed for tests (they construct renderers directly); `Window::UsesNoWindow` stays SOFTWARE-only unless decided (section 7).
- **Text and passes** [V `Renderer.hpp:174-187`, docs/text.html:351]: GL text is antialiased (fwidth) and blended, with outline/shadow composited under the face; the Vulkan text shader is a port of GL's, so Vulkan should match OpenGL, not Software (which alpha-tests). Particles draw CPU billboards through UpdateMesh in the Transparent queue, additive optional (`RenderState::additive`); Software ignores blending (`RenderState.hpp` comments).

## 3. Minimal viable scope ("draws a lit textured mesh and text like the OpenGL path")
In: headless + windowed init, offscreen target, readback, SetRenderTargetSize, meshes (+UpdateMesh, IndexRange), textures with all TextureOptions, the 3 built-in shaders, materials incl. aux textures and PBR flags, scene lighting, all RenderState combinations, wireframe if `fillModeNonSolid` exists, swapchain present + resize/minimise, validation clean, Shutdown destroys everything (validation reports leaks at device destroy).
Out of v1: custom user GLSL (CreateShaderProgram returns nullptr + one warning, as text does today), MSAA, multiple cameras/targets, compute/instancing, shadows, macOS (MoltenVK), Wayland, editor-host `--renderer vulkan` (decision 6), making Vulkan a default (decision 5).

## 4. Verification strategy (CI has no GPU)
1. **Software Vulkan on Linux CI: Mesa lavapipe.** Add `mesa-vulkan-drivers vulkan-validationlayers glslang-tools` to the three Linux apt lines and the Dockerfile build stage [M package names on noble], pin the ICD with `VK_DRIVER_FILES=/usr/share/vulkan/icd.d/lvp_icd.x86_64.json` (aarch64 leg: `lvp_icd.aarch64.json`) [M paths]. Lavapipe in Mesa 24.x on Ubuntu 24.04 is Vulkan 1.3 conformant [M]. This puts real Vulkan execution in the required check `linux (Release, x86_64, Clang)`.
2. **Windows CI**: compile always. Execution optional: the action has `install_swiftshader` (Windows only) and `install_lavapipe` (Windows prebuilt or apt on Linux) inputs [V action.yml on main; [M] that the `@v1` tag the workflow pins has them]. Recommend Linux execution first, Windows SwiftShader/lavapipe as a later small PR. Tests GTEST_SKIP with a clear reason when no Vulkan device exists, so local Windows runs without a driver still pass.
3. **One golden harness, two backends.** Today's goldens are structural, not image files [V: `SoftwareMeshGoldenTests.cpp` header comment; no PNGs under tests/]: exact colours in regions for nearest/unlit, brightness comparisons for lit. Factor each file's `Render(build, camera, lighting)` to take a renderer factory and run the suite for Software always and Vulkan when a device exists (gtest value-parameterised). Candidates [V counts of TEST lines]: engine/rendering Software*Golden 52 (Mesh 5, Image 2, Model 1, Particles 6, Text 6, TextEffects 6, TextPasses 24, WorldCanvas 2), EditModeLighting 2; renderer/software Golden 16, Lighting 21, NormalMapPbr 23, RenderTarget 2, Resource 14. Assertions that encode Software-only behaviour (no blending, alpha-tested text, early-Z reordering) get a per-backend expectation (Vulkan expects GL semantics: blended, antialiased).
4. **Cross-backend diff** for scenes both should agree on: per-pixel |Vulkan - Software| <= 2/255 for unlit nearest, and for lit/linear-filtered scenes mean error <= 2/255 with <= 1% of pixels over 8/255 after excluding a 1-pixel border of each coverage edge (rasterisation tie rules differ) [M thresholds, tune in PR C].
5. **Validation layers ON in tests**: the debug messenger counts errors/warnings; the fixture fails the test on any error and on undestroyed objects at teardown. Optional synchronization validation in one CI leg (slow) [M cost]. Release builds keep validation off unless `N2_VULKAN_VALIDATION=1` (replaces the hard-coded `true`).
6. **Shader parity test** like `tests/engine/rendering/OpenGlShaderSourceTests.cpp` (which exists because GL cannot run in CI [V]): every uniform `Material::ApplyUniforms` sets has an offset in the Vulkan block table, and the Vulkan GLSL declares it.
7. Side note [M]: the same Mesa install brings llvmpipe, so OpenGL goldens could run in CI too (Xvfb or EGL needed); out of scope, worth a separate issue.

## 6. Third-party dependencies and licences
- **VulkanMemoryAllocator (AMD)**: MIT [V upstream LICENSE.txt]; one header, vendored under `external/` like the other deps (`external/` holds mbedtls, sol2, cgltf, ... [V]) at a pinned release. Hand-rolled alternative: one `vkAllocateMemory` per buffer/image is simplest but per-frame text/particle buffers would churn allocations against `maxMemoryAllocationCount` (4096 on many drivers [M]); a correct sub-allocator is ~300+ lines of risk.
- **glslang** (offline compiler, `glslangValidator`): NOT plain Apache. Core is BSD-3-Clause; the preprocessor adds NVIDIA 2002 and Khronos notices; the file also carries BSD-2, MIT, Apache-2.0 texts, and a GPL-3+Bison-exception section it says no longer applies (Bison removed) [V upstream LICENSE.txt]. Used only as a build tool its licence does not attach to the shipped engine [M, legal reading]; linking it at runtime would require shipping those notices.
- **shaderc** (glslc, libshaderc): Apache-2.0 [V upstream LICENSE]; it embeds glslang + SPIRV-Tools, so a runtime link brings both licence sets [M].
- **CMake support** [V local CMake module docs]: `find_package(Vulkan COMPONENTS glslc glslangValidator)` exists since CMake 3.24 (targets `Vulkan::glslc`, `Vulkan::glslangValidator`); the project requires 3.25 (`CMakeLists.txt:1`).
- CI-only, not shipped: Mesa lavapipe (MIT [M]), SwiftShader (Apache-2.0 [M]), Khronos validation layers (Apache-2.0 [M]).

## 7. Risks
- Lavapipe hides real-driver issues (format support, memory types, timing, sync bugs that only show on a fast GPU): validation + sync validation reduce, not remove, this.
- `stripdown: true` in the Windows SDK cache may remove `glslangValidator` [M]; PR B must check, or use glslc / install the tool separately.
- Committed vs built SPIR-V: build-time compile needs the tool on every builder (Windows SDK, Linux apt, Docker build stage); committed SPIR-V drifts byte-for-byte between glslang versions, so a "regenerate and diff" CI check would be flaky unless the tool version is pinned.
- Behaviour divergence: Vulkan (blended, antialiased like GL) vs Software (opaque, alpha-tested) means some goldens need per-backend expectations; a sloppy split could weaken the existing Software assertions. Keep the Software expectations byte-identical.
- Golden harness refactor touches ~170 existing tests in shared files; merge conflicts with in-flight rendering PRs (e.g. #129 particles PR-C) [V PR exists per progress log].
- Frames in flight + UpdateMesh/Destroy* during a frame: use-after-free if the deletion queue is wrong (validation catches most).
- Dependency weight: Vulkan headers/loader are already required [V]; VMA adds one header. A runtime shader compiler would add tens of MB [M].
- Scope creep into a "render graph": keep IRenderer unchanged; no new interface methods are needed for v1 [V by section 2].

## 8. Decisions for the user
1. **Scope**: v1 = section 3 (built-in shaders only, custom GLSL returns null), or also runtime custom shaders now.
2. **Allocator**: VMA vendored (recommended) vs hand-rolled.
3. **Shader toolchain**: (a) compile GLSL to SPIR-V at build time with `glslangValidator`/`glslc` via FindVulkan components and embed as arrays (recommended; adds `glslang-tools` to Linux/Docker builds), (b) commit generated SPIR-V headers with a pinned-tool regeneration check, or (c) runtime glslang/shaderc (only needed for decision 1's custom shaders).
4. **Build option**: add `N2ENGINE_RENDERER_VULKAN` (default ON) so a build without the shader tool or Vulkan SDK can compile the backend out (also drops `libvulkan1` from the Docker image), or keep Vulkan always required as today.
5. **Default renderer on Linux**: keep OpenGL as default (recommended until PR F passes on real hardware) vs make Vulkan the Linux default afterwards.
6. **Editor host**: allow `--renderer vulkan` (headless works on lavapipe in Docker [M faster than the software renderer, unmeasured]) or not in v1.
7. **CI**: Linux lavapipe only (recommended) or also a Windows SwiftShader/lavapipe execution leg; sync validation in CI yes/no.
8. **Priority vs soft bodies** (physx-soft-bodies.md in progress): Vulkan PR 0-E needs no hardware and can run while soft bodies wait on the GPU PC; recommend Vulkan 0-A first if the GPU PC is the bottleneck for soft bodies, else soft bodies first.

## 9. Cannot be verified without hardware (the user's GPU PC)
Swapchain creation, surface format/colour-space choice and present modes (mailbox/FIFO, vsync), resize/minimise/out-of-date handling, HiDPI framebuffer sizes, real-window input with Vulkan, discrete-vs-integrated device scoring with two GPUs, vendor quirks (NVIDIA/AMD/Intel format support for RGB8/sRGB blits, memory heaps/ReBAR, push-constant limits), validation-clean on a real driver, performance (pipeline creation hitches, per-frame UpdateMesh churn with text and 100k-particle billboards, frames in flight), and the editor running on Windows with Vulkan. Wayland and macOS are out of scope.

## Decisions (user, 2026-10-14)
- Approved with ALL recommended choices: built-in shaders only (custom GLSL returns null in v1); vendor VMA (MIT); compile SPIR-V at build time with glslangValidator/glslc and embed it (adds glslang-tools to the Linux/Docker builds); an N2ENGINE_RENDERER_VULKAN build option; always render offscreen (Present copies to the window); CI on Linux lavapipe only, validation layers on and failing tests on errors/leaks; OpenGL stays the Linux default until the final present PR passes on the user's real GPU; the editor host keeps refusing --renderer vulkan in v1.
- Priority: Vulkan FIRST (PRs 0-E need no hardware and no #129); soft bodies start after #129 merges. PR F (swapchain/present) needs the user's GPU PC.
