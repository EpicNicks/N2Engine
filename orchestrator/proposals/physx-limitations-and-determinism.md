# Report (first pass): PhysX limitations a custom physics system would resolve, and determinism for networked games (#157)

Status: research only, no engine changes. N2Engine `origin/master` 7222391 (fetched 2026-10-15). PhysX headers: `external/PhysX/physx/include/` (5.6.1, git-tracked). Companion to #156 (cost of our own physics) and #155 (web build).
Marks: **[V]** verified in this repo / the PhysX 5.6.1 headers (file:line given), **[M]** from memory, to verify against the named source before anyone relies on it. **[E]** = my own illustration experiment (not PhysX).

## Executive summary
- **Determinism is the one limitation that is both real and structural.** PhysX's own header text promises determinism only for "the exact scene (same actors created in the same order) and simulated using the same time-stepping scheme" (`PxSceneDesc.h:244-245`) [V]. `eENABLE_ENHANCED_DETERMINISM` only adds independence from *additional, non-interacting* actors, still requires consistent insertion order in a newly-created scene, and is "not currently supported on GPU" (`PxSceneDesc.h:250-258`) [V]. Nothing in the headers promises results across platforms, compilers or binaries; our Windows build uses NVIDIA's prebuilt MSVC binaries and Linux uses our own CI-built static libs, so Windows vs Linux PhysX are different binaries [V CMakeLists.txt:41-66, cmake/PhysXLinuxHashes.cmake]. **Cross-platform deterministic lockstep with PhysX is not supportable.** Same-binary, same-machine-class determinism is plausible but unmeasured.
- **Rollback (cheap snapshot/restore) is CONFIRMED as a limitation for the normal scene API**: the scene is not a serializable object (no `eSCENE` in `PxConcreteType`, `common/PxTypeInfo.h:53-80`) [V]; binary serialization covers actors/shapes/materials and is "not supported" while the scene is simulating (`extensions/PxSerialization.h:~200,~222`) [V]; internal contact caches/warm-start/broadphase state are not exposed. **Workaround exists**: PhysX *immediate mode* (`PxImmediateMode.h:111-269`) gives user-owned body data and user-owned contact caches [V], which makes snapshot-by-copy possible, at the price of writing our own broadphase, islands and pipeline around it.
- **Server-authoritative + client prediction/reconciliation needs none of that**: PhysX is fine for it. My chaos illustration [E] shows 1-ulp perturbations stay below 1 mm for >14 s in every scene with up to 30 bodies, and still reach 1 mm only after 2-3 s in a 300-body active pile. A 6-12-step (100-200 ms) prediction window is many orders of magnitude inside that, so reconciliation corrects it trivially; bit-determinism is only required for input-only lockstep/rollback.
- **N2Engine itself has determinism blockers independent of PhysX** (all [V]): run-to-run Lua `pairs()` order and `math.random` seeds (Lua 5.4 seeds from `time(NULL)` + addresses), the engine `Random` API (seeded from `std::random_device`, implementation-defined distributions), coroutine order keyed by `GameObject*` in an `unordered_map`, pointer-keyed collision-matrix refiltering order in `PhysXBackend`, timeScale-scaled fixed dt, frame-timed attach queue (spawned bodies enter at a frame-dependent tick), and SIMD tiers that differ bit-wise (Quaternion dot, Vector3 normalize). None is hard to fix individually; the PhysX backend is the hard part.
- **Recommended design**: three project-level **network presets** (None/offline default; Server authoritative; Deterministic lockstep/rollback) that apply a locked/tunable bundle of settings, an editor nudge on the first network component, a validation report with one-click fixes, and an engine that refuses to start a deterministic project whose configuration cannot honour it. Honest constraint: **no physics backend declares determinism today, so the Deterministic preset is shown as "requires a deterministic physics backend (none installed)"** until #156 delivers one (custom, or an alternative like Box2D v3/Jolt/Rapier-class). PhysX is fully acceptable for the Authoritative preset.
- No gameplay netcode exists in the engine [V: no `replicat|netcode|NetworkIdentity|rollback|lockstep` hits in `engine/` or `editor-server/`; the only networking is the editor host protocol]. Everything below is forward design.

## 2. How determinism is normally solved (references are [M] unless marked)
| Model | What it needs from physics | Who uses it [M] | Verify |
|---|---|---|---|
| **Deterministic lockstep** (send inputs only; every peer simulates) | Bit-identical results on every peer: same op order, no FMA contraction, no fast-math, own or correctly-rounded transcendental functions, fixed dt, ordered iteration, deterministic RNG, no thread-order dependence, same build or a cross-platform-proven one. Desync detection via state hashes. | RTS games (Age of Empires, StarCraft), Factorio | Classic "1500 archers" article (Bettner/Terrano) |
| **Rollback** (lockstep + predict remote inputs, rewind + resimulate on correction) | Everything above **plus** cheap save/restore of the full simulation state several times per frame (resimulate up to N frames). | GGPO-based fighting games; Photon Quantum; Rocket League does *not* (see below) | GGPO docs: `save_game_state`/`load_game_state` callbacks, prediction window (default ~8 frames) |
| **Server-authoritative + client prediction + reconciliation** | No bit determinism. Server simulates; clients predict their own entities, receive snapshots, rewind their own state to the server's, replay unacknowledged inputs, smooth the error. Physics needs "set state" APIs and tolerance to corrections. | Most shooters (Source engine, Overwatch), Unity Netcode/NGO, Unreal (CharacterMovement + physics replication); Rocket League (Bullet, server-authoritative with client prediction of the car, GDC 2018 "It IS Rocket Science") | Rocket League GDC talk; Valve "Source Multiplayer Networking" wiki |
| **Snapshot interpolation** | None: clients render buffered server snapshots 1-2 intervals in the past. Fine for cosmetic or remote objects. | Quake-style, most remote entities in any engine | Gaffer on Games "Snapshot Interpolation" |

Engine reference points [M], each to verify against the vendor doc:
- **Unity Physics (DOTS)**: stateless by design (no caching between steps; state is ECS components), so snapshot = copy components; deterministic on the same architecture/build with Burst; cross-platform claims depend on Burst's deterministic float mode. Verify: Unity Physics manual "Design philosophy" and Burst `FloatMode.Deterministic` status.
- **Havok Physics for Unity**: stateful (caches), faster for stacking, deterministic on the same platform, no rollback-friendly state copy. Verify: Unity Havok package docs.
- **Box2D v3** (2024-25): claims cross-platform determinism (requires `-ffp-contract=off`, own `b2ComputeCosSin`/atan, deterministic multithreading independent of thread count) and is 2D, small, C. Verify: Box2D v3.1 release notes and Erin Catto's "Determinism" blog post (2024).
- **Rapier**: `enhanced-determinism` Cargo feature = cross-platform IEEE-754 determinism (disables SIMD/parallel, uses pure-Rust libm), plus snapshot via serde. Verify: rapier.rs docs "Determinism".
- **Jolt Physics** (not in the issue, but the closest drop-in alternative to PhysX): `CROSS_PLATFORM_DETERMINISTIC` build option, `PhysicsSystem::SaveState/RestoreState` through a `StateRecorder` (designed for rollback), WASM build (JoltPhysics.js). Verify: Jolt `Docs/Architecture.md` "Deterministic simulation" and "Rolling back a simulation".
- **Photon Quantum**: own deterministic engine + physics on fixed point (`FP`, Q48.16), predict/rollback built in. Verify: Photon Quantum docs "Fixed point".
- **GGPO**: requires a deterministic sim, save/load/free state callbacks, input delay + prediction window, checksum-based desync detection. Verify: GGPO developer guide.

## 3. Error magnitude and the chaos argument
Per-step float error is ~1 ulp, but contact-rich systems are chaotic: a contact that is active in one run and not in the other, or a different solve order, flips which way a pile collapses; after that the difference is macroscopic.

**Illustration [E] (NOT a PhysX measurement):** Node.js script `scratchpad/chaos/chaos.js` (not in any repo): 2D discs, gravity, sequential-impulse PGS (10 iterations, friction 0.5, Baumgarte 0.2), every arithmetic result rounded to float32 with `Math.fround`, dt = 1/60, 60 s (pile300: 30 s). Each scene runs twice, the second with one body's x moved by **+1 ulp**; the table gives the first step at which any body differs by more than the threshold.

| Scene | Bodies | > 1 µm | > 1 mm | > 1 cm | > 10 cm | Max divergence |
|---|---|---|---|---|---|---|
| free flight | 1 | never | never | never | never | 1.2e-7 m |
| one disc bouncing/sliding | 1 | never | never | never | never | 6.0e-8 m |
| aligned stack | 5 | never | never | never | never | 2.6e-7 m |
| leaning stack | 5 | 37.3 s | never | never | never | 3.8e-6 m |
| aligned stack | 10 | 27.9 s | never | never | never | 4.1e-5 m |
| pile (settles) | 30 | 0.07-14.8 s / never | never | never | never | 1e-6 to 5e-6 m |
| pile (stays active) | 100 | 0.07-1.5 s | 14.7-19.8 s | 27.2-27.8 s | 54.7-56.8 s / never | 0.10-0.17 m |
| pile (tall, active) | 300 | 0.07-1.0 s | 2.2-2.9 s | 5.1-8.6 s | 10.4-12.4 s | 1.1-1.7 m |
(ranges = three runs perturbing different bodies)

Reading: (1) free flight and resting contact do not amplify; error stays at the ulp scale. (2) Divergence grows with the number of *simultaneously active* contacts; once a pile sleeps/settles, the difference freezes. (3) In a large active pile, 1 ulp becomes metres within ~10 s. Consequences:
- **Lockstep/rollback without bit-determinism desyncs in seconds** in any physics-heavy scene, and nothing tells you until a state hash differs. "Almost deterministic" is not a usable category.
- **Authoritative reconciliation is easily enough**: at 60 Hz a 100-200 ms prediction window is 6-12 steps; in this model even the worst scene diverges by << 1 mm over 12 steps. The server's correction each snapshot resets the error, so chaos never gets time to amplify. Remaining artefacts are game-design ones (visible pops on misprediction of *other* players' effects on piles), handled by smoothing and by not predicting physics you do not own.
- Real PhysX numbers will differ (3D, PCM manifolds, TGS/PGS, islands, sleeping). **Follow-up F1 (CI test, needs PhysX on a CI leg):** a gtest `PhysXDeterminismTest` that builds (a) one free body, (b) a 10-box stack, (c) a 100-box pile, (d) a capsule ragdoll-like chain, runs 600 fixed steps twice in fresh scenes with identical insertion order and asserts bitwise-equal poses (same-binary determinism, with and without `eENABLE_ENHANCED_DETERMINISM`, with 0 and 4 dispatcher threads), then perturbs one initial x by 1 ulp (`std::nextafter`) and records the step at which max pose divergence crosses 1 µm / 1 mm / 1 cm (reported, not asserted). Running it on the Windows and Linux legs and comparing a printed state hash answers the cross-platform question empirically (expected: differ).

## 4. Where the correction belongs: network simulation presets (recommended design)
Correction belongs in the **chosen network model**, not silently in the engine: authoritative games correct on the host (prediction + reconciliation); deterministic games must prevent divergence by configuration, and the engine must refuse configurations that cannot honour it. A single flag is not enough because each model implies a bundle of settings, so the design is **presets**.

### 4.1 Settings model
New `network` block in the project settings file, next to `physics` (parsed by `ProjectSettings.cpp`, which already applies `physics` at `:162` and `fixedTimestep` at `:30`) [V]:
```json
"network": {
  "preset": "none | authoritative | deterministic",
  "customised": false,
  "overrides": { },
  "tickRate": 60,
  "...": "preset-specific values below"
}
```
The preset writes the *effective* values of the settings it governs; `overrides` records any value the user changed away from the preset (that makes the state "Customised", 4.4). Presets are data (a table in the engine, exposed to the editor) so the editor and the engine validate the same rules.

### 4.2 Preset bundles
L = locked by the preset (changing it marks Customised and lists lost guarantees), T = tunable within the preset, S = checked at engine startup (refuse to start if unmet, in a Deterministic project; warn in Authoritative).

| Setting | None / offline (default) | Server authoritative (prediction + reconciliation) | Deterministic lockstep / rollback |
|---|---|---|---|
| Physics backend | any (PhysX) | any; PhysX OK (T) | must declare `IsDeterministic() == Cross-platform` (or `SameBinary` if the user accepts same-build-only peers) (L, S). **Today: none qualifies.** |
| GPU physics (`physics.gpu`) | any | `off` recommended (L for the server instance: server must be CPU, headless host has no GPU), clients T | `off` (L, S) |
| Fixed timestep | project value | on, rate = tick rate (T: 30/60/120 Hz) | on, rate = tick rate (L, S); timeScale must not change the physics dt (L, S, see blocker B5) |
| Simulation tick driver | frame-driven accumulator | tick counter owned by netcode; catch-up clamp T | tick counter owned by netcode; no wall-clock clamp dropping ticks (L, S) |
| Math SIMD tier | detected | detected | one fixed tier for all peers: `Scalar` forced (L, S) until a deterministic math path exists |
| Floating-point build profile | default | default | strict profile flag compiled in: `-ffp-contract=off` on all targets, no fast-math, `/fp:precise` + no `/fp:contract` on MSVC, Release-only peers (L, S: engine checks a compile-time `N2_STRICT_FP` define) |
| Transcendental functions | std | std | engine-owned `Math::Sin/Cos/Atan2/Acos` (deterministic implementations) used by math, Lua bindings and physics (L, S) |
| Simulation state snapshot/restore | n/a | per-entity "set state" for owned predicted entities (S: backend reports `SupportsSetState`) | full-world `SaveState/RestoreState` (rollback) (L, S: backend reports `SupportsSnapshot`); lockstep-only variant may waive it (T: `rollback: on/off`) |
| Input delay | n/a | 0 (T) | 2 ticks (T: 0-6) |
| Prediction / rollback window | n/a | client prediction window = RTT-bounded, max 250 ms (T) | max rollback 8 ticks (T: 0-15; 0 = pure lockstep) |
| State sync / snapshot rate | n/a | server snapshots 20-30 Hz (T), delta-compressed | none (inputs only); periodic state hash every 30 ticks for desync detection (T rate, L enabled) |
| Interpolation | n/a | remote entities rendered 2 snapshots behind (T: interpolation delay ms) | render interpolation between ticks only (T) |
| Reconciliation / smoothing | n/a | rewind owned entities to server state, replay inputs; visual smoothing of the error over 100 ms (T), snap threshold 1 m (T) | none (bit-exact) |
| Authority rules for physics bodies | n/a | server owns all dynamic bodies; client predicts only its own avatar/kinematic controller; remote and shared dynamic bodies are interpolated (T: per-body `predict` opt-in) | every peer simulates everything; no per-body authority (L) |
| RNG policy | any | gameplay RNG server-side; clients may use cosmetic RNG freely (T) | only the seeded deterministic stream (`Math::DeterministicRandom`, ParticleRandom-style), seed from session; `Random.*` and Lua `math.random` redirected or disabled (L, S) |
| Ordering rules | none | none | ordered containers in every simulation path, stable spawn order (by tick + spawner id), coroutine order by creation index, Lua `pairs()` banned in sim code or a deterministic string hash seed (L, S where checkable) |
| Threads | any | any | physics dispatcher threads 0, or a backend that proves thread-count independence (L, S) |
| Allowed backends shown in the picker | all | all | only backends with the declaration; others greyed with the reason |

### 4.3 Editor UX
- **Project Settings > Network panel** (new section beside Physics): a preset picker with three cards (None, Server authoritative, Deterministic lockstep/rollback), one line each on what it is for, and the bundle table above as the detail view (locked rows shown with a lock icon, tunable rows editable). The Deterministic card shows a badge **"Requires a deterministic physics backend (none installed)"** and cannot be selected while no backend declares determinism; a link explains why and points to #156. (It may be selectable for projects with *no* Rigidbody components, since then physics is not a blocker; decision D3.)
- **Nudge on the first network component**: when `AddComponent` (`protocol.json:580`) adds the first component tagged `network` (none exist yet) and the preset is `none`, show a non-blocking panel: "This project has no network model. Choose one:" with the two presets and "Not now". It never blocks the add.
- **Customised state**: changing a locked value switches the preset label to "Server authoritative (customised)" / "Deterministic (customised)" and lists the guarantees lost, e.g. "Physics dt follows timeScale: peers that pause differently desync", "SIMD tier Auto: x86 and ARM peers will desync". "Reset to preset" restores the bundle.
- **Validation report** (panel in Network settings and a row in Engine Health): requirement, status met/not met, why, one-click fix where a fix is mechanical: set `physics.gpu=off`, set fixed timestep, force SIMD Scalar, enable state hashing, replace `Random.*` calls (opens the files), turn off dispatcher threads. Not-fixable items (no deterministic backend; strict-FP build profile missing in this build) say what is needed. Data comes from the engine (validation is engine code; the editor only renders it), returned through `GetEngineHealth` (`protocol.json:557`) as a `"Network"` `SubsystemStatus` row plus a detail list, and the panel writes changes through `SetProjectSettings` (`:660`) [V command names; schema additions would need a minor protocol bump from 1.12.0 and client regeneration].

### 4.4 Engine startup validation
At `Application::Init` (after `ProjectSettings` load, before scene load):
- `IPhysicsBackend` gains `virtual DeterminismLevel GetDeterminism() const { return DeterminismLevel::None; }` (`None | SameBinary | CrossPlatform`) plus `SupportsSnapshot()`/`SupportsSetState()`. `PhysXBackend` returns `None` (or `SameBinary` once F1 proves it with enhanced determinism, CPU, 0 threads), `SupportsSetState() = true`, `SupportsSnapshot() = false`.
- Deterministic preset: fail start with a clear `Failed` health row and log (never silently degrade) unless: backend level >= required; GPU dynamics off and the scene confirmed CPU; fixed timestep on; SIMD tier forced to the preset tier (`Math::SetSIMDLevel`, `MathRegistrar.cpp:60`) [V function exists]; the `N2_STRICT_FP` compile flag present; RNG redirected; Lua determinism shims installed; dispatcher threads 0.
- Authoritative preset: warn only (GPU on the server, missing `SupportsSetState`).
- Peers exchange a **determinism fingerprint** at session start (engine version, build profile, compiler id, architecture, SIMD tier, backend id + level, tick rate) and refuse to pair on mismatch.

### Staged plan
1. **Cheap (S1, CI-verifiable, useful even offline: replays, tests):** `math.simdTier` setting (force Scalar); strict-FP compile profile (CMake option `N2ENGINE_STRICT_FP`, defines `N2_STRICT_FP`); `Math::DeterministicRandom` + Lua `Random` redirect; constant Lua hash seed + seeded `math.random`; ordered containers for coroutines, refiltering and touch maps; PhysX 0-thread + enhanced-determinism option; F1 determinism gtest.
2. **Medium (S2):** deterministic transcendental functions; netcode-owned tick loop (timeScale-independent dt, tick-aligned spawns); `IPhysicsBackend::GetDeterminism/SupportsSnapshot/SupportsSetState`; network presets in settings + startup validation + Engine Health row; editor Network panel, nudge and validation report; exact-equality tier tests.
3. **Large (S3, the #156 decision):** a deterministic physics backend (custom, or integrate an alternative that already claims cross-platform determinism + snapshot: Jolt with `CROSS_PLATFORM_DETERMINISTIC`, Box2D v3 for 2D, Rapier via C bindings is awkward) behind `IPhysicsBackend`, declaring `CrossPlatform` and `SupportsSnapshot`; only then does the Deterministic preset become selectable.

## 6. Recommendation
- **Justify a custom or alternative engine:** determinism across platforms (CONFIRMED, structural), cheap rollback snapshots (CONFIRMED for the scene API), native 2D (CONFIRMED), and the web/size story (size CONFIRMED, web PARTLY). These are exactly the needs of a deterministic-lockstep/rollback preset and of a small web build.
- **Workable with PhysX:** server-authoritative networking (PhysX is adequate: set-state APIs exist, reconciliation absorbs chaos), threading (0 workers), inspectability (source is public), special solvers (kinematics, CCT, scene queries, immediate mode), platform reach on desktop.
- So: **keep PhysX as the default 3D backend and the backend for the Authoritative preset**; do the cheap engine-side fixes (S1) regardless, since they also give reproducible replays and tests; and feed #156 the requirement list for a second backend: deterministic by construction (strict float, own trig, fixed order, single-thread or deterministic parallel), plain-data state with save/restore, 2D-capable or 2D-first, small enough for WASM. Evaluate "integrate Jolt/Box2D v3" against "write our own" in #156 before committing to custom code; an alternative engine meets most of the list today [M, verify].

## 7. Decisions for the user
- **D1** Preset names and set: None / Server authoritative / Deterministic lockstep-rollback (as above)? Or split lockstep and rollback into two presets?
- **D2** Determinism target: cross-platform (Windows + Linux + web peers) or same-build-only? Cross-platform rules out PhysX and requires B2/B8 everywhere.
- **D3** While no deterministic backend exists: hide the Deterministic preset, show it disabled with the reason (recommended), or allow it for projects without Rigidbody components?
- **D4** Startup behaviour in Deterministic mode with an unmet requirement: refuse to start (recommended) or start with a `Failed` Network health row?
- **D5** Do S1 (cheap fixes) now, independent of netcode? (Recommended: yes; they are small, CI-testable and help replays/tests.)
- **D6** #156 scope: evaluate integrating Jolt (3D) and/or Box2D v3 (2D) before a custom engine?
- **D7** Lua in deterministic sim code: patch the hash seed and offer an ordered iteration helper, or forbid `pairs()` in sim scripts by lint?
