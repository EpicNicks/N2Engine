# Proposal: soft bodies (PhysX GPU deformable volumes + a CPU backend)

Status: research only, no code. N2Engine master 2abaa16; PR #129 (particles PR-C, branch `feat-particles-physx-pbd`, head 17246ef) read with `git show`. Marks: [V] verified in the repo, in the engine's PhysX headers (`external/PhysX/physx/include/`, 5.6.1) or in the PhysX source clone (tag `107.3-physx-5.6.1`, paths relative to its `physx/`); [M] from memory, an estimate, or unverifiable until a GPU run.
Follows `physx-particles.md` ("Later: soft bodies reuse the same GPU scene, probe, PxCudaContextManager and asset") and its 2026-10-13 decisions (both a PhysX and a CPU backend, `backend: Auto|PhysX|CPU`, `physics.gpu` default off, Windows first, Linux GPU asset deferred).

## 1. What PhysX 5.6.1 offers
1. **GPU only, no CPU soft bodies in 5.6.1 [V].** `PxDeformableVolume` (FEM; `PxSoftBody` survives only as a deprecated alias, `include/PxSoftBody.h`) says "exclusively supported on GPU. The full GPU pipeline needs to be enabled" (`PxDeformableVolume.h:69-71`). Source: `NpScene::addDeformableVolume` refuses without `eENABLE_GPU_DYNAMICS` ("Deformable volumes can only be simulated by GPU-accelerated scenes!", `source/physx/src/NpScene.cpp:1507-1511`); `NpPhysics::createDeformableVolume(PxCudaContextManager&)` returns NULL when `PX_SUPPORT_GPU_PHYSX` is 0 (`NpPhysics.cpp:575-583`). Deformable surfaces (cloth) are the same (`NpScene.cpp:1460`). So the Linux CPU-only static libs can never run them, and Windows needs `physics.gpu` auto/on plus a Ready probe.
2. **Limits [V]**: 4095 deformable volumes per scene, 1,048,575 tets per volume (`PxDeformableVolume.h:55-64`). Hardware is the particles one: NVIDIA compute capability 7.0+, CUDA 12.8-class driver (see physx-particles.md section 1.7).
3. **Data model [V]**: a `PxDeformableVolumeMesh` bundles a *collision* tet mesh (conforming to the surface), a *simulation* tet mesh (usually a voxel hex-derived mesh) and aux data (sim to collision mapping, masses). Per-volume DEVICE buffers: `getPositionInvMassBufferD` (collision verts), `getSimPositionInvMassBufferD`, `getSimVelocityBufferD`, `getRestPositionBufferD`, each PxVec4 per vertex; writes need `markDirty(PxDeformableVolumeDataFlag::...)` and are forbidden between `simulate` and `fetchResults` (`PxDeformableVolume.h:130-265`, flags `PxDeformableVolumeFlag.h:67-74`). Host mirror helpers in `PxDeformableVolumeExt`: `allocateAndInitializeHostMirror` (pinned memory), `transform`, `updateMass`/`setMass`, `copyToDevice` (`extensions/PxDeformableVolumeExt.h:69-256`).
4. **Creation [V]** (`snippets/snippetdeformablevolume/SnippetDeformableVolume.cpp:82-128`): cook the mesh; `createDeformableVolume(cudaCM)`; `createDeformableVolumeMaterial(youngs, poissons, dynamicFriction, elasticityDamping)` (`PxPhysics.h:908`); `createShape(PxTetrahedronMeshGeometry(collisionMesh), material)`; `attachShape`, `attachSimulationMesh(simMesh, auxData)`; `scene->addActor`; then the host-mirror init above. Material models `eCO_ROTATIONAL` (default, needs well-shaped tets) and `eNEO_HOOKEAN` (robust to bad tets) (`PxDeformableVolumeMaterial.h:39-44`). Body flags `eDISABLE_SELF_COLLISION`, `eENABLE_SPECULATIVE_CCD`, `eKINEMATIC` (`PxDeformableBodyFlag.h:47-49`), `ePARTIALLY_KINEMATIC` + `setKinematicTargetBufferD` (a DEVICE buffer of targets) for pinned vertices (`PxDeformableVolume.h:268-303`).
5. **Attachments [V]**: the new path is `PxPhysics::createDeformableAttachment(PxDeformableAttachmentData)` (`PxPhysics.h:686`) with targets eVERTEX / eTETRAHEDRON / eRIGID / eWORLD (`PxDeformableAttachment.h:70-111`); every per-actor `addRigidAttachment`/`addTetRigidAttachment`/particle attachment on `PxDeformableVolume` is `PX_DEPRECATED` (`PxDeformableVolume.h:469-645`). Use only the new API.
6. **Scene [V]**: exactly the particles scene (GPU dynamics + GPU broadphase + `cudaContextManager`). The snippets use TGS (`SnippetDeformableVolume.cpp:201`) but the attachment snippet uses PGS (`SnippetDeformableVolumeAttachment.cpp:312`); the engine sets no `solverType` (PGS default) [V grep], so no solver change is needed [M that PGS quality is acceptable]. `PxGpuDynamicsMemoryConfig::maxDeformableVolumeContacts` exists (`PxSceneDesc.h:468`); defaults adequate for a few bodies [M].
7. **Read-back [V]**: the snippet does `simulate; fetchResults(true);` then `memcpyDtoH` of `getPositionInvMassBufferD` under `PxScopedCudaLock` (`SnippetDeformableVolume.cpp:220-231`, `.h:73-79`). `fetchResultsParticleSystem` is documented as particle-only (`PxScene.h:1174-1177`); whether deformables need any extra sync is [M] (snippet suggests not).
8. **Rendering a fine mesh from a coarse simulation [V]**: `snippetdeformablevolumeskinning` embeds render vertices in the simulation tets with `PxDeformableSkinningExt::initializeInterpolatedVertices` (CPU; `PxTetrahedronMeshEmbeddingInfo {uvw, tet id}`, `extensions/PxDeformableSkinningExt.h:67-100`, `PxDeformableSkinning.h:84`) and then skins on the GPU. We only need the CPU embedding: skin on the host from the read-back positions, the same code the CPU backend uses.
9. **Cooking and tet generation are CPU code [V]**: `PxCreateDeformableVolumeMesh`/`PxCookDeformableVolumeMesh` (`cooking/PxCooking.h:727-818`, `source/physxcooking/src/Cooking.cpp:126-158`) and `GuCookingTetrahedronMesh.cpp` have no `PX_SUPPORT_GPU_PHYSX` guard; GPU use needs `PxCookingParams::buildGPUData = true` (`SnippetDeformableVolume.cpp:182`). `PxTetMaker` (PhysXExtensions, `source/physxextensions/src/tet/*`) offers `createConformingTetrahedronMesh` (Delaunay; needs a watertight manifold, optional `validateTriangleMesh`), `createVoxelTetrahedronMesh(...FromEdgeLength)` (5 or 6 tets/voxel, plus input-point-to-tet map), `createRelaxedVoxelTetrahedralMesh`, `createTreeBasedTetrahedralMesh`, `remeshTriangleMesh`/`simplifyTriangleMesh`, and `PxRemeshingExt` (`extensions/PxTetMakerExt.h:67-213`). `PxDeformableVolumeExt::createDeformableVolumeMesh` = conforming collision mesh + voxel simulation mesh (`ExtDeformableVolumeExt.cpp:312-333`). The engine links PhysXCooking and PhysXExtensions on Windows (`CMakeLists.txt:51-52`) and Linux (`:146-147`) but no engine code calls cooking yet [V grep]. Consequence: tet generation and cooking can be unit-tested on every CI leg with PhysX ON (Windows PhysX ON, Linux x86_64, Linux arm64), not on the Windows PhysX OFF leg [V tests.yml matrix].
10. **Binaries [V]**: the same `PhysXGpu_64.dll` serves particles and deformables [M: one GPU module, not separately verified]; the slim Windows package keeps it and checks it (`physx-windows-slim.yml:114-115, 298-317`). Nothing new to ship on Windows. Linux: `N2ENGINE_PHYSX_GPU_PROBE` is 0 on Linux (PR #129 `PhysXGpuSupport.hpp`), so no deformables there until the deferred Linux GPU asset.

## 2. Engine-side design
**Seam (mirror PR #129)**: `ISoftBodyBackend` (engine/include/engine/physics/ISoftBodyBackend.hpp), no PhysX/CUDA types, main thread only, generation-counted 64-bit handles exactly like `IParticleBackend` (`MakeParticleHandle`/`NextParticleBackendGeneration`, PR #129 `IParticleBackend.hpp`) [V pattern]; recommend lifting that generation/handle helper into a shared header rather than copying it. Calls: `CreateBody(desc) -> handle` (desc: a shared `TetMeshData` + embedding, world pose and scale, density, stiffness/Poisson/damping/friction, material model, solver iterations, self-collision, pinned vertex set), `Destroy`, `SetParams`, `SetPinnedTargets`, `AddVelocity(handle, Vector3)` (a push for scripts), `Step(dt)` (CPU does the work, GPU no-op), `CopySurfacePositions(handle, std::vector<Vector3>&)` (embedded render positions, world space). `IPhysicsBackend::GetSoftBodyBackend()` returns nullptr by default (beside `GetParticleBackend`, `IPhysicsBackend.hpp:37`) [V].
**Driver layer**: `IDeformableDriver` like `IPbdDriver` (PR #129 `engine/include/engine/particles/PbdDriver.hpp`): `CreateVolume(cooked mesh bytes or TetMeshData, material, error&)`, `DestroyVolume`, `GetStaging` (host mirror spans), `Upload(dirty)`, `ReadBack(count)`, `SetKinematicTargets`, `GetDeviceName`. Real `PhysXDeformableDriver` is the only file with CUDA/device pointers (cook with `buildGPUData`, create, pinned mirrors, `copyToDevice`, `memcpyDtoH` after `fetchResults`). `PhysXBackend` owns `_softBodies` beside `_particles`, created when the GPU scene is Ready, read back after `fetchResults` (as `_particles->OnSceneStepped`, PR #129 `PhysXBackend.cpp` Update), released before the scene and CUDA context, plus `InstallDeformableDriverForTesting` [V pattern].
**GPU status coupling (must fix in PR-A)**: PR #129's `FailParticles` rewrites the single `_gpuStatus` to Unavailable/Failed [V]. If soft bodies reuse that, a soft-body failure would flip the Particles row (and `Physics.IsGpuAvailable`, `LuaPhysicsBindings.cpp:194-199`). Proposal: keep `_gpuStatus` for the scene/probe and add per-feature failure state (`particles`, `softBodies`), each health row composing scene status + its own failure.
**Tet data**: `TetMeshData {positions, tets (4 indices), surfaceEmbedding (per render vertex: tet id + barycentric)}` built from the sibling `MeshRenderer`'s mesh CPU data (`Mesh::GetVertices/GetIndices`, `Mesh.hpp:107-108`) [V]. Steps: weld by position (render vertices are split at UV/normal seams: `Vertex` carries normal/uv per vertex, `RenderTypes.hpp:15-22` [V]; imported models nearly always have seams [M]); generate tets; embed the original (unwelded) vertices so seams move together. Cache in memory keyed by mesh identity + `Mesh::GetVersion()` + settings. NOT in `Mesh::SetCpuCache`: that slot holds one object per mesh (the picking BVH) and a second type evicts it (`Mesh.hpp:121-140`) [V].
**Component** `Physics::SoftBody final : public Component` (not IRenderable), requires a `MeshRenderer` on the same GameObject and refuses (one warning, inert) with a `Rigidbody` there. Fields via `RegisterMember` + `N2_SERIALIZE_ENUM` (as `Light`/`ParticleSystem`): `backend` Auto|PhysX|CPU (same `SelectParticleBackend` semantics, PR #129 `ParticleBackendSelection.hpp`), `resolution` (voxels along the longest axis, default 10), `density`, `stiffness` (Young's modulus, PhysX units; CPU maps it to compliance), `poisson`, `damping`, `friction`, `materialModel` CoRotational|NeoHookean (PhysX only), `solverIterations`, `selfCollision` (PhysX only), `collideWithGround` + `groundHeight` (CPU), pin settings (decision 5). Registration `Add<Physics::SoftBody>(registry, "SoftBody")` in `BuiltinComponents.cpp:47-65` [V]. No asset field (the mesh is the MeshRenderer's), so no new field type.
**Rendering**: add a runtime-only override to `MeshRenderer` (`SetDeformedMesh(std::shared_ptr<Mesh>)`, never serialized, cleared on destroy; today it has `SetMesh` + serialized `_mesh`, `MeshRenderer.hpp:67-92`) [V]. SoftBody owns a runtime `Mesh` cloned from the source; after each step it writes skinned positions + recomputed area-weighted normals and calls `Mesh::SetData`, which bumps the version (`Mesh.cpp:324-341`), and `GpuCache` then re-uploads in place via `IRenderer::UpdateMesh` (`GpuCache.cpp:299`) [V]. This keeps materials, submeshes, lighting and shadows with zero renderer changes; OpenGL and software work, Vulkan draws nothing (as for every mesh today). Cost: copy + `Validate` + bounds per update [V code], 64 B/vertex upload (10k vertices = 640 KB/frame). Tangents stay the rest ones (normal maps slightly off under big deformation) [M]. Picking during play hits a fresh BVH per version [M cost, play-mode picking is rare].
**Lua**: `MakeAccess<SoftBody>` + `BindComponentType` (`LuaComponentBindings.cpp:106-115, 675+`) [V pattern]: fields, `AddVelocity(v)`, `Reset()`, `GetActiveBackendName()`; `engine-api.lua` stubs; docs `docs/soft-bodies.html` + `docs/physics.html`.
**Health**: a `"SoftBodies"` row beside `"Particles"` (Application.cpp ~236 creates the Particles row [V]): Disabled (physics.gpu off / no GPU), Running "PhysX GPU: <device>", Failed only for physics.gpu=on; detail adds usage "SoftBodies: 1 CPU, 2 PhysX" (as `ParticleUsage::Compose`) [V pattern].
**Editor / protocol: no change [V]**: `SubsystemStatus` is `{name,state,detail}` (`editor-server/protocol/protocol.json:850-854`, protocol 1.12.0), inspector fields come from `GetComponentTypes` via RegisterMember. The frontend shows health rows and component fields generically [M, frontend not re-read]. Optional later: a "GPU soft bodies unavailable" inspector hint.
**Play mode**: as ParticleSystem (`ParticleSystem.hpp` header comment) [V]: simulate only in play; edit mode shows the undeformed MeshRenderer (the override only exists in play); deformation is never serialized; leaving play destroys it with the snapshot scene (`EditorServer::EnterPlayMode`, `EditorServer.hpp:500`); pause (no fixed steps) freezes it. Simulation in world space: moving the GameObject in play does not drag the body (unless pinned/kinematic); render vertices are converted into the object's local space with its current inverse transform each update. Tet generation happens at attach (play start), so a large mesh can stall entering play: measure, then move to import time if needed (decision 2).

## 3. CPU backend (the fallback)
- **Algorithm**: XPBD on the same tets: per-tet volume constraint + per-edge distance constraints (or an XPBD Neo-Hookean tet energy) [M literature: Macklin/Müller], Gauss-Seidel, fixed sub-steps, ground plane, velocity damping, pinned vertices, deterministic for a fixed dt. Single-threaded v1.
- **Tets without PhysX**: the Windows PhysX OFF build has no `PxTetMaker`. Options: (a) an engine voxel tetrahedraliser (grid, inside test by ray parity or winding number, 5 tets per voxel, embed render vertices): about 300-400 lines, works in every build and is easy to test [M]; (b) use `PxTetMaker` when PhysX is linked and leave SoftBody inert on PhysX OFF. Recommend (a) for CPU and PhysX's own cooking pipeline for GPU (conforming collision + voxel sim mesh), accepting that the two backends' meshes differ.
- **Effort [M]**: tetrahedraliser 300-400 lines; XPBD backend 400-600; component + render override + Lua 600-800; tests 1,200-1,800 (particles: CPU backend 193 lines, ParticleSystem.cpp 534, simulation tests 871, component tests 721 [V wc]). Roughly 1.5-2x the particles PR-B.
- **Limits**: a few thousand tets per body at 60 Hz single-threaded [M]; no self-collision; collides with the ground plane only in v1 (static Box/Sphere/Capsule colliders later via closest-point projection); no two-way coupling (soft bodies do not push Rigidbodies); behaviour will not match PhysX FEM (different solver and parameters), so an `Auto` project looks different on a GPU machine with physics.gpu on.

1. **PR-A (CI)** seam: `ISoftBodyBackend`, shared generation/handle helper, `GetSoftBodyBackend()` default null, `SoftBodies` health row (Disabled everywhere in CI), per-feature GPU failure state (refactor of PR #129's `FailParticles` coupling). Starts after #129 merges (shared `PhysXBackend.cpp`, `GpuStatus.hpp`, `Application.cpp`).
2. **PR-B (CI)** tet pipeline + CPU XPBD backend + `SoftBody` component + MeshRenderer override + Lua + docs. Can split into B1 (tetrahedraliser + CPU backend, pure logic) and B2 (component, rendering, Lua). Fully headless-testable.
3. **PR-C (GPU PC)** PhysX backend: `IDeformableDriver`, `PhysXDeformableDriver` (cooking with `buildGPUData`, pinned mirrors, read-back), backend logic + fake-driver tests, checklist doc. Merge after the user's GPU run (same rule as #129).
4. **PR-D (deferred with the Linux GPU asset)**: nothing soft-body specific; when `libPhysXGpu_64.so` lands and `N2ENGINE_PHYSX_GPU_PROBE` turns on for Linux x86_64, soft bodies follow. Tet generation and the CPU backend already work on Linux and arm64. Only extra work: run the GPU checklist on a Linux GPU host if one exists.
5. **PR-E (optional)** authored tet import (TetGen `.node/.ele`, Gmsh `.msh`; no tet format exists in the engine today [V grep]); import-time tet caching in the model `.meta` (`ModelSettings` customData, `Model.hpp`) or a sidecar; pinning to a Rigidbody (eRIGID attachment on GPU, a moving pin set on CPU); CPU collision with static colliders; multithreaded CPU solver; GPU skinning.

## 6. Risks
- Imported meshes are often not watertight/manifold: conforming TetMaker fails [V it validates]; the voxel paths are tolerant [M]. Mitigation: voxel path by default, `PxTetMaker::remeshTriangleMesh` repair, a clear inert-with-warning path.
- Per-frame `Mesh::SetData` copy + validation + upload on large meshes; mitigation: drive a decimated render mesh or cap vertices with a warning.
- CPU vs GPU behaviour mismatch under `Auto` (different solvers and parameter meanings).
- The GPU-status coupling above; and the GPU scene changes rigid-body behaviour for the whole project (inherited from particles).
- PhysX API churn: 5.6 renamed SoftBody to DeformableVolume and deprecated the old attachments; isolated behind the driver.
- Untuned FEM parameters (no GPU to tune on); entering play stalls on big meshes until tets are cached.

## 7. Decisions for the user
1. CPU fallback: yes (XPBD tets, recommended, matches the particles decision and runs headless/CI/Linux) or GPU-only (then a SoftBody is inert without physics.gpu, which is off by default, so most projects see nothing).
2. Tet authoring: auto-generate from the MeshRenderer's surface only (recommended v1), generated at play start with an in-memory cache vs at import into `.meta`/sidecar; external tet import later (PR-E) or never.
3. Default behaviour: `backend = Auto` (CPU unless physics.gpu auto/on and Ready) and `physics.gpu` stays off (recommended, consistent with particles).
4. SoftBody drives a sibling MeshRenderer via a runtime mesh override (recommended) vs its own renderable with mesh/material fields.
5. Pinning in v1: none (recommended; v1 bodies only fall and squash), a local pin box, or attach to a Rigidbody (PR-E).
6. CPU tets: engine voxel tetrahedraliser (works with PhysX OFF, recommended) vs PxTetMaker only (SoftBody inert on PhysX OFF builds).
7. Priority vs Vulkan #43: the files are disjoint (physics/particles vs renderer), so A/B can run in parallel with Vulkan; if one at a time, Vulkan first (it unblocks meshes, text and particles on the Vulkan renderer, while soft bodies are a showcase whose GPU half needs the user's PC). Batch soft-body PR-C with the pending #129 GPU run if the user prefers fewer GPU sessions.

## 8. Cannot be verified without hardware
Real deformable creation and stepping, whether `fetchResults(true)` alone makes the device buffers safe to read, read-back timing, VRAM per body, perf with N bodies and with particles in the same scene, PGS vs TGS quality, material-model stability on real imported (seamed, non-manifold) meshes, kinematic targets/attachments, PhysXGpu_64.dll behaviour when the driver or DLL is missing, and anything Linux GPU. On CI: only the CPU backend, tet generation, cooking (CPU) and the fake-driver logic.

## Decisions (user, 2026-10-14)
- Approved with ALL recommended choices: CPU fallback YES (engine XPBD solver + the engine's own voxel tetrahedraliser, works without PhysX); tets auto-generated from the mesh surface at play start with an in-memory cache; component `backend = Auto` with physics.gpu staying off by default; SoftBody drives a sibling MeshRenderer through a runtime-only deformed-mesh override; no pinning in v1.
- Sequencing: PR-A (seam, SoftBodies health row, split the failure state per feature) waits until particles PR-C (#129) has merged (that waits for the user's GPU run); PR-B (tets + CPU backend + component + rendering) is CI-verifiable; PR-C (PhysX backend) needs the user's GPU PC, ideally in the same session as the PR-C particles run. Priority: Vulkan first.
