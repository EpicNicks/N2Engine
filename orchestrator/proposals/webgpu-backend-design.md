# Proposal: WebGPU rendering backend for the web player (issue #155, stage 7)

Status: design only. Nothing was changed, built or run. N2Engine master 5da1380 (2026-10-20); web stages 0-4 merged (#163, #167, #170, #174, #181), stage 5 PhysX-on-WASM open as PR #184, Vulkan stages 0-E merged, stage F (swapchain) held for the user's GPU run.
Marks: **[V]** verified by reading this repo (path:line, paths relative to N2Engine/); **[M]** from memory, unverified: re-check against the named source before relying on it (browser support and Emscripten/Dawn details change monthly); **[E]** my estimate, nothing measured.

## Executive summary
- **What exists to build on [V]:** the renderer seam is `IRenderer` (`renderer/include/renderer/common/Renderer.hpp:55-246`): immediate-mode ordered draws with a per-draw `RenderState`, `UpdateMesh` every frame (text, particles, GpuCache), and `ReadFramebuffer` (RGBA8, bottom row first). The Vulkan backend already solved most of what WebGPU needs: GL clip conventions on a 0..1-depth API, a per-draw dynamic-offset uniform ring, std140 material blocks written through a name table, a lighting block built by a pure function, a pipeline cache keyed by (shader, RenderState, wireframe), always rendering offscreen, and a golden + cross-backend-diff harness against the software renderer. The shader interface table and lighting block builder are **already Vulkan-free headers** (`VulkanShaderInterface.hpp:18`, `VulkanLighting.hpp:14-16`), and `VulkanMaterial`'s public shape uses no Vulkan type (`renderer/src/vulkan/VulkanDraw.hpp:66-128`).
- **What does not carry over:** SPIR-V (browsers take WGSL only), VMA and the frame/fence/deletion machinery (WebGPU orders queue work itself), combined image samplers (WebGPU has separate textures and samplers), `row_major` blocks (WGSL has no row-major matrices), GLSL `inverse()` (no WGSL built-in), polygon-mode wireframe (not in core WebGPU), blit-based mipmaps (no blit), and **synchronous readback** (WebGPU maps buffers asynchronously).
- **Recommended shape:** a `WebGpuRenderer` in `renderer/src/webgpu/`, written once against `webgpu.h` and compiled two ways: for the browser with Emscripten's **emdawnwebgpu** port, and natively against **Dawn** for CI, where it executes on the Mesa lavapipe Vulkan driver the Linux legs already install. Shaders: **hand-written WGSL ports of the three built-ins** (unlit, lit, text; ~520 lines of GLSL today [V `wc`]), tied to a shared interface table by a text parity test and validated by Tint (and optionally naga) in CI. Goldens: the existing Vulkan golden suite and `CrossBackendDiff.hpp` reused for WebGPU against the software renderer (and against Vulkan for blended/antialiased scenes).
- **Browser side:** one wasm containing both the software renderer and WebGPU. The loader asks for a WebGPU adapter and device **in JavaScript while the files download**, before the Start click; on any failure (no `navigator.gpu`, insecure context, null adapter, device error) it starts the engine on the software renderer, exactly as today. No ASYNCIFY or JSPI is needed. The baseline promise (any static host, no special headers) is kept because the fallback is the current player; WebGPU itself only appears on https or localhost (secure context) in browsers that ship it.
- **What CI can prove:** WGSL validity, interface parity, the backend's images on Dawn-over-lavapipe vs the software renderer, the Emscripten link and the size budgets, the loader's selection logic against a mock `navigator.gpu`. **What only the user can prove:** that it draws in real browsers (Chrome/Edge, Safari, Firefox, mobile), colours/format on a real canvas, HiDPI, performance, device loss, the http/iframe fallback.
- Plan: 7 PRs (G0-G6), G0-G3 independent of the browser and of Vulkan stage F; G5 needs the user's browsers. Ten decisions W1-W10 in section 9.

## 1. Goals, non-goals, and what the user already decided
Decided (issue #155 body, maintainer 2026-10-15) [V]: player only, no in-browser editor; **software renderer first, then "progress toward a WebGPU backend"**; **WebGL2 is not a target** ("revisit only if browser coverage demands it"); the **baseline build needs no cross-origin isolation or custom headers**; build profiles dev/size/speed from the start; Emscripten is the toolchain; stage 7 = "WebGPU backend (design first: shader translation, pipeline/resource model reuse from the Vulkan backend, cross-backend goldens)". docs/web-build.html:99-102 restates the same [V].

Goals of stage 7 v1:
1. A `WebGpuRenderer` implementing `IRenderer` with the same scope the Vulkan backend has (built-in unlit/lit/text shaders, materials with the 4 aux textures and PBR flags, scene lighting, every `RenderState`, `IndexRange`, `UpdateMesh`, `SetRenderTargetSize`, `ReadFramebuffer`), drawing with OpenGL semantics (blended, antialiased text) like Vulkan (`Renderer.hpp:51-53,184-186`) [V].
2. The web player uses it when the browser offers WebGPU and falls back to the software renderer otherwise, with no reload loops and no change to the hosting contract (docs/web-build.html:361-369 output contract) [V].
3. CI evidence comparable to Vulkan's: cross-backend goldens without a GPU.

Non-goals for v1 (proposed): custom user shaders (Vulkan v1 also ships built-ins only; `Resources::LoadShader` is the only entry and nothing in the repo calls it, `engine/src/io/Resources.cpp:92-125` [V], vulkan-backend.md section 2); compute shaders, GPU particles or GPU soft bodies (the GPU paths are PhysX CUDA and PhysX is CPU-only on the web, docs/web-build.html:134,231 [V]: CPU particles and CPU soft bodies already work on the software player and draw through `UpdateMesh`, `ParticleSystem.cpp:526`, `TextDrawing.cpp:333`, `GpuCache.cpp:299` [V]); post-effects (none exist: no bloom/tonemap/post-process code in engine/ or renderer/ [V grep]); MSAA; WebGL2; the threaded build (stage 6) is orthogonal; native WebGPU as a user-selectable renderer (W8).

## 2. Browser facts (all [M] unless marked; re-verify at G5 time)
**Availability** (to my knowledge, mid-2026):
| Browser | WebGPU by default | Notes |
|---|---|---|
| Chrome / Edge desktop | 113+ on Windows (D3D12), macOS (Metal), ChromeOS | Linux rollout was partial (some GPUs/drivers, later versions); blocklisted GPUs get a null adapter |
| Chrome Android | 121+, Android 12+ with supported Qualcomm/ARM GPUs | many older phones get none |
| Safari | 26 (macOS 26, iOS/iPadOS 26, visionOS) | iOS < 26 has none: still a large share of iPhones in 2026 |
| Firefox | 141 on Windows; macOS (Apple silicon) a few versions later | Linux and Android later / behind a pref |
| Older / embedded webviews | mostly none | software fallback |
So a meaningful fraction of visitors will still get the software renderer; the fallback is a permanent path, not a stopgap.

**Secure context.** `navigator.gpu` exists only in secure contexts (https, `http://localhost`/`127.0.0.1`, `file:` is already unsupported by the player, docs/web-build.html:226 [V]). Effect on "any static host, any URL": the package still runs everywhere (software), but **plain-http hosting never gets WebGPU**. An iframe inherits secure-context status from its ancestors (an https game embedded in an http page is not a secure context). Whether a cross-origin iframe needs a Permissions-Policy allowance for WebGPU: I am not aware of one being enforced, but this must be checked; if one exists, embedding portals must add `allow=...` or the game falls back.

**Features and limits that matter here** (core defaults): `maxBindGroups` 4; `maxUniformBufferBindingSize` 64 KiB; `maxDynamicUniformBuffersPerPipelineLayout` 8; `minUniformBufferOffsetAlignment` 256 (fixed, unlike Vulkan's per-device value); 16 sampled textures and 16 samplers per stage; 16 vertex attributes; `maxTextureDimension2D` 8192; `bytesPerRow` of texture-buffer copies must be a multiple of 256. Formats: `r8unorm`, `rg8unorm`, `rgba8unorm`, `rgba8unorm-srgb`, `depth24plus`, `depth32float` exist; **no 3-channel format**; no mipmap generation; no polygon mode (wireframe), no geometry shaders, no texture swizzle in core; compute and storage buffers exist (not needed in v1). Our needs fit: 3 dynamic UBOs (PerDraw, Lighting, Material: `VulkanShaderInterface.hpp:20-27` [V]), 5 textures + 5 samplers in one group, 192-byte per-draw block, 752-byte lighting block (`:86-90` [V]). There is also a "compatibility" feature level for older GLES-class GPUs (shipping in Chrome around 2025-26); our shaders use nothing it lacks as far as I know, but v1 should request core and treat compatibility as a later reach option.

**Async device acquisition vs the single-threaded main loop.** `requestAdapter`/`requestDevice` return promises; there is no synchronous way to get a device. The player is single-threaded (`N2ENGINE_SINGLE_THREADED`, docs/web-build.html:148 [V]) and its `main` builds the renderer synchronously inside `Application::Init` -> `Window::InitWindow` (`WebPlayer.cpp:372-377`, `Window.cpp:66-91` [V]). Options: (a) **acquire in JS before `callMain`** and hand the device in (no wasm changes to the control flow; recommended); (b) acquire in C++ with callbacks and start `emscripten_set_main_loop` from the callback (works without ASYNCIFY, but splits `main` and `Application::Init`); (c) ASYNCIFY (large code-size cost, tens of percent [M]) or JSPI (not in every browser [M]). Frames already run from `emscripten_set_main_loop(Frame, 0, EM_TRUE)` paced by requestAnimationFrame (`WebPlayer.cpp:431` [V]); on the web the canvas's current texture is presented when the rAF callback returns, so `IRenderer::Present` maps to "nothing to do" in the browser (no `wgpuSurfacePresent` [M]).

**Device loss.** `device.lost` resolves on driver reset, GPU process crash, tab backgrounding on some mobiles, or `destroy()`. A lost device cannot be revived; a new adapter+device is needed (async again) and every GPU resource must be re-created. The engine already re-acquires resources when a renderer's lifetime token expires: `GpuCache::Acquire` drops entries whose owner lifetime differs and re-creates them (`engine/src/rendering/GpuCache.cpp:140-157` [V]); `MeshDrawing`, `ParticleSystem` and `TextDrawing` check `_rendererLifetime.expired()` (`MeshDrawing.cpp:46,97`, `ParticleSystem.cpp:400`, `TextDrawing.cpp:262` [V]). So "renderer calls `EndLifetime()` and comes back with a new device" is a recovery path the engine mostly supports; whether every holder re-uploads correctly is unverified.

**Canvas context exclusivity.** A canvas that has a `2d` context cannot later get `webgpu` and vice versa [M, spec]. The shell creates the 2D context lazily on the first frame (`web/shell.html` `present()`: `canvas.getContext('2d', {alpha:false})` [V]). So the choice must be made before the first frame, and a mid-game fallback to software needs a **fresh canvas element**.

## 3. The Emscripten route and the build
- **Bindings.** Two Emscripten options [M]: the old built-in `-sUSE_WEBGPU=1` (`library_webgpu.js`, an older `webgpu.h`, `Module.preinitializedWebGPUDevice` + `emscripten_webgpu_get_device()`), deprecated during the 4.0 series in favour of **emdawnwebgpu** (`--use-port=emdawnwebgpu`), maintained by the Dawn team, tracking the standard `webgpu.h` (webgpu-headers) that native Dawn implements. The pinned Emscripten is 4.0.10 (docs/web-build.html:107 [V]); whether 4.0.10 still accepts `USE_WEBGPU` and which Dawn revision its emdawnwebgpu port pins must be checked in G4. Recommend emdawnwebgpu (W6): the same header and C API as native Dawn, so one source file compiles for both the browser and the CI harness. Dawn or wgpu-native themselves are **not** compiled into the browser build: in the browser the port is a JS library calling `navigator.gpu`.
- **Handing in a JS device.** emdawnwebgpu exposes a way to import a JS `GPUDevice` into its handle table (I recall a `WebGPU.importJsDevice`-style helper [M]); if not, option (b) above. G5 must confirm.
- **Remote port download.** A `--use-port` port is fetched at build time (like the GLFW/OpenAL header downloads the web configure already does, docs/web-build.html:161 [V]); pinned by the Emscripten version. CI already needs network at configure.
- **CMake.** `cmake/N2EngineWeb.cmake` adds flags globally (`add_compile_options`/`add_link_options`, lines 15, 33-34, 54-70 [V]). Proposed: a cache option `N2ENGINE_RENDERER_WEBGPU` (web default ON from G4; native default OFF, ON only in the harness CI job), mirroring `N2ENGINE_RENDERER_VULKAN` (`renderer/CMakeLists.txt:20-23,105-106` [V], `RendererConfig.hpp` [V]); the renderer's `GLOB_RECURSE` picks up `src/webgpu/` and is filtered out when OFF, as Vulkan's is. The port flag goes on the renderer target (compile, for the header) and the player link (`web/CMakeLists.txt:47-54` [V]).
- **Size** (nothing measured; [E]): the WebGPU backend in C++ ~2-2.5k lines (Vulkan's three files are 4.1k lines, `wc` [V], but most of that is sync, allocation and descriptor-pool code WebGPU does not need) -> **+120-250 KB raw wasm in `size`, +30-70 KB brotli**; the emdawnwebgpu JS glue **+40-120 KB raw `index.js`, +10-25 KB brotli** (closure-minified smaller); WGSL source strings ~25 KB raw, ~6 KB brotli. Against the `size` budgets (`web/budgets.json`: wasm.raw 4,500,000, wasm.brotli 880,000, initial.brotli 935,000 [V]; measured 3,946,067 / 765,466 / 818,354, docs/web-build.html:381-385 [V]) that is +3-6 % wasm and +5-10 % initial brotli: it may eat most of the ~13 % headroom, so G4 re-baselines the budgets in the same PR as the docs require ("A stage that adds a feature ... is expected to raise the relevant budgets in the same pull request", docs/web-build.html:396 [V]). PR #184 (PhysX) also moves the budgets: order G4 after it.

## 4. Shaders and the backend design
### 4.1 Source of truth and translation
Today: OpenGL has GLSL 330 strings in `OpenGLRenderer.cpp` (vulkan-backend.md section 2, `OpenGlShaderSourceTests.cpp` exists [V]); Vulkan has GLSL 450 files `renderer/shaders/vulkan/{unlit,lit,text}.{vert,frag}` (523 lines [V]) compiled to SPIR-V at build time by glslangValidator/glslc and embedded (`renderer/CMakeLists.txt:120-214` [V]); `VulkanShaderParityTests.cpp` parses the GLSL as text against the C++ table (`VulkanShaderInterface.hpp:11-16` [V]). No reflection anywhere.

Options:
| Option | For | Against |
|---|---|---|
| A. Hand-written WGSL for the 3 built-ins + text parity test + CI validator (recommended, W1) | No build tool in the web job; readable WGSL; WGSL-specific fixes (matrices, inverse, separate samplers) written once by hand; same pattern as the Vulkan port (which was itself a hand port of GL's) | A third copy of each shader (GL 330, Vulkan 450, WGSL): drift risk, mitigated by the parity test and the cross-backend goldens |
| B. GLSL 450 -> SPIR-V (existing step) -> WGSL with Tint or naga at build time | One source for Vulkan and WebGPU | Needs Tint (part of Dawn) or naga-cli in every web build; the current GLSL hits known translator gaps [M]: `row_major` blocks, combined `sampler2D` (Tint's SPIR-V reader wants separate image/sampler), `inverse()` (GLSL.std.450 MatrixInverse), `OpKill`; the GLSL would have to be rewritten for the translator anyway |
| C. GLSL -> WGSL directly with naga's GLSL front end | No SPIR-V step | naga's GLSL front end is a subset [M]; Rust toolchain in CI |
| D. Runtime translation in the browser | Custom shaders later | Ships a compiler (MBs) into a size-budgeted wasm: no |
If custom user shaders become a feature (they are not in v1 for any backend), revisit B with WGSL as the authored language for web.

### 4.2 What the WGSL must do differently [V for the GLSL facts, M for WGSL rules]
- **Matrices.** The GLSL declares `layout(std140, row_major) uniform PerDraw` and copies the engine's row-major matrices as they are (`unlit.vert:13-19`, `lit.vert:11-15` [V]). WGSL matrices are column-major only, so the uploaded bytes read as the transpose. Either transpose on upload (3 x 64 bytes per draw, CPU) or write the WGSL with row-vector products (`v * M` order), which is exact and free; `lit.vert:28-37` also takes `mat3(uModel)`, `inverse`, `determinant` and a tangent transform, which must be written with the transposed reading in mind. Recommend transposing on upload: the WGSL then reads like the GLSL and the parity test stays simple.
- **`inverse()`** (`lit.vert:28` [V]) has no WGSL built-in: write a 3x3 adjugate/determinant helper (or pass a normal matrix per draw, which changes the shared block: not recommended).
- **Samplers.** Vulkan uses 5 COMBINED_IMAGE_SAMPLER bindings (`VulkanDraw.cpp:27-29` [V]); WebGPU binds textures and samplers separately: group 1 = binding 0 material UBO (dynamic), bindings 1-5 textures, 6-10 samplers (11 entries, within the per-stage limits). Bind groups are cached by (texture ids, sampler keys), as Vulkan caches material sets by the five views and samplers (`VulkanDraw.hpp:154-156` [V]).
- **Clip space and winding.** Keep the GL-convention z remap in the vertex shader (`z = (z + w) / 2`, `unlit.vert:26-27` [V]). WebGPU's NDC is y-up with framebuffer row 0 at the top, which is exactly what Vulkan gets from its negative-height viewport (`VulkanRenderer.cpp:1291-1298` [V]); WebGPU forbids negative viewports and does not need one [M]. Front faces: `frontFace: 'ccw'`, `cullMode` from `RenderState::cull` (GL's CCW front, `RenderState.hpp` comment [V]); the cull goldens confirm.
- **Depth/blend/state** map 1:1 from Vulkan's pipeline creation: depth compare `less` (`VulkanDraw.cpp:873` [V], GL `glDepthFunc(GL_LESS)` `OpenGLRenderer.cpp:91` [V]), depth write only while depth-testing, blend SRC_ALPHA/ONE_MINUS_SRC_ALPHA or SRC_ALPHA/ONE for colour and alpha (`VulkanDraw.cpp:14-17` [V]); pipelines cached by the same packed `PipelineKey` (`VulkanDraw.hpp:160-176` [V]); at most 3 x 2 x 2 x 3 x 3 = 108 variants, created lazily. Creating a render pipeline on first use stalls in browsers (shader compile) [M]; `createRenderPipelineAsync` or pre-warming the common states at Initialize is a G7-level optimisation.
- **Derivatives and uniformity.** `text.frag` uses `fwidth` and `lit.frag` samples after a `discard` and inside branches on uniform values (`text.frag:35-63`, `lit.frag:153-197` [V]). WGSL's uniformity analysis accepts derivatives/`textureSample` under conditions on uniform-buffer values, and `discard` is demote-to-helper so it does not break uniformity [M]; the CI validator (G1) is what proves it.
- **Colour space.** Same rule as Vulkan: UNORM colour target, lit shader encodes in-shader when lighting is linear (`VulkanLighting.hpp:19-22` [V]); sRGB textures use `rgba8unorm-srgb`, 3 channels expand to RGBA8 with alpha 255 (as `VulkanResources.cpp:590-607` [V]); a 1-channel texture samples (r,0,0,1) natively [M].

### 4.3 Reuse vs rewrite
| Vulkan piece [V] | WebGPU |
|---|---|
| `VulkanShaderInterface.hpp` (block tables, offsets, attributes; Vulkan-free) | **Reuse**: move to `renderer/include/renderer/common/GpuShaderInterface.hpp` (rename). std140 offsets are also valid WGSL uniform-buffer offsets for these blocks (vec3 align 16, struct strides 32/48/64 are multiples of 16) [M, the parity test checks] |
| `VulkanLighting.hpp` (752-byte block, pure) | **Reuse** as is (moved) |
| `VulkanMaterial` (name -> offset writes, snapshot at DrawMesh; no Vulkan types in its interface, `VulkanDraw.hpp:63-128`) | **Reuse** by lifting it to a shared `BlockMaterial` |
| Per-frame chained uniform ring, persistently mapped (`VulkanDraw.cpp:41-49`) | **Rewrite smaller**: a CPU staging vector per frame, one `queue.writeBuffer` before `queue.submit` at EndFrame; dynamic offsets aligned to 256 |
| Descriptor pools reset per frame slot, material sets by key | Bind groups cached by key (immutable, garbage-collected by WebGPU); the frame group per uniform buffer |
| VMA, fences, 2 frames in flight, retire-to-slot deletion (`VulkanResources.cpp:27-31`) | **Drop**: WebGPU orders queue work and defers destruction itself [M]. One hazard remains: `writeBuffer` executes at once on the queue timeline, before the frame's command buffer is submitted, so **`UpdateMesh` on a mesh already drawn in the current (unsubmitted) frame must write a new buffer** (or the earlier draw sees the new vertices). Rule: per mesh, "drawn this frame" flag -> allocate fresh, else write in place |
| Blit mipmaps (`VulkanResources.cpp:209+`) | No blit in WebGPU: generate mips on the CPU at upload (box filter, linear-space for sRGB) [recommended, simple and testable] or a render-pass downsampler |
| Staging uploads, image layout transitions | `queue.writeTexture` / `writeBuffer`; no layouts |
| Offscreen colour + depth, Present blits to swapchain (stage F) | **Same decision**: always render to an offscreen `rgba8unorm` + `depth24plus` target; Present = one full-screen-triangle pass into the canvas's current texture (format from `getPreferredCanvasFormat()`, often `bgra8unorm` [M], so a copy would not do; the pass also handles the swizzle), canvas `alphaMode: 'opaque'` (the software player forces alpha 255 for the same reason, `WebPlayer.cpp:243-247` [V]) |
| ReadFramebuffer: copy, wait fence, flip to bottom-first (`VulkanRenderer.cpp:1364-1431`) | Copy with 256-aligned `bytesPerRow`, `mapAsync`, flip. **Natively** (CI harness) the wait is `wgpuInstanceWaitAny`/process-events and is synchronous; **in the browser** it cannot block, so `ReadFramebuffer` returns the previous completed readback (or nothing) and the player never calls it on the WebGPU path (it presents to the canvas instead) |
| Wireframe (`VK_POLYGON_MODE_LINE`, `VulkanDraw.cpp:852`) | Not in core WebGPU: `SetWireframe` logs once and is ignored in v1 (W9) |
| GPU selection API | `powerPreference: 'high-performance'` only |

### 4.4 Engine-side changes
- `Config::ApplicationOptions::RenderBackend` has OPENGL, VULKAN, SOFTWARE (`engine/include/engine/config/ApplicationOptions.hpp:13-18` [V]); add `WEBGPU` (+ `RenderBackendName`, `Application.cpp:57-69` [V]).
- `Window::UsesNoWindow` is `isHeadless && SOFTWARE` (`Window.cpp:61-64` [V]); the windowless path constructs a `SoftwareRenderer` directly (`:74-91` [V]). Extend it to WEBGPU (no GLFW: the renderer takes `Initialize(nullptr, w, h)` and the canvas is attached through a WebGPU-specific call, e.g. the page's `#canvas` selector, mirroring Vulkan's headless `Initialize(nullptr)`).
- `WebPlayer.cpp` takes `--renderer software|webgpu` (argument parsing at `:340-364` [V]), and on WebGPU skips the read-back/flip/`n2Present` path (`PresentFrame`, `:231-249` [V]) in favour of `IRenderer::Present`. The 1280-pixel cap (`:81` [V]) exists for the software renderer's cost; WebGPU can honour devicePixelRatio up to a higher cap (W7).
- Text (SDF glyph atlas, R8 texture, `UpdateMesh` per change), UI (second `SetViewProjection` in the frame, handled by the per-draw ring), particles (CPU billboards, additive) and CPU soft bodies need nothing new beyond Vulkan's semantics.

## 5. Selection, fallback and the loader/shell
Decision procedure, in `n2-loader.js`, run in parallel with the downloads (so it costs no extra wall time), result shown in the page log:
1. URL override `?renderer=software|webgpu` wins (also the escape hatch for a user whose GPU misbehaves).
2. `window.isSecureContext && navigator.gpu` else software ("WebGPU unavailable: not a secure context" / "browser has no WebGPU").
3. `await navigator.gpu.requestAdapter({powerPreference: 'high-performance'})` with a timeout (a few seconds [E]); null/timeout/throw -> software.
4. `await adapter.requestDevice()` with default limits (we need none above them); throw -> software.
5. Success: keep the device, pass it to the module before `callMain(['--renderer', 'webgpu'])`; the canvas gets its `webgpu` context only then.
No step reloads the page. A failure before the first frame is silent apart from one log line, because the fallback is a working game.

**After start** (device lost or an uncaptured validation error storm): the renderer stops drawing, logs the reason, and tries **one** re-acquisition (async; frames skipped meanwhile; the engine re-uploads through the lifetime token, section 2). If that fails, the page shows "The graphics device was lost" with a button that reloads with `?renderer=software` (W5). No automatic reload, so no loop is possible; optionally a `sessionStorage` note (wrapped in try/catch: it throws in some sandboxed iframes [M]) makes the next load in the same tab start on software with a "try WebGPU again" link.

Loader/shell changes: `createGpuProbe()` in `n2-loader.js` (unit-tested under node with a mock `navigator.gpu`, like `scripts/web-loader-test.mjs` and `web-audio-unlock-test.mjs` today, docs/web-build.html:401 [V]); `shell.html` passes the renderer argument and keeps the 2D `present()` only for software; the package contract does not change (same files, no worker, no headers). The node package smoke (`scripts/web-package-smoke.mjs`) keeps running the software path (node has no `navigator.gpu`), so it also asserts that the fallback is taken.

Plus static checks in the existing web job: WGSL validated by `tint` (from the Dawn build, or a prebuilt) and, cheaply, by `naga-cli` [E: ~2-3 min `cargo install`, cacheable], so both Chrome's and Firefox's compilers accept the shaders; WebKit's WGSL compiler has no CI path (user check).

**Goldens and tolerances.** Today the Vulkan goldens are separate files mirroring the software ones (`tests/renderer/vulkan/`: 28 files incl. helpers, 9 of them `Vulkan*GoldenTests.cpp` [V `ls`]) plus `CrossBackendDiff.hpp` (strict mode: every pixel within 2/255 for unlit nearest; lit mode: mean <= 2/255, <= 1 % over 8/255, coverage-edge exclusion from flat unlit masks, bounded exclusion, `CrossBackendDiff.hpp:14-47` [V]) and `BlendReference.hpp`. Proposal: move `CrossBackendDiff.hpp`/`BlendReference.hpp` to `tests/renderer/common/`, and parameterise the GPU golden bodies by a renderer factory so Vulkan and WebGPU run the same scenes (the refactor vulkan-backend.md section 4.3 proposed but stages took as separate files). Comparisons: WebGPU vs Software with the same tolerances and the same per-backend expectations Vulkan has (blended, antialiased text); **WebGPU vs Vulkan** on blended/text scenes where Software differs by design, with the strict tolerance (both are GL-semantics GPU backends on the same lavapipe). Mipmapped textures: compare with mips off or against a CPU reference, because Vulkan blits and WebGPU generates on the CPU.

**What only the user's real browsers can check** (to go into docs/web-checklist.html): that WebGPU is picked in Chrome/Edge (Windows, macOS), Safari 26 (macOS, iOS), Firefox (Windows), Android Chrome, and that software is picked on http, on an iOS < 26 device and with `?renderer=software`; colours and orientation against the software render of the same scene (canvas format, sRGB look, alpha); resizing, HiDPI sharpness, fullscreen-size canvases; frame rate vs software on the same machine; first-frame hitch from pipeline compilation; device loss (Chrome `about:gpucrash`, GPU driver reset) and the fallback button; embedding in an https iframe on another origin; tab hide/show; memory growth over minutes; WebKit's WGSL compiler accepting the shaders.

## 8. Risks and open questions
- **Dawn in CI** is the biggest cost: build time, a large FetchContent dependency, and API churn between Dawn revisions; pinning it to emdawnwebgpu's revision ties it to the Emscripten pin (a pin bump becomes two bumps).
- **Lavapipe and SwiftShader hide real-GPU and real-browser issues** (formats, timing, Safari's and Firefox's implementations, mobile tilers); only the user's checklist covers them.
- **Three shader copies** (GL 330, Vulkan 450, WGSL): a fix in one must reach all; parity tests check interfaces, not maths; goldens check maths only for scenes they cover.
- **Readback asymmetry**: synchronous natively, asynchronous in the browser. Anything on the web that calls `ReadFramebuffer` expecting the current frame (none in the player today [V `WebPlayer.cpp`], screenshots later) needs an async API.
- **Device loss recovery** relies on every resource holder honouring the lifetime token; untested for a mid-scene renderer re-init.
- **Size budgets**: the estimate may be off by 2x; if the glue is large, the `size` profile's initial download grows noticeably for users who will get the software renderer anyway.
- **First-frame stalls** from lazy pipeline creation (up to 108 variants) on slower browsers.
- **Linux desktop and older iOS** users mostly get software for now; the WebGPU work helps Windows/macOS/new-iOS/Android-Chrome users first.
- Open: does the pinned Emscripten 4.0.10 have emdawnwebgpu, and how does it import a JS device? Does a cross-origin iframe need a Permissions-Policy for WebGPU? Should a "fallback adapter" (software WebGPU, e.g. SwiftShader in Chrome) be used or should we prefer our own software renderer? Does compatibility mode matter for the Android share?

## 9. Decisions for the user
- **W1 Shader source**: hand-write WGSL ports of the three built-in shaders, tied to the shared interface table by a parity test and validated by Tint (and naga) in CI, or translate the Vulkan GLSL to WGSL at build time with Tint/naga? *Recommend hand-written WGSL.*
- **W2 CI execution**: run the WebGPU goldens natively on Dawn over lavapipe in a new non-required Linux job, or use prebuilt wgpu-native, or only Chrome headless? *Recommend Dawn on lavapipe (pinned to emdawnwebgpu's Dawn), Chrome headless later as optional G6.*
- **W3 Artifacts**: one wasm containing both the software and WebGPU renderers chosen at load, or two separate packages? *Recommend one wasm.*
- **W4 Default**: use WebGPU automatically when the browser offers it (software otherwise, `?renderer=` override), or keep software as default with WebGPU opt-in? *Recommend automatic WebGPU with the override.*
- **W5 Device lost**: one silent re-acquire, then a "continue with the software renderer" button (no automatic reload), or an automatic reload once (guarded by sessionStorage)? *Recommend the button, no automatic reload.*
- **W6 Bindings and async**: emdawnwebgpu with the device acquired in the loader's JavaScript before `callMain` (no ASYNCIFY/JSPI), or the deprecated `-sUSE_WEBGPU` / an ASYNCIFY build? *Recommend emdawnwebgpu + JS-side acquisition.*
- **W7 Resolution**: on WebGPU follow devicePixelRatio up to a higher cap (e.g. 2560 pixels wide), or keep the software player's 1280 cap? *Recommend devicePixelRatio with a 2560 cap.*
- **W8 Native exposure**: build the WebGPU backend natively only for the CI harness (option OFF by default, not selectable in lua_project or the editor host), or make it a selectable native renderer? *Recommend CI-only natively.*
- **W9 v1 scope**: built-in shaders only, wireframe ignored with one warning, no compute, particles and soft bodies on the CPU paths, or include any of those? *Recommend that minimal scope.*
- **W10 Priority**: start G0-G3 now (no browser or GPU needed, independent of #184 and Vulkan stage F) or after the stage 5/6 web work? *Recommend G0-G2 now, G4 after #184 merges.*
